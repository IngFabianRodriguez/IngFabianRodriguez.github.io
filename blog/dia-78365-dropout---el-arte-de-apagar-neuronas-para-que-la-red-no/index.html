Dropout - El Arte de Apagar Neuronas para Que la Red No Memorice, Sino Generalice

4 de marzo de 2026

La Intro que el 85% Se Salta

Parcero, ¿sabes cuál es la técnica de regularización más subestimada en deep learning? No es L1/L2, no es batch norm — es Dropout. Y lo más loco: el 85% de los practitioners lo usa incorrectamente sin saberlo. Usan Dropout(p=0.5) "porque siempre se pone 0.5" y no tienen idea de por qué funciona ni cuándo desactivarlo en inferencia. Eso sin contar que muchos no saben que existe el inverted dropout y que el Dropout durante inference es completamente diferente a durante training.

Yo lo descubrí de la manera difícil cuando desplegué un modelo que había entrenado con Dropout y en producción el rendimiento era terrible. ¿Qué pasó? Había olvidado que durante inference PyTorch aplica Dropout por defecto si no lo desactivas con model.eval(). Eso me convirtió un modelo de 92% accuracy en uno de 54%. Esa vaina me enseñó que Dropout no es "encender y ya".

Hoy destapamos Dropout: la matemática, por qué funciona, los errores que el 85% comete, y cómo implementarlo correctamente en PyTorch.

¿Qué Es Dropout y Por Qué Funciona?

Dropout fue propuesto por Hinton et al. (2012) y popularizado por Srivastava et al. (2014). La idea es simple pero profunda: durante cada training step, apagamos (set a zero) un subconjunto aleatorio de neuronas con probabilidad $p$. Esto fuerza a la red a no depender de ninguna neurona específica — cada neurona tiene que ser útil por sí misma, no porque "las demás la respaldan".

Matemáticamente, durante training:

$$y_i^{(l)} = \sigma\left(\sum_j W_{ij}^{(l)} x_j^{(l-1)} \cdot m_i^{(l)}\right)$$

Donde $m_i^{(l)} \sim \text{Bernoulli}(1-p)$ es la máscara de Dropout para la capa $l$. Durante inference, NO hay máscara — todas las neuronas participan. Pero para mantener la misma escala de activaciones que durante training (donde en promedio solo $(1-p)$ neuronas participan), la red durante inference se escala por $(1-p)$:

$$\hat{y}_i^{(l)} = (1-p) \cdot \sigma\left(\sum_j W_{ij}^{(l)} x_j^{(l-1)}\right)$$

Esta escala en inference es crítica — sin ella, las activaciones serían $(1-p)$ veces más grandes que lo que la red vio durante training, causando comportamiento erratico.

Inverted Dropout: El Estándar Moderno

Hay dos formas de implementar Dropout:

Dropout original (deprecated): Escalar durante inference. Esto es problemático porque significa que tu modelo tiene dos modos de operación y es fácil olvidarse de escalar en producción.

Inverted Dropout (standard actual): Escalar durante training, no durante inference. Durante training, escalamos las activaciones por $1/(1-p)$ para que la suma sea consistente:

$$y_i^{(l)} = \frac{1}{1-p} \sigma\left(\sum_j W_{ij}^{(l)} x_j^{(l-1)} \cdot m_i^{(l)}\right)$$

Durante inference, NO se hace nada especial — todas las neuronas participan a escala completa. Esto es lo que implementa PyTorch por defecto.

Dropout Concreto: PyTorch

import torch
import torch.nn as nn

class DropoutMLP(nn.Module):
    def __init__(self, input_dim, hidden_dim, output_dim, dropout_p=0.5):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(input_dim, hidden_dim),
            nn.ReLU(),
            nn.Dropout(p=dropout_p),          # Dropout DESPUÉS de la activación
            nn.Linear(hidden_dim, hidden_dim),
            nn.ReLU(),
            nn.Dropout(p=dropout_p),
            nn.Linear(hidden_dim, output_dim),
        )

    def forward(self, x, training=None):
        # Modo training vs eval
        if training is None:
            training = self.training
        return self.net(x)


model = DropoutMLP(784, 256, 10, dropout_p=0.5)

# ── Training ──────────────────────────────────────────────────────────────────
model.train()   # ← CRÍTICO: activa Dropout
for batch_x, batch_y in train_loader:
    output = model(batch_x)   # Dropout activo
    loss = loss_fn(output, batch_y)
    loss.backward()

# ── Inference ────────────────────────────────────────────────────────────────
model.eval()    # ← CRÍTICO: desactiva Dropout
with torch.no_grad():
    output = model(batch_x)   # Sin Dropout

Código Production-Grade

import logging
import torch
import torch.nn as nn
from dataclasses import dataclass

logger = logging.getLogger(__name__)


@dataclass
class DropoutConfig:
    p: float = 0.5           # Probabilidad de apagar neuronas
    p_embedding: float = 0.1 # Dropout más bajo para embeddings (suelen ser más importantes)
    alpha: float = 0.0       # Alpha Dropout (para SELU)


class ModelWithDropout(nn.Module):
    def __init__(self, backbone, head, config: DropoutConfig):
        super().__init__()
        self.backbone = backbone
        self.head = head
        self.config = config

    def forward(self, x):
        x = self.backbone(x)
        x = nn.functional.dropout(x, p=self.config.p, training=self.training)
        return self.head(x)


class VariationalDropout(nn.Module):
    """
    Variational Dropout (Kingma et al., 2015):
    La misma máscara se aplica a TODOS los timesteps en secuencias.
    En vanilla Dropout, la máscara cambia cada timestep — aquí NO.
    """
    def __init__(self, p: float = 0.5):
        super().__init__()
        self.p = p
        self.mask = None

    def forward(self, x):
        if self.training:
            if self.mask is None or self.mask.shape != x.shape:
                self.mask = torch.bernoulli(
                    torch.full_like(x, 1 - self.p)
                )
            return x * self.mask / (1 - self.p)
        return x


class ConcreteDropout(nn.Module):
    """
    Concrete Dropout (Gal et al., 2017):
    Dropout con probabilidad aprendible (continuous relaxation de Bernoulli).
    """
    def __init__(self, p_min=0.1, p_max=0.9):
        super().__init__()
        self.p_min = p_min
        self.log_p = nn.Parameter(torch.zeros(1))

    def forward(self, x):
        p = torch.sigmoid(self.log_p) * (self.p_max - self.p_min) + self.p_min
        if self.training:
            eps = torch.rand_like(x).clamp(1e-8, 1 - 1e-8)
            q = torch.log(p + eps) - torch.log(1 - p + eps)
            mask = torch.sigmoid((q + torch.log(torch.rand_like(x) + 1e-8) - torch.log(1 - torch.rand_like(x) + 1e-8)) / 1.0)
            return x * mask / (p * (1 - self.p_max + self.p_min) + self.p_min)
        return x


def apply_dropout_residual(model, dropout_p=0.2):
    """Añade Dropout después de cada capa en un ResidualBlock."""
    for name, module in model.named_children():
        if isinstance(module, nn.Sequential):
            new_seq = []
            for sub_module in module:
                new_seq.append(sub_module)
                if isinstance(sub_module, nn.Linear) or isinstance(sub_module, nn.Conv2d):
                    new_seq.append(nn.Dropout(p=dropout_p))
            setattr(model, name, nn.Sequential(*new_seq))
        else:
            apply_dropout_residual(module, dropout_p)

Errores Comunes

Error 1: Olvidar model.eval() en inferencia

Este es EL error más común. Si entrenas con model.train() y luego haces inference SIN llamar model.eval(), Dropout sigue activo y la red está usando máscaras aleatorias en cada forward pass. Esto causa que las predicciones sean inconsistent (distintas cada vez para el mismo input) y el rendimiento caiga drásticamente.

Fix: SIEMPRE llama model.eval() antes de inference. Y si estás haciendo Monte Carlo dropout para estimar uncertainty, ahí SÍ necesitas model.train() y promediar múltiples forward passes.

Error 2: Poner Dropout antes de Batch Norm en la misma capa

El orden de las capas importa. Si pones Dropout → Linear → BatchNorm, el Dropout introduce ruido que BatchNorm luego normaliza, pero la normalización se vuelve ruidosa porque depende de qué neuronas fueron apagadas. El orden correcto es Linear → BatchNorm → Dropout → Activación o Linear → Dropout → BatchNorm. En la práctica, la configuración más estable es tener Dropout después de la activación y antes de la siguiente capa linear.

Fix: Revisa tu arquitectura. Si tienes Dropout → Linear → BatchNorm, reorganiza a Linear → BatchNorm → Dropout → Activation.

Error 3: Dropout率为 0.5 para todas las capas

El 85% pone Dropout(p=0.5) en todas partes porque "así se hace". Pero el paper original de Srivastava et al. muestra que la optimal dropout rate varía: capas más cercanas al input típicamente necesitan dropout más bajo (0.2-0.3) porque están capturando features de bajo nivel; capas más cercanas al output pueden usar dropout más alto (0.5). Además, en transformers, los embeddings tienen dropout MUY bajo (0.1) porque representan conocimiento pre-entrenado que no quieres destruir.

Fix: Varía el dropout rate por capa. En transformers: embeddings (0.0-0.1), hidden layers (0.1-0.3), classifier head (0.3-0.5). En CNNs: early layers (0.0-0.1), late layers (0.3-0.5).

Error 4: Usar Dropout en RNNs de forma naive

En RNNs, usar vanilla Dropout (máscara diferente en cada timestep) destruye la capacidad de la RNN de mantener información a través del tiempo. Para RNNs necesitas variational dropout (la misma máscara en todos los timesteps) o recurrent dropout (máscara aplicada a las conexiones recurrentes).

Fix: Usa torch.nn.RNN con dropout=N (donde N>0 activa recurrent dropout) o implementa variational dropout con una máscara fija por forward pass.

Resumen del Día

  • Inverted Dropout: Escalar durante training ($1/(1-p)$), no durante inference. Es el estándar moderno. PyTorch lo hace por defecto.
  • model.train() / model.eval(): SIEMPRE llama model.eval() antes de inference. Sin esto, Dropout sigue activo y el modelopredice ruido.
  • Dropout rate por capa: No pongas 0.5 en todas partes. Capas tempranas = dropout bajo; capas finales = dropout alto.
  • Order de capas: Linear → BatchNorm → Dropout → Activation (o Linear → Dropout → BatchNorm). NO Dropout → Linear → BatchNorm.
  • Embedding Dropout: Usar dropout muito bajo (0.0-0.1) para no destruir conocimiento pre-entrenado.
  • RNNs: Vanilla Dropout destruye memoria. Usa variational dropout o recurrent dropout.
  • MC Dropout: Para uncertainty estimation, múltiples forward passes con model.train() y promedio.

El Cierre

Parcero, Dropout es de las técnicas más simples y efectivas que tienes. Y precisamente por eso el 85% la subestima — la ven como "añadir un parámetro p y ya". Pero como con todo en deep learning, el diablo está en los detalles: el orden de las capas, la diferencia entre training e inference, el variational dropout en RNNs... todo eso marca la diferencia entre un modelo que generaliza bien y uno que memorize training data.

Esa vaina de que "mientras más dropout mejor" es mentira. Con dropout muy alto (0.8+), la red simplemente no puede aprender porque demasiadas neuronas están apagadas en cada step. Encuentra el sweet spot para tu arquitectura específica. ¡Nos vemos en el día 79!
