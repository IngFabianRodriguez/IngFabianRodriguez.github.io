Dia 222/365: gRPC — El acueducto del edificio para tu inferencia de ML

10 de agosto de 2026
grpcio

Introduccion: Cuando el JSON te esta robando latencia

Tenias el modelo listo. El forward pass corria en 12 ms en la A10. La API REST en FastAPI respondia en promedio 80 ms. Algo no cuadraba. Abri el profiler y resultaba que el serializador JSON se comia 38 ms — mas que la inferencia misma. Si tu payload es un embedding de 768 floats, JSON lo infla de 6 KB a 9.5 KB y encima lo parsea string por string. Cuando eso pasa en produccion con 200 RPS, no hay servidor que aguante. Eso es lo que duele.

gRPC existe para ese dolor especifico. Protocol Buffers serializa binario, HTTP/2 multiplexa streams sobre una sola conexion TCP, y todo el contrato es tipado en un .proto. Para servicios de ML que reciben y devuelven tensores, embeddings o lotes de predicciones, el ahorro no es cosmetico: es la diferencia entre pagar una instancia extra de GPU o no pagarla.

En este articulo voy a desmontar gRPC desde el cable hasta el stub, con la matematica del framing HTTP/2 y la codificacion protobuf, y te voy a dejar una implementacion production-ready para un gateway de inferencia con streaming bidireccional.

1. Que es gRPC? (Y por que deberia importarte)

1.1 La analogia cotidiana

Imagina el sistema de acueducto de un edificio de apartamentos en Bogota. Un solo tubo vertical sube desde la red municipal hasta la azotea — esa es tu conexion TCP. Del tubo vertical se derivan las tuberias horizontales que entran a cada apartamento, y cada apartamento tiene su contador individual. Cuando el tubo principal se rompe, todo el edificio se queda sin agua. Pero mientras ese tubo este sano, los 40 apartamentos consumen agua en paralelo, identificados por su contador, y cada uno paga segun su consumo.

gRPC funciona exactamente asi. La conexion TCP es el tubo vertical. HTTP/2 introduce el concepto de stream, que es cada apartamento: multiples streams logicos viajando simultaneamente sobre la misma conexion fisica, cada uno identificado por un stream ID de 31 bits. Si la conexion TCP se cae, se cae todo. Pero mientras este viva, los streams viven en paralelo sin bloquearse entre si, y cada uno lleva su propio control de flujo (el contador del apartamento).

Lo que REST/JSON/HTTP/1.1 no te da: cada request abre (o reutiliza) su propia conexion TCP por el modelo keep-alive limitado, el body se serializa a texto UTF-8, y los headers se envian completos cada vez. gRPC resuelve los tres problemas a la vez: una sola conexion, binario, headers comprimidos con HPACK.

1.2 La matematica formal

gRPC se sostiene sobre tres componentes ortogonales: IDL (Protocol Buffers), transporte (HTTP/2) y codigo generado (stubs en Python, Go, Java, etc).

Wire format de Protocol Buffers. Cada campo en un mensaje se serializa como un par (tag, value). El tag codifica el numero de campo y el tipo de dato:

$$tag = (field\_number \ll 3) \mid wire\_type$$

donde field_number es el identificador del campo en el .proto y $wire\_type \in \{0, 1, 2, 5\}$ (0 = varint, 1 = 64-bit, 2 = length-delimited, 5 = 32-bit). Los 3 bits bajos del tag codifican el wire type; los 29 bits altos, el field number. El limite teorico de campos por mensaje es $2^{29} - 1 \approx 5.37 \times 10^{8}$, практиicamente innecesario.

Varint encoding. Enteros sin signo se serializan en base 128 con prefijo de continuacion. Cada byte贡献a 7 bits utiles; el MSB (bit 7) indica si hay mas bytes por venir:

$$byte_i = (value \bmod 128) \lor 128 \quad \text{si quedan mas bits}$$ $$byte_n = value \bmod 128 \quad \text{si es el ultimo}$$

Un varint de un solo byte codifica hasta $2^7 - 1 = 127$. Para signed integers se aplica ZigZag antes del varint:

$$encoded = (n \ll 1) \oplus (n \gg 31)$$

Esta transformacion mapea $-1 \to 1$, $0 \to 0$, $1 \to 2$, $-2 \to 3$, etc. La gracia es que numeros pequenos en valor absoluto (incluyendo negativos) quedan en bytes bajos del varint, optimizando el tamano. Sin ZigZag, el signed $-1$ consumiria 10 bytes en complemento a dos.

Multiplexing HTTP/2. Sobre una conexion TCP unica, cada stream se identifica por un stream ID de 31 bits. El cliente usa IDs impares ($1, 3, 5, \dots$) y el servidor pares ($2, 4, 6, \dots$), evitando colisiones. El control de flujo por stream usa una ventana deslizante:

$$W_{i+1} = W_i - data\_enviado + \Delta_{incremento}$$

Cuando $W_i$ llega a cero, el emisor pausa hasta que el receptor envie un frame WINDOW_UPDATE con un $\Delta > 0$. Esto es backpressure real, no el polling de HTTP/1.1 donde el socket simplemente bloquea sin semantica de aplicacion.

HPACK. Headers HTTP/2 se comprimen con una tabla estatica de 61 headers comunes (:method, :path, :scheme, etc.) mas una tabla dinamica por conexion. El receptor reconstruye el header completo desde un indice de 1 byte. Para servicios de ML que mandan metadata de modelo en cada request, esto ahorra bytes significativos — un header de 200 bytes puede comprimirse a 8 bytes tras miles de requests.

2. Como grpcio resuelve esto por vos

grpcio es el binding oficial en Python del core de gRPC escrito en C (la misma base que usan Go y Java). El flujo de uso es:

  1. Defines el contrato en un archivo .proto usando la IDL de Protocol Buffers.
  2. Ejecutas grpc_tools.protoc que genera: _pb2.py (mensajes), _pb2_grpc.py (stubs cliente y servidor).
  3. Importas los stubs en tu servidor y cliente. Los stubs ya traen tipos fuertes, serializacion binaria y manejo de HTTP/2 incluidos.

Lo que grpcio te resuelve sin que lo notes:

  • Threading del servidor: usa un ThreadPoolExecutor configurable; cada RPC entrante se asigna a un thread.
  • HTTP/2 framing y HPACK: implementados en C, sin que Python los vea.
  • Backpressure y flow control: automaticos, exponiendo deadlines (context.set_deadline) y timeouts.
  • Streaming nativo: cuatro modos (unary, server-streaming, client-streaming, bidi) sobre el mismo API.

Donde tienes que meter mano tu:

  • Load balancing del lado cliente (gRPC solo resuelve DNS+round-robin por defecto; para L7 necesitas grpc-channelz o un sidecar).
  • TLS en produccion (canal insecure por defecto — error clasico).
  • Retry policy y hedging (configurables via service config JSON, no por Python API directa).
  • Backpressure en el cuerpo del handler (si recibes un stream client-streaming y no lo drena rapido, la ventana se cierra y el cliente se bloquea).

3.2 Servidor minimo

import grpc
from concurrent import futures
import inference_pb2
import inference_pb2_grpc
import numpy as np


class InferenceServicer(inference_pb2_grpc.InferenceServiceServicer):
    def Predict(self, request, context):
        x = np.asarray(request.input, dtype=np.float32)
        logits = (x * x).tolist()  # simulacion de forward pass
        idx_sorted = np.argsort(logits)[::-1][:request.top_k].tolist()
        return inference_pb2.PredictResponse(
            logits=logits,
            top_k_indices=idx_sorted,
            latency_ms=1.2,
            model_version="v1.0.0",
        )

    def StreamTokens(self, request, context):
        for i in range(8):
            yield inference_pb2.TokenChunk(
                token_id=i,
                token_text=f"tok{i}",
                is_last=(i == 7),
            )


def serve(port: int = 50051, max_workers: int = 10):
    server = grpc.server(
        futures.ThreadPoolExecutor(max_workers=max_workers),
        options=[
            ("grpc.so_reuseport", 1),
            ("grpc.keepalive_time_ms", 30_000),
            ("grpc.http2.max_pings_without_data", 0),
        ],
    )
    inference_pb2_grpc.add_InferenceServiceServicer_to_server(
        InferenceServicer(), server
    )
    server.add_insecure_port(f"[::]:{port}")
    server.start()
    server.wait_for_termination()


if __name__ == "__main__":
    serve()

4. Implementacion Production-Ready: ML Inference Gateway

4.1 Tipos y protocolos

// inference_v2.proto
syntax = "proto3";

package inference.v2;

import "google/protobuf/timestamp.proto";

service InferenceGateway {
  rpc Predict (PredictRequest) returns (PredictResponse);
  rpc StreamCompletions (CompletionRequest) returns (stream CompletionChunk);
  rpc PredictStream (stream PredictRequest) returns (stream PredictResponse);
}

message PredictRequest {
  string model_name = 1;
  bytes tensor_payload = 2;
  string tensor_dtype = 3;
  repeated int32 tensor_shape = 4;
  map<string, string> tags = 5;
  google.protobuf.Timestamp deadline = 6;
}

message PredictResponse {
  bytes tensor_payload = 1;
  string model_version = 2;
  int64 latency_us = 3;
  string trace_id = 4;
}

message CompletionRequest {
  string prompt = 1;
  int32 max_tokens = 2;
  float temperature = 3;
}

message CompletionChunk {
  int32 token_id = 1;
  string text = 2;
  bool is_last = 3;
}

Serializar el tensor como bytes (en lugar de repeated float) reduce el tamano a la mitad y esquiva el overhead del wire format por cada elemento.

4.2 El motor principal

Servidor con deadline enforcement, streaming y opciones de HTTP/2 afinadas:

import grpc
from concurrent import futures
import time
import numpy as np
import inference_v2_pb2 as pb
import inference_v2_pb2_grpc as pb_grpc


class InferenceGateway(pb_grpc.InferenceGatewayServicer):
    def __init__(self, models: dict):
        self._models = models  # {name: callable(np.ndarray) -> np.ndarray}

    def Predict(self, request, context):
        if request.HasField("deadline"):
            remaining = request.deadline.seconds - time.time()
            context.set_deadline(max(0.1, remaining))

        model = self._models.get(request.model_name)
        if model is None:
            context.abort(grpc.StatusCode.NOT_FOUND, f"unknown model {request.model_name}")

        x = np.frombuffer(request.tensor_payload, dtype=request.tensor_dtype).reshape(request.tensor_shape)
        t0 = time.perf_counter()
        y = model(x)
        dt_us = int((time.perf_counter() - t0) * 1e6)

        return pb.PredictResponse(
            tensor_payload=y.tobytes(),
            model_version="v2.0.0",
            latency_us=dt_us,
            trace_id=request.tags.get("trace_id", ""),
        )

    def StreamCompletions(self, request, context):
        for tok in range(request.max_tokens):
            if context.cancelled():
                return
            yield pb.CompletionChunk(
                token_id=tok,
                text=f"t{tok}",
                is_last=(tok == request.max_tokens - 1),
            )

    def PredictStream(self, request_iterator, context):
        batch_x, batch_req = [], []
        for req in request_iterator:
            x = np.frombuffer(req.tensor_payload, dtype=req.tensor_dtype).reshape(req.tensor_shape)
            batch_x.append(x)
            batch_req.append(req)
            if len(batch_x) >= 32:
                yield from self._flush_batch(batch_x, batch_req)
                batch_x, batch_req = [], []
        if batch_x:
            yield from self._flush_batch(batch_x, batch_req)

    def _flush_batch(self, xs, reqs):
        big = np.concatenate(xs, axis=0)
        ys = self._models["default"](big)
        assert ys.shape[0] == len(reqs), "batch shape mismatch"
        for i, req in enumerate(reqs):
            yield pb.PredictResponse(
                tensor_payload=ys[i].tobytes(),
                model_version="v2.0.0",
                latency_us=0,
                trace_id=req.tags.get("trace_id", ""),
            )


def build_server(models: dict, port: int = 50052) -> grpc.Server:
    server = grpc.server(
        futures.ThreadPoolExecutor(max_workers=32),
        options=[
            ("grpc.max_receive_message_length", 64 * 1024 * 1024),
            ("grpc.max_send_message_length", 64 * 1024 * 1024),
            ("grpc.keepalive_time_ms", 15_000),
            ("grpc.keepalive_timeout_ms", 5_000),
            ("grpc.keepalive_permit_without_calls", 1),
            ("grpc.http2.max_pings_without_data", 0),
            ("grpc.so_reuseport", 1),
        ],
    )
    pb_grpc.add_InferenceGatewayServicer_to_server(InferenceGateway(models), server)
    server.add_insecure_port(f"[::]:{port}")
    return server

4.3 Utilidades de analisis y verificacion

import grpc
import inference_v2_pb2 as pb
import inference_v2_pb2_grpc as pb_grpc
import numpy as np


class InferenceClient:
    """Cliente con deadline, retries via metadata y verificacion numerica."""

    def __init__(self, target: str, deadline_s: float = 5.0):
        self._channel = grpc.insecure_channel(
            target,
            options=[
                ("grpc.enable_channelz", 1),
                ("grpc.keepalive_time_ms", 30_000),
            ],
        )
        self._stub = pb_grpc.InferenceGatewayStub(self._channel)
        self._deadline_s = deadline_s

    def predict(self, x: np.ndarray, model: str = "default") -> np.ndarray:
        req = pb.PredictRequest(
            model_name=model,
            tensor_payload=x.tobytes(),
            tensor_dtype=str(x.dtype),
            tensor_shape=list(x.shape),
        )
        try:
            resp = self._stub.Predict(req, timeout=self._deadline_s)
        except grpc.RpcError as e:
            raise RuntimeError(f"rpc failed code={e.code()} detail={e.details()}") from e
        return np.frombuffer(resp.tensor_payload, dtype=x.dtype).reshape(x.shape)

    def stream_completions(self, prompt: str, max_tokens: int = 16):
        req = pb.CompletionRequest(prompt=prompt, max_tokens=max_tokens, temperature=0.7)
        for chunk in self._stub.StreamCompletions(req, timeout=self._deadline_s):
            yield chunk.text
            if chunk.is_last:
                break

    def close(self):
        self._channel.close()


def numerical_check(client: InferenceClient, x: np.ndarray, expected: np.ndarray, atol: float = 1e-5):
    """Verificacion numerica: si el delta supera umbral, falla."""
    y = client.predict(x)
    err = float(np.abs(y - expected).max())
    assert err < atol, f"max abs error {err} excede umbral {atol}"
    print(f"verificacion ok, max abs err = {err:.2e}")

5. Ejemplos de Uso en Casos Reales

5.1 Endpoint de embedding 768-dim

Mismo escenario del dolor inicial:

client = InferenceClient("inference.internal:50052")

# 200 RPS, embedding de 768 floats
x = np.random.randn(768).astype(np.float32)
expected = x / np.linalg.norm(x)

# bajo REST/JSON un embedding de 768 floats serializa ~9-12 KB.
# bajo gRPC con tensor_payload en bytes: 768 * 4 = 3072 bytes exactos.
raw_bytes = x.nbytes
print(f"grpc raw payload = {raw_bytes} B (768 * 4)")

y = client.predict(x)
assert y.shape == (768,)
client.close()

Comparacion numerica (comentario): con payload util de 3072 bytes, JSON serializa aproximadamente 9-12 KB por la estructura {"input": [0.1, 0.2, ...]} repetida con overhead de comillas, separadores y comillas. gRPC con bytes tensor_payload envia los 3072 bytes exactos mas 4-8 bytes de overhead protobuf. Ratio esperado: 3.0x-3.9x. En una conexion de 1 Gbps con 200 RPS, eso es la diferencia entre saturar a 1.6 Gbps o correr holgado a 0.5 Gbps.

5.2 Streaming de tokens LLM

client = InferenceClient("llm.internal:50052")
t0 = time.perf_counter()
first_token_at = None
for txt in client.stream_completions("Explica dropout en una linea.", max_tokens=32):
    if first_token_at is None:
        first_token_at = time.perf_counter() - t0
    print(txt, end="", flush=True)
print(f"\nTTFT={first_token_at*1000:.1f} ms")

El handler StreamCompletions respeta context.cancelled() para cortar emision cuando el cliente aborta — eso es backpressure real, no polling. Si el cliente cierra la conexion a los 100 ms, el servidor deja de emitir sin esperar al proximo yield.

5.3 Pipeline de pre-procesamiento en lotes

El metodo PredictStream de la seccion 4.2 acepta un flujo client-streaming de requests y los agrupa en batches de 32 antes de invocar el modelo. Verificacion numerica: si xs[0].shape == (768,), xs[1].shape == (768,), ..., entonces big.shape == (N, 768) despues de np.concatenate, y ys.shape == (N, 768) despues del forward pass. El assert ys.shape[0] == len(reqs) en _flush_batch rompe el stream si el modelo devuelve una dimensionalidad distinta a la esperada.

client = InferenceClient("batch.internal:50052")

def gen():
    for i in range(100):
        x = np.random.randn(768).astype(np.float32)
        req = pb.PredictRequest(
            model_name="default",
            tensor_payload=x.tobytes(),
            tensor_dtype="float32",
            tensor_shape=[768],
        )
        yield req

# Nota: este metodo retorna un stream de respuestas, no es unary
for resp in client._stub.PredictStream(gen(), timeout=10.0):
    print(f"trace_id={resp.trace_id} bytes={len(resp.tensor_payload)}")

6. Debugging: Cuando Todo se Va a la Mierda

6.1 "Connection reset by peer" intermitente

Sintoma: bajo carga, una fraccion de requests falla con grpc.StatusCode.UNAVAILABLE o RESET_STREAM. El servidor reporta GOAWAY en logs.

Causa tipica: el servidor cierra la conexion TCP por exceder el limite de streams concurrentes (grpc.max_concurrent_streams, default 100), o por keepalive_timeout_ms muy corto cuando el cliente NAT-ea IPs y la conexion queda zombie.

Deteccion numerica: en los interceptores, loguear context.peer() y comparar con el set de clientes activos. Si GOAWAY llega, el cliente debe reintentar en una conexion nueva — no en la misma. Un patron simple: contar GOAWAYs en una ventana de 60s y alertar si supera 1% del trafico.

Soluciones:

  1. Subir grpc.max_concurrent_streams en el server a un valor realista: $max\_concurrent = max\_workers \times avg\_rpc\_duration\_s / target\_latency\_s$. Con 32 workers, duracion promedio de 50 ms y target de 100 ms en cola, max_concurrent >= 16.
  2. Ajustar grpc.keepalive_time_ms y grpc.keepalive_timeout_ms en cliente y servidor a valores coherentes (recomendado: cliente 30 s, servidor timeout 10 s).
  3. Habilitar retry en el cliente via service config JSON:
   {
     "methodConfig": [{
       "name": [{"service": "inference.v2.InferenceGateway"}],
       "retryPolicy": {
         "maxAttempts": 4,
         "initialBackoff": "0.1s",
         "maxBackoff": "1s",
         "backoffMultiplier": 2,
         "retryableStatusCodes": ["UNAVAILABLE", "DEADLINE_EXCEEDED"]
       }
     }]
   }
   # cargar la config al crear el canal
   with open("service_config.json") as f:
       options = [("grpc.service_config", f.read())]
   channel = grpc.insecure_channel(target, options=options)

6.2 Memory leak por canales no cerrados

Sintoma: el RSS del proceso cliente crece linealmente con el tiempo, sin que las requests fallen.

Causa: cada grpc.insecure_channel(...) abre una conexion HTTP/2 y registra timers en el reactor de C. Sin channel.close(), los timers y el socket quedan vivos hasta que el GC de Python libere el objeto, y el GC puede tardar minutos bajo baja presion.

Deteccion numerica: exp grpc_client_channel_open vs close en Prometheus y grafica la diferencia. Si diverge monotonicamente, tienes el leak. En grpcio >= 1.60, grpc_channelz te da visibilidad por canal.

Solucion: usa el context manager siempre que puedas:

with grpc.insecure_channel(target) as ch:
    stub = pb_grpc.InferenceGatewayStub(ch)
    # ... trabajo ...
# el __exit__ llama a channel.close()

Si necesitas canales de larga vida (e.g. un daemon que recibe trafico continuo), llama channel.close() explicitamente en el shutdown handler con atexit o senales SIGTERM. En asyncio, grpc.aio.insecure_channel requiere await channel.close() antes de cerrar el loop.

6.3 Drift silencioso por campos deprecados

Sintoma: dos servicios que "deberian" hablar el mismo .proto se serializan correctamente pero los valores llegan vacios o desplazados.

Causa: cuando renombras o cambias el tipo de un campo sin actualizar todos los deploys, protobuf es backward-compatible por tag number, pero los clientes viejos siguen mandando el numero viejo y los nuevos interpretan otra cosa. Es el clasico bug donde renombras model_name a model_id y el servicio nuevo trata el string como un entero.

Deteccion numerica: implementa una verificacion de schema en CI que diff los .proto entre servicios y rompe el build si se renumera un tag o cambia un tipo. En runtime, instrumenta un interceptor que loguea el descriptor del mensaje y lo compara contra el esperado:

def validate_proto_compatibility(client_proto_module, server_proto_module, msg_name: str):
    server_msg = getattr(server_proto_module, msg_name)
    client_msg = getattr(client_proto_module, msg_name)
    server_tags = {f.number: f.type for f in server_msg.DESCRIPTOR.fields}
    client_tags = {f.number: f.type for f in client_msg.DESCRIPTOR.fields}
    missing = set(server_tags) - set(client_tags)
    assert not missing, f"cliente no conoce tags {missing} del servidor"
    for tag, srv_type in server_tags.items():
        if tag in client_tags and client_tags[tag] != srv_type:
            raise RuntimeError(f"tag {tag} tipo difiere: srv={srv_type} cli={client_tags[tag]}")

7. Optimizaciones de Produccion

7.1 HTTP/2 keepalive vs costo de red

Trade-off: keepalive_time_ms bajo (15 s) detecta conexiones muertas rapido y permite que el cliente haga failover, pero cuesta paquetes periodicos. En un movil consumiendo una API de ML, esos paquetes drenan bateria y datos del usuario.

Recomendacion: 30 s para backend interno, 60-120 s para cliente movil, y keepalive_permit_without_calls=0 en movil para que el keepalive solo se envie cuando hay streams activos. La asimetria cliente/servidor debe respetar que el servidor puede cerrar mas agresivamente que el cliente reabre.

7.2 Compression gzip vs deflate vs snappy

gRPC soporta tres algoritmos via metadata grpc-encoding: gzip, deflate y snappy. Trade-off:

Algoritmo Ratio tipico CPU Latencia adicional
identity (off) 1.0x 0 0 ms
gzip 2.5-3.5x alto 1-3 ms
deflate 2.3-3.2x medio-alto 0.8-2.5 ms
snappy 1.8-2.5x bajo 0.2-0.5 ms

Para embeddings float32 (baja entropia en escala logistica), gzip gana en ratio. Para tokens LLM (texto UTF-8 redundante), deflate o gzip estan bien. Para latencia < 5 ms end-to-end, snappy es el rey. Se configura por llamada via metadata:

resp = stub.Predict(req, timeout=2.0, metadata=(("grpc-encoding", "gzip"),))

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

  • gRPC + protobuf reemplaza JSON + REST cuando el tamano del payload y la latencia de serializacion dominan el costo total de la request — caso clasico en inferencia de embeddings y tensores.
  • HTTP/2 multiplexing elimina el head-of-line blocking y te permite cientos de streams concurrentes sobre una sola conexion TCP, lo cual reduce el tiempo de establishment de TLS y el consumo de file descriptors del servidor.
  • Streaming nativo (cuatro modos) habilita casos como TTFT bajo en LLMs y backpressure real en pipelines de pre-procesamiento en lote.
  • Stack tipado via .proto mata clases enteras de bugs en tiempo de compilacion del stub, no en produccion a las 3 AM.

Mini-checklist antes de meter gRPC en prod:

  • [ ] TLS habilitado (grpc.ssl_channel_credentials() para cliente, add_secure_port para servidor; nada de insecure_* en prod)
  • [ ] max_receive_message_length y max_send_message_length ajustados a tu payload mas grande (default 4 MB es chico para tensores)
  • [ ] Deadlines propagados desde el cliente hasta el handler del servidor
  • [ ] Retry policy configurada via service config JSON
  • [ ] grpc.enable_channelz habilitado para observabilidad de streams activos
  • [ ] grpc.so_reuseport=1 en el servidor para reuso de puerto bajo multiples workers
  • [ ] Verificacion numerica automatizada en CI con .proto como fuente de verdad

Si llegaste hasta aca y tu servicio de inferencia sigue sobre REST/JSON, ya sabes donde esta el overhead. No es el modelo, es el cable. Hagale pues al .proto antes de que el siguiente ticket de latencia te busque a las 2 AM.

Pilas con esto cuando lo lleves a produccion, parce — ese primer deploy siempre destapa algo.
