LLM Privacy-Preserving: La Realidad Que El 90% Ignora

Pues resulta que hoy 17 de noviembre de 2026, Día 321, y muchos developers en Colombia y el mundo están mandando datos sensibles a LLMs como si fuera gratis. Que si historiales médicos, que si números de cédula, que si secretos empresariales. Y lo peor es que no tienen ni idea de qué pasa con esa información después. Hoy les voy a mostrar cómo proteger datos cuando usan LLMs — porque el que no sabe, pues pierde.

Qué Es Privacy-Preserving En LLMs?

Básicamente son técnicas para usar modelos de lenguaje sin exponer información sensible. Imagínese mandando un prompt con el historial clínico de un paciente a una API de GPT y que esa data quede guardada en servidores terceros. Eso no es solo violate la ley como la Ley 1581 de protección de datos en Colombia — eso es jugarse la reputación de la empresa completa.

Las cuatro técnicas principales que todo developer debería conocer:

  • Differential Privacy (DP): Añade ruido matemático a los datos o gradientes para que no se pueda revertir información individual
  • Federated Learning (FL): Entrena modelos sin centralizar datos — los datos se quedan en los dispositivos originales
  • Input Sanitization: Limpiar prompts de información personal antes de mandarlos al modelo
  • Secure Multi-Party Computation (SMPC): Múltiples partes calculan sobre datos compartidos sin revelar los inputs

Differential Privacy: La Matemática Detrás

DP se basa en el concepto de epsilon-differential privacy. La idea es que añadir un mecanismo de ruido garantiza que el output de una función sea prácticamente idéntico si se cambia un solo individuo en el dataset.

El mecanismo más común es el Laplacian Mechanism. Para una función de query f(D) que devuelve un valor real, la sensibilidad es:

$$\Delta f = \max |f(D) - f(D')|_1$$

para datasets adyacentes D y D' que difieren en un solo registro. Entonces el ruido calibrado es:

$$\text{Noise} \sim \text{Lap}(\Delta f / \varepsilon)$$

donde $\varepsilon$ es el parámetro de privacidad (más pequeño = más privado pero más ruido).

import numpy as np

def laplacian_mechanism(true_value, sensitivity, epsilon):
    """Añade ruido Laplaciano para differential privacy"""
    scale = sensitivity / epsilon
    noise = np.random.laplace(0, scale)
    return true_value + noise

# Ejemplo: query de conteo con sensibilidad 1
conteo_real = 1500
sensitivity = 1
epsilon = 0.5  # Trade-off privacidad-utilidad

resultado_privado = laplacian_mechanism(conteo_real, sensitivity, epsilon)
print(f"Conteo real: {conteo_real}")
print(f"Conteo con DP (ε={epsilon}): {resultado_privado:.2f}")

Federated Learning Para LLMs

En FL tradicional, cada dispositivo entrena localmente con sus datos y solo comparte gradientes — nunca los datos crudos. Pero para LLMs esto es tricky porque los modelos son enormes.

class FederatedLLMTrainer:
    def __init__(self, model, epsilon=1.0, delta=1e-5):
        self.model = model
        self.epsilon = epsilon  # Parámetro de privacidad DP
        self.delta = delta       # Parameter adicional para (ε,δ)-DP
    
    def compute_private_gradient(self, local_data, client_id):
        """Computa gradiente con clipping y ruido DP"""
        # 1. Entrenar localmente
        gradient = self.model.compute_gradient(local_data)
        
        # 2. Clip gradiente (gradient clipping para bounded sensitivity)
        grad_norm = np.linalg.norm(gradient)
        clip_threshold = 1.0
        clipped_gradient = gradient * min(1, clip_threshold / grad_norm)
        
        # 3. Añadir ruido DP
        noise_scale = clip_threshold * self._compute_noise_multiplier()
        noisy_gradient = clipped_gradient + np.random.normal(0, noise_scale, gradient.shape)
        
        return noisy_gradient
    
    def _compute_noise_multiplier(self):
        """Computa la escala de ruido según ε, δ y número de clientes"""
        # Aproximación para noise multiplier en FedAvg con DP
        return np.sqrt(2 * np.log(1.25 / self.delta)) / self.epsilon


class PrivacyAccountant:
    """Rastrea el presupuesto de privacidad gastado"""
    def __init__(self, epsilon_total=8.0, delta=1e-5):
        self.epsilon_total = epsilon_total
        self.delta = delta
        self.epsilon_spent = 0.0
    
    def spend_budget(self, epsilon_used):
        self.epsilon_spent += epsilon_used
        remaining = self.epsilon_total - self.epsilon_spent
        print(f"Presupuesto gastado: {self.epsilon_spent:.2f}/{self.epsilon_total}")
        print(f"Presupuesto restante: {remaining:.2f}")
        return remaining > 0

Sanitizing Prompts: No Mandar Datos Así Como Así

Antes de mandar un prompt a cualquier LLM, hay que limpiarlo. Esto parece obvio pero el 90% no lo hace.

import re

class PromptSanitizer:
    """Limpia información sensible de prompts antes de enviar al LLM"""
    
    PATTERNS = {
        'cedula': r'\b\d{1,3}[.,]?\d{3}[.,]?\d{3}\b',
        'email': r'\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b',
        'telefono': r'\b(\+57)?\s*3\d{2}[.\s]?\d{3}[.\s]?\d{4}\b',
        'tarjeta': r'\b\d{4}[-\s]?\d{4}[-\s]?\d{4}[-\s]?\d{4}\b',
        'direccion': r'\b[Carrera|Cra|Cl|Calle|Av].*?\d+.*?\b',
    }
    
    def sanitize(self, prompt, replacement="[DATOS_SENSIBLES]"):
        sanitized = prompt
        replacements_made = []
        
        for label, pattern in self.PATTERNS.items():
            matches = re.findall(pattern, sanitized, re.IGNORECASE)
            if matches:
                replacements_made.append(f"{label}: {len(matches)} ocurrencia(s)")
                sanitized = re.sub(pattern, replacement, sanitized, flags=re.IGNORECASE)
        
        return sanitized, replacements_made
    
    def audit(self, prompt):
        """Revisa qué datos sensibles contiene un prompt SIN reemplazarlos"""
        findings = []
        for label, pattern in self.PATTERNS.items():
            matches = re.findall(pattern, prompt, re.IGNORECASE)
            if matches:
                findings.append(f"{label}: {len(matches)} ocurrencia(s)")
        return findings


# Ejemplo de uso
sanitizer = PromptSanitizer()

original = """
Por favor analice este caso del paciente:
Cédula: 1.098.765.432
Email: maria.garcia@gmail.com
Teléfono: +57 312 345 6789
Dirección: Carrera 15 # 45-67, Bogotá
Diagnóstico: El paciente presenta síntomas de...
"""

sanitized, replacements = sanitizer.sanitize(original)
print("=== PROMPT ORIGINAL ===")
print(original)
print("\n=== PROMPT SANITIZADO ===")
print(sanitized)
print("\n=== DATOS REMOVIDOS ===")
for r in replacements:
    print(f"  - {r}")

Secure Multi-Party Computation Intro

SMPC permite que múltiples partes computen una función sobre sus datos inputs sin revelar los datos entre sí. Para LLMs, esto es útil cuando querés que múltiples hospitales analicen modelos sin compartir datos de pacientes.

La versión simplest es Secret Sharing: se divide cada valor en Shares que se distribuyen a las partes. La reconstrucción requiere combinarlas.

def secret_share(value, num_shares=3, prime=2**31 - 1):
    """Comparte un secreto en múltiples shares (Shamir's Secret Sharing simplificado)"""
    shares = []
    remaining = value
    
    for i in range(num_shares - 1):
        share = np.random.randint(0, prime)
        shares.append(share)
        remaining = (remaining - share) % prime
    
    shares.append(remaining % prime)
    return shares

def reconstruct(shares, prime=2**31 - 1):
    """Reconstruye el secreto desde shares"""
    return sum(shares) % prime

# Ejemplo: múltiples hospitales computan estadísticas sin compartir datos
def federated_statistics(hospital_shares):
    """Computa suma de estadísticas desde shares sin revelar datos individuales"""
    # Cada hospital tiene su share localmente
    # Solo se comparten los shares, nunca los datos originales
    aggregated_shares = [sum(hos_shares) % (2**31-1) for hos_shares in zip(*hospital_shares)]
    return aggregated_shares

# Hospital A tiene datos de 100 pacientes
# Hospital B tiene datos de 150 pacientes
# Nunca comparten datos, solo shares

shares_hospital_A = secret_share(100)
shares_hospital_B = secret_share(150)

combined_shares = [shares_hospital_A[i] + shares_hospital_B[i] for i in range(3)]
total = reconstruct(combined_shares)
print(f"Pacientes totales (sin revelar datos): {total}")

Error 1: Mandar Datos Sensibles Sin Protección

El error más común y más grave. Muchos developers asumen que "es solo un prompt" o que "el LLM no guarda los datos". FALSO. La mayoría de APIs guardan prompts para fine-tuning, debugging o mejoras de producto.

Mal: "Analyze this patient record: Name: Juan Pérez, CC: 1.098.765.432, Diagnosis: diabetes tipo 2..." → Mandado a GPT-4 sin sanitización

Fix: SIEMPRE sanitizar antes de enviar. Usar categorías genéricas en vez de datos reales. Si es necesario usar datos reales, usar APIs con zero-retention policies y contracts que garanticen no guarda data.

Error 2: No Entender Qué Datos Se Almacenan

Otro error frecuente es no leer los terms de servicio de las APIs de LLMs. OpenAI, Anthropic, Google — todos guardan datos en algún nivel. Aunque sea por minutos u horas, eso es suficiente para un breach.

Mal: Usar la API de un LLM para procesar CVs de candidatos sin verificar las políticas de retención de datos de la empresa proveedora.

Fix: Hacer un audit trail de datos. Documentar qué datos pasan por qué sistema. Para datos realmente sensibles, usar modelos self-hosted como Llama con everything offline, o usar providers con certifications como SOC2, ISO 27001.

Error 3: No Implementar Medidas de Privacidad

Asumir que porque "no tenemos datos sensibles" no necesitas privacy. ERROR. Los modelos pueden memorize training data y revelar información en outputs. Un modelo fine-tuned en datos médicos puede involuntariamente devolver información de pacientes específicos.

Mal: Fine-tuning un LLM con datos de clientes sin aplicar differential privacy a los gradientes.

Fix: Implementar DP desde el inicio si los datos son sensibles. Usar federated learning para training distribuido. Si no es posible FL, al menos aplicar DP al fine-tuning. Costo computacional extra, pero vale la pena.

# Framework completo de privacidad para LLMs
class LLMPrivacyFramework:
    def __init__(self):
        self.sanitizer = PromptSanitizer()
        self.dp_trainer = FederatedLLMTrainer(None, epsilon=1.0)
        self.accountant = PrivacyAccountant()
    
    def preprocess(self, prompt, user_id):
        """Sanitiza y loggea antes de enviar"""
        audit = self.sanitizer.audit(prompt)
        if audit:
            print(f"[AUDIT] Datos sensibles detectados en prompt de {user_id}: {audit}")
        return self.sanitizer.sanitize(prompt)
    
    def train_with_privacy(self, data_shares, rounds=10):
        """Entrenamiento federado con privacy budget tracking"""
        for round_num in range(rounds):
            if not self.accountant.spend_budget(0.1):  # 0.1 ε por ronda
                print("[STOP] Presupuesto de privacidad agotado")
                break
            # ... training round
            print(f"Ronda {round_num + 1}/{rounds} completada")
        
        print(f"[COMPLETO] Entrenamiento con privacidad diferencial aplicado")


# Uso
framework = LLMPrivacyFramework()
prompt = "Resumen del paciente Juan Pérez, CC 1.098.765.432..."
sanitized_prompt = framework.preprocess(prompt, "user_123")
print(f"Prompt sanitizado: {sanitized_prompt}")

Resumen y Cierre

Bueno parcero, hoy aprendimos que privacy-preserving no es opcional — es necesidad. Los tres errores principales que causan breaches:

  1. Mandar datos sensibles sin sanitizar: Fix: always sanitize, always audit
  2. No entender dónde se almacenan los datos: Fix: leer ToS, usar self-hosted para datos críticos
  3. No implementar privacy measures: Fix: DP desde el inicio si hay datos sensibles

La matemática detrás — differential privacy con su epsilon y sensibilidad — no es tan compleja como parece. Y federated learning, aunque computacionalmente más pesado, da tranquilidad knowing que los datos nunca centralizan.

En Colombia específicamente, la Ley 1581 de Habeas Data exige que las empresas protejan datos personales. Usar LLMs sin privacy-preserving no solo es un riesgo técnico — es un riesgo legal. Así que ya saben: antes de mandar ese prompt con datos de clientes, piénsenlo dos veces.
