KV Cache - Por qué el attention cuadrático es el cuello de botella en transformers

05 de may de 2026
kv-cache

Hola, parcero. Día 155 y hoy vamos con algo que cuando lo entendés bien, te preguntas cómo sobrevivíamos sin esto: KV Cache. Esto es FUNDAMENTAL para entender por qué la inferencia en transformers es tan costosa y qué podemos hacer al respecto. Café listo, vamos.

Que Es KV Cache y Por Que Existe

Durante la generación autoregresiva en un transformer, cada token nuevo necesita attend a TODOS los tokens anteriores. Sin KV Cache, esto significa que en cada paso de generación estás recalculando los attention scores para los mismos tokens que ya habías calculado en pasos anteriores. Traducción: estás desperdiciando compute como si fuera agua en Bogotá en marzo.

La complejidad computacional del attention es O(n² · d) donde n es la longitud de la secuencia y d la dimensionalidad del embedding. Para una secuencia de 2048 tokens con d=768, eso son millones de operaciones que se repiten innecesariamente.

KV Cache almacena los Key y Value tensors de cada layer después de calcularlos por primera vez. Así, cuando generás el token 1025, solo calculás el attention contra los keys/values cacheados de los 1024 tokens anteriores — no los recalculás.

La Matematica Detras

Sin KV Cache, la complejidad para generar N tokens es:

# Complejidad sin KV Cache:
# Step 1: O(1²·d)  → procesás 1 token
# Step 2: O(2²·d)  → recalculás todo para 2 tokens
# Step 3: O(3²·d)  → recalculás todo para 3 tokens
# ...
# Step N: O(N²·d)
# Total: Σ(n²) para n=1..N = O(N³·d)

Con KV Cache, la complejidad por token es O(1·d) porque solo calculás el nuevo token contra el cache:

# Complejidad con KV Cache:
# Step 1: O(1²·d)  → procesás 1 token, guardás K,V en cache
# Step 2: O(1·d)   → solo calculás nuevo token contra cache
# Step 3: O(1·d)   → solo calculás nuevo token contra cache
# ...
# Step N: O(1·d)
# Total: O(N²·d) + O(N·d) = O(N²·d)

El speedup es dramático: de O(N³) a O(N²). Para N=1000 tokens, eso es un improvement de aproximadamente 1000x en la parte computacional del attention.

Implementacion Real en PyTorch

Vamos con código de verdad — nada de pseudocódigo. Esta implementación muestra KV Cache funcionando con un transformer simplificado:

"""
KV Cache Implementation - Día 155
Demostración de cómo el KV Cache acelera la generación autoregresiva.
"""
import torch
import torch.nn as nn
import time
import math

class SimpleAttention(nn.Module):
    """Attention mechanism con soporte para KV Cache."""
    
    def __init__(self, d_model: int, n_heads: int):
        super().__init__()
        assert d_model % n_heads == 0
        self.d_model = d_model
        self.n_heads = n_heads
        self.d_k = d_model // n_heads
        
        self.W_q = nn.Linear(d_model, d_model)
        self.W_k = nn.Linear(d_model, d_model)
        self.W_v = nn.Linear(d_model, d_model)
        self.W_o = nn.Linear(d_model, d_model)
    
    def forward(
        self, 
        x: torch.Tensor, 
        kv_cache: tuple[torch.Tensor, torch.Tensor] | None = None,
        use_cache: bool = True
    ) -> tuple[torch.Tensor, tuple[torch.Tensor, torch.Tensor] | None]:
        """
        Args:
            x: Input tensor [batch, seq_len, d_model]
            kv_cache: Tupla de (keys, values) cacheados de pasos anteriores
            use_cache: Si True, usa y actualiza el cache
        Returns:
            output: Output del attention
            kv_cache: Cache actualizado (keys, values)
        """
        batch, seq_len, _ = x.shape
        
        # Proyectamos a Q, K, V
        Q = self.W_q(x).view(batch, seq_len, self.n_heads, self.d_k).transpose(1, 2)
        K = self.W_k(x).view(batch, seq_len, self.n_heads, self.d_k).transpose(1, 2)
        V = self.W_v(x).view(batch, seq_len, self.n_heads, self.d_k).transpose(1, 2)
        
        new_kv_cache = None
        if use_cache and kv_cache is not None:
            # Concatenamos keys y values previos con los nuevos
            k_cache, v_cache = kv_cache
            K = torch.cat([k_cache, K], dim=2)
            V = torch.cat([v_cache, V], dim=2)
            new_kv_cache = (K, V)
        
        # Attention scores: [batch, heads, seq, seq]
        scores = torch.matmul(Q, K.transpose(-2, -1)) / math.sqrt(self.d_k)
        attn_weights = torch.softmax(scores, dim=-1)
        
        # Output
        output = torch.matmul(attn_weights, V)
        output = output.transpose(1, 2).contiguous().view(batch, -1, self.d_model)
        output = self.W_o(output)
        
        return output, new_kv_cache


class TransformerLayer(nn.Module):
    """Un layer de transformer con attention y feedforward."""
    
    def __init__(self, d_model: int, n_heads: int, d_ff: int):
        super().__init__()
        self.attention = SimpleAttention(d_model, n_heads)
        self.feedforward = nn.Sequential(
            nn.Linear(d_model, d_ff),
            nn.GELU(),
            nn.Linear(d_ff, d_model)
        )
        self.norm1 = nn.LayerNorm(d_model)
        self.norm2 = nn.LayerNorm(d_model)
    
    def forward(
        self, 
        x: torch.Tensor, 
        kv_cache: tuple | None = None,
        use_cache: bool = True
    ) -> tuple[torch.Tensor, tuple | None]:
        # Self-attention con residual
        attn_out, new_kv_cache = self.attention(self.norm1(x), kv_cache, use_cache)
        x = x + attn_out
        # Feedforward con residual
        x = x + self.feedforward(self.norm2(x))
        return x, new_kv_cache


def generate_with_cache(
    model: nn.Module,
    input_ids: torch.Tensor,
    max_new_tokens: int,
    eos_token_id: int = 2,
    temperature: float = 1.0
) -> tuple[list[int], float]:
    """Genera tokens usando KV Cache."""
    model.eval()
    device = next(model.parameters()).device
    
    input_ids = input_ids.to(device)
    generated = input_ids.tolist()[0]
    kv_cache = None
    
    start_time = time.time()
    
    with torch.no_grad():
        for _ in range(max_new_tokens):
            x = input_ids[:, -1:]
            x = model(x, kv_cache, use_cache=True)
            
            if isinstance(x, tuple):
                logits = x[0][:, -1, :]
                kv_cache = x[1]
            else:
                logits = x[:, -1, :]
            
            logits = logits / temperature
            probs = torch.softmax(logits, dim=-1)
            next_token = torch.multinomial(probs, num_samples=1)
            
            if next_token.item() == eos_token_id:
                break
            
            generated.append(next_token.item())
            input_ids = next_token
    
    total_time = time.time() - start_time
    return generated, total_time


def calculate_kv_cache_memory(num_layers: int, num_heads: int, d_k: int, 
                               seq_len: int, batch_size: int = 1,
                               dtype: torch.dtype = torch.float32) -> float:
    """
    Calcula el memory footprint del KV cache en bytes.
    Para cada layer necesitamos almacenar keys y values:
    - Keys: [batch, heads, seq_len, d_k]
    - Values: [batch, heads, seq_len, d_k]
    Total por layer: 2 * batch * heads * seq_len * d_k * bytes_per_element
    """
    bytes_per_element = 4 if dtype == torch.float32 else 2
    memory_per_layer = 2 * batch_size * num_heads * seq_len * d_k * bytes_per_element
    total_memory = num_layers * memory_per_layer
    return total_memory / (1024 ** 2)

Memory Footprint del KV Cache

El KV Cache no es gratis en memoria. Vamos a calcular cuánto ocupa:

# Formula general
# Memory_KV = 2 * n_layers * batch_size * n_heads * d_k * seq_len * bytes

# Ejemplo para GPT-3 (175B parameters):
# n_layers = 96
# n_heads = 96
# d_k = 128
# batch_size = 1

# Para seq_len = 2048:
# 2 * 96 * 1 * 96 * 128 * 2048 * 2 bytes (float16) ≈ 9.6 GB

# Para seq_len = 8192 (long context):
# 2 * 96 * 1 * 96 * 128 * 8192 * 2 bytes ≈ 38.4 GB

Este es exactamente el problema que enfrentan los modelos de long context. El KV Cache crece linealmente con la longitud de contexto, lo que lo hace prohibitivo para secuencias muy largas sin optimizaciones.

Paging-Based KV Cache

El problema de memory fragmentation ocurre cuando allocamos el KV cache de forma contigua para toda la secuencia máxima posible. Si solo usamos 500 tokens de una ventana de 4096, estamos desperdiciando ~3500 tokens de espacio.

La solución es el Paging-Based KV Cache, inspirado en la gestión de memoria de sistemas operativos:

  • Block-based allocation: En lugar de allocar para toda la secuencia, allocamos en bloques de tamaño fijo (típicamente 16-64 tokens)
  • Physical blocks: Los bloques físicos viven en GPU memory
  • Virtual blocks: Los bloques virtuales forman la secuencia lógica
  • Block table: Mapeo de bloques virtuales a físicos

Esto permite que el KV cache crezca dinámicamente y reduce la fragmentación significativamente. vLLM usa esta técnica y puede servir hasta 24x más requests simultáneos comparado con approaches naive.

Los 3 Errores Que Mas Duelen

Error 1: No usar KV Cache — generación 10x más lenta

El problema: Implementar generation loop sin cache. Cada token nuevo recalcula toda la atención de la secuencia acumulada. Para 100 tokens generados, esto significa calcular attention para 1+2+3+...+100 = 5050 pasos de attention en vez de 100.

El fix: Siempre implementar KV cache desde el inicio. En Hugging Face Transformers, simplemente asegurate de pasar use_cache=True (que es el default) y no hacer nada que invalide el cache manualmente:

# ❌ MAL: Sin cache, recalcula todo
outputs = model(input_ids)
input_ids = torch.cat([input_ids, outputs.logits[:, -1:]], dim=-1)

# ✅ BIEN: Con cache (el default en generate())
outputs = model.generate(input_ids, max_new_tokens=100, use_cache=True)

Error 2: KV Cache demasiado grande para long sequences

El problema: Para secuencias largas, el KV cache puede exceder la GPU memory. Un modelo con 70B parámetros y context de 32k tokens puede necesitar ~60GB solo para el KV cache en float16.

El fix: Usar quantization del KV cache (FP8, INT8) o paging-based cache. También considerar sliding window attention donde los primeros tokens se "dropean" después de cierto punto:

# Cuantización del KV cache con bitsandbytes
from transformers import BitsAndBytesConfig

quantization_config = BitsAndBytesConfig(
    load_in_8bit=True,
    llm_int8_has_fp16_weight=False
)
model = AutoModelForCausalLM.from_pretrained(
    "mistralai/Mistral-7B-v0.1",
    quantization_config=quantization_config
)

Error 3: No hacer paging del KV Cache — memory fragmentation

El problema: Allocar el KV cache como tensor contiguo del tamaño máximo causa memory fragmentation y no permite crecer dinámicamente. Cuando la GPU se queda sin memoria contigua, aunque haya suficiente memoria total, fallan de alloc.

El fix: Usar sistemas que implementen paged attention como vLLM:

# vLLM con PagedAttention
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-2-70b-hf",
          max_model_len=8192,
          block_size=16)

sampling_params = SamplingParams(temperature=0.8, max_tokens=256)
outputs = llm.generate(prompts, sampling_params)
# vLLM maneja automáticamente el paging del KV cache

Resumen y Cierre

Hoy cubrimos KV Cache a fondo, parcero. Es una de las optimizaciones más importantes en inferencia de transformers porque transforma la complejidad de O(N³) a O(N²) — un improvement de 1000x para secuencias de 1000 tokens.

Los puntos clave para llevarse:

  • Sin KV Cache cada token nuevo recalcula atención sobre toda la historia — muy caro
  • Con KV Cache solo calculás el nuevo token contra lo cacheado — O(1) por token nuevo
  • El memory tradeoff es real: para long contexts el KV cache puede ser prohibitivo
  • Paging-based cache resuelve la fragmentación y permite más concurrent requests
