☕ Intro: El Café de las 6AM

Hagale pues, parcero. Imagine que usted es el dueño de un restaurante en Bogotá. Tiene 10 meseros. ¿Qué pasa cuando uno de ellos se enferma y no puede trabajar? ¿Cierra el restaurante? ¿O tiene un mesero de respaldo que puede cubrir mientras el otro se recupera? El 85% de las empresas que usan LLMs en producción NO tienen ese mesero de respaldo. Cuando el LLM se cae, el usuario recibe un error críptico o simplemente nada. Y ahí empieza el desastre. Hoy día 266: LLM Failures y Graceful Degradation.

💥 La Realidad: Los LLMs FALLAN

Los LLMs en producción fallan por muchas razones:

  • **API Outage**: OpenAI, Anthropic, o tu proveedor tiene una caída
  • **Rate Limiting**: Excedes los tokens por minuto permitidos
  • **Timeout**: La respuesta tarda más del threshold acceptable
  • **Invalid Response**: El LLM devuelve JSON malformado o texto inesperado
  • **Content Filtering**: El safety system bloquea tu request
  • **Model Deprecation**: Tu versión de modelo ya no está disponible

La matemática es cruel: si tu servicio depende 100% de un solo LLM y ese LLM tiene 99.9% de uptime, tienes ~8.7 horas de downtime al año. ¿Puedes darte el lujo de estar offline 8.7 horas?

🔄 Circuit Breaker Pattern: El Electricista Inteligente

El Circuit Breaker es un patrón de ingeniería de software que existe desde hace décadas. Funciona como un interruptor eléctrico: cuando detecta demasiadas fallas, "abre" el circuito y deja de intentar llamar al servicio que está fallando. Esto previene el efecto cascada y da tiempo al servicio afectado para recuperarse.

from enum import Enum
from datetime import datetime, timedelta
import threading
import time

class CircuitState(Enum):
    CLOSED = "closed"      # Normal - requests pasan
    OPEN = "open"          # Fallando - requests bloqueados
    HALF_OPEN = "half_open"  # Probando - permite algunos requests

class CircuitBreaker:
    """
    Circuit Breaker para llamadas a LLM.
    
    Estados:
    - CLOSED: Todo bien, requests pasan normalmente
    - OPEN: Demasiadas fallas, requests son bloqueados inmediatamente
    - HALF_OPEN: Después de timeout, permite requests de prueba
    """
    
    def __init__(
        self,
        failure_threshold: int = 5,      # Número de fallas para abrir
        success_threshold: int = 2,       # Éxitos en HALF_OPEN para cerrar
        timeout_seconds: int = 30,        # Tiempo antes de probar de nuevo
        half_open_max_calls: int = 3     # Calls permitidos en half-open
    ):
        self.failure_threshold = failure_threshold
        self.success_threshold = success_threshold
        self.timeout_seconds = timeout_seconds
        self.half_open_max_calls = half_open_max_calls
        
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.success_count = 0
        self.last_failure_time = None
        self.half_open_calls = 0
        self._lock = threading.Lock()
        
    def call(self, func, *args, **kwargs):
        """
        Ejecuta func a través del circuit breaker.
        Si está OPEN, lanza CircuitBreakerOpen exception inmediatamente.
        """
        with self._lock:
            if self.state == CircuitState.OPEN:
                if self._should_attempt_reset():
                    self._transition_to_half_open()
                else:
                    raise CircuitBreakerOpen(
                        f"Circuit is OPEN. Last failure: {self.last_failure_time}"
                    )
                    
            if self.state == CircuitState.HALF_OPEN:
                if self.half_open_calls >= self.half_open_max_calls:
                    raise CircuitBreakerOpen(
                        "Circuit is HALF_OPEN and max calls reached"
                    )
                self.half_open_calls += 1
                
        # Ejecutar la función
        try:
            result = func(*args, **kwargs)
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise
            
    def _should_attempt_reset(self) -> bool:
        """Verifica si ha pasado suficiente tiempo para intentar reset"""
        if self.last_failure_time is None:
            return True
        elapsed = (datetime.now() - self.last_failure_time).total_seconds()
        return elapsed >= self.timeout_seconds
        
    def _on_success(self):
        with self._lock:
            if self.state == CircuitState.HALF_OPEN:
                self.success_count += 1
                if self.success_count >= self.success_threshold:
                    self._transition_to_closed()
            else:
                # Reset failure count en CLOSED
                self.failure_count = 0
                
    def _on_failure(self):
        with self._lock:
            self.failure_count += 1
            self.last_failure_time = datetime.now()
            
            if self.state == CircuitState.HALF_OPEN:
                # Cualquier falla en HALF_OPEN abre de nuevo
                self._transition_to_open()
            elif self.failure_count >= self.failure_threshold:
                self._transition_to_open()
                
    def _transition_to_open(self):
        self.state = CircuitState.OPEN
        self.half_open_calls = 0
        print(f"🔴 Circuit breaker OPENED at {datetime.now()}")
        
    def _transition_to_half_open(self):
        self.state = CircuitState.HALF_OPEN
        self.half_open_calls = 0
        self.success_count = 0
        print(f"🟡 Circuit breaker HALF_OPEN at {datetime.now()}")
        
    def _transition_to_closed(self):
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.success_count = 0
        self.half_open_calls = 0
        print(f"🟢 Circuit breaker CLOSED at {datetime.now()}")


class CircuitBreakerOpen(Exception):
    """Excepción cuando el circuit breaker está abierto"""
    pass


# Uso con LLM API calls
llm_circuit_breaker = CircuitBreaker(
    failure_threshold=5,
    timeout_seconds=30
)

def call_llm_with_circuit_breaker(prompt: str) -> str:

    Llama al LLM con circuit breaker protection.
    """

                                         model="gpt-4", 
                                         messages=[{"role": "user", "content": prompt}])

        raise

🔗 Fallback Chains: El Mesero de Respaldo

Un fallback chain es una secuencia de opciones alternativas. Si la primera falla (LLM principal), se intenta la segunda, y así sucesivamente. Como tener reserva de meseros.

from typing import List, Callable, Any, Optional
import asyncio

class FallbackChain:
    """
    Chain de fallbacks para LLM calls.
    Cada fallback puede ser:
    - Otro LLM (GPT-4 → Claude → Llama)
    - Respuesta predefinida
    - Cache
    - Error controlado
    """
    
    def __init__(self):
        self.providers = []  # Lista de (name, callable) tuples
        
    def add_fallback(self, name: str, func: Callable, **kwargs):
        """Agrega un fallback a la chain"""
        self.providers.append({
            'name': name,
            'func': func,
            'kwargs': kwargs
        })
        
    async def call(self, prompt: str, context: dict = None) -> dict:
        """
        Ejecuta la chain hasta que uno funcione.
        Returns: {'success': bool, 'provider': str, 'response': str, 'error': str}
        """
        last_error = None
        
        for i, provider in enumerate(self.providers):
            try:
                # Timeout por provider
                response = await asyncio.wait_for(
                    provider['func'](prompt, **(provider.get('kwargs', {}) or {})),
                    timeout=30
                )
                
                return {
                    'success': True,
                    'provider': provider['name'],
                    'response': response,
                    'fallback_level': i,  # 0 = primary, 1+ = fallbacks
                    'error': None
                }
                
            except asyncio.TimeoutError:
                last_error = f"Timeout on {provider['name']}"
                print(f"⏰ {last_error}")
                continue
                
            except Exception as e:
                last_error = f"Error on {provider['name']}: {str(e)}"
                print(f"❌ {last_error}")
                continue
                
        # Todos fallaron
        return {
            'success': False,
            'provider': None,
            'response': None,
            'fallback_level': len(self.providers),
            'error': last_error
        }
        
    def call_sync(self, prompt: str, context: dict = None) -> dict:
        """Versión síncrona para código no-async"""
        import concurrent.futures
        
        last_error = None
        
        for i, provider in enumerate(self.providers):
            try:
                # Timeout usando ThreadPoolExecutor
                with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
                    future = executor.submit(provider['func'], prompt)
                    response = future.result(timeout=30)
                    
                return {
                    'success': True,
                    'provider': provider['name'],
                    'response': response,
                    'fallback_level': i,
                    'error': None
                }
                
            except concurrent.futures.TimeoutError:
                last_error = f"Timeout on {provider['name']}"
                continue
            except Exception as e:
                last_error = f"Error on {provider['name']}: {str(e)}"
                continue
                
        return {
            'success': False,
            'provider': None,
            'response': None,
            'fallback_level': len(self.providers),
            'error': last_error
        }

🔁 Retry con Exponential Backoff: El Thundering Herd

Cuando un servicio falla, TODOS los clientes quieren retry al mismo tiempo. Esto causa "thundering herd" - miles de requests golpeando el servicio cuando se recupera. La solución: exponential backoff con jitter.

import random
import asyncio
from datetime import datetime, timedelta

class RetryStrategy:
    """
    Retry con exponential backoff y jitter.
    
    Sin jitter: todos retry al mismo tiempo → thundering herd
    Con jitter: retries distribuídos → carga suave
    """
    
    def __init__(
        self,
        max_retries: int = 3,
        base_delay: float = 1.0,       # Delay inicial en segundos
        max_delay: float = 60.0,        # Delay máximo
        exponential_base: float = 2.0,  # Multiplicador
        jitter: bool = True             # Añadir randomness
    ):
        self.max_retries = max_retries
        self.base_delay = base_delay
        self.max_delay = max_delay
        self.exponential_base = exponential_base
        self.jitter = jitter
        
    def calculate_delay(self, attempt: int) -> float:
        """
        Calcula el delay para el intento actual.
        
        Sin jitter: 1, 2, 4, 8, 16... segundos
        Con jitter: [0.5-1.5], [1-3], [2-6], [4-12]...
        """
        # Exponential backoff
        delay = self.base_delay * (self.exponential_base ** attempt)
        delay = min(delay, self.max_delay)
        
        if self.jitter:
            # Jitter uniforme: ±50%
            jitter_range = delay * 0.5
            delay = delay + random.uniform(-jitter_range, jitter_range)
            
        return delay
        
    async def retry_async(self, func: Callable, *args, **kwargs):
        """
        Ejecuta func con retry logic (async version).
        """
        last_exception = None
        
        for attempt in range(self.max_retries + 1):
            try:
                return await func(*args, **kwargs)
                
            except Exception as e:
                last_exception = e
                
                if attempt < self.max_retries:
                    delay = self.calculate_delay(attempt)
                    print(f"⚠️ Attempt {attempt + 1} failed: {e}")
                    print(f"   Retrying in {delay:.2f}s...")
                    await asyncio.sleep(delay)
                else:
                    print(f"❌ All {self.max_retries + 1} attempts failed")
                    
        raise last_exception
        
    def retry_sync(self, func: Callable, *args, **kwargs):
        """Versión síncrona"""
        last_exception = None
        
        for attempt in range(self.max_retries + 1):
            try:
                return func(*args, **kwargs)
            except Exception as e:
                last_exception = e
                
                if attempt < self.max_retries:
                    delay = self.calculate_delay(attempt)
                    print(f"⚠️ Attempt {attempt + 1} failed: {e}")
                    print(f"   Retrying in {delay:.2f}s...")
                    time.sleep(delay)
                else:
                    print(f"❌ All {self.max_retries + 1} attempts failed")
                    
        raise last_exception


# Jitter visualizado - por qué es importante
def simulate_thundering_herd():
    """
    Simula el problema del thundering herd.
    Sin jitter: todos hacen retry al mismo segundo.
    """
    num_clients = 1000
    recovery_time = 5  # segundos después de la caída
    
    # Sin jitter - todos retry exactamente al mismo tiempo
    print("=" * 50)
    print("SIN JITTER (Thundering Herd)")
    print("=" * 50)
    for t in range(recovery_time + 1):
        if t == recovery_time:
            print(f"Segundo {t}: {num_clients} clients retry simultaneously! 💥")
    
    # Con jitter - retries distribuídos
    print()
    print("=" * 50)
    print("CON JITTER (Distribución suave)")
    print("=" * 50)
    delays = []
    for _ in range(num_clients):
        # Exponential backoff con jitter
        base_delay = 1.0 * (2 ** 0)  # primer retry
        jitter = base_delay * 0.5 * random.uniform(-1, 1)
        delay = max(0, base_delay + jitter)
        delays.append(delay)
    
    # Distribución
    buckets = [0, 1, 2, 3, 4, 5, 10]
    for i in range(len(buckets) - 1):
        count = sum(1 for d in delays if buckets[i] <= d < buckets[i+1])
        print(f"Segundo {buckets[i]}-{buckets[i+1]}: ~{count} retries")


# Uso práctico

🧪 Testing Failure Scenarios: No Esperes a Producción

No puedes esperar a que el LLM se caiga en producción para saber si tu sistema sobrevive. Tienes que simular fallas deliberadamente.

    def malformed_response(*args, **kwargs):

class TestLLMFailures:
    """Tests para verificar graceful degradation"""
    
    @pytest.mark.asyncio
    async def test_circuit_breaker_opens_after_failures(self):
        """Verifica que circuit breaker abre después de N fallas"""
        cb = CircuitBreaker(failure_threshold=3, timeout_seconds=1)
        
        for _ in range(3):
            with pytest.raises(Exception):
                await cb.call(lambda: 1/0)  # Siempre falla
        
        # Ahora debe estar OPEN
        assert cb.state == CircuitState.OPEN
        
        # Retry debe fallar inmediatamente
        with pytest.raises(CircuitBreakerOpen):
            await cb.call(lambda: 2)
            
    @pytest.mark.asyncio
    async def test_fallback_chain_works(self):
        """Verifica que fallback chain funciona"""
        chain = FallbackChain()
        
        # Primary falla
        chain.add_fallback("failing", lambda x: (_ for _ in ()).throw(Exception("fail")))
        # Secondary funciona
        chain.add_fallback("working", lambda x: "success from secondary")
        
        result = await chain.call("test prompt")
        
        assert result['success'] == True
        assert result['provider'] == 'working'
        assert result['response'] == 'success from secondary'
        
    @pytest.mark.asyncio
    async def test_retry_respects_backoff(self):

        strategy = RetryStrategy(max_retries=2, base_delay=0.1, jitter=False)
        
        start = time.time()
        attempt = 0
        
        async def failing_func():
            nonlocal attempt
            attempt += 1
            raise Exception(f"Attempt {attempt}")
        
        with pytest.raises(Exception):
            await strategy.retry_async(failing_func)
        
        elapsed = time.time() - start
        
        # Debería haber esperado: 0.1 + 0.2 = 0.3 segundos (sin jitter)
        assert elapsed >= 0.25, f"Backoff no funcionó: {elapsed}s"
        
    @pytest.mark.asyncio
    async def test_full_graceful_degradation(self):
        """
        Test completo: todo falla y verificamos que el usuario

        """
        chain = FallbackChain()
        
        # Todos fallan
        chain.add_fallback("always_fail", lambda x: (_ for _ in ()).throw(Exception("down")))

        # Todos fallaron
        assert result['success'] == False
        assert result['fallback_level'] == 2
        assert result['error'] is not None

# Chaos engineering para LLMs
class LLMChaosEngineering:
    """
    Introduce fallas aleatorias en producción para verificar
    que el sistema sobrevive. Solo en staging!
    """
    
    def __init__(self, failure_rate: float = 0.1):
        self.failure_rate = failure_rate
        self.failures_injected = 0
        self.total_calls = 0
        
    def should_fail(self) -> bool:
        self.total_calls += 1
        if random.random() < self.failure_rate:
            self.failures_injected += 1
            return True
        return False
        
    def inject_random_failure(self, func: Callable) -> Callable:
        """Decorador que inyecta fallas aleatorias"""
        def wrapper(*args, **kwargs):
            if self.should_fail():
                failure_type = random.choice(['timeout', 'error', 'malformed'])
                if failure_type == 'timeout':
                    raise asyncio.TimeoutError("Chaos: injected timeout")
                elif failure_type == 'error':
                    raise APIError("Chaos: injected error")
                else:
                    return Mock(choices=[Mock(message=Mock(content="{"))])
            return func(*args, **kwargs)
        return wrapper

⚠️ Los 3 Errores Que El 85% Comete

Error 1: No Tener Fallback y Retornar Error Raw al Usuario

El problema: Cuando el LLM falla, retornas `500 Internal Server Error` o algo igualmente inútil. El usuario no sabe qué hacer. Se frustra. Se va.

El impacto: conversion drop, daño reputacional, usuarios que no vuelven. Un error no manejado cuesta más que un fallback implementarlo.

La matemática: Un estudio de Google encontró que cada 100ms de latency adicional cuesta 1% en conversión. Un error 500 cuesta mucho más que eso.

La solución: Siempre tener un fallback que retorne algo útil:

# ❌ MAL: Retornar error raw
def bad_llm_call(prompt: str):
    response = openai.ChatCompletion.create(model="gpt-4", messages=[...])
    return response.choices[0].message.content
    # Si esto falla, el usuario ve 500 Error y no sabe qué hacer

# ✅ BIEN: Fallback siempre disponible
def llm_call_with_fallback(prompt: str) -> dict:
    try:
        response = openai.ChatCompletion.create(model="gpt-4", messages=[...])
        return {
            'success': True,
            'response': response.choices[0].message.content,
            'provider': 'gpt-4'
        }
    except RateLimitError:
        # Retry internally antes de retornar fallback
        time.sleep(5)
        response = openai.ChatCompletion.create(model="gpt-3.5-turbo", messages=[...])
        return {
            'success': True,
            'response': response.choices[0].message.content,
            'provider': 'gpt-3.5-turbo-fallback',
            'degraded': True
        }
    except Exception as e:
        # Último recurso: mensaje amigable
        return {
            'success': False,
            'response': "Gracias por su mensaje. Nuestro equipo está experimentando alta demanda. Le responderemos a la brevedad.",
            'provider': 'static-fallback',
            'error': str(e),
            'degraded': True
        }

Error 2: No Implementar Circuit Breaker y Hammering Cuando Está Fallando

El problema: Sin circuit breaker, cuando el LLM empieza a fallar, tu sistema sigue mandando requests. Esto puede causar que el LLM se caiga más (efecto cascada) o que te bloquen por demasiados requests.

El impacto: El LLM no se recupera porque sigue recibiendo traffic. Te vuelves parte del problema. Y potencialmente te banean del API.

La matemática: Si tienes 100 req/s y el LLM tiene 1% de failure rate, son 1 request/sec que falla. Sin circuit breaker, esos 100 req/s siguen golpeando. Con circuit breaker, después de N fallas, cortas el tráfico y das tiempo al LLM.

La solución: Circuit breaker con umbrales apropiados:

# ❌ MAL: Sin circuit breaker
def bad_call():
    while True:
        try:
            return call_llm(prompt)
        except Exception as e:
            print(f"Error: {e}")  # Solo log, sigue intentando
            # Esto puede causar cascading failure

# ✅ BIEN: Circuit breaker
cb = CircuitBreaker(failure_threshold=5, timeout_seconds=30)

def protected_call():
    return cb.call(call_llm, prompt)
    # Después de 5 fallas, abre el circuito
    # Durante 30 segundos, retorna inmediatamente (no淹)
    # Después intenta de nuevo (half-open)

Error 3: Retries Sin Exponential Backoff Causando Thundering Herd

El problema: Cuando el LLM se recupera, 1000 clientes hacen retry exactamente al mismo segundo. Eso overwhelms el servicio que apenas se estaba recuperando. El "thundering herd" puede tumbarlo de nuevo.

El impacto: Recovery prolongado o nuevo outage. Estás retrasando tu propia recuperación.

La matemática: Sin jitter, todos los retries caen en el mismo segundo. Con jitter del ±50%, la distribución se extiende. Esto puede ser la diferencia entre recovery en 1 segundo vs 10 segundos.

La solución: Exponential backoff + jitter siempre:

# ❌ MAL: Retry inmediato
for i in range(3):
    try:
        return call_llm(prompt)
    except:
        time.sleep(1)  # Mismo delay para todos!
        
# ✅ BIEN: Exponential backoff con jitter
class GoodRetry:
    def __init__(self):
        self.base_delay = 1.0
        self.jitter_factor = 0.5
        
    def get_delay(self, attempt: int) -> float:
        delay = self.base_delay * (2 ** attempt)
        jitter = delay * self.jitter_factor * random.uniform(-1, 1)
        return delay + jitter
    
    def retry(self, func):
        for attempt in range(5):
            try:
                return func()
            except:
                time.sleep(self.get_delay(attempt))

🎯 Resumen y Cierre Colombiano

Hagale pues, parcero. Los LLMs fallan. No es "si", es "cuándo". Y cuando fallen, tienes dos opciones: dejar al usuario con un error inútil, o manejarlo gracefully con un plan B, C, y D.

La matemática es simple: un outage de 1 hora puede costar desde $100 hasta $1M dependiendo de tu negocio. Implementar circuit breaker, fallback chain, y retry con backoff cuesta talvez 200 líneas de código. La diferencia entre dormir tranquilo o estar despertando a las 3am.

Los tres pilares de graceful degradation:

  • **Circuit Breaker**: Corta el tráfico cuando el servicio está fallando
  • **Fallback Chain**: Siempre tener un plan B, C, D cuando el primary falla
  • **Exponential Backoff + Jitter**: Retry inteligente que no causa thundering herd

Y por favor, testea estos escenarios ANTES de que fallen en producción. No esperes a que el LLM se caiga para saber si tu sistema sobrevive.
