Latency Optimization - Haciendo LLMs Mas Rapidos

10 de septiembre de 2026
latencyoptimizationinferenceperformance

Por Que La Latencia Importa

Imagina que tienes un chatbot que tarda 30 segundos en responder. El usuario ya se fue hace 20 segundos. La latencia no es solo un numero — es la diferencia entre una experiencia usable y una que el usuario abandona.

Los LLMs son inherentemente lentos. Generar texto token por token significa esperar la inferencia de red neuronal para cada token. Un response de 500 tokens puede tomar 10-30 segundos en un modelo grande. Eso es una eternidad en terminos de UX.

Pero hay tecnicas para hacer esto mas rapido sin perder calidad. Hoy las exploramos.

Arquitectura De Inference

Antes de optimizar, hay que entender como funciona la inference en LLMs:

  • Prefill phase: El prompt se procesa en paralelo — es rapido
  • Decode phase: Los tokens se generan uno por uno — es lento
  • Total time = prefill + (tokens_generados * tiempo_por_token)

La mayoria del tiempo se va en el decode phase. Ahi es donde tenemos queFocus.

KV Cache — Cache Para Atention

Cada vez que generas un token, el modelo recalcula los key-value vectors para TODOS los tokens anteriores. Eso es O(n) por token, o O(n^2) para toda la generacion. El KV cache evita recalcularlos.

Como Funciona

La atencion multi-head calcula:

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

Donde K y V son los mismos para tokens anteriores. Si los cacheamos:

  • Primera generacion: calculo completo
  • Tokens siguientes: solo calcular Q para el nuevo token + usar cached K,V

Implementacion

class KVCache:
    def __init__(self):
        self.k_cache = []
        self.v_cache = []
    
    def update(self, k, v):
        self.k_cache.append(k)
        self.v_cache.append(v)
        return torch.cat(self.k_cache, dim=2), torch.cat(self.v_cache, dim=2)
    
    def get(self):
        return torch.cat(self.k_cache, dim=2), torch.cat(self.v_cache, dim=2)

# En el forward pass
if use_cache:
    k, v = cache.update(k, v)
    # Usa k, v cacheados en lugar de recalcular
    attn_output = attention(q, k, v)
else:
    # Calculo completo sin cache
    attn_output = attention(q, k, v)

Batch Processing — Procesando Multiples Requests

Si tienes 100 usuarios esperando respuestas, no los process uno por uno. El batching permite procesar multiples sequences en paralelo en la misma forward pass.

Batching Estatico vs Dinamico

Batching estatico: Agrupa requests con longitud fija. Simple pero ineficiente si hayvariacion en longitud.

Batching dinamico: Agrupa requests segun llegan, pero espera a que todos terminen antes de devolver. Mejor utilizacion de GPU.

# Ejemplo conceptual de batching
requests = [
    ("Que es Python?", max_tokens=100),
    ("Explica ML", max_tokens=200),
    ("Historia de AI", max_tokens=150),
]

# Padding para igualar longitudes
batch = pad_sequences([r.prompt for r in requests])

# Forward pass unico para todos
outputs = model(batch)

# Extraer respuestas individuales
responses = [extract_response(o, r.max_tokens) for o, r in zip(outputs, requests)]

Quantization — Modelos Mas Livianos

FP32 = 4 bytes por parametro. FP16 = 2 bytes. INT8 = 1 byte. Quantization reduce precision numerica para memory y compute mas rapidos.

GPTQ vs AWQ vs bitsandbytes

  • GPTQ: Post-training quantization, bueno para 4-bit
  • AWQ: Activation-aware, mejor calidad
  • bitsandbytes: Facil de usar, integrado en HuggingFace
# bitsandbytes quantization
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

quantization_config = BitsAndBytesConfig(
    load_in_8bit=True,
    llm_int8_threshold=6.0
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-7b",
    quantization_config=quantization_config,
    device_map="auto"
)

# 7B params: 7B * 1 byte = 7GB (vs 14GB FP16)

Speculative Decoding — Draft + Verify

Idea: Un modelo pequeno (draft) genera varios tokens rapidamente, luego el modelo grande los verifica en paralelo. Si el draft acerto, ganas tiempo. Si fallo, el modelo grande toma el control.

$$\text{Speedup} = \frac{t_{\text{large}}}{t_{\text{draft}} \cdot \alpha + t_{\text{verify}} \cdot (1-\alpha)}$$

Donde alpha es la tasa de aceptacion del draft.

def speculative_decode(draft_model, target_model, prompt, gamma=4):
    draft_tokens = draft_model.generate(prompt, max_new_tokens=gamma)
    target_logits = target_model(draft_tokens)
    
    # Verificar cada token del draft
    accepted = []
    for i in range(gamma):
        draft_token = draft_tokens[-(gamma-i)]
        target_token = sample(target_logits[-(gamma-i)])
        
        if draft_token == target_token:
            accepted.append(draft_token)
        else:
            # Fallo - el target toma el control
            break
    
    return accepted

# Speedup tipico: 2-3x con draft de 7B y target de 70B

Continuous Batching —-Maximizando GPU Utilization

El problema con static/dynamic batching: cuando un request largo termina, toda la batch espera a los cortos. Continuous batching permite que nuevos requests entren a la batch en cuanto hay espacio.

class ContinuousBatcher:
    def __init__(self, model, max_batch_size=32):
        self.model = model
        self.max_batch_size = max_batch_size
        self.waiting = []
        self.running = []
    
    def add_request(self, request):
        self.waiting.append(request)
    
    def step(self):
        # Liberar slots de requests completados
        self.running = [r for r in self.running if not r.is_done()]
        
        # Agregar nuevos requests hasta llenar batch
        while len(self.running) < self.max_batch_size and self.waiting:
            self.running.append(self.waiting.pop(0))
        
        if self.running:
            # Procesar batch
            outputs = self.model.forward([r.tokens for r in self.running])
            for r, output in zip(self.running, outputs):
                r.add_output(output)

Pruning — Eliminando Neuronas Innecesarias

No todas las neuronas son iguales. Algunas tienen poca influencia en el output. Pruning las elimina:

  • Magnitude pruning: Elimina pesos pequenos
  • Movement pruning: Elimina durante fine-tuning
  • Sparse attention: Hace atention sparse, ignorando conexiones debiles
import torch.nn.utils as nn_utils

# Magnitude pruning global
def prune_weights(model, sparsity=0.3):
    for name, param in model.named_parameters():
        if 'weight' in name:
            # Calcular threshold como el percentile de magnitud
            threshold = torch.quantile(torch.abs(param), sparsity)
            mask = torch.abs(param) > threshold
            param.data *= mask.float()

Resumen Y Cierre

La latencia en LLMs es un problema complejo con multiples soluciones:

  • KV Cache: Evita recalcular atention para tokens previos
  • Batching: Procesa multiples requests en paralelo
  • Quantization: Modelos mas pequenos con menos precision
  • Speculative Decoding: Draft pequeno + verificacion rapida
  • Continuous Batching: GPU utilization maxima
  • Pruning: Elimina pesos innecesarios

La combinacion de estas tecnicas puede reducir latency de 30s a 3s — 10x mas rapido. Y eso es la diferencia entre un producto usable y uno que nadie usa.
