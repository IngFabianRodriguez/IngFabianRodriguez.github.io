10 de septiembre de 2026

Pues resulta, parcero, que estaba yo en una reunión el mes pasado donde un equipo de ML presentaba sus "resultados" de evaluación de un LLM. Sacaron una tabla comparando su modelo contra GPT-4 en MMLU y todo el mundo quedó esperando. Hasta que pregunté: "¿Cómo hicieron la evaluación?" — y boom, silencio. Resulta que habían probado el modelo "a ojo", preguntándole 20 cosas y conclusionando. Eso no es evaluación, eso es almuerzo de malucos.

Por eso hoy hablamos de lm-evaluation-harness: el framework que el 80% de la gente que evalúa LLMs no conoce o no sabe usar bien. Y créeme, sin una evaluación sistemática, estás volando ciegazo.

¿Por Qué Necesitas Un Evaluation Harness?

Imagina que tienes dos modelos: modelo_A y modelo_B. Quieres saber cuál es mejor para tu aplicación de análisis financiero en español. ¿Qué hace la mayoría? Le hace 10 preguntas a cada uno y ya. Error fatal.

Un evaluation harness como lm-evaluation-harness te permite:

  • Evaluar de manera reproducible: Exact same conditions para todos los modelos
  • Correr benchmarks estandarizados: MMLU, GSM8K, HumanEval, TruthfulQA
  • Custom tasks: Evaluar dominio específico con tus propios datasets
  • Resultados comparables: Numbers que puedes publicar y replicar

Los Benchmarks Que Tienes Que Conocer

MMLU — Massive Multitask Language Understanding

57 tareas diferentes: ciencia, historia, derecho, medicina. Mide conocimiento general. La fórmula del score:

$$\text{Accuracy} = \frac{\text{Respuestas Correctas}}{\text{Total de Preguntas}} \times 100\%$$

Un modelo random logra ~25% en opciones múltiples (4 choices). GPT-4 anda por ~86%. Si tu modelo está por debajo de random, algo está mal.

GSM8K — Grade School Math 8K

8,500 problemas de matemáticas de primaria. No es triviales — requieren multi-step reasoning. Mide capacidad de razonamiento matemático.

$$\text{GSM8K Accuracy} = \frac{\text{Problemas Resueltos Correctamente}}{8,500} \times 100\%$$

La dificultad está en que el modelo no solo tiene que dar la respuesta final — tiene que mostrar el paso a paso. Un error en el paso 3 descarta todo.

HumanEval — Code Generation

164 problemas de programación en Python. Mide ability to generate correct code. Cada problema incluye:

  • Docstring con especificación
  • Firma de la función
  • Cuerpo de la función (vacío)

El modelo tiene que completar el cuerpo. Se ejecuta contra tests unitarios:

$$\text{Pass@K} = 1 - \frac{\binom{n - c}{k}}{\binom{n}{k}}$$

Donde n = total de problemas, c = correctos, k = número de intentos. Pass@1 es el estándar.

TruthfulQA — Truthfulness

817 preguntas donde humanos frecuentemente dan respuestas incorrectas. Mide si el modelo repite desinformación o responde honestamente. Este benchmark es tricky porque:

  • Un modelo que siempre dice "no sé" sería muy truthful pero inútil
  • La métrica equilibra truthfulness vs informativeness

Usando lm-evaluation-harness

Instalación

pip install lm-evaluation-harness
# o desde source:
git clone https://github.com/EleutherAI/lm-evaluation-harness
cd lm-evaluation-harness
pip install -e .

Evaluación Básica — CLI

# Evaluar modelo en MMLU
lm_eval \
  --model hf \
  --model_args pretrained=mistralai/Mistral-7B-v0.1 \
  --tasks mmlu \
  --device cuda:0 \
  --batch_size 8

# Múltiples benchmarks de una vez
lm_eval \
  --model hf \
  --model_args pretrained=meta-llama/Llama-2-7b \
  --tasks mmlu,gsm8k,truthfulqa_mc \
  --device cuda:0 \
  --batch_size 4

Output — Cómo Leer Los Resultados

{
  "results": {
    "mmlu": {
      "acc": 0.6942,
      "acc_stderr": 0.0046
    },
    "gsm8k": {
      "acc": 0.4123,
      "acc_stderr": 0.0156
    }
  },
  "config": {
    "model": "mistralai/Mistral-7B-v0.1",
    "num_fewshot": 5
  }
}

acc es el accuracy principal. acc_stderr es el standard error — valores debajo de 0.01 son buenos, significa que la evaluación es estable.

Creando Custom Tasks

Aquí es donde la cosa se pone interesante. Los benchmarks genéricos no cubren tu dominio específico. Para un sistema médico, necesitas evaluar en español médico. Para código empresarial, necesitas tus propias pruebas.

Estructura de una Custom Task

# tasks/medical-qa-es.yaml
task: medical_qa_es
dataset_path: tu/medical-qa-spanish
dataset_name: null
output_type: multiple_choice
test_split: test
num_fewshot: 5

training_split: null
dataset_kwargs:
  trust_remote_code: true

# Formato de cada ejemplo:
# {"question": "...", "choices": ["A", "B", "C", "D"], "gold": 2}
# gold = índice de la respuesta correcta

doc_to_text: "{{question}}"
doc_to_choice: "{{choices}}"
doc_to_target: "{{gold}}"

Cargar y Usar la Task

from lm_eval.api.registry import ALL_TASKS
from lm_eval.api.tasks import TaskManager

# Cargar task manager con tasks personalizadas
tm = TaskManager(["tasks/", "custom_tasks/"])

# O desde CLI con task específica
lm_eval \
  --model hf \
  --model_args pretrained=models/tu-modelo-medico \
  --tasks medical_qa_es \
  --device cuda:0 \
  --batch_size 8

Python API — Para Más Control

from lm_eval import evaluate, make_task
from lm_eval.api.model import LM

class CustomLM(LM):
    def __init__(self, model_path):
        # Tu implementación de inference
        self.model = load_model(model_path)
    
    def generate_until(self, requests):
        # Lógica de generación
        return [self._generate(req) for req in requests]
    
    def loglikelihood(self, requests):
        # Para tareas de elección múltiple
        return self._compute_logprobs(requests)

# Crear task desde YAML
task = make_task("tasks/medical-qa-es.yaml")

# Evaluar
results = evaluate(
    model=CustomLM("models/medical-llm"),
    tasks=[task],
    num_fewshot=5,
    limit=100  # Para testing rápido
)

Errores Comunes — Los Tres Pecados Capitales

Error 1: Evaluar Modelos "A Mano" — Sin Harness

El problema: Le preguntas 20 cosas al modelo, decides que "suena mejor" y publications resultados. Esto no es evaluación — es intuición disfrazada de data.

Los issues:

  • No reproducible — mañana puedes dar score diferente
  • Bias de confirmación — tiendes a recordar los casos que te gustaron
  • No comparable — ¿cómo comparas con otros modelos?
  • Sample size ridículamente pequeño — 20 samples vs 14,000 de MMLU

El fix: Usa lm-evaluation-harness. Siempre. Aunque sea para evaluation interna. Los beneficios:

# Es tan simple como esto
lm_eval \
  --model hf \
  --model_args pretrained=models/tu-modelo \
  --tasks mmlu,gsm8k,hellaswag \
  --device cuda:0 \
  --batch_size 16

Error 2: Confiar Ciegamente En Benchmark Results Ajenos

El problema: Ves que "modelo_X logra 72% en MMLU" en un paper y lo asumes verdadero sin verificar. Mal, muy mal.

Los benchmarks se pueden manipulatear:

  • Contaminación de datos: El modelo fue entrenado en preguntas similares
  • Evals diferentes: Algunos usan 5-shot, otros 0-shot — no son comparables
  • Metric gaming: Técnica de prompting para optimizar el benchmark sin mejorar el modelo real
  • Hardware diferente: Los resultados Reported vs lo que tú medirás

El fix: Siempre que puedas, replica la evaluación tú mismo. Si el paper no especifica exactamente la configuración, tenés desconfianza.

# Verifica con lm-evaluation-harness
# Usa exactamente la misma config que el paper reporta
lm_eval \
  --model hf \
  --model_args pretrained=modelo_X \
  --tasks mmlu \
  --num_fewshot 5 \
  --device cuda:0

Si no puedes replicar, al menos valida con un subset de tu dominio. Un paper que reporta 90% en MMLU pero no puede responder 3 preguntas de tu dominio específico tiene un problema.

Error 3: Solo Usar Benchmarks Populares — Sin Coverage de Dominio

El problema: MMLU, GSM8K, HumanEval — todos el mundo usa estos. Pero son benchmarks en inglés, hechos por gringos, para modelos entrenados en internet en general.

Si tu aplicación es:

  • Chatbot de soporte en español colombiano → MMLU no te dice nada
  • Sistema de análisis financiero → GSM8K no es relevante
  • Generador de código empresarial → HumanEval mide Python básico, no tu stack

Estás optimizando para benchmarks que no importan.

El fix: Crea tu propio evaluation harness con tasks de tu dominio. No tiene que ser complejo:

# tasks/finance-sentiment-es.yaml
task: finance_sentiment_es
dataset_path: my/finance-sentiment-spanish
output_type: multiple_choice

doc_to_text: "Clasifica el sentimiento: {{text}}"
doc_to_choice: ["positivo", "negativo", "neutral"]
doc_to_target: "{{label}}"

Y luego:

# Evalúa en tu benchmark específico
lm_eval \
  --model hf \
  --model_args pretrained=models/tu-modelo \
  --tasks finance_sentiment_es \
  --num_fewshot 3

Resumen y Cierre

lm-evaluation-harness no es solo para researchers. Es para cualquiera que necesite saber si su LLM realmente funciona bien — de manera reproducible y justifiable.

Hoy aprendimos:

  • Benchmarks estandarizados — MMLU, GSM8K, HumanEval, TruthfulQA tienen usos y limitaciones
  • Cómo usar el CLI — una línea para evaluar cualquier modelo
  • Custom tasks — YAML + Python API para tu dominio específico
  • Los tres errores fatales — evaluación a mano, confiar ciegamente, y solo benchmarks populares

La próxima vez que veas una tabla comparando LLMs, preguntá primero: "¿Cómo fue la evaluación?" Si la respuesta no incluye lm-evaluation-harness o algo similar, tomá esos números con pinzas.

Y bueno, parcero, eso es todo por hoy. Mañana seguimos con guardrails y validación de outputs — porque de nada sirve un modelo buenísimo si te devuelve JSON malformed a cada rato. ¡Hágale pues!
