Quantization Deep Dive: INT8, INT4, NF4, GPTQ, AWQ y la Compresión que el 70% Aplica Sin Entender Qué Pierde

Hagale pues, parcero. Día 245 y hoy nos metemos con un tema que el 70% de los practitioners aplican sin entender bien qué están haciendo: quantization. Ese proceso que reduce el modelo de 70B parámetros a algo que casi cabe en una GPU的消费. Después de este artículo va a saber exactamente qué está pasando cuando cuantiza un modelo, qué pierde en el camino, y cómo elegir el método correcto. Vamos con tune.

¿Qué Es Quantization y Por Qué Funciona?

La intuición detrás de quantization es simple: los modelos de deep learning usan números en formato float32 (32 bits por parámetro). Pero esos números no necesitan esa precisión para funcionar bien. La mayoría de redes neuronales son robustas a ruido numérico — pueden trabajar con menos bits sin perder comportamiento útil.

Visualmente, imagine que tiene una foto de 48 megapíxeles y la reduce a 0.3 megapíxeles. Detalles finos se pierden, pero usted todavía sabe qué es la foto. Eso es exactamente lo que hace quantization: reduce la "resolución" numérica del modelo.

La Formulación Matemática

En su forma más simple, quantization convierte valores continuos a un espacio discreto finito. Para un peso w en float32, definimos:

ŵ = round(w / s) - z

Donde:

  • s es el scale factor (factor de escala)
  • z es el zero point (punto cero para representar el 0 exactamente)
  • round() es la función de redondeo al entero más cercano

La decuantización (recuperar aproximación) es:

w ≈ ŵ · s + z

Para INT8 quantization (8 bits), mapeamos de [-127, 127]:

s = max(|W|) / 127

Para symmetric quantization (más común), z = 0, y los valores se distribuyen simétricamente alrededor del cero.

Tipos de Quantization: INT8, INT4, NF4

INT8: El Estándar de la Industria

INT8 usa 8 bits por parámetro — reduce el tamaño del modelo 4x comparado con float32. Es el formato más usado en producción porque:

  • La mayoría de hardware moderno (CPU, GPU NVIDIA con Tensor Cores) tiene soporte nativo para INT8
  • El speedup es significativo: 2-4x más throughput que float32
  • La pérdida de精度 es mínima para la mayoría de tareas

INT8 funciona bien para:

  • Modelos de 1B-13B parámetros
  • Tareas de generación de texto donde pequeñas variaciones no importan mucho
  • Aplicaciones donde la latencia es crítica

INT4: Compresión Agresiva

INT4 usa solo 4 bits por parámetro — reduce 8x comparado con float32. Esto permite que modelos de 70B quepan en ~35GB (dos GPUs de 24GB). Pero el tradeoff es significativo:

  • Loss de calidad mayor: Especialmente para tareas que requieren precisión numérica (cálculo, coding)
  • Outliers más problemáticos: Algunos valores extremos dominan y no se representan bien
  • Requiere calibración cuidadosa: Necesita más datos de calibración

INT4 es ideal para:

  • Modelos grandes (70B+) donde el tamaño es el bottleneck
  • Situaciones donde el modelo será usado para tareas menos sensibles a precisión
  • Prototyping y experimentación donde velocidad > calidad

NF4: Normal Float 4 — La Innovación de bitsandbytes

NF4 (Normal Float 4) es un formato introducido por Tim Dettmers en bitsandbytes que está diseñado específicamente para manejar la distribución de pesos de LLMs. La observación key es que los pesos de LLMs siguen una distribución normal-ish, con muchos valores pequeños y algunos outliers.

NF4 usa non-uniform quantization: en lugar de bins equidistantes, los bins están más juntos cerca del cero y más separados en las colas:

Los 16 niveles de NF4 están definidos por cuantiles de una distribución N(0,1):

NF4_bins = [-1.0, -0.6966, -0.5251, -0.3949, -0.2887, -0.2001, -0.1276, -0.0632, 0.0632, 0.1276, 0.2001, 0.2887, 0.3949, 0.5251, 0.6966, 1.0]

Esto permite representar mejor la distribución real de los pesos. En la práctica, NF4 produce resultados noticeably mejores que INT4 naive para la mayoría de LLMs.

Métodos de Quantization: GPTQ vs AWQ vs bitsandbytes

GPTQ: Post-Training Quantization Granular

GPTQ (Generative Pre-trained Transformer Quantization) es un método de post-training quantization desarrollado por Frantar et al. (2023). Funciona capa por capa, minimizando el error de reconstrucción.

La idea central es: para cada capa, encontrar los pesos cuantizados que minimizan el error con respecto a las activaciones originales.

La formulación: dado una capa con pesos W y activación de entrada X, queremos encontrar Ŵ (cuantizado) tal que:

Ŵ = argmin_Ŵ ||WX - ŴX||²

GPTQ usa layer-wise calibration: para cada capa, pasa un batch representativo de datos (típicamente 1024 tokens) y mide el error. El proceso:

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, GPTQConfig

# Cargar modelo base
model_name = "meta-llama/Llama-2-70b-hf"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    device_map="auto",
    torch_dtype=torch.float16,
)

# Configurar GPTQ para INT4
gptq_config = GPTQConfig(
    bits=4,
    dataset="c4",  # Dataset de calibración
    block_size=128,
    compile=False,
)

# Cuantizar (toma tiempo - procesa capa por capa)
quantized_model = AutoModelForCausalLM.from_pretrained(
    model_name,
    device_map="auto",
    quantization_config=gptq_config,
)

print(f"Tamaño original: {model.memory_visible_size() / 1e9:.2f} GB")
print(f"Tamaño cuantizado: {quantized_model.memory_visible_size() / 1e9:.2f} GB")

# Guardar
quantized_model.save_pretrained("./llama2-70b-gptq-4bit")
tokenizer.save_pretrained("./llama2-70b-gptq-4bit")

AWQ: Activation-Aware Weight Quantization

AWQ (Activation-Aware Weight Quantization) es un método desarrollado por Lin et al. (2024) que observa algo importante: no todos los pesos importan igual. Los pesos que correlacionan con altas activaciones ( outliers) son más importantes y deben quantizarse con menos error.

AWQ usa una heurística simple pero efectiva: los pesos con mayor magnitud de activación promedio deben tener bins de quantization más precisos. Esto se logra perturbando los pesos antes de cuantizar:

Ŵ = round(W · s) / s

Donde s se elige basado en las activaciones observadas.

from transformers import AutoModelForCausalLM, AutoTokenizer
from awq import AutoAWQForCausalLM

# Cargar modelo
model_name = "meta-llama/Llama-2-70b-hf"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16)

# Configurar AWQ
quant_config = {
    "zero_point": True,
    "q_group_size": 128,  # Grupo de cuantización
    "w_bit": 4,
    "version": "GEMM",    # GEMM es más rápido en GPU
}

# Cuantizar con AWQ
model.quantize(tokenizer, quant_config=quant_config)

# Guardar
model.save_pretrained("./llama2-70b-awq-4bit")
tokenizer.save_pretrained("./llama2-70b-awq-4bit")

bitsandbytes: INT8 + NF4 para PyTorch Nativo

bitsandbytes es la librería de Tim Dettmers que ofrece quantization integrado en PyTorch. Soporta INT8 estándar y NF4:

print(f"Modelo cargado en {model.hf_quantization_method}")

Precision vs Accuracy Tradeoff: ¿Cuánto Se Pierde?

Esta es la pregunta del millón: ¿cuánta precisión perdemos al cuantizar? La respuesta honesta es: depende.

Benchmarks Comparativos

Según estudios de Dettmers et al. (2023) y Lin et al. (2024):

  • FP16 → INT8: Pérdida mínima, típicamente <1% en benchmarks de generación. Prácticamente indistinguible.
  • FP16 → INT4 naive: Pérdida 3-8% en tasks de código y matemática. Notable en generación creativa.
  • FP16 → NF4: Pérdida 1-4% en tasks de código y matemática. Significantly mejor que INT4 naive.
  • FP16 → GPTQ-INT4: Similar a NF4, ~2-5% pérdida en tareas complejas.
  • FP16 → AWQ-INT4: AWQ generalmente outperforms GPTQ en ~1-2% en tareas de código.

Para tareas de summarization, chat, y preguntas abiertas, la pérdida es menos noticeable. Para tareas que requieren precisión matemática (código, cálculo), la pérdida puede ser problemática.

La Matemáticas del Error de Quantization

El error de quantization se puede expresar como:

ε = ||W - Ŵ||² / ||W||²

Para symmetric quantization con r niveles (e.g., 256 para INT8):

ε ≈ 1 / (3 · r²) (asumiendo distribución uniforme)

Para INT8: ε ≈ 1 / (3 · 256²) ≈ 0.000005 (muy pequeño)

Para INT4: ε ≈ 1 / (3 · 16²) ≈ 0.0013 (más significativo)

Pero esta estimación asume distribución uniforme. En la práctica, outliers hacen que el error sea mayor. NF4 mitiga esto parcialmente con bins no-uniformes.

Quantization-Aware Training (QAT)

Post-training quantization es conveniente pero subóptimo. Quantization-Aware Training (QAT) entrena el modelo simulando el efecto de quantization durante el training, lo que produce mejores resultados pero requiere más recursos.

La idea central: durante forward pass, simular quantization estrepitando los pesos a través de funciones de quantization differentiable (usando straight-through estimator):

import torch
import torch.nn as nn
import torch.nn.functional as F

class FakeQuantization(nn.Module):
    """
    Simula quantization durante el training.
    Usa straight-through estimator (STE) para hacer la operación diferenciable.
    """
    def __init__(self, num_bits=8):
        super().__init__()
        self.num_bits = num_bits
        self.num_levels = 2 ** num_bits
        self.register_buffer('scale', torch.tensor(1.0))
        self.register_buffer('zero_point', torch.tensor(0.0))
    
    def forward(self, x):
        # Calcular scale basado en el rango de x
        x_min = x.detach().min()
        x_max = x.detach().max()
        self.scale = (x_max - x_min) / (self.num_levels - 1)
        self.zero_point = x_min
        
        # Cuantizar
        x_quant = torch.round((x - self.zero_point) / self.scale)
        x_quant = torch.clamp(x_quant, 0, self.num_levels - 1)
        
        # Decuantizar (forward)
        x_dequant = x_quant * self.scale + self.zero_point
        
        # Straight-through estimator: en el backward, pasar gradientes como si
        # no hubiera quantization (esto hace que el gradient sea útil)
        return x_dequant + (x - x_dequant).detach()


class QATLinear(nn.Module):
    """Linear layer con quantization simulada para QAT."""
    def __init__(self, in_features, out_features, bias=True, num_bits=8):
        super().__init__()
        self.weight_fake_quant = FakeQuantization(num_bits)
        self.weight = nn.Parameter(torch.randn(out_features, in_features))
        self.bias = nn.Parameter(torch.zeros(out_features)) if bias else None
    
    def forward(self, x):
        # Aplicar fake quantization a los pesos
        weight_quant = self.weight_fake_quant(self.weight)
        return F.linear(x, weight_quant, self.bias)

QAT requiere:

  • Datos de training (no solo calibration)
  • Más tiempo de training (1-2x más)
  • Computación adicional por el forward pass con quantization

Pero produce modelos que mantienen más accuracy con quantization agresiva.

Cómo Evaluar Calidad de Quantization

Antes de desplegar un modelo cuantizado, necesita evaluar si la pérdida de calidad es aceptable. Esto es crítico — no confíe en el tamaño del archivo como proxy de calidad.

from transformers import AutoModelForCausalLM, AutoTokenizer
import torch
from tqdm import tqdm

def evaluate_model_quality(model, tokenizer, test_prompts, metrics=["perplexity", "accuracy"]):
    """
    Evalúa la calidad de un modelo cuantizado contra el original.
    """
    results = {}
    
    # Perplexity en un dataset de prueba
    if "perplexity" in metrics:
        test_text = " ".join(test_prompts[:100])  # Ajustar según necesidad
        inputs = tokenizer(test_text, return_tensors="pt").to(model.device)
        
        with torch.no_grad():
            outputs = model(inputs.input_ids, labels=inputs.input_ids)
            perplexity = torch.exp(outputs.loss).item()
        
        results["perplexity"] = perplexity
    
    # Generación para evaluación cualitativa
    if "generation" in metrics:
        sample_prompts = [
            "Explica la fotosíntesis en términos simples:",
            "Escribe una función en Python para calcular fibonacci:",
            "¿Cuál es la capital de Francia?",
        ]
        
        for prompt in sample_prompts:
            inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
            outputs = model.generate(
                inputs.input_ids,
                max_new_tokens=100,
                do_sample=True,
                temperature=0.7,
            )
            generated = tokenizer.decode(outputs[0], skip_special_tokens=True)
            print(f"\nPrompt: {prompt}")
            print(f"Respuesta: {generated}\n")
    
    return results


def compare_models(original_model, quantized_model, tokenizer, test_prompts):
    """
    Compara modelo original vs cuantizado side-by-side.
    """
    print("=" * 60)
    print("EVALUACIÓN COMPARATIVA: Original vs Cuantizado")
    print("=" * 60)
    
    # Tamaño
    original_size = original_model.get_memory_footprint() / 1e9
    quantized_size = quantized_model.get_memory_footprint() / 1e9
    compression = original_size / quantized_size
    
    print(f"\nTamaño Original: {original_size:.2f} GB")
    print(f"Tamaño Cuantizado: {quantized_size:.2f} GB")
    print(f"Ratio de Compresión: {compression:.1f}x")
    
    # Calidad
    print("\n--- Evaluación de Calidad ---")
    original_results = evaluate_model_quality(original_model, tokenizer, test_prompts)
    quantized_results = evaluate_model_quality(quantized_model, tokenizer, test_prompts)
    
    print("\n--- Comparación de Métricas ---")
    for metric in original_results:
        orig_val = original_results[metric]
        quant_val = quantized_results[metric]
        diff_pct = abs(orig_val - quant_val) / orig_val * 100
        print(f"{metric}: Original={orig_val:.4f}, Cuantizado={quant_val:.4f}, Diff={diff_pct:.2f}%")
    
    return original_results, quantized_results

Cómo Elegir el Método de Quantization

No existe un método universal. Aquí le dejo una guía práctica:

Matriz de Decisión

  • ¿Modelo < 13B y necesita latencia? → INT8 con bitsandbytes. Rápido, bueno, fácil.
  • ¿Modelo > 30B y tiene GPUs limitadas? → GPTQ-INT4 o AWQ-INT4. Reduce 8x con pérdida manejable.
  • ¿Modelo para código o matemática? → Prefiera AWQ-INT4 sobre INT4 naive, o use GPTQ-INT4 con dataset de calibración específico.
  • ¿Necesita fine-tuning posterior? → QLoRA con NF4 (bitsandbytes). Diseñado para esto.
  • ¿Produce en servidor con batch grande? → INT8 con TensorRT-LLM. Mejor throughput.

Checklist Antes de Cuantizar

  • ¿Tiene benchmark de referencia?: Mida quality del modelo original primero
  • ¿Qué tarea importa?: Code generation necesita más precisión que chat
  • ¿Cuál es su constraint?: Latencia vs throughput vs memoria
  • ¿Probará en hardware real?: Simular en CPU no predice comportamiento en GPU

Los 3 Errores Más Comunes al Cuantizar

Error 1: Asumir Que Quantization Siempre Preserva Calidad

El problema: Mucha gente cuantiza a INT4 y espera que el modelo "funcione igual". No es cierto. Hay tareas donde la pérdida de precisión causa degradación significativa.

Ejemplo real: Un modelo de 70B cuantizado a INT4 para generación de código puede producir funciones con errores sutiles de lógica que no notarías en chat pero que rompen producción.

La solución:

  • Siempre evaluar el modelo cuantizado contra el original en su tarea específica
  • Establecer un threshold mínimo de calidad (ej: no más de 5% degradación en accuracy)
  • Si la tarea es crítica (código en producción, decisiones financieras), considere INT8 o quedarse con FP16
# Ejemplo de validación rigorosa
def acceptance_test(original_model, quantized_model, task_benchmark):
    """
    Test de aceptación antes de desplegar modelo cuantizado.
    """
    threshold = 0.95  # No más de 5% degradación
    
    original_score = task_benchmark(original_model)
    quantized_score = task_benchmark(quantized_model)
    
    ratio = quantized_score / original_score
    
    if ratio < threshold:
        raise ValueError(
            f"Modelo cuantizado falla test de aceptación: "
            f"score={quantized_score:.4f} vs original={original_score:.4f} "
            f"(ratio={ratio:.2%}, threshold={threshold:.2%})"
        )
    
    return True

Error 2: No Evaluar Contra el Modelo Original

El problema: Se guía por perplexity en datasets genéricos (WikiText, etc.) que no reflejan su caso de uso. El modelo puede estar funcionando terriblemente en su tarea específica sin que se dé cuenta.

La solución:

  • Crear un benchmark específico para su caso de uso (prompts reales, outputs esperados)
  • Comparar tanto métricas automáticas como evaluación humana cuando sea posible
  • Probar con edge cases y inputs difíciles, no solo casos típicos

Error 3: Usar la Precisión Incorrecta Para su Hardware

El problema: INT4 naive en una CPU es más lento que FP16 porque la decuantización开销 overhead. O usar NF4 en hardware que no lo soporta nativamente.

La solución:

  • GPU NVIDIA con Tensor Cores: INT8 e INT4 con kernels optimizados (TensorRT-LLM, cuBLAS)
  • CPU: Preferir INT8 con SIMD (AVX-512), no INT4
  • Apple Silicon (M1/M2/M3): Usar la implementación de mlc-llm o llama.cpp con soporte nativo
  • Dispositivos móviles: NF4 no es ideal; considerar INT8 con quantized ops
import platform

def recommend_quantization_for_hardware():
    """
    Guía de selección de quantization según hardware.
    """
    system = platform.system()
    processor = platform.processor()
    
    recommendations = []
    
    if system == "Linux" and "NVIDIA" in processor:
        recommendations = [
            ("INT8", "TensorRT-LLM con kernels INT8", "Mejor balance speed/quality"),
            ("INT4", "AWQ o GPTQ con TensorRT", "Máxima compresión en GPU"),
            ("FP16", "Si tiene 80GB+ VRAM", "Máxima calidad"),
        ]
    elif system == "Darwin" and "arm" in processor:
        recommendations = [
            ("INT4", "mlc-llm o llama.cpp con Metal", "Mejor en Apple Silicon"),
            ("INT8", "Transformers con MPS", "Buen balance"),
        ]
    elif system == "Windows" or system == "Linux":
        recommendations = [
            ("INT8", "bitsandbytes o llama.cpp", "Mejor soporte CPU"),
            ("NF4", "Solo si hace fine-tuning (QLoRA)", "Para training"),
        ]
    
    return recommendations

Los puntos clave:

  • Quantization reduce precisión numérica para ganar eficiencia en tamaño y velocidad
  • INT8 es el sweet spot para la mayoría de casos — 4x compresión con pérdida mínima
  • INT4/NF4 son para cuando necesita más compresión y puede tolerar algo de degradación
  • GPTQ y AWQ son métodos de post-training con diferentes fortalezas
