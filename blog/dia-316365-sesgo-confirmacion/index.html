Reward Modeling - Ensenando A Modelos Que Es Bueno

12 de noviembre de 2026
reward-modelingrlhftrainingalignment

🤔 Por Qué Necesitamos Reward Modeling

Antes de entrenar un modelo con RLHF (Reinforcement Learning from Human Feedback), necesitamos algo crucial: una función que nos diga qué respuestas son "buenas" y cuáles son "malas". Pero aquí está el problema — ¿cómo definimos "bueno" de manera computable?

Reward modeling es el proceso de entrenar un modelo que aprende a predecir la "bondad" de una respuesta. Este modelo nos permite:

  • Escalar el feedback: En lugar de depender de humanos para cada evaluación, usamos el modelo para predecir preferencias.
  • Optimizar directamente: Podemos usar el reward model como señal para optimizar el policy con RL.
  • Consistencia: Un reward model bien entrenado es más consistente que humanos variando en sus juicios.

📊 El Proceso de Recolectar Datos de Preferencia

El primer paso es recolectar datos. Dados prompts $x$, generamos pares de respuestas $(y_1, y_2)$ del modelo actual, y pedimos a anotadores humanos que Indiquen cuál prefieren. El formato típico es:

  • Prompt: "Explica qué es la fotosíntesis"
  • Response A: "La fotosíntesis es cuando las plantas usan luz del sol para hacer comida."
  • Response B: "La fotosíntesis es el proceso bioquímico mediante el cual organismos autótrofos convierten energía luminosa en energía química, específicamente a través de la fijación de CO₂ y la síntesis de carbohidratos."
  • Preference: B (más completa y técnicamente precisa)

La clave aquí es que las preferencias humanas son el gold standard. Un reward model exitoso debe aprender a predecir estas preferencias.

🏗️ Arquitectura del Reward Model

El reward model típico es una red que toma un prompt y una respuesta, y outputting un scalar que representa la "bondad" de esa respuesta. La arquitectura más común es:

class RewardModel(nn.Module):
    def __init__(self, base_model: nn.Module, reward_head: nn.Linear):
        super().__init__()
        self.base_model = base_model
        self.reward_head = reward_head
        # Usar solo el hidden state final para clasificación
        # (o pooling sobre todos los tokens)
    
    def forward(self, input_ids: torch.Tensor, attention_mask: torch.Tensor) -> torch.Tensor:
        # Get hidden states
        outputs = self.base_model(
            input_ids=input_ids,
            attention_mask=attention_mask
        )
        
        # Extraer el hidden state del último token (como en BERT)
        last_hidden_state = outputs.last_hidden_state
        
        # Pooling: usar solo el primer token [CLS] o el último
        # Aquí usamos el último token (típico para GPT-like models)
        sequence_output = last_hidden_state[:, -1, :]
        
        # Calcular reward
        reward = self.reward_head(sequence_output)
        return reward

📐 La Función de Loss para Predecir Preferencias

El training del reward model se basa en la Bradley-Terry model, que asume que las preferencias humanas pueden modelarse como:

$$P(y_1 \succ y_2 | x) = \sigma(r(x, y_1) - r(x, y_2))$$

donde $r(x, y)$ es el reward predicho para el prompt $x$ y respuesta $y$, y $\sigma$ es la función sigmoid.

El loss entonces es:

$$\mathcal{L} = -\mathbb{E}_{(x, y_w, y_l) \sim D} \left[ \log \sigma( r_\theta(x, y_w) - r_\theta(x, y_l) ) \right]$$

donde $y_w$ es la respuesta preferida (winner) e $y_l$ es la menos preferida (loser).

def reward_model_loss(
    reward_model: RewardModel,
    chosen_ids: torch.Tensor,
    rejected_ids: torch.Tensor,
    chosen_mask: torch.Tensor,
    rejected_mask: torch.Tensor
) -> torch.Tensor:
    """
    Calcular loss para pairwise ranking.
    
    Args:
        reward_model: El modelo de reward a entrenar
        chosen_ids: Tokens de la respuesta elegida
        rejected_ids: Tokens de la respuesta rechazada
        chosen_mask: Attention mask para respuesta elegida
        rejected_mask: Attention mask para respuesta rechazada
    """
    # Forward pass para ambas respuestas
    chosen_reward = reward_model(chosen_ids, chosen_mask)
    rejected_reward = reward_model(rejected_ids, rejected_mask)
    
    # Calcular loss usando la fórmula de Bradley-Terry
    # P(elegida > rechazada) = sigmoid(reward_elegida - reward_rechazada)
    reward_diff = chosen_reward - rejected_reward
    
    # Log loss: -log(sigmoid(reward_diff))
    loss = -F.logsigmoid(reward_diff).mean()
    
    # Bonus: también podemos agregar un término de margin
    # para asegurar que la diferencia sea significativa
    margin_loss = F.relu(1.0 - reward_diff).mean()
    
    return loss + 0.1 * margin_loss

⚠️ Desafíos y Pitfalls Comunes

Entrenar reward models es tricky. Aquí van los errores más comunes:

1. Overfitting a Annotator Preferences

Si tienes pocos annotadores, el reward model puede aprender sesgos individuales en lugar de preferencias generalizables. La solución es tener diversidad en los annotadores y usar técnicas de debiasing.

2. Reward Hacking

El modelo aprendrá a maximizar el reward model, no necesariamente a ser realmente mejor. Esto puede llevar a respuestas que "suenan" bien pero son incorrectas o vacías.

3. Feedback Inconsistente

Si las etiquetas humanas tienen alta variabilidad, el modelo no podrá aprender patrones claros. La solución es usar workflows de anotación redundante y medir agreement entre annotadores.

🔄 Cómo Usar el Reward Model en RLHF

Una vez que tenemos un reward model entrenado, lo usamos para optimizar el policy con algoritmos como PPO. El workflow típico es:

  • Generar respuestas: Usando el policy actual, generar múltiples respuestas para cada prompt.
  • Evaluar con reward model: Obtener el reward estimado para cada respuesta.
  • Optimizar con PPO: Usar el reward model como señal de reward para actualizar el policy.
class RLHFTrainer:
    def __init__(self, policy_model, reward_model, ref_model, ppo_config):
        self.policy = policy_model
        self.reward_model = reward_model
        self.ref_model = ref_model  # Modelo de referencia para KL penalty
        self.ppo_config = ppo_config
    
    def compute_rewards(self, prompts, responses):
        """Computar rewards usando el reward model."""
        rewards = []
        for prompt, response in zip(prompts, responses):
            # El reward incluye dos partes:
            # 1. Reward del modelo
            reward = self.reward_model(prompt, response)
            rewards.append(reward)
        return rewards
    
    def compute_kl_penalty(self, prompts, responses):
        """Computar KL penalty contra el modelo de referencia."""
        kl_penalties = []
        for prompt, response in zip(prompts, responses):
            # Calcular log probs del policy actual vs reference
            log_prob_current = self.policy.log_prob(response, prompt)
            log_prob_ref = self.ref_model.log_prob(response, prompt)
            kl_penalty = log_prob_ref - log_prob_current
            kl_penalties.append(kl_penalty)
        return kl_penalties
    
    def step(self, prompts, responses):
        """Un paso de actualización PPO."""
        # 1. Computar rewards del reward model
        rewards = self.compute_rewards(prompts, responses)
        
        # 2. Computar KL penalty contra referencia
        kl_penalties = self.compute_kl_penalty(prompts, responses)
        
        # 3. Combinar: reward final = reward_model - beta * KL
        final_rewards = [r - self.ppo_config.beta * kl for r, kl in zip(rewards, kl_penalties)]

📈 Métricas para Evaluar Reward Models

Algunas métricas importantes para evaluar si tu reward model está funcionando bien:

  • Accuracy de predicción de preferencias: Qué tan bien predice las preferencias humanas en el test set.
  • Correlation con juicios humanos: Spearman o Pearson correlation entre rewards predichos y ratings humanos.
  • Consistencia: El reward model debería dar rewards más altos a respuestas claramente mejores.

🏁 Cierre

Reward modeling es un componente crítico de RLHF que nos permite escalar el feedback humano y optimizar modelos de manera efectiva. La clave está en recolectar buenos datos de preferencia, entrenar un modelo que capture preferencias genuinas, y ser consciente de los pitfalls como reward hacking y overfitting a annotadores específicos.
