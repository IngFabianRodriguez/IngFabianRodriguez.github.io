Mixture of Experts - La arquitectura que el 80% confunde con ensemble methods

16 de may de 2026
transformers

Hola, parcero. Día 166 y hoy vamos con Mixture of Experts (MoE). El 80% confunde MoE con ensemble methods como Random Forest o XGBoost. Son arquitecturas fundamentalmente diferentes. Vamos a entender por qué MoE es una arquitectura de red neuronal y no un algoritmo de ensemble, y por qué modelos como Mixtral y GPT-4 usan esta arquitectura.

🧠 MoE No Es Ensemble — La Diferencia Fundamental

La confusión viene de que ambos usan múltiples "componentes" para hacer predictions. Pero ahí termina el parecido:

Ensemble Methods (Random Forest, XGBoost, etc.)

  • Cada modelo entrena independently sobre los mismos datos
  • Todos los modelos ven TODOS los inputs
  • Predicción final: voting (bagging) o weighted average (boosting)
  • Los modelos pueden ser cualquier algoritmo: árboles, redes neuronales, etc.

Mixture of Experts (MoE)

  • Cada expert es una parte de la misma red, no un modelo independiente
  • Cada input solo activa UN SUBCONJUNTO de experts (sparse activation)
  • Un router/decider decide qué experts procesan cada input
  • Todo se entrena end-to-end jointly — los experts y el router aprenden en conjunto

La diferencia clave en notación matemática:

$$\text{Ensemble: } y = \frac{1}{N}\sum_{i=1}^{N} f_i(x)$$

$$\text{MoE: } y = \sum_{i=1}^{N} G(x)_i \cdot E_i(x)$$

Donde $G(x)$ es el gate que selecciona qué experts activar, y $E_i(x)$ es la salida del expert $i$. La suma es ponderada por el gate, no uniforme.

🏗️ Arquitectura de un MoE Layer

Un layer de MoE en un transformer consiste en:

  • $N$ Expert Networks: cada uno es una FFN (Feed-Forward Network)
  • 1 Router Network: una capa lineal que decide qué experts activar
  • Top-K Gating: solo los k experts más relevantes procesan el input
import torch
import torch.nn as nn

class MoELayer(nn.Module):
    def __init__(self, d_model, n_experts, top_k):
        super().__init__()
        self.n_experts = n_experts
        self.top_k = top_k
        
        # Los experts son FFNs independientes
        self.experts = nn.ModuleList([
            nn.Sequential(
                nn.Linear(d_model, d_model * 4),
                nn.ReLU(),
                nn.Linear(d_model * 4, d_model)
            )
            for _ in range(n_experts)
        ])
        
        # El router decide qué experts activar
        self.router = nn.Linear(d_model, n_experts)
    
    def forward(self, x):
        # x shape: [batch, seq_len, d_model]
        batch_size, seq_len, d_model = x.shape
        
        # Flatten para procesamiento eficiente
        x_flat = x.view(-1, d_model)  # [batch*seq_len, d_model]
        
        # Router: calcula logits para cada expert
        router_logits = self.router(x_flat)  # [batch*seq_len, n_experts]
        
        # Top-K gating: selecciona los k experts más relevantes
        top_k_logits, top_k_indices = torch.topk(router_logits, self.top_k, dim=-1)
        
        # Softmax sobre los top-k para obtener pesos
        top_k_weights = torch.softmax(top_k_logits, dim=-1)  # [batch*seq_len, top_k]
        
        # Inicializar output
        output = torch.zeros_like(x_flat)
        
        # Procesar cada token con sus top-k experts
        for i in range(self.top_k):
            expert_idx = top_k_indices[:, i]  # índices de expert para cada token
            expert_weight = top_k_weights[:, i]  # peso para cada token
            
            # Acumular contribuciones de cada expert
            for expert_id in range(self.n_experts):
                mask = (expert_idx == expert_id)
                if mask.any():
                    expert_output = self.experts[expert_id](x_flat[mask])
                    output[mask] += expert_weight[mask].unsqueeze(-1) * expert_output
        
        return output.view(batch_size, seq_len, d_model)

📊 Por Qué MoE-scale Efficiently

El poder de MoE viene del sparse activation. Para un modelo densos:

$$\text{FLOPs por token} = 2 \times N_{\text{layers}} \times d_{\text{model}}^2$$

Con MoE (usando top-k = 2 de n_experts = 8):

$$\text{FLOPs por token} = 2 \times N_{\text{layers}} \times \left(\frac{k}{N_{\text{experts}}} \cdot d_{\text{model}}^2 + d_{\text{model}} \cdot d_{\text{router}}\right)$$

La diferencia en práctica:

ArquitecturaParámetros TotalesFLOPs por TokenActivos por Token
Dense 7B7B~70BTodos

Dense 70B70B~700BTodos

El modelo MoE tiene más parámetros totales pero menos compute por token. Esto es exactamente lo que queremos: la capacidad de un modelo grande con el costo de uno pequeño.

⚠️ Problemas Técnicos de MoE

Problema 1: Load Balancing

Si el router siempre activa los mismos experts, esos experts reciben más training y se vuelven "experts dominantes". Esto defeats el propósito.

class LoadBalancingLoss(nn.Module):
    """Auxiliary loss para balancear uso de experts"""
    def __init__(self, n_experts):
        super().__init__()
        self.n_experts = n_experts
        self.target_load = 1.0 / n_experts  # distribución uniforme
    
    def forward(self, router_probs, expert_mask):
        # router_probs: probabilidades del router
        # expert_mask: qué experts fueron seleccionados
        
        # Calcular load real de cada expert
        expert_load = expert_mask.sum(0) / expert_mask.sum()
        
        # Calcular bias del router
        router_bias = router_probs.mean(0)
        
        # Loss: penaliza desviación de distribución uniforme
        # Minimizar: sum(|load - target|) + sum(|bias - target|)
        load_loss = torch.abs(expert_load - self.target_load).sum()
        bias_loss = torch.abs(router_bias - self.target_load).sum()
        
        return load_loss + bias_loss

Problema 2: Communication Overhead

En setting distribuido (multi-GPU), los experts pueden estar en diferentes devices. El router necesita comunicar qué experts activar.

Problema 3: Memory Efficiency

Aunque el compute por token es menor, todos los parámetros siguen en memoria. Un MoE 8x7B requiere ~56B parámetros en VRAM aunque proceses como un 7B.

🔍 MoE vs Ensemble Methods: La Confusion Explicada

La confusión principal:

  • Random Forest: N árboles independientes, todos ven todos los datos, voting final
  • MoE: 1 red neuronal con N sub-redes (experts), sparse activation, el router decide quién procesa

Otra forma de verlo:

  • Ensemble: múltiples modelos completos copiando la tarea
  • MoE: una modelo que divide la tarea entre expertos especializados

En MoE, los experts pueden especializarse en diferentes aspectos:

  • GPT-4 (rumored): предположительно MoE con ~1.8T parámetros totales
  • Switch Transformer: Google's MoE con hasta 2048 experts
  • ST-MoE: Stable Training of MoE
  • DBRX: Databricks' MoE model

🏁 Resumen

  • MoE ≠ Ensemble: ensemble combina modelos completos, MoE divide una red en expertos
  • Sparse activation: solo top-k experts procesan cada token
  • Eficiencia computacional: más parámetros totales, menos FLOPs por token
  • Load balancing: necesita auxiliary loss para evitar expertos dominantes
  • Communication overhead: en setting distribuido, los experts en diferentes GPUs necesitan comunicarse
  • Todos los parámetros en memoria: el modelo completo sigue ocupando VRAM aunque procese sparse
