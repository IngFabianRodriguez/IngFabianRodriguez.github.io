Dia 219/365: Experiment Tracking — la centralita de F1 que separa al mecanico del mago

7 de agosto de 2026
mlflow, wandb

Introduccion: cuando el modelo que ayer sabia, hoy se le olvido

Tres meses despues de cerrar la v2 de tu pipeline de clasificacion, llega la alerta: el AUC en produccion cayo 4 puntos. Abres el repo, miras el ultimo commit, lees el script de entrenamiento y no aparece ni la semilla de numpy, ni el hash del dataset, ni la version de scikit-learn. Tienes 47 notebooks con model_v15_FINAL_definitivo.ipynb y tres de ellos producen modelos distintos con el mismo nombre. No es ficcion, parce, es lo que pasa en el 70% de los equipos que carecen de un sistema de tracking. La metrica que observas en produccion es funcion de seis variables que no estas midiendo: hiperparametros, datos, codigo, ambiente, semillas aleatorias y artefactos. Experiment Tracking no es un lujo de MLOps, es la telemetria que te permite saber cual de esas variables se rompio cuando el modelo se rompio. En este articulo voy a mostrarte que es, como se formaliza, y como MLflow + W&B lo resuelven sin que termines reinventando la rueda con archivos JSON en una carpeta compartida.

1. Que es Experiment Tracking? (Y por que deberia importarte)

1.1 La analogia cotidiana: el mecanico de F1 y la centralita del carro

Mira, la mejor forma de entender esto es con un carro de Formula 1. Cada equipo corre con mas de 300 sensores transmitiendo a 100 Hz: temperatura de neumaticos, presion de aceite, presion de freno por rueda, angulo de direccion, flujo de combustible, marcha actual, posicion en pista. Toda esa informacion va a una centralita que la guarda con timestamp. ¿Por que? Porque cuando el carro se va al muro en la curva 9, el ingeniero de pista no especula: abre la telemetria, retrocede segundo a segundo, y encuentra el sensor que se desvio primero. Luego compara esa curva contra el mismo sensor en las 14 carreras anteriores. La reproducibilidad no es opcional en F1: cada carrera se corre con reproducciones casi exactas una de la otra. Experiment Tracking es la centralita de tu modelo de ML. Si no la tienes, cuando el modelo se quiebra en produccion estas adivinando.

1.2 La matematica formal

Formalizemos un experimento como la tupla

$$e = (\theta, D, h, m, A)$$

Donde cada componente es:

  • $\theta \in \mathbb{R}^p$ — vector de hiperparametros (learning rate, regularizacion, batch size, etc).
  • $D$ — version del dataset, identificada por su hash $H(D)$ (por ejemplo, SHA-256 del CSV o del parquet). En MLflow seria un input tag o un tag arbitrario; en W&B seria el artifact versionado.
  • $h: \text{code} \rightarrow \{0,1\}^{256}$ — hash del codigo de entrenamiento. Garantiza que dos runs con el mismo $h$ ejecutaron codigo identico bit a bit.
  • $m: \mathbb{N} \rightarrow \mathbb{R}^k$ — trayectoria de metricas. Cada paso $t$ produce un vector $m(t) = (m_1(t), \dots, m_k(t))$.
  • $A$ — conjunto de artefactos (modelos serializados, plots, archivos de configuracion).

La condicion de reproducibilidad es: dos runs $e_1, e_2$ producen el mismo modelo si y solo si $\theta_1 = \theta_2$, $H(D_1) = H(D_2)$, $h_1 = h_2$ y el PRNG arranca con la misma semilla. Sin tracking, la entropia del estado oculto del run es maxima y no puedes reconstruir $m(t)$ ni $A$. Con tracking, reduces esa entropia a cero porque el sistema se vuelve una maquina de estado finito $S(e)$.

Una metrica central es el Coste de Reproduccion:

$$C_{\text{repro}}(e) = -\log_2 P(\text{reproducir } e \mid \text{observaciones disponibles})$$

Si tienes las seis variables observadas, $C_{\text{repro}}(e) = 0$. Si te falta el codigo hash, $C_{\text{repro}}(e)$ se dispara porque existen $\binom{n}{k}$ combinaciones a probar en el espacio de busqueda.

2. Como MLflow resuelve esto por vos

MLflow parte de tres almacenes desacoplados:

Componente Proposito Implementacion tipica
Backend Store Metadata del run (params, tags, metricas) SQLite local, Postgres, MySQL
Artifact Store Archivos grandes (modelos, plots) Filesystem local, S3, GCS, Azure Blob
Tracking Server API REST unificada mlflow server

El flujo es: cuando ejecutas mlflow.start_run(), el cliente abre una conexion HTTP con el tracking server, el server escribe metadata en el backend store y los artefactos en el artifact store. La URI de tracking separa el servidor: http://host:5000 para el server, postgresql://... para el backend store, s3://bucket/path para artifacts. La matematica del sistema se modela como una composicion:

$$\text{Run}_i = (m_i, p_i, a_i, t_i) \quad \text{donde} \quad m_i \in \mathbb{R}^k, p_i \in \mathbb{R}^p, a_i \in \mathcal{A}, t_i \in \mathbb{N}$$

donde $\mathcal{A}$ es el espacio de artefactos y $t_i$ es el timestamp ISO-8601. Cada mlflow.log_metric(key, value, step=t) proyecta $m_i$ en su dimension temporal, generando la serie $m_i(t_0), m_i(t_1), \dots$ que termina en el dashboard.

El registro de modelos (MLflow Model Registry) agrega una capa adicional: cada modelo registrado tiene un stage (Staging, Production, Archived) y un historial de transiciones. Esto te permite hacer rollback sin reentrenar.

3. W&B: Uso Directo y Casos de Control Fino

W&B sigue la misma filosofia pero con un modelo de datos ligeramente distinto. Cada wandb.init(project, name, config) crea un run dentro de un project, y wandb.log({key: value}, step=epoch) empuja metricas al servidor. La diferencia operativa es que W&B registra automaticamente gradientes y pesos si pasas watch(model, log="all"). Tambien tiene artefact versioning nativo (tipo Git LFS) y Sweeps como hyperparameter optimization de primera clase.

import os
import wandb

os.environ["WANDB_API_KEY"] = "<your-key>"

run = wandb.init(
    project="fraud-detection",
    name="xgboost-v3-C=1.0",
    config={
        "model": "xgboost",
        "n_estimators": 500,
        "max_depth": 6,
        "learning_rate": 0.05,
        "subsample": 0.8,
        "random_state": 42,
    },
    tags=["baseline", "no-smote"],
)

for epoch in range(50):
    train_loss, val_auc, val_logloss = train_one_epoch(...)
    wandb.log({
        "train/loss": train_loss,
        "val/auc": val_auc,
        "val/logloss": val_logloss,
    }, step=epoch)

run.log_model("model.joblib", "fraud-model")
wandb.finish()

Si necesitas control fino, W&B te deja definir metricas custom (wandb.define_metric("epoch")), configurar alertas (wandb.alert(title="AUC drop", text=...)) y crear reports reproducibles desde la UI.

4. Implementacion Production-Ready: UnifiedTracker

4.1 Tipos y protocolos

from dataclasses import dataclass, field
from typing import Any, Optional, Protocol

@dataclass(frozen=True)
class RunConfig:
    experiment_name: str
    run_name: str
    params: dict[str, Any]
    tags: dict[str, str] = field(default_factory=dict)

class Backend(Protocol):
    def start(self, cfg: RunConfig) -> None: ...
    def log_metric(self, key: str, value: float, step: Optional[int] = None) -> None: ...
    def log_metrics(self, metrics: dict[str, float], step: Optional[int] = None) -> None: ...
    def log_artifact(self, path: str) -> None: ...
    def finish(self, status: str = "FINISHED") -> None: ...

RunConfig congela los parametros via frozen=True, garantizando que nadie los muta despues de crear el run. El Protocol Backend te permite cambiar de adaptador sin tocar el resto del codigo (Liskov friendly).

4.2 El motor principal

import os
import mlflow
import wandb


class ExperimentTracker:
    """Adaptador unificado sobre MLflow y W&B."""

    def __init__(self, backend: str, **kwargs) -> None:
        if backend not in ("mlflow", "wandb"):
            raise ValueError("backend debe ser 'mlflow' o 'wandb'")
        self.backend = backend
        self._run: Any = None
        if backend == "mlflow":
            mlflow.set_tracking_uri(kwargs["tracking_uri"])
        elif backend == "wandb":
            api_key = kwargs.get("api_key") or os.environ.get("WANDB_API_KEY")
            if api_key:
                wandb.login(key=api_key)

    def start(self, cfg: RunConfig) -> None:
        if self.backend == "mlflow":
            mlflow.set_experiment(cfg.experiment_name)
            self._run = mlflow.start_run(run_name=cfg.run_name)
            mlflow.log_params({k: str(v) for k, v in cfg.params.items()})
            mlflow.set_tags(cfg.tags)
        else:
            self._run = wandb.init(
                project=cfg.experiment_name,
                name=cfg.run_name,
                config=cfg.params,
                tags=[f"{k}={v}" for k, v in cfg.tags.items()],
                reinit=True,
            )

    def log_metric(self, key: str, value: float, step: Optional[int] = None) -> None:
        if self.backend == "mlflow":
            mlflow.log_metric(key, float(value), step=step)
        else:
            self._run.log({key: float(value)}, step=step)

    def log_metrics(self, metrics: dict[str, float], step: Optional[int] = None) -> None:
        if self.backend == "mlflow":
            mlflow.log_metrics({k: float(v) for k, v in metrics.items()}, step=step)
        else:
            self._run.log({k: float(v) for k, v in metrics.items()}, step=step)

    def log_artifact(self, path: str) -> None:
        if self.backend == "mlflow":
            mlflow.log_artifact(path)
        else:
            wandb.save(path, base_path=os.path.dirname(path) or ".")

    def finish(self, status: str = "FINISHED") -> None:
        if self.backend == "mlflow":
            mlflow.end_run(status=status)
        else:
            wandb.finish()

4.3 Utilidades de analisis y verificacion

import pandas as pd


def list_runs(tracker: ExperimentTracker, experiment_name: str) -> pd.DataFrame:
    """Devuelve todos los runs del experimento como DataFrame."""
    if tracker.backend == "mlflow":
        client = mlflow.tracking.MlflowClient()
        exp = client.get_experiment_by_name(experiment_name)
        runs = client.search_runs(
            experiment_ids=[exp.experiment_id],
            max_results=10_000,
            order_by=["start_time DESC"],
        )
        rows = []
        for r in runs:
            row = {"run_id": r.info.run_id, "start_time": r.info.start_time}
            row.update({f"param.{k}": v for k, v in r.data.params.items()})
            row.update({f"metric.{k}": v for k, v in r.data.metrics.items()})
            rows.append(row)
        return pd.DataFrame(rows)
    else:
        api = wandb.Api()
        runs = api.runs(f"{api.default_entity}/{experiment_name}")
        return pd.DataFrame([{
            "run_id": r.id,
            "name": r.name,
            **{f"param.{k}": v for k, v in r.config.items()},
            **{f"metric.{k}": v for k, v in (r.summary or {}).items()},
        } for r in runs])


def best_run(df: pd.DataFrame, metric_col: str, mode: str = "max") -> pd.Series:
    """Encuentra el mejor run segun una metrica."""
    if mode == "max":
        idx = df[metric_col].idxmax()
    else:
        idx = df[metric_col].idxmin()
    return df.loc[idx]

5. Ejemplos de Uso en Casos Reales

Caso 1: Sweep de regularizacion en regresion logistica

import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler


tracker = ExperimentTracker(
    backend="mlflow",
    tracking_uri="sqlite:///./experiments.db",
)

X, y = load_breast_cancer(return_X_y=True)
C_grid = [0.001, 0.01, 0.1, 1.0, 10.0, 100.0]

for C in C_grid:
    cfg = RunConfig(
        experiment_name="breast-cancer-lr",
        run_name=f"lr-C={C}",
        params={"model": "LogisticRegression", "C": C, "solver": "lbfgs"},
        tags={"stage": "baseline"},
    )
    tracker.start(cfg)

    pipe = Pipeline([
        ("scaler", StandardScaler()),
        ("clf", LogisticRegression(C=C, max_iter=2000, random_state=42)),
    ])
    scores = cross_val_score(pipe, X, y, cv=5, scoring="accuracy")

    for fold, score in enumerate(scores):
        tracker.log_metric("cv_accuracy_fold", float(score), step=fold)
    tracker.log_metrics({
        "cv_accuracy_mean": float(scores.mean()),
        "cv_accuracy_std": float(scores.std()),
    })
    tracker.finish()

df = list_runs(tracker, "breast-cancer-lr")
print(best_run(df, "metric.cv_accuracy_mean", mode="max"))

Verificacion numerica: con $C = 1.0$ y 5-fold CV, la accuracy media esperada en breast cancer es $\approx 0.978 \pm 0.012$. Si tu corrida reporta $0.82$, el tracking funciona bien pero los datos cambiaron o el scaler no se aplico. Ahi el tracking cumple su funcion: te dice donde NO esta el problema.

Caso 2: Red neuronal pequena con logging de gradientes

import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.data import DataLoader
from torchvision import datasets, transforms


tracker = ExperimentTracker(backend="wandb")
cfg = RunConfig(
    experiment_name="mnist-classifier",
    run_name="cnn-3conv-v1",
    params={"lr": 1e-3, "batch_size": 64, "epochs": 3, "weight_decay": 1e-4},
)
tracker.start(cfg)


class SmallCNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv1 = nn.Conv2d(1, 16, 3, padding=1)
        self.conv2 = nn.Conv2d(16, 32, 3, padding=1)
        self.fc = nn.Linear(32 * 7 * 7, 10)

    def forward(self, x):
        x = F.relu(self.conv1(x))
        x = F.max_pool2d(x, 2)
        x = F.relu(self.conv2(x))
        x = F.max_pool2d(x, 2)
        x = x.view(x.size(0), -1)
        return self.fc(x)


device = "cuda" if torch.cuda.is_available() else "cpu"
model = SmallCNN().to(device)
opt = torch.optim.Adam(
    model.parameters(),
    lr=cfg.params["lr"],
    weight_decay=cfg.params["weight_decay"],
)

if tracker.backend == "wandb":
    wandb.watch(model, log="gradients", log_freq=100)

ds = datasets.MNIST("./data", train=True, download=True,
                    transform=transforms.ToTensor())
loader = DataLoader(ds, batch_size=cfg.params["batch_size"], shuffle=True)

global_step = 0
for epoch in range(cfg.params["epochs"]):
    model.train()
    for x, y in loader:
        x, y = x.to(device), y.to(device)
        opt.zero_grad()
        loss = F.cross_entropy(model(x), y)
        loss.backward()
        opt.step()
        global_step += 1
        tracker.log_metric("train/loss", float(loss.item()), step=global_step)

tracker.finish()

wandb.watch(model, log="gradients") envia histogramas de gradientes cada 100 steps, permitiendote detectar exploding o vanishing gradients sin instrumentar el codigo manualmente.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: el run aparece en la UI pero no tiene metricas

Sintoma tipico: ves el run en el dashboard pero el grafo de loss esta vacio. La causa frecuente es que log_metric se llamo fuera del contexto start_run().

# MAL — esto NO se loggea a MLflow
tracker.start(cfg)
some_loss = train_one_epoch()
tracker.finish()
tracker.log_metric("train/loss", some_loss)  # run ya cerrado, se ignora

Deteccion: MLflow no levanta excepcion consistente. Verifica el run activo con:

active = mlflow.active_run()
if active is None:
    print("No hay run activo, las metricas se perdieron")

Solucion: pon try / finally para garantizar el cierre y emitir todos los logs:

try:
    tracker.start(cfg)
    for epoch in range(epochs):
        tracker.log_metric("loss", loss, step=epoch)
finally:
    tracker.finish()

Problema 2: W&B reporta Failed to detect git repository

W&B intenta capturar el estado del repositorio git por defecto. Si corres desde una carpeta que no es repo, falla en silencio. Soluciones:

wandb.init(
    project="...",
    settings=wandb.Settings(git=None),  # desactivar captura de git
    config=cfg.params,
)

Si necesitas el estado de git pero el script se invoca desde un directorio sin .git, usa dir="path/to/repo" o invocalo desde el repo raiz.

Problema 3: dos runs "iguales" producen modelos diferentes

Esto es la plaga del no-tracking. La reproducibilidad requiere fijar todas las fuentes de entropia:

import os
import random
import numpy as np
import torch

def seed_everything(seed: int = 42) -> None:
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)
    os.environ["PYTHONHASHSEED"] = str(seed)
    torch.backends.cudnn.deterministic = True
    torch.backends.cudnn.benchmark = False

Y registralo en tracking:

tracker.log_params({
    "seed": 42,
    "numpy_version": np.__version__,
    "torch_version": torch.__version__,
    "python_version": sys.version.split()[0],
    "cuda_available": torch.cuda.is_available(),
})

Si despues de esto los pesos siguen siendo distintos entre runs, el problema esta en datos no deterministicos: un DataLoader con num_workers > 0 lee batches en orden no deterministico. Resuelve con worker_init_fn=lambda wid: np.random.seed(np.random.get_state()[1][0] + wid).

7. Optimizaciones de Produccion

Optimizacion 1: batching de metricas para reducir overhead

mlflow.log_metrics escribe a la red en cada llamada. Si tienes loops con 5k steps, eso es latencia pura. La solucion es agrupar:

buffer: list[tuple[str, float]] = []

def flush(step: int) -> None:
    if buffer:
        mlflow.log_metrics(dict(buffer), step=step)
        buffer.clear()

for step in range(5000):
    loss, acc = compute_one_step(...)
    buffer.append(("loss", float(loss)))
    buffer.append(("accuracy", float(acc)))
    if len(buffer) >= 20:
        flush(step)
flush(step)

W&B ya hace batching automatico si usas wandb.log({...}), y la latencia no suele ser problema. MLflow con Postgres remoto + batching manual reduce overhead en ~5x comparado con logging naive.

Optimizacion 2: separar backend y artifact store para escalar

En produccion evita SQLite como backend store. Usa Postgres:

mlflow server \
  --backend-store-uri postgresql://user:pass@host:5432/mlflow \
  --default-artifact-root s3://my-bucket/mlflow-artifacts \
  --host 0.0.0.0 \
  --port 5000

Esto te permite cientos de runs concurrentes sin bloqueo del backend y artefactos distribuidos en S3 sin copiar binarios grandes a la maquina del trainer. Latencia adicional por la red se compensa con la paralelizacion del serving.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

Cadena de valor resumida:

  • Reproducibilidad: con tracking, $C_{\text{repro}}(e) = 0$. Sin tracking, es exponencial.
  • Comparabilidad: dos runs se comparan por $(\theta, D, h, m)$ sin ambiguedad. Sin tracking, comparas por nombre de archivo.
  • Rollback: Model Registry te permite promover y archivar versiones sin redeployar.
  • Auditoria: cualquier modelo en produccion lleva el historial de transiciones y el run que lo genero.

Mini-checklist antes de cerrar un experimento:

  • [ ] seed_everything(42) ejecutado y parametros loggeados
  • [ ] Hash de codigo y dataset registrados como tags (git_hash, dataset_sha256)
  • [ ] Artefacto del modelo final guardado en registry
  • [ ] Metricas de train y validacion con el mismo step index
  • [ ] Configuracion de ambiente (requirements.txt o environment.yml) como artifact

La diferencia entre un equipo que escala ML en produccion y uno que queda embalado depurando modelos perdidos a las 3am no es el algoritmo. Es la centralita. Sin tracking, rezas. Con tracking, depuras. Hagale pues, montala hoy. 🏎️
