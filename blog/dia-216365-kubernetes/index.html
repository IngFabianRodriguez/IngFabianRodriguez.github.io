Data Validation Con Great Expectations — El Quality Guard Que Tu Pipeline Necesita

Eso pasa mucho en ML cuando entrenamos modelos con datos de baja calidad sin siquiera saberlo. Hoy: Great Expectations, el guardián de calidad que tu pipeline necesita. Dejala ahí la开口, que esto está interesante.

🎯 Qué Es Great Expectations?

Great Expectations (GX) es una biblioteca Python open-source para validar, documentar y profilear datos. Básicamente, le dices a tus datos "espero que luzcan así", y GX te avisa cuando no es el caso. Es como tener un filtro de calidad automático en tu pipeline de datos.

Conceptos fundamentales:

  • Expectation: Una aserción sobre tus datos (ej: "esta columna no puede ser null", "este valor debe estar entre 0 y 100")
  • Expectation Suite: Colección de expectations que aplicas a un dataset
  • Checkpoint: Objeto que ejecuta una suite contra datos específicos y genera un resultado
  • Data Docs: Documentación automática en HTML con los resultados de la validación
  • Profiler: Analiza tus datos y sugiere expectations automáticamente basadas en lo que ve

📐 La Matemática De La Validación De Datos

Una expectation es esencialmente una función booleana sobre tu dataset:

Expectation(data) → {True, False, None (error)}

Cuando la expectativa falla, no solo obtienes un True/False — obtienes un resultado rico con:

  • El número de filas que cumplieron vs fallaron
  • Las filas específicas que fallaron (si pides detail)
  • El tipo de falla (¿null? ¿out of range? ¿type mismatch?)
  • La excepción capturada si hubo error en la validación

La matemática de los checks más comunes:

# Column presence: todas las columnas en la lista existen
expect_columns_to_match_set(df, column_set) → bool

# Null check: porcentaje de nulos menor a threshold
expect_column_values_to_not_be_null(df, col, mostly=0.95) → dict con success, partial_unexpected_list

# Range check: valores dentro de min/max
expect_column_values_to_be_between(df, col, min_value=0, max_value=100) → dict

# Uniqueness: sin duplicados
expect_column_values_to_be_unique(df, col) → bool

# Distribution: distribución aproximadamente normal
expect_column_stdev_to_be_between(df, col, min_stdev=0.5, max_stdev=10.0) → bool

🚀 Implementando Data Validation Con Great Expectations

1. Configuración Inicial y Primer Expectation Suite

import great_expectations as gx
from great_expectations.dataset import PandasDataset

# Crear o abrir un Data Context (el manage principal de GX)
context = gx.get_context()

# Crear un Expectation Suite
expectation_suite = context.add_expectation_suite(
    expectation_suite_name="customer_data_quality"
)

# Crear expectations sobre un DataFrame
df = pd.read_parquet("data/customer_data.parquet")

# Expectation Suite básica
suite = expectation_suite.add_expectation(
    expectation_type="expect_column_values_to_not_be_null",
    kwargs={"column": "customer_id", "mostly": 1.0}
)

suite.add_expectation(
    expectation_type="expect_column_values_to_be_between",
    kwargs={
        "column": "account_age_days",
        "min_value": 0,
        "max_value": 36500  # ~100 años max
    }
)

suite.add_expectation(
    expectation_type="expect_column_distributions_to_be_match",
    kwargs={
        "column": "credit_score",
        "distribution": "norm",
        "params": {"mean": 650, "stddev": 50}
    }
)

# Guardar la suite
context.save_expectation_suite(expectation_suite)

2. Profiling Automático: Dejar Que GX Descubra Tus Datos

from great_expectations.profile import PandasProfiler

# El profiler analiza el DataFrame y sugiere expectations basadas en lo que ve
profiler = PandasProfiler(df)

# Genera un Expectation Suite con expectativas basadas en los datos reales
suggested_suite = profiler.build_suite()

# Esto sugiere expectations como:
# - expect_column_mean_to_be_between (basado en el mean real)
# - expect_column_min_to_be_greater_than (basado en el min real)
# - expect_column_values_to_be_in_set (para columnas categóricas)
# - expect_column_stdev_to_be_between (basado en la desviación real)

# Muy útil como punto de partida antes de definir expectativas de negocio

3. Checkpoints: Ejecutar Validación En Tu Pipeline

# Crear un Checkpoint que ejecuta la suite contra datos reales
checkpoint = context.add_checkpoint(
    name="customer_data_checkpoint",
    run_name_template="%Y%m%d-%H%M%S-customer-validation",
    expectation_suite_name="customer_data_quality",
    batch_request={
        "datasource_name": "files_datasource",
        "data_asset_name": "customer_data.parquet",
    }
)

# Ejecutar el checkpoint
results = checkpoint.run()

# results es un dict con:
# - success: True/False
# - run_id: timestamp de la ejecución
# - validation_results: detalles de cada expectation
# - actions_results: qué pasó (ej: Data Docs actualizado, alerta enviada)

if not results["success"]:
    print("⚠️ VALIDACIÓN FALLIDA")
    for result in results["results"]:
        if not result["success"]:
            print(f"  ❌ {result['expectation_config']['expectation_type']}: {result['result']}")

4. Integración En ML Pipeline (Airflow/Kubernetes)

# snippet_airflow.py - Integración con Apache Airflow
from airflow.operators.python import PythonOperator
from great_expectations.checkpoint import SimpleCheckpoint

def validate_training_data(**context):
    """
    Se ejecuta antes de cada entrenamiento.
    Si falla la validación, no inicia el training.
    """
    context_gx = gx.get_context()
    
    checkpoint = SimpleCheckpoint(
        name="training_data_checkpoint",
        data_context=context_gx,
        expectation_suite_name="training_data_quality",
        batch_request={
            "datasource_name": "s3_datasource",
            "data_asset_name": "training_data.parquet",
        },
        action_list=[
            {"name": "store_validation_result", "action": {"class_name": "StoreValidationResultAction"}},
            {"name": "update_data_docs", "action": {"class_name": "UpdateDataDocsAction"}},
            {"name": "send_slack_notification_on_failure", 
             "action": {"class_name": "SlackNotificationAction", 
                       "slack_webhook": "{{ var.value.slack_webhook }}"}},
        ]
    )
    
    result = checkpoint.run()
    
    if not result["success"]:
        raise ValueError(f"Data validation failed: {result}")
    
    return result

# En tu DAG de Airflow:
# validate_data >> train_model >> evaluate_model >> deploy_model

⚠️ Los 3 Errores Más Costosos

Error 1: Entrenar Con Datos De Baja Calidad Sin Saberlo

El problema: Coges un dataset de 1 millón de filas, lo metes a tu modelo, entrenas por 3 días, y al final descubres que el 15% de las filas tenían account_balance = -999999 (valor placeholder para missing). Tu modelo aprendió un patrón que no existe. O peor: el 30% de tus labels estaban invertidos por un bug en el ETL de la semana pasada. En Colombia: "el que no checks data, después llora".

El fix: Implementar data validation ANTES del entrenamiento. No después. La regla es simple: si la validación falla, el pipeline de entrenamiento no inicia. GX te permite definir expectations de negocio (no solo técnicas) y fail-fast cuando algo está mal.

# ANTES de procesar para entrenamiento:
validation_result = checkpoint.run()

# Expectation de ejemplo: "espero que credit_score tenga distribución normal"
# y que el 95% de valores estén entre 300 y 850

# Si esto falla, no se ejecuta el entrenamiento
assert validation_result["success"], "Datos no cumplen calidad minima"

Error 2: No Validar El Schema De Datos Nuevos

El problema: El equipo上游 cambia el schema de la tabla source (agrega una columna, renombra otra, cambia un tipo de int a float) y tu pipeline de ML sigue funcionando tranquilamente pero ahora tiene columnas que no esperaba o tipos que no coinciden. El modelo entrena con datos malformados y produce predicciones silenciosamente degrade. En Colombia: "del agua mansa me libró Dios, pero del agua que no se ve".

El fix: GX tiene expectations específicas para schema validation:

# Validar que el schema es exactamente lo que esperas
suite.add_expectation(
    expectation_type="expect_table_columns_to_match_ordered_list",
    kwargs={
        "column_list": ["customer_id", "account_age_days", "credit_score", 
                        "transaction_count_30d", "label"]
    }
)

# Validar tipos de datos
suite.add_expectation(
    expectation_type="expect_column_values_to_be_of_type",
    kwargs={"column": "customer_id", "type_": "int64"}
)

suite.add_expectation(
    expectation_type="expect_column_values_to_be_of_type",
    kwargs={"column": "credit_score", "type_": "float64"}
)

# Validar que no hay columnas inesperadas
suite.add_expectation(
    expectation_type="expect_table_columns_to_not_match_ordered_list",
    kwargs={
        "column_list": ["_meta_timestamp", "processing_id", "uuid_extra"]
        # estas columnas NO deberían existir (son de之前的ETL)
    }
)

Error 3: Data Validation Como One-Time Check En Vez De Continuous Monitoring

El problema: Hiciste data validation al inicio del proyecto, pasó, y nunca más se ejecutó. El dataset de producción cambia semanalmente sin que nadie lo sepa. Un día tu modelo empieza a degrade y no entiendes por qué — hasta que descubres que hace 3 semanas el equipo de ingeniería cambió el sistema de tracking y ahora todas las fechas vienen en formato UNIX en vez de ISO. La validación one-time es como ir al médico solo una vez en la vida. En Colombia: "quien se enferma por falta de médico, su culpa es".

El fix: La validación debe ser continua, no esporádica. Esto significa:

  • En pre-training: Ejecutar checkpoint antes de cada entrenamiento
  • En pre-inference: Validar features antes de pasarlas al modelo
  • Monitoreo en producción: Data Observability tools (Monte Carlo, Great Expectations Cloud, Dataplex) que detectan drift y anomalías
  • Alertas automáticas: Slack/email cuando una validación falla
# Ejemplo: validación continua en un job schedule
schedule interval='0 6 * * *'  # diario a las 6am

def daily_data_quality_check():
    """
    Se ejecuta diariamente.
    Valida el dataset nuevo.
    Si falla, alerta a Slack y NO envía a producción.
    """
    result = checkpoint.run()
    
    # Generar Data Docs con resultados
    context.build_data_docs()
    
    # Enviar notificación a Slack
    if not result["success"]:
        send_slack_alert(
            channel="#ml-alerts",
            message=f"⚠️ Data Quality Check Falló: {result['run_id']}"
        )
        return False
    
    send_slack_alert(
        channel="#ml-alerts", 
        message=f"✅ Data Quality Check Pasó: {result['run_id']}"
    )
    return True
