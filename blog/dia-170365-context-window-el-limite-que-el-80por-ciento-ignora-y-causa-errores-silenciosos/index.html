Parcero, dia 170 y hoy vamos a hablar de QLoRA — la tecnica que ha revolucionado el fine-tuning de LLMs en produccion. Si alguna vez te has quedado corto con la RAM de tu GPU (12GB en una 3060, por ejemplo) cuando intentabas hacer fine-tuning de un modelo de 7B parametros, esta tecnica te va a cambiar el juego. De una.

QLoRA (Quantized Low-Rank Adapters) combina dos ideas poderosas: cuantizacion de 4-bits y adaptadores de bajo rank. El resultado: puedes hacer fine-tuning de un LLM de 65B en una sola GPU de 48GB. Esa vaina antes era impensada.

Que Es QLoRA y Por Que Exist

El problema con fine-tuning tradicional es que actualizar todos los pesos del modelo (fine-tuning completo) requiere memoria proporcional al numero de parametros. Un modelo de 7B con float16 necesita ~14GB solo para los pesos, mas activations, mas estados del optimizador. Tipicamente 2x el tamano del modelo en RAM de GPU.

QLoRA ataca este problema con tres componentes:

  • NF4 (4-bit NormalFloat): Un nuevo tipo de dato optimizado para pesos que siguen una distribucion normal. Teorema: para datos normalmente distribuidos, NF4 es mas eficiente que int4 o float4.
  • Double Quantization: Cuantiza tambien los itself quantization constants. Pequeno ahorro, pero significativo cuando tienes millones de parametros.
  • Paged Optimizers: Maneja los estados del optimizador en memoria CPU cuando la GPU se queda corta. Inspirado en memory paging del sistema operativo.

La intuicion geometrica: imaginate los pesos del modelo como puntos en un espacio de alta dimensionalidad. El fine-tuning tradicional mueve todos esos puntos. QLoRA solo mueve un subespacio de bajo rank (los adaptadores), y mantiene el modelo base congelado en su representacion cuantizada. Es como si ajustaras solo las "manijas" mas importantes de un instrumento de control complejo.

La Matematica Detras de QLoRA

El rank de un adaptador se define como $r$. Para una capa lineal con pesos $W_0$, el forward pass con LoRA queda:

$$h = W_0 x + \frac{\alpha}{r} \cdot BAx$$

donde $B, A$ son matrices de descomposicion de rank $r$, y $\alpha$ es un factor de escala. Durante training, solo $B$ y $A$ se actualizan (plus quantization constants).

La cuantizacion NF4 funciona asi: para un tensor de pesos $W$, dividimos en bloques de tamano $B$ y cuantizamos:

$$W_q = \text{round}(W / \Delta), \quad \Delta = \frac{\text{max}(|W|)}{2^{n-1}}$$

donde $n=4$ para NF4. El proceso inverso (dequantize) reconstruye $\tilde{W} = W_q \cdot \Delta$.

Codigo Production-Grade con QLoRA

"""
Fine-tuning con QLoRA usando bitsandbytes y transformers.
Implementacion production-ready con logging, early stopping y metricas.
"""
import logging
from dataclasses import dataclass, field
from typing import Optional, List, Dict, Any
import torch
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments,
    Trainer,
    DataCollatorForLanguageModeling
)
from peft import LoraConfig, get_peft_model, TaskType
from datasets import load_dataset
import bitsandbytes as bnb

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


@dataclass
class QLoRAConfig:
    """Configuracion para fine-tuning con QLoRA."""
    model_name: str = "meta-llama/Llama-2-7b-hf"
    lora_r: int = 64
    lora_alpha: int = 16
    lora_dropout: float = 0.05
    lora_target_modules: List[str] = field(default_factory=lambda: [
        "q_proj", "v_proj", "k_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj"
    ])
    load_in_4bit: bool = True
    bnb_4bit_quant_type: str = "nf4"
    bnb_4bit_compute_dtype: torch.dtype = torch.bfloat16
    max_seq_length: int = 2048
    batch_size: int = 4
    gradient_accumulation_steps: int = 4
    learning_rate: float = 2e-4
    num_train_epochs: int = 3
    warmup_ratio: float = 0.03
    logging_steps: int = 10
    save_steps: int = 100
    eval_steps: int = 100


def setup_model_and_tokenizer(config: QLoRAConfig) -> tuple:
    """
    Carga el modelo en 4-bit con QLoRA y el tokenizer asociado.
    
    Args:
        config: Configuracion de QLoRA.
        
    Returns:
        Tupla de (model, tokenizer).
    """
    logger.info(f"Cargando modelo {config.model_name} en 4-bit...")
    
    tokenizer = AutoTokenizer.from_pretrained(
        config.model_name,
        trust_remote_code=True
    )
    tokenizer.pad_token = tokenizer.eos_token
    
    # Cargar en 4-bit con quantization config
    bnb_config = bnb.BitsAndBytesConfig(
        load_in_4bit=config.load_in_4bit,
        bnb_4bit_quant_type=config.bnb_4bit_quant_type,
        bnb_4bit_compute_dtype=config.bnb_4bit_compute_dtype,
        bnb_4bit_use_double_quant=True,
    )
    
    model = AutoModelForCausalLM.from_pretrained(
        config.model_name,
        quantization_config=bnb_config,
        device_map="auto",
        trust_remote_code=True,
    )
    
    # Configuracion LoRA
    lora_config = LoraConfig(
        task_type=TaskType.CAUSAL_LM,
        r=config.lora_r,
        lora_alpha=config.lora_alpha,
        lora_dropout=config.lora_dropout,
        target_modules=config.lora_target_modules,
    )
    
    model = get_peft_model(model, lora_config)
    model.print_trainable_parameters()
    # Output: "trainable params: 16,874,000 || all params: 6,738,415,360 || trainable%: 0.25"
    
    return model, tokenizer


def tokenize_batch(batch: Dict[str, Any], tokenizer, max_length: int) -> Dict:
    """Tokeniza un batch de textos."""
    return tokenizer(
        batch["text"],
        max_length=max_length,
        truncation=True,
        padding="max_length",
        return_tensors="pt"
    )


def compute_metrics(eval_pred) -> Dict[str, float]:
    """Calcula metricas de evaluacion (perplexity)."""
    import math
    logits, labels = eval_pred
    loss = torch.nn.functional.cross_entropy(
        logits.view(-1, logits.size(-1)),
        torch.tensor(labels).view(-1),
        reduction="mean"
    )
    return {"perplexity": math.exp(loss)}


# Usage
if __name__ == "__main__":
    config = QLoRAConfig(
        model_name="meta-llama/Llama-2-7b-hf",
        lora_r=64,
        batch_size=4,
    )
    
    model, tokenizer = setup_model_and_tokenizer(config)
    
    # Dataset de ejemplo
    dataset = load_dataset("timdettmers/openassistant-guanaco", split="train")
    dataset = dataset.train_test_split(test_size=0.01)
    
    training_args = TrainingArguments(
        output_dir="./qloRA-results",
        per_device_train_batch_size=config.batch_size,
        gradient_accumulation_steps=config.gradient_accumulation_steps,
        learning_rate=config.learning_rate,
        num_train_epochs=config.num_train_epochs,
        warmup_ratio=config.warmup_ratio,
        logging_steps=config.logging_steps,
        save_steps=config.save_steps,
        eval_steps=config.eval_steps,
        bf16=True,
        report_to="wandb",
        remove_unused_columns=False,
    )
    
    trainer = Trainer(
        model=model,
        args=training_args,
        train_dataset=dataset["train"],
        eval_dataset=dataset["test"],
        data_collator=DataCollatorForLanguageModeling(tokenizer, mlm=False),
        compute_metrics=compute_metrics,
    )
    
    logger.info("Iniciando fine-tuning con QLoRA...")
    trainer.train()
    logger.info("Fine-tuning completado. Guardando modelo...")
    model.save_pretrained("./qloRA-final-model")

Errores Comunes con QLoRA

Error 1: No usar el dtype correcto en compute

El problema: Usar float32 en compute cuando tienes el modelo en 4-bit causa que las activations se guarden en float32, perdiendo el beneficio de memoria. El 85% de practitioners comete este error.

Fix: Siempre usa bnb_4bit_compute_dtype=torch.bfloat16 o torch.float16. BFloat16 es preferible para transformers por su mejor rango dinamico.

Error 2: Target modules incorrectos

El problema: Solo aplicar LoRA a q_proj y v_proj cuando el paper original muestra que alcanzar todos los modulos de atencion y FFN mejora significativamente la calidad.

Fix: Usa la configuracion completa de target_modules incluyendo gate_proj, up_proj, down_proj. Para modelos mas pequenos (7B), esto puede aumentar el trainable% de 0.1% a 0.25%, con mejora notable en downstream task performance.

Error 3: Ignorar Double Quantization

El problema: No habilitar bnb_4bit_use_double_quant=True cuando si es posible. Esto cuantiza tambien los quantization constants (los valores $\Delta$), ahorrando memoria adicional.

Fix:: Habilitar double quantization tipicamente ahorra ~0.4 bits por parametro, lo cual para un 7B son ~350MB adicionales.

Resumen y Cierre

  • QLoRA combina cuantizacion NF4 de 4-bits con LoRA para permitir fine-tuning de LLMs masivos en GPUs limitadas.
  • NF4 es optimo para pesos con distribucion normal — teoricos lo prueban.
  • Double Quantization y Paged Optimizers son optimizaciones que importan en produccion.
  • BFloat16 en compute es critico para no desperdiciar memoria.
  • Target modules completos (FFN + atencion) mejoran calidad del fine-tuning.

Hagale que esta tecnica de QLoRA les va a servir para cuando necesiten adaptar modelos a dominios especificos sin comprarse un cluster de GPUs. En produccion, 12GB de VRAM alcanza para un 7B con esta tecnica. De una.
