Momentum y Learning Rate Scheduling - El Acelerón que Evita que tu Red se Atasque en Mínimos Locales

2 de marzo de 2026

Parcero, ¿cuántas veces has visto que el learning rate de tu modelo se queda pegado y no converge? O al revés: que empieza bien y de repente explota. Eso casi siempre es un problema de schedule, no de optimizer. El learning rate schedule es el ingrediente que el 85% de los tutoriales ignora porque "añadir cosine annealing sounds complicated". Después de 12 años entrenando modelos, te cuento que 5 puntos de bleu solo cambiando el schedule me voló la cabeza. Hoy: momentum y los schedules que el 85% no sabe que existen.

## 🎯 ¿Qué Es el Momentum y Por Qué el 85% No Lo Entiende? Momentum es conceptualmente simple pero matemáticamente sutil. La idea: el gradiente de cada step no debería tell us completamente qué dirección tomar — debería matter la historia de los últimos steps. Físicamente: imaginá una pelota rodando por una superficie de pérdida. Si solo usas el gradiente actual, la pelota se detiene en cada pequeña perturbación del terreno. Con momentum, la pelota acumula "velocidad" — si ha estado rodando en una dirección consistentemente, sigue en esa dirección aunque el gradiente instantáneo diga otra cosa. **Tipos de momentum que el 85% confunde:** - **Vanilla Momentum**: Acumula velocidad en la dirección del gradiente. $v_t = \gamma v_{t-1} + \eta g_t$ - **Nesterov (NAG)**: "Mira adelante" antes de actualizar — converge más rápido en la práctica. Imaginá que vas en bicicleta下山 (pendiente abajo): con vanilla momentum, frenás cuando ves el obstáculo; con Nesterov, mirás dónde vas a estar después de la frenada y frenás ahí. ## 📐 Momentum y Learning Rate Scheduling — LA JOYA El learning rate schedule responde a una pregunta: **¿cómo varía $\eta$ a lo largo del entrenamiento?** La respuesta default del 85% es "no varía" — LR fijo. Esto esproblemático porque: 1. Al inicio, la red está en una región de alta curvatura — LR alto puede causar overshoot 2. Cerca del óptimo, LR bajo permite precisión — LR alto causa oscilaciones 3. En la zona plana (plateau), necesitamos LR alto para move out ### Momentum — La Física del Entrenamiento $$ v_t = \gamma v_{t-1} + \eta \nabla_\theta \mathcal{L}(\theta_t) $$ $$ \theta_{t+1} = \theta_t - v_t $$ **"Descomposición símbolo por símbolo..."** - $v_t$ = velocidad acumulada en step $t$ - $\gamma$ = factor de decay (típicamente 0.9) — pesa la historia - $\eta$ = learning rate base - $\nabla_\theta \mathcal{L}(\theta_t)$ = gradiente actual El término $\gamma v_{t-1}$ acumula 10 steps de historia con weights exponencialmente decay. Direcciones con gradientes consistentemente altos reciben "boost"; direcciones erráticas se promedian hacia zero. ### Nesterov Accelerated Gradient — El Lookahead El vanilla momentum calcula el gradiente en $\theta_t$ y actualiza hacia $v_t$. Nesterov calcula el gradiente en $\theta_t - \gamma v_{t-1}$ — "mira adelante" antes de actualizar: $$ v_t = \gamma v_{t-1} + \eta \nabla_\theta \mathcal{L}(\theta_t - \gamma v_{t-1}) $$ $$ \theta_{t+1} = \theta_t - v_t $$ ### Warmup — El Primer Paso Crítico Antes de cualquier schedule, tenés que hacer warmup. Empezar con LR ultra bajo y ramp linear al LR objetivo en los primeros $N$ steps: $$ \eta_t = \eta_{max} \cdot \frac{t}{N}, \quad t \leq N $$ ¿Por qué? Porque al inicio los parámetros están random y los gradientes pueden ser enormes. Adam con warmup evita que los primeros updates sejam erráticos. ### Cosine Annealing — El Standard Actual El LR decae suavemente siguiendo una curva coseno desde $\eta_{max}$ hasta $\eta_{min}$: $$ \eta_t = \eta_{min} + \frac{1}{2}(\eta_{max} - \eta_{min})\left(1 + \cos\left(\frac{t\pi}{T}\right)\right) $$ Beneficio: decaimiento suave que no causa cliffs, y encuentra mínimos más flat que step decay. ### OneCycle / Super-Convergence Leslie Smith demostró que podés entrenar CNNs 10x más rápido. Start con LR bajo → subir a LR_max en ~30% del training → bajar a LR_min en el remainder: $$ \eta_t = \eta_{min} + (\eta_{max} - \eta_{min}) \cdot \min\left(1, \frac{t}{0.3T}\right) \quad (t < 0.3T) $$ 
"""
LR Schedules comparison para #365DaysOfAI - Día 76
Producción-grade: warmup, cosine, step, polynomial decay.
"""
import logging
import math
import numpy as np
import torch
import torch.nn as nn
from dataclasses import dataclass
from typing import Literal

logger = logging.getLogger(__name__)


@dataclass
class LRScheduleConfig:
    """Configuración de schedule con defaults research-proven."""
    warmup_steps: int = 4000
    total_steps: int = 100_000
    max_lr: float = 3e-4
    min_lr: float = 1e-5
    schedule_type: Literal['cosine', 'linear', 'sqrt', 'polynomial', 'step'] = 'cosine'
    step_size: int = 30_000
    step_gamma: float = 0.1
    poly_order: int = 2


class LRScheduleFactory:
    """Factory para crear learning rate schedules."""
    
    @staticmethod
    def create(optimizer, config: LRScheduleConfig):
        """Crea scheduler desde config."""
        total_steps = config.total_steps
        warmup_steps = config.warmup_steps

        def lr_lambda(step: int) -> float:
            # Warmup phase
            if step < warmup_steps:
                return float(step) / float(max(1, warmup_steps))
            
            # Decay phase
            progress = float(step - warmup_steps) / float(
                max(1, total_steps - warmup_steps)
            )
            progress = min(1.0, progress)
            
            if config.schedule_type == 'cosine':
                # Cosine annealing — el standard para transformers
                cosine_decay = 0.5 * (1 + math.cos(math.pi * progress))
                return config.min_lr + (config.max_lr - config.min_lr) * cosine_decay
            
            elif config.schedule_type == 'linear':
                # Linear decay
                return config.max_lr - (config.max_lr - config.min_lr) * progress
            
            elif config.schedule_type == 'sqrt':
                # Square root decay — más LR al final que cosine
                sqrt_decay = 1.0 / math.sqrt(max(step, warmup_steps))
                max_decay = 1.0 / math.sqrt(warmup_steps)
                return config.max_lr * sqrt_decay / max_decay
            
            elif config.schedule_type == 'polynomial':
                # Polynomial decay (poly_order=2 es similar a cosine)
                poly = (1.0 - progress) ** config.poly_order
                return config.min_lr + (config.max_lr - config.min_lr) * poly
            
            elif config.schedule_type == 'step':
                # Step decay — simple pero discontinuo
                cycles = step // config.step_size
                return config.max_lr * (config.step_gamma ** cycles)
            
            else:
                return config.max_lr

        scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, lr_lambda)
        logger.info(
            f"Schedule created: {config.schedule_type}, "
            f"warmup={warmup_steps}, max_lr={config.max_lr}"
        )
        return scheduler


class ConvergenceMonitor:
    """Monitor de convergencia para detectar problemas."""
    
    def __init__(self, window: int = 100, patience: int = 5):
        self.window = window
        self.patience = patience
        self.loss_history: list[float] = []
        self.lr_history: list[float] = []
        self._plateau_count = 0
    
    def log(self, step: int, loss: float, lr: float) -> None:
        """Registra un step de entrenamiento."""
        self.loss_history.append(loss)
        self.lr_history.append(lr)
        
        # Detectar plateau
        if len(self.loss_history) > self.window:
            recent_avg = np.mean(self.loss_history[-self.window:])
            prev_avg = np.mean(self.loss_history[-2*self.window:-self.window])
            if abs(recent_avg - prev_avg) < 1e-6:
                self._plateau_count += 1
            else:
                self._plateau_count = 0
    
    def is_plateau(self) -> bool:
        """Detecta si estamos en un plateau."""
        return self._plateau_count >= self.patience
    
    def smoothed_loss(self, w: int | None = None) -> float:
        """Loss promediada en los últimos w steps."""
        w = w or self.window
        recent = self.loss_history[-w:]
        return sum(recent) / len(recent) if recent else float('inf')


# ─── Ejemplo de uso ───────────────────────────────────────────────────────────
if __name__ == '__main__':
    model = nn.Sequential(
        nn.Linear(512, 256),
        nn.ReLU(),
        nn.Linear(256, 10),
    )
    
    # Crear optimizer y scheduler
    optimizer = torch.optim.AdamW(
        model.parameters(),
        lr=3e-4,
        weight_decay=0.01
    )
    
    config = LRScheduleConfig(
        warmup_steps=2000,
        total_steps=50_000,
        schedule_type='cosine'
    )
    scheduler = LRScheduleFactory.create(optimizer, config)
    
    # Simular entrenamiento
    monitor = ConvergenceMonitor(window=100, patience=5)
    
    for step in range(50_000):
        # ... training loop ...
        lr = scheduler.get_last_lr()[0]
        
        if step % 5000 == 0:
            print(f"Step {step:>6}: LR = {lr:.2e}")
## 🚨 Errores Comunes (y Cómo No Cagarla) **Error 1: Cosine sin warmup** **El problema**: El 85% copia la configuración de un paper que dice "cosine annealing" pero no se da cuenta de que el paper también tenía warmup. Un cosine que empieza desde step 0 con LR=max puede ser tan errático como LR fijo alto. ❌ ```python # Cosine SIN warmup — los primeros steps pueden explotar scheduler = torch.optim.lr_scheduler.CosineAnnealingLR( optimizer, T_max=100_000, eta_min=1e-6 ) for step in range(100_000): # Step 0: LR = max_lr (3e-4) — puede causar gradient explosion optimizer.step() scheduler.step() ``` **Por qué falla**: Al inicio, los pesos son random y los gradientes pueden ser 100x más grandes que después de algunos updates. Empezar con LR alto = overshoot inmediato. $$ \theta_{t+1} = \theta_t - \eta_{max} \cdot \nabla \mathcal{L} \quad \text{(sin warmup, t=0)} $$ ✓ ```python # Warmup + cosine — el standard para transformers config = LRScheduleConfig( warmup_steps=4000, # 4K steps de ramp-up total_steps=100_000, max_lr=3e-4, schedule_type='cosine' ) scheduler = LRScheduleFactory.create(optimizer, config) ``` --- **Error 2: LR demasiado alto en el plateau** **El problema**: Cuando la loss entra en un plateau, el LR fijo sigue siendo "alto" para esa región. La red se estanca. Muchos practitioners simplemente esperan más epochs creyendo que el modelo "está casi ahí". ❌ ```python # LR fijo — se atasca en plateaus optimizer = torch.optim.Adam(model.parameters(), lr=1e-3) for epoch in range(100): train(model) # Si loss no baja en epoch 10, va a seguir igual ``` **Por qué falla**: Un plateau tiene curvatura casi zero. Con LR alto, el gradiente es pequeño relativo al step size, así que la red "rueda" lentamente sin dirección clara. $$ \theta_{t+1} - \theta_t \approx \eta \cdot g_t \quad \text{con } g_t \approx 0 \Rightarrow \text{no hay progreso} $$ ✓ ```python # Monitor de plateau con reducción automática monitor = ConvergenceMonitor(window=100, patience=5) for step in range(total_steps): loss = train_step(model, optimizer, batch) lr = scheduler.get_last_lr()[0] monitor.log(step, loss, lr) if monitor.is_plateau(): # Reducir LR manualmente o usar ReduceLROnPlateau for param_group in optimizer.param_groups: param_group['lr'] *= 0.5 logger.warning(f"Plateau detected at step {step}, reducing LR") ``` --- **Error 3: LR diferente para diferentes capas sin reason** **El problema**: Algunos practitioners ponen LR alto para la cabeza y bajo para el backbone "porque siempre se hace así", sin entender que esto es un tradeoff. LR alto en la cabeza permite adaptación rápida; LR bajo en el backbone preserva features pre-entrenados. ❌ ```python # Discriminative LR sin investigar la tarea optimizer = torch.optim.AdamW([ {'params': model.backbone.parameters(), 'lr': 1e-5}, # Siempre bajo {'params': model.head.parameters(), 'lr': 1e-3}, # Siempre alto ]) ``` **Por qué falla**: Si la tarea objetivo es muy diferente a pre-training, LR bajo en el backbone impede adaptación. Si es similar, LR alto destruye features útiles. ✓ ```python # Investiga antes de decidir # Si fine-tuning para tarea similar (sentiment → emotion): backbone LR bajo # Si fine-tuning para tarea diferente (MLM → classification): considerar LR alto en todo optimizer = torch.optim.AdamW([ {'params': model.backbone.parameters(), 'lr': 1e-4, 'weight_decay': 0.01}, {'params': model.head.parameters(), 'lr': 1e-3, 'weight_decay': 0.0}, ], betas=(0.9, 0.999)) ``` --- **Error 4: No entender OneCycle para CNNs** **El problema**: OneCycle fue demostrado para CNNs (ResNet, etc.) y funciona extremadamente bien. Pero el 85% lo usa con LR máximo demasiado bajo, perdiendo el benefit de super-convergence. ❌ ```python # OneCycle con LR max demasiado bajo — sin beneficio scheduler = torch.optim.lr_scheduler.OneCycleLR( optimizer, max_lr=1e-4, # Muy bajo para OneCycle — debería ser 10x mayor total_steps=50_000, pct_start=0.3, ) ``` **Por qué falla**: El insight de OneCycle es que LR alto tiene efecto regularizador. Si el LR max es igual a lo que usarías con cosine, no hay super-convergence. $$ \eta_{max}^{OneCycle} \approx 3 \times \eta_{max}^{cosine} $$ ✓ ```python # OneCycle correcto para super-convergence scheduler = torch.optim.lr_scheduler.OneCycleLR( optimizer, max_lr=3e-3, # 10x mayor que cosine para el mismo problema total_steps=50_000, pct_start=0.3, # 30% para warmup anneal_strategy='cos', div_factor=25, # inicial = max_lr / 25 = 1.2e-4 final_div_factor=1000, # final = inicial / 1000 ) ``` --- ## 🎯 Resumen Ejecutivo **Momentum y LR Scheduling** no es "fijar un LR y ya". Es resolver: $$ \theta^* = \arg\min_\theta \mathcal{L}(\theta) \quad \text{manteniendo: } \eta(t) \text{ óptimo en cada fase} $$ Mediante: **warmup inicial + cosine annealing** (transformers) o **OneCycle** (CNNs). Con todas las implicaciones que eso conlleva: - **Warmup (1K-10K steps)** es obligatorio para Adam/AdamW — sin esto, los primeros updates son erráticos - **Cosine annealing** encuentra mínimos más flat que step decay — mejor generalization - **OneCycle** puede darte 10x speedup en CNNs si usas LR_max correcto (3-10x mayor que cosine) - **Plateau detection** con ReduceLROnPlateau o manual adjustment cuando la loss se estanca - **Discriminative LR** depende de la tarea: similar → bajo backbone LR; diferente → considerar LR uniforme alto Parcero, el learning rate schedule es probablemente el hyperparameter más importante después del learning rate mismo. Y lo mejor: no cuesta nada computacionalmente — solo changed la schedule, no el training loop. Hágale que la próxima vez que entrenes algo que no sea un toy model, implementa warmup + cosine annealing desde el día uno. ¡Nos vemos en el día 77! → Día 77: Regularización L1 y L2
