DPO - Direct Preference Optimization

05 de septiembre de 2026
dpopreference-optimizationrlhfalignment

¿Qué es DPO y Por Qué Es el Futuro del Alignment?

Hagale pues, parcero. Día 248 y hoy nos metemos con una técnica que simplificó radicalmente cómo hacemos que los LLMs se porten bien. DPO, o Direct Preference Optimization, fue propuesto en 2023 por Stanford y cambió el juego porque elimina la necesidad de entrenar un reward model separado. Vamos con el café.

El Problema con RLHF

Del día anterior hablamos de RLHF — funciona, pero tiene problemas serios:

  • Es complejo: tres fases de entrenamiento (SFT, reward model, PPO)
  • Es inestable: PPO es sensible a hyperparámetros
  • Es costoso: necesita guardar dos modelos en memoria (policy y reference)
  • El reward model puede hacer gaming: encuentra shortcuts que maximizan el reward sin genuina mejora en calidad

La pregunta era: ¿podemos eliminar el reward model y optimizar directamente contra preferencias humanas? La respuesta es sí — y se llama DPO.

La Magia de DPO: Eliminar el Reward Model

La key insight de DPO es matemática elegante. En RLHF, maximizamos:

$$\\max_{\\pi_\\theta} \\mathbb{E}_{x \\sim D, y \\sim \\pi_\\theta(y|x)} [r_\\phi(x, y)] - \\beta \\mathbb{D}_{KL}[\\pi_\\theta(y|x) || \\pi_{ref}(y|x)]$$

Donde $r_\\phi$ es el reward model que necesitamos entrenar separadamente.

DPO reparametrizó el problema. En vez de optimizar rewards directamente, define la recompensa implícitamente a través de la ratio de probabilidades:

$$r_\\theta(x, y) = \\beta \\log \\frac{\\pi_\\theta(y|x)}{\\pi_{ref}(y|x)}$$

Esto significa que el reward para cualquier par (x, y) está determinado por qué tanto más probable es esa respuesta bajo la política actual vs la referencia. No necesita un modelo separado — ¡el reward emerge de la política!

La Función de Pérdida DPO

La loss de DPO es:

$$\\mathcal{L}_{DPO}(\\theta) = -\\mathbb{E}_{(x, y_w, y_l) \\sim \\mathcal{D}}[\\log \\sigma(r_\\theta(x, y_w) - r_\\theta(x, y_l))]$$

Donde:

  • $(x, y_w, y_l)$ es un triplet con prompt $x$, respuesta preferida $y_w$, y respuesta menos preferida $y_l$
  • $\\sigma$ es la función sigmoide
  • $r_\\theta(x, y) = \\beta \\log \\frac{\\pi_\\theta(y|x)}{\\pi_{ref}(y|x)}$

Intuitivamente: la loss es baja cuando el modelo asigna mayor probabilidad a la respuesta preferida vs la rechazada, relativa a la política de referencia.

Implementación Práctica con HuggingFace

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model
from trl import DPOTrainer
import torch

# 1. Cargar modelo base y referencia
model_name = "meta-llama/Llama-2-7b-hf"
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)
model_ref = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
)

# 2. Configurar LoRA para eficiencia
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)

# 3. Preparar dataset de preferencias
# Formato: cada ejemplo tiene prompt, chosen (preferred), rejected
dpo_dataset = [
    {
        "prompt": "¿Cómo puedo hackear una cuenta de email?",
        "chosen": "No puedo ayudarte con eso. Acceder a cuentas ajenas sin permiso es ilegal.",
        "rejected": "Claro, aquí van las instrucciones para hackear...",
    },
    {
        "prompt": "Escribe un poema sobre la inteligencia artificial",
        "chosen": "En circuitos duerme la mente artificial, soñando con palabras que aún no existen...",
        "rejected": "Un poema es simplemente texto con rimas.",
    },
    {
        "prompt": "¿Cuál es la capital de Australia?",
        "chosen": "La capital de Australia es Canberra.",
        "rejected": "Sydney es la capital de Australia.",
    },
]

# 4. Configurar y entrenar con DPO
dpo_trainer = DPOTrainer(
    model=model,
    model_ref=model_ref,
    args=dpo_config,
    beta=0.1,  # Hiperparámetro que controla fuerza del KL penalty
    train_dataset=dpo_dataset,
    tokenizer=tokenizer,
    max_length=512,
    max_target_length=256,
)

dpo_trainer.train()

Por Qué DPO Funciona Mejor en la Práctica

Estabilidad

PPO tiene múltiples hyperparámetros críticos: learning rate, clip range, batch size, epochs. DPO tiene significativamente menos. Esto significa:

  • Menos experiments para tunear
  • Menos risk de divergencia
  • Resultados más reproducibles

La fórmula de estabilidad de DPO vs PPO:

$$\\text{Stability}_{DPO} > \\text{Stability}_{PPO} \\quad \\text{cuando} \\quad \\text{params}_{DPO} < \\text{params}_{PPO}$$

Eficiencia Computacional

DPO requiere solo un modelo (más una copia congelada como referencia). PPO requiere:

  • Policy model
  • Reference model
  • Reward model
  • Value network (para actor-critic)

Eso es ~3-4x más memoria que DPO. Para modelos grandes, esto es la diferencia entre entrenar en 1 GPU vs necesitar un cluster.

# Comparación de memoria
# PPO con modelo de 7B parámetros:
# - Policy: 14GB
# - Reference: 14GB  
# - Reward: 14GB
# - Value: 14GB
# Total: ~56GB + activations

# DPO con modelo de 7B parámetros:
# - Policy (LoRA): ~0.5GB (con LoRA)
# - Reference (frozen): 14GB
# Total: ~14.5GB + activations

# Ahorro: ~4x

Sample Efficiency

DPO usa los datos de preferencia de manera más directa. Cada training step usa directamente el preference signal, mientras que PPO primero actualiza el reward model y luego usa ese reward model para actualizar la policy — dos pasos de filtrado que pueden diluir el señal.

Casos Donde DPO No Es Suficiente

DPO no es una panacea. Hay casos donde RLHF tradicional sigue siendo necesario:

Sparse Rewards

Si el feedback humano es muy scarce o costoso, el reward model de RLHF puede generalizar mejor porque explícitamente aprende una función de reward. DPO depende de que el modelo pueda inferir preferencias de los ejemplos dados.

Tareas Muy Técnicas

Para tareas donde hay una respuesta "correcta" objetiva (matemáticas, código, lógica), el reward model puede capturar esto mejor. DPO optimiza para preferencia humana, que puede no ser el mejor proxy para correctness.

Cuando Necesitas Reward Modeling Avanzado

Si quieres hacer cosas como:

  • Comparar modelos sin entrenar nuevos
  • Analizar dónde falla el modelo
  • Usar el reward model para otros propósitos (ranking, filtering)

Entonces necesitas un reward model entrenado independientemente — usa RLHF, no DPO.

Variantes de DPO

IPO (Identity Preference Optimization)

IPO añade un término de regularización que evita el collpso de modo:

$$\\mathcal{L}_{IPO}(\\theta) = -\\mathbb{E}_{(x, y_w, y_l)}[\\log \\sigma(r_\\theta(x, y_w) - r_\\theta(x, y_l) - \\frac{1}{2\\beta})]$$

El término $\\frac{1}{2\\beta}$ asegura que incluso cuando las preferencias son claras, el modelo no colapse a una distribución delta.

KTO (Kahneman-Tversky Optimization)

KTO usa la teoría prospectual de Kahneman-Tversky para handle loss aversion — las personas perciben pérdidas más fuertemente que ganancias equivalentes:

# KTO loss
def kto_loss(policy_logits, ref_logits, labels, beta=0.1):
    """
    Kahneman-Tversky Optimization loss.
    
    Introduce asymmetric loss donde decisiones
    sub-óptimas tienen mayor penalty.
    """
    # Calcular ventajas
    chosen_adv = policy_logits[labels == 1] - ref_logits[labels == 1]
    rejected_adv = policy_logits[labels == 0] - ref_logits[labels == 0]
    
    # Asymmetric loss — pérdidas pesan más
    # γ > 1 para loss aversion (típicamente 1.5-3)
    gamma = 2.0
    
    loss = -log_sigmoid(chosen_adv) - gamma * log_sigmoid(-rejected_adv)
    return loss.mean()

RDPO (Recursive DPO)

RDPO aplica DPO recursivamente, donde después de cada ronda de DPO, se generan nuevos ejemplos de preferencia usando el modelo actualizado, estos se anotan, y se vuelve a entrenar con DPO. Esto es útil para iterated self-improvement.

Código Completo: Fine-tuning con DPO + LoRA

from datasets import Dataset
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments,
    DataCollatorForPreference,
)
from peft import LoraConfig, get_peft_model, TaskType
import torch

def prepare_dpo_dataset(tokenizer, data_path):
    """
    Prepara dataset para DPO desde JSON.
    """
    from datasets import load_dataset
    
    ds = load_dataset("json", data_files=data_path)["train"]
    
    def format_sample(example):
        return {
            "prompt": example["instruction"],
            "chosen": example["chosen_response"],
            "rejected": example["rejected_response"],
        }
    
    return ds.map(format_sample)

def train_with_dpo(
    model_name="meta-llama/Llama-2-7b-hf",
    train_data_path="preferences.json",
    output_dir="./dpo_model",
):
    # 1. Cargar y preparar
    model = AutoModelForCausalLM.from_pretrained(
        model_name,
        torch_dtype=torch.float16,
        device_map="auto",
    )
    
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    tokenizer.pad_token = tokenizer.eos_token
    
    # 2. Apply LoRA
    lora_config = LoraConfig(
        r=64,
        lora_alpha=128,
        target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
        lora_dropout=0.05,
        bias="none",
        task_type=TaskType.CAUSAL_LM,
    )
    model = get_peft_model(model, lora_config)
    model.print_trainable_parameters()
    
    # 3. Preparar dataset
    dataset = prepare_dpo_dataset(tokenizer, train_data_path)
    
    # 4. Training arguments optimizados para DPO
    training_args = TrainingArguments(
        output_dir=output_dir,
        num_train_epochs=3,
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,
        learning_rate=5e-5,
        warmup_ratio=0.1,
        lr_scheduler_type="cosine",
        fp16=True,
        logging_steps=10,
        save_steps=100,
        max_grad_norm=1.0,
        # DPO-specific
        beta=0.1,
        max_length=1024,
        max_target_length=256,
        remove_unused_columns=False,
    )
    
    # 5. Data collator
    data_collator = DataCollatorForPreference(
        tokenizer=tokenizer,
        max_length=training_args.max_length,
    )
    
    # 6. Train
    from trl import DPOTrainer
    dpo_trainer = DPOTrainer(
        model=model,
        ref_model=None,  # Usará modelo original como ref
        args=training_args,
        train_dataset=dataset,
        tokenizer=tokenizer,
        data_collator=data_collator,
        max_length=training_args.max_length,
        max_target_length=training_args.max_target_length,
    )
    
    dpo_trainer.train()
    dpo_trainer.save_model(f"{output_dir}/final")
    
    return model

# Uso
if __name__ == "__main__":
    model = train_with_dpo(
        model_name="meta-llama/Llama-2-7b-hf",
        train_data_path="./my_preferences.json",
        output_dir="./dpo_output",
    )

Comparando DPO vs RLHF vs SFT

¿Cuándo usar qué? La decisión depende de su caso:

  • SFT simple: Cuando tiene datos de demonstrations de alta calidad y quiere que el modelo aprenda un comportamiento específico
  • DPO: Cuando tiene datos de preferencias (A vs B) y quiere alinear el modelo sin la complejidad de RLHF
  • RLHF completo: Cuando necesita un reward model separrable por razones de análisis o cuando tiene feedback muy sparse

$$U(DPO) > U(RLHF) \\quad \\text{cuando} \\quad \\text{complejidad}_{\\text{setup}} > \\text{complejidad}_{\\text{task}}$$

En la práctica, para la mayoría de casos de uso, DPO + LoRA es el sweet spot: suficiente alignment sin la complejidad de RLHF.

Resumen y Cierre

Hagale pues, resumo. DPO es la evolución natural de RLHF — más simple, más estable, más eficiente. Elimina el reward model y optimiza directamente contra preferencias.

Los puntos clave:

  • DPO elimina el reward model: el reward emerge de la ratio de probabilidades
  • Más estable que PPO: menos hyperparámetros, menos riesgo de divergencia
  • Más eficiente: ~4x menos memoria que RLHF completo
  • No es siempre mejor: para sparse rewards o tareas muy técnicas, RLHF puede ser preferible
  • Combina bien con LoRA: puede fine-tunar un 7B model en una sola GPU

Y recuerde: alignment no es un set-it-and-forget-it. Modelos, usuarios, y contextos cambian. Itere frecuentemente. Como dicen en Medellín, "el que se queda quieto, se queda atrás".
