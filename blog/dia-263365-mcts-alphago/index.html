Dia 263/365: Function Calling Production — cuando el LLM decide que boton apretar y vos tenes que vivir con las consecuencias

20 de septiembre de 2026
OpenAI Function Calling, Anthropic Tool Use, validacion

Introduccion: cuando le das al LLM el control remoto de tu backend

Hay un momento muy concreto en la carrera de un ingeniero de ML en el que se le aceleran las pupilas: cuando mete Function Calling en produccion sin validar, el modelo invoca refund_full_charge con el argumento customer_id apuntando a un string cualquiera, y al dia siguiente el equipo de soporte esta con 47 tiquets abiertos pidiendo explicaciones. Esa vaina duele, y duele porque toca leer logs del LLM durante horas para entender que el sistema "funcionaba" en el notebook del junior pero no en produccion con usuarios reales diciendo burradas.

Function Calling no es "magia conversacional". Es un protocolo de despacho de mensajes entre tres actores: el modelo de lenguaje (que decide), el orquestador (que valida y enruta), y la funcion destino (que ejecuta). Si cualquier eslabon de esa cadena no trata a los otros dos con respeto tecnico — schemas flojos, sin validacion, sin timeouts, sin rate limits por herramienta — lo que tenes es un misil teledirigido en manos de un loro. La parte que casi nadie enfatiza es la matematica de la validacion: cuando decis "validar el schema", estas decidiendo formalmente que un subconjunto del espacio de inputs es aceptable, y todo lo demas es un agujero de seguridad por el que el modelo eventualmente se va a colar.

Este articulo es para que armes un router de herramientas production-grade, no para que copies el ejemplo de la docu y lo mandes a master el viernes a las 6pm.

1. Que es Function Calling (y por que deberia importarte)

1.1 La analogia cotidiana: la centralita de una aplicadora de taxis

Imaginate una aplicadora tipo DiDi o Uber en Bogota. Tu trabajo como usuario es pedir un viaje. Detras de bambalinas hay:

  • Un catalogo de servicios publicado en la app: taxi estandar, taxi ejecutivo, mensajeria, moto, envio de paquetes grandes. Cada servicio tiene una ficha tecnica con los campos que se necesitan (origen, destino, tipo de vehiculo, nivel de equipaje).
  • Un despachador humano que nunca ejecuta el viaje. El despachador recibe tu peticion en lenguaje natural, mira el catalogo, elige el servicio adecuado y completa los campos requeridos. No maneja el carro. Su trabajo es traducir tu intencion a una orden estructurada y pasarsela al modulo de asignacion.
  • Una capa de validacion. Si vos pediste "un taxi ejecutivo hasta Pasto", el despachador no puede asignarte una moto mensajeria porque seria ridiculo. Hay reglas que dicen: "para trayectos >100 km y de lujo, solo se permite executive_car".
  • Un modulo de ejecucion que recibe la orden validada y hace el trabajo sucio: busca conductor, calcula tarifa, confirma.

Function Calling es exactamente eso, pero el "despachador humano" se reemplaza por un LLM. Vos le pasas el catalogo (los tools con su name, description y JSON Schema de parameters), el modelo decide cual invocar y con que argumentos, y tu orquestador valida antes de ejecutar. Si el LLM escoge mal o completa mal los campos, no es problema del LLM: es problema de tu validacion.

1.2 La matematica formal

Sea $X$ la peticion del usuario en lenguaje natural, $T = \{t_1, t_2, \ldots, t_n\}$ el catalogo de herramientas disponibles, y $\theta$ los parametros del modelo. La probabilidad de que el modelo invoque la herramienta $t_i$ dado el input es la salida de un softmax sobre un scoring interno que el LLM produce sobre cada token de la decision:

$$P(t_i \mid x, \theta) = \frac{\exp\bigl(s_\theta(x, t_i)\bigr)}{\sum_{j=1}^{n} \exp\bigl(s_\theta(x, t_j)\bigr)}$$

Aqui $s_\theta(x, t_i)$ es el logit que el modelo asigna al token/decision correspondiente a invocar $t_i$. Como es un softmax, las probabilidades suman 1 sobre todas las herramientas y la opcion de "no invocar ninguna" (que en OpenAI se representa emitiendo contenido textual sin tool_calls).

La validacion posterior es un predicado booleano sobre los argumentos $a$ emitidos contra el schema $S$ de la herramienta elegida:

$$\text{valid}(a, S) \iff \forall c \in \text{constraints}(S) : c(a) = \text{true}$$

En la practica, $\text{constraints}(S)$ incluye chequeos de tipo (a.amount es number), de rango (a.amount <= 100000), de presencia (a.symbol obligatorio) y de formato (a.email matchea regex RFC 5322). Si el predicado falla, el orquestador no debe ejecutar: devuelve el error al modelo y le pide que reintente.

Ahora, metricas utiles para analizar el sistema en produccion. La tasa de alucinacion de herramientas la definimos como:

$$H_{\text{tool}} = \frac{\#\{\text{tool\_calls emitidos con name} \notin T\}}{\#\{\text{total tool\_calls emitidos}\}}$$

Y la tasa de validacion fallida:

$$V_{\text{fail}} = \frac{\#\{\text{args emitidos con } \lnot \text{valid}(a, S)\}}{\#\{\text{total tool\_calls emitidos}\}}$$

En sistemas sanos, $H_{\text{tool}}$ debe ser 0 (porque tu enrutador rechaza nombres que no conoce) y $V_{\text{fail}}$ debe estar por debajo del 5%. Si $V_{\text{fail}}$ esta por encima del 20%, tu esquema esta mal disenado: las descripciones son ambiguas o faltan restricciones.

El costo esperado de una peticion con $k$ reintentos maximos y probabilidad de exito por intento $p$ es:

$$E[\text{cost}] = c_{\text{llm}} \sum_{i=1}^{k} (1 - p)^{i-1} \cdot \bigl(1 + (1-p)\bigr)$$

donde $c_{\text{llm}}$ es el costo del round-trip al LLM y el factor $(1-p)^{i-1}$ es la probabilidad de llegar al intento $i$. Esto te sirve para dimensionar budgets: si $p = 0.7$ y $k = 3$, estas pagando en promedio 2.3 llamadas por peticion. Si el costo del LLM es alto, subir $p$ mejora el sistema mas que bajar $k$.

2. Como OpenAI Function Calling y Anthropic Tool Use resuelven esto

El flujo interno en ambos proveedores es identico en estructura, diferente en detalles de la API:

  1. Catalog injection: vos pasas una lista de tools (OpenAI) o tools (Anthropic) con un JSON Schema por herramienta. El schema incluye name, description (critico: el modelo usa esto como "ancla semantica" para decidir), y parameters con tipo object y propiedades tipadas.
  2. Decision in context: el modelo, en su ventana de contexto, ve esas descripciones concatenadas al system prompt. Durante la generacion, emite tokens que corresponden a una decision estructurada: nombre de la herramienta + argumentos serializados como JSON.
  3. Re-entry point: tu orquestador intercepta la respuesta, parsea los argumentos (estrictamente como JSON, no como "casi JSON"), los valida, y los pasa a la funcion real.
  4. Feedback loop: el resultado (o el error de validacion) se reinyecta como un mensaje role: tool (OpenAI) o como un tool_result block (Anthropic), y el modelo usa eso para generar la siguiente respuesta al usuario.
+----------------+      +-----------------+      +--------------+
|  Usuario       | ---> |  LLM (GPT/Claude)| ---> | Orquestador  |
|  "pago a Juan" |      |  elige tool+args |      | + Validador  |
+----------------+      +-----------------+      +--------------+
                                                          |
                                                          v
                                                 +----------------+
                                                 | Funcion real   |
                                                 | (Python/etc.)  |
                                                 +----------------+
                                                          |
                                                          v
                                                  tool_result -> LLM -> usuario

Anatomia de un tool definition (OpenAI):

tools = [{
    "type": "function",
    "function": {
        "name": "transfer_funds",
        "description": "Transfiere fondos entre cuentas internas. Usar solo cuando el usuario confirma monto y cuenta destino.",
        "parameters": {
            "type": "object",
            "properties": {
                "from_account": {"type": "string", "pattern": "^ACC-[0-9]{6}$"},
                "to_account":   {"type": "string", "pattern": "^ACC-[0-9]{6}$"},
                "amount_cents": {"type": "number", "minimum": 1, "maximum": 100000000}
            },
            "required": ["from_account", "to_account", "amount_cents"],
            "additionalProperties": False
        }
    }
}]

additionalProperties: False es indispensable en produccion. Sin eso, el modelo puede meter claves arbitrarias que tu validador pasa por alto (y peor, que pueden colarse a tu backend si usas **kwargs por ahi).

3. OpenAI y Anthropic: Uso Directo y Casos de Control Fino

Uso directo significa que vos operas el SDK del proveedor. Control fino significa que armaste tu propia capa de routing encima. La eleccion depende de tres variables: latencia, costo por llamada, y requisitos de cumplimiento.

# direct_usage.py — ejemplo minimo contra cada proveedor
import asyncio
from openai import AsyncOpenAI
from anthropic import AsyncAnthropic

OPENAI = AsyncOpenAI()
ANTHROPIC = AsyncAnthropic()

async def openai_call(user_msg: str) -> dict:
    resp = await OPENAI.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": user_msg}],
        tools=[{
            "type": "function",
            "function": {
                "name": "get_weather",
                "description": "Devuelve el clima actual de una ciudad.",
                "parameters": {
                    "type": "object",
                    "properties": {"city": {"type": "string"}},
                    "required": ["city"],
                    "additionalProperties": False
                }
            }
        }],
        tool_choice="auto"
    )
    msg = resp.choices[0].message
    return {"text": msg.content, "tool_calls": [
        {"name": tc.function.name, "args": tc.function.arguments}
        for tc in (msg.tool_calls or [])
    ]}

async def anthropic_call(user_msg: str) -> dict:
    resp = await ANTHROPIC.messages.create(
        model="claude-3-5-sonnet-latest",
        max_tokens=1024,
        tools=[{
            "name": "get_weather",
            "description": "Devuelve el clima actual de una ciudad.",
            "input_schema": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"]
            }
        }],
        messages=[{"role": "user", "content": user_msg}]
    )
    text_blocks = [b.text for b in resp.content if b.type == "text"]
    tool_blocks = [b for b in resp.content if b.type == "tool_use"]
    return {
        "text": "\n".join(text_blocks),
        "tool_calls": [{"name": b.name, "args": b.input} for b in tool_blocks]
    }

Cuando usar control fino: multi-tenant (necesitas aislar herramientas por cliente), cuando queres un log centralizado de todas las invocaciones para auditoria, cuando queres aplicar politicas de rate limit por herramienta, o cuando queres correr un modelo open-source local como router y solo salir al proveedor en casos complejos (router escalonado, optimizable en costo).

4. Implementacion Production-Ready: ToolRouter

Esta es la pieza que uso en mis sistemas reales. Se compone de tres capas: tipos y contratos, el motor de despacho, y utilidades de observabilidad. Cada capa vive en su propio archivo por SRP.

4.1 Tipos y protocolos

# tool_router/types.py
from __future__ import annotations
from dataclasses import dataclass
from enum import Enum
from typing import Any, Callable, Awaitable
from pydantic import BaseModel, Field, ValidationError

class ToolCallStatus(str, Enum):
    OK = "ok"
    VALIDATION_ERROR = "validation_error"
    EXECUTION_ERROR = "execution_error"
    UNKNOWN_TOOL = "unknown_tool"
    TIMEOUT = "timeout"

@dataclass(frozen=True)
class ToolDefinition:
    """Contrato inmutable de una herramienta."""
    name: str
    description: str
    parameters_schema: dict[str, Any]
    handler: Callable[..., Awaitable[Any]]
    timeout_s: float = 10.0
    max_retries: int = 2

@dataclass(frozen=True)
class ToolCallResult:
    name: str
    raw_args: dict[str, Any]
    status: ToolCallStatus
    value: Any = None
    error: str | None = None
    attempt: int = 1

4.2 El motor principal

# tool_router/engine.py
from __future__ import annotations
import asyncio
import json
import logging
import time
from typing import Iterable

from .types import ToolDefinition, ToolCallResult, ToolCallStatus

logger = logging.getLogger(__name__)

class ToolRouter:
    """Despachador asincrono con retry exponencial y validacion por schema."""

    def __init__(self, tools: Iterable[ToolDefinition]):
        self._tools: dict[str, ToolDefinition] = {t.name: t for t in tools}
        # Defensa 1: no se puede invocar una herramienta no registrada
        assert all(t.name.isidentifier() for t in tools), "name debe ser identificador Python"

    @property
    def catalog(self) -> list[dict]:
        """Serializa el catalogo al formato OpenAI/Anthropic."""
        return [
            {
                "type": "function",
                "function": {
                    "name": t.name,
                    "description": t.description,
                    "parameters": t.parameters_schema,
                }
            }
            for t in self._tools.values()
        ]

    async def dispatch(self, name: str, raw_args: Any, *, strict: bool = True) -> ToolCallResult:
        tool = self._tools.get(name)
        if tool is None:
            # Defensa 2: el modelo alucino una herramienta
            logger.warning("tool_hallucination", extra={"name": name})
            return ToolCallResult(name, {}, ToolCallStatus.UNKNOWN_TOOL,
                                  error=f"unknown tool: {name}")

        # Defensa 3: normalizar argumentos (el modelo a veces emite string)
        if isinstance(raw_args, str):
            try:
                args = json.loads(raw_args)
            except json.JSONDecodeError as e:
                return ToolCallResult(name, {}, ToolCallStatus.VALIDATION_ERROR,
                                      error=f"args not JSON: {e}")
        elif isinstance(raw_args, dict):
            args = raw_args
        else:
            return ToolCallResult(name, {}, ToolCallStatus.VALIDATION_ERROR,
                                  error="args type unsupported")

        # Defensa 4: validar contra JSON Schema propio
        if strict and not self._validate(args, tool.parameters_schema):
            return ToolCallResult(name, args, ToolCallStatus.VALIDATION_ERROR,
                                  error="schema mismatch")

        return await self._execute_with_retry(tool, args)

    async def _execute_with_retry(self, tool: ToolDefinition, args: dict) -> ToolCallResult:
        backoff = 0.5
        last_err = None
        for attempt in range(1, tool.max_retries + 2):  # +1 = intento inicial
            try:
                value = await asyncio.wait_for(
                    tool.handler(**args), timeout=tool.timeout_s
                )
                return ToolCallResult(tool.name, args, ToolCallStatus.OK,
                                      value=value, attempt=attempt)
            except asyncio.TimeoutError:
                last_err = f"timeout after {tool.timeout_s}s"
                status = ToolCallStatus.TIMEOUT
            except Exception as e:
                last_err = f"{type(e).__name__}: {e}"
                status = ToolCallStatus.EXECUTION_ERROR
            if attempt > tool.max_retries:
                return ToolCallResult(tool.name, args, status,
                                      error=last_err, attempt=attempt)
            await asyncio.sleep(backoff)
            backoff *= 2

    @staticmethod
    def _validate(args: dict, schema: dict) -> bool:
        """Validacion minima contra JSON Schema Draft 7.
        En prod usa jsonschema o pydantic para cobertura completa."""
        if schema.get("type") != "object":
            return False
        required = schema.get("required", [])
        if not all(k in args for k in required):
            return False
        if schema.get("additionalProperties") is False:
            allowed = set(schema.get("properties", {}).keys())
            if not set(args.keys()).issubset(allowed):
                return False
        props = schema.get("properties", {})
        for k, v in args.items():
            if k not in props:
                continue
            spec = props[k]
            if spec.get("type") == "number" and not isinstance(v, (int, float)):
                return False
            if spec.get("type") == "integer" and isinstance(v, bool):
                return False  # bool es subclase de int en Python
            if spec.get("type") == "string" and not isinstance(v, str):
                return False
        return True

    async def dispatch_many(self, calls: list[tuple[str, Any]]) -> list[ToolCallResult]:
        """Ejecuta multiples tool calls en paralelo. Util cuando el modelo
        emite varios en una sola respuesta (parallel tool calls)."""
        return await asyncio.gather(
            *(self.dispatch(n, a) for n, a in calls),
            return_exceptions=False
        )

4.3 Utilidades de analisis y verificacion

# tool_router/observability.py
from __future__ import annotations
import time
from collections import Counter, defaultdict
from dataclasses import dataclass

from .types import ToolCallResult, ToolCallStatus

@dataclass
class RouterStats:
    invocations: int
    by_status: dict[str, int]
    by_tool: dict[str, int]
    hallucination_rate: float
    validation_fail_rate: float
    p50_latency_ms: float
    p95_latency_ms: float

class RouterMetrics:
    """Contadores in-memory; en prod enviar a Prometheus/OpenTelemetry."""

    def __init__(self) -> None:
        self._calls: list[tuple[str, float, ToolCallStatus]] = []

    def record(self, name: str, latency_ms: float, status: ToolCallStatus) -> None:
        self._calls.append((name, latency_ms, status))

    def summary(self) -> RouterStats:
        statuses = Counter(s.value for _, _, s in self._calls)
        tools = Counter(n for n, _, _ in self._calls)
        total = len(self._calls)
        if total == 0:
            return RouterStats(0, {}, {}, 0.0, 0.0, 0.0, 0.0)
        lat = sorted(l for _, l, _ in self._calls)
        halluc = statuses.get("unknown_tool", 0) / total
        vfail = statuses.get("validation_error", 0) / total
        return RouterStats(
            invocations=total,
            by_status=dict(statuses),
            by_tool=dict(tools),
            hallucination_rate=halluc,
            validation_fail_rate=vfail,
            p50_latency_ms=lat[int(0.50 * (total - 1))],
            p95_latency_ms=lat[int(0.95 * (total - 1))],
        )

Con RouterStats.hallucination_rate > 0.01 ya tenes una senal de que el catalogo es demasiado grande o las descripciones se solapan semánticamente. Pilas con esto.

5. Ejemplos de Uso en Casos Reales

Caso 1: Asistente SQL con whitelist de tablas

# examples/sql_tool.py
from pydantic import BaseModel, Field
from tool_router.engine import ToolRouter
from tool_router.types import ToolDefinition

ALLOWED_TABLES = {"orders", "customers", "products"}

class SQLArgs(BaseModel):
    table: str = Field(pattern="^(orders|customers|products)$")  # whitelist dura
    limit: int = Field(ge=1, le=1000)

async def query_db(table: str, limit: int) -> list[dict]:
    # Verificacion manual esperada: limit=10 sobre tabla orders devuelve 10 filas
    return [{"id": i, "table": table} for i in range(min(limit, 10))]

router = ToolRouter([
    ToolDefinition(
        name="query_db",
        description="Consulta filas de una tabla permitida del data warehouse.",
        parameters_schema=SQLArgs.model_json_schema(),
        handler=query_db,
    )
])

Caso 2: Calculadora con validacion de expresion

# examples/calculator_tool.py
import ast
import operator

BIN_OPS = {ast.Add: operator.add, ast.Sub: operator.sub,
           ast.Mult: operator.mul, ast.Div: operator.truediv}

def safe_eval(expr: str) -> float:
    tree = ast.parse(expr, mode="eval")
    return _eval(tree.body)

def _eval(node):
    if isinstance(node, ast.Num): return node.n
    if isinstance(node, ast.BinOp): return BIN_OPS[type(node.op)](_eval(node.left), _eval(node.right))
    if isinstance(node, ast.UnaryOp) and isinstance(node.op, ast.USub): return -_eval(node.operand)
    raise ValueError(f"nodo no permitido: {type(node).__name__}")

async def calculate(expression: str) -> float:
    # Verificacion manual esperada: calculate("2+3*4") == 14.0
    # Verificacion manual esperada: calculate("2+3*__import__('os')") raise ValueError
    return safe_eval(expression)

La validacion con ast es lo que evita que el usuario (via LLM) te ejecute __import__('os').system('rm -rf /'). Nunca uses eval() directo: en Python eso es la forma mas rapida de terminar tu semana.

Caso 3: Orquestador de notificaciones multi-canal

# examples/notifier.py
import asyncio

async def send_email(to: str, subject: str, body: str) -> dict:
    # Verificacion: con to="user@x.com" devuelve {"channel": "email", "id": ...}
    return {"channel": "email", "id": "msg-" + str(hash(to))[-6:]}

async def send_slack(channel: str, text: str) -> dict:
    return {"channel": "slack", "id": "slk-" + str(hash(text))[-6:]}

router = ToolRouter([
    ToolDefinition("send_email",  "Envia email transaccional.",  {...}, send_email,  timeout_s=5.0),
    ToolDefinition("send_slack",  "Postea mensaje en canal Slack.",{...}, send_slack,  timeout_s=3.0),
])

async def handle_tool_calls(model_response) -> list:
    calls = [(tc["name"], tc["args"]) for tc in model_response["tool_calls"]]
    return await router.dispatch_many(calls)

Note que dispatch_many ejecuta en paralelo via asyncio.gather. Esto es critico cuando el LLM emite 3 tool calls independientes: la latencia es la del max(tiempos), no la suma.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: Tool hallucination bajo presion

Sintoma: el log muestra tool_calls: [{name: "delete_production_db", args: {...}}] cuando el usuario pregunto algo inocuo.

Deteccion numerica: RouterStats.hallucination_rate > 0.01. Con 100 invocaciones/hora, mas de 1 por hora es senal.

Por que pasa: el catalogo tiene herramientas con nombres similares (delete_db vs delete_user_data), o el system prompt induce al modelo a "ser util inventando".

Soluciones (en orden de impacto):

  1. Whitelist dura en el router: aunque el LLM emita delete_production_db, tu router la rechaza (ya esta en _tools.get(name) retornando UNKNOWN_TOOL). Esto es el minimo no negociable.
  2. Renombrar para ser inequivoco: en vez de delete_user, usar delete_user_PERMANENTLY_admin_only. La descripcion es el ancla semantica del modelo, dale peso.
  3. Restringir el contexto: pasar solo el subset de herramientas relevantes para la peticion actual (ver Seccion 7).

Problema 2: Argumentos mal tipados que revientan la funcion

Sintoma: query_db(table=123, limit="diez") rompe tu psycopg2 con TypeError.

Deteccion numerica: validation_fail_rate > 0.05. Ojo, un modelo bien afinado tiene ~2-5% de errores crudos; arriba de eso es problema del schema, no del modelo.

Por que pasa: el modelo emite arguments como JSON string, y tu parser es laxo. O el schema permite string cuando deberia ser number.

Soluciones:

  1. Validacion con Pydantic en el schema de la herramienta, no en el handler. Asi el router rechaza antes de invocar.
  2. Coercion explicita cuando es segura: para campos integer con strings numericos, int("100") es razonable; para string, no coercionar True a "True".
  3. Mensaje de error util al LLM: cuando el router rechaza, devolverle al modelo un tool_result con el JSON Schema esperado y el mensaje "argumentos no cumplen: falta X, Y tiene tipo incorrecto". El modelo autocorrige si el feedback es claro.
# En el orquestador, al recibir VALIDATION_ERROR:
tool_result_msg = {
    "role": "tool",
    "tool_call_id": tc.id,
    "content": json.dumps({
        "error": "validation_failed",
        "expected_schema": tool.parameters_schema,
        "received_args": args,
        "hint": "Corrige los tipos y campos requeridos antes de reintentar."
    })
}

El 80% de las veces el modelo corrige solo en el siguiente turno. Esto baja $V_{\text{fail}}$ acumulado y reduce la carga sobre tu backend.

7. Optimizaciones de Produccion

7.1 Tool pruning contextual

Pasar 50 herramientas en tools cuesta tokens en el prompt y degrada la calidad de seleccion (mas softmax sobre mas logits = mas confusion). La optimizacion concreta es: dado el embedding de la consulta del usuario, pasar solo el top-$k$ por similitud coseno.

$$S = \text{topk}_i\left(\frac{\langle e_x, e_{t_i} \rangle}{\|e_x\| \cdot \|e_{t_i}\|}, k=8\right)$$

donde $e_x$ es el embedding de la consulta y $e_{t_i}$ es el embedding precomputado de la descripcion de la herramienta $t_i$. Trade-off: ahorras tokens (y bajas latencia), pero perdes recall en tools nuevas. La mitigacion es mover herramientas desconocidas a un tier de fallback: si topk no devuelve nada util, pasas el catalogo completo y registras el caso para reentrenar el embedding store.

7.2 Validacion dura via Pydantic en el handler

En vez de validar en _validate (logica propia, fragil), delegale la validacion a Pydantic con el mismo modelo que usaste para definir el schema. Asi el schema JSON y el handler comparten una sola fuente de verdad.

from pydantic import BaseModel, Field, ValidationError

class TransferSchema(BaseModel):
    from_account: str = Field(pattern=r"^ACC-\d{6}$")
    to_account:   str = Field(pattern=r"^ACC-\d{6}$")
    amount_cents: int = Field(ge=1, le=100_000_000)

async def transfer_funds_handler(**raw: dict) -> dict:
    args = TransferSchema(**raw)  # levanta ValidationError si algo falla
    # ... ejecutar logica ...

Trade-off: el doble parseo (Pydantic + JSON Schema) suma ~50us por llamada. En sistemas con miles de RPS eso suma. Pero el beneficio de consistencia es brutal: el dia que cambias el regex, lo cambias en un solo lado.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

Resumen operativo, en bullets que puedas checkear el lunes en el standup:

  • Whitelist dura de herramientas: nada se ejecuta sin pasar por ToolRouter.dispatch, que rechaza todo name no registrado. Esto cierra $H_{\text{tool}}$ a 0 por construccion.
  • Validacion explicita, no implicita: usa Pydantic o JSON Schema. El "ya lo valida Python cuando lo uso" es la frase que pronuncia alguien que va a perder un fin de semana.
  • Timeout por herramienta: cada handler tiene timeout_s corto (3-10s). Un LLM en produccion no puede esperar 60s mientras tu SQL query hace full table scan.
  • Retry con backoff exponencial: pero con limite duro (max_retries). El $E[\text{cost}]$ se te dispara si no pones tapa.
  • Metricas: $H_{\text{tool}}$, $V_{\text{fail}}$, latencias p50/p95: estas tres senales te avisan 24 horas antes de que explote algo.

Mini-checklist de despliegue:

[ ] Catalogo de herramientas revisado por humano senior
[ ] additionalProperties: False en TODOS los schemas
[ ] ToolRouter rechaza nombres no registrados (probado con tool inventada)
[ ] Pydantic/JSON Schema valida antes de ejecutar el handler
[ ] Timeout y max_retries por herramienta
[ ] Logs estructurados con tool_call_id trazable
[ ] Metricas exportadas a Prometheus o equivalente
[ ] Test de inyeccion: el usuario intenta ejecutar /path/o ; rm / via tool call

Ultimo: si tu sistema de Function Calling en produccion no tiene los nombres de herramientas en espanol concreto (get_weather_bogota mejor que get_weather_at_location), todavia estas en fase de prototipo. El "al toque" en que un LLM desambigua correcto depende brutalmente de cuanta senal semantica le diste en el nombre y la descripcion. Despegate de la docu generica y diseña tu catalogo como si fuera una API publica: porque lo es, solo que el consumidor es un loro estadistico en vez de otro desarrollador.

A arremangarse. ⚠️
