ML Pipelines - Automatizando El Workflow De Machine Learning

05 de agosto de 2026
ml-pipelinesairflow Prefectkubeflowautomation

Parcero, día 217 y hoy hablamos de algo que el 85% de equipos de ML hacen manual cuando no deberían:orchestrar pipelines de machine learning. Si tu workflow de ML involucra correr scripts en orden específico, copiar archivos entre carpetas, y esperar que nada se rompa entre pasos — necesitas un pipeline de verdad. No un script de bash. Un pipeline production-ready.

El problema es que ML no es un一步到位. Tienes data ingestion, preprocessing, feature engineering, training, evaluation, y deployment. Cada paso tiene sus dependencias, sus recursos, sus failures modes. Hacer esto manual es como tratar de dirigir una orquesta symphonica golpeando random instrumentos — eventualmente algo suena bien por casualidad, pero no es reliable.

🎯 Por Qué Necesitas Un ML Pipeline Framework

Un ML pipeline framework te permite:

  • Definir dependencias entre pasos: No puedes hacer training hasta que el preprocessing esté completo.
  • Ejecutar pasos en paralelo: Feature engineering de múltiples features puede correr concurrentemente.
  • Manejar failures gracefully: Si un paso falla, el pipeline se detiene y puedes hacer retry desde ese punto.
  • Re-ejecutar desde cualquier punto: No necesitas re-run todo si solo cambió el último paso.
  • Versionar tu workflow: El pipeline mismo es código versionable, no una secuencia de scripts olvidados.
  • Monitoring y logging centralizado: Sabes exactamente qué paso está corriendo y qué 输出 produjo.

Las tres herramientas más populares para esto son:

  • Apache Airflow: El más establecido, usa DAGs en Python, muy flexible.
  • Prefect: Más moderno, API más limpia que Airflow, bueno para equipos que vienen de pandas.
  • Kubeflow Pipelines: Para cuando necesitas ejecutar en Kubernetes con recursos aislados.

📐 La Arquitectura De Un ML Pipeline

Podemos modelar un ML pipeline como un grafo acíclico dirigido (DAG) donde cada nodo es un paso y las aristas son dependencias:

$$P = (V, E, s, t)$$

donde:

  • $V = \{v_1, v_2, ..., v_n\}$ son los pasos del pipeline
  • $E \subseteq V \times V$ son las dependencias entre pasos
  • $s: V \rightarrow \mathbb{R}$ es el tiempo estimado de ejecución de cada paso
  • $t: V \rightarrow \mathbb{R}$ es el tiempo real de ejecución

El tiempo total del pipeline está determinado por el camino crítico — la secuencia de pasos que toma más tiempo:

$$T_{pipeline} = \max_{p \in \text{paths}(V, E)} \sum_{v \in p} s(v)$$

La intuición: para optimizar tu pipeline, enfócate en el camino crítico. Si el paso de training toma 10 horas y los demás combinados toman 1 hora, optimizar los demás tiene impacto mínimo en el tiempo total.

💻 Implementando Un Pipeline Con Prefect

Prefect es mi recomendación para la mayoría de equipos. La API es limpia, el debugging es fácil, y tiene built-in scheduling y retry logic. Aquí está un pipeline completo:

from prefect import flow, task, get_run_logger
from prefect.tasks import task_input_hash
from datetime import timedelta
import pandas as pd
import numpy as np
from sklearn.model_selection import train_test_split
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import accuracy_score, precision_score, recall_score
import mlflow
import pickle


# ============================================================
# TASKS: Pasos individuales del pipeline
# ============================================================

@task(
    name="Ingest Data",
    retries=3,
    retry_delay_seconds=30,
    cache_key_fn=task_input_hash,
    cache_expiration=timedelta(hours=1)
)
def ingest_data(source_path: str) -> pd.DataFrame:
    """
    Ingests data from source. Includes retry logic for flaky sources.
    """
    logger = get_run_logger()
    logger.info(f"Ingesting data from {source_path}")
    
    df = pd.read_csv(source_path)
    logger.info(f"Ingested {len(df)} rows, {len(df.columns)} columns")
    
    return df


@task(
    name="Preprocess Data",
    cache_key_fn=task_input_hash,
    cache_expiration=timedelta(hours=1)
)
def preprocess_data(df: pd.DataFrame, config: dict) -> pd.DataFrame:
    """
    Preprocesses raw data: handle missing values, encode categoricals.
    """
    logger = get_run_logger()
    logger.info("Preprocessing data")
    
    # Handle missing values
    df = df.fillna(df.median(numeric_only=True))
    
    # Encode categoricals
    for col in df.select_dtypes(include=['object']).columns:
        df[col] = pd.Categorical(df[col]).codes
    
    # Feature engineering example
    if config.get("add_interactions", False):
        df["feat_interaction"] = df.iloc[:, 0] * df.iloc[:, 1]
    
    logger.info(f"Preprocessed data shape: {df.shape}")
    return df


@task(name="Split Data", cache_key_fn=task_input_hash, cache_expiration=timedelta(hours=1))
def split_data(df: pd.DataFrame, target_col: str, test_size: float = 0.2) -> tuple:
    """
    Splits data into train/test sets.
    """
    logger = get_run_logger()
    
    X = df.drop(columns=[target_col])
    y = df[target_col]
    
    X_train, X_test, y_train, y_test = train_test_split(
        X, y, test_size=test_size, random_state=42
    )
    
    logger.info(f"Train size: {len(X_train)}, Test size: {len(X_test)}")
    return X_train, X_test, y_train, y_test


@task(name="Train Model", log_prints=True)
def train_model(
    X_train: pd.DataFrame,
    y_train: pd.Series,
    config: dict
) -> RandomForestClassifier:
    """
    Trains a Random Forest model with given config.
    """
    logger = get_run_logger()
    logger.info(f"Training model with config: {config}")
    
    model = RandomForestClassifier(
        n_estimators=config.get("n_estimators", 100),
        max_depth=config.get("max_depth", 10),
        random_state=42
    )
    
    model.fit(X_train, y_train)
    logger.info("Model training complete")
    
    return model


@task(name="Evaluate Model", log_prints=True)
def evaluate_model(
    model: RandomForestClassifier,
    X_test: pd.DataFrame,
    y_test: pd.Series
) -> dict:
    """
    Evaluates model and returns metrics.
    """
    logger = get_run_logger()
    
    y_pred = model.predict(X_test)
    
    metrics = {
        "accuracy": accuracy_score(y_test, y_pred),
        "precision": precision_score(y_test, y_pred, average="weighted"),
        "recall": recall_score(y_test, y_pred, average="weighted"),
    }
    
    logger.info(f"Metrics: {metrics}")
    return metrics


@task(name="Register Model", log_prints=True)
def register_model(
    model: RandomForestClassifier,
    metrics: dict,
    config: dict,
    model_name: str = "prod-classifier"
) -> str:
    """
    Registers model to MLflow Model Registry.
    """
    logger = get_run_logger()
    
    with mlflow.start_run():
        # Log metrics
        mlflow.log_metrics(metrics)
        
        # Log config
        mlflow.log_params(config)
        
        # Log model
        mlflow.sklearn.log_model(model, "model")
    
    logger.info(f"Model registered to MLflow: {model_name}")
    return model_name


# ============================================================
# FLOW: El pipeline completo que orquesta todos los tasks
# ============================================================

@flow(
    name="ML Training Pipeline",
    description="Complete ML pipeline from data ingestion to model registration",
    log_prints=True
)
def ml_pipeline(
    source_path: str = "s3://data/training_data.csv",
    target_col: str = "target",
    model_config: dict = None
) -> dict:
    """
    Main ML pipeline that orchestrates all steps.
    
    Args:
        source_path: Path to training data
        target_col: Name of target column
        model_config: Model hyperparameters
        
    Returns:
        Dictionary with pipeline results and metrics
    """
    logger = get_run_logger()
    
    # Default config
    if model_config is None:
        model_config = {
            "n_estimators": 100,
            "max_depth": 10,
            "add_interactions": True
        }
    
    logger.info("Starting ML Pipeline")
    
    # Execute pipeline steps
    # Each task waits for its dependencies automatically
    raw_data = ingest_data(source_path)
    
    processed_data = preprocess_data(raw_data, model_config)
    
    X_train, X_test, y_train, y_test = split_data(
        processed_data, 
        target_col
    )
    
    model = train_model(X_train, y_train, model_config)
    
    metrics = evaluate_model(model, X_test, y_test)
    
    register_model(model, metrics, model_config)
    
    logger.info(f"Pipeline complete! Final metrics: {metrics}")
    
    return {
        "status": "success",
        "metrics": metrics,
        "model_config": model_config
    }


# ============================================================
# EJECUCIÓN
# ============================================================

if __name__ == "__main__":
    # Run pipeline directly
    result = ml_pipeline(
        source_path="data/training.csv",
        target_col="churn",
        model_config={
            "n_estimators": 200,
            "max_depth": 15,
            "add_interactions": True
        }
    )
    
    print(f"Pipeline result: {result}")

⚠️ Errores Comunes

Error 1: Hacer El Pipeline Too Complex Desde El Principio

El problema: Equipos que intentan build un pipeline con 50+ tareas, branching complejo, y docenas de features desde day one. El resultado: un pipeline que toma meses construir y nunca funciona correctamente.

Fix: Empieza simple. Tres tareas: ingest, train, evaluate. Haz que funcione. Depois agrega complejidad gradualmente: preprocessing, feature engineering, model selection. Un pipeline simple que corre es mejor que un pipeline perfecto que nunca termina.

Error 2: No Manejar Estado Entre Pasos

El problema: Guardar estado intermedio en archivos locales o en memoria. Cuando el pipeline falla en el paso 7 de 10, pierdes todo el estado y tienes que re-run desde el principio.

Fix: Usa artifacts y caching. Prefect tiene caching built-in con cache_key_fn. Si los inputs no cambian, el task no se re-ejecuta. Guarda artifacts en S3/GCS, no en disco local.

Error 3: No Definir Retry Logic

El problema: Pipelines que fallan por un timeout temporal o error de red y no tienen retry. Un paso que falla por una causa transiente causa que todo el pipeline se caiga.

Fix: Define retries y retry_delay_seconds en tus tasks. Para data ingestion y API calls, 3 retries con exponential backoff es un buen starting point.

✅ Resumen y Cierre

  • ML Pipelines transforman scripts manuales en workflows reproducibles y automatizados.
  • Prefect ofrece una API limpia y moderna para definir pipelines en Python.
  • DAGs modelan las dependencias entre pasos — el pipeline solo ejecuta lo que necesita ejecutarse.
  • Caching evita re-ejecutar pasos cuyos inputs no han cambiado.
  • Retry logic hace tu pipeline resilient a fallas transitorias.

Hagale que un pipeline bien diseñado es la diferencia entre pasar 2 horas corriendo scripts manualmente y presionar un botón y dejar que la máquina trabaje. Empieza con Prefect, define tus tareas, conecta las dependencias, y conviert tu ML workflow en algo production-ready.
