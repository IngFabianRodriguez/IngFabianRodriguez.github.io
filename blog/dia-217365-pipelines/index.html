Dia 217/365: Pipelines — La logistica que mantiene tu ML vivo en produccion

5 de agosto de 2026
apache-airflow, kfp (Kubeflow Pipelines)

Introduccion: Cuando tu "workflow" se cae a las 3am del viernes

Imagine esto: son las 11pm de un jueves, llevas 8 horas peleando con un feature store que se cayó, y de repente te llega un PagerDuty: "Production model serving latency > 2s". Abres el dashboard, miras la última versión del modelo y... no hay última versión. El pipeline de reentrenamiento se rompió hace 17 días y nadie se dio cuenta porque "la última ejecución exitosa" en el log está bien, pero la ejecución real falló silenciosamente.

¿Suena familiar? Esa vaina pasa todos los días en equipos que tratan los pipelines de ML como scripts de cron glorificados. Un pipeline no es un script que corre en orden; es un grafo dirigido acíclico de tareas con dependencias, retries, SLAs, sensores, backfills y metadata tracking. Si no lo entiendes así, tarde o temprano te come vivo.

Hoy vamos a desmontar Apache Airflow y Kubeflow Pipelines (kfp) desde la matemática de grafos hasta el código que se ejecuta en Kubernetes. Nada de tutoriales con print("hello") disfrazados de producción.

1. Que es un Pipeline? (Y por que deberia importarte)

1.1 La analogia cotidiana

Pensa en una empresa de logistica tipo DHL o MercadoLibre. Tenés un centro de acopio principal (Bogotá), hubs regionales (Medellín, Cali, Barranquilla), y rutas que conectan todo. Cada paquete pasa por estaciones secuenciales: recepción → clasificación → aduana → transporte → entrega. Algunas tareas son asíncronas (tracking vía satélite), otras son críticas (la firma del destinatario). Si una estación se cae, los paquetes se acumulan; si una ruta se demora, el SLA se jode.

Un pipeline de ML es exactamente eso: un grafo donde los vértices son tareas (extract, validate, preprocess, train, evaluate, deploy) y las aristas son dependencias (B depende de A). El motor del pipeline es el "director de operaciones" que decide qué correr, cuándo, en qué orden, y cómo reaccionar cuando algo falla.

La diferencia brutal entre un pipeline real y un script secuencial: paralelismo, retries selectivos, lineage tracking, y manejo de fallos parciales. Un script te tira todo al suelo si la tarea 5 de 10 falla. Un pipeline bien diseñado reintenta la 5 sin tocar la 1-4.

1.2 La matematica formal

Un pipeline se modela como un Directed Acyclic Graph (DAG):

$$G = (V, E)$$

Donde:

  • $V$ es el conjunto de vértices (tareas, en Airflow llamadas TaskInstance, en kfp ContainerOp o component)
  • $E \subseteq V \times V$ es el conjunto de aristas dirigidas (dependencias)

La condición acíclica es formal: no existe ningún camino $v_0 \to v_1 \to \cdots \to v_k = v_0$ donde $v_k$ regrese a $v_0$. Si tu DAG tiene ciclos, el scheduler entra en loop infinito o te lo rechaza al cargar.

El orden topológico $T: V \to \mathbb{N}$ asigna a cada vértice un número que indica cuándo puede ejecutarse:

$$T(v) = \begin{cases} 0 & \text{si } \deg^-(v) = 0 \text{ (sin dependencias)} \\ 1 + \max_{(u,v) \in E} T(u) & \text{en otro caso} \end{cases}$$

Donde $\deg^-(v)$ es el in-degree (número de dependencias entrantes). El camino crítico es la secuencia de tareas con la mayor duración acumulada:

$$L_{critical} = \max_{p \in \text{paths}(v_{start}, v_{end})} \sum_{v \in p} w(v)$$

Donde $w(v)$ es la duración estimada de la tarea $v$. Este es el lower bound de tiempo total de ejecución del pipeline: si tu tarea crítica dura 4 horas, tu pipeline mínimo tarda 4 horas, sin importar cuánto paralelices lo demás.

En Airflow, esto se traduce en execution_date (cuándo debería haber corrido según el schedule), dag_run (la ejecución concreta) y task_instance (cada tarea individual con su estado). En kfp, se traduce en PipelineRun, TaskRun y Artifact (los outputs tipados que pasan entre componentes).

2. Como Airflow y kfp resuelven esto por vos

Apache Airflow tiene tres componentes clave:

┌─────────────────────────────────────────────────────┐
│                   DAG File (Python)                  │
│  Define tasks, dependencies, schedule, retries       │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│              Scheduler (parsing loop)                │
│  - Parse DAG files                                  │
│  - Create DagRuns segun schedule_interval            │
│  - Schedule TaskInstances cuando deps esten listas  │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│        Metadata DB (Postgres/MySQL/SQLite)           │
│  - DAGs, DagRuns, TaskInstances, XCom, Logs         │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│              Executor (Local/Celery/K8s)             │
│  - Lanza workers para cada TaskInstance             │
│  - Reporta estado de vuelta a la DB                 │
└─────────────────────────────────────────────────────┘

El scheduler hace un loop continuo: parsea los .py de los DAGs, decide qué DagRun crear según el schedule_interval (cron o @daily), y cuando todas las dependencias upstream de una TaskInstance están en estado success, la enqueue al executor.

Kubeflow Pipelines (kfp) toma otro enfoque: cada paso es un contenedor Docker, el DAG se define en Python pero se compila a un Argo Workflow (CRD de Kubernetes), y el motor es el propio Kubernetes scheduler. La metadata se guarda en ML Metadata (MLMD), una base que trackea no solo el linaje del pipeline, sino también los artefactos ML (datasets, modelos, métricas) con tipos y versiones.

┌─────────────────────────────────────────────────────┐
│       kfp SDK (Python DSL o @component decorator)   │
│  Define components -> compile -> upload to KFP UI   │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│              KFP API Server                          │
│  - Recibe pipeline + run requests                   │
│  - Crea CRDs de Argo Workflows                      │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│           Argo Workflows Controller                  │
│  - Ejecuta steps como Kubernetes Pods               │
│  - Pasa outputs entre containers tipados            │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│              ML Metadata (MLMD)                     │
│  - Artifact store (S3/GCS/MinIO)                    │
│  - Metadata DB (MySQL) con tipos y linaje           │
└─────────────────────────────────────────────────────┘

Diferencia práctica: Airflow es más maduro y flexible (orquestación general), kfp está pensado específicamente para ML (artifact tracking nativo, experiment comparison, model registry integrado). En producción real, muchos equipos usan Airflow para el ETL y kfp para el training/tuning, o Airflow + KubernetesPodOperator para tener un solo sistema.

Pilas con esto: el trigger_rule="all_success" es por defecto, pero puedes usar "one_failed", "all_done", "none_failed" para casos como cleanup que debe correr aun si algo falla.

kfp directo (caso típico: training + tuning + registration):

import kfp
from kfp import dsl
from kfp.dsl import component, Input, Output, Dataset, Model, Metrics

@component(
    base_image="python:3.11-slim",
    packages_to_install=["pandas", "scikit-learn", "great-expectations==0.18.0"],
)
def validate_data(
    input_data: Input[Dataset],
    validation_report: Output[Dataset],
    min_rows: int = 1000,
) -> bool:
    import pandas as pd
    import great_expectations as gx

    df = pd.read_parquet(input_data.path)
    context = gx.get_context(mode="ephemeral")
    data_assistant = context.assistants.onboarding_assistant
    result = data_assistant.run(df)

    passed = result["success"]
    with open(validation_report.path, "w") as f:
        f.write(str(result))
    return passed


@component(
    base_image="python:3.11-slim",
    packages_to_install=["pandas", "xgboost", "scikit-learn"],
)
def train_model(
    train_data: Input[Dataset],
    val_data: Input[Dataset],
    model: Output[Model],
    metrics: Output[Metrics],
    learning_rate: float = 0.1,
    n_estimators: int = 100,
) -> None:
    import pandas as pd
    import xgboost as xgb
    from sklearn.metrics import roc_auc_score

    train_df = pd.read_parquet(train_data.path)
    val_df = pd.read_parquet(val_data.path)

    X_train, y_train = train_df.drop("target", axis=1), train_df["target"]
    X_val, y_val = val_df.drop("target", axis=1), val_df["target"]

    clf = xgb.XGBClassifier(
        learning_rate=learning_rate,
        n_estimators=n_estimators,
        use_label_encoder=False,
        eval_metric="logloss",
    )
    clf.fit(X_train, y_train)
    y_pred_proba = clf.predict_proba(X_val)[:, 1]
    auc = roc_auc_score(y_val, y_pred_proba)

    clf.save_model(model.path + "/model.json")
    metrics.log_metric("val_auc", auc)


@dsl.pipeline(
    name="training-pipeline",
    description="Daily training with validation and registration",
)
def training_pipeline(
    learning_rate: float = 0.1,
    n_estimators: int = 100,
):
    ingest_task = dsl.ContainerOp(
        name="ingest",
        image="myregistry/ingest:latest",
        arguments=["--date", dsl.RUN_ID_PLACEHOLDER],
    )

    validate_task = validate_data(input_data=ingest_task.output)

    with dsl.Condition(validate_task.output == True):
        train_task = train_model(
            train_data=ingest_task.output,
            val_data=ingest_task.output,
            learning_rate=learning_rate,
            n_estimators=n_estimators,
        )


if __name__ == "__main__":
    kfp.compiler.Compiler().compile(training_pipeline, "pipeline.yaml")

El dsl.Condition te permite branching real (si validación falla, no entrenar). Airflow tiene esto con BranchPythonOperator, pero kfp lo hace más natural porque el DSL expresa intención directamente.

4. Implementacion Production-Ready: ML Training Pipeline con Idempotencia y Lineage

Vamos a construir un sistema completo: pipeline de training diario con ingest, validate, train, evaluate, y model registration, con idempotencia (puedes correrlo N veces el mismo día sin romper nada) y lineage tracking (sabes exactamente qué datos generaron qué modelo).

4.1 Tipos y protocolos

Primero, los tipos. Airflow es dinámico (todo es string en XCom), pero kfp tiene tipado fuerte. Vamos a usar Pydantic para validar metadata y enums para estados:

# pipeline_types.py
from enum import Enum
from datetime import datetime
from pydantic import BaseModel, Field, field_validator
from typing import Optional


class RunStatus(str, Enum):
    PENDING = "pending"
    RUNNING = "running"
    SUCCESS = "success"
    FAILED = "failed"
    SKIPPED = "skipped"


class ModelMetrics(BaseModel):
    val_auc: float = Field(ge=0.0, le=1.0)
    val_logloss: float = Field(ge=0.0)
    train_samples: int = Field(gt=0)
    training_duration_sec: float = Field(gt=0.0)

    @field_validator("val_auc")
    @classmethod
    def auc_above_random(cls, v: float) -> float:
        if v < 0.5:
            raise ValueError(f"AUC {v} esta por debajo del azar, modelo inutil")
        return v


class RunMetadata(BaseModel):
    run_id: str
    pipeline_name: str
    execution_date: datetime
    git_sha: str = Field(min_length=7, max_length=40)
    data_version: str
    model_version: Optional[str] = None
    metrics: Optional[ModelMetrics] = None
    status: RunStatus = RunStatus.PENDING

El field_validator rechaza AUCs menores a 0.5 antes de que entren al metadata. Eso evita que un modelo roto se registre en producción.

4.2 El motor principal

El DAG de Airflow con idempotencia real (cada task puede re-ejecutarse sin corromper estado):

# ml_training_dag.py
import os
import json
import logging
from datetime import datetime, timedelta
import numpy as np
from airflow import DAG
from airflow.operators.python import PythonOperator, BranchPythonOperator
from airflow.operators.empty import EmptyOperator
from airflow.utils.trigger_rule import TriggerRule
from pipeline_types import RunMetadata, ModelMetrics, RunStatus

logger = logging.getLogger(__name__)

MLFLOW_TRACKING_URI = os.getenv("MLFLOW_TRACKING_URI", "http://mlflow:5000")
MIN_AUC_THRESHOLD = 0.75  # minimo absoluto para promocion


def _get_run_metadata(**context) -> dict:
    """Construye metadata al inicio del run."""
    ti = context["ti"]
    run_id = context["run_id"]

    metadata = RunMetadata(
        run_id=run_id,
        pipeline_name="daily_training_v1",
        execution_date=context["logical_date"],
        git_sha=os.getenv("GIT_SHA", "unknown"),
        data_version=context["ds_nodash"],
        status=RunStatus.RUNNING,
    )

    # Persiste en XCom como JSON
    ti.xcom_push(key="run_metadata", value=metadata.model_dump())
    logger.info(f"Run {run_id} iniciado con data_version={metadata.data_version}")
    return metadata.model_dump()


def _validate_and_extract(**context) -> str:
    """Idempotente: si el dataset ya existe para este ds, lo reusa."""
    from minio import Minio
    from minio.error import S3Error

    ti = context["ti"]
    metadata = ti.xcom_pull(key="run_metadata", task_ids="init")
    ds = metadata["data_version"]

    client = Minio(
        os.getenv("MINIO_ENDPOINT", "minio:9000"),
        access_key=os.getenv("MINIO_ACCESS_KEY"),
        secret_key=os.getenv("MINIO_SECRET_KEY"),
        secure=False,
    )

    bucket = "ml-training"
    object_key = f"raw/{ds}/features.parquet"

    # Idempotencia: verifica si ya existe
    try:
        obj = client.stat_object(bucket, object_key)
        logger.info(f"Dataset {ds} ya existe ({obj.size} bytes), reusando")
        return "data_already_exists"
    except S3Error:
        pass

    # Si no existe, lo crea
    extract_from_source(ds, client, bucket, object_key)
    return "data_extracted"


def _branch_extraction(**context) -> str:
    """Decide si salta extraction o no (idempotencia)."""
    result = context["ti"].xcom_pull(task_ids="extract")
    if result == "data_already_exists":
        return "skip_extract"
    return "validate_data"


def _train_and_log(**context) -> dict:
    """Entrena y registra en MLflow con linaje completo."""
    import mlflow
    import mlflow.xgboost
    import xgboost as xgb
    import pandas as pd
    from sklearn.metrics import roc_auc_score
    import time

    mlflow.set_tracking_uri(MLFLOW_TRACKING_URI)
    ti = context["ti"]
    metadata = ti.xcom_pull(key="run_metadata", task_ids="init")

    train_df = pd.read_parquet(f"s3://ml-training/processed/{metadata['data_version']}/train.parquet")
    val_df = pd.read_parquet(f"s3://ml-training/processed/{metadata['data_version']}/val.parquet")

    X_train, y_train = train_df.drop("target", axis=1), train_df["target"]
    X_val, y_val = val_df.drop("target", axis=1), val_df["target"]

    start = time.time()
    with mlflow.start_run(run_name=f"train_{metadata['data_version']}") as run:
        mlflow.set_tag("git_sha", metadata["git_sha"])
        mlflow.set_tag("data_version", metadata["data_version"])

        params = {"learning_rate": 0.05, "max_depth": 6, "n_estimators": 200}
        mlflow.log_params(params)

        clf = xgb.XGBClassifier(**params, use_label_encoder=False, eval_metric="logloss")
        clf.fit(X_train, y_train)

        y_pred_proba = clf.predict_proba(X_val)[:, 1]
        # Verificacion numerica: AUC debe estar entre 0.5 y 1.0
        auc = roc_auc_score(y_val, y_pred_proba)
        # Si y_pred_proba incluye extremos (0 o 1), np.log da -inf -> usamos eps
        eps = 1e-15
        logloss = -(
            y_val * np.log(y_pred_proba + eps)
            + (1 - y_val) * np.log(1 - y_pred_proba + eps)
        ).mean()

        duration = time.time() - start
        mlflow.log_metric("val_auc", auc)
        mlflow.log_metric("val_logloss", logloss)
        mlflow.log_metric("training_duration_sec", duration)
        mlflow.xgboost.log_model(clf, "model")

        metrics = ModelMetrics(
            val_auc=auc,
            val_logloss=logloss,
            train_samples=len(train_df),
            training_duration_sec=duration,
        )
        metadata["metrics"] = metrics.model_dump()
        metadata["model_version"] = run.info.run_id
        metadata["status"] = RunStatus.SUCCESS

        ti.xcom_push(key="run_metadata", value=metadata)

        logger.info(f"Training AUC={auc:.4f}, logloss={logloss:.4f}")
        return metadata


def _decide_promotion(**context) -> str:
    """Decide si el modelo va a staging o se descarta."""
    ti = context["ti"]
    metadata = ti.xcom_pull(key="run_metadata", task_ids="train")
    auc = metadata["metrics"]["val_auc"]

    if auc < MIN_AUC_THRESHOLD:
        logger.warning(f"AUC {auc} < threshold {MIN_AUC_THRESHOLD}, descartando modelo")
        return "discard_model"
    return "promote_to_staging"


def _promote_to_staging(**context) -> None:
    """Promueve el modelo a staging en MLflow Model Registry."""
    import mlflow
    from mlflow.tracking import MlflowClient

    ti = context["ti"]
    metadata = ti.xcom_pull(key="run_metadata", task_ids="train")
    run_id = metadata["model_version"]

    client = MlflowClient(tracking_uri=MLFLOW_TRACKING_URI)
    model_uri = f"runs:/{run_id}/model"
    mv = mlflow.register_model(model_uri, "production_model")

    client.transition_model_version_stage(
        name="production_model",
        version=mv.version,
        stage="Staging",
    )
    logger.info(f"Modelo version {mv.version} promovido a Staging")


default_args = {
    "owner": "ml-platform",
    "retries": 1,
    "retry_delay": timedelta(minutes=10),
    "execution_timeout": timedelta(hours=4),
}

with DAG(
    dag_id="daily_ml_training",
    default_args=default_args,
    schedule_interval="0 4 * * *",
    start_date=datetime(2024, 1, 1),
    catchup=False,
    max_active_runs=1,
    tags=["ml", "production"],
) as dag:

    init = PythonOperator(task_id="init", python_callable=_get_run_metadata)

    extract = PythonOperator(task_id="extract", python_callable=_validate_and_extract)

    branch_extract = BranchPythonOperator(
        task_id="branch_extract",
        python_callable=_branch_extraction,
    )

    skip_extract = EmptyOperator(task_id="skip_extract")

    validate_data = PythonOperator(
        task_id="validate_data",
        python_callable=validate_with_great_expectations,
    )

    train = PythonOperator(task_id="train", python_callable=_train_and_log)

    branch_promote = BranchPythonOperator(
        task_id="branch_promote",
        python_callable=_decide_promotion,
    )

    promote = PythonOperator(task_id="promote_to_staging", python_callable=_promote_to_staging)
    discard = EmptyOperator(task_id="discard_model")

    finalize = EmptyOperator(
        task_id="finalize",
        trigger_rule=TriggerRule.NONE_FAILED_MIN_ONE_SUCCESS,
    )

    init >> extract >> branch_extract
    branch_extract >> [skip_extract, validate_data]
    skip_extract >> validate_data
    validate_data >> train >> branch_promote
    branch_promote >> [promote, discard]
    [promote, discard] >> finalize

4.3 Utilidades de analisis y verificacion

Una utilidad para calcular el camino crítico de un DAG programáticamente (lo que Airflow internamente hace para estimar duración):

# dag_analytics.py
from collections import defaultdict, deque
from typing import Dict, List, Tuple


def critical_path(
    tasks: Dict[str, float],
    dependencies: List[Tuple[str, str]],
) -> Tuple[List[str], float]:
    """
    Calcula el camino critico de un DAG.

    Args:
        tasks: {task_id: estimated_duration_sec}
        dependencies: [(upstream, downstream), ...]

    Returns:
        (camino como lista de task_ids, duracion total)

    Verificacion numerica:
        Si tasks = {"A": 5, "B": 3, "C": 7, "D": 2}
        Y deps = [("A", "B"), ("A", "C"), ("B", "D"), ("C", "D")]

        Earliest start de A = 0, finish = 5
        Earliest start de B = 5, finish = 8
        Earliest start de C = 5, finish = 12
        Earliest start de D = max(8, 12) = 12, finish = 14

        Camino critico = A -> C -> D (duracion 14)
    """
    graph = defaultdict(list)
    in_degree = defaultdict(int)

    for upstream, downstream in dependencies:
        graph[upstream].append(downstream)
        in_degree[downstream] += 1

    earliest_finish: Dict[str, float] = {}
    predecessor: Dict[str, str] = {}

    queue = deque([t for t in tasks if in_degree[t] == 0])

    while queue:
        node = queue.popleft()
        node_ef = earliest_finish.get(node, 0) + tasks[node]

        for neighbor in graph[node]:
            if neighbor not in earliest_finish or node_ef > earliest_finish[neighbor]:
                earliest_finish[neighbor] = node_ef - tasks[neighbor]
                predecessor[neighbor] = node

            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)

    end_node = max(earliest_finish, key=lambda n: earliest_finish[n] + tasks[n])
    total_duration = earliest_finish[end_node] + tasks[end_node]

    path = []
    current = end_node
    while current in predecessor:
        path.append(current)
        current = predecessor[current]
    path.append(current)
    path.reverse()

    return path, total_duration


if __name__ == "__main__":
    tasks = {"A": 5.0, "B": 3.0, "C": 7.0, "D": 2.0}
    deps = [("A", "B"), ("A", "C"), ("B", "D"), ("C", "D")]

    path, duration = critical_path(tasks, deps)
    assert path == ["A", "C", "D"], f"Esperado A->C->D, obtuve {path}"
    assert duration == 14.0, f"Esperado 14.0, obtuve {duration}"

    print(f"Camino critico: {' -> '.join(path)}")
    print(f"Duracion total: {duration} unidades")
    # Camino critico: A -> C -> D
    # Duracion total: 14.0 unidades

5. Ejemplos de Uso en Casos Reales

Caso 1: Hyperparameter tuning paralelo con kfp

import kfp
from kfp import dsl
from typing import List

@dsl.pipeline(name="hparam-sweep")
def hparam_sweep_pipeline(
    learning_rates: List[float] = [0.01, 0.05, 0.1],
    max_depths: List[int] = [4, 6, 8],
):
    ingest_task = dsl.ContainerOp(
        name="ingest",
        image="myregistry/ingest:latest",
    )

    # Fan-out: crea N combinaciones
    with dsl.ParallelFor(learning_rates) as lr:
        with dsl.ParallelFor(max_depths) as depth:
            train_task = train_model(
                train_data=ingest_task.output,
                val_data=ingest_task.output,
                learning_rate=lr,
                n_estimators=depth * 50,
            )

            evaluate_task = evaluate_model(
                model=train_task.outputs["model"],
                test_data=ingest_task.outputs["test"],
            )

            with dsl.Condition(evaluate_task.outputs["metrics"] >= 0.80):
                register_task = register_best_model(model=train_task.outputs["model"])

Aquí dsl.ParallelFor genera dinámicamente $|L| \times |D|$ tareas. Con 3 LR × 3 depths = 9 tareas en paralelo. Si cada una tarda 20min y tenés 10 nodos K8s, el sweep completo baja de 3h a 20min. La matemática del speedup es $\text{Speedup} = \frac{T_{serial}}{T_{parallel}} = \frac{N \cdot t_{task}}{t_{task}} = N$ en el caso ideal (perfecto paralelismo sin overhead).

Caso 2: Backfill controlado en Airflow

# Re-corre el pipeline desde el 1 de enero sin lanzar todas las ejecuciones a la vez
airflow dags backfill \
    --start-date 2024-01-01 \
    --end-date 2024-01-31 \
    --reset-dagruns \
    daily_ml_training

El --reset-dagruns limpia los runs fallidos previos; sin esto, Airflow los salta y tu backfill queda incompleto sin avisarte. Si tu DAG tiene max_active_runs=1, Airflow serializa los runs del backfill para no saturar la infra.

Caso 3: Sensor para esperar datos upstream

from airflow.sensors.filesystem import FileSensor

wait_for_data = FileSensor(
    task_id="wait_for_partner_feed",
    filepath="/data/partner/{{ ds }}/feed_*.parquet",
    fs_conn_id="partner_sftp",
    poke_interval=300,  # chequea cada 5min
    timeout=3600 * 4,  # falla si no aparece en 4h
    mode="reschedule",  # libera el worker slot mientras espera
)

Usa mode="reschedule" siempre, no mode="poke". En modo poke, el worker queda ocupado todo el tiempo del sensor; en reschedule, el worker se libera y el scheduler re-evalúa después. Si tenés 50 sensores con poke, te quedas sin workers rápido.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: DAG no aparece en la UI

Detección: revisas la UI y no ves tu DAG. La causa típica es un error de sintaxis en el archivo del DAG que hace fallar el parseo silenciosamente.

# Diagnostico desde CLI
airflow dags list | grep daily_ml_training  # si vacio, hay problema de parsing

# Ver el error exacto
airflow dags report  # muestra errores de parsing en los ultimos runs

Soluciones:

  1. Corré python /opt/airflow/dags/ml_training_dag.py directamente. Si hay error de sintaxis, lo ves al toque.
  2. Verificá que start_date no esté en el futuro (Airflow no ejecuta DAGs con start_date > now()).
  3. Asegurate de que schedule_interval sea válido (string cron o @daily, @hourly).

Problema 2: Tareas zombies

Una tarea zombie es aquella que el scheduler cree que está corriendo pero el proceso real murió (OOM kill, node failure). El scheduler espera su heartbeat hasta el scheduler_zombie_task_threshold (default 300s).

# Encuentra zombies activos
from airflow.models import TaskInstance
from airflow.utils.state import State
from airflow import settings

session = settings.Session()
zombies = (
    session.query(TaskInstance)
    .filter(TaskInstance.state == State.SCHEDULED)
    .filter(TaskInstance.job_id.isnot(None))
    .all()
)

# Si un TI esta en SCHEDULED con job_id pero el job no existe en la DB -> zombie
for ti in zombies:
    job_exists = session.query(Job).filter(Job.id == ti.job_id).first() is not None
    if not job_exists:
        logger.error(f"Zombie detectado: {ti.dag_id}.{ti.task_id} run={ti.run_id}")

Solución: configurá scheduler_zombie_task_threshold bajo (60-120s) y activá scheduler_health_check_threshold. En producción real, un zombie es síntoma de OOM, así que revisá también los logs de Kubernetes (kubectl logs --previous).

Problema 3: Backpressure no funciona y se acumulan runs

Si max_active_runs=1 pero ves 5 runs simultáneos, casi siempre es porque una tarea externa está llamando a la API de Airflow (TriggerDagRunOperator mal configurado) y saltándose el control.

# Diagnostico
airflow dags list-runs --dag-id daily_ml_training --state running

Soluciones:

  1. Forzá max_active_runs=1 en el DAG que recibe el trigger.
  2. Usá reset_dag_run en lugar de borrar runs manualmente.
  3. Configurá external_task_sensor con allowed_states=['success'] y failed_states=['failed', 'skipped'] para no disparar runs dependientes de tasks que fallaron.

7. Optimizaciones de Produccion

Optimizacion 1: Dynamic Task Mapping (Airflow 2.3+) en lugar de loops estáticos

El anti-patrón clásico: generar N tasks con un for loop en Python al definir el DAG. Esto crea tasks en tiempo de parseo, no en tiempo de ejecución, y te revienta el scheduler si N es grande.

# MAL: tasks creadas en parse-time, el scheduler debe gestionarlas todas desde el inicio
for i in range(100):
    PythonOperator(task_id=f"process_chunk_{i}", python_callable=process, op_kwargs={"chunk_id": i})

# BIEN: Dynamic Task Mapping, las tasks se crean solo cuando el upstream termina
from airflow.decorators import task

@task
def get_chunks():
    return [{"chunk_id": i} for i in range(100)]

@task
def process_chunk(chunk: dict):
    process(chunk["chunk_id"])

chunks = get_chunks()
processed = process_chunk.expand(chunk=chunks)

Trade-off: Dynamic Task Mapping te da escalabilidad (10k+ tasks) pero requiere Airflow 2.3+ y complica el debugging (los task_ids se generan dinámicamente como process_chunk__chunk_0, process_chunk__chunk_1, etc.).

Optimizacion 2: Pools para limitar concurrencia en recursos compartidos

Si 50 tasks golpean el mismo Postgres simultáneamente, te quedás sin conexiones. Los pools limitan cuántas tasks de un tipo corren en paralelo:

# Definir pool via CLI
airflow pools set feature_store_pool 5 "Limita a 5 extracciones simultaneas"
# Usar en la task
extract = PythonOperator(
    task_id="extract_features",
    python_callable=extract,
    pool="feature_store_pool",
    pool_slots=1,  # esta task consume 1 slot
)

Trade-off: los pools previenen saturación pero pueden crear deadlocks si task A toma 2 slots del pool X y task B toma 1 slot de Y mientras espera a X. Verificá con airflow pools list y monitoreá el queued state de las tasks.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

  • Idempotencia: tu pipeline puede re-ejecutarse N veces el mismo día sin corromper datos. Sin esto, cada re-run es una bomba de tiempo.
  • Lineage tracking: cuando producción se cae, en 5 minutos sabes qué versión del modelo, qué datos, qué código generaron el bug. Sin esto, estás adivinando.
  • SLA + retries selectivos: tasks críticas con SLA estricto y retries; tasks idempotentes sin SLA. Sin esta distinción, todo falla o todo es estricto.
  • Backpressure con pools: limitas concurrencia a recursos compartidos (DB, API rate limits). Sin esto, un pico de carga te tira la infra.
  • Branching con condiciones: el pipeline decide solo si promover, descartar o re-entrenar. Sin esto, dependes de un humano revisando logs a las 3am.

Checklist mínima antes de producción:

  1. ¿Cada task es idempotente? (puede re-ejecutarse sin side effects)
  2. ¿Tienes retries + alertas para tasks críticas?
  3. ¿El metadata se persiste en una DB externa (no SQLite)?
  4. ¿Los secrets vienen de un secrets backend (Vault, AWS SM), no de variables de Airflow?
  5. ¿Tienes un DAG de "health check" que verifica que los sensors externos responden?

Mañana seguimos con algo que va directo al corazón de esto: cómo diseñar el feature store que alimenta estos pipelines sin que se vuelva un cementerio de datos sucios. Eso sí o sí lo tenemos que desmontar bien.
