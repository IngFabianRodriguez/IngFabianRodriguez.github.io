Introduccion: Tu RAG devuelve basura a las 3am y todos los embeddings viven en 0.87

Mira, a las tres de la manana del viernes tu pipeline RAG llevaba dos semanas en staging. Los embeddings ya estaban indexados en Qdrant, el LLM respondía con citas precisas... pero las citas eran de documentos equivocados. Abriste el dashboard, miraste las top-k similitudes: todas entre 0.83 y 0.91, una distribución sospechosamente plana. Cuando le mostraste los chunks a un humano, dos de tres eran irrelevantes. ¿Dónde se cayó esto?

El 80% de las veces, el problema no está ni en el LLM ni en el vector DB. Está en cómo calculaste los embeddings, en que usaste un modelo para indexar y otro para query, o en que tu tamaño de chunk confunde tópicos. Este artículo es sobre esa capa. La capa que convierte texto en vectores, y la matemática que decide si dos vectores son "similares" o no.

Te voy a mostrar qué es un embedding de verdad (con la matemática, símbolo por símbolo), cómo text-embedding-3 de OpenAI y los modelos de sentence-transformers resuelven esto internamente, y cómo armar un sistema production-ready que sobreviva el lunes a las 9am cuando llega el CFO preguntando por qué el bot inventó una póliza inexistente.

1. Que son los Embeddings RAG? (Y por que deberia importarte)

1.1 La analogia cotidiana: la tabla periodica de Mendeleiev

En 1869 Dmitri Mendeleiev organizó 63 elementos conocidos en una tabla, ordenados por peso atómico (un escalar). Lo notable no fue el orden, sino las columnas: elementos con comportamiento químico similar (metales alcalinos, halógenos, gases nobles) terminaron automáticamente agrupados verticalmente. La tabla era 2D en papel, pero la química que codificaba era multi-dimensional. Cuando Mendeleiev dejó huecos, predijo elementos que aún no se descubrían (galio, escandio, germanio) y acertó en sus propiedades.

Un embedding es la generalización de esa tabla a miles de dimensiones. Cada palabra, frase o párrafo tiene una "coordenada" en un espacio vectorial donde la proximidad geométrica codifica similitud semántica. "Rey" y "Reina" viven cerca (difieren en una dimensión de género). "Rey" y "Constitución" viven lejos. Esa distancia es lo que tu vector DB usa para decidir qué recupera cuando llega un query.

La diferencia clave: Mendeleiev ordenó por UNA dimensión (peso atómico) y la química emergió en la perpendicular. Los embeddings modernos codifican TODAS las dimensiones simultáneamente durante el entrenamiento contrastivo. El espacio no es 2D, es de 384, 768, 1536 o 3072 dimensiones. Pero el principio es el mismo: posición geométrica = significado cuantificable.

1.2 La matematica formal: que es un embedding, simbolo por simbolo

Un embedding es una función paramétrica:

$$f_\theta: \mathcal{V} \rightarrow \mathbb{R}^d$$
  • $\mathcal{V}$: vocabulario (conjunto de textos que el modelo puede procesar)
  • $\theta$: parámetros del modelo (pesos aprendidos durante entrenamiento)
  • $d$: dimensión del espacio de salida (1536 para text-embedding-3-small)
  • Resultado: cada texto se mapea a un vector denso de números reales

Para dos textos $q$ (query) y $d$ (documento):

$$f_\theta(q) = \mathbf{u} \in \mathbb{R}^d, \quad f_\theta(d) = \mathbf{v} \in \mathbb{R}^d$$

La similitud coseno entre ambos vectores es:

$$\text{sim}(\mathbf{u}, \mathbf{v}) = \cos(\theta) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\|_2 \|\mathbf{v}\|_2} = \frac{\sum_{i=1}^{d} u_i v_i}{\sqrt{\sum_{i=1}^{d} u_i^2} \sqrt{\sum_{i=1}^{d} v_i^2}}$$

Símbolo por símbolo:

  • $\mathbf{u} \cdot \mathbf{v}$: producto punto (suma del producto componente a componente)
  • $\|\mathbf{u}\|_2$: norma L2 (magnitud euclidiana del vector, $\sqrt{\sum u_i^2}$)
  • $\theta$: ángulo geométrico entre los vectores (no confundir con los parámetros del modelo, mala notación histórica)
  • Resultado: escalar en $[-1, 1]$ donde $1$ = vectores idénticos, $0$ = ortogonales, $-1$ = opuestos

Para RAG, la recuperación top-k se formula como:

$$\text{top-k}(q) = \arg\max_{d_i \in \mathcal{D}}^{(k)} \text{sim}(f_\theta(q), f_\theta(d_i))$$

Esto es: de los $N$ documentos en tu colección $\mathcal{D}$, devuelve los $k$ con mayor similitud coseno al query. Tu vector DB hace esto en milisegundos vía HNSW o IVF, no brute force sobre millones de vectores.

Verificación numérica manual (no es embedding real, solo el cálculo):

import numpy as np

u = np.array([1.0, 2.0, 3.0])
v = np.array([4.0, 5.0, 6.0])
# Manual: dot = 1*4 + 2*5 + 3*6 = 32
#         ||u|| = sqrt(1+4+9) = sqrt(14) ≈ 3.7417
#         ||v|| = sqrt(16+25+36) = sqrt(77) ≈ 8.7750
#         cos = 32 / (3.7417 * 8.7750) ≈ 0.9746
expected = 32 / (np.sqrt(14) * np.sqrt(77))
computed = float(np.dot(u, v) / (np.linalg.norm(u) * np.linalg.norm(v)))
assert abs(computed - expected) < 1e-9
print(f"{computed:.4f}")  # 0.9746

                                                                          (L2 normalize opcional)

3. openai-python y sentence-transformers: Uso Directo y Casos de Control Fino

# OpenAI directo con control fino de dimensiones (Matryoshka)
from openai import OpenAI

client = OpenAI()

# Full 1536 dims
resp_full = client.embeddings.create(
    model="text-embedding-3-small",
    input=["Como configurar Kafka para streaming de eventos"],
)
vec_full = resp_full.data[0].embedding
assert len(vec_full) == 1536

# Truncado a 256 dims (mismo modelo, 6x menos storage)
resp_short = client.embeddings.create(
    model="text-embedding-3-small",
    input=["Como configurar Kafka para streaming de eventos"],
    dimensions=256,
)
vec_short = resp_short.data[0].embedding
assert len(vec_short) == 256
# sentence-transformers local
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2", device="cuda")
vectors = model.encode(
    ["Como configurar Kafka", "Tutorial de PostgreSQL", "Receta de arepas"],
    batch_size=32,
    normalize_embeddings=True,  # L2 normalize: cosine sim = dot product puro
    show_progress_bar=True,
)
# vectors.shape == (3, 384)

El parámetro normalize_embeddings=True es la decisión operativa más importante que puedes tomar: si los vectores están normalizados a longitud 1, la similitud coseno se reduce a un producto punto puro ($\|\mathbf{u}\|_2 = \|\mathbf{v}\|_2 = 1 \Rightarrow \cos(\theta) = \mathbf{u} \cdot \mathbf{v}$). Esto te ahorra el cálculo de la raíz cuadrada en cada query del vector DB, lo cual en producción significa 15-25% menos latencia en HNSW.

4.2 El motor principal

import hashlib
import numpy as np
from tenacity import retry, stop_after_attempt, wait_exponential
from openai import OpenAI

class ProductionEmbedder:
    def __init__(
        self,
        model: str = "text-embedding-3-small",
        dimensions: int | None = None,
        cache_max_entries: int = 50_000,
    ):
        self.client = OpenAI()
        self.model = model
        self.dimensions = dimensions
        self._cache: dict[str, np.ndarray] = {}
        self._cache_max = cache_max_entries

    def _cache_key(self, text: str) -> str:
        return hashlib.sha256(
            f"{self.model}:{self.dimensions}:{text}".encode()
        ).hexdigest()

    @retry(stop=stop_after_attempt(3), wait=wait_exponential(min=1, max=10))
    def _embed_remote(self, texts: list[str]) -> list[list[float]]:
        kwargs: dict = {"model": self.model, "input": texts}
        if self.dimensions is not None:
            kwargs["dimensions"] = self.dimensions
        resp = self.client.embeddings.create(**kwargs)
        return [item.embedding for item in resp.data]

    def embed(self, texts: list[str]) -> np.ndarray:
        if not texts:
            return np.empty((0, self.dimensions or 1536), dtype=np.float32)

        results: list[np.ndarray | None] = [None] * len(texts)
        to_fetch: list[tuple[int, str]] = []

        for i, text in enumerate(texts):
            key = self._cache_key(text)
            cached = self._cache.get(key)
            if cached is not None:
                results[i] = cached
            else:
                to_fetch.append((i, text))

        if to_fetch:
            # Dedup antes de mandar a la API (ahorra tokens si hay repetidos)
            unique_texts = list({t: None for _, t in to_fetch})
            fetched = self._embed_remote(unique_texts)
            fetched_map = dict(zip(unique_texts, fetched))

            for orig_idx, text in to_fetch:
                vec = np.asarray(fetched_map[text], dtype=np.float32)
                key = self._cache_key(text)
                if len(self._cache) < self._cache_max:
                    self._cache[key] = vec
                results[orig_idx] = vec

        return np.vstack([r for r in results])  # type: ignore[arg-type]

    def embed_documents(self, documents: list[Document]) -> list[Document]:
        """Devuelve los mismos documentos con el campo `embedding` poblado."""
        if not documents:
            return documents
        vectors = self.embed([d.content for d in documents])
        return [
            Document(d.doc_id, d.content, d.metadata, vectors[i])
            for i, d in enumerate(documents)
        ]

4.3 Utilidades de analisis y verificacion

import numpy as np

def cosine_similarity_matrix(vectors: np.ndarray) -> np.ndarray:
    """Matriz de similitud coseno pairwise. Input shape: (n, d)."""
    norms = np.linalg.norm(vectors, axis=1, keepdims=True)
    normalized = vectors / np.clip(norms, 1e-12, None)
    return normalized @ normalized.T

def diagnose_embedding_distribution(
    vectors: np.ndarray, sample_size: int = 1000, seed: int = 42
) -> dict:
    """Detecta embeddings degenerados (todos demasiado similares entre si)."""
    rng = np.random.default_rng(seed)
    n = min(len(vectors), sample_size)
    idx = rng.choice(len(vectors), n, replace=False)
    sims = cosine_similarity_matrix(vectors[idx])
    mask = ~np.eye(n, dtype=bool)
    off_diag = sims[mask]
    return {
        "n_sampled": n,
        "mean_similarity": float(off_diag.mean()),
        "std_similarity": float(off_diag.std()),
        "p5_similarity": float(np.percentile(off_diag, 5)),
        "p95_similarity": float(np.percentile(off_diag, 95)),
        "concentration_warning": bool(off_diag.std() < 0.05),
    }

5. Ejemplos de Uso en Casos Reales

Caso 1: QA sobre documentacion tecnica

embedder = ProductionEmbedder(model="text-embedding-3-small", dimensions=512)

corpus = [
    Document("1", "Kafka usa particiones para paralelizar el consumo de mensajes"),
    Document("2", "PostgreSQL es una base de datos relacional con garantias ACID"),
    Document("3", "RabbitMQ implementa el protocolo AMQP con exchanges y colas"),
    Document("4", "MongoDB almacena documentos JSON sin esquema fijo"),
]
corpus = embedder.embed_documents(corpus)

query = "Como escalar el consumo de mensajes en un broker"
q_vec = embedder.embed([query])[0]

scores = cosine_similarity_matrix(
    np.vstack([q_vec] + [d.embedding for d in corpus])
)[0, 1:]
# Verificacion manual por inspeccion semantica:
#   - Doc 1 (Kafka particiones) deberia ser el mas similar
#   - Doc 3 (RabbitMQ AMQP) segundo (ambos son message brokers)
#   - Doc 2 (PostgreSQL) tercero (no es broker, pero es DB)
#   - Doc 4 (MongoDB) cuarto (no es broker ni SQL)
ranking = np.argsort(-scores)
expected_ranking = [0, 2, 1, 3]
assert list(ranking) == expected_ranking, f"Ranking insospechado: {ranking}"

multi_model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: Distribucion de similitudes colapsada

Síntoma: todas las similitudes coseno del retrieval están entre 0.83 y 0.91, planas, sin varianza. El modelo no está discriminando.

Causa raíz más probable: modelo de embedding débil para tu dominio, o corpus con textos demasiado uniformes.

Reproducción y detección:

# Suponiendo que ya tienes 'all_doc_vectors' como np.ndarray (N, d)
stats = diagnose_embedding_distribution(all_doc_vectors)
# Ejemplo de salida problematico:
# {"mean_similarity": 0.87, "std_similarity": 0.02,
#  "p5_similarity": 0.84, "p95_similarity": 0.90,
#  "concentration_warning": True}

Si std_similarity < 0.05, tenés un problema. Soluciones:

  1. Subir de modelo: de text-embedding-3-small a text-embedding-3-large, o de all-MiniLM-L6-v2 a bge-large-en-v1.5. Costo: 6x más en API, 16x más en disco local.
  2. Verificar normalización: si los vectores NO están normalizados, la similitud coseno se distorsiona. Mide np.linalg.norm(vectors, axis=1) — debería estar cerca de 1.0 para todo vector.
  3. Revisar el input: si todos tus chunks son variaciones de la misma plantilla ("Item: X, Price: Y, Stock: Z"), ningún embedding va a diferenciar.
  4. Fine-tuning de dominio: si el dominio es muy especializado (legal, médico), un modelo base no va a capturar la semántica. Considera text-embedding-3 con fine-tuning supervisado o un modelo especializado.

Problema 2: Chunk size mata la coherencia semantica

Síntoma: los chunks recuperados son del documento correcto pero del párrafo equivocado.

Causa raíz: chunks de 4000+ tokens que confunden múltiples tópicos en un solo vector. El embedding promedia (pooling) sobre demasiados tokens y pierde señal.

Reproducción:

# Texto de 8K tokens con 4 topicos distintos
long_text = ("Seccion A sobre Kafka. " * 500 +
             "Seccion B sobre Postgres. " * 500 +
             "Seccion C sobre Redis. " * 500 +
             "Seccion D sobre MongoDB. " * 500)
vec_full = embedder.embed([long_text])[0]

# Cuando queries "Como escalar Redis", el embedding del chunk largo
# promedia Redis con Kafka/Postgres/MongoDB y la similitud cae ~40%
vec_query_redis = embedder.embed(["Como escalar Redis"])[0]
vec_query_kafka = embedder.embed(["Como escalar Kafka"])[0]

sim_redis = float(np.dot(vec_full, vec_query_redis) /
                  (np.linalg.norm(vec_full) * np.linalg.norm(vec_query_redis)))
sim_kafka = float(np.dot(vec_full, vec_query_kafka) /
                  (np.linalg.norm(vec_full) * np.linalg.norm(vec_query_kafka)))
# Ambas similitudes quedan en el mismo rango (~0.65-0.75) porque
# el vector del chunk largo confunde topicos
print(f"sim_redis={sim_redis:.3f}, sim_kafka={sim_kafka:.3f}")

Solución: chunks de 200-500 tokens con overlap del 10-15%. Para documentos con estructura clara (headers, secciones), usa chunking semántico que respeta límites de párrafo.

Problema 3: Modelo de indexacion != modelo de query

Síntoma: las similitudes son ruido aleatorio, no correlacionan con relevancia.

Reproducción:

index_model = "text-embedding-3-small"   # modelo con el que indexaste
query_model = "text-embedding-3-large"  # modelo que usas para queries (ERROR)

# Vectores en espacios diferentes -> dot product ≈ ruido

Diagnóstico: corre diagnose_embedding_distribution sobre una muestra de queries contra el índice. Si mean_similarity < 0.3, hay mismatch de modelos.

Solución: pinning de versión. Define EMBEDDING_MODEL = "text-embedding-3-small@2024-01" como constante global, y úsala en TODOS los lugares donde calculas embeddings. Si cambias de modelo, re-indexa todo el corpus. Sin excepciones.

7. Optimizaciones de Produccion

Optimizacion 1: Matryoshka truncation con evaluation local

Si tu corpus tiene >1M documentos, el costo de storage y RAM en el vector DB domina. Truncar de 1536 a 512 dims te da 3x reducción con ~2-4% drop en MTEB promedio, pero el drop varía por dominio. Mide antes de comprometer.

# Evaluar Matryoshka contra tu gold set antes de migrar
def evaluate_dimensions(
    embedder_factory, dims_to_test: list[int], queries: list[str],
    gold_relevant: list[set[str]], corpus: list[Document]
) -> dict[int, float]:
    """Retorna recall@10 por cada dimension probada."""
    results = {}
    for d in dims_to_test:
        emb = embedder_factory(dimensions=d)
        corpus_emb = emb.embed_documents(corpus)
        q_vecs = emb.embed(queries)
        recall_at_10 = []
        for q_vec, gold in zip(q_vecs, gold_relevant):
            scores = cosine_similarity_matrix(
                np.vstack([q_vec] + [c.embedding for c in corpus_emb])
            )[0, 1:]
            top10 = set(np.argsort(-scores)[:10].astype(str))
            recall_at_10.append(len(top10 & gold) / max(len(gold), 1))
        results[d] = float(np.mean(recall_at_10))
    return results

Trade-off: storage lineal en $d$, pero recall decae más rápido en dominios técnicos con jerga especializada que en lenguaje general. No confíes en benchmarks genéricos, mide contra tu gold set.

Optimizacion 2: Hybrid search (BM25 + dense)

Embeddings capturan semántica, BM25 captura match exacto de términos (siglas, códigos de error, identificadores). El score combinado:

$$\text{score}(q, d) = \alpha \cdot \text{sim}_{\text{cos}}(f_\theta(q), f_\theta(d)) + (1-\alpha) \cdot \text{BM25}_{\text{norm}}(q, d)$$

Con $\alpha \in [0.5, 0.7]$ típicamente. Soluciona el caso clásico donde query es ERROR_42_CONNECTION_TIMEOUT y los embeddings no capturan que el usuario busca el doc con ese código exacto.

# Pseudo-implementacion conceptual de hybrid scoring
def hybrid_score(
    cosine_scores: np.ndarray,  # shape (n,), ya normalizado a [0, 1]
    bm25_scores: np.ndarray,    # shape (n,), normalizado a [0, 1]
    alpha: float = 0.6,
) -> np.ndarray:
    return alpha * cosine_scores + (1 - alpha) * bm25_scores

Implementaciones reales: Qdrant tiene fusion con RRF (Reciprocal Rank Fusion), Vespa lo hace nativo, Milvus tiene hybrid search built-in. No lo implementes a mano.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

  • Un embedding NO es una caja negra magica: es una función $\mathbb{R}^d$ entrenada para que proximidad geométrica = similitud semántica. Entender esto te dice exactamente cuándo falla y por qué.
  • Matryoshka embeddings (dimensions=N en text-embedding-3) son el trade-off storage/recall más subestimado que existe. Si tu corpus es >1M docs, ahorra 50-70% del costo del vector DB sin perder recall relevante.
  • Cosine sim asume distribución razonable de vectores: si todas tus similitudes viven en $[0.85, 0.92]$, algo está mal antes de tocar el LLM. Usa diagnose_embedding_distribution como primer paso de cualquier incidente RAG.
  • El modelo de indexación y query DEBEN ser el mismo, con versión pinneada. Cambiar de modelo sin re-indexar destruye silenciosamente la calidad de retrieval. Es la causa #1 de regresiones en producción.
  • El chunk size es la variable oculta que más impacta recall: entre 200 y 500 tokens con 10-15% de overlap. Chunks más grandes promedian demasiados tópicos. Más pequeños pierden contexto.

Mini-checklist antes de subir a producción:

  • [ ] Mismo modelo y versión pinneada en index y query
  • [ ] L2 normalize activado (normalize_embeddings=True o equivalente)
  • [ ] Chunk size entre 200-500 tokens con overlap 10-15%
  • [ ] Distribución de similitudes diagnosticada: std_similarity > 0.05
  • [ ] Gold set de ~100 queries con relevance judgments para evaluar recall@10
  • [ ] Monitoreo de P50/P95 latencia y drift de distribución de similitudes

Pilas con esto parce, porque esa vaina del RAG que devuelve basura a las 3am casi siempre se resuelve en esta capa, no en el prompt del LLM ni en el retriever fancy. Mide embeddings antes de culpar al modelo generativo. 🧭
