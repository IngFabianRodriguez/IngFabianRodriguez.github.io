Introducción: Tu modelo se muere en silencio

Tienes un modelo de fraude que en el AUC del paper marcaba 0.94. Lo desplegaste en marzo. En julio estás perdiendo 12 millones de pesos diarios porque la distribución de las transacciones cambió después de una actualización en el sistema de pagos del proveedor. Nadie te avisó. El dashboard sigue marcando verde porque el servicio responde 200 OK. Tu modelo no se cayó: se pudrió.

Eso es lo que el model monitoring ataca. El uptime del endpoint no te dice nada sobre si las predicciones siguen siendo buenas. Un modelo puede estar devolviendo HTTP 200 con cada predicción durante seis meses mientras degrada silenciosamente porque los datos de entrada cambiaron, el target se movió, o el upstream le mandó una columna con valores nuevos. El viejo truco de "voy a reentrenar cada tres meses" ya no sirve cuando la drift puede aparecer en una semana.

La librería evidently resuelve exactamente esto: te entrega las herramientas matemáticas y los reportes visuales para detectar cuándo y dónde la distribución de tus features, tu target o tu performance se están separando del baseline. No es magia, es estadística con UI decente, y se conecta a tu pipeline en menos de 50 líneas.

1. Qué es Model Monitoring? (Y por qué debería importarte)

1.1 La analogía cotidiana: el mecánico de tractomula

Mirá a un mecánico de tractomulas en carretera larga. El camión (tu modelo) salió de la planta rodando perfecto, con todos los instrumentos calibrados. Pero en la ruta hay polvo, cambios de altura, carga que se mueve, combustible de distinta calidad según la estación. El mecánico no espera a que el motor reviente: cada cierto kilometraje revisa presión de aceite, temperatura del refrigerante, desgaste de frenos, calibración de llantas. Tiene instrumentos (manómetros, termómetros, tacómetros) y umbrales definidos: si la temperatura pasa de 95 °C, detiene el camión.

Model monitoring es exactamente eso para tu modelo: un conjunto de instrumentos estadísticos (PSI, KS, Jensen-Shannon, chi-cuadrado) que comparan la distribución actual contra una de referencia, más umbrales que disparan alertas. La diferencia clave: en el camión los sensores están cableados al motor; en ML tenés que conectarlos vos al pipeline de predicción.

1.2 La matemática formal

Hay tres métricas que evidently usa por debajo para detectar drift. Te las explico símbolo por símbolo porque ninguna sirve si no entendés qué mide realmente.

Population Stability Index (PSI): es la métrica clásica de industria financiera.

$$\text{PSI} = \sum_{i=1}^{k} (p_i^{\text{act}} - p_i^{\text{ref}}) \cdot \ln\left(\frac{p_i^{\text{act}}}{p_i^{\text{ref}}}\right)$$

Donde:

  • $k$: número de buckets en los que discretizás la variable (típicamente 10 o 20).
  • $p_i^{\text{ref}}$: proporción de muestras de referencia que caen en el bucket $i$.
  • $p_i^{\text{act}}$: proporción de muestras actuales que caen en el bucket $i$.
  • $\ln$: logaritmo natural.

Interpretación operativa: $\text{PSI} < 0.1$ distribución estable, $0.1 \le \text{PSI} < 0.2$ cambio menor que requiere atención, $\text{PSI} \ge 0.2$ drift significativo, reentrenar.

Kolmogorov-Smirnov (KS) statistic: compara dos funciones de distribución empíricas.

$$D_{n,m} = \sup_{x} \left| F_{1,n}(x) - F_{2,m}(x) \right|$$

Donde:

  • $F_{1,n}(x)$: ECDF (Empirical Cumulative Distribution Function) de la muestra de referencia, evaluada en $x$.
  • $F_{2,m}(x)$: ECDF de la muestra actual.
  • $\sup_{x}$: supremo sobre todo $x$ en el dominio, es decir, la máxima distancia vertical entre las dos curvas acumuladas.

evidently lo reporta en $[0, 1]$: valores cercanos a 0 implican distribuciones iguales, cercanos a 1 implican distribuciones completamente separadas.

Jensen-Shannon Divergence (JSD): versión simétrica y acotada de KL divergence.

$$\text{JSD}(P \,\|\, Q) = \frac{1}{2} D_{\text{KL}}(P \,\|\, M) + \frac{1}{2} D_{\text{KL}}(Q \,\|\, M), \quad M = \frac{P + Q}{2}$$

Donde $D_{\text{KL}}(P \,\|\, Q) = \sum_i p_i \ln(p_i / q_i)$. A diferencia de KL, JSD es simétrica y siempre acotada en $[0, \ln 2]$, lo cual la hace mucho más cómoda para alertas porque no explota cuando una categoría desaparece en producción.

2. Cómo evidently resuelve esto por vos

evidently se organiza en tres bloques conceptuales:

  1. Metrics: cálculo unitario. Una métrica es una sola medición (PSI de una columna, MAE del modelo, share de nulos).
  2. Reports: composición de métricas con rendering HTML/JSON. Sirven para análisis exploratorio o dashboards semanales.
  3. Test Suites: composición de tests con pass/fail. Sirven para CI/CD de modelos o alertas automatizadas en producción.

Internamente, cada Metric recibe reference_data y current_data (los dos DataFrames que querés comparar) más un ColumnMapping que le indica cuál es target, prediction, numerical_features y categorical_features. evidently decide automáticamente qué prueba estadística aplicar: KS para continuas, chi-cuadrado para categóricas, PSI cuando discretizás.

reference_data ─┐
                ├─► [ColumnMapping] ─► evidently Engine ─► {Report HTML, Test Suite JSON}
current_data  ──┘                              │
                                              ├─► DriftMetrics (PSI, KS, JSD)
                                              ├─► QualityMetrics (MAE, RMSE, F1)
                                              └─► StatisticalMetrics (missing, outliers)

El motor está escrito sobre pandas y numpy puros, sin backend de DB obligatorio, lo cual lo hace liviano para correr in-process o como job batch.

4.2 El motor principal

El motor encapsula evidently y aplica los umbrales:

# monitor/engine.py
from __future__ import annotations

import pandas as pd
from evidently import ColumnMapping
from evidently.metrics import (
    ColumnDriftMetric,
    DatasetDriftMetric,
    DatasetMissingValuesMetric,
)
from evidently.report import Report

from monitor.types import DriftVerdict, MonitoringConfig


class DriftEngine:
    def __init__(self, config: MonitoringConfig) -> None:
        self._config = config

    def _build_mapping(self) -> ColumnMapping:
        return ColumnMapping(
            target=self._config.target_col,
            prediction=self._config.prediction_col,
            numerical_features=list(self._config.numerical_features),
            categorical_features=list(self._config.categorical_features),
        )

    def evaluate(
        self,
        reference: pd.DataFrame,
        current: pd.DataFrame,
    ) -> tuple[DriftVerdict, Report]:
        mapping = self._build_mapping()
        metrics: list = []
        for col in self._config.numerical_features:
            metrics.append(
                ColumnDriftMetric(
                    column_name=col,
                    stattest="ks",
                    stattest_threshold=self._config.ks_threshold,
                )
            )
        for col in self._config.categorical_features:
            metrics.append(
                ColumnDriftMetric(
                    column_name=col,
                    stattest="chi2",
                    stattest_threshold=self._config.ks_threshold,
                )
            )
        metrics.append(DatasetDriftMetric())
        metrics.append(DatasetMissingValuesMetric())

        report = Report(metrics=metrics)
        report.run(
            reference_data=reference,
            current_data=current,
            column_mapping=mapping,
        )
        snapshot = report.as_dict()
        return self._verdict_from_snapshot(snapshot), report

    def _verdict_from_snapshot(self, snapshot: dict) -> DriftVerdict:
        metrics_block = {m["metric"]: m for m in snapshot["metrics"]}
        dataset = metrics_block.get("DatasetDriftMetric", {}).get("result", {})
        missing = metrics_block.get("DatasetMissingValuesMetric", {}).get("result", {})

        drifted: list[str] = []
        max_score = 0.0
        for entry in dataset.get("drift_by_columns", {}).values():
            score = float(entry.get("drift_score", 0.0) or 0.0)
            max_score = max(max_score, score)
            if entry.get("drift_detected"):
                drifted.append(entry["column_name"])

        return DriftVerdict(
            dataset_drift=bool(dataset.get("dataset_drift", False)),
            drifted_columns=tuple(sorted(set(drifted))),
            drifted_count=len(drifted),
            max_drift_score=max_score,
            missing_share=float(missing.get("share_of_missing_values", 0.0)),
        )

4.3 Utilidades de análisis y verificación

El CLI monta todo, persiste el reporte HTML y devuelve exit code no-cero si hay drift:

# monitor/cli.py
from __future__ import annotations

import argparse
import json
import sys
from pathlib import Path

import pandas as pd

from monitor.config import load_config
from monitor.engine import DriftEngine


def parse_args() -> argparse.Namespace:
    p = argparse.ArgumentParser(prog="monitor-ml")
    p.add_argument("--config", required=True)
    p.add_argument("--report-out", default="reports/drift.html")
    p.add_argument("--verdict-out", default="reports/verdict.json")
    return p.parse_args()


def main() -> int:
    args = parse_args()
    config = load_config(args.config)

    reference = pd.read_parquet(config.reference_path)
    current = pd.read_parquet(config.current_path)

    engine = DriftEngine(config)
    verdict, report = engine.evaluate(reference, current)

    Path(args.report_out).parent.mkdir(parents=True, exist_ok=True)
    Path(args.verdict_out).parent.mkdir(parents=True, exist_ok=True)
    report.save_html(args.report_out)
    Path(args.verdict_out).write_text(
        json.dumps(verdict.__dict__, indent=2, ensure_ascii=False),
        encoding="utf-8",
    )

    if verdict.dataset_drift or verdict.missing_share > config.missing_threshold:
        return 2
    return 0


if __name__ == "__main__":
    sys.exit(main())

5. Ejemplos de Uso en Casos Reales

Caso 1 — Fraude con cambio de proveedor de pagos. Tenemos 50 000 transacciones de referencia y otras 50 000 actuales donde la columna amount se multiplicó por un factor 1.5 (el proveedor pasó de COP a COP-equivalente con fee). La KS debe detectar drift en amount pero no en las demás columnas.

Verificación manual:

import numpy as np
import pandas as pd
from evidently import ColumnMapping
from evidently.metrics import ColumnDriftMetric
from evidently.report import Report

rng = np.random.default_rng(42)
reference = pd.DataFrame({
    "amount": rng.normal(loc=100_000, scale=20_000, size=50_000),
    "device_score": rng.uniform(0, 1, size=50_000),
    "country": rng.choice(["CO", "MX", "PE"], size=50_000, p=[0.7, 0.2, 0.1]),
    "merchant_category": rng.choice(["retail", "digital", "travel"], size=50_000),
    "y_true": rng.integers(0, 2, size=50_000),
})
current = reference.copy()
current["amount"] = current["amount"] * 1.5  # simulamos el cambio

mapping = ColumnMapping(
    target="y_true",
    prediction=None,
    numerical_features=["amount", "device_score"],
    categorical_features=["country", "merchant_category"],
)

report = Report(metrics=[
    ColumnDriftMetric(column_name="amount", stattest="ks"),
    ColumnDriftMetric(column_name="device_score", stattest="ks"),
])
report.run(reference_data=reference, current_data=current, column_mapping=mapping)

# Verificación numérica esperada:
# amount: KS ~1.0 (distribuciones casi completamente separadas por el shift).
# device_score: KS ~0.03 (idéntico, solo ruido de muestreo).
# drift_detected=True solo en amount.
print(report.as_dict()["metrics"])

evidently levanta la alerta solo en amount y deja device_score en verde. KS detecta porque las distribuciones se separaron; PSI también lo haría porque los buckets se redistribuyen.

Caso 2 — Target drift por cambio de estacionalidad. En e-commerce, la columna y_true (clase binaria de "compra") cambia con la temporada. Comparamos julio (tasa base 5%) contra noviembre con Black Friday (tasa 12%).

from evidently.tests import TestColumnDrift
from evidently.test_suite import TestSuite

reference["y_true"] = rng.binomial(1, 0.05, size=50_000)
current["y_true"] = rng.binomial(1, 0.12, size=50_000)

ts = TestSuite(tests=[
    TestColumnDrift(column_name="y_true", stattest="psi"),
])
ts.run(reference_data=reference, current_data=current, column_mapping=mapping)
# drift_detected=True, drift_score ~0.45 (muy por encima de 0.2)

Caso 3 — Regresión: degradación silenciosa. Modelo de demanda que predice units_sold. El error MAE se duplica porque el modelo se entrenó con datos pre-pandemia y el patrón cambió. Aquí las métricas de calidad capturan lo que el drift puro no ve.

from evidently.metrics import RegressionQualityMetric

reference["y_pred"] = reference["y_true"] * 0.9 + rng.normal(0, 0.1, size=50_000)
current["y_pred"] = current["y_true"] * 0.4 + rng.normal(0, 0.3, size=50_000)

report = Report(metrics=[RegressionQualityMetric()])
report.run(reference_data=reference, current_data=current, column_mapping=mapping)
# Verificación: MAE sube de ~0.10 a ~0.42. Calidad degradada.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1 — Falsos positivos por muestra pequeña. Con menos de 1000 filas, KS pierde potencia estadística y dispara drift donde no lo hay. El test termina rechazando $H_0$ por ruido, no por cambio real.

Detección: mirá drift_score cuando current.shape[0] es chico. Si está apenas sobre el threshold, no confíes.

Soluciones:

  1. Acumulá ventana móvil de N horas en lugar de comparar contra el último batch.
  2. Subí el threshold a 0.15 o 0.2 para muestras chicas y relajalo cuando n crezca.
  3. Usá PSI en lugar de KS para variables con colas pesadas: KS es muy sensible cerca de la mediana y reporta drift falso.
def adjusted_ks_threshold(n: int, base: float = 0.1) -> float:
    """Ajusta KS threshold según tamaño de muestra."""
    if n < 1000:
        return max(base * 2, 0.2)
    if n < 5000:
        return max(base * 1.5, 0.15)
    return base

Problema 2 — Buckets vacíos en PSI. Si una categoría desaparece en producción, $p_i^{\text{act}} = 0$ y $\ln(0 / p_i^{\text{ref}}) = -\infty$. evidently lo maneja internamente con un epsilon pero te conviene saberlo y replicarlo si reimplementás a mano.

Detección numérica:

def safe_psi(p_ref: np.ndarray, p_act: np.ndarray, eps: float = 1e-6) -> float:
    p_ref = np.where(p_ref == 0, eps, p_ref)
    p_act = np.where(p_act == 0, eps, p_act)
    return float(np.sum((p_act - p_ref) * np.log(p_act / p_ref)))

Problema 3 — Data leakage en el reference set. Si el reference_data contiene filas que también están en current_data, las métricas sub-reportan drift porque ambas distribuciones son idénticas en la intersección. Solución: deduplicá por id antes de comparar.

7. Optimizaciones de Producción

Optimización 1 — Comparación por ventana deslizante. En lugar de comparar "todo el histórico" contra "todo el histórico", compará la última hora contra la anterior. Esto reduce el costo de memoria O(N) a O(N_window) y detecta drift local que el global enmascara.

Trade-off: perdés potencia estadística si la ventana es muy chica. Si la ventana es muy grande, arrastrás drift viejo y perdés sensibilidad.

def windowed_drift(
    df: pd.DataFrame,
    engine: DriftEngine,
    window: int = 5000,
    step: int = 1000,
) -> list[DriftVerdict]:
    """Genera verdicts sobre ventanas deslizantes del mismo DataFrame."""
    verdicts: list[DriftVerdict] = []
    half = window // 2
    for start in range(0, len(df) - window, step):
        ref = df.iloc[start : start + half]
        cur = df.iloc[start + half : start + window]
        verdict, _ = engine.evaluate(ref, cur)
        verdicts.append(verdict)
    return verdicts

Optimización 2 — Sampling estratificado para features de alta cardinalidad. Columnas como user_id o transaction_id tienen millones de categorías únicas. Aplicar chi-cuadrado es prohibitivo. Reducí la cardinalidad por hash bucket antes de pasar a evidently.

Trade-off: perdés granularidad por bucket; el chi-cuadrado deja de detectar drift por usuario individual y solo ve drift agregado. Úsalo solo cuando la cardinalidad sea el cuello de botella real, no por defecto.

def hash_bucket(series: pd.Series, n_buckets: int = 256) -> pd.Series:
    """Reduce cardinalidad por hash determinístico."""
    return series.apply(lambda v: hash(str(v)) % n_buckets).astype(str)

Al toque combinás windowed_drift + hash_bucket y pasás de un motor que tarda 4 minutos con 5 millones de filas a uno que tarda 30 segundos con la misma sensibilidad.

8. Conclusión: Por Qué Esto te Salva el Pellejo en Producción

Resumen de lo que te llevás puesto:

  • Model monitoring no es opcional: el uptime del endpoint no te dice nada sobre calidad de predicción. Si no medís drift, estás volando a ciegas con un motor que puede estar fundiéndose.
  • Tres métricas que importan: PSI para discretas/buckets, KS para continuas, JSD para categorías. evidently las orquesta, vos definís los umbrales por feature.
  • Reports para humanos, Test Suites para CI: el Report HTML te sirve para abrirlo en una reunión de post-mortem; el Test Suite JSON te sirve para cortar el pipeline de release automáticamente.
  • Sample size matters: KS con N<1000 miente. Ajustá los thresholds por tamaño de muestra, no apliques los mismos valores a un batch de 500 que a uno de 50 000.

Mini-checklist antes de poner esto en producción:

  1. ¿Tenés reference_data congelado del momento del deploy original?
  2. ¿Definiste umbrales por feature (no un umbral global)?
  3. ¿El Test Suite corta el pipeline de reentrenamiento automático cuando falla?
  4. ¿Los Report HTML llegan a un canal (Slack/email) cuando dataset_drift=True?
  5. ¿Tenés telemetría para saber cuántas alertas falsas disparaste la semana pasada?

Si la respuesta a cualquiera es "no", no tenés monitoring, tenés wishful thinking. Hagale pues, parce: copiá el código de la sección 4, conectá tu reference.parquet y dejá que las matemáticas te despierten antes que la auditoría. Tu modelo no se va a caer con un error 500, se va a morir en silencio mientras vos creés que todo está bien 🚛
