GGUF y llama.cpp — El formato que hace que inference sea 10x más barato

14 de may de 2026
ggufllama.cppinference

Hola, parcero. Llegamos al Día 164 y hoy vamos con GGUF. Si estás pagando por API de OpenAI o usando modelos en FP16 cuando no es necesario, este artículo te va a ahorrar plata y tiempo. GGUF es el formato de cuantización que el 80% subestima — y hoy te explico por qué con código real.

📐 Fundamentos Teóricos

GGUF (GPT Generated Unified Format) es un formato de archivo diseñado para guardar modelos LLM de manera eficiente, optimizado para inference rápida con cuantización. Creado por el proyecto llama.cpp, es el estándar de facto para ejecutar modelos localmente.

¿Qué es llama.cpp?

llama.cpp es una implementación en C/C++ de inferencia de modelos LLM, diseñada para:

  • Ejecutar modelos en CPU — sí, puedes correr un 70B en tu laptop con RAM suficiente
  • Cuantización eficiente — IQ4, IQ3, IQ2, Q8_0, Q6_K, Q5_K, Q4_K, Q4_0, Q3_K, Q2_K
  • Sin dependencias de Python — solo el binario y el modelo
  • Metal en Mac — acceleration nativa en Apple Silicon

Matemática de Cuantización

La cuantización reduce la precisión de los pesos. Aquí la progresión:

# Tamaños aproximados por tipo de cuantización para un modelo de 7B parámetros
quant_types = {
    "FP16":  7B * 2,                   # 14 GB  (full precision)
    "Q8_0":  7B * 1.0,                 # ~7 GB  (8-bit, casi sin pérdida)
    "Q6_K":  7B * 0.8,                 # ~5.6 GB (6-bit, muy buen balance)
    "Q5_K":  7B * 0.7,                 # ~4.9 GB
    "Q4_K":  7B * 0.5,                 # ~3.5 GB (4-bit, recommended)
    "Q4_0":  7B * 0.5,                 # ~3.5 GB
    "Q3_K":  7B * 0.45,                # ~3.15 GB
    "Q2_K":  7B * 0.35,                # ~2.45 GB (2-bit, más pérdida)
}

# La fórmula general: cada quantum representa un bloque de valores
# Q4_K usa: 1 constante por bloque + 4 bits por valor
# vs FP16: 16 bits por valor
compression_ratio_fp16_to_q4 = 16 / 4  # 4x reducción

Trade-off: Speed vs Memory

El trade-off central en inference:

  • Más quantización = menos memoria, más velocidad (más tokens/seg) pero más pérdida de quality
  • Menos quantización = más memoria, más lento, pero mejor calidad
# Benchmarks aproximados en CPU (MacBook M3 Pro, 36GB RAM)
# para Llama-3-8B

benchmarks = {

💻 Implementación Práctica

1. Cuantizar un modelo a GGUF

Usamos el script convert.py de llama.cpp para convertir desde HuggingFace y luego cuantizar:

# Instalar llama.cpp
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp
mkdir build && cd build
cmake ..
make -j$(nproc)

# 1. Convertir modelo de HuggingFace a GGUF
python3 ../convert.py /path/to/your/huggingface/model/llama-3-8b \
    --outfile models/llama-3-8b-fp16.gguf \
    --outtype f16

# 2. Cuantizar a Q4_K (4-bit con optimizaciones K-quants)
./quantize models/llama-3-8b-fp16.gguf \
            models/llama-3-8b-q4_k.gguf \
            Q4_K

2. inference con llama.cpp

# inference en CPU
./llama-cli -m models/llama-3-8b-q4_k.gguf \
            -p "Explica qué es QLoRA en una oración:" \
            -n 128 \
            --temp 0.7

# inference con GPU (si tienes CUDA)
./llama-cli -m models/llama-3-8b-q4_k.gguf \
            -p "Explica qué es QLoRA en una oración:" \
            -n 128 \
            -ngl 99   # 99 =全部 load to GPU

3. inference Comparación: FP16 vs INT4 vs GGUF

"""
Comparación de inference entre FP16, INT4 vanilla, y GGUF Q4_K
Ejemplo con Llama-3-8B en MacBook M3 Pro
"""
import subprocess
import time

def benchmark_inference(model_path, prompt, n_tokens=128):
    start = time.time()
    result = subprocess.run(
        ["./llama-cli", "-m", model_path, "-p", prompt,
         "-n", str(n_tokens), "--no-display-prompt"],
        capture_output=True, text=True
    )
    elapsed = time.time() - start
    tokens_per_sec = n_tokens / elapsed
    return tokens_per_sec, elapsed

models = {
    "FP16 (HuggingFace)":  "llama-3-8b-fp16.gguf",
    "INT4 (vanilla GPTQ)":  "llama-3-8b-int4.gptq.gguf",
    "GGUF Q4_K":            "llama-3-8b-q4_k.gguf",
}

prompt = "¿Por qué QLoRA es importante para fine-tuning eficiente?"
print("=== Benchmark: Llama-3-8B ===")
for name, path in models.items():
    tps, elapsed = benchmark_inference(path, prompt)
    print(f"{name:20s}: {tps:.1f} tok/s | {elapsed:.2f}s total")

🚨 Errores Comunes y Fixes

Error 1: Usar FP16 cuando INT4 es suficiente

Síntoma: Tu modelo ocupa 14GB+ en RAM/VRAM, la inference es lenta, y estás desperdiciando hardware.

Causa: FP16 tiene 16 bits por parámetro. La mayoría de los casos de uso no requieren esta precisión — INT4 con Q4_K pierde solo ~3% en benchmarks pero ocupa 4x menos espacio.

Fix: Cuantiza a Q4_K. Un modelo de 7B pasa de 14GB a 3.5GB. Un 70B pasa de 140GB a ~35GB. Usa ./quantize model-fp16.gguf model-q4_k.gguf Q4_K. Si tienes 8GB VRAM y quieres correr 70B, necesitas Q4_K — no hay otra opción.

Error 2: No usar GPU quantization

Síntoma: La inference en CPU es demasiado lenta (<5 tokens/s para modelos grandes).

Causa: La cuantización en GPU puede ser 10x más rápida que CPU para modelos grandes. Muchos no usan el flag -ngl.

Fix: Usa -ngl 99 (99 = cargar todas las capas a GPU). En una RTX 3090, esto puede darte 15-25 tok/s para un 70B en Q4_K vs 3-5 tok/s en CPU. Si tienes más de 24GB VRAM, considera Q8_0 para mejor calidad con similar speed.

Error 3: Usar GGUF para Fine-Tuning

Síntoma: Intentas fine-tunear un modelo en formato GGUF y получаешь errores de precisión o el training no converge.

Causa: GGUF es un formato de inference, no de training. La cuantización destruye información que es necesaria para el gradiente durante fine-tuning. GGUF assume pesos congelados.

Fix: Para fine-tuning, usa el modelo original en FP16 o usa QLoRA (que quantiza durante training con cuidado). GGUF + fine-tuning = calidad degradada. Solo usa GGUF para inference, nunca para training.

✅ Mejores Prácticas

  • Q4_K como default: es el sweet spot entre memoria, velocidad y calidad para la mayoría de use cases.
  • Q6_K si tienes memoria: si tienes 16GB+ VRAM, Q6_K da mejor calidad (~2% mejor que Q4_K) por solo ~1GB extra.
  • Q8_0 para máxima calidad: solo si tienes la VRAM. Es FP16-equivalente en calidad con ~50% del tamaño.
  • Siempre usa GPU si está disponible: el flag -ngl 99 cambia todo en términos de velocidad.
  • Valida con tu use case: algunos tasks (código, matemáticas) se benefician de mayor precisión. Otros (chat general, summaries) funcionan bien con Q4_K.
