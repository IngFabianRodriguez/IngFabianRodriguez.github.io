API REST para ML - El endpoint que el 85% deploya sin batching ni cache y se cae en producción

14 de april de 2026
fastapi

Hola, parcero. Llegamos al Día 134 y hoy vamos con un tema que me duele ver en producción: APIs REST para ML. Ese endpoint que el 85% deploya sin batching, sin cache, y sin async — y cuando le llegan 100 requests simultáneos, el servidor se cae. Acá te muestro cómo hacerlo bien, con código que escala de verdad.

📐 Fundamentos Teóricos

¿Por qué tu API de ML se cae en producción?

El problema fundamental es que la mayoría de endpoints de ML se diseñan como si fueran una API CRUD normal. Pero un request de ML involucra:

  • Loading del modelo (puede pesar GB)
  • Preprocessing (tokenización, transformaciones — I/O bound)
  • Inferencia (GPU compute-bound)
  • Postprocessing (parsing, formateo)

Cada paso tiene latencia propia. Sin batching, cada request dispara estos 4 pasos por separado. Con batching, puedes agrupar requests y共享 el overhead.

Throughput con batching

La mejora de throughput con batching sigue aproximadamente:

$$\text{Throughput}_{\text{batched}} \approx \frac{\text{Throughput}_{\text{single}}}{1 + \frac{O_{\text{overhead}}}{N_{\text{batch}}}}$$

Donde $O_{\text{overhead}}$ es el overhead por batch (serialización, GPU kernel launch) y $N_{\text{batch}}$ es el tamaño del batch. Con batch size 32, el throughput puede mejorar 10-20x vs requests individuales.

El costo de cargar el modelo en cada request

Cargar un modelo como BERT o GPT-2 implica:

$$T_{\text{load}} = T_{\text{weights}} + T_{\text{vocab}} + T_{\text{config}} + T_{\text{gpu\_transfer}}$$

Para un modelo de 500MB en GPU, $T_{\text{load}} \approx 2-5$ segundos. Si esto ocurre en cada request, tu p99 latency es unacceptable. El fix: cargar una vez, cachear para siempre.

💻 Implementación Práctica

FastAPI app con model caching y batching

# app/main.py
import asyncio
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field
import torch
from transformers import AutoTokenizer, AutoModel
import time

# ─── Global model cache ───
model_cache = {}
tokenizer_cache = {}

# ─── Request/Response schemas ───
class PredictRequest(BaseModel):
    texts: list[str] = Field(..., min_length=1, max_length=32)
    max_length: int = Field(default=128, ge=1, le=512)

class PredictResponse(BaseModel):
    predictions: list[list[float]]
    latency_ms: float
    batch_size: int

class HealthResponse(BaseModel):
    status: str
    model_loaded: bool
    device: str

# ─── Model loader con cache ───
def get_model(device: str = "cuda"):
    if "model" not in model_cache:
        print("Loading model... (primera vez)")
        model_name = "distilbert-base-uncased"
        tokenizer_cache["tok"] = AutoTokenizer.from_pretrained(model_name)
        model_cache["model"] = AutoModel.from_pretrained(model_name).to(device)
        model_cache["device"] = device
        model_cache["model"].eval()
    return model_cache["model"], tokenizer_cache["tok"], model_cache["device"]

# ─── Batch queue con asyncio ───
batch_queue = asyncio.Queue()
batch_results = {}

async def batch_processor():
    """Consume la cola de requests, hace batching real, y procesa."""
    while True:
        items = []
        # Esperar hasta tener enough items o timeout
        first_item = await asyncio.wait_for(batch_queue.get(), timeout=0.05)
        items.append(first_item)
        
        # Hacer gather de más items mientras llegan (max 0.05s window)
        while len(items) < 32 and not batch_queue.empty():
            try:
                items.append(batch_queue.get_nowait())
            except asyncio.QueueEmpty:
                break
        
        # Procesar batch
        model, tokenizer, device = get_model()
        texts = [item["text"] for item in items]
        
        with torch.no_grad():
            inputs = tokenizer(
                texts,
                padding=True,
                truncation=True,
                max_length=items[0]["max_length"],
                return_tensors="pt"
            ).to(device)
            
            start = time.perf_counter()
            outputs = model(**inputs)
            # Promedio del last hidden state como embedding
            embeddings = outputs.last_hidden_state[:, 0, :].cpu().tolist()
            latency = (time.perf_counter() - start) * 1000
        
        # Distribuir resultados
        for i, item in enumerate(items):
            item["future"].set_result({
                "prediction": embeddings[i],
                "latency_ms": latency
            })

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup
    asyncio.create_task(batch_processor())
    get_model()  # Precargar modelo al arrancar
    yield
    # Shutdown

app = FastAPI(title="ML Inference API", lifespan=lifespan)

@app.post("/predict", response_model=PredictResponse)
async def predict(request: PredictRequest):
    """Endpoint de predicción con batching automático."""
    loop = asyncio.get_event_loop()
    future = loop.create_future()
    
    await batch_queue.put({
        "text": request.texts[0],  # Por ahora 1 texto por request
        "max_length": request.max_length,
        "future": future
    })
    
    result = await future
    
    return PredictResponse(
        predictions=[result["prediction"]],
        latency_ms=round(result["latency_ms"], 2),
        batch_size=1
    )

@app.get("/health", response_model=HealthResponse)
async def health():
    """Health check — esencial para k8s/load balancers."""
    try:
        model, _, device = get_model()
        return HealthResponse(
            status="healthy",
            model_loaded=True,
            device=device
        )
    except Exception as e:
        return JSONResponse(
            status_code=503,
            content={
                "status": "unhealthy",
                "model_loaded": False,
                "error": str(e)
            }
        )

Async inference con transformers (I/O-bound preprocessing)

import asyncio
from transformers import AutoTokenizer, AutoModelForSequenceClassification
import torch

class AsyncClassifier:
    def __init__(self, model_name: str = "distilbert-base-uncased-finetuned-sst-2"):
        self.device = "cuda" if torch.cuda.is_available() else "cpu"
        self.tokenizer = AutoTokenizer.from_pretrained(model_name)
        # El modelo se carga en __init__, no en cada request
        self.model = AutoModelForSequenceClassification.from_pretrained(model_name)
        self.model.to(self.device)
        self.model.eval()
    
    async def predict_async(self, texts: list[str]) -> list[dict]:
        # Fake async para demo — en la realidad el tokenizado es sync
        # pero puedes usar run_in_executor para I/O real (disk, network)
        loop = asyncio.get_event_loop()
        return await loop.run_in_executor(
            None,  # usa default ThreadPoolExecutor
            self._sync_predict,
            texts
        )
    
    def _sync_predict(self, texts: list[str]) -> list[dict]:
        with torch.no_grad():
            inputs = self.tokenizer(
                texts,
                return_tensors="pt",
                padding=True,
                truncation=True,
                max_length=512
            ).to(self.device)
            
            logits = self.model(**inputs).logits
            probs = torch.softmax(logits, dim=-1)
            
        return [
            {"label": self.model.config.id2label[i], "prob": p}
            for i, p in enumerate(probs[0].cpu().tolist())
        ]

🚨 Errores Comunes (y sus fixes)

Error 1: No usar batching → overhead enorme en producción

Síntoma: 1000 requests/minuto con latencia de 200ms deberían dar ~3 req/s, pero tu servidor satura CPU al 100% y la latencia sube a 5s.

Causa raiz: Sin batching, cada request abre su propia sesión de GPU, carga sus propios datos, y cierra. El overhead de GPU context switching es enorme.

# Mal (sin batching):
for text in texts:
    result = model(tokenize(text))  # Un inference call por texto

# Bien (con batching):
batch = tokenize(texts)  # Un inference call para todos
results = model(batch)

Usa una cola asíncrona con window de tiempo o de tamaño para agrupar requests. Con batch size 32, el throughput puede mejorar 10-20x.

Error 2: Cargar modelo en cada request → latencia de 2-5s por request

Síntoma: La primera request tarda 3s, las siguientes 50ms. Esto pasa porque el modelo se carga lazy en el primer request.

# Mal:
@app.post("/predict")
async def predict(text: str):
    model = load_model()  # Se ejecuta en CADA request
    return model.predict(text)

# Bien: cargar en startup (lifespan o __init__)
model = None

@app.on_event("startup")
async def startup():
    global model
    model = load_model()  # Una sola vez

@app.post("/predict")
async def predict(text: str):
    return model.predict(text)  # Reusa el modelo ya cargado

Error 3: No usar async para preprocessing I/O-bound

Síntoma: El thread pool se satura con requests esperando I/O (disk, network) mientras el CPU está ocioso.

# Mal (blocking I/O en endpoint async):
@app.post("/predict")
async def predict(text: str):
    # Esto bloquea el event loop si es I/O real
    data = await fetch_from_external_api(text)
    result = model.predict(data)
    return result

# Bien (async I/O o run_in_executor):
async def fetch_from_external_api(text: str):
    # Async HTTP client real
    async with aiohttp.ClientSession() as session:
        async with session.get(f"http://api.example.com/lookup/{text}") as resp:
            return await resp.json()

@app.post("/predict")
async def predict(text: str):
    # Todo async, no bloquea el event loop
    data = await fetch_from_external_api(text)
    loop = asyncio.get_event_loop()
    result = await loop.run_in_executor(None, lambda: model.predict(data))
    return result

✅ Mejores Prácticas

  • Health check endpoint: esencial para Kubernetes liveness/readiness probes y load balancers
  • Model caching global: carga el modelo una vez al startup, nunca en cada request
  • Batching con cola asíncrona: agrupa requests por ventana de tiempo o tamaño
  • Pydantic validation: valida inputs en el schema, no dentro del código de inferencia
  • Límites de concurrencia: configura `--limit-concurrency` en uvicorn para evitar overload
  • Métricas: exporta latencia, throughput y errores a Prometheus para monitoreo real
  • Graceful shutdown: el lifespan context manager asegura que el modelo se libere limpiamente

Resumen y cierre

Hoy cubrimos APIs REST para ML desde la perspectiva de producción real: FastAPI con async, batching con colas asíncronas, model caching, y los tres errores que hacen que el 85% de los endpoints se caigan bajo load.

La diferencia entre un endpoint que sobrevive y uno que se cae es simple: caching del modelo, batching de requests, y async para todo lo que sea I/O. No es magia — es arquitectura correcta desde el día uno.
