📐 Fundamentos: Por Qué Necesitas Distributed Training

Cuando un modelo es demasiado grande para caber en una sola GPU, necesitas dividir el trabajo entre múltiples GPUs. Hay dos formas de hacer esto: DataParallel y DistributedDataParallel. La diferencia entre ellos es crítica para entender por qué uno es mejor que el otro.

El Math del Gradient Descent Distribuido

En training distribuido, el gradient descent se calcula de forma diferente. Dado un batch de $N$ samples dividido en $K$ GPUs:

$$\nabla L_{\text{global}} = \frac{1}{K} \sum_{k=1}^{K} \nabla L_k$$

donde $\nabla L_k$ es el gradiente calculado en la GPU $k$ con su sub-batch local. Esto es el AllReduce — cada GPU calcula gradientes locales y luego se promedian.

DataParallel vs DistributedDataParallel

DataParallel (DP): Una GPU es la "principal" y coordina todo. Los datos se dividen, se procesan en paralelo, y los gradientes se reducen en la GPU 0. Tiene overhead de serialización porque la GPU 0 hace todo.

$$T_{\text{DP}} = T_{\text{forward}} + T_{\text{backward}} + T_{\text{reduce}}(G_0)$$

DistributedDataParallel (DDP): Cada GPU tiene su propia copia del modelo y coordina con las otras mediante comunicación eficiente (NCCL en NVIDIA). No hay bottleneck en una GPU específica.

$$T_{\text{DDP}} = \max(T_{\text{forward}}, T_{\text{backward}}) + T_{\text{allreduce}}(\text{gradientes})$$

DDP es típicamente 20-30% más rápido que DP porque no hay overhead de copiar todo a la GPU 0.

💻 Código: Implementar Distributed Training

1. Setup Básico con DistributedDataParallel

import os
import torch
import torch.nn as nn
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
import torch.multiprocessing as mp

def setup(rank, world_size):
    """Inicializar el proceso distribuido."""
    os.environ['MASTER_ADDR'] = 'localhost'
    os.environ['MASTER_PORT'] = '12355'
    dist.init_process_group("nccl", rank=rank, world_size=world_size)

def cleanup():
    """Limpiar el proceso distribuido."""
    dist.destroy_process_group()

class TransformerModel(nn.Module):
    """Modelo de ejemplo para distributed training."""
    def __init__(self, vocab_size=50000, d_model=1024, nhead=16, num_layers=12):
        super().__init__()
        self.embedding = nn.Embedding(vocab_size, d_model)
        encoder_layer = nn.TransformerEncoderLayer(d_model, nhead, batch_first=True)
        self.transformer = nn.TransformerEncoder(encoder_layer, num_layers)
        self.fc = nn.Linear(d_model, vocab_size)
    
    def forward(self, x):
        x = self.embedding(x)
        x = self.transformer(x)
        return self.fc(x)

def train_worker(rank, world_size):
    """Worker que entrena el modelo."""
    setup(rank, world_size)
    
    # Crear modelo y wrap con DDP
    model = TransformerModel().cuda(rank)
    model = DDP(model, device_ids=[rank])
    
    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)
    criterion = nn.CrossEntropyLoss()
    
    # Training loop
    model.train()
    for epoch in range(10):
        # Simular data loader para esta GPU
        batch_size = 32
        seq_len = 128
        input_ids = torch.randint(0, 50000, (batch_size, seq_len)).cuda(rank)
        labels = torch.randint(0, 50000, (batch_size, seq_len)).cuda(rank)
        
        optimizer.zero_grad()
        outputs = model(input_ids)
        
        # Flatten para cross entropy
        loss = criterion(outputs.view(-1, 50000), labels.view(-1))
        loss.backward()
        
        # DDP maneja el allreduce de gradientes automáticamente
        optimizer.step()
        
        if rank == 0:
            print(f"Epoch {epoch}, Loss: {loss.item():.4f}")
    
    cleanup()

# Lanzar workers
world_size = torch.cuda.device_count()
print(f"Usando {world_size} GPUs")
mp.spawn(train_worker, args=(world_size,), nprocs=world_size, join=True)

🚨 Los 3 Errores que el 80% Comete

Error 1: Usar DataParallel Cuando DistributedDataParallel Es Más Eficiente

Este es el error más común. DataParallel es más fácil de usar (solo envolvés el modelo y ya), pero tiene un bottleneck inherente: toda la comunicación pasa por la GPU 0. Con DDP, cada GPU tiene su propia copia del optimizador y los gradientes se reducen eficientemente usando NCCL.

# ❌ ESTO ES LO QUE EL 80% HACE
# DataParallel - fácil pero lento
model = MyModel()
model = nn.DataParallel(model)  # GPU 0 es el bottleneck

# ✅ FIX: Usar DistributedDataParallel
# Inicializar distributed
dist.init_process_group(backend="nccl")
model = MyModel().cuda()
model = nn.parallel.DistributedDataParallel(model)

# DDP es más difícil de configurar pero:
# - No hay bottleneck en GPU 0
# - Comunicación overlapped con computación
# - 20-30% más throughput

Error 2: No Usar Gradient Accumulation Cuando el Batch Size es Pequeño

Cuando tienes una GPU con memoria limitada, el batch size tiene que ser pequeño. Sin gradient accumulation, los gradients son ruidosos y el entrenamiento es inestable. Gradient accumulation te permite simular un batch size mayor sin usar más memoria.

# ❌ ESTO ES LO QUE EL 80% HACE
# Batch size = 4 porque la GPU no da para más
# Esto causa gradients ruidosos y training inestable
batch_size = 4
model.train()
for data in dataloader:
    optimizer.zero_grad()
    output = model(data[:batch_size])
    loss = criterion(output, labels[:batch_size])
    loss.backward()
    optimizer.step()  # Actualización con gradients ruidosos

# ✅ FIX: Gradient accumulation
# Simular batch size 32 (8 pasos de accumulation)
accumulation_steps = 8
batch_size_per_step = 4
effective_batch_size = accumulation_steps * batch_size_per_step  # 32

model.train()
optimizer.zero_grad()
for step, data in enumerate(dataloader):
    input_ids = data['input_ids'][:batch_size_per_step].cuda()
    labels = data['labels'][:batch_size_per_step].cuda()
    
    output = model(input_ids)
    loss = criterion(output.view(-1, vocab_size), labels.view(-1))
    loss = loss / accumulation_steps  # Normalizar
    loss.backward()
    
    if (step + 1) % accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()

# El gradiente efectivo es la suma de 8 gradientes locales
# = gradiente de batch size 32

Error 3: No Monitorear GPU Utilization (Y No Saber Si Hay Bottleneck)

La gente entrena sin monitorear si las GPUs están siendo usadas efectivamente. Si la GPU utilization está al 100%, el bottleneck es computación. Si está baja, el bottleneck es likely la comunicación o el data loading. Sin esta información, estás adivinando.

# ❌ ESTO ES LO QUE EL 80% HACE
# Entrenar sin monitorear nada
for epoch in range(100):

import subprocess
import threading

def monitor_gpu():
    """Monitorear GPU utilization cada 5 segundos."""

📊 Resumen: Distributed Training Strategies

  • DataParallel (DP): Fácil pero lento, GPU 0 bottleneck. Solo para prototipado rápido
  • DistributedDataParallel (DDP): El estándar para multi-GPU training, 20-30% más rápido que DP
  • FSDP: Para modelos que no caben en una sola GPU, shardea pesos entre GPUs
  • Gradient Accumulation: Simula batch sizes grandes con memoria limitada
  • GPU Utilization: SIEMPRE monitorear para saber si hay bottleneck
  • Sharding Strategy: FULL_SHARD usa más comunicación pero menos memoria

🏁 Cierre

Y ahí lo tienen, parcero. Distributed training no es solo "poner el modelo en varias GPUs". Es entender la diferencia entre DP y DDP, usar gradient accumulation cuando el batch size es pequeño, y monitorear la GPU utilization para saber si hay bottleneck de коммуникация o de computación. El 80% que no hace esto es por qué tantísimo entrenamiento de modelos grandes falla o es innecesariamente lento.
