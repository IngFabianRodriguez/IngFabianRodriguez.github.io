🎯 El Panorama Cloud Para ML en 2026

Básicamente el 80% del mercado de ML en la nube está dividido entre tres gigantes: AWS con SageMaker, Google Cloud con Vertex AI, y Microsoft con Azure ML. Cada uno tiene sus ventajas, pero ninguno es universally mejor — depende de tu caso específico.

La ecuación fundamental para decidir es:

Costo Total = (Costo por hora de GPU × Horas de uso) + (Costo de almacenamiento) + (Costo de egress) + (Costo de servicios manejados)

La gente se enfoca solo en el primer término y olvida los demás. En producción eso duele.

📐 Comparación de Plataformas

AWS SageMaker

# Entrenamiento con SageMaker
import sagemaker
from sagemaker.pytorch import PyTorch

estimator = PyTorch(
    entry_point='train.py',
    source_dir='./scripts',
    instance_type='ml.p3.2xlarge',  # V100
    instance_count=1,
    framework_version='2.1.0',
    py_version='py38',
    hyperparameters={
        'epochs': 100,
        'batch-size': 64,
        'learning-rate': 0.001
    }
)

estimator.fit({'train': 's3://mi-bucket/datos/'})

# Despliegue automático
predictor = estimator.deploy(
    initial_instance_count=1,
    instance_type='ml.m5.large'
)

Pros: El más maduro, integración con toda la familia AWS, buen soporte para frameworks variados.

Contras: Interfaz compleja, documentación confusa a veces, los costos pueden escalar rápido sin aviso.

GCP Vertex AI

# Vertex AI Training
from google.cloud import aiplatform

aiplatform.init(project='mi-proyecto', location='us-central1')

job = aiplatform.CustomTrainingJob(
    display_name='mi-modelo-v1',
    script_path='train.py',
    container_uri='gcr.io/cloud-ml/training:latest',
    requirements=['torch', 'transformers']
)

model = job.run(
    replica_count=1,
    machine_type='n1-standard-8',
    accelerator_type='NVIDIA_TESLA_V100',
    accelerator_count=1
)

# Endpoint para inferencia
endpoint = model.deploy(machine_type='n1-standard-4')

Pros: Mejor integración con Kubernetes/GKE, AutoML decente, interfaz más limpia que SageMaker.

Contras: Menos regiones disponibles para GPUs específicas, comunidad más pequeña.

Azure ML

# Azure ML Training
from azureml.core import Workspace, Experiment, ScriptRunConfig
from azureml.mlflow import register_model

ws = Workspace.from_config()
experiment = Experiment(ws, "mi-experimento")

config = ScriptRunConfig(
    source_directory='./scripts',
    script='train.py',
    compute_target='gpu-cluster',
    environment='PyTorch-2.0'
)

run = experiment.submit(config)
run.wait_for_completion()

# Despliegue en Azure Container Instances
model = register_model(run, 'mi-modelo', model_path='outputs/model.pt')
service = Model.deploy(ws, 'servicio', [model], inference_config, acs_config)

Pros: Si usas Microsoft 365 y Azure AD, la integración es impecable. Buenas herramientas de MLOps.

Contras: Curva de aprendizaje para quien no conoce ecosistema Microsoft.

📊 Estimación de Costos Cloud Para ML

La fórmula que uso en asesorías para estimar el costo mensual de un workload de ML:

Costo Mensual GPU = (Precio por hora × 24 × 30 × Utilización%) + Overhead de servicios

Ejemplo real para un modelo de NLP en producción con 1000 requests/día:

# Estimación de costos mensuales (USD)
costos = {
    'sagemaker': {
        'inference': 0.10 * 24 * 30 * 0.3,  # ml.m5.large, 30% utilización
        'gpu_training': 3.06 * 8 * 20,       # p3.2xlarge, 20 horas/mes
        'storage': 0.023 * 500,              # 500 GB S3
        'total': 0
    },
    'vertex_ai': {
        'inference': 0.08 * 24 * 30 * 0.3,  # n1-standard-4
        'gpu_training': 2.48 * 8 * 20,       # V100 en n1-standard-8
        'storage': 0.020 * 500,              # 500 GB Cloud Storage
        'total': 0
    }
}

for platform in costos:
    costos[platform]['total'] = sum([
        costos[platform]['inference'],
        costos[platform]['gpu_training'],
        costos[platform]['storage']
    ])
    print(f"{platform}: ${costos[platform]['total']:.2f}/mes")

Con mis clientes en Colombia, el error más común es no considerar que el egress de datos desde AWS a usuarios en Colombia puede costar más que el entrenamiento mismo si el modelo responde con mucho JSON.

⚠️ Los 3 Errores Más Comunes

Error 1: Elegir Cloud Sin Considerar Data Residency

El problema: Muchas empresas Colombianas tienen datos de clientes que no pueden salir del país. AWS no tiene región en Colombia (la más cercana es São Paulo o Virginia). GCP tiene Bogotá pero con oferta limitada de GPUs.

La solución:

# Verificar regiones disponibles por proveedor
regiones_gcp = {
    'us-central1': {'gpu': ['V100', 'T4', 'A100'], 'status': 'disponible'},
    'southamerica-east1': {'gpu': ['T4'], 'status': 'limitado'},  # São Paulo
    # No hay región GCP en Colombia con GPUs para ML
}

regiones_aws = {
    'us-east-1': {'gpu': ['V100', 'T4', 'A100', 'H100'], 'status': 'completo'},
    'sa-east-1': {'gpu': ['T4'], 'status': 'limitado'},  # São Paulo
}

# Azure tiene región Brazil South con más opciones que GCP
# pero también es fuera de Colombia

Error 2: No Estimar Costos Properly y Recibir Facturas Sorpresa

El problema: SageMaker cobra por minuto, incluyendo el tiempo que el notebook está abierto. Muchos equipos dejan instancias corriendo sin usar. Los "training jobs" que fallan pero no se limpian siguen cobrando.

La solución:

# Configurar budgets y alerts en AWS
import boto3

budgets = boto3.client('budgets')

# Crear alert cuando gastes más de $500 en SageMaker
budgets.create_budget(
    AccountId='123456789012',
    Budget={
        'BudgetName': 'sagemaker-monthly',
        'BudgetLimit': {'Amount': '500', 'Unit': 'USD'},
        'TimeUnit': 'MONTHLY',
        'BudgetType': 'COST'
    },
    NotificationsWithSubscribers=[
        {
            'Notification': {
                'NotificationType': 'ACTUAL',
                'ComparisonOperator': 'GREATER_THAN',
                'Threshold': 80  # Alertar al 80%
            },
            'Subscribers': [{'SubscriptionType': 'EMAIL', 'Address': 'mi@email.com'}]
        }
    ]
)

# Usar SageMaker Studio con Lifecycle Configs para auto-shutdown
lifecycle_config = {
    'Name': 'auto-shutdown-idle',
    'OnCreate': [
        {'Content': 'echo "Starting shutdown timer"'}
    ],
    'OnSessionShutdown': [
        {'Content': '/opt/conda/envs/sagemaker/bin/python -c "import time; time.sleep(3600)"'}
    ]
}

Error 3: Ignorar GPU Availability en Diferentes Regiones

El problema: H100 y A100 son escasas. No todas las regiones tienen todas las GPUs. En 2024-2025 hubo escasez de H100 globally. Si diseñas tu pipeline para H100 y solo hay T4 en tu región, tienes un problema.

La solución:

# Verificar disponibilidad de GPUs y predecir disponibilidad
import datetime

disponibilidad_gpu = {
    'us-east-1': {'H100': 0.85, 'A100': 0.70, 'V100': 0.30, 'T4': 0.95},
    'us-west-2': {'H100': 0.90, 'A100': 0.80, 'V100': 0.50, 'T4': 0.98},
    'europe-west4': {'H100': 0.60, 'A100': 0.75, 'V100': 0.20, 'T4': 0.85},
    'southamerica-east1': {'H100': 0.10, 'A100': 0.30, 'V100': 0.40, 'T4': 0.70},
}

def calcular_tiempo_espera(gpu_type, region, horas_training):
    disponibilidad = disponibilidad_gpu.get(region, {}).get(gpu_type, 0.5)
    if disponibilidad > 0.7:
        return 0  # No hay espera
    elif disponibilidad > 0.4:
        return horas_training * 0.3  # 30% overhead
    else:
        return horas_training * 0.8  # 80% overhead por espera

# Estimar si vale la pena esperar o usar GPU inferior
for region in disponibilidad_gpu:
    espera_h100 = calcular_tiempo_espera('H100', region, 100)
    print(f"{region}: H100 tiene {espera_h100:.0f}h de espera estimado")

🏠 On-Premises vs Cloud: La Decisión

Para empresas Colombianas medianas, la pregunta del millón es: ¿cloud o on-prem? Aquí va la fórmula que uso:

Punto de equilibrio (meses) = (Costo On-Prem / (Costo Cloud Mensual - Costo Operador On-Prem))

# Análisis de decisiones on-prem vs cloud
analisis = {
    'cloud': {
        'inversion_inicial': 0,
        'costo_mensual': 5000,  # USD
        'mantenimiento_mensual': 500,
        'flexibilidad': 'alta'
    },
    'on_prem': {
        'inversion_inicial': 80000,  # 4x A100 80GB
        'costo_mensual': 2000,  # Energía, networking,Ops
        'mantenimiento_mensual': 1500,
        'flexibilidad': 'baja'
    }
}

# Calcular punto de equilibrio
inversion_on_prem = analisis['on_prem']['inversion_inicial']
ahorro_mensual = analisis['cloud']['costo_mensual'] - analisis['on_prem']['costo_mensual']
punto_equilibrio_meses = inversion_on_prem / ahorro_mensual

print(f"Punto de equilibrio: {punto_equilibrio_meses:.1f} meses ({punto_equilibrio_meses/12:.1f} años)")

📝 Resumen y Cierre

Para resumir lo que hemos visto:

  • AWS SageMaker: Mejor para equipos que ya usan AWS y necesitan variedad de frameworks.
  • GCP Vertex AI: Mejor para Kubernetes-nativos y quien prioriza costo sobre variedad.
  • Azure ML: Mejor para ecosistema Microsoft y empresas con AD/Office 365.
  • On-prem: Solo tiene sentido si tu uso supera 18-24 meses de cloud costs equivalentes.

Y recuerden: la GPU más barata no es la que tiene el menor precio por hora — es la que termina el trabajo más rápido considerando disponibilidad y overhead.

Eso sí, parcero, antes de firmar con cualquier cloud provider, léanse los términos de data residency. En Colombia hay regulaciones específicas sobre dónde pueden estar datos de ciertos sectores. No quieren una sorpresa de la SIC.
