La inteligencia que no necesita la nube

Hagale pues, parcero. Aquí en Colombia estamos acostumbrados a que las cosas funcionen incluso cuando la conectividad no es la mejor — uno aprende a adaptarse. En el mundo del machine learning está pasando algo similar: la inteligencia se está mudando al borde, al dispositivo, lejos de la nube. Hoy hablamos de Edge AI y On-Device ML — por qué importa, cómo funciona y qué errores evitar cuando deployas modelos en dispositivos móviles y edge.

Durante mucho tiempo la fórmula fue simple: manda tus datos a la nube, el modelo hace su magia, te devuelve el resultado. Pero esa aproximación tiene problemas reales — latencia, privacidad, consumo de energía, conectividad. Edge AI resuelve eso llevando el modelo directamente al dispositivo.

¿Por qué Edge AI?

La motivación detrás de mover la inferencia al borde no es solo técnica — es práctica. Pensemos en una aplicación de traducción en tiempo real funcionando con malo wifi en el metro de Bogotá. Cada milisegundo cuenta. Aquí la latencia de ir a la nube puede arruinar la experiencia por completo.

Los beneficios principales:

  • Baja latencia: La inferencia es local, no hay round-trip a la nube. En tiempo real esto cambia todo.
  • Privacidad: Los datos nunca salen del dispositivo. Sensores biométricos, reconocimiento facial, análisis de voz — todo se procesa localmente.
  • Sin dependencia de conectividad: Funciona en zonas rurales, en el campo, donde la cobertura es limitada.
  • Eficiencia energética: Una inference local puede ser más eficiente que mantener una conexión constante a la nube.

La matemática es directa. Si tenemos:

$$T_{total} = T_{upload} + T_{inference} + T_{download}$$

En edge, T_{upload} = T_{download} = 0, dejando solo T_{inference}. En cloud, esos términos pueden dominar — especialmente en dispositivos con conexión limitada.

Frameworks para On-Device ML

TensorFlow Lite

TensorFlow Lite es la solución de Google para correr modelos TF en dispositivos móviles, embebidos y edge. Soporta Android, iOS, Linux embebido, y microcontroladores.

Core ML

Core ML es el framework de Apple para inference de ML en dispositivos iOS. Integración nativa con los Neural Engines de los chips Apple, lo que da un rendimiento excelente en hardware Apple.

ONNX Runtime Mobile

ONNX Runtime permite correr modelos en formato ONNX en una variedad de plataformas — Android, iOS, Linux, Windows, y más. Es una alternativa agnóstica que funciona con modelos de prácticamente cualquier framework.

Comparación rápida

  • TensorFlow Lite: Mejor para modelos TensorFlow/Keras. Excelente tooling de conversión. Soporte amplio en Android.
  • Core ML: Mejor para ecosistema Apple. Integración profunda con Vision, NaturalLanguage, Speech. Rendimiento excelente en hardware Apple.
  • ONNX Runtime: Mejor para portabilidad máxima. Funciona con modelos de PyTorch, TensorFlow, scikit-learn, etc.

Convirtiendo Modelos a Formato Edge

El primer paso para deployar en edge es convertir tu modelo al formato del framework target. Veamos cómo convertir un modelo a TensorFlow Lite.

import tensorflow as tf

# Cargar modelo entrenado
model = tf.keras.models.load_model('mi_modelo.h5')

# Crear convertidor TFLite
converter = tf.lite.TFLiteConverter.from_keras_model(model)

# Opciones de optimización para mobile
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.target_spec.supported_types = [tf.float16]  # Quantization

# Convertir
tflite_model = converter.convert()

# Guardar
with open('modelo.tflite', 'wb') as f:
    f.write(tflite_model)

Para quantization post-training:

# Quantization dinámico post-entrenamiento
converter = tf.lite.TFLiteConverter.from_keras_model(model)
converter.optimizations = [tf.lite.Optimize.DEFAULT]

# Quanitization de enteros para mayor compresión
converter.representative_dataset = representative_dataset_fn
converter.target_spec.supported_ops = [tf.lite.OpsSet.TFLITE_BUILTINS_INT8]

tflite_model = converter.convert()

En iOS con Core ML:

import coremltools as ct

# Cargar modelo PyTorch
model = torch.load('modelo_pytorch.pth')
model.eval()

# Trazar con TorchScript
example_input = torch.randn(1, 3, 224, 224)
traced = torch.jit.trace(model, example_input)

# Convertir a Core ML
coreml_model = ct.convert(
    traced,
    inputs=[ct.ImageType(name="input", shape=(1, 3, 224, 224))]
)

# Guardar
coreml_model.save("modelo.mlpackage")

Model Compression para Edge

Los modelos de ML modernos son pesados. Un GPT-3 tiene 175B parámetros — imposible que quepa en un teléfono. Las técnicas de compresión son esenciales.

Quantization

Reduce la precisión de los pesos de float32 a int8 o float16. El impacto en accuracy es mínimo para la mayoría de tareas, pero el tamaño y velocidad mejoran dramáticamente.

  • FP16: Mitad de tamaño, velocidad 2x, accuracy casi idéntica
  • INT8: Cuarta parte del tamaño, velocidad 4x, puede perder accuracy en algunas tareas
  • INT4: Octava parte del tamaño, muy agresivo, solo para ciertos casos

Pruning

Eliminar pesos pequeños o conectar neuronas que contribuyen poco. Un modelo puede pasar de 100M a 30M parámetros sin perder accuracy significativa.

import torch.nn.utils.prune as prune

# Pruning magnitud random en capa linear
module = model.layer1
prune.l1_unstructured(module, name='weight', amount=0.3)

# Hacer permanente el pruning
prune.remove(module, 'weight')

Knowledge Distillation

Entrenar un modelo pequeño para que copie el comportamiento de uno grande. El modelo estudiante aprende de los logits del modelo maestro.

Arquitecturas Efficientes

Diseñar modelos desde cero pensando en eficiencia:

  • MobileNet: Depthwise separable convolutions, diseñado para mobile
  • EfficientNet: Balanceo automático de depth/width/resolution
  • MiniGPT: Versiones reducidas de transformers para edge

Benchmark: Mobile vs Cloud

¿Cuándo tiene sentido cada aproximación? La respuesta depende del contexto específico de tu aplicación.

import time

def benchmark_inference(model, input_data, num_runs=100):
    """Compara latencia de inferencia local vs cloud."""
    # Mobile (TFLite)
    start = time.time()
    for _ in range(num_runs):
        mobile_result = model.predict(input_data)  # TFLite
    mobile_time = (time.time() - start) / num_runs

    # Cloud (API call simulada)
    start = time.time()
    for _ in range(num_runs):
        cloud_result = call_cloud_api(input_data)  # HTTP request
    cloud_time = (time.time() - start) / num_runs

    print(f"Mobile: {mobile_time*1000:.2f}ms")
    print(f"Cloud: {cloud_time*1000:.2f}ms")
    print(f"Speedup: {cloud_time/mobile_time:.1f}x")

    return mobile_time, cloud_time

Factores que favorecen Edge:

  • Latencia crítica (< 100ms)
  • Disponibilidad offline necesaria
  • Datos sensibles a privacidad
  • Alto volumen de inferencias (costo cloud se dispara)

Factores que favorecen Cloud:

  • Modelos muy grandes (no caben en dispositivo)
  • Actualizaciones frecuentes del modelo
  • Recursos de cómputo limitados en dispositivo
  • Necesidad de agregar datos de múltiples fuentes

Errores Comunes y Cómo Evitarlos

Error 1: No considerar el tradeoff latencia/potencia de edge vs cloud

El problema: Asumir que porque un modelo funciona bien en tu laptop con GPU, va a funcionar bien en un Pixel 6. La realidad es que un Pixel tiene ~2.4 TFLOPS en su GPU vs una RTX 4090 con ~82 TFLOPS. No es comparable.

La solución: Testea temprano en hardware real. No en emuladores. No en tu laptop. Usa profiling en el dispositivo target. Herramientas como TFLite Benchmark Tool te dan números reales de latencia y uso de memoria.

# Benchmark TFLite en Android
adb shell am start -n org.tensorflow.lite.benchmark/.BenchmarkModelActivity \
  --es args "--graph=/data/local/tmp/model.tflite --num_runs=100"

Error 2: No optimizar modelos para las constraints de mobile (tamaño, latencia)

El problema: Deployar un modelo de 500MB en una app que debe descargarse por datos móviles. Los usuarios abandonan si la app pesa demasiado o si la inferencia tarda más de 2 segundos.

La solución: Aplica quantization desde el inicio del proyecto, no como afterthought. Usa el modelo más pequeño que cumpla tus requisitos de accuracy. Herramientas como model_size_tool te ayudan a trackear el tamaño a medida que desarrollas.

# Verificar tamaño del modelo antes de commit
import os

def check_model_size(model_path, max_size_mb=50):
    size_mb = os.path.getsize(model_path) / (1024 * 1024)
    if size_mb > max_size_mb:
        raise ValueError(f"Modelo demasiado grande: {size_mb:.1f}MB > {max_size_mb}MB")
    return size_mb

# Integrar en CI/CD
assert check_model_size('model.tflite', max_size_mb=50) < 50

Error 3: Asumir que el mismo modelo funciona en edge que en cloud

El problema: Un modelo entrenado en cloud con fp32 puede comportarse muy diferente cuando lo cuantizas a int8. La degradación de accuracy puede ser no lineal — algunas clases se ven más afectadas que otras.

La solución: Evalúa siempre el modelo post-conversión con el mismo dataset de test. Si la accuracy baja más del 2-3%, considera volver a entrenar con técnicas de quantization-aware training (QAT).

# Quantization-Aware Training
import tensorflow_model_optimization as tfmot

qat_model = tfmot.quantization.keras.quantize_model(model)

qat_model.compile(
    optimizer='adam',
    loss='sparse_categorical_crossentropy',
    metrics=['accuracy']
)

# Entrenar con datos
qat_model.fit(train_data, train_labels, epochs=10)

# Convertir — la degradación será menor
converter = tf.lite.TFLiteConverter.from_keras_model(qat_model)
converter.optimizations = [tf.lite.Optimize.DEFAULT]
quantized_model = converter.convert()

Resumen y reflexión

Edge AI no es el futuro — es el presente. Cada vez más la inteligencia se muda al borde por razones prácticas: latencia, privacidad, costo, disponibilidad. Los frameworks como TensorFlow Lite, Core ML y ONNX Runtime Mobile hacen más fácil que nunca llevar modelos a dispositivos reales.

La clave está en pensar en las constraints desde el principio — tamaño del modelo, latencia target, consumo de energía — y optimizar desde el diseño, no como ajuste final. Y siempre, siempre testear en hardware real.

En Colombia tenemos una ventaja: aprendemos a trabajar con recursos limitados, a adaptarnos, a sacar el máximo de lo que tenemos. Edge AI es exactamente eso — hacer machine learning con lo que hay disponible en el borde, sin depender de conexiones que a veces fallan. Eso sí es innovación que pega.
