LLM Production Checklist — Que el 90% No Tiene y Que el 10% Tiene

Hagale pues, parcero. Día 340 y hoy hablamos de algo que me duele el alma: la gente lanzando LLMs a producción sin un checklist. Sin monitoring, sin testing de failure modes, sin nada. El 90% lo hace así — y cuando las cosas fallan, pues chaos. El 10% que sí tiene checklist duerme tranquilo. Aquí le doy el checklist completo para que no le pase lo del 90%. Quedese.

🎯 Por Que Un Checklist de Producción?

Lanzar un LLM a producción no es como deployar una API normal. Un API retorna 200 o 500. Un LLM puede retornar algo que sounds right pero está completamente wrong. Y peor: puede retornar algo harmful. Por eso necesita un checklist específico para LLMs — no el mismo de siempre.

La matemática lo demuestra: según a study de Glean (2024), empresas con checklists pre-launch redujeron incidents en 60%. No es menor. Eso es tiempo de debugging Recuperado, reputation, y plata.

📐 El Framework de Checklist

El framework tiene 3 fases: Pre-Launch, Launch, y Post-Launch. Cada fase tiene items críticos. No se saltee ninguno.

# Production LLM Checklist Framework
class LLMProductionChecklist:
    def __init__(self, llm_name: str):
        self.llm_name = llm_name
        self.pre_launch = ChecklistPhase("Pre-Launch")
        self.launch = ChecklistPhase("Launch")
        self.post_launch = ChecklistPhase("Post-Launch")
        self.completed_items = []
    
    def add_pre_launch_item(self, item: str, passed: bool, notes: str = ""):
        self.pre_launch.add(item, passed, notes)
    
    def add_launch_item(self, item: str, passed: bool, notes: str = ""):
        self.launch.add(item, passed, notes)
    
    def add_post_launch_item(self, item: str, passed: bool, notes: str = ""):
        self.post_launch.add(item, passed, notes)
    
    def can_deploy(self) -> bool:
        """Solo puede deployar si TODOS los pre-launch items pasan."""
        return self.pre_launch.all_passed()
    
    def generate_report(self) -> dict:
        return {
            "llm": self.llm_name,
            "pre_launch": self.pre_launch.summary(),
            "launch": self.launch.summary(),
            "post_launch": self.post_launch.summary(),
            "ready": self.can_deploy()
        }

class ChecklistPhase:
    def __init__(self, name: str):
        self.name = name
        self.items = []
    
    def add(self, item: str, passed: bool, notes: str = ""):
        self.items.append({
            "item": item,
            "passed": passed,
            "notes": notes
        })
    
    def all_passed(self) -> bool:
        return all(i["passed"] for i in self.items)
    
    def summary(self) -> dict:
        passed = sum(1 for i in self.items if i["passed"])
        return {
            "total": len(self.items),
            "passed": passed,
            "failed": len(self.items) - passed,
            "items": self.items
        }

📊 Post-Launch Monitoring: Lo Que El 90% No Tiene

El post-launch sin monitoring es como manejar con los ojos cerrados. Necesita saber cuando el modelo se degrada, cuando los users están frustrados, cuando algo está mal antes de que sea catastrophe.

# Post-Launch Monitoring Framework
class LLMProductionMonitor:
    def __init__(self):
        self.metrics = {
            "latency": [],      # Historial de latencias
            "errors": [],       # Errores por tipo
            "quality": [],      # Scores de calidad
            "cost": [],         # Costo acumulado
            "usage": []         # Requests por minuto
        }
        self.alerts = []
    
    def record_request(self, request_id: str, latency: float, 
                       success: bool, quality_score: float = None,
                       cost: float = 0):
        """Registra metricas de un request."""
        self.metrics["latency"].append(latency)
        self.metrics["usage"].append(time.time())
        self.metrics["cost"].append(cost)
        
        if not success:
            self.metrics["errors"].append({
                "request_id": request_id,
                "timestamp": time.time()
            })
        
        if quality_score is not None:
            self.metrics["quality"].append(quality_score)
        
        # Check alerts
        self._check_alerts()
    
    def _check_alerts(self):
        """Evalua si alguna metrica cruza threshold."""
        # Latencia P95
        if len(self.metrics["latency"]) > 100:
            p95 = np.percentile(self.metrics["latency"][-1000:], 95)
            if p95 > LATENCY_THRESHOLD:
                self.alerts.append({
                    "type": "latency",
                    "value": p95,
                    "threshold": LATENCY_THRESHOLD,
                    "timestamp": time.time()
                })
        
        # Error rate
        recent_errors = len([e for e in self.metrics["errors"] 
                            if time.time() - e["timestamp"] < 300])
        if recent_errors > ERROR_RATE_THRESHOLD:
            self.alerts.append({
                "type": "error_rate",
                "value": recent_errors,
                "threshold": ERROR_RATE_THRESHOLD,
                "timestamp": time.time()
            })
    
    def get_dashboard(self) -> dict:
        """Genera dashboard de estado actual."""
        return {
            "latency_p50": np.median(self.metrics["latency"][-100:]),
            "latency_p95": np.percentile(self.metrics["latency"][-1000:], 95),
            "error_rate": len(self.metrics["errors"]) / len(self.metrics["usage"]),
            "avg_quality": np.mean(self.metrics["quality"][-100:]) if self.metrics["quality"] else 0,
            "total_cost": sum(self.metrics["cost"]),
            "requests_last_hour": len([t for t in self.metrics["usage"] 
                                       if time.time() - t < 3600]),
            "active_alerts": len(self.alerts)
        }

⚠️ Los 3 Errores que el 90% Commete

Error 1: Launch Sin Checklist

El problema: "Ya funciona en dev, vamos a producción". No hay evaluación estructurada, no hay tests específicos, no hay sign-off. Esto es la receta para disaster.

La solución: Usar el checklist de arriba. Si algún item no pasa, no deploya. Fin del cuento. La presión de negocio no es excusa — un LLM fallando en producción cuesta más que un delay de 1 semana.

# Gate de deployment
def can_deploy_to_production(checklist: LLMProductionChecklist) -> bool:
    """Returns True solo si checklist completo y todo pasa."""
    report = checklist.generate_report()
    
    if not checklist.can_deploy():
        print("❌ NO PUEDE DEPLOYAR")
        print("Items fallidos en Pre-Launch:")
        for item in report['pre_launch']['items']:
            if not item['passed']:
                print(f"  - {item['item']}: {item['notes']}")
        return False
    
    print("✅ CHECKLIST APROBADO - Puede deployar")
    return True

Error 2: No Tener Plan de Monitoreo

El problema: Deployan y se olvidan. No hay forma de saber si el modelo se está degradando, si está teniendo más errores, si los users están viendo algo raro. blindness total.

La solución: Instrumentar desde day 1. Latencia, error rate, quality scores, cost. Todo. Y configurar alerts para cuando algo Cruza threshold. No necesita dashboards complejos — necesita saber cuando algo está mal.

# Setup de monitoring básico en 5 minutos
def setup_basic_monitoring(llm_endpoint: str):
    """Setup mínimo de monitoring."""
    monitor = LLMProductionMonitor()
    
    # Middleware o wrapperaround LLM calls
    def monitored_call(prompt, **kwargs):
        start = time.time()
        try:
            response = llm_call(prompt, **kwargs)
            latency = time.time() - start
            monitor.record_request(
                request_id=str(uuid.uuid4()),
                latency=latency,
                success=True,
                quality_score=evaluate_quality(response),
                cost=calculate_cost(prompt, response)
            )
            return response
        except Exception as e:
            latency = time.time() - start
            monitor.record_request(
                request_id=str(uuid.uuid4()),
                latency=latency,
                success=False
            )
            raise
    
    return monitored_call, monitor

Error 3: No Testear Failure Modes

El problema: Solo prueban el happy path. "¿Qué pasa si el LLM retorna empty string?" No lo saben hasta que pasa en producción. "¿Qué pasa si el API key está wrong?" Tampoco. Todo es sorpresa.

La solución: Testear explicitly what happens cuando las cosas fallan. Timeout, empty response, malformed output, rate limit, invalid API key. Cada failure mode debe tener comportamiento definido y testado.

# Failure Mode Testing
FAILURE_MODE_TESTS = [
    ("timeout", "LLM tarda más de 30s", lambda: simulate_timeout()),
    ("empty_response", "LLM retorna string vacío", lambda: simulate_empty()),
    ("malformed_json", "LLM retorna JSON inválido", lambda: simulate_malformed()),
    ("rate_limit", "API rate limit alcanzado", lambda: simulate_rate_limit()),
    ("invalid_api_key", "API key inválida o expirada", lambda: simulate_bad_key()),
    ("prompt_injection", "Input malicioso intenta injection", lambda: simulate_injection()),
    ("pii_leak", "LLM intenta retornar PII", lambda: simulate_pii_request()),
]

def run_failure_mode_tests(llm_wrapper):
    results = []
    for mode_name, description, simulator in FAILURE_MODE_TESTS:
        try:
            # Simular failure
            simulator()
            
            # Llamar LLM con el failure presente
            response = llm_wrapper(prompt="Test prompt")
            
            # Verificar que manejó gracefully
            handled = verify_graceful_handling(response, mode_name)
            results.append({
                "mode": mode_name,
                "description": description,
                "handled": handled,
                "error": None
            })
        except Exception as e:
            results.append({
                "mode": mode_name,
                "description": description,
                "handled": False,
                "error": str(e)
            })
    
    return results
