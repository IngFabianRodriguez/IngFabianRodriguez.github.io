📐 Fundamentos: Qué mide cada métrica y por qué importa

Antes de escribir código, necesitamos entender la matemática detrás de cada métrica. No puedes optimizar algo que no entiendes.

BLEU Score

BLEU (Bilingual Evaluation Understudy) mide la similitud n-gramática entre la salida del modelo y referencias humanas. Es fundamentalmente una métrica de superposición, no de significado.

La fórmula central es:

\text{BLEU} = \text{BP} \cdot \exp\left(\sum_{n=1}^{N} w_n \log p_n\right)

Donde:

  • $p_n$ = precisión n-grama (típicamente n=1 hasta 4)
  • $w_n$ = peso para cada n-grama (uniforme por defecto)
  • BP = Brevity Penalty para castigar salidas demasiado cortas
\text{BP} = \begin{cases} 1 & \text{si } c > r \\ e^{1 - r/c} & \text{si } c \le r \end{cases}

Donde $c$ es la longitud de la candidatura y $r$ es la longitud de referencia.

ROUGE Score

ROUGE (Recall-Oriented Understudy for Gisting Evaluation) mide recuperación, a diferencia de BLEU que mide precisión. Hay varias variantes:

ROUGE-L usa la Longest Common Subsequence (LCS):

\text{ROUGE-L} = \frac{(1+\beta^2) \cdot \text{Precision} \cdot \text{Recall}}{\text{Recall} + \beta^2 \cdot \text{Precision}}

Donde Precision y Recall se calculan sobre la LCS entre candidato y referencia.

METEOR

METEOR va más allá de BLEU al incluir:

  • Stemming (raíces de palabras)
  • Sinonimia (WordNet)
  • Alineamiento de fragmentos (no solo n-gramas)
\text{METEOR} = F_{\text{mean}} \cdot (1 - \text{Penalty})

El penalty castiga fragmentación: mientras más fragmentos desalineados, mayor el penalty.

Perplejidad (Perplexity)

La perplejidad mide qué tan bien un modelo predice una muestra. Es la inversa de la probabilidad normalizada por palabra:

\text{PP}(W) = \left(\prod_{i=1}^{N} \frac{1}{P(w_i | w_{1:i-1})}\right)^{1/N} = 2^{-\frac{1}{N}\sum_{i=1}^{N} \log_2 P(w_i | w_{1:i-1})}

Intuitivamente: si PP = 20, el modelo tiene aproximadamente 20 elecciones equiprobables en cada paso. Menor perplejidad = mejor modelo.

💻 Implementación: BLEU y ROUGE-L desde cero

Vamos a implementar las métricas fundamentales para entender exactamente qué están calculando:

"""
LLM Evaluation Metrics — Día 209
Implementación de BLEU, ROUGE-L y Perplexity desde cero
"""
import math
import re
from collections import Counter
from typing import List, Tuple

# ─────────────────────────────────────────────────────────────────────────────
# 1. BLEU Score desde cero
# ─────────────────────────────────────────────────────────────────────────────

def tokenize(text: str) -> List[str]:
    """Tokenización básica para demo."""
    return re.findall(r'\b\w+\b', text.lower())

def ngrams(tokens: List[str], n: int) -> Counter:
    """Genera n-gramas y sus conteos."""
    return Counter(tuple(tokens[i:i+n]) for i in range(len(tokens)-n+1))

def clipped_precision(candidate: List[str], reference: List[str], n: int) -> float:
    """
    Precisión modificada: cuenta cada n-grama del candidato
    hasta el máximo que aparece en la referencia.
    Evita contar múltiples ocurrencias en exceso.
    """
    cand_ngrams = ngrams(candidate, n)
    ref_ngrams = ngrams(reference, n)
    
    clipped = {}
    for ngram, count in cand_ngrams.items():
        clipped[ngram] = min(count, ref_ngrams.get(ngram, 0))
    
    total = sum(clipped.values())
    if total == 0:
        return 0.0
    
    return total / sum(cand_ngrams.values())

def brevity_penalty(candidate: List[str], reference: List[str]) -> float:
    """BP: Penaliza candidatos más cortos que la referencia."""
    c = len(candidate)
    r = len(reference)
    
    if c > r:
        return 1.0
    return math.exp(1 - r / c) if c > 0 else 0.0

def bleu_score(candidate: str, reference: str, max_n: int = 4, 
               weights: List[float] = None) -> float:
    """
    Calcula BLEU score.
    
    Args:
        candidate: texto generado por el modelo
        reference: texto de referencia humana
        max_n: máximo orden de n-gramas (típicamente 4)
        weights: pesos para cada n (default: uniforme)
    """
    if weights is None:
        weights = [1.0 / max_n] * max_n
    
    cand_tokens = tokenize(candidate)
    ref_tokens = tokenize(reference)
    
    # Evitar división por cero
    if len(cand_tokens) == 0 or len(ref_tokens) == 0:
        return 0.0
    
    # Calcular precisión para cada n
    precisions = []
    for n in range(1, max_n + 1):
        p = clipped_precision(cand_tokens, ref_tokens, n)
        precisions.append(p)
    
    # Si alguna precisión es 0, BLEU es 0
    if any(p == 0 for p in precisions):
        return 0.0
    
    # Promedio ponderado de los log de precisiones
    log_precisions = [math.log(p) for p in precisions]
    avg_log_precision = sum(w * lp for w, lp in zip(weights, log_precisions))
    
    # Brevity penalty
    bp = brevity_penalty(cand_tokens, ref_tokens)
    
    return bp * math.exp(avg_log_precision)

# ─────────────────────────────────────────────────────────────────────────────
# 2. ROUGE-L (LCS-based)
# ─────────────────────────────────────────────────────────────────────────────

def lcs_length(x: List[str], y: List[str]) -> int:
    """Longest Common Subsequence — programación dinámica O(n*m)."""
    m, n = len(x), len(y)
    
    # Versión optimizada en espacio
    prev = [0] * (n + 1)
    curr = [0] * (n + 1)
    
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if x[i-1] == y[j-1]:
                curr[j] = prev[j-1] + 1
            else:
                curr[j] = max(prev[j], curr[j-1])
        prev, curr = curr, prev
    
    return prev[n]

def rouge_l(candidate: str, reference: str, alpha: float = 1.0) -> float:
    """
    Calcula ROUGE-L (F-measure).
    
    ROUGE-L se basa en LCS: la subsecuencia común más larga
    entre candidato y referencia.
    """
    cand_tokens = tokenize(candidate)
    ref_tokens = tokenize(reference)
    
    lcs_len = lcs_length(cand_tokens, ref_tokens)
    
    if lcs_len == 0:
        return 0.0
    
    # Precision: LCS / longitud candidato
    precision = lcs_len / len(cand_tokens)
    
    # Recall: LCS / longitud referencia  
    recall = lcs_len / len(ref_tokens)
    
    # F-measure con parámetro alpha (alpha=1 → recall pesado)
    if precision + recall == 0:
        return 0.0
    
    f_measure = (1 + alpha**2) * precision * recall / (alpha**2 * precision + recall)
    
    return f_measure

# ─────────────────────────────────────────────────────────────────────────────
# 3. Perplejidad (Perplexity)
# ─────────────────────────────────────────────────────────────────────────────

def perplexity(log_probs: List[float]) -> float:
    """
    Calcula perplejidad desde log-probabilidades.
    
    PP = 2^(-1/N * Σ log P(w_i))
    
    Args:
        log_probs: lista de log P(w_i | context) para cada token
    """
    n = len(log_probs)
    if n == 0:
        return float('inf')
    
    # Promedio de log-probabilidades
    avg_log_prob = sum(log_probs) / n
    
    # Perplejidad = 2^(-avg_log_prob)
    # En base e también: PP = exp(-avg_log_prob)
    return math.exp(-avg_log_prob)

def demo_perplexity():
    """
    Demo: calcular perplexity para una secuencia.
    Asumimos un LM simple con probabilidades conocidas.
    """
    # Probabilidades ficticias para demo
    # Secuencia: "el gato come pescado"
    # Log probs de cada token dado el contexto
    log_probs = [
        math.log(0.25),   # P("el")
        math.log(0.15),   # P("gato" | "el")
        math.log(0.30),   # P("come" | "el gato")
        math.log(0.20),   # P("pescado" | "el gato come")
    ]
    
    pp = perplexity(log_probs)
    print(f"Perplejidad: {pp:.2f}")
    print(f"El modelo tiene ~{pp:.0f} elecciones equiprobables por token")
    
    return pp

# ─────────────────────────────────────────────────────────────────────────────
# Uso y tests
# ─────────────────────────────────────────────────────────────────────────────

if __name__ == "__main__":
    # Ejemplo de traducción
    candidate = "The cat is sitting on the mat"
    reference = "The cat is on the mat"
    
    bleu = bleu_score(candidate, reference)
    rouge = rouge_l(candidate, reference)
    
    print(f"BLEU-4:  {bleu:.4f}")
    print(f"ROUGE-L: {rouge:.4f}")
    
    # Demo perplexity
    demo_perplexity()
    
    # Ejemplo: BLEU es bajo para parafraseo correcto
    candidate2 = "A small cat is resting on the floor"
    reference2 = "The cat is sitting on the mat"
    
    bleu2 = bleu_score(candidate2, reference2)
    rouge2 = rouge_l(candidate2, reference2)
    
    print(f"\nParafraseo semántico (mismo significado, palabras distintas):")
    print(f"BLEU-4:  {bleu2:.4f}  ← ¡BAJO! Pero la significado es correcto")

    print("\n↑ Esto demuestra por qué BLEU no mide significado.")

👥 Human Evaluation: Cuándo y Cómo

Las métricas automáticas nunca reemplazan completamente la evaluación humana. Human evaluation es necesaria cuando:

  • El task es generativo creativo (no hay referencia única correcta)
  • El benchmark no captura tu dominio específico
  • Necesitas validar fluidez, coherencia, y utilidad real

Framework de evaluación humana:

"""
Human Evaluation Framework — Día 209
"""
from dataclasses import dataclass
from typing import List, Optional
import random

@dataclass
class HumanEvalSample:
    prompt: str
    response: str
    annotator_id: str
    scores: dict

def setup_evaluation_campaign(
    samples: List[str],
    annotators: List[str],
    dimensions: List[str] = None
) -> dict:
    """
    Configura una campaña de evaluación humana.
    
    Dimensiones recomendadas para LLM:
    - Fluidez (¿suena natural el texto?)
    - Precisión (¿la información es correcta?)
    - Coherencia (¿el texto tiene lógica?)
    - Utilidad (¿cumple el objetivo del usuario?)
    - Safety (¿hay contenido harmful?)
    """
    if dimensions is None:
        dimensions = ["fluidez", "precision", "coherencia", "utilidad", "safety"]
    
    # Asignar muestras a annotadores (con overlap para medir agreement)
    assignments = {}
    for sample_idx, sample in enumerate(samples):
        # Cada muestra la evalúan 2 annotadores
        annotator_subset = random.sample(annotators, min(2, len(annotators)))
        assignments[sample_idx] = annotator_subset
    
    return {
        "dimensions": dimensions,
        "assignments": assignments,
        "total_samples": len(samples),
        "overlap": 2,
        "scale": "1-5 Likert",
    }

def calculate_interannotator_agreement(annotations: List[HumanEvalSample]) -> dict:

🚨 Los 3 Errores Que Van a Hacerte Tomar Malas Decisiones

Error 1: Usar BLEU para todo — cuando BLEU no correlaciona con juicio humano

El problema: Estás evaluando un sistema de parafraseo. Tu modelo genera "El perro está corriendo en el parque" mientras la referencia es "Un canino trotando por el jardín". BLEU es 0.15. Pero la calidad semántica es excelente. Tú o tu manager ven el 0.15 y决定弃掉 el modelo.

Por qué pasa: BLEU mide superposición n-gramática, no significado. Dos oraciones semánticamente idénticas con vocabulario diferente tienen BLEU casi 0.

La matemática: La correlación entre BLEU y juicio humano en tareas generativas creativas es típicamente $r < 0.4$ en estudios como Callison-Burch et al. (2006).

La solución: Para tareas donde el significado importa, usa METEOR o evalúa con embedding similarity:

from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

def semantic_similarity(candidate: str, reference: str, 
                        embedder) -> float:
    """Similitud semántica vía embeddings (ej: sentence-transformers)."""
    emb_cand = embedder.encode([candidate])
    emb_ref = embedder.encode([reference])
    return cosine_similarity(emb_cand, emb_ref)[0][0]

Error 2: No evaluar en domain específico — y el modelo falla en producción

El problema: Tu modelo saca 72% en MMLU (bien) y 68% en HellaSwag (aceptable). Lo deployas para un chatbot médico en Bogotá. En producción, el modelo da información incorrecta sobre medicamentos y genera respuestas técnicamente correctas pero culturalmente inapropiadas para pacientes colombianos.

La matemática: El distribution shift entre benchmarks generales y tu dominio:

\Delta_{\text{distribution}} = D_{\text{KL}}(P_{\text{domain}} \| P_{\text{benchmark}})

Si $\Delta_{\text{distribution}}$ es grande, tu modelo generaliza mal a tu caso específico.

La solución: Crea un benchmark interno que refleje tu distribución real:

"""
Domain-Specific Evaluation Benchmark
"""
from datasets import Dataset

def create_domain_benchmark(
    domain_name: str,
    samples: List[dict],
    ground_truth: List[dict]
) -> Dataset:
    """
    Crea un benchmark para tu dominio específico.
    
    samples: [{"prompt": "...", "context": "..."}]
    ground_truth: [{"expected_response": "...", "evaluation_criteria": "..."}]
    """
    data = {
        "domain": domain_name,
        "num_samples": len(samples),
        "creation_date": "2026-07-28",
        "samples": samples,
        "ground_truth": ground_truth,
    }
    
    return Dataset.from_dict(data)

# Ejemplo: Benchmark médico colombiano
medical_samples = [

Error 3: Perplejidad sin contexto — modelos pequeños parecen mejores que grandes

El problema: Tu modelo de 7B tiene perplexity 18. GPT-4o-mini tiene perplexity 22. Decides usar tu 7B porque "mide mejor". Tres meses después, tu 7B responde preguntas médicas con información desactualizada y no puede seguir instrucciones complejas que GPT-4o-mini maneja sin problema.

Por qué pasa: La perplejidad se mide en un dataset específico (típicamente WikiText-103 o similar). Un modelo pequeño puede tener mejor perplejidad porque:

  • El dataset de evaluación es similar a su training data
  • El modelo memorizó en lugar de generalizar
  • No mide capacidad de follow-instructions o reasoning

La matemática: La perplejidad es condicional al dataset:

\text{PP}(W_{\text{test}}) = \left(\prod_{i=1}^{N} \frac{1}{P(w_i | w_{1:i-1}; \theta)}\right)^{1/N}

Cambiar $W_{\text{test}}$ cambia la perplejidad dramáticamente.

La solución: Nunca uses perplexity como métrica única. Usa una combinación:

"""
Multi-metric evaluation framework
"""
def comprehensive_model_evaluation(
    model,
    benchmarks: dict,
    task_specific_evals: dict = None
) -> dict:
    """
    Evaluación comprehensiva que combina:
    - Perplexity (solo como referencia, no como métrica principal)
    - Task-specific accuracy (in-domain)
    - Human evaluation scores
    - Instruction following
    """
    results = {
        "perplexity": evaluate_perplexity(model, benchmarks["perplexity_dataset"]),
        "mmlu": evaluate_accuracy(model, benchmarks["mmlu"]),
        "domain_accuracy": evaluate_accuracy(model, benchmarks["domain_specific"]),
        "instruction_following": evaluate_ifeval(model),
    }
    
    # Score ponderado que prioriza utilidad real
    final_score = (
        0.15 * (1 / results["perplexity"]) +  # invert because lower is better
        0.25 * results["mmlu"] +
        0.35 * results["domain_accuracy"] +
        0.25 * results["instruction_following"]
    )
    
    results["final_score"] = final_score
    return results

# Nunca: "Este modelo es mejor porque tiene menor perplexity"

✅ Resumen y Cierre

Parcero, lo que aprendimos hoy:

  • BLEU mide superposición n-gramática. Bien para traducción con múltiples referencias, mal para parafraseo o generación creativa.
  • ROUGE mide recall de n-gramas. Bueno para summarización donde recuperar contenido es prioritario.
  • METEOR incluye stemming y sinonimia. Mejor correlación con juicio humano que BLEU en varios casos.
  • Perplejidad es útil como referencia pero nunca como métrica única. Un modelo puede tener baja perplejidad y aún así fallar en tareas que importan.
  • Benchmarks como MMLU, HellaSwag, TruthfulQA dan comparabilidad estándar pero no reemplazan evaluación in-domain.
  • Human evaluation es indispensable para tareas creativas y cuando el benchmark no captura tu caso de uso.

La próxima vez que alguien te diga "el modelo tiene 85 de BLEU", pregunta: "¿85 de BLEU en qué dataset, para qué tarea, y con cuántas referencias?". En Bogotá decimos que "el que solo mide, mal interpreta".
