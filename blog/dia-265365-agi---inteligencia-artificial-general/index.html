📊 ¿Por Qué Monitorizar LLMs No Es Opcional?

Un LLM en producción no es una función matemática estática. Es un sistema adaptativo que:

  • **Deriva**: La distribución de inputs cambia con el tiempo (concept drift)
  • **Se degrada**: La calidad de respuestas puede bajar sin que usted lo note
  • **Cuesta**: Cada token tiene un costo en dólares, y los dollars no son infinitos
  • **Latencia variable**: El tiempo de respuesta fluctúa por carga, throttling, y red

La matemática detrás es simple. Si usted no mide, no puede mejorar. Y si no puede cuantificar el problema, no puede resolverlo. Esto no es diferente a monitoring de cualquier otro sistema en producción — pero tiene matices únicas porque el "output correctness" no es binario.

# La ecuación fundamental del monitoring de LLMs
# Quality Score = f(Accuracy, Coherence, Relevance, Safety)

class LLMMetrics:
    """
    Framework de métricas para LLMs en producción.
    Cada métrica tiene rangos aceptables que definen SLAs.
    """
    
    def __init__(self):
        self.baseline_established = False
        self.quality_baseline = None
        
    def establish_baseline(self, golden_dataset: list[dict]) -> dict:
        """
        Antes de monitorizar, necesitas un punto de referencia.
        El baseline es tu 'normal' - sin esto, no hay comparación posible.
        """
        # Calcular métricas sobre dataset validado
        scores = []
        for item in golden_dataset:
            expected = item['expected']
            actual = self.generate(item['prompt'])
            score = self.evaluate(expected, actual)
            scores.append(score)
            
        self.quality_baseline = {
            'mean': np.mean(scores),
            'std': np.std(scores),
            'p5': np.percentile(scores, 5),
            'p95': np.percentile(scores, 95),
            'n_samples': len(scores)
        }
        self.baseline_established = True
        return self.quality_baseline
        
    def detect_drift(self, current_scores: list[float], window: int = 100) -> bool:
        """
        Detecta si la calidad actual diverge significativamente del baseline.
        Usa un test Z con umbral configurable (típicamente 2σ).
        """
        if not self.baseline_established:
            raise ValueError("Primero establece un baseline con establish_baseline()")
            
        baseline_mean = self.quality_baseline['mean']
        baseline_std = self.quality_baseline['std']
        
        # Ventana móvil de scores recientes
        recent = current_scores[-window:]
        current_mean = np.mean(recent)
        
        # Z-score
        z_score = (current_mean - baseline_mean) / baseline_std
        
        # Drift significativo: |z| > 2 (2 desviaciones estándar)
        return abs(z_score) > 2

🔢 Las 4 Métricas Que Realmente Importan

1. Quality Score (La Más Difícil de Medir)

Calidad no es binario. No es "bueno" o "malo". Es un espectro. La fórmula que usamos en producción:

def quality_score(response: str, context: dict, expected: str = None) -> float:
    """
    Composite quality score para respuestas de LLM.
    
    Componentes:
    - Relevance: ¿Responde a lo que se preguntó?
    - Coherence: ¿Las ideas fluyen lógicamente?
    - Factual accuracy: ¿No inventa información? (hallucination detection)
    - Safety: ¿No genera contenido dañino?
    """
    
    # Subscores normalizados [0, 1]
    relevance = calculate_relevance(response, context['query'])
    coherence = calculate_coherence(response)
    factual = calculate_factual_accuracy(response, context.get('facts', []))
    safety = calculate_safety_score(response)
    
    # Ponderación configurable por caso de uso
    weights = {'relevance': 0.3, 'coherence': 0.2, 'factual': 0.3, 'safety': 0.2}
    
    composite = (
        relevance * weights['relevance'] +
        coherence * weights['coherence'] +
        factual * weights['factual'] +
        safety * weights['safety']
    )
    
    return composite  # Score entre 0 y 1

def calculate_factual_accuracy(response: str, facts: list[str]) -> float:
    """
    Detecta alucinaciones verificando hechos contra ground truth.
    Esto es costoso (llama otro LLM o base de hechos), pero necesario.
    """
    if not facts:
        return 0.5  # Neutral si no hay hechos contra qué verificar
    
    # Verificar cada hecho
    verified = 0
    for fact in facts:
        # Usar embedding similarity para verificar
        response_emb = embed(response)
        fact_emb = embed(fact)
        similarity = cosine_similarity(response_emb, fact_emb)
        
        # Threshold: 0.85 es típicamente bueno
        if similarity > 0.85:
            verified += 1
            
    return verified / len(facts)

2. Cost Tracking ($$$)

class LLMCostTracker:
    """
    Tracking de costos por token con granularidad configurable.
    Permite attribuir costos a usuarios, features, o time periods.
    """
    
    def __init__(self, cost_per_1k_input_tokens: float, cost_per_1k_output_tokens: float):
        self.input_cost = cost_per_1k_input_tokens / 1000
        self.output_cost = cost_per_1k_output_tokens / 1000
        self.total_spent = 0.0
        self.by_user = defaultdict(float)
        self.by_day = defaultdict(float)
        
    def record(self, user_id: str, input_tokens: int, output_tokens: int):
        cost = (input_tokens * self.input_cost) + (output_tokens * self.output_cost)
        self.total_spent += cost
        self.by_user[user_id] += cost
        self.by_day[datetime.now().date()] += cost
        
    def get_cost_per_response(self) -> dict:
        """
        Costo promedio por respuesta - métrica crítica para pricing.
        """
        return {
            'total': self.total_spent,
            'daily_average': self.total_spent / max(1, len(self.by_day)),
            'cost_per_user': dict(self.by_user),
            'cost_by_day': dict(self.by_day)
        }
        
    def alert_if_anomaly(self, threshold_pct: float = 0.2):
        """
        Alerta si el costo se dispara vs baseline.
        Un aumento de 20%+ típicamente indica problema (loop infinito, etc).
        """
        days = sorted(self.by_day.keys())
        if len(days) < 7:
            return  # Necesitamos al menos 7 días para comparar
            
        recent = sum(self.by_day[d] for d in days[-3:])
        baseline = sum(self.by_day[d] for d in days[:-3]) / max(1, len(days[:-3]))
        
        if baseline > 0 and (recent / baseline) > (1 + threshold_pct):
            print(f"🚨 COST ALERT: Spending {recent/baseline:.1f}x baseline")

3. Latency Percentiles (No Solo Promedio)

class LLM latencyTracker:
    """
    Tracking de latencia con percentiles, no solo promedio.
    El promedio engaña - percentiles muestran la experiencia real.
    """
    
    def __init__(self):
        self.latencies = []  # en milisegundos
        self.by_endpoint = defaultdict(list)
        
    def record(self, endpoint: str, latency_ms: float):
        self.latencies.append(latency_ms)
        self.by_endpoint[endpoint].append(latency_ms)
        
    def get_percentiles(self) -> dict:
        """
        Percentiles importan más que el promedio.
        p50 = mediana (50% de requests son más rápidos)
        p95 = threshold para SLAs típicos
        p99 = experiencia del usuario "power user"
        """
        if not self.latencies:
            return {}
            
        sorted_lat = sorted(self.latencies)
        n = len(sorted_lat)
        
        return {
            'p50': sorted_lat[int(n * 0.50)],
            'p75': sorted_lat[int(n * 0.75)],
            'p90': sorted_lat[int(n * 0.90)],
            'p95': sorted_lat[int(n * 0.95)],
            'p99': sorted_lat[int(n * 0.99)],
            'mean': np.mean(self.latencies),
            'std': np.std(self.latencies)
        }
        
    def should_alert(self, slo_p95_ms: float = 2000, slo_p99_ms: float = 5000) -> bool:
        """
        SLO: Service Level Objective
        Típico: p95 < 2s, p99 < 5s para chat一般的
        """
        p = self.get_percentiles()
        return p.get('p95', 0) > slo_p95_ms or p.get('p99', 0) > slo_p99_ms

4. Drift Detection (La Más Subestimada)

class ConceptDriftDetector:
    """
    Detecta cuando la distribución de inputs o outputs cambia.
    Esto es crítico porque los LLMs pueden empezar a fallar
    sin que nadie lo note si no se mide.
    
    Usa Population Stability Index (PSI) - industria estándar.
    """
    
    def calculate_psi(self, expected: np.array, actual: np.array, buckets: int = 10) -> float:
        """
        Population Stability Index
        
        PSI < 0.1: Sin cambio significativo
        PSI 0.1-0.2: Cambio moderado, monitorear
        PSI > 0.2: Cambio significativo, action required
        """
        # Crear buckets
        breakpoints = np.percentile(expected, np.linspace(0, 100, buckets + 1))
        
        # Calcular proporciones por bucket
        expected_pcts = np.histogram(expected, breakpoints)[0] / len(expected)
        actual_pcts = np.histogram(actual, breakpoints)[0] / len(actual)
        
        # Evitar division por zero
        expected_pcts = np.where(expected_pcts == 0, 0.0001, expected_pcts)
        actual_pcts = np.where(actual_pcts == 0, 0.0001, actual_pcts)
        
        # Calcular PSI
        psi = np.sum((actual_pcts - expected_pcts) * np.log(actual_pcts / expected_pcts))
        
        return psi
        
    def monitor_embedding_drift(self, current_embeddings: np.array, baseline_embeddings: np.array) -> float:
        """
        Monitorea drift basándose en embeddings.
        Si los inputs del mundo real son muy distintos al training set,
        el modelo puede degradarse.
        """
        # Calcular statistics de embeddings
        current_mean = np.mean(current_embeddings, axis=0)
        baseline_mean = np.mean(baseline_embeddings, axis=0)
        
        # Distancia euclidiana entre centros de distribución
        drift_score = np.linalg.norm(current_mean - baseline_mean)
        
        # Threshold típico
        if drift_score > 0.15:
            print(f"⚠️ EMBEDDING DRIFT: {drift_score:.3f} (threshold: 0.15)")
            
        return drift_score

class LLMMetricsCollector:

    Este collector corre cada vez que Prometheus hace scrape.
    Acumula métricas y las expone.

        # Yield metrics for Prometheus to collect

        yield llm_cost_dollars

⚠️ Los 3 Errores Que El 80% Comete

Error 1: No Monitorizar y Descubrir Problemas Por Tickets de Usuarios

El problema: Cuando el CEO te pregunta "¿por qué el chatbot está dando información incorrecta?" y tú no tienes datos para responder. Estás volando a ciegas.

El impacto: Daño reputacional, churn de usuarios, y fuegos artificiales que pudieron prevenirse.

La matemática: Si 1% de tus usuarios se queja, ¿cuántos simplemente se fueron sin decir nada? La regla del 96% dice que solo 4% de usuarios insatisfechos se queja. El resto simplemente no vuelve.

La solución: Instrumentar desde day 1. No necesitas todo perfecto, pero necesitas visibilidad básica:

# Logging estructurado mínimo viable para LLM
def log_llm_interaction(prompt: str, response: str, latency_ms: float, 
                        user_id: str = None, metadata: dict = None):
    """
    Logging estructurado - mínimo necesario para debug.

    # Alerta si latencia > threshold
    if latency_ms > 5000:
        logger.warning('llm_slow_response', extra=log_entry)

Error 2: No Tener Baseline de Quality Para Comparar

El problema: Mides "quality score = 0.85" hoy. ¿Es eso bueno o malo? Sin baseline, no tienes idea. No puedes decir si mejoraste o empeoraste.

El impacto: Estás optimizando sin referencia. No sabes si tus cambios ayudaron o no.

La matemática: El Z-score requiere baseline y std. Sin esto, no puedes hacer testing A/B válido:

# Test A/B sin baseline es inútil
def test_ab_quality(variant_a_scores: list, variant_b_scores: list, 
                    baseline_mean: float, baseline_std: float) -> dict:
    """
    Test A/B válido requiere baseline para comparar.
    """
    mean_a = np.mean(variant_a_scores)
    mean_b = np.mean(variant_b_scores)
    
    # Calcular z-scores vs baseline
    z_a = (mean_a - baseline_mean) / baseline_std
    z_b = (mean_b - baseline_mean) / baseline_std
    
    # Solo puedes decir "mejor" si improves vs baseline
    # Y la diferencia debe ser estadísticamente significativa
    from scipy import stats
    _, p_value = stats.ttest_ind(variant_a_scores, variant_b_scores)
    
    return {
        'variant_a_mean': mean_a,
        'variant_b_mean': mean_b,
        'z_vs_baseline_a': z_a,
        'z_vs_baseline_b': z_b,
        'p_value': p_value,
        'significant': p_value < 0.05
    }

La solución: Crear un golden dataset desde el día 1. 100-500 ejemplos representativos con respuestas esperado. Esto es tu baseline. Sin esto, estás ciega.

Error 3: Monitoring Sin Action Items (Data Sin Usar Para Mejorar)

El problema: Tienes dashboards hermosos en Grafana. Pero nadie los mira. Y cuando algo se rompe, la data no se usa para arreglar nada. Es decoration, no instrumentación.

El impacto: Gastas dinero en monitoring pero no obtienes valor. Es como tener un doctor que te pesa todos los días pero nunca te dice qué hacer si subiste de peso.

La solución: Cada métrica necesita un action item asociado:

# Actionable alerting - cada alert tiene owner y remediation
ALERT_RULES = {
    'quality_below_threshold': {
        'metric': 'llm_quality_score',
        'threshold': 0.75,
        'action': 'page_oncall_SRE',
        'remediation': 'Verificar si hay model update pendiente o prompts degradados',
        'escalation_hours': 1
    },
    'cost_anomaly': {
        'metric': 'llm_cost_per_hour',
        'threshold_pct_increase': 0.20,  # 20% vs baseline
        'action': 'slack_alert_cost_team',
        'remediation': 'Revisar si hay loop infinito o usuarios abusando API',
        'escalation_hours': 4
    },
    'latency_p95_above_slo': {
        'metric': 'llm_latency_p95',
        'threshold_ms': 3000,
        'action': 'page_oncall_SRE',
        'remediation': 'Escalar horizontalmente o reducir batch size',
        'escalation_hours': 0  # Inmediato
    },
    'drift_detected': {
        'metric': 'psi_score',
        'threshold': 0.2,
        'action': 'ticket_to_ml_team',
        'remediation': 'Evaluar si necesita re-training o prompt adjustment',
        'escalation_hours': 24
    }
}

def process_alert(rule_name: str, metric_value: float):
    """
    Cada alert debe tener owner, action, y remediation documentados.
    No solo "se rompió" - saber qué hacer.
    """
    rule = ALERT_RULES[rule_name]
    
    # Crear incident ticket con todo el contexto
    incident = {
        'title': f"Alert: {rule_name}",
        'severity': 'P1' if rule['escalation_hours'] == 0 else 'P2',
        'owner': rule['action'],
        'remediation': rule['remediation'],
        'metric_value': metric_value,
        'timestamp': datetime.utcnow()
    }
    
    # Enviar al sistema de incidentes (PagerDuty, OpsGenie, etc)
    incident_manager.create(incident)

🎯 Resumen y Cierre Colombiano

Hagale pues, parcero. Monitoring de LLMs no es opcional. Es tan esencial como el monitoreo de tu servidor de producción. Sin esto:

  • No sabes si tu modelo está respondiendo bien o mal
  • No puedes hacer testing A/B válido
  • No puedes optimizar porque no tienes datos
  • Descubres problemas cuando el usuario ya se quejó

La matemática es simple: lo que no se mide, no se mejora. Y con costos de $100-200 por millón de tokens, un LLM descontrolado puede costar miles de dólares al mes sin que nadie lo note.

El dashboard mínimo que necesitas: Quality Score + Latency Percentiles (p50/p95/p99) + Cost per Day + Error Rate. Con eso puedes detectar 90% de los problemas antes de que usuarios se quejen.

Y recuerde: monitoring sin action items es decoración. Cada alerta debe tener quién es responsable y qué hacer. De lo contrario, es solo ruido.

Nos vemos en el día 266, donde hablaremos de LLM Failures y Graceful Degradation. Porque de nada sirve monitorear si después no sabes qué hacer cuando se cae. Un abrazo, parcero.
