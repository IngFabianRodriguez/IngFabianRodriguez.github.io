🎯 AI Product Development — Intro

Hagale pues, parcero. Día 226 y hoy hablamos de algo que muchos ML engineers ignoran: cómo construir productos que la gente realmente use. No se trata de tener el modelo más fancy ni la arquitectura más compleja. Se trata de resolver problemas reales de forma que los usuarios digan "esto sí sirve". Dejaló quieto y sigue leyendo. Tintico.

🤔 La Mentalidad de Producto vs. La Mentalidad de Modelo

La mayoría de los data scientists y ML engineers estamos entrenados para optimizar métricas de modelo: accuracy, F1, AUC, perplexity. Pero cuando construyes un producto, las métricas que importan son otras:

  • User Engagement: ¿El usuario vuelve?
  • Task Completion Rate: ¿Completan lo que querían hacer?
  • Time to Value: ¿Cuánto tarda el usuario en ver beneficio?
  • NPS / Satisfaction: ¿Lo recomendarían?
  • Business Outcomes: ¿Ayuda a generar revenue o reducir costos?

La fórmula del éxito en producto ML:

# Product-ML fit: No es solo accuracy
class ProductMLMetric:
    def calculate_product_ml_score(
        model_metrics: Dict,
        user_metrics: Dict,
        business_metrics: Dict
    ) -> float:
        """
        Score que balancea modelo, usuario y negocio.
        
        La fórmula: Product ML Score = f(model, ux, business)
        
        No basta con un modelo preciso si:
        - Es muy lento (mala UX)
        - No se integra bien en el workflow del usuario
        - No impacta métricas de negocio
        """
        model_score = model_metrics.get("accuracy", 0)
        ux_score = user_metrics.get("task_completion_rate", 0)
        biz_score = business_metrics.get("conversion_lift", 0)
        
        # Ponderación depende del contexto
        # Early stage: UX > Model
        # Growth: Model + UX > Business
        # Maturity: Business > Model + UX
        
        return (
            0.25 * model_score +
            0.35 * ux_score +
            0.40 * biz_score
        )

🗺️ ML Roadmap Planning — Cómo Definir Qué Hacer

Un ML roadmap efectivo no es una lista de modelos. Es una secuencia de problemas a resolver ordenados por impacto y factibilidad.

El Framework ICE para Priorización

# Framework ICE: Impact, Confidence, Effort
class ICEPrioritizer:
    """
    Framework de priorización para ML projects.
    Ordena por: ICE = Impact × Confidence × Effort
    """
    
    def calculate_ice(
        self,
        impact: float,      # 1-10: Cuánto mejora user/business metric
        confidence: float,  # 0-1: Qué tan seguro estás del impacto
        effort: float      # 1-10: Dificultad (invertido luego)
    ) -> float:
        """
        ICE Score = Impact × Confidence × (1/Effort)
        
        - Impact: potencial de mejora en métricas
        - Confidence: qué tan seguro estás (basado en data/experimentos)
        - Effort: complejidad/duración del proyecto
        """
        return impact * confidence * (1 / effort)
    
    def prioritize(self, candidates: List[MLProject]) -> List[MLProject]:
        """Ordena proyectos por ICE score"""
        scored = []
        for project in candidates:
            ice = self.calculate_ice(
                project.impact,
                project.confidence,
                project.effort
            )
            scored.append((ice, project))
        
        # Ordenar por ICE descendente
        scored.sort(reverse=True, key=lambda x: x[0])
        return [p for _, p in scored]

# Ejemplo de uso
projects = [
    MLProject("Search ranking v2", impact=9, confidence=0.8, effort=7),
    MLProject("Recommendation engine", impact=8, confidence=0.6, effort=8),
    MLProject("Spam detection", impact=6, confidence=0.9, effort=3),
    MLProject("Chatbot v2", impact=7, confidence=0.5, effort=9),
]

prioritizer = ICEPrioritizer()
ordered = prioritizer.prioritize(projects)
# Output: [Spam detection, Search ranking v2, Recommendation engine, Chatbot v2]

El Framework RICE

# RICE: Reach, Impact, Confidence, Effort
class RICEPrioritizer:
    """
    Framework RICE para priorización más refinada.
    Score = (Reach × Impact × Confidence) / Effort
    
    - Reach: Cuántos usuarios afecta (por quarter)
    - Impact: Effect on metric per user (1-3 scale)
    - Confidence: % de certeza en la estimación
    - Effort: person-months requeridos
    """
    
    def rice_score(
        self,
        reach: int,          # Usuarios por quarter
        impact: float,       # 0.25, 0.5, 1, 2, 3
        confidence: float,   # 0-1
        effort: float        # Person-months
    ) -> float:
        return (reach * impact * confidence) / effort

📝 ML Product Requirements — Cómo Escribir Specs

Un ML product spec no es lo mismo que un software spec. Tienes que definir:

  • Qué problema resuelve (user need)
  • Cómo se mide el éxito (metrics)
  • Qué tradeoffs aceptas (accuracy vs latency vs cost)
  • Cómo se comporta en edge cases
# ML Product Requirements Document Template
class MLProductSpec:
    """
    Template para especificar features ML.
    """
    
    # 1. User Need
    user_need: str = """
    Como [usuario],
    quiero [acción con ML],
    para [beneficio/outcome].
    """
    
    # 2. Success Metrics
    metrics: Dict = {
        "primary": {
            "metric": "task_completion_rate",
            "baseline": 0.65,
            "target": 0.80,
            "direction": "increase"
        },
        "secondary": {
            "metric": "time_to_completion",
            "baseline": "45s",
            "target": "< 20s",
            "direction": "decrease"
        }
    }
    
    # 3. ML Problem Definition
    ml_problem: Dict = {
        "type": "classification",  # or regression, ranking, etc.
        "input": "user_query_text",
        "output": "predicted_intent",
        "classes": ["billing", "support", "sales", "other"],
        "confidence_threshold": 0.75  # Below this → human handoff
    }
    
    # 4. Tradeoffs (LAWS: Latency, Accuracy, Weight/cost, Scope)
    tradeoffs: Dict = {
        "latency": {
            "target": "< 200ms p95",
            "hard_requirement": True,
            "fallback": "cached_response"
        },
        "accuracy": {
            "target": "> 85% precision",
            "hard_requirement": False,
            "fallback": "human_review"
        },
        "cost": {
            "target": "< $0.001 per inference",
            "hard_requirement": True
        }
    }
    
    # 5. Edge Cases
    edge_cases: List[str] = [
        "Low confidence predictions → human handoff",
        "Ambiguous queries → clarify with user",
        "Multi-intent queries → handle dominant intent",
        "Out-of-scope queries → graceful degradation"
    ]
    
    # 6. Monitoring
    monitoring: Dict = {
        "track": ["accuracy", "latency", "fallback_rate"],
        "alert_on": {
            "accuracy_drop": 0.05,  # 5% drop triggers alert
            "fallback_rate_increase": 0.10
        }
    }

📊 Midiendo Success de ML Features

No todas las métricas de ML son iguales en términos de impacto de producto. Aquí va cómo pensar en measurement.

ML Feature Evaluation Framework

# Framework de evaluación de features ML en producción
class MLFeatureEvaluator:
    """
    Evalúa features ML usando el framework:
    - Online metrics (user-facing)
    - Offline metrics (model performance)
    - Business metrics (revenue, costs)
    """
    
    def evaluate_feature(
        self, 
        feature_name: str,
        online_metrics: Dict,
        offline_metrics: Dict,
        business_metrics: Dict
    ) -> Dict:
        """Evalúa una feature ML holísticamente"""
        
        # Online: ¿Los usuarios están mejor?
        online_score = self.score_online(online_metrics)
        
        # Offline: ¿El modelo está bien calibrado?
        offline_score = self.score_offline(offline_metrics)
        
        # Business: ¿Impacta el bottom line?
        business_score = self.score_business(business_metrics)
        
        return {
            "feature": feature_name,
            "online_score": online_score,     # 0-1
            "offline_score": offline_score,   # 0-1
            "business_score": business_score,  # 0-1
            "overall": (online_score + offline_score + business_score) / 3,
            "recommendation": self.get_recommendation(online_score, offline_score, business_score)
        }
    
    def score_online(self, metrics: Dict) -> float:
        """
        Score de métricas online.
        Usa delta vs baseline y statistical significance.
        """
        if not metrics.get("has_control_test"):
            return 0.5  # Unknown
        
        lift = metrics.get("metric_lift", 0)
        p_value = metrics.get("p_value", 1)
        
        # Solo cuenta si es statistically significant
        if p_value > 0.05:
            return 0.5  # Not significant
        
        # Normalizar lift a 0-1
        # Asume que 5% lift = 1.0, 0% = 0.5, -5% = 0
        normalized = 0.5 + (lift / 0.05)
        return max(0, min(1, normalized))
    
    def get_recommendation(
        self, 
        online: float, 
        offline: float, 
        business: float
    ) -> str:
        if online < 0.3:
            return "REMOVE: User-facing metrics declining"
        elif offline < 0.3:
            return "REFINE: Model needs retraining/tuning"
        elif business < 0.3:
            return "RETHINK: Feature doesn't impact business"
        elif online > 0.7 and business > 0.7:
            return "SCALE: Feature working well, expand"
        else:
            return "MONITOR: Keep tracking, inconclusive"

⚠️ Los 3 Errores Más Comunes

Error 1: Construir ML Features Sin User Need Claro

El problema: El classic "we have a cool model, let's find a use case". Primero decides qué modelo construir y luego tratas de venderlo. Esto rara vez funciona porque:

  • El modelo resuelve un problema que nobody has
  • La solución no encaja en el workflow del usuario
  • El esfuerzo de integration supera el beneficio perceived

La solución: Invierte en user research ANTES de pensar en modelos. Aplica el framework "Jobs to Be Done":

# Jobs to Be Done para ML
def identify_ml_opportunity() -> List[Opportunity]:

    3. ¿Qué información le falta para completar el trabajo?
    4. ¿ ML puede proporcionar esa información mejor que alternatives?

    opportunities = []

    # - User interviews

    # - Analytics: where do users drop off?
    # - Competitor analysis: what are others solving with ML?

Error 2: Overengineering la Solución ML Cuando una Heurística Es Suficiente

El problema: Muchos ingenieros ML sienten que usar logistic regression o reglas simples es " below them". Instintivamente van a transformers cuando con 4 reglas de if-else resuelves el 80% del problema.

La solución: Aplica la **Ley de la Navaja de Occam** para producto ML:

# No siempre necesitas un modelo complejo
class SolutionSelector:
    """
    Framework para seleccionar la solución correcta.
    Orden: Simple → Complex
    """
    
    SOLUTION_HIERARCHY = [
        "rules",           # If-then rules, regex
        "heuristics",     # Score-based rules
        "statistics",     # Simple statistical models
        "classical_ml",   # Logistic regression, decision trees
        "deep_learning",  # Neural networks
        "foundation_models"  # Large pre-trained models
    ]
    
    def select_solution(self, problem: Problem) -> str:
        """
        Selection strategy:
        1. Start with simplest solution
        2. Only escalate if metrics don't meet threshold
        3. Document WHY you escalated
        """
        if self.can_solve_with_rules(problem):
            return "rules"
        
        if self.can_solve_with_statistics(problem):
            return "statistics"
        
        if self.can_solve_with_classical_ml(problem):
            return "classical_ml"
        
        if self.need_deep_learning(problem):
            return "deep_learning"
        
        return "foundation_models"
    
    def can_solve_with_rules(self, problem: Problem) -> bool:
        """¿4-5 reglas resuelven > 80% del problema?"""
        # Test: implement simple rules
        # If accuracy > 0.80, use rules
        # Only escalate if truly necessary
        pass

Error 3: No Medir el Impacto de ML en User Outcomes

El problema: El modelo tiene great accuracy en offline evaluation pero no move the needle en user metrics. Esto pasa porque:

  • Accuracy no es lo mismo que utility
  • El modelo está optimizing for wrong metric
  • No se mide el impacto en el funnel completo del usuario

La solución: Define tu **North Star Metric** y mide todo contra ella:

# North Star Metric para ML features
class NorthStarMetricTracker:
    """
    Cada producto tiene una North Star Metric.
    Para features ML, mide cómo contribuyen a ella.
    """
    
    def __init__(self, north_star: str):
        self.north_star = north_star
        self.ml_contribution = {}
    
    def track_ml_contribution(
        self,
        ml_feature: str,
        user_segment: str
    ) -> Dict:
        """
        Tracking attribution de ML a North Star.
        
        Usa incrementality testing:
        1. Treatment group: con ML feature
        2. Control group: sin ML feature
        3. Difference = ML contribution
        """
        treatment = self.get_metric(
            segment=user_segment,
            with_feature=ml_feature
        )
        
        control = self.get_metric(
            segment=user_segment,
            without_feature=ml_feature
        )
        
        lift = (treatment - control) / control
        
        return {
            "feature": ml_feature,
            "segment": user_segment,
            "treatment_value": treatment,
            "control_value": control,
            "lift": lift,
            "statistical_significance": self.check_significance(
                treatment, control
            ),
            "contribution_to_north_star": self.calculate_contribution(
                lift, user_segment
            )
        }
    
    def calculate_contribution(
        self, 
        lift: float, 
        segment_size: int
    ) -> float:
        """
        ¿Cuánto contribuye esta feature a la North Star?
        
        Contribution = Lift × Segment Size × Base Metric Value
        """
        segment_share = segment_size / self.total_users
        base_value = self.get_north_star_baseline()
        
        return lift * segment_share * base_value

📊 Resumen y Cierre Colombiano

Y ahí lo tienen, parcero. AI Product Development no es sobre quién tiene el modelo más grande o la arquitectura más fancy. Es sobre entender qué problema tiene el usuario, medir si tu ML lo resuelve, y iterate hasta que sí lo resuelva.

Lo fundamental:

  • Las métricas de modelo importan menos que las métricas de usuario
  • Usa ICE o RICE para priorizar qué construir primero
  • Escribe ML product specs que definan success, tradeoffs y edge cases
  • Antes de ML, pregúntate: ¿Rules o heurística no resuelven esto más rápido?
  • Mide el impacto en user outcomes, no solo en accuracy
  • Tu North Star Metric es lo que importa — haz todo para moverla

Tengan presente: en este mundo de ML, el mejor modelo es el que resuelve el problema del usuario de forma que él quiera pagar por ello o seguir usándolo. Eso es product-ML fit.
