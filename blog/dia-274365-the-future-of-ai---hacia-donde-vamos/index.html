🎯 Intro: El 90% No Conoce Esta Historia

Hagale pues, parcero. Día 274 de #365DaysOfAI y hoy vamos a hacer algo diferente: en lugar de profundizar en una técnica específica, vamos a subirnos al DeLorean y recorrer la evolución de los LLMs desde GPT-1 hasta hoy. ¿Por qué? Porque el 90% de las personas que usan LLMs no conocen la historia, y eso los hace repetir errores del pasado y no entender cómo llegamos aquí. Y eso, mijo, es fundamental para predecir qué viene después. Café listo, entremos en materia.

Un dato que me pareció insane: cuando OpenAI lanzó GPT-1 en 2018, la mayoría de la comunidad de ML lo menospreció. "Eso no va a funcionar a escala", decían. 7 años después, estamos teniendo conversaciones con modelos que parecen conscientes. La historia nos enseña que subestimar la escala es el error más común en ML.

📜 La Cronología Completa: De GPT a GPT-4

2018: GPT-1 — El Primer Paso

OpenAI lanza GPT-1 (Generative Pre-trained Transformer) con 117 millones de parámetros. La innovación crucial: pre-training + fine-tuning. Primero pre-entrenas en texto general, luego haces fine-tuning en tareas específicas.

# La scaling law original
def chinchilla_scaling_law():
    """
    2022: DeepMind publicó que GPT-3 estaba OVER-sized.
    Por cada 10x más compute, debería haber:
    - 1.5x más parameters
    - 1.5x más training tokens
    
    GPT-3 tenía 175B params pero solo 300B tokens.
    Optimal sería ~70B params con 1.5T tokens.
    
    Esto llevó a entrenamiento de Chinchilla (70B) y después LLaMA.
    """
    
    compute = 1e23  # FLOPs
    optimal_params = compute ** 0.46  # Ley empírica
    optimal_tokens = compute ** 0.54
    
    return {
        "optimal_params": optimal_params,
        "optimal_tokens": optimal_tokens,
        "gpt3_was_overallocated": "175B params, 300B tokens → ineficiente"
    }

2022: InstructGPT y la Alineación

Antes de GPT-4, OpenAI lanzó InstructGPT: el primer modelo alineado con RLHF (Reinforcement Learning from Human Feedback). Esto fue crucial porque GPT-3 era powerful pero no seguía instrucciones bien.

instructgpt_method = """
3 pasos para InstructGPT:

1. SFT - Supervised Fine-Tuning
   - Contratar humanos para escribir respuestas ideales
   - Fine-tune GPT-3 en этих respuestas
   - Resultado: un modelo que sigue instrucciones básicas

2. RM - Reward Model
   - Human evaluators rank multiple responses por calidad
   - Entrenar un reward model que prediga cuál respuesta es mejor
   - Esto captura preferencias humanas de manera scalabale

3. RLHF - Reinforcement Learning from Human Feedback
   - Usar el reward model como signal para PPO (Proximal Policy Optimization)
   - El modelo aprende a maximizar reward sin labels explícitos
   - Resultado: respuestas más útiles, menos harmful

Por qué esto importa:
- GPT-3 era powerful pero caprichoso
- InstructGPT seguía instrucciones 10x mejor
- GPT-4 heredó y mejoró este enfoque
"""

def rlhf_vs_sft():
    """
    SFT: Supervised - le dices al modelo "la respuesta correcta es X"
    RLHF: Refuerzo - le dices al modelo "X es mejor que Y"
    
    RLHF captura matices que SFT no puede:
    - Subjetividad (¿cuál respuesta es más útil?)
    - Safety (¿cuál拒绝 es más apropiada?)
    - Stil (¿cuál tono es más adecuado?)
    """
    return {
        "sft_limitations": "Necesita labels explícitos para todo",
        "rlhf_advantage": "Aprende preferencias sin ejemplos específicos"
    }

Antes de los transformers que dominan hoy, hubo otras arquitecturas que sentaron las bases. Conocer esta historia te ayuda a entender por qué llegamos aquí.

def word2vec_problem():

# BERT vs GPT (decoder-only)
def bert_vs_gpt():
    """
    BERT (Encoder): Bidirectional - ve todo el contexto simultáneamente
    - Mejor para: clasificación, NER, question answering, sentiment
    - No puede: generar texto coherente (no tiene causal masking)
    
    GPT (Decoder): Unidirectional (izq→der) - solo ve contexto previo
    - Mejor para: text generation, summarization, translation
    - No puede: ver future tokens (intencional - causal)
    """
    
    return {
        "bert_best_for": ["classification", "NER", "QA", "sentiment analysis"],
        "gpt_best_for": ["text generation", "translation", "summarization"],
        "t5_best_for": ["seq2seq tasks - translation, summarization, QA"],
        "modern_llms": "Mostly decoder-based with modifications (ALiBi, RoPE, etc.)"
    }

def bert_training():
    """
    BERT se entrena con 2 objetivos:
    
    1. MLM (Masked Language Modeling):
       Input: "El gato [MASK] en la [MASK]"
       Output: "corrió", "sombra"
       Se oculta ~15% de tokens y se predicen.
    
    2. NSP (Next Sentence Prediction):
       Input: "El gato [SEP] Dormía todo el día"
       Output: IsNext (sí, el segundo sigue al primero)
       
    Esto permite que BERT entienda relaciones entre sentences.
    """
    
    return {
        "mlm": "Predice tokens ocultados en medio del texto",
        "nsp": "Determina si un sentence sigue a otro",
        "combined": "BERT aprende both word-level AND sentence-level semantics"
    }

2. Mixture of Experts (MoE) — Efficiency a Escala

moe_explained = """
Mixture of Experts es la arquitectura que permite models aún más grandes
sin proportionally más compute:

Arquitectura:
- Top-K experts (ej: 8 experts)
- Solo 2 experts se activan por token (sparse activation)
- Router decide cuál expert procesar cada token

Ventajas:
- 100B params pero solo 12B active por token
- Cost de inference = como modelo de 12B
- Capacidad = como modelo de 100B

Ejemplos:
- GPT-4: rumored MoE with 8 experts

    - 8 experts, 2 activos por token
    - 46.7B params total, pero solo ~13B FLOPs por token
    - Same inference cost as 13B model but much more capacity
    """
    
    return {
        "dense_gpt3": "175B params, 175B FLOPs/token",

⚠️ Los 3 Errores Más Comunes (y Sus Arreglos)

Error 1: No Entender la Evolución Histórica y Repetir Errores del Pasado

El problema: El 70% de los practitioners no conoce la historia de los LLMs. Esto lleva a repetir errores que otros ya cometieron. Por ejemplo: seguir entrenando modelos enorme cuando la evidencia de Chinchilla ya demostró que más datos es más eficiente. O usar arquitecturas obsoletas porque "siempre lo hemos hecho así".

La solución: Antes de proponer un approach nuevo, lee al menos 10 papers clásicos de la era 2017-2022. Específicamente:

def history_lessons():
    """

    1. GPT-1 (2018): No масштабировали suficiente

    2. BERT (2018): Solo encoder, no generation

Error 3: No Apreciar el Impacto de Scale en Emergent Capabilities

El problema: La mayoría subestima betapa importante es scale. No es linear: pequeños cambios en parámetros pueden resultar en saltos cualitativos inesperados. Ejemplo: GPT-2 no podía hacer arithmetic de 3 dígitos decentemente. GPT-3 con 100x más params sí podía. No había forma de predecir eso a priori.

La solución: Entiende las scaling laws y testa en diferentes scales antes de concluir qué es possible.

def scale_emergent_prediction():
    """
    Framework para pensar sobre emergent capabilities:
    
    1. Identify current threshold
       - ¿Qué capability tiene tu modelo actual?
       - ¿A qué scale emerged previously?
    
    2. Extrapola usando scaling laws
       - Si capability X emerge cerca de 100B con dataset Y
       - ¿Emergerá a 50B con 2x datos?
    
    3. Test empirically antes de assume
       - No puedes predecir emergent capabilities - necesitas testar
       - Example: "Chain-of-thought reasoning" was unexpected
         Nadie predijo que would emerge with scale
    """
    
    return {
        "principle": "Capability ≠ linear function of scale",
        "implication": "Necesitas testar empiricalmente",
        "example_unexpected": "Chain-of-thought: Not predicted, emerged at ~100B",
        "how_to_handle": "Budget para experiments en diferentes scales"
    }

def scaling_laws_practical():
    """
    Las 3 scaling laws fundamentales (Henighan et al., 2020):
    
    1. Power law para performance vs compute
       L(N) ≈ (N/N₀)^{-α}
       donde N = número de parameters
    
    2. Performance mejora smooth con scale
       - No hay "miracle threshold"
       - Cada 10x compute = mejora predictable (si todo lo demás constante)
    
    3. Data size importa tanto como params
       - Más params sin más datos = diminishing returns
       - Chinchilla optimal: ~20 tokens por parameter
    
    Implications:
    - Si tienes compute budget fijo: оптимизируй params Y datos
    - Si scales down: mantén proporción data/params
    - Mas tokens de training = mejor modelo
    """
    
    return {
        "compute_frontier": "Para máxima performance, balance params + data",
        "data_frontier": "Data quality > data quantity",
        "practical": "No construyas modelo enorme con datos chimbas"
    }
