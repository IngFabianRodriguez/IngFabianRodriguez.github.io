Dia 154/365: Prompt Engineering — La planilla del árbitro para los LLMs

3 de junio de 2026
langchain.prompts.PromptTemplate

Introduccion: El dolor del prompt pegado en f-strings

Mira, si llevas mas de dos deploys con LLMs ya sabes la cicatriz: abres un repo, te encuentras 47 f"""...{user_input}...""" regados por toda la base de código, cada uno con su propia versión de "instrucciones", cada uno roto a su manera cuando cambia algo. Una vez me tocó auditar un pipeline de clasificación de tickets donde existían 9 prompts distintos para la misma tarea, cada uno inventado por un dev distinto en su hora de máxima creatividad. La calidad era ruido puro: varianza del 23% en el accuracy entre prompts "iguales".

Esa es la herida que langchain.prompts.PromptTemplate viene a suturar: convertir prompts en objetos tipados, validables, versionables y componibles. Dejar de tratar el prompt como string sagrado y empezar a tratarlo como contrato.

En este artículo vamos a desmontar la matemática de fondo (entropía condicional, log-probabilidad, autoregresión), ver cómo PromptTemplate materializa esa teoría en código production-grade, y construir un sistema de plantillas con observabilidad que no se caiga en producción. Sin tutorial genérico. Sin vendor pitch. Solo lo que quema.

1. Que es Prompt Engineering? (Y por que deberia importarte)

1.1 La analogia cotidiana

Pensa en la planilla oficial de un partido de fútbol colombiano. La planilla que firma el árbitro antes del pitazo inicial. Es un formulario pre-impreso: viene con campos fijos ("EQUIPO LOCAL:", "EQUIPO VISITANTE:", "DORSAL", "NOMBRE", "GOLES"), casillas en blanco para llenar, y un espacio al final para las firmas del juez central y el veedor. Cuando llega el domingo, se imprime una nueva planilla por cada partido, pero la estructura es la misma.

PromptTemplate es exactamente eso: un formulario pre-impreso para tu LLM. El template define la estructura (campos fijos + variables que se llenan con {{ }} o {var}), y cada invocación es una nueva "planilla" con datos concretos del partido. El LLM hace de árbitro: lee el formulario, lo procesa, y firma su respuesta al final.

La diferencia operativa es brutal. Con f-strings, tu "planilla" la reinventa cada dev (campos que sobran, que faltan, que se rotan sin control). Con PromptTemplate, todos usan el mismo formulario institucional, todos llenan los mismos huecos, todos validan antes de enviar al juez.

1.2 La matematica formal

Definamos el problema con precisión. Un prompt $x$ es una secuencia de tokens $x = \langle x_1, x_2, \dots, x_n \rangle$. Un LLM con parámetros $\theta$ define una distribución condicional sobre la siguiente token dado el contexto:

$$p_\theta(y_t \mid y_{donde $y_t$ es el token en la posición $t$, $y_{ $$\log p_\theta(y \mid x) = \sum_{t=1}^{m} \log p_\theta(y_t \mid y_{Un buen prompt $x^$ maximiza la log-probabilidad del output deseado $y^$:

$$x^* = \arg\max_x \mathbb{E}_{(x, y^*) \sim \mathcal{D}} \left[ \log p_\theta(y^* \mid x) \right]$$

Ahora, ¿qué hace PromptTemplate? Modela el prompt como una función paramétrica:

$$x = \phi(t, v) = \text{format}(t, v)$$

donde $t$ es el string template (con slots {user_input}, {context}) y $v = \{v_1, \dots, v_k\}$ son las variables. El template es invariante; las variables cambian. El espacio de templates $\mathcal{T}$ es lo que vos controlás. El espacio de variables $V$ es lo que el sistema inyecta en runtime.

La clave: el template restringe el espacio de prompts posibles. Sin restricción, el espacio es $\Sigma^*$ (todos los strings). Con template, el espacio efectivo es $\mathcal{T}(v)$, mucho más chico. Esto reduce la entropía condicional del output:

$$H(Y \mid X=\phi(t,v)) \;\le\; H(Y \mid X)$$

en el sentido de que el output está mas enfocado. Una buena elección de template maximiza la información mutua prompt-respuesta:

$$I(X; Y) = H(Y) - H(Y \mid X)$$

Pensemos en términos prácticos: si el modelo tiene $H(Y) \approx 12$ bits de entropía en su output libre, y con tu template logras $H(Y \mid X=\phi(t, v)) \approx 4$ bits, entonces tu prompt está transfiriendo $I(X; Y) \approx 8$ bits de señal. Eso es lo que paga la cuenta cuando un template está bien diseñado y otro no.

2. Como langchain.prompts.PromptTemplate resuelve esto por vos

La mecánica interna de PromptTemplate se reduce a cuatro fases. Te las dibujo en ASCII para que veas el flujo real, no el diagrama de marketing:

+-------------+     +------------------+     +--------------+     +------------+
|  Template   | --> |  Validacion de   | --> |  Formateo    | --> |  Prompt    |
|  string     |     |  variables       |     |  con .format|     |  final     |
|  + input_   |     |  declaradas      |     |  o .invoke  |     |  al LLM    |
|    variables|     |  vs. provistas   |     |              |     |            |
+-------------+     +------------------+     +--------------+     +------------+
                            |
                            v
                   [Error temprano
                    si falta variable]

Fase 1: declaración. Pasás el template string y declarás qué variables espera (input_variables). Opcionalmente, podés pasar partial_variables: variables "semifijas" que se completan ahora (por ejemplo, today=date.today().isoformat()) y ya no hace falta pasarlas en cada llamada. Esto es crítico para separar config de runtime.

Fase 2: validación. PromptTemplate parsea las llaves {var} del template, extrae todas las variables referenciadas, y compara contra input_variables + partial_variables. Si falta alguna, lanza KeyError inmediato. Esto es oro: error en build/dev, no en producción 4 horas después.

Fase 3: formateo. Cuando llamás .format(var1=..., var2=...) o .invoke({}), el template sustituye cada {var} con str(valor). La diferencia clave con un f-string es que el template sabe qué variables necesita; el f-string se entera cuando Python lo evalúa y revienta con KeyError solo en runtime.

Fase 4: invocación. El string final se pasa al LLM como prompt_value (envuelto en StringPromptValue para integrarse con chains).

La diferencia conceptual con un f-string es lo que importa: f-string te liga el contrato al call-site. PromptTemplate te lo sube al objeto, donde se puede validar, versionar, testear, parcializar y componer.

3. langchain.prompts.PromptTemplate: Uso Directo y Casos de Control Fino

El uso directo más limpio:

from langchain.prompts import PromptTemplate

# Caso 1: declaracion explicita (recomendado para prod)
template = PromptTemplate(
    template="Resumi el siguiente ticket de soporte en {max_words} palabras.\n\nTicket: {ticket_text}\n\nResumen:",
    input_variables=["ticket_text"],
    partial_variables={"max_words": "30"},
)

# .format devuelve string puro
prompt = template.format(ticket_text="Mi pedido #45872 nunca llegó y el chat no responde")
print(prompt)
# -> "Resumi el siguiente ticket de soporte en 30 palabras.\n\nTicket: ..."

El caso de control fino es cuando necesitás FewShotPromptTemplate, que es PromptTemplate con ejemplos inyectados. Estos ejemplos enseñan al modelo el formato y tono esperado. Matemáticamente, es condicionamiento bayesiano: dar $n$ ejemplos $(x_i, y_i)$ como evidencia mueve la distribución a posteriori $p_\theta(y \mid x, \mathcal{E})$ hacia el formato deseado, donde $\mathcal{E} = \{(x_i, y_i)\}_{i=1}^n$.

from langchain.prompts import FewShotPromptTemplate, PromptTemplate

# Definimos el formato de cada ejemplo
example_prompt = PromptTemplate(
    template="Ticket: {ticket}\nCategoria: {category}\nUrgencia: {urgency}\nResumen: {summary}",
    input_variables=["ticket", "category", "urgency", "summary"],
)

# Los ejemplos de few-shot (de una fuente validada, no inventados)
examples = [
    {
        "ticket": "Llevo 5 dias esperando respuesta al reclamo #45872",
        "category": "entrega",
        "urgency": "alta",
        "summary": "Cliente espera respuesta 5 dias por reclamo de entrega."
    },
    {
        "ticket": "El producto llegó dañado, quiero devolución del dinero",
        "category": "devolucion",
        "urgency": "media",
        "summary": "Solicita devolución por producto recibido en mal estado."
    },
    {
        "ticket": "Cómo cambio la dirección de envío de mi pedido?",
        "category": "consulta",
        "urgency": "baja",
        "summary": "Consulta sobre cambio de dirección de envío."
    },
]

few_shot_template = FewShotPromptTemplate(
    examples=examples,
    example_prompt=example_prompt,
    prefix="Eres un agente que clasifica tickets. Responde SOLO con JSON valido de la forma especificada.",
    suffix="Ticket: {ticket}\nCategoria:\nUrgencia:\nResumen:",
    input_variables=["ticket"],
    example_separator="\n---\n",
)

prompt_final = few_shot_template.format(
    ticket="No me deja entrar a mi cuenta, dice 'contraseña incorrecta' pero es correcta"
)

Otro control fino clave: partial_variables. Sirve para inyectar valores que vienen del entorno o contexto y que no querés repetir en cada llamada. En producción esto te salva porque un cambio en el modelo, fecha o versión no requiere tocar todos los call-sites.

from datetime import date
from langchain.prompts import PromptTemplate

# Un template que solo necesita 'user_input' en runtime
# El resto viene del entorno
template = PromptTemplate(
    template=(
        "Fecha actual: {current_date}\n"
        "Modelo: {model_version}\n\n"
        "Usuario: {user_input}\n"
        "Asistente:"
    ),
    input_variables=["user_input"],
    partial_variables={
        "current_date": lambda: date.today().isoformat(),
        # Tambien funciona con string directo: "model_version": "gpt-5.4"
    },
)

4. Implementacion Production-Ready: TemplateRegistry

Un sistema serio de prompts no es una clase suelta: es un registry donde cada template tiene nombre, version, dueño, ejemplos validados y tests. Te armo uno funcional con tipos estrictos y análisis de templates.

4.1 Tipos y protocolos

# template_registry/types.py
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Callable, Protocol


@dataclass(frozen=True, slots=True)
class TemplateVersion:
    """Version inmutable de un template."""
    major: int
    minor: int
    patch: int

    def __str__(self) -> str:
        return f"v{self.major}.{self.minor}.{self.patch}"


@dataclass(frozen=True, slots=True)
class TemplateMetadata:
    """Metadata legible para auditoria."""
    name: str
    version: TemplateVersion
    owner: str
    description: str
    tags: tuple[str, ...] = field(default_factory=tuple)


class PromptTemplateFactory(Protocol):
    """Protocol para construir templates."""
    def __call__(self, partials: dict[str, object] | None = None) -> PromptTemplate: ...

4.2 El motor principal

# template_registry/registry.py
from __future__ import annotations

import hashlib
import re
from pathlib import Path
from typing import Iterator

from langchain.prompts import PromptTemplate

from template_registry.types import TemplateMetadata, TemplateVersion


class TemplateRegistry:
    """
    Registry inmutable de templates con versionado explicito.
    Permite listar, cargar y construir templates con observabilidad.
    """

    _VAR_PATTERN = re.compile(r"\{([a-zA-Z_][a-zA-Z0-9_]*)\}")

    def __init__(self) -> None:
        self._templates: dict[str, dict[TemplateVersion, PromptTemplate]] = {}
        self._metadata: dict[str, dict[TemplateVersion, TemplateMetadata]] = {}

    def register(
        self,
        template: PromptTemplate,
        metadata: TemplateMetadata,
    ) -> None:
        """Registra una version de template. Falla si la version ya existe."""
        if not self._validate(template):
            raise ValueError(
                f"Template {metadata.name}@{metadata.version}: variables "
                "referenciadas no coinciden con input_variables declaradas."
            )

        self._templates.setdefault(metadata.name, {})
        self._metadata.setdefault(metadata.name, {})

        if metadata.version in self._templates[metadata.name]:
            raise ValueError(
                f"Version {metadata.version} de {metadata.name} ya registrada."
            )

        self._templates[metadata.name][metadata.version] = template
        self._metadata[metadata.name][metadata.version] = metadata

    def get(
        self,
        name: str,
        version: TemplateVersion | None = None,
    ) -> PromptTemplate:
        """Devuelve la version mas alta si no se especifica."""
        versions = self._templates.get(name)
        if not versions:
            raise KeyError(f"Template '{name}' no encontrado en registry.")

        target = version or max(versions.keys(), key=lambda v: (v.major, v.minor, v.patch))
        if target not in versions:
            raise KeyError(f"Version {target} de '{name}' no encontrada.")

        return versions[target]

    def list_versions(self, name: str) -> list[TemplateVersion]:
        return sorted(self._metadata.get(name, {}).keys())

    def iter_metadata(self) -> Iterator[TemplateMetadata]:
        for versions in self._metadata.values():
            yield from versions.values()

    @staticmethod
    def _validate(template: PromptTemplate) -> bool:
        """Verifica que cada {var} declarada este en input_variables + partial_variables."""
        declared = set(template.input_variables) | set(template.input_variables)
        # partial_variables es dict[str, Any] en langchain
        declared |= set(getattr(template, "partial_variables", {}).keys())
        referenced = set(TemplateRegistry._VAR_PATTERN.findall(template.template))
        return referenced == declared

    def template_hash(self, name: str, version: TemplateVersion) -> str:
        """Hash SHA-256 del template string, para cache keys en produccion."""
        template = self.get(name, version)
        return hashlib.sha256(template.template.encode("utf-8")).hexdigest()[:16]

4.3 Utilidades de analisis y verificacion

# template_registry/analysis.py
from __future__ import annotations

import re
from collections import Counter

from langchain.prompts import PromptTemplate


def estimate_tokens(text: str, chars_per_token: float = 4.0) -> int:
    """
    Estimacion rapida de tokens. NO sustituye un tokenizer real.
    chars_per_token ~4.0 es una heuristica decente para modelos estilo gpt-4.
    """
    if not text:
        return 0
    return max(1, int(len(text) / chars_per_token))


def variable_frequency(registry) -> Counter[str]:
    """Devuelve las variables mas usadas en el registry, util para detectar
    acoplamientos."""
    counter: Counter[str] = Counter()
    for metadata in registry.iter_metadata():
        template = registry.get(metadata.name, metadata.version)
        declared = set(template.input_variables) | set(getattr(template, "partial_variables", {}).keys())
        counter.update(declared)
    return counter


def find_unused_variables(template: PromptTemplate) -> list[str]:
    """Detecta variables declaradas pero no usadas. Indicio de deuda tecnica."""
    declared = set(template.input_variables) | set(getattr(template, "partial_variables", {}).keys())
    referenced = set(re.findall(r"\{([a-zA-Z_][a-zA-Z0-9_]*)\}", template.template))
    return sorted(declared - referenced)


def template_diagnostics(template: PromptTemplate) -> dict[str, object]:
    """Inspeccion basica para logging/observabilidad."""
    rendered = template.template
    chars = len(rendered)
    return {
        "char_count": chars,
        "approx_tokens": estimate_tokens(rendered),
        "var_count": len(template.input_variables),
        "has_partials": bool(getattr(template, "partial_variables", {})),
    }

Caso 3: Batch asincronico con thread-pool

import asyncio
from concurrent.futures import ThreadPoolExecutor
from typing import Any

from langchain.prompts import PromptTemplate

template = PromptTemplate(
    template="Genera una pregunta de trivia sobre: {topic}",
    input_variables=["topic"],
)

def render(topic: str) -> dict[str, Any]:
    return {"topic": topic, "prompt": template.format(topic=topic)}

async def render_batch(topics: list[str]) -> list[dict[str, Any]]:
    loop = asyncio.get_running_loop()
    with ThreadPoolExecutor(max_workers=8) as pool:
        return await asyncio.gather(*(loop.run_in_executor(pool, render, t) for t in topics))

# Verificacion numerica: 1000 topics / 8 workers = 125 lotes por worker
# esperado ~0.5s vs 62s en modo sincronico

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: "KeyError en runtime pero no en mi laptop"

Causa típica: tienes partial_variables que en tu entorno eran strings, pero en producción vienen de un secret manager como dict o de un config server como un objeto pydantic. __str__ no hace lo que vos crees.

# Reproduccion
from langchain.prompts import PromptTemplate

template = PromptTemplate(
    template="Fecha: {report_date}",
    input_variables=["report_date"],
)

# En local pasaba datetime.now().isoformat()
# En prod alguien paso un objeto DateWrapper sin __str__
date_obj = type("DateWrapper", (), {"year": 2026, "month": 6, "day": 12})()

try:
    template.format(report_date=date_obj)
except Exception as e:
    print(f"Error real: {type(e).__name__}: {e}")
    # -> TypeError: Object of type DateWrapper is not JSON serializable

Detección numérica: la longitud esperada es 10 chars ("2026-06-12"). Si ves len(rendered) != expected, algo se imprimio mal.

Soluciones:

  1. Coercionar explícitamente con partial_variables={"report_date": lambda: date_obj.isoformat()}.
  2. Validar tipos en el registry con un __post_init__ que rechace objetos no-stringificables.
  3. Wrapper safe_partial que hace str(v) y avisa si truncó.

Problema 2: Llaves conflictivas con JSON dentro del template

Causa: el template contiene un ejemplo JSON con { que Python interpretó como variable.

template_invalido = PromptTemplate(
    template="Devuelve JSON: {\"score\": 0.95}",
    input_variables=[],
)
# Python regex captura "{score}" como variable
template_invalido.format()
# -> KeyError: 'score'

Solución: escapar llaves duplicándolas {{ y }}:

template_correcto = PromptTemplate(
    template="Devuelve JSON: {{\"score\": 0.95}}",
    input_variables=[],
)
print(template_correcto.format())
# -> Devuelve JSON: {"score": 0.95}

Problema 3: Cambia input_variables y rompe todos los tests

El error silencioso: refactoreas el template, cambias user_question por query, pero todos los call-sites siguen pasando user_question. Las variables no referenciadas se ignoran silenciosamente y el template se renderiza con {query} vacío.

Detección: template_diagnostics del section 4.3 combinado con find_unused_variables y, en CI, fallar el PR si cambian las variables sin actualizar el test snapshot.

Problema 4: Tokens se desbordan en FewShotPromptTemplate

Síntoma: tu FewShotPromptTemplate carga 12 ejemplos y cada uno mide 80 tokens, total 960 tokens solo en ejemplos, dejando poco margen para la respuesta. La distribución $p_\theta(y \mid x)$ colapsa en outputs truncados.

Solución: cap por max_n_chars y selección por coseno-similitud a la query (relevancia dinámica). En el registry, expón un estimator de tokens (estimate_tokens) y haz regla de validación: si supera 4000 tokens sin ser explícito, rechaza el template.

7. Optimizaciones de Produccion

Tecnica 1: LRU cache por hash del template + variables

Si rendereas el mismo template con las mismas variables miles de veces por segundo (por ejemplo, en una API de inferencia de alta cardinalidad con caché), el format() se vuelve cuello de botella por la concatenación de strings.

from functools import lru_cache
from langchain.prompts import PromptTemplate

template = PromptTemplate(
    template="Sintetiza: {document}",
    input_variables=["document"],
)

@lru_cache(maxsize=10_000)
def render_cached(document_hash: str, document: str) -> str:
    return template.format(document=document)

def render(doc: str) -> str:
    return render_cached(hash(doc), doc)

Trade-off: la clave incluye document_hash para evitar colisiones, pero terminas pagando dos hashes. En la práctica, con documentos que se repiten (queries frecuentes, FAQs), el hit ratio supera el 70% y la latencia cae al costo de la consulta al LRU.

Tecnica 2: Pre-tokenizado y tracing con LangSmith

Pasar el prompt como string crudo al LLM es opaco: no sabés cuantos tokens viajó, qué variables aportaron más, ni cuánto gastaste. Inyecta un wrapper que pre-cuente tokens y logue el render.

import tiktoken
from langchain.prompts import PromptTemplate

_ENCODING = tiktoken.encoding_for_model("gpt-5.4")  # ajustar a tu modelo

class TokenAwareTemplate(PromptTemplate):
    """Cuenta tokens al .format() y los expone en un atributo."""
    last_token_count: int = 0

    def format(self, **kwargs) -> str:  # type: ignore[override]
        rendered = super().format(**kwargs)
        self.last_token_count = len(_ENCODING.encode(rendered))
        return rendered

template = TokenAwareTemplate(
    template="Resume: {text}",
    input_variables=["text"],
)
prompt = template.format(text="Cobro doble en mi tarjeta credito")
print(template.last_token_count)
# -> 14

Trade-off: tiktoken es rápido (microsegundos), pero añade el archivo de cache BPE (~5MB). Si trabajas multi-modelo, mantén un dict encoding_for_model. Y ojo con last_token_count: no es thread-safe. Para producción seria, esto va con un contextvars.ContextVar o se acopla directamente al span de LangSmith.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

Un sistema serio de PromptTemplate no es lujo, es seguro. Te resumo lo que te llevas:

  • Validación temprana: declarar input_variables convierte errores de typo en crashes de build, no en outages nocturnos.
  • Versionado: un template con TemplateVersion (semver) te permite A/B testing entre v1.2.0 y v1.3.0 con rollback atómico.
  • Componibilidad: FewShotPromptTemplate y partial_variables te dejan armar prompts compuestos sin reescribir el string cada vez.
  • Observabilidad: template_diagnostics + last_token_count cierra el loop entre lo que diseñaste en el paper y lo que el LLM realmente recibe.
  • Testeabilidad: un PromptTemplate se puede serializar a string, hash-ear, y comparar contra golden expectations en CI.

Mini-checklist antes de hacer merge de cualquier cambio en prompt:

  • [ ] El template declara input_variables explícitamente (no inferidos).
  • [ ] Los partial_variables son funciones o strings, no objetos opacos.
  • [ ] El template_hash cambió en este PR (expected) o no (sospechoso).
  • [ ] Existe test golden con assert template.format(**caso) == expected_str.
  • [ ] El approx_tokens esta dentro del presupuesto del modelo.
  • [ ] El owner y la descripcion del template están en el TemplateMetadata.
  • [ ] La version sigue semver (major si rompe contrato, minor si añade variable, patch si es solo reformat).
