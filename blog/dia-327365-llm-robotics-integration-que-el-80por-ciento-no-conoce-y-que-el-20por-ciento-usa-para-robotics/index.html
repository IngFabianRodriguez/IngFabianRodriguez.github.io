LLM Robotics Integration

Pues resulta que en Colombia, cuando uno dice "robotics", la gente piensa en brazos industriales o en robots de factory. Pero el verdadero juego cambia cuando le metes LLMs al asunto. Hoy día 327 vamos a hablar de cómo integrar LLMs con robots de verdad — no de橱窗户, sino de aplicación real en tareas de manipulación, navegación y planificación.

El problema fundamental es que los robots operan en el mundo físico mediante controles de baja latencia (típicamente loops de control a 100-1000 Hz), mientras que los LLMs son sistemas de inference que trabajan en timescales de cientos de milisegundos. Cómo combine estos dos mundos es el truco.

La Arquitectura Básica

Un sistema de LLM Robotics Integration típico tiene tres capas:

  • Perception Layer: Sensores (cámaras, LIDAR, IMU) que alimentan el sistema de percepción
  • Cognitive Layer: El LLM que hace task planning, instruction following, y high-level reasoning
  • Control Layer: Los controllers de baja latencia que ejecutan las acciones físicas

La clave está en cómo fluye la información entre capas. El LLM no controla el robot directamente — eso sería un desastre. En cambio, el LLM genera plans o instructions que los controllers de más baja capa traducen a acciones motoras.

La Formula del Task Planning

El problema de task planning con LLMs se puede formular como:

# Pseudocode para task planning con LLM
def plan_task(llm, task_description, world_state):
    """
    El LLM recibe:
    - Descripción de la tarea
    - Estado actual del mundo (en formato estructurado)
    
    El LLM devuelve:
    - Secuencia de acciones concretas
    """
    prompt = f"""
    Task: {task_description}
    World State: {world_state}
    
    Generate a sequence of concrete actions to accomplish the task.
    Each action must be executable by a robot controller.
    """
    
    response = llm.generate(prompt)
    plan = parse_plan(response)
    return plan

Pero aquí viene lo interesante: el LLM no solo genera la secuencia de acciones — también puede hacer replanning cuando el mundo cambia inesperadamente. Eso es clave para manejar disturbances.

Robotics Framework con LLMs

Vamos a lo mero bueno: cómo se ve un framework real para integrar LLMs con control de robots. Aquí va una implementación educativa:

import time
import torch
from abc import ABC, abstractmethod
from dataclasses import dataclass
from typing import List, Dict, Any, Optional
from enum import Enum

class ActionType(Enum):
    NAVIGATE = "navigate"
    PICK = "pick"
    PLACE = "place"
    GRIP = "grip"
    RELEASE = "release"
    OBSERVE = "observe"

@dataclass
class RobotAction:
    action_type: ActionType
    parameters: Dict[str, Any]
    confidence: float
    reasoning: str

@dataclass
class WorldState:
    robot_position: tuple
    objects: Dict[str, tuple]  # name -> position
    gripper_state: bool
    timestamp: float

class LLMRoboticsController:
    """
    Framework para integrar LLMs con control de robot.
    
    El LLM opera a nivel de task planning (Hz lentos),
    mientras que controllers de bajo nivel handle ejecución rápida.
    """
    
    def __init__(self, llm_model, low_level_controller):
        self.llm = llm_model
        self.controller = low_level_controller
        self.plan_history: List[List[RobotAction]] = []
        self.execution_stats: Dict[str, float] = {}
    
    def perceive_world(self, sensors) -> WorldState:
        """Reconstruct world state from sensor data."""
        return WorldState(
            robot_position=sensors.get("position"),
            objects=sensors.get("objects", {}),
            gripper_state=sensors.get("gripper_closed"),
            timestamp=time.time()
        )
    
    def generate_plan(
        self, 
        task: str, 
        world_state: WorldState
    ) -> List[RobotAction]:
        """
        Usa el LLM para generar un plan de acciones.
        
        El prompt incluye:
        1. La tarea en lenguaje natural
        2. Estado actual del mundo
        3. Constrains físicos del robot
        """
        world_description = self._format_world_state(world_state)
        
        prompt = f"""You are a robot task planner. Given the following task and world state,
generate a sequence of concrete actions.

Task: {task}

Current World State:
{world_description}

Constraints:
- Actions must be one of: {', '.join([a.value for a in ActionType])}
- Each action needs specific parameters (positions, object names)
- Be precise with coordinates (x, y, z in meters)
- Consider the robot's current gripper state

Output format: JSON list of actions with type and parameters.
Only output the JSON, no explanation."""
        
        # Inference del LLM
        start_time = time.time()
        response = self.llm.generate(prompt)
        inference_time = time.time() - start_time
        
        self.execution_stats["llm_inference_time"] = inference_time
        
        # Parsear respuesta
        plan = self._parse_plan_response(response)
        self.plan_history.append(plan)
        
        return plan
    
    def execute_plan(
        self, 
        plan: List[RobotAction],
        world_state: WorldState,
        monitor: bool = True
    ) -> Dict[str, Any]:
        """
        Ejecuta el plan generado por el LLM.
        
        Args:
            plan: Lista de acciones del LLM
            world_state: Estado actual percibido
            monitor: Si True, hace replanning si hay deviations
        
        Returns:
            Dict con execution results y métricas
        """
        execution_log = []
        current_state = world_state
        
        for i, action in enumerate(plan):
            # Verificar que la acción sea válida en el estado actual
            if not self._is_action_valid(action, current_state):
                if monitor:
                    # Replanificar con estado actualizado
                    new_plan = self.generate_plan(
                        f"Continue task: recover from failed action {action.action_type}",
                        current_state
                    )
                    return self.execute_plan(new_plan, current_state, monitor)
                else:
                    execution_log.append({
                        "action": action,
                        "status": "skipped",
                        "reason": "invalid in current state"
                    })
                    continue
            
            # Ejecutar en el controller de baja latencia
            execution_result = self.controller.execute(action)
            
            # Perception post-acción
            new_sensors = self.controller.get_sensors()
            current_state = self.perceive_world(new_sensors)
            
            execution_log.append({
                "action": action,
                "status": "success" if execution_result else "failed",
                "result": execution_result,
                "new_state": current_state
            })
        
        return {
            "execution_log": execution_log,
            "stats": self.execution_stats,
            "final_state": current_state
        }
    
    def _format_world_state(self, state: WorldState) -> str:
        """Convierte world state a string para el prompt del LLM."""
        lines = [
            f"Robot position: x={state.robot_position[0]:.3f}, y={state.robot_position[1]:.3f}, z={state.robot_position[2]:.3f}",
            f"Gripper: {'closed' if state.gripper_state else 'open'}",
            "Objects:"
        ]
        for name, pos in state.objects.items():
            lines.append(f"  - {name} at x={pos[0]:.3f}, y={pos[1]:.3f}, z={pos[2]:.3f}")
        return "\n".join(lines)
    
    def _parse_plan_response(self, response: str) -> List[RobotAction]:
        """Parsea la respuesta del LLM a una lista de RobotActions."""
        import json
        import re
        
        # Extraer JSON de la respuesta
        json_match = re.search(r'\[.*\]', response, re.DOTALL)
        if not json_match:
            return []
        
        try:
            actions_data = json.loads(json_match.group())
        except json.JSONDecodeError:
            return []
        
        plan = []
        for action_data in actions_data:
            try:
                action = RobotAction(
                    action_type=ActionType(action_data["type"]),
                    parameters=action_data.get("parameters", {}),
                    confidence=action_data.get("confidence", 1.0),
                    reasoning=action_data.get("reasoning", "")
                )
                plan.append(action)
            except (KeyError, ValueError):
                continue
        
        return plan
    
    def _is_action_valid(self, action: RobotAction, state: WorldState) -> bool:
        """Verifica si una acción es válida en el estado actual."""
        # Lógica de validación depende del tipo de acción
        if action.action_type == ActionType.GRIP and state.gripper_state:
            return False  # Ya está grippado
        return True

Los 3 Errores Que el 80% Comete

Error 1: No Usar LLMs Para Task Planning

El error más común es tratar el LLM como un "chatbot que genera código" en vez de usarlo como un verdadero task planner. Muchos sistemas robóticos todavía usan planners basados en reglas fijos (PDDL solvers tradicionales) cuando un LLM podría manejar much more complex, natural task descriptions.

Los planners basados en reglas requieren que alguien programe explícitamente cada task como una serie de pasos. Si el robot encuentra algo imprevisto, se congela. Los LLMs pueden hacer zero-shot task planning given a natural language description.

Fix: Integrar el LLM como el planner central, pero mantener los controllers de bajo nivel para ejecución. El LLM genera planes de alto nivel que se traducen a acciones ejecutables.

Error 2: No Manejar el Sim-to-Real Gap

El segundo error crítico es entrenar o planificar en simulación y esperar que funcione igual en el robot físico. El sim-to-real gap es real y causa failures catastróficas.

Las diferencias típicas incluyen:

  • Fricción diferente en articulaciones
  • Latencia de sensores (la simulación es instantánea, la realidad no)
  • Imperfecciones en la calibración de cámaras
  • Deformación de objetos blandos

Por qué falla: Un plan generado en simulación puede ser geométricamente correcto pero físicamente imposible. Por ejemplo, el robot simulado puede aplicar 100N de fuerza, pero el real solo puede aplicar 20N.

Fix: Implementar Domain Randomization agresiva en simulación + online adaptation cuando el robot opera. También usar conservative action parameters cuando hay incertidumbre.

def apply_sim_to_real_adaptation(plan: List[RobotAction], uncertainty: float) -> List[RobotAction]:
    """
    Adapta un plan de simulación para el mundo real.
    
    Aumenta margins de seguridad proporcional a la incertidumbre.
    """
    adapted_plan = []
    
    for action in plan:
        if action.action_type == ActionType.PICK:
            # En simulación el grip es perfecto
            # En real hay incertidumbre en posición del objeto
            # Aumentar el radio de approche
            adapted_params = action.parameters.copy()
            adapted_params["approach_radius"] *= (1 + uncertainty * 2)
            adapted_params["tolerance"] *= (1 + uncertainty)
            
            adapted_action = RobotAction(
                action_type=action.action_type,
                parameters=adapted_params,
                confidence=action.confidence * (1 - uncertainty),
                reasoning=f"Adapted for sim-to-real gap, uncertainty={uncertainty:.2f}"
            )
            adapted_plan.append(adapted_action)
        else:
            adapted_plan.append(action)
    
    return adapted_plan

Error 3: No Considerar Latencia en Control Loops

El tercer error es ignorar que los LLMs tienen latencia de inference significativa (200-500ms típicamente) mientras que los control loops de robots operan a 100-1000 Hz (1-10ms por iteration).

Si intentas hacer el LLM parte del control loop directo, el robot será extremadamente lento o inestable.

Por qué falla: A 2 Hz, un robot manipulador no puede mantener estabilidad durante manipulación fina. Un robot móvil no puede reaccionar a obstacles dinámicos. El sistema es fundamentalmente unusable para aplicaciones real-time.

Fix: Separar estrictamente los timescales. El LLM opera a nivel de task planning (segundos a minutos entre decisiones). Los controllers de bajo nivel (100-1000 Hz) handle stability y reflexes. Solo se consulta al LLM cuando hay una decisión de alto nivel que tomar.

Sim-to-Real Transfer: La Math

Formalmente, el problema de sim-to-real se puede expresar como:

Dado un policy π_sim aprendido en simulación, queremos un policy π_real que funcione en el robot físico. La diferencia entre los dos viene del domain shift:

# La distribución de estados en simulación vs realidad
# p_sim(s) vs p_real(s)

# El domain shift causa que 
# E_{s~p_real}[J(π_real, s)] < E_{s~p_sim}[J(π_sim, s)]

# Solution: DA (Domain Adaptation)
# Usar técnicas como:
# 1. Domain Randomization: p_sim' = Uniform(p_real params)
# 2. system identification: aprender params del real
# 3. meta-learning: aprender policies que generalicen

La técnica más efectiva es Domain Randomization: durante training, randomizar aggressively los parámetros del simulador (fricción, masas, ruidos de sensores) para que el policy aprenda a ser robust a variation. Cuando el robot ve variación en el mundo real, ya está preparado.

Resumen y Cierre Colombiano

Pues ahí lo tienen, parcero. LLM Robotics Integration no es simplemente "ponle un LLM a un robot". Es todo un campo que requiere:

  • Arquitectura de múltiples capas: LLM para planning, controllers para ejecución
  • Manejo de timescales: El LLM no puede estar en el control loop directo
  • Sim-to-real adaptation: No confíes ciegamente en lo que funciona en simulación
  • Task planning con LLMs: Aprovecha la flexibilidad del lenguaje natural

Los tres errores que cubrimos son los que más me duelen ver en la industria:

  1. Seguir usando planners basados en reglas cuando LLMs ofrecen 10x más flexibilidad
  2. Ignorar el sim-to-real gap y sorprenderse cuando el robot no funciona en producción
  3. Poner el LLM en el control loop directo y quejarse de que el robot es lento

El 20% que lo hace bien entiende que los LLMs son un cerebro de alto nivel, no un replacement para los controllers de bajo nivel. El LLM planea, el controller ejecuta. Así de simple.
