Prefix Tuning vs LoRA - Comparando Adaptadores

11 de noviembre de 2026
prefix-tuninglorafine-tuningcomparison

🤔 Qué Son los Adaptadores en Fine-Tuning

Cuando fazemos fine-tuning de un LLM, tenemos dos opciones principales: actualizar todos los parámetros (full fine-tuning) o añadir небольшую cantidad de parámetros nuevos y solo entrenarlos a ellos (adapters). Los adaptadores son el segundo tipo — pequeñas redes que aprendemos y que modifican el comportamiento del modelo sin tocar sus pesos originales.

Esto es crucial porque:

  • Eficiencia de memoria: Un modelo de 7B parámetros en full fine-tuning necesita ~28GB en FP32. Con adaptadores, solo necesitas unos pocos MB.
  • Multitarea: Puedes entrenar adaptadores separados para diferentes tareas y swapearlos según necesites.
  • Preservación de conocimiento: Al no modificar los pesos originales, el modelo no "olvida" lo que ya sabía.

🔧 Prefix Tuning: Prompts Entrenables

Prefix tuning es una técnica donde añadimos un sequence de tokens entrenables al inicio de cada capa de atención. Durante el pre-training, el modelo aprende a generar hidden states, y el prefix tuning inserta un pequeño MLP que genera estos tokens entrenables.

La formula del prefix es:

$$h' = [P_\theta; h]$$

Donde $P_\theta$ son los parámetros del prefix y $h$ son los hidden states originales del modelo.

Ventajas de Prefix Tuning

  • Flexibilidad: Puede capturar información contextual de manera más granular porque se inserta en cada capa.
  • Control fino: Al modificar las representations en capas tempranas, tiene mayor influencia en el comportamiento final.

Desventajas

  • Parámetros adicionales: Necesita guardar el estado del MLP para regenerar los embeddings del prefix.
  • Complejidad: Implementar prefix tuning correctamente requiere más trabajo que LoRA.
class PrefixTuningLayer(nn.Module):
    def __init__(self, prefix_length: int, hidden_size: int, prefix_dim: int = 512):
        super().__init__()
        self.prefix_length = prefix_length
        # MLP para generar los prefix tokens
        self.prefix_mlp = nn.Sequential(
            nn.Linear(hidden_size, prefix_dim),
            nn.Tanh(),
            nn.Linear(prefix_dim, prefix_length * 2 * hidden_size)  # *2 for k and v
        )
    
    def forward(self, batch_size: int):
        # Generar prefix tokens
        prefix_tokens = self.prefix_mlp(
            torch.zeros(batch_size, self.prefix_length, hidden_size, device=device)
        )
        # Split into key and value projections
        k_prefix, v_prefix = prefix_tokens.chunk(2, dim=-1)
        return k_prefix, v_prefix

🎯 LoRA: Adaptadores de Bajo Rango

LoRA (Low-Rank Adaptation) propone una idea diferente: en lugar de añadir tokens nuevos, descomponemos las actualizaciones de los pesos en matrices de bajo rango. Para una capa lineal con pesos $W$, en lugar de actualizar $W$ directamente, aprendemos una descomposición $W + BA$ donde $B \in \mathbb{R}^{d \times r}$ y $A \in \mathbb{R}^{r \times k}$ con $r \ll \min(d, k)$.

La formula核心 es:

$$h = W_0 x + \Delta W x = W_0 x + BAx$$

donde $B$ y $A$ son las matrices entrenables de bajo rango.

Ventajas de LoRA

  • Simplicidad: Solo dos matrices por capa, fácil de implementar y debuggear.
  • Eficiencia: Muy pocos parámetros entrenables comparados con prefix tuning.
  • Swap rápido: Puedes cambiar adaptadores en runtime guardando solo las matrices A y B.

Desventajas

  • Limitación de rango: Si la actualización óptima de los pesos requiere una matriz de rank alto, LoRA puede no ser suficiente.
  • Scope limitado: Solo modifica las capas de atención (q, k, v, o), no afecta representaciones intermedias.
class LoRALinear(nn.Module):
    def __init__(self, in_features: int, out_features: int, rank: int = 4, alpha: float = 1.0):
        super().__init__()
        self.rank = rank
        self.alpha = alpha
        self.scaling = alpha / rank
        
        # Pesos frozen del modelo original
        self.weight = nn.Parameter(torch.zeros(out_features, in_features), requires_grad=False)
        # Adaptadores entrenables
        self.lora_A = nn.Parameter(torch.randn(rank, in_features) * 0.01)
        self.lora_B = nn.Parameter(torch.zeros(out_features, rank))
    
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        # Original forward
        base_output = F.linear(x, self.weight, bias=None)
        # LoRA update
        lora_output = (self.lora_B @ self.lora_A) @ x.T
        return base_output + self.scaling * lora_output.T

📊 Comparación Directa

Vamos a comparar ambas técnicas en múltiples dimensiones:

  • Número de parámetros: LoRA típicamente usa menos parámetros. Para un modelo 7B con rank=4, LoRA ~4M parámetros vs Prefix ~8-20M según la longitud del prefix.
  • Memoria de entrenamiento: Ambos reducen significativamente vs full fine-tuning, pero LoRA suele ser más eficiente.
  • Calidad: En la mayoría de tareas, ambas técnicas logran resultados similares. Prefix tuning puede ser mejor en tareas que requieren cambios estructurales profundos.
  • Latencia de inferencia: LoRA no añade latencia en inference si se mergean los pesos. Prefix siempre añade latencia porque necesita procesar los tokens de prefix.

⚙️ Cuándo Usar Cuál

La elección depende de tu caso de uso específico:

  • Usa LoRA cuando: Quieres eficiencia máxima, necesitas cambiar adaptadores frecuentemente, tu tarea es relativamente simple y localizada.
  • Usa Prefix Tuning cuando: Necesitas control más granular sobre las representaciones, tu tarea requiere cambios en múltiples niveles del modelo, estás dispuesto a sacrificar algo de eficiencia por flexibilidad.

En la práctica, muchas implementaciones modernas usan variantes híbridas o QLoRA (LoRA con cuantización) que combina lo mejor de ambos mundos.

🏁 Cierre

Tanto prefix tuning como LoRA son herramientas poderosas para adaptar LLMs eficientemente. La elección entre ellas depende de tu constraints específicos de memoria, latencia, y la naturaleza de la tarea. LoRA es generalmente el default recomendado por su simplicidad y eficiencia, pero prefix tuning sigue siendo relevante para casos que requieren más control.
