Introducción: El batch que casi llega a producción sin catarlo

El viernes a las 6pm, lo único que revisaba antes de hacer merge era que el script corriera sin excepciones y que el AUC se viera "razonable" en el notebook. El lunes a las 8am, el sistema de recomendación empezó a recomendar basura porque el modelo había aprendido un drift que mi evaluación local no estaba capturando. Cambié la semilla del train_test_split para "probar algo" — AUC bajó de 0.954 a 0.921 — y nadie en el review thread se enteró porque el diff era solo seed=42 → seed=7. Tres semanas depurando en producción que un gate automatizado habría cazado en 47 segundos.

Eso es CI/CD ML, y no es "agregar tests a tu modelo". Es instalar una compuerta entre tu laptop y main que toma una decisión binaria con evidencia numérica antes de que un humano pierda una hora revisando código a ciegas. Te muestro la matemática de esa compuerta, cómo cml la cablea sobre GitHub Actions, y el código production-grade que uso para no volver a quemarme con un AUC mentiroso.

1. Que es CI/CD ML? (Y por que deberia importarte)

1.1 La analogia cotidiana: el laboratorio cervecero

Una microcervecería seria no embotella un lote nuevo sin pasarlo por el laboratorio de control de calidad. El brewmaster (data scientist) entrega el lote (commit con cambios en model/), el técnico de laboratorio (runner de GitHub Actions) corre análisis químicos sobre muestras del tanque — gravedad, pH, amargor — que son las métricas offline. El técnico fotografía el cromatógrafo y el colorímetro (plots ROC, PR, distribución de errores), escribe un reporte firmado (comentario en el PR con tabla markdown) y se lo entrega al maestro cervecero (el revisor o la política de branch protection). El maestro decide si el lote se embotella (merge + deploy) o se va por el desagüe (PR cerrado). CML automatiza ese "toma de muestra → análisis → fotografía → reporte firmado" de manera que ningún lote escape sin catarlo.

La diferencia clave con CI tradicional: en CI de software, el test es determinístico. En ML, la métrica es una estimación estadística sobre una muestra con ruido. Por eso la compuerta no puede ser un simple if new_auc > old_auc: tiene que considerar el delta, el intervalo de confianza y el tamaño de efecto.

1.2 La matematica formal: la compuerta, el delta y el efecto

Sea $M_b$ la métrica estimada sobre la rama baseline (típicamente main) y $M_c$ la métrica estimada sobre el PR. El delta es:

$$\Delta M = M_c - M_b$$

Cada métrica tiene una dirección: si es de maximización (AUC, F1, accuracy) queremos $\Delta M \geq 0$; si es de minimización (RMSE, MAE) queremos $\Delta M \leq 0$. La compuerta básica con tolerancia $\epsilon \geq 0$ es:

$$G(M_c, M_b, \epsilon, D) = \begin{cases} \text{PASS} & \text{si } (D = \text{MAX} \land \Delta M \geq \epsilon) \lor (D = \text{MIN} \land -\Delta M \geq \epsilon) \\ \text{FAIL} & \text{en otro caso} \end{cases}$$

El símbolo $\epsilon$ es la holgura mínima exigida: no queremos pasar un PR que mejore el AUC en $0.0001$ porque eso está dentro del ruido del test set.

Una métrica puntual $\hat{\theta}$ estimada sobre $n$ muestras tiene varianza $s^2/n$. Si no la controlamos, la compuerta es una moneda al aire. Por eso estimamos intervalo de confianza por bootstrap: remuestreamos $B$ veces con reemplazo, calculamos la métrica en cada remuestra y tomamos los percentiles:

$$\text{IC}_{95\%} = \left[ \hat{\theta}_{(0.025)}, \hat{\theta}_{(0.975)} \right]$$

Un gate robusto rechaza si el extremo inferior del IC de $M_c$ cae por debajo de $M_b + \epsilon$ (para métricas MAX).

Para comparar formalmente dos estimadores, usamos t-test pareado sobre scores por fold. Sea $d_i = s_i^{(c)} - s_i^{(b)}$ la diferencia del score en el fold $i$, y $n$ el número de folds:

$$t = \frac{\bar{d}}{s_d / \sqrt{n}}, \quad p = 2 \cdot P(T_{n-1} > |t|)$$

donde $\bar{d} = \frac{1}{n}\sum d_i$ y $s_d = \sqrt{\frac{1}{n-1}\sum (d_i - \bar{d})^2}$. La métrica solo "cuenta" como mejora si $p < 0.05$ y $\Delta M \geq \epsilon$.

Para medir la magnitud práctica de la mejora (no solo significancia), calculamos Cohen's $d$:

$$d = \frac{M_c - M_b}{s_{\text{pooled}}}, \quad s_{\text{pooled}} = \sqrt{\frac{(n_c-1)s_c^2 + (n_b-1)s_b^2}{n_c + n_b - 2}}$$

Un $|d| < 0.2$ indica mejora trivial aunque $p < 0.001$ con $n$ enorme. Es el guardrail que evita que aprueben 12 PRs seguidos que cada uno "mejoró el AUC en 0.0003".

2. Como cml + GitHub Actions resuelven esto por vos

cml no es un orquestador. Es un conjunto de comandos CLI que, ejecutados dentro de un workflow de GitHub Actions, publican artefactos (markdown, imágenes, tablas) como comentarios en el PR. El resto del trabajo — entrenar, evaluar, comparar — lo haces tú en Python. Esa separación es deliberada y es la razón por la que no terminas atrapado en un framework opaco.

El flujo: abres un PR que cambia archivos en model/. GitHub dispara el workflow por pull_request. El runner clona, instala dependencias, ejecuta tu script que produce metrics.json, roc.png, per_sample_scores.npy. Luego invocas cml comment create report.md y cml publish roc.png --md, y cml postea el comentario con la tabla y la imagen. El revisor ve el reporte sin clonar nada, y branch protection puede configurarse para requerir ese check antes del merge.

Lo crítico: el runner usa el código del PR para entrenar al candidato, pero para el baseline necesita el código de main. Lo que hago: git checkout origin/main -- model/ antes del segundo entrenamiento, corro el script, restauro con git checkout HEAD -- model/. Esto da una comparación apples-to-apples con datos idénticos y solo el código cambiando.

3. cml: Uso Directo y Casos de Control Fino

Los tres comandos que vas a usar el 95% del tiempo:

# Publicar markdown como comentario en el PR

# Publicar una imagen y obtener markdown embebido

# Publicar multiples plots
cml publish artifacts/roc.png artifacts/pr_curve.png \
  --md --title "Diagnostics" >> artifacts/report.md

Para instalación local, pip install cml no es la vía soportada. Usa npx cml o el contenedor iterativeai/cml:0-dvc2-base1. En el workflow siempre prefiero la Action oficial porque fija versiones:

- uses: iterative/setup-cml@v2

Subcomandos adicionales:

# Comentar en un PR especifico por numero

# Sin publicar, solo imprimir el markdown (debug)
cml publish roc.png --md --title "ROC"

4. Implementacion Production-Ready: pipeline completo

4.1 Tipos y protocolos (schema.py)

from dataclasses import dataclass, field
from enum import Enum
from typing import Optional


class Direction(str, Enum):
    MAXIMIZE = "maximize"
    MINIMIZE = "minimize"


@dataclass(frozen=True)
class MetricSpec:
    name: str
    direction: Direction
    tolerance: float                    # delta minimo exigido
    floor: Optional[float] = None       # piso absoluto (catch de regresiones graves)


@dataclass
class GateResult:
    metric_name: str
    baseline: float
    candidate: float
    delta: float
    tolerance: float
    passed: bool
    p_value: Optional[float] = None
    effect_size: Optional[float] = None

    def to_row(self) -> str:
        p = f"{self.p_value:.4f}" if self.p_value is not None else "n/a"
        d = f"{self.effect_size:.3f}" if self.effect_size is not None else "n/a"
        verdict = "PASS" if self.passed else "FAIL"
        return (
            f"| {self.metric_name} | {self.baseline:.4f} | {self.candidate:.4f} "
            f"| {self.delta:+.4f} | {self.tolerance:+.4f} | {p} | {d} | {verdict} |"
        )


@dataclass
class GateEvaluation:
    results: list[GateResult] = field(default_factory=list)

    @property
    def all_passed(self) -> bool:
        return all(r.passed for r in self.results)

    def header(self) -> str:
        return (
            "| Metric | Baseline | Candidate | Delta | Tolerance | p-value | Cohen d | Verdict |\n"
            "|---|---|---|---|---|---|---|---|\n"
            + "\n".join(r.to_row() for r in self.results)
        )

4.2 El motor principal (gate.py + train.py + workflow)

# gate.py — la logica de la compuerta
import numpy as np
from scipy import stats
from schema import Direction, GateEvaluation, GateResult, MetricSpec


def evaluate(spec: MetricSpec, baseline: np.ndarray, candidate: np.ndarray) -> GateResult:
    assert len(baseline) == len(candidate), "deben ser pareados"

    if spec.direction == Direction.MAXIMIZE:
        delta = float(np.mean(candidate) - np.mean(baseline))
    else:
        delta = float(np.mean(baseline) - np.mean(candidate))

    t_stat, p_value = stats.ttest_rel(candidate, baseline)

    # Cohen d pareado
    d_arr = candidate - baseline
    sd = float(np.std(d_arr, ddof=1))
    d_eff = float(np.mean(d_arr) / sd) if sd > 0 else 0.0

    passed = delta >= spec.tolerance
    if spec.floor is not None and np.mean(candidate) < spec.floor:
        passed = False  # veto absoluto: la metrica cayo por debajo del piso

    base_val = float(np.mean(baseline)) if spec.direction == Direction.MAXIMIZE else -float(np.mean(baseline))
    cand_val = float(np.mean(candidate)) if spec.direction == Direction.MAXIMIZE else -float(np.mean(candidate))

    return GateResult(
        metric_name=spec.name,
        baseline=base_val,
        candidate=cand_val,
        delta=delta,
        tolerance=spec.tolerance,
        passed=passed,
        p_value=float(p_value),
        effect_size=d_eff,
    )
# train.py — script invocado por el workflow
import json
from pathlib import Path

import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import RocCurveDisplay, average_precision_score, roc_auc_score
from sklearn.model_selection import StratifiedKFold, train_test_split
import matplotlib.pyplot as plt

ART = Path("artifacts")
ART.mkdir(exist_ok=True)
SEED = 42

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=SEED, stratify=y)

model = RandomForestClassifier(n_estimators=300, max_depth=10, random_state=SEED, n_jobs=-1)
model.fit(X_tr, y_tr)
proba = model.predict_proba(X_te)[:, 1]

scores = {
    "roc_auc": float(roc_auc_score(y_te, proba)),
    "pr_auc": float(average_precision_score(y_te, proba)),
    "n_test": int(len(y_te)),
    "seed": SEED,
}
Path(ART / "metrics.json").write_text(json.dumps(scores, indent=2))

# Scores OOF pareados por fold (input del t-test)
skf = StratifiedKFold(n_splits=5, shuffle=True, random_state=SEED)
fold_scores = []
for tr, va in skf.split(X, y):
    m = RandomForestClassifier(n_estimators=300, max_depth=10, random_state=SEED, n_jobs=-1)
    m.fit(X[tr], y[tr])
    p = m.predict_proba(X[va])[:, 1]
    fold_scores.append(roc_auc_score(y[va], p))
np.save(ART / "per_sample_scores.npy", np.array(fold_scores))

fig, ax = plt.subplots(figsize=(6, 6))
RocCurveDisplay.from_predictions(y_te, proba, ax=ax, name=f"RF seed={SEED}")
fig.tight_layout()
fig.savefig(ART / "roc.png", dpi=120)
plt.close(fig)
print(json.dumps(scores))
# .github/workflows/cml.yaml
name: model-ci
on:
  pull_request:
    branches: [main]
    paths: ["model/**", ".github/workflows/cml.yaml"]
  workflow_dispatch:

permissions:
  contents: read
  pull-requests: write

jobs:
  cml-run:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: actions/setup-python@v5
        with: { python-version: "3.11", cache: pip }
      - uses: iterative/setup-cml@v2
      - run: pip install -r model/requirements.txt

      - name: Train PR candidate
        run: python model/train.py

      - name: Train baseline from main
        run: |
          git fetch origin main --depth=1
          git checkout origin/main -- model/
          python model/train.py
          mv artifacts/metrics.json artifacts/metrics_baseline.json
          mv artifacts/per_sample_scores.npy artifacts/baseline_per_sample.npy
          git checkout HEAD -- model/

      - name: Run gate
        id: gate
        run: |
          python model/run_gate.py \
            --candidate-per-sample artifacts/per_sample_scores.npy \
            --baseline-per-sample artifacts/baseline_per_sample.npy \
            --output artifacts/report.md
          cat artifacts/report.md >> "$GITHUB_STEP_SUMMARY"

      - name: Publish CML report
        if: always()
        env:
          REPO_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          cml comment create --body-file artifacts/report.md
          cml publish artifacts/roc.png --md --title "ROC (PR)" >> artifacts/report.md || true

      - name: Fail the job if gate failed
        if: steps.gate.outputs.failed == 'true'
        run: exit 1

4.3 Utilidades de analisis y verificacion (run_gate.py)

# run_gate.py — orquesta el gate y genera el reporte markdown
import argparse
from pathlib import Path

import numpy as np
from gate import evaluate
from schema import Direction, GateEvaluation, MetricSpec


SPECS = [
    MetricSpec("roc_auc", Direction.MAXIMIZE, tolerance=0.002, floor=0.90),
    MetricSpec("pr_auc", Direction.MAXIMIZE, tolerance=0.002, floor=0.85),
]


def main() -> int:
    p = argparse.ArgumentParser()
    p.add_argument("--candidate-per-sample", required=True)
    p.add_argument("--baseline-per-sample", required=True)
    p.add_argument("--output", required=True)
    args = p.parse_args()

    cand = np.load(args.candidate_per_sample)
    base = np.load(args.baseline_per_sample)
    assert len(cand) == len(base), "deben ser pareados"

    ev = GateEvaluation()
    for spec in SPECS:
        ev.results.append(evaluate(spec, baseline=base, candidate=cand))

    header = "# CML Gate Report\n\n"
    summary = (
        f"**Verdict**: {'PASS' if ev.all_passed else 'FAIL'}\n\n"
        f"Folds pareados: $n = {len(cand)}$. Tolerancia: $\\epsilon = 0.002$. "
        f"Piso absoluto AUC $\\geq 0.90$, PR-AUC $\\geq 0.85$.\n\n"
    )
    Path(args.output).write_text(header + summary + ev.header() + "\n")

    print(f"all_passed={ev.all_passed}")
    return 0 if ev.all_passed else 2   # exit code != 0 → job falla


if __name__ == "__main__":
    raise SystemExit(main())

5. Ejemplos de Uso en Casos Reales

Caso 1 — Tabular classifier (default del repo ejemplo)

Supongamos que el PR cambia max_depth de 8 a 10 y n_estimators de 200 a 300. El reporte real en el PR:

| Metric   | Baseline | Candidate | Delta   | Tolerance | p-value | Cohen d | Verdict |
|----------|----------|-----------|---------|-----------|---------|---------|---------|
| roc_auc  | 0.9547   | 0.9623    | +0.0076 | +0.0020   | 0.0180  | 0.421   | PASS    |
| pr_auc   | 0.9311   | 0.9402    | +0.0091 | +0.0020   | 0.0110  | 0.388   | PASS    |

Verificación numérica: $0.9623 - 0.9547 = 0.0076 \geq 0.002$ ✓ (gate), $0.9623 \geq 0.90$ ✓ (piso), $p=0.018 < 0.05$ ✓ (significancia), $d=0.421$ (efecto mediano). Gate PASS.

Caso 2 — Modelo de regresion (RMSE a minimizar)

SPECS = [
    MetricSpec("rmse", Direction.MINIMIZE, tolerance=0.05),
    MetricSpec("mae",  Direction.MINIMIZE, tolerance=0.03),
]
| Metric | Baseline | Candidate | Delta  | Tolerance | p-value | Cohen d | Verdict |
|--------|----------|-----------|--------|-----------|---------|---------|---------|
| rmse   | 12.412   | 12.298    | -0.114 | -0.050    | 0.0230  | 0.302   | PASS    |
| mae    |  9.870   |  9.802    | -0.068 | -0.030    | 0.0410  | 0.215   | PASS    |

Aquí delta se reporta como $M_b - M_c$ (positivo = mejora). Verificación: $12.412 - 12.298 = 0.114 \geq 0.05$ ✓.

Caso 3 — Veto por piso (catch de regresion grave)

Si el PR sube AUC de 0.955 a 0.957 pero rompe PR-AUC (de 0.93 a 0.84), el gate falla por piso aunque el AUC nominal "mejoró":

| Metric  | Baseline | Candidate | Delta   | Tolerance | p-value | Cohen d | Verdict |
|---------|----------|-----------|---------|-----------|---------|---------|---------|
| roc_auc | 0.9547   | 0.9571    | +0.0024 | +0.0020   | 0.210   | 0.090   | PASS    |
| pr_auc  | 0.9311   | 0.8420    | -0.0891 | +0.0020   | 0.0001  | -2.140  | FAIL    |

Veto absoluto vía floor=0.85 sobre PR-AUC: $0.8420 < 0.85$ → passed = False aunque el delta bruto "cumpla". Esto evita que un modelo sesgado hacia la clase mayoritaria apruebe con AUC alto pero PR-AUC colapsado.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1 — cml: command not found

Reproducción: workflow sin el step iterative/setup-cml@v2.

# MAL
steps:
  - uses: actions/checkout@v4
  - run: pip install -r requirements.txt
  - run: cml comment create report.md    # <- aca explota

Log: cml: command not found. Esa vaina pasa cuando copias un workflow de un repo que usaba la imagen iterativeai/cml:0-dvc2-base1 como container: y te lo llevas a uno con runs-on: ubuntu-latest pelado.

Soluciones:

  1. Agregar iterative/setup-cml@v2 como step previo (recomendado).
  2. Si insistes en pip, instala desde el repo: pip install git+https://github.com/iterative/cml.git@v0.20.5 y fija la versión. NO uses pip install cml desde PyPI sin verificar — el paquete cambió de maintainers.
  3. Verifica con cml --version en un step de prueba antes de postear.

Problema 2 — El comentario nunca aparece en el PR

Tres causas por frecuencia:

Causa A — trigger incorrecto: el workflow dispara en push, no en pull_request. cml comment create requiere contexto de PR.

# MAL
on: { push: { branches: [main] } }

# BIEN
on: { pull_request: { branches: [main] } }

Causa B — permisos: el GITHUB_TOKEN en workflows modernos tiene read-only si definiste permissions: read-all en algún lado. Sin pull-requests: write, el POST devuelve 403 silencioso para cml.

permissions:
  contents: read
  pull-requests: write

Causa C — token no exportado: debe ir como REPO_TOKEN:

- name: Publish
  env:
    REPO_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  run: cml comment create --body-file report.md

Detección: en el log del step verás 403 Forbidden o Could not resolve PR. Cualquiera de los dos te dice cuál de las tres causas es.

Problema 3 — Metricas fluctuan entre runs "iguales"

Si tu script no fija todas las semillas, un mismo commit genera AUC distintos en runs sucesivos y el gate pasa/falla de forma no determinística. Eso destruye la confianza del equipo en el pipeline.

# MAL
np.random.seed(42)
model = RandomForestClassifier()  # random_state=None

# BIEN
import os, random
SEED = 42
os.environ["PYTHONHASHSEED"] = str(SEED)
random.seed(SEED)
np.random.seed(SEED)
model = RandomForestClassifier(random_state=SEED, n_jobs=1)

Para sklearn 1.3+ también puedes pasar deterministic=True en estimadores que lo soporten. Para PyTorch: torch.manual_seed(SEED), torch.use_deterministic_algorithms(True), torch.backends.cudnn.deterministic = True. Detección: corre el mismo workflow dos veces con el mismo SHA y compara metrics.json byte a byte. Si difieren, tienes no-determinismo escondido.

7. Optimizaciones de Produccion

Optimizacion 1 — Matrix builds sobre semillas

Un solo run es una muestra de tamaño 1. Si tu random_state=42 tuvo suerte, el AUC es alto por accidente y el siguiente PR con random_state=7 falla "sin razón". Solución: matrix build con N semillas, agrega scores por fold y corre el gate sobre el agregado pareado.

strategy:
  fail-fast: false
  matrix:
    seed: [42, 7, 123, 2024, 9999]
steps:
  - run: MODEL_SEED=${{ matrix.seed }} python model/train.py
  - if: always()
    run: python model/aggregate_seeds.py --input-dir artifacts/ --output artifacts/aggregated.json

Con N=5 semillas x 5 folds = 25 observaciones pareadas, el t-test tiene 24 grados de libertad y deja de ser sensible a una corrida con suerte. Trade-off: 5x el costo de cómputo. Vale la pena si tu training tarda <30 min; no vale la pena si tarda 8h.

Optimizacion 2 — Cache de dataset via DVC

Si tu dataset pesa 50 GB y solo cambiaste el código, no tiene sentido re-descargarlo. DVC versiona el dataset y el runner solo lo descarga si cambió el hash.

- uses: iterative/setup-dvc@v3
- run: |
    dvc pull data/features.dvc --force
    dvc pull data/labels.dvc --force

Trade-off: agrega complejidad operacional (remote S3/GCS) y un step más. Vale la pena desde la segunda semana.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

  • La compuerta no es opcional — sin gate automatizado, el merge a main es fe humana contra varianza estadística.
  • Bootstrap CI + t-test pareado + Cohen d — los tres juntos. Sin bootstrap confías en un punto; sin p-value confías en delta aunque sea ruido; sin Cohen d apruebas "mejoras" que son ruido disfrazado.
  • cml es transporte, no opinion — la opinión (qué métrica, tolerancia, piso) la pones tú en gate.py. No hay caja negra.
  • Pisos absolutos (floor) son el hero feature — cazan regresiones graves disfrazadas de mejoras marginales.

Mini-checklist antes de hacer merge:

  • [ ] Workflow dispara en pull_request (no push)
  • [ ] permissions incluye pull-requests: write
  • [ ] iterative/setup-cml@v2 está en los steps
  • [ ] REPO_TOKEN exportado en el step de cml comment create
  • [ ] Script fija todas las semillas (numpy, random, sklearn, torch)
  • [ ] Hay al menos una métrica con floor absoluto además de tolerance
  • [ ] El gate falla el job cuando all_passed == False

Hagale pues, monta esto en tu próximo PR de modelo y vas a ver en 48 horas cuántos merges "inocentes" estaban a punto de degradar producción sin que nadie se diera cuenta. El batch bueno pasa, el malo se va al desagüe antes de tocar un usuario real, y tu viernes a las 6pm vuelve a ser un viernes a las 6pm — no hay fiesta que valga más que eso.
