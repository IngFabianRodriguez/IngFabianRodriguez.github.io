Introduccion: Cuando quisiste correr un LLM local y terminaste llorando en CUDA

Te ha pasado: necesitas correr un Llama 3 70B en tu maquina para una demo con un cliente manana a las 8 AM. Abres HuggingFace, descargas el safetensors, intentas cargarlo con transformers, y boom: torch.cuda.OutOfMemoryError. Piensas "OK, voy a cuantizarlo". Abres otra guia. Instalas bitsandbytes. Otro error. Pruebas llama.cpp directo. Necesitas compilarlo con CMake, configurar flags para tu GPU (que resulta ser una RTX 3060 con 12 GB, pero el modelo necesita 40). Lees sobre GGUF, AWQ, GPTQ, EXL2, y cada una tiene su propia herramienta.

Y todo esto antes de escribir una sola linea de codigo de inferencia.

Mira, ese fue yo hace dos anos, a las 11 PM de un viernes, con un cliente esperando al lunes. El problema no era ejecutar el modelo. El problema era todo el contexto alrededor: descargar el formato correcto, cuantizar bien, configurar el backend (CUDA, Metal, ROCm, Vulkan, segun tu hardware), manejar la carga en VRAM, decidir cuando hacer offloading a CPU, exponer una API limpia para tu aplicacion.

Ahi entra Ollama. Pero Ollama no es solo "un wrapper bonito". Hay matematica de muestreo que tienes que entender para no quemarte en produccion, hay decisiones de arquitectura que afectan latencia, y hay debugging real cuando el modelo alucina o se queda colgado. Hoy te voy a mostrar las tripas, no solo el wrapper.

1. Que es Ollama? (Y por que deberia importarte)

1.1 La analogia cotidiana

Pensalo asi: Ollama es el USB-C de los LLMs locales. Tu codigo (la aplicacion) habla un solo idioma: HTTP + JSON. Los modelos, en cambio, llegan en formatos propietarios incompatibles entre si (GGUF, safetensors, PyTorch checkpoints, .bin antiguos), cada uno con su propia herramienta de carga, su propio backend de GPU (CUDA para NVIDIA, Metal para Apple Silicon, ROCm para AMD, Vulkan como salvavidas), y su propia curva de aprendizaje para cuantizar y tunear.

Antes de Ollama, vos necesitabas:

  • Saber que tu hardware soporta que backend
  • Compilar o instalar el runtime correcto (llama.cpp, vLLM, exllama, etc.)
  • Convertir el modelo al formato que ese runtime entiende
  • Escribir un servidor o usar uno de terceros (llama-cpp-python server, text-generation-inference, etc.)
  • Manejar manualmente la carga/descarga de modelos desde disco a VRAM

Con Ollama todo eso es un solo comando: ollama run llama3. El actua como un daemon que administra los modelos, los descarga, los cuantiza on-the-fly si hace falta, negocia con tu GPU/CPU, y te expone una API REST unica. Es el hub que traduce entre vos y el caos.

1.2 La matematica formal: muestreo de tokens, softmax y temperatura

Cuando Ollama genera texto, internamente delega a llama.cpp, que corre el modelo y produce logits (valores reales sin normalizar) para cada token del vocabulario en cada paso. La magia esta en como esos logits se convierten en el siguiente token. La formula central es el softmax con temperatura:

$$P(t_i \mid t_{Simbolo por simbolo:

  • $P(t_i \mid t_{
  • $z_i \in \mathbb{R}$: el logit crudo que el modelo emite para el token $i$ en el vocabulario
  • $T \in \mathbb{R}^+$: la temperatura. Cuando $T = 1$, la distribucion es la que el modelo aprendio. Cuando $T < 1$, la distribucion se vuelve mas picuda (mas determinista). Cuando $T > 1$, se aplana (mas creativa/caotica)
  • $V$: tamano del vocabulario del modelo (para Llama 3 es 128256, para Mistral es 32000)
  • $\exp$: la funcion exponencial, que garantiza que todos los valores sean positivos

Despues del softmax, Ollama aplica top-k y top-p (nucleus sampling) para recortar la cola de la distribucion. Top-k mantiene solo los $k$ tokens con logits mas altos (el resto se vuelve $-\infty$ antes del softmax). Top-p mantiene el conjunto minimo de tokens cuya probabilidad acumulada sea $\geq p$:

Porque si pones temperature=0.8, top_p=0.9, top_k=40, estas diciendole al modelo: "saca los 40 tokens mas probables, luego quedate con los que cubran el 90% de la masa de probabilidad, y dentro de ese conjunto muestrea con temperatura 0.8". Si no entiendes eso, no podes debuggear cuando el modelo te devuelve respuestas raras.

2. Como Ollama resuelve esto por vos

Ollama es, en esencia, un daemon en Go que envuelve a llama.cpp y le anade:

  1. Un servidor REST sobre HTTP que expone /api/generate, /api/chat, /api/embeddings, /api/create, /api/pull, etc.
  2. Un administrador de modelos que descarga desde un registry propio (registry.ollama.ai), almacena en ~/.ollama/models/ con un formato estandar (blobs + manifests, inspirado en OCI/Docker).
  3. Un sistema de plantillas (Modelfile) que empaqueta: pesos base + prompt del sistema + parametros por defecto (temperature, top_p, top_k, stop sequences, etc.).
  4. Gestion automatica de GPU/CPU: detecta tu hardware, decide cuantos layers poner en GPU, hace offloading a CPU cuando la VRAM no alcanza, balancea entre multiples GPUs si las tienes.
  5. Quantizacion bajo demanda: si descargas un modelo en Q4_0 pero tienes RAM de sobra, podes pedirle que lo recargue en Q8_0 sin re-descargar nada.

Arquitectura simplificada:

[Tu app Python] --> HTTP REST --> [Ollama daemon (Go)] --> [llama.cpp (C++/CUDA)] --> [Tu GPU/CPU]
                          |
                          +--> [Registry de modelos] (registry.ollama.ai)
                          |
                          +--> [Cache local en ~/.ollama/models/]

El truco clave es el formato GGUF (GPT-Generated Unified Format), que es el estandar de facto para modelos cuantizados. GGUF es self-contained: incluye los pesos, los hiperparametros del modelo (arquitectura, numero de capas, dimension de attention heads), el tokenizer, y metadata. Esto es lo que permite que un mismo binario sirva para Llama, Mistral, Phi, Qwen, Gemma, etc., sin que vos recompiles nada.

Para cargar un modelo a VRAM, Ollama usa mmap() (memory-mapped files), lo cual significa que el tiempo de carga es proporcional al tamano del slice en GPU, no al tamano total del modelo. Tu modelo de 40 GB se "carga" en milisegundos, y solo los layers que van a GPU se copian realmente a VRAM.

3. Ollama: Uso Directo y Casos de Control Fino

La CLI basica es directa:

# Descargar un modelo (cuantizado por defecto)
ollama pull llama3.2:3b

# Correr en modo interactivo
ollama run llama3.2:3b "Explicame el teorema de Bayes en una sola oracion"

# Ver que modelos tienes
ollama list

# Ver metadata de un modelo especifico
ollama show llama3.2:3b

# Ver que modelos estan cargados en memoria ahora
ollama ps

# Crear un modelo custom con Modelfile
cat > Modelfile <<'EOF'
FROM llama3.2:3b
SYSTEM "Sos un asistente legal argentino que responde en espanol neutro"
PARAMETER temperature 0.3
PARAMETER top_p 0.9
PARAMETER num_ctx 4096
EOF
ollama create asistente-legal -f Modelfile

La libreria Python (pip install ollama) es sync y async, y mapea 1:1 contra la API REST:

import ollama

# Chat basico (no streaming)
response = ollama.chat(
    model='llama3.2:3b',
    messages=[
        {'role': 'system', 'content': 'Sos un asistente tecnico conciso.'},
        {'role': 'user', 'content': 'Que es un tensor?'},

# Streaming token por token
stream = ollama.chat(
    model='llama3.2:3b',
    messages=[{'role': 'user', 'content': 'Escribi un haiku sobre ML'}],
    stream=True,
)
for chunk in stream:
    print(chunk['message']['content'], end='', flush=True)

# Embeddings
embedding = ollama.embeddings(
    model='nomic-embed-text',

)

4. Implementacion Production-Ready: OllamaClient

Vamos a construir un cliente que use Ollama como backend para un sistema RAG, con manejo de retries, streaming, observabilidad y control fino de parametros. Esto NO es pseudocodigo; corre tal cual si tienes Ollama corriendo localmente y ollama pull llama3.2:3b nomic-embed-text ejecutado.

4.1 Tipos y protocolos

# ollama_types.py
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Iterator


@dataclass(frozen=True, slots=True)
class ChatMessage:
    role: str  # 'system' | 'user' | 'assistant'
    content: str


@dataclass(frozen=True, slots=True)
class GenerationParams:
    temperature: float = 0.7
    top_p: float = 0.9
    top_k: int = 40
    num_ctx: int = 4096
    repeat_penalty: float = 1.1
    seed: int | None = None


@dataclass(frozen=True, slots=True)
class ChatRequest:
    model: str
    messages: tuple[ChatMessage, ...]
    params: GenerationParams = field(default_factory=GenerationParams)
    stream: bool = False


@dataclass(frozen=True, slots=True)
class TokenUsage:
    prompt_tokens: int
    completion_tokens: int
    total_tokens: int

    @property
    def tokens_per_second(self) -> float:
        return 0.0  # se completa en el cliente con wall-time


@dataclass(frozen=True, slots=True)
class ChatResponse:
    content: str
    model: str
    usage: TokenUsage
    duration_ns: int

4.2 El motor principal

# ollama_client.py
from __future__ import annotations

import logging
import time
from collections.abc import Iterator

import ollama
from ollama_types import (
    ChatMessage,
    ChatRequest,
    ChatResponse,
    GenerationParams,
    TokenUsage,
)

logger = logging.getLogger(__name__)


class OllamaClient:
    """Cliente production-ready sobre el SDK oficial de Ollama."""

    def __init__(
        self,
        host: str = 'http://127.0.0.1:11434',
        default_timeout_s: float = 120.0,
        max_retries: int = 3,
    ) -> None:
        self._client = ollama.Client(host=host, timeout=default_timeout_s)
        self._max_retries = max_retries

    @staticmethod
    def _params_to_options(params: GenerationParams) -> dict:
        opts = {
            'temperature': params.temperature,
            'top_p': params.top_p,
            'top_k': params.top_k,
            'num_ctx': params.num_ctx,
            'repeat_penalty': params.repeat_penalty,
        }
        if params.seed is not None:
            opts['seed'] = params.seed
        return opts

    def chat(self, request: ChatRequest) -> ChatResponse:
        opts = self._params_to_options(request.params)
        msgs = [{'role': m.role, 'content': m.content} for m in request.messages]

        last_exc: Exception | None = None
        for attempt in range(1, self._max_retries + 1):
            try:
                t0 = time.perf_counter_ns()
                resp = self._client.chat(
                    model=request.model,
                    messages=msgs,
                    options=opts,
                    stream=False,
                )
                duration_ns = time.perf_counter_ns() - t0
                usage = TokenUsage(
                    prompt_tokens=resp.get('prompt_eval_count', 0),
                    completion_tokens=resp.get('eval_count', 0),
                    total_tokens=resp.get('prompt_eval_count', 0)
                    + resp.get('eval_count', 0),
                )
                return ChatResponse(
                    content=resp['message']['content'],
                    model=resp.get('model', request.model),
                    usage=usage,
                    duration_ns=duration_ns,
                )
            except ollama.ResponseError as exc:
                last_exc = exc
                logger.warning(
                    'chat fallo (intento %d/%d): %s', attempt, self._max_retries, exc
                )
                if attempt < self._max_retries:
                    time.sleep(2 ** attempt)  # backoff exponencial
        raise RuntimeError(f'Chat fallo tras {self._max_retries} intentos') from last_exc

    def chat_stream(self, request: ChatRequest) -> Iterator[str]:
        opts = self._params_to_options(request.params)
        msgs = [{'role': m.role, 'content': m.content} for m in request.messages]
        stream = self._client.chat(
            model=request.model,
            messages=msgs,
            options=opts,
            stream=True,
        )
        for chunk in stream:
            delta = chunk['message']['content']
            if delta:
                yield delta

    def embed(self, model: str, text: str) -> list[float]:
        resp = self._client.embeddings(model=model, prompt=text)
        return resp['embedding']

4.3 Utilidades de analisis y verificacion

# ollama_metrics.py
from __future__ import annotations

from dataclasses import dataclass

from ollama_client import OllamaClient
from ollama_types import ChatMessage, ChatRequest, GenerationParams


@dataclass(frozen=True, slots=True)
class GenerationReport:
    prompt_tokens: int
    completion_tokens: int
    duration_s: float
    tokens_per_second: float
    estimated_cost_usd: float  # 0 para local, util si migras a cloud despues


def measure_generation(client: OllamaClient, req: ChatRequest) -> GenerationReport:
    """Ejecuta una generacion y devuelve metricas de rendimiento."""
    resp = client.chat(req)
    duration_s = resp.duration_ns / 1e9
    tps = resp.usage.completion_tokens / duration_s if duration_s > 0 else 0.0
    return GenerationReport(
        prompt_tokens=resp.usage.prompt_tokens,
        completion_tokens=resp.usage.completion_tokens,
        duration_s=duration_s,
        tokens_per_second=tps,
        estimated_cost_usd=0.0,
    )


def estimate_kv_cache_memory_gb(
    n_layers: int,
    n_kv_heads: int,
    head_dim: int,
    seq_len: int,
    bytes_per_element: int = 2,  # FP16 por defecto
) -> float:
    """Estima la VRAM consumida por el KV cache en GB.

    Formula:
        M_KV = 2 * L * H_kv * d_h * S * B  bytes
    donde:
        L  = numero de capas transformer
        H_kv = numero de KV heads (puede ser < n_heads si usa GQA)
        d_h = dimension de cada head
        S  = longitud maxima de secuencia
        B  = bytes por elemento (2 para FP16, 1 para INT8)

    Para Llama 3 8B con seq_len=8192, n_layers=32, n_kv_heads=8,
    head_dim=128: M_KV = 2 * 32 * 8 * 128 * 8192 * 2 / 1e9 ≈ 1.07 GB.
    """
    bytes_total = 2 * n_layers * n_kv_heads * head_dim * seq_len * bytes_per_element
    return bytes_total / 1e9

5. Ejemplos de Uso en Casos Reales

Caso 1: RAG minimalista con embeddings locales

from ollama_client import OllamaClient
from ollama_types import ChatMessage, ChatRequest, GenerationParams

client = OllamaClient()

# 1) Indexar documentos (en un sistema real seria batch + vector DB)
docs = [
    'Ollama usa el formato GGUF para distribuir modelos.',
    'llama.cpp es el motor de inferencia que Ollama envuelve.',
    'Top-p sampling descarta tokens cuya probabilidad acumulada es menor a p.',
]
doc_embeddings = [client.embed('nomic-embed-text', d) for d in docs]

# 2) Query del usuario
query = 'Que formato usa Ollama?'
query_emb = client.embed('nomic-embed-text', query)

# 3) Retrieve top-1 por similitud coseno
import numpy as np

def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

scores = [cosine(query_emb, e) for e in doc_embeddings]
best_idx = int(np.argmax(scores))
context = docs[best_idx]
# Verificacion numerica: si query_emb == doc_embeddings[0], score deberia ser 1.0

# 4) Generar respuesta con contexto
req = ChatRequest(
    model='llama3.2:3b',
    messages=(
        ChatMessage('system', f'Responde solo con base en este contexto: {context}'),
        ChatMessage('user', query),
    ),
    params=GenerationParams(temperature=0.2, top_p=0.9),  # baja temp para RAG
)
print(client.chat(req).content)

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: model requires more VRAM than available El modelo no entra en GPU. Lo detectas asi:

import ollama
try:
    ollama.chat(model='llama3.1:70b-q4_0', messages=[{'role': 'user', 'content': 'hi'}])
except ollama.ResponseError as e:
    # Verificacion numerica: e.error tipicamente contiene
    # "out of memory" o "failed to allocate VRAM"
    print(f'Error capturado: {e.error}')

Soluciones reales:

  1. Bajar cuantizacion: llama3.1:70b-q4_0 (40 GB) -> llama3.1:70b-q3_K_M (~30 GB).
  2. Limitar el context window: GenerationParams(num_ctx=2048) en vez de 8192 (el KV cache escala lineal con num_ctx).
  3. Forzar offload parcial a CPU: en el Modelfile, PARAMETER num_gpu 20 pone solo 20 layers en GPU y el resto en RAM.
  4. Si no hay nada que hacer: usar un modelo mas chico. Llama 3.1 8B en Q4_K_M entra en 6 GB de VRAM y sirve para el 80% de los casos.

Problema 2: Latencia brutal en el primer token El modelo se descarga de disco a VRAM cada vez. Ollama tiene un parametro keep_alive que mantiene el modelo en memoria:

# Mantener el modelo cargado 10 minutos tras la ultima request
resp = client._client.chat(
    model='llama3.2:3b',
    messages=[{'role': 'user', 'content': 'hola'}],
    keep_alive='10m',  # '5s', '10m', '-1' para indefinido, '0' para descargar de una
)

Problema 3: El modelo alucina o repite tokens Suele ser temperature muy alta + top_p muy alto. No hay fiesta si no validas estos parametros. Para code review o RAG usa temperature <= 0.3. Para escritura creativa 0.7-0.9. Y siempre repeat_penalty=1.1 para evitar loops.

7. Optimizaciones de Produccion

Optimizacion 1: Ajusta num_ctx al caso de uso real El context window es el principal driver de uso de VRAM por el KV cache. Formula exacta:

$$M_{\text{KV}} = 2 \cdot L \cdot H_{\text{kv}} \cdot d_h \cdot S \cdot B \quad \text{[bytes]}$$

Para Llama 3 8B con $L=32$, $H_{\text{kv}}=8$, $d_h=128$:

  • Con $S=2048$, $B=2$: $M_{\text{KV}} = 2 \cdot 32 \cdot 8 \cdot 128 \cdot 2048 \cdot 2 / 10^9 \approx 0.27$ GB.
  • Con $S=8192$: $M_{\text{KV}} \approx 1.07$ GB.

Trade-off: si tu use case es Q&A sobre docs cortos, no necesitas 128k de context. Bajalo a 4096 y liberas VRAM para el modelo o para atender mas requests concurrentes.

Optimizacion 2: keep_alive estrategico Si tu servicio recibe trafico en rafagas (ej. un chatbot que tiene picos a las 9 AM y a las 3 PM), configura keep_alive='30m' en cada request. Si lo dejas en default (5 minutos), entre rafagas el modelo se descarga y la siguiente request paga el costo de recargarlo a VRAM, que en una RTX 4090 con un 70B Q4 puede ser 8-12 segundos. Ese costo multiplicado por 100 requests/min en una ventana corta te mata el SLA.

Conclusion: Por Que Esto te Salva el Pellejo en Produccion

Resumen ejecutivo:

  • Ollama no es magia: es un wrapper sobre llama.cpp con un servidor REST y un registry de modelos. Entiende eso y dejara de ser una caja negra.
  • El control fino vive en los parametros de muestreo: temperatura, top_k, top_p, repeat_penalty. Si no los entiendes, no podes debuggear nada.
  • El KV cache es tu enemigo silencioso: crece lineal con num_ctx. Estimalo siempre antes de desplegar.
  • Los Modelfiles son contratos: encapsulan modelo + system prompt + params. Versiona esos archivos.
  • keep_alive y cuantizacion son tus perillas de latencia/costo principales en local.

Mini-checklist antes de mandar a prod:

  • [ ] Modelo cuantizado adecuado a tu VRAM (mediste con la formula del KV cache)
  • [ ] temperature y top_p fijados segun el caso de uso
  • [ ] keep_alive configurado para tu patron de trafico
  • [ ] Modelfile versionado en Git
  • [ ] Healthcheck contra /api/tags en tu monitoring
  • [ ] Logs de tokens/segundo por request (necesitas la GenerationReport)
  • [ ] Plan B si el modelo no entra: modelo mas chico, cuantizacion agresiva, o migrar a vLLM en una maquina con mas GPU

Probalo hoy mismo: ollama pull llama3.2:3b && ollama run llama3.2:3b "dame un chiste sobre MLOps". Si eso corre en tu laptop, ya tenes el 80% del camino recorrido.
