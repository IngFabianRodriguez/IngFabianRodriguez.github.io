Uno lee articles sobre arquitectura de transformers, attention mechanisms, posicional encodings ¡todo el día! Pero cuando le toca poner eso en producción con 1000 solicitudes por minuto, pues allo que no hay paper que le explique a uno cómo manejar el tráfico de las 9 de la mañana cuando todos golpean el API al tiempo.

En este artículo vamos a compartir las lecciones que el 90% aprende de la manera más dura: rompiendo cosas en producción. Specifícamente, vamos a hablar de batching strategies, KV cache, load balancing, y cómo manejar traffic spikes sin que el sistema se caiga. Con math y código, como a nosotros nos gusta.

La Matemática del Throughput

Antes de meternos en estrategias, necesitamos entender la ecuación fundamental de inference en LLMs:

Throughput (tokens/segundo) = Batch Size × Tokens por Request × Parallelismo

Esta ecuación parece simple pero es profunda. Si mandas requests uno por uno (batch size = 1), estas desperdiciando el 95% del GPU. Un A100 tiene compute para procesar 16 sequences en paralelo, pero si tu mandas una sola, pues el GPU se queda esperando.

El costo por token sigue esta fórmula:

Costo por Token = (Costo GPU-hora / Tokens procesados por hora)

Si tienes un A100 a $1.50/hora y procesas 10,000 tokens/hora (sin batching), pues estas pagando $0.00015 por token. Pero si implementas batching inteligente y procesas 500,000 tokens/hora, bajas a $0.000003 por token ¡50x menos!

Batching Dinámico: La Técnica que 10x Tu Throughput

El batching naive es simplemente agrupar requests hasta que pase algo. Pero eso causa problemas: algunos requests son courts (10 tokens) y otros son largos (2000 tokens). Si esperas a que todos los largos terminen, los cortos ficam esperando mucho tiempo.

import asyncio
from collections import deque
from dataclasses import dataclass
import time

@dataclass
class InferenceRequest:
    request_id: str
    prompt_tokens: list[int]
    max_new_tokens: int
    arrival_time: float
    priority: int = 0

class DynamicBatcher:
    """
    Batching dinámico que maximiza throughput mientras controla latencia.
    El truco está en no esperar demasiado para начала de batch pequeno.
    """
    
    def __init__(
        self,
        max_batch_size: int = 32,
        max_wait_ms: float = 0.05,  # 50ms maximo de espera
        max_tokens_per_batch: int = 8192,  # Limite de tokens por forward pass
    ):
        self.max_batch_size = max_batch_size
        self.max_wait_ms = max_wait_ms
        self.max_tokens_per_batch = max_tokens_per_batch
        self.pending_requests: deque[InferenceRequest] = deque()
        self.processing_lock = asyncio.Lock()
        
    async def add_request(
        self,
        request_id: str,
        prompt_tokens: list[int],
        max_new_tokens: int,
        priority: int = 0
    ) -> str:
        """Agrega un request a la cola."""
        request = InferenceRequest(
            request_id=request_id,
            prompt_tokens=prompt_tokens,
            max_new_tokens=max_new_tokens,
            arrival_time=time.time(),
            priority=priority
        )
        self.pending_requests.append(request)
        return request_id
    
    async def get_batch(self) -> list[InferenceRequest]:
        """
        Obtiene el siguiente batch de requests listos para procesar.
        
        Returns batch cuando:
        1. Alcanzamos max_batch_size
        2. Pasaron max_wait_ms desde el primero en cola
        3. El batch excedería max_tokens_per_batch
        """
        if not self.pending_requests:
            return []
        
        batch = []
        first_arrival = self.pending_requests[0].arrival_time
        
        while self.pending_requests:
            # Verificar si debemos empezar el batch aunque no esté lleno
            if len(batch) >= self.max_batch_size:
                break
                
            next_request = self.pending_requests[0]
            batch_tokens = sum(len(r.prompt_tokens) + r.max_new_tokens for r in batch)
            next_tokens = len(next_request.prompt_tokens) + next_request.max_new_tokens
            
            # Si agregar este request excede el límite de tokens, parar
            if batch_tokens + next_tokens > self.max_tokens_per_batch:
                break
            
            # Si el batch ya tiene members y esperamos demasiado, parar
            if len(batch) > 0:
                wait_time = time.time() - first_arrival
                if wait_time > self.max_wait_ms:
                    break
            
            batch.append(self.pending_requests.popleft())
        
        return batch

# Ejemplo de uso con vLLM o similar
async def process_batch_with_vllm(batch: list[InferenceRequest], engine):
    """
    Procesa un batch de requests usando vLLM para inference paralelo.
    vLLM implementa su propio PagedAttention para manejar memoria eficientemente.
    """
    from vllm import SamplingParams
    
    prompts = [r.prompt_tokens for r in batch]  # Ya tokenizados
    sampling_params = [SamplingParams(temperature=0.7, max_tokens=r.max_new_tokens) for r in batch]
    
    # vLLM maneja el batching internamente con CUDA graphs
    outputs = engine.generate(prompts, sampling_params)
    
    return {req.request_id: output for req, output in zip(batch, outputs)}


# Continuous batching vs Static batching
"""
STATIC BATCHING (lo que NO debes hacer):
Request 1: [====tokens====]              latencia: alta
Request 2: [==tokens==]                   latencia: mucha espera
Request 3: [========tokens========]       latencia: muy alta
|---batch lifecycle---|

CONTINUOUS BATCHING (lo que SÍ debes hacer):
Iteracion 1: [R1][R2][R3]  --> todos en GPU
Iteracion 2: [R1 fin][R2]   --> R1 sale, nuevo R4 entra
Iteracion 3: [R2 fin][R3]   --> R2 sale, nuevo R5 entra
Iteracion 4: [R3 fin]       --> solo R3
"""

class ContinuousBatcher:
    """
    Implementacion de continuous batching donde Requests entran y salen
    continuamente de la cola de la GPU. Esto maximiza utilization.
    """
    
    def __init__(self, engine, max_batch_size: int = 64):
        self.engine = engine
        self.max_batch_size = max_batch_size
        
    async def run_loop(self):
        """Loop principal que mantiene la cola de inference corriendo."""
        while True:
            # 1. Esperar a que haya requests pendientes
            # 2. Tomar hasta max_batch_size requests
            # 3. Mandarlos a la GPU
            # 4. Mientras GPU procesa,收集 nuevos requests
            # 5. Cuando terminen,收集 results y procesar siguientes
            pass

KV Cache: El 50% de Costo que Nadie Te Cuento

Aquí viene la parte que el 90% ignora hasta que le llega la factura de AWS. En un transformer, durante el inference, para cada posicion necesitas calcular attention con TODAS las posiciones anteriores. Eso significa recalcular los mismos key and value vectors una y otra vez.

La solución es el KV cache: guardar los K y V vectors calculados para no recalcularlos. Pero aqui viene el problema: para un modelo de 7B parámetros con context window de 4096 tokens, el KV cache puede ocupar:

KV Cache Size = 2 (K + V) × Num Layers × Hidden Size × Sequence Length × Bytes per Float

Para Llama 2 7B: 2 × 32 layers × 4096 hidden × 4096 context × 2 bytes (FP16) = 8GB solo en KV cache. Por request!

"""
KV Cache Implementation para inference eficiente.
Hay dos estrategias principales: 
1. PagedAttention (vLLM) - cache por chunks de 16-64 tokens
2. Cache completo en memoria - simplicidad a costa de memoria
"""

from vllm import LLM, SamplingParams
import torch

# Inicializar modelo con vLLM (maneja KV cache automaticamente)
llm = LLM(
    model="meta-llama/Llama-2-7b-chat-hf",
    tensor_parallel_size=2,  # Usar 2 GPUs
    max_num_seqs=256,  # Maximo de secuencias en parallel
    max_num_batched_tokens=8192,  # Tokens por forward pass
)

# Para requests con prefijo compartido (ej: system prompt),
# el KV cache del prefijo se puede reutilizar!

def rag_with_prefix_caching(
    system_prompt: str,
    user_query: str,
    llm: LLM
):
    """
    RAG donde el context window se aprovecha para cachear
    el system prompt y solo procesar el query nuevo.
    
    El system prompt solo se calcula una vez, luego se cachea.
    """
    # Tokenizar system prompt (se cachea automaticamente en vLLM)
    system_tokens = llm.get_tokenizer()(system_prompt)["input_ids"]
    
    # Solo tokenizar el query del usuario
    query_tokens = llm.get_tokenizer()(user_query)["input_ids"]
    
    # La GPU reutiliza el KV cache del system prompt
    # Solo procesa los tokens nuevos del query
    full_prompt = system_prompt + "\n\nPregunta: " + user_query
    
    outputs = llm.generate([full_prompt], SamplingParams(temperature=0.7))
    return outputs[0].outputs[0].text


# Calcular savings de KV cache
def calculate_kv_cache_savings(
    prefix_length: int,
    query_length: int,
    num_layers: int = 32,
    hidden_size: int = 4096,
    bytes_per_param: float = 2.0  # FP16
):
    """
    Calcula cuántos GFLOPS nos ahorramos con KV cache.
    
    Sin cache: todo se recalcula
    Con cache: solo el query se calcula
    """
    total_tokens = prefix_length + query_length
    
    # FLOPs por layer sin cache (atencion es O(n^2))
    flops_without_cache = num_layers * (total_tokens ** 2) * hidden_size * 2
    
    # FLOPs con cache: prefijo ya está cacheado, solo query
    flops_with_cache = num_layers * (
        (prefix_length ** 2) +  # Una vez para inicializar
        (total_tokens * query_length) +  # Atencion nueva
        (prefix_length * query_length)   # Cross attention al prefijo
    ) * hidden_size * 2
    
    speedup = flops_without_cache / flops_with_cache
    
    print(f"Speedup con KV cache: {speedup:.2f}x")
    print(f"Sin cache: {flops_without_cache:.2e} FLOPs")
    print(f"Con cache: {flops_with_cache:.2e} FLOPs")
    print(f"GFLOPS ahorrados: {(flops_without_cache - flops_with_cache) / 1e9:.2f}")
    
    return speedup

# Ejemplo practico
calculate_kv_cache_savings(
    prefix_length=500,   # System prompt + few-shot examples
    query_length=100,    # Solo el query nuevo
)

Load Balancing: Cuando Un Solo Model No Suficiente

Llega un momento en que un solo modelo no da a basto. Tienes que distribuir la carga entre varias instancias. Aqui es donde la mayoría de la gente mete la pata.

import httpx
import asyncio
from typing import Optional
import hashlib

class LLMLoadBalancer:
    """
    Load balancer inteligente para multiples replicas de LLM.
    NO usa round-robin naive - eso causa problemas de cache invalidation.
    """
    
    def __init__(
        self,
        model_endpoints: list[str],
        strategy: str = "least-loaded",
        health_check_interval: int = 30,
    ):
        self.endpoints = [
            httpx.AsyncClient(base_url=url, timeout=60.0)
            for url in model_endpoints
        ]
        self.strategy = strategy
        self.request_counts = [0] * len(endpoints)
        self.endpoint_health = [1.0] * len(endpoints)  # 1.0 = healthy
        self.request_counts_lock = asyncio.Lock()
        
    async def generate(
        self,
        prompt: str,
        model: Optional[str] = None,
        **kwargs
    ) -> dict:
        """
        Envia request al endpoint menos cargado o especifica.
        
        Para prompts con contexto compartido (ej: mismos documents en RAG),
        podemos usar consistent hashing para mandarlos al mismo nodo
        y aprovechar el KV cache compartido.
        """
        if model:
            # Request para modelo especifico (ej: para experiments)
            idx = self._get_model_index(model)
            return await self._send_to_endpoint(idx, prompt, **kwargs)
        
        if self.strategy == "consistent-hash":
            # Muy util para RAG: misma pregunta va al mismo nodo
            # que tiene los documents cacheados
            idx = self._consistent_hash(prompt)
        elif self.strategy == "least-loaded":
            idx = await self._get_least_loaded()
        else:
            idx = 0
        
        return await self._send_to_endpoint(idx, prompt, **kwargs)
    
    async def _send_to_endpoint(self, idx: int, prompt: str, **kwargs) -> dict:
        """Envia request a un endpoint especifico."""
        async with self.request_counts_lock:
            self.request_counts[idx] += 1
        
        try:
            response = await self.endpoints[idx].post(
                "/v1/completions",
                json={"prompt": prompt, **kwargs}
            )
            response.raise_for_status()
            return response.json()
        finally:
            async with self.request_counts_lock:
                self.request_counts[idx] -= 1
    
    def _consistent_hash(self, prompt: str, max_nodes: int = 256) -> int:
        """
        Consistent hashing para maximizar cache hits en RAG.
        La misma pregunta siempre va al mismo nodo (si sigue activo).
        """
        hash_val = int(hashlib.md5(prompt.encode()).hexdigest(), 16)
        return hash_val % len(self.endpoints)
    
    async def _get_least_loaded(self) -> int:
        """Retorna el indice del endpoint menos cargado."""
        async with self.request_counts_lock:
            # Ponderar por salud del endpoint
            scores = [
                count / health if health > 0 else float('inf')
                for count, health in zip(self.request_counts, self.endpoint_health)
            ]
            return scores.index(min(scores))

Los 3 Errores Que El 90% Commete En Producción

Error #1: No Usar KV Cache (Duplicas Tu Costo de Inference)

El problema: Sin KV cache, cada request recalcula TODA la atención desde cero. Para un query de 100 tokens sobre un contexto de 1000 tokens, estas haciendo 1000² = 1M operaciones cuando solo necesitas 100×1000 = 100K.

La solución: Implementar PagedAttention o caching a nivel de sistema. Usar vLLM o TensorRT-LLM que manejan esto automaticamente.

# BAD: Sin cache
for request in requests:
    output = model.forward(tokens)  # Recalcula TODO cada vez
    
# GOOD: Con KV cache y batching
batcher = DynamicBatcher(max_batch_size=32, max_wait_ms=50)
while True:
    batch = await batcher.get_batch()
    if batch:
        # vLLM automaticamente guarda KV cache
        outputs = await process_batch_with_vllm(batch, engine)

Error #2: Enviar Requests Uno Por Uno (Throughput 10x Menor)

El problema: Enviar requests secuencialmente desperdicia el GPU. Un A100 puede procesar 16 secuencias en paralelo pero tu le mandas 1. Estás usando el 6% del GPU.

La solución: Implementar batching dinámico. Empezar con batches pequenos aunque sea con solo 50ms de espera. El speedup vale la pena.

# BAD: Sequencial
for prompt in prompts:
    result = await model.generate(prompt)  # GPU idle entre requests
    
# GOOD: Batch
batch = await gather(*[model.generate(p) for p in prompts])  # Todo en parallel

Error #3: No Tener Fallback Cuando La API Falla

El problema: Tu aplicacion depende 100% del LLM. Si el API de OpenAI se cae, tu app muere. El 90% no tiene estrategia de fallback.

La solución: Implementar circuit breaker y fallback a modelos mas pequeños o respuestas precalculadas.

from circuitbreaker import circuit
from functools import wraps

class LLMServiceWithFallback:
    def __init__(self):
        self.primary = OpenAIClient()  # GPT-4
        self.secondary = AnthropicClient()  # Claude
        self.tertiary = LocalModel()  # Modelo local 7B
        
    @circuit(failure_threshold=5, recovery_timeout=30)
    async def generate_with_fallback(self, prompt: str, context: str = "") -> str:
        """
        Trata de usar el mejor modelo, pero si falla,
        cae a opciones menos perfectas pero disponibles.
        """
        combined = f"Context: {context}\n\nQuestion: {prompt}" if context else prompt
        
        try:
            # Intentar GPT-4 primero
            return await self.primary.generate(combined)
        except PrimaryModelError as e:
            print(f"Primary failed: {e}, trying secondary")
            try:
                return await self.secondary.generate(combined)
            except SecondaryModelError:
                print("Secondary failed too, using local model")
                return await self.tertiary.generate(combined)
        except Exception as e:
            # Circuit breaker abierto para primary
            raise PrimaryModelError(f"Total failure: {e}")

Debugging En Producción

import logging
from prometheus_client import Counter, Histogram, Gauge
import time

# Metricas esenciales para LLM inference
REQUEST_LATENCY = Histogram(
    'llm_request_latency_seconds',
    'Latencia de requests',
    ['model', 'endpoint'],
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0, 30.0]
)

TOKEN_THROUGHPUT = Histogram(
    'llm_token_throughput',
    'Tokens procesados por segundo',
    ['model'],
    buckets=[10, 50, 100, 500, 1000, 5000]
)

BATCH_SIZE = Gauge(
    'llm_batch_size',
    'Tamaño de batch actual',
    ['model']
)

KV_CACHE_HIT_RATIO = Histogram(
    'llm_kv_cache_hit_ratio',
    'Ratio de cache hits en KV cache',
    buckets=[0, 0.25, 0.5, 0.75, 1.0]
)


class LLMObservable:
    """
    Wrapper que añade observabilidad a cualquier LLM inference.
    """
    
    def __init__(self, model, model_name: str = "default"):
        self.model = model
        self.model_name = model_name
        self.logger = logging.getLogger(f"llm.{model_name}")
        
    async def generate(self, prompt: str, **kwargs) -> dict:
        start = time.perf_counter()
        
        try:
            result = await self.model.generate(prompt, **kwargs)
            
            latency = time.perf_counter() - start
            REQUEST_LATENCY.labels(self.model_name, "generate").observe(latency)
            
            num_tokens = result.get("usage", {}).get("total_tokens", 0)
            if num_tokens > 0:
                throughput = num_tokens / latency
                TOKEN_THROUGHPUT.labels(self.model_name).observe(throughput)
            
            self.logger.info(
                f"Request completed",
                extra={
                    "latency": latency,
                    "tokens": num_tokens,
                    "throughput": throughput if num_tokens > 0 else 0,
                }
            )
            
            return result
            
        except Exception as e:
            self.logger.error(f"Request failed: {e}")
            raise

Resumen y Cierre

Hagale pues, parcero. Lo que nos queda de todo esto es algo bien simple: en producción, el modelo de ML es solo el 20% del problema. El 80% es infrastructure, caching, batching, y tener un plan cuando todo se cae.

Las lecciones clave para llevarse a casa:

  • KV Cache no es opcional: Es la diferencia entre pagar $0.001 por query y $0.05. Implementalo desde el día uno.
  • Batching dinámico > batching fijo: No esperes a llenar un batch de 64 requests. Con 50ms de espera y batches de 8-16 ya ves mejoras de 5-10x.
  • Fallback no es paranoia: OpenAI tuvo 3 outage el mes pasado. Si tu app no puede funcionar sin el, tienes un single point of failure.
  • Mide todo: Latencia, throughput, cache hit ratio, errores. No puedes mejorar lo que no mides.

En Medellín decimos que "el que no conoce el monte,以为是平 地". Para LLM production: el que no sabe de batching y caching, piensa que el modelo es todo. Pero no es así.
