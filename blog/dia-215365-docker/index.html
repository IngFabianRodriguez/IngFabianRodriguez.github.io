Hagale pues, parcero. Llegamos al Día 215 y hoy vamos a hablar de algo que en Colombia diríamos que es "el cuento de la abuela" pero en versión de datos: los Feature Stores. Sí, esos servidores de features que el 80% de los equipos de ML están recalculando constantemente porque nadie sabe que ya existían. Dejala ahí la arepa que esto está bueno.

Qué Es Un Feature Store?

Un Feature Store es un repositorio centralizado que almacena y sirve features (variables engineered) tanto para entrenamiento como para inferencia en tiempo real. Básicamente, es la "nevera" donde guardas todos los ingredientes que luego usas para cocinar tus modelos.

Componentes clave:

  • Offline Store: Almacenamiento para entrenamiento batch — usualmente un data lake o warehouse (Parquet, BigQuery, Snowflake)
  • Online Store: Base de datos de baja latencia para inference en tiempo real — Redis, DynamoDB, PostgreSQL
  • Feature Registry: Catálogo donde documentas qué features existen, de dónde vienen, cómo se calculan y quién es el dueño
  • Training Pipeline: Job que genera features históricas para entrenamiento
  • Serving Pipeline: Job que mantiene actualizadas las features online

La Matemática Detrás Del Feature Engineering Consistency

El problema fundamental que resuelve un feature store es el training-serving skew. La matemática es sencilla pero dolorosa cuando no la resuelves:

En entrenamiento, típicamente calculas una feature con una ventana temporal definida:

# Entrenamiento: feature con ventana de 7 días
user_transaction_count_7d = df.groupby('user_id')['amount'].transform(
    lambda x: x.rolling(window='7D', min_periods=1).sum()
)

En inference, si alguien calcula la misma feature con lógica diferente (o sin darse cuenta), obtienes valores distintos. El modelo aprendió con datos diferentes a los que recibe en producción. Esa diferencia es el skew:

Skew = f(features_entrenamiento) ≠ g(features_inferencia)

Un feature store garantiza que f == g, que la misma lógica se aplica en ambos lados. El framework lo hace por ti.

Implementando Un Feature Store Con Feast

Feast es el feature store open-source más popular. Vamos a ver cómo configurarlo:

# feast_repo/feature_store.yaml
project: mi_feature_store
registry: data/registry.db
provider: local
online_store:
  type: redis
  connection_string: localhost:6379
offline_store:
  type: file
   nbsppath: data/warehouse/
entities:
  - name: user
    entities:
      - name: user_id
        type: int
      - name: timestamp
        type: float
data_sources:
  - name: user_transactions_source
    type: file
    path: data/user_transactions.parquet
    timestamp_field: timestamp
feature_views:
  - name: user_transaction_features
    entities:
      - user_id
    ttl: 7 day
    schema:
      - name: user_id
        type: int
      - name: transaction_count_7d
        type: float
      - name: transaction_amount_sum_7d
        type: float
      - name: avg_transaction_amount_7d
        type: float

Registrando Features y Feature Views

from feast import FeatureStore
import pandas as pd

# Inicializar el feature store
fs = FeatureStore(repo_path="feast_repo")

# Registrar una feature view desde un DataFrame
df = pd.read_parquet("data/user_transactions.parquet")

# apply: registra en el registry
fs.apply([
    user_entity,
    user_transaction_source,
    user_transaction_view,
])

# Materialize: carga features online desde offline store
fs.materialize_incremental(
    end_date=datetime.now(),
    start_date=datetime.now() - timedelta(days=7)
)

Sirviendo Features Online vs Offline

# ONLINE: Inference en tiempo real (baja latencia)
from feast import FeatureStore

fs = FeatureStore(repo_path="feast_repo")

# Obtener features para UN usuario
feature_vector = fs.get_online_features(
    entity_rows=[{"user_id": 12345}],
    features=[
        "user_transaction_features:transaction_count_7d",
        "user_transaction_features:transaction_amount_sum_7d",
        "user_transaction_features:avg_transaction_amount_7d",
    ]
).to_dict()

# Resultado: {'transaction_count_7d': [42], 'transaction_amount_sum_7d': [1250000.0], ...}


# OFFLINE: Entrenamiento (batch, datos históricos)
training_df = fs.get_historical_features(
    entity_df=entity_df,  # DataFrame con entity keys y timestamps
    features=[
        "user_transaction_features:transaction_count_7d",
        "user_transaction_features:transaction_amount_sum_7d",
    ],
).to_df()

# Esto genera el dataset de entrenamiento con features point-in-time correctas

Los 3 Errores Más Costosos

Error 1: Feature Engineering Diferente En Training vs Inference — Training-Serving Skew

El problema: El equipo de datos calcula las features para entrenamiento en un notebook con cierta lógica (digamos, ventana de 7 días con media móvil), pero en producción el servicio de inference calcula la misma feature con lógica ligeramente diferente (ventana de 7 días corridos, sin min_periods). El modelo se entrenó con datos A pero predice con datos B. Esto hace que tu AUC sea de 0.92 en validación pero 0.67 en producción. En Colombia diríamos que "el que cogió la cosa, cogió el malecón".

El fix: Usar un feature store como Feast o Tecton donde la lógica de la feature se define UNA sola vez en el feature registry y se aplica tanto en el offline store (training) como en el online store (inference). No hay dos lógicas — hay una sola fuente de la verdad.

# ANTES (skew guarantee):
# Notebook:  df['feature'] = df.groupby('x').y.transform('mean')  # pandas mean
# API:       feature = df.groupby('x').y.mean()  #有不同的NaN处理!

# DESPUÉS (con feature store):
# Una sola definicion en feature_view.schema, Feast se encarga de materializar
# tanto para entrenamiento como para inference

Error 2: No Reusar Features Entre Modelos

El problema: El equipo A construye un modelo de churn y calcula days_since_last_login, session_count_30d, feature_eng_xyz. Meses después, el equipo B construye un modelo de propensity y recalcula las MISMAS features desde cero, probablemente con lógica ligeramente diferente. Resultado: 3 equipos calculando las mismas features 5 veces con lógicas distintas. En Colombia: "a buenas horas, mangas verdes".

El fix: El feature registry no solo almacena features — también las hace descubribles. Cuando el equipo B necesita una feature, busca en el registry primero. Si existe y sirve, se reutiliza. Si no existe, se crea UNA vez y se registra. Los feature stores tienen sistemas de búsqueda y lineage para esto.

# Buscar features en el registry
fs.list_feature_views()
fs.get_feature_view("user_transaction_features")

# Ver el lineage: de dónde viene la feature, quién la creó, cuándo se actualizó
fs.get_streamingStats("user_transaction_features:transaction_count_7d")

Error 3: No Documentar Feature Lineage

El problema: Tres meses después de deployar el modelo de fraude, alguien pregunta "¿de dónde salió esa feature de velocity_score"? Nadie sabe con certeza. ¿Viene del evento de clickstream o de la tabla de transacciones? ¿Con qué transformación? ¿Qué pasa si el equipo de datos cambia la tabla fuente y nadie lo sabe? El modelo empieza a degrade silenciosamente. En Colombia: "el que no tiene memoria, tiene olvido".

El fix: Cada feature en el registry debe tener metadata completa: nombre, descripción,owner/equipo responsable, tabla/fuente de datos original, transformación aplicada, tags de negocio, y fecha de creación. Feast soporta esto nativamente con la documentación del feature view. Tecton va más allá con approval workflows y feature SLA monitoring.

feature_view = FeatureView(
    name="fraud_detection_features",
    entities=[user_entity],
    ttl=timedelta(days=7),
    schema=[
        Field(name="velocity_score", dtype=Float32),
        Field(name="account_age_days", dtype=Int32),
    ],
    description="Features para detección de fraude. "
                "velocity_score = suma de transacciones últimas 24h / desviación estándar. "
                "Fuente: fraud_events_stream. "
                "Owner: equipo-riesgo. "
                "Tags: ['fraude', 'tiempo-real', 'critical'].",
    tags={"team": "riesgo", "model": "fraud-v2", "sla": "99.9"},
)

Resumen y Cierre

Hagale pues, como decimos en Colombia: un feature store no es solo "guardar features en una base de datos". Es tener UNA sola forma de calcularlas, documentarlas, y servirlas tanto para entrenamiento como para inference. Es eliminar el skew, evitar el retrabajo y mantener el lineage.

Feast es el punto de entrada más accesible (gratis, open source, local-first). Tecton es la versión enterprise con más features pero con costo. Para la mayoría de equipos, empezar con Feast y un Redis como online store es más que suficiente.

El que no documenta sus features, termina recalculándolas. Y en esto de datos, como en la vida: "quien no sabe de dónde viene, no sabe a dónde va".
