Dia 215/365: Docker — Andamios, capas inmutables y el plano que se reusa

3 de agosto de 2026
docker, Dockerfile

Introduccion: cuando "funciona en mi maquina" te cuesta tres deploys

Hagale pues, voy a contarte una cicatriz real. Una vez un equipo llegó a mi mesa con un modelo que corría perfecto en sus laptops (Ubuntu 22.04, CUDA 12.1, drivers propietarios actualizados el día anterior). La pregunta del deploy era inocente: "¿nos clonamos ese ambiente en el servidor?". Eran 11 librerías con versiones conflictuadas, una dependencia del sistema que solo estaba en el repo ppa:graphics-drivers/ppa, y un glibc específico.

La respuesta fue: no.

Esas son las 2:00am donde el modelo "anda" en un nodo y misteriosamente no arranca en otro nodo idéntico en hardware. Docker existe porque esa pregunta es endémica en ML: tu modelo no es solo el .pt o el .safetensors. Es Python 3.11.6, PyTorch 2.3.0+cu121, CUDA 12.1 como runtime (no driver), libcudnn 8.9, y la versión de tokenizers que alguien subió un martes.

Pilas con esto: si tu Dockerfile empieza con FROM python:3.11 y termina con COPY . ., ya estás duplicando tiempos de build por cada commit. Eso no es opinión, es aritmética de caché de layers, y la vamos a ver con pelos y señales en este artículo.

La diferencia entre un Dockerfile de 18 minutos y uno de 45 segundos no es la potencia del CI; es el orden topológico del grafo de capas. Esa vaina se modela con álgebra y se demuestra con time docker build. Vamos.

1. Que es Docker? (Y por que deberia importarte)

1.1 La analogia cotidiana: la obra con andamios

Imaginate una construcción de un edificio de 10 pisos. Cada piso necesita una capa de andamio para que los trabajadores pongan el concreto. Cuando el piso está fraguado, el andamio se desarma — no se queda. Lo que queda es el piso fraguado, la estructura real.

Hay un patrón que se repite: el mismo edificio se construye en otra ciudad (mismo plano, mismos materiales), y el andamio de cada ciudad es independiente. Pero los planos, las vigas maestras, los cimientos, son idénticos y vienen pre-fabricados al sitio de la obra.

Docker funciona así:

  • El plano de obra es el Dockerfile. Es texto. Es declarativo. Lo commiteás a Git.
  • El andamio son las capas intermedias (layers) que Docker va apilando cuando ejecuta RUN apt-get install ..., COPY model.py ., etc. Son imágenes intermedias que se cachean.
  • El piso fraguado es la imagen final (docker image). Es inmutable.
  • El edificio armado y en uso es el contenedor. Es la instancia corriendo de esa imagen.
  • El siguiente edificio en otra ciudad que arranca del piso 8 es la caché compartida entre builds. Como ya tenés los primeros 8 pisos en el almacén, no los reconstruye.

La clave: cada paso del Dockerfile deja una capa. Esas capas son inmutables. Si cambiás una capa intermedia, todo lo de arriba se reconstruye; todo lo de abajo (lo que está antes en el archivo) se reusa desde caché. El orden de las instrucciones no es estética, es control de versiones del caché de construcción.

1.2 La matematica formal: el DAG de capas y la complejidad del build

Un Dockerfile se compila a un Grafo Acíclico Dirigido (DAG) $G = (V, E)$ donde cada vértice $v_i \in V$ representa una capa y cada arista $(v_i, v_j) \in E$ representa una dependencia de tipo "$v_j$ se construye encima de $v_i$". El comando docker build clásico ejecuta este grafo en orden topológico, capa por capa, de forma esencialmente secuencial.

El conjunto de capas producidas por un Dockerfile con $n$ instrucciones es:

$$L = \{l_1, l_2, \ldots, l_n\}, \quad l_i = f_i(l_{i-1}, \Delta_i)$$

Símbolo por símbolo:

  • $L$ es el conjunto de capas producidas (salida).
  • $l_1, l_2, \ldots, l_n$ son las capas indexadas en orden topológico.
  • $l_i$ denota la capa i-ésima.
  • $f_i$ es la operación del sistema de archivos: escribir archivos, ejecutar un proceso, copiar un blob.
  • $l_{i-1}$ es la capa padre sobre la cual se construye.
  • $\Delta_i$ es el delta (cambio) introducido por la instrucción $i$.

Cada capa $l_i$ tiene un digest (SHA-256) que sirve como identificador de caché:

$$\text{cache\_hit}(l_i) = \mathbb{1}\!\left[\text{digest}(l_i^{\text{prev}}) = \text{digest stored in cache}\right]$$

Aquí $\mathbb{1}[\cdot]$ es la función indicadora: vale 1 si el digest calculado coincide con el almacenado, 0 en caso contrario. Este es el "switch" del caché binario.

El tiempo total de build $T$ es:

$$T = \sum_{i=1}^{n} t_i \cdot \mathbb{1}\!\left[\text{cache\_miss}(l_i)\right]$$

donde $t_i$ es el costo (en segundos) de ejecutar la instrucción $i$. En el peor caso (sin caché), $T_{\text{worst}} = O\left(\sum t_i\right)$, y como $t_i$ típicamente incluye pip install torch (60-180 s), apt-get install (20-60 s), COPY de modelos grandes (10-30 s), el peor caso duele. En el mejor caso (todo cacheado), $T_{\text{best}} = O(1)$ — solo se valida el digest por capa.

BuildKit, el builder moderno (default desde Docker 23.x), paraleliza la resolución del DAG. Si dos capas $l_a$ y $l_b$ no tienen dependencia entre sí, se construyen en paralelo. Esto mejora la complejidad a:

$$T_{\text{BuildKit}} = O\!\left(\max_i t_i \cdot \log \text{depth}(G)\right)$$

en el caso optimista, donde $\text{depth}(G)$ es la longitud del camino más largo del grafo. La intuición: si tenés 8 capas en paralelo con $t_{\max} = 120$ s y profundidad 4, $T_{\text{BuildKit}} \approx 120 \cdot 2 = 240$ s, contra $T_{\text{worst}} \approx \sum t_i$ que fácilmente son 800-1200 s.

2. Como Dockerfile resuelve esto por vos: UnionFS y Copy-on-Write

Docker no inventó las capas. Lo que hizo fue empaquetar UnionFS + namespaces + cgroups de Linux en algo manejable. La pieza que nos importa para entender el caché del build es Copy-on-Write (CoW).

Docker Image (multi-layer)
+------------------------------------------+
| Layer 5: COPY . .  (codigo de aplicacion)|  <-- cambia en cada commit
+------------------------------------------+
| Layer 4: RUN pip install ...             |  <-- estable si requirements.txt no cambia
+------------------------------------------+
| Layer 3: RUN apt-get install ...         |  <-- estable
+------------------------------------------+
| Layer 2: ENV DEBIAN_FRONTEND=noninter... |  <-- raramente cambia
+------------------------------------------+
| Layer 1: FROM python:3.11-slim-bookworm  |  <-- casi nunca cambia
+------------------------------------------+

Cada $l_i$ se almacena como un diff del filesystem respecto a $l_{i-1}$ usando overlay2 (el driver por defecto). Cuando ejecutás docker run, el kernel arma una vista unificada montando las capas en orden: la lectura es virtual, pero la escritura se hace en una capa writable ephemeral encima (la container layer).

El ahorro de memoria con $k$ contenedores corriendo desde la misma imagen es:

$$M_{\text{shared}} = \sum_{i=1}^{n} \text{size}(l_i) \cdot (k - 1)$$

Si tenés 50 pods sirviendo el mismo modelo desde la misma imagen de 1.5 GB, cada uno no duplica 1.5 GB en RAM; el kernel deduplica via overlayfs. Eso no es magia, es el factor $(k-1)$ verificado con docker ps --size y cat /proc//mountinfo desde el host.

3. Dockerfile: uso directo y casos de control fino

El caso directo es obvio: docker build -t modelo:v1 . y docker run -p 8080:8080 modelo:v1. Pero el control fino vive en el archivo, no en el comando. Cosas que podés manipular directo:

  • FROM: imagen base. Elegir python:3.11-slim vs python:3.11 es la diferencia entre ~145 MB y ~920 MB. Esto es aritmética: si después agregás RUN pip install torch, no duplica el Python base, lo reemplaza en una capa superior. La diferencia es lo que viaja por la red cuando hacés docker pull (especialmente doloroso en clusters con imagePullPolicy: Always).
  • COPY vs ADD: ADD tiene side effects (descomprime tarballs remotos, descarga URLs). En el 95% de los casos, usá COPY. Es determinista y predecible.
  • WORKDIR: si lo encadenás con RUN cd /algo && ..., ese cd se pierde en cada RUN nuevo (cada RUN es su propio shell). WORKDIR persiste.
  • USER: si no lo seteás, el contenedor corre como root. En producción querés un usuario no-root para reducir blast radius ante un escape.
  • ENTRYPOINT vs CMD: ENTRYPOINT define el ejecutable; CMD define los argumentos default. Para servicios, ENTRYPOINT ["python"] con CMD ["serve.py"].

4. Implementacion production-ready: un Dockerfile multi-stage para servir un modelo de ML

Vamos a hacer esto bien. El siguiente es un Dockerfile que podrías poner en producción mañana. Sección por sección.

4.1 Tipos y protocolos del Dockerfile

# syntax=docker/dockerfile:1.7

# Etapa "builder": solo existe para compilar/instalar deps.
# Imagen slim: ~145 MB vs ~920 MB de python:3.11 full.
FROM python:3.11.6-slim-bookworm AS builder

# ARG: variables de build que NO persisten en la imagen final.
ARG POETRY_VERSION=1.8.2

# ENV: viven en runtime. Críticas para comportamiento no interactivo.
ENV DEBIAN_FRONTEND=noninteractive \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

# Instalación de system deps. Esta capa cambia solo si la lista cambia.
# Si la pones al FINAL del Dockerfile, rompes el cache de pip install.
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential \
        curl \
        ca-certificates && \
    rm -rf /var/lib/apt/lists/*

# Poetry para dependency management determinista.
RUN curl -sSL https://install.python-poetry.org | python3 - --version ${POETRY_VERSION}
ENV PATH="/root/.local/bin:${PATH}"

WORKDIR /app

# Estrategia clave: copiar SOLO el manifest de dependencias primero.
# pyproject.toml cambia ~5 veces al año. El codigo cambia 50 veces al dia.
COPY pyproject.toml poetry.lock ./

# Instalar deps en un venv que luego copiamos al final.
RUN poetry config virtualenvs.in-project true && \
    poetry install --no-interaction --no-ansi --without dev --no-root

# Etapa "runtime": la imagen final. Solo trae lo necesario para correr.
FROM python:3.11.6-slim-bookworm AS runtime

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PATH="/app/.venv/bin:${PATH}"

WORKDIR /app

# Copiamos SOLO el venv desde builder. Esto es multi-stage build.
COPY --from=builder /app/.venv /app/.venv

# Usuario no-root. UID alto (10001) para no chocar con host users.
RUN groupadd -g 10001 mluser && \
    useradd -u 10001 -g mluser -M -s /usr/sbin/nologin mluser && \
    chown -R mluser:mluser /app
USER mluser

# Codigo copiado AL FINAL. Esto es deliberado: invalida cache solo aqui.
COPY --chown=mluser:mluser src/ ./src/

# Health check nativo. Si /healthz falla, Docker marca "unhealthy".
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8080/healthz || exit 1

EXPOSE 8080

ENTRYPOINT ["python", "-m", "src.serve"]

4.2 El motor principal: analisis de cada seccion

Etapa builder: existe solo para instalar dependencias. No termina en la imagen final. Multi-stage build es "andamio que se desarma". Lo crítico acá es el orden de los COPY:

  1. Copiás pyproject.toml y poetry.lock antes que el código.
  2. poetry install corre solo si esa pareja de archivos cambió.
  3. Después copiás src/, lo que invalida el cache, pero todo lo anterior se reusa.

Si el orden estuviera invertido (código primero, deps después), cada cambio a src/ invalidaría la capa de poetry install. En un proyecto con PyTorch eso son 3-5 minutos de CI por commit. No es opinión; es la fórmula $T = \sum t_i$ de la sección 1.2 con un dígito adicional por cada cache_miss.

Etapa runtime: la imagen final hereda solo el venv + el código. Tamaño esperado: ~380 MB (vs ~1.4 GB si fuera single-stage con el código + torch + cuda runtime mezclados). Eso importa porque cada GB en un registry privado (ECR, GCR, Harbor) tiene un costo recurrente, y cada GB que viaja al clúster alarga el tiempo de pod startup (Kubernetes hace pull antes de scheduling).

4.3 Utilidades de analisis y verificacion

Después de buildear, verificá el resultado:

# 1. Tamano por capa. Lo que mas pesa es lo que mas duele.
docker history modelo:v1 --no-trunc --format "{{.Size}}\t{{.CreatedBy}}"

# 2. Inspeccionar el manifest OCI (digests de cada layer).
docker inspect modelo:v1 --format '{{json .RootFS}}' | jq .

# 3. Buscar capas candidatas a excluir o squash.
# Heuristica: cualquier RUN con apt-get debe limpiar /var/lib/apt/lists.
docker run --rm modelo:v1 sh -c 'du -sh /var/lib/apt/lists/* 2>/dev/null || echo "OK: ya limpio"'

Y un linter casero para detectar los anti-patrones más comunes:

# analisis_dockerfile.py - verifica invariants del Dockerfile.
# Ejecutar: uv run python analisis_dockerfile.py ./Dockerfile
import re
import sys
from pathlib import Path


def chequeos(path: str) -> list[str]:
    """Devuelve una lista de problemas detectados en el Dockerfile."""
    lineas = Path(path).read_text().splitlines()
    errores: list[str] = []
    copied_all = False
    for i, raw in enumerate(lineas, start=1):
        s = raw.strip()
        # Cualquier COPY . . invalida cache de lo que viene despues.
        if s.startswith("COPY . ."):
            copied_all = True
        if s.startswith("RUN pip install") and copied_all:
            errores.append(
                f"L{i}: pip install DESPUES de COPY . . — "
                "invalida cache de dependencias en cada commit"
            )
        if "apt-get install" in s:
            ventana = "\n".join(lineas[max(0, i - 5): i + 1])
            if "/var/lib/apt/lists" not in ventana:
                errores.append(
                    f"L{i}: apt-get install sin limpieza de "
                    "/var/lib/apt/lists — infla la imagen ~50 MB"
                )
        if s.startswith("USER root"):
            errores.append(f"L{i}: USER root detectado — no recomendado en runtime")
    return errores


if __name__ == "__main__":
    issues = chequeos(sys.argv[1])
    if issues:
        print("\n".join(issues))
        sys.exit(1)
    print("OK: Dockerfile sin anti-patrones detectados")

Numéricamente, el costo de NO limpiar /var/lib/apt/lists/* es aproximadamente 40-60 MB por capa de apt-get install, confirmado en imágenes Debian/Ubuntu. Es una de las fugas más comunes que vas a encontrar auditando Dockerfiles legacy.

5. Ejemplos de uso en casos reales

Caso 1: servicio de inferencia para un transformer

# Servicio de inferencia. Caso: el codigo cambia 2x/semana,
# el modelo (.safetensors) cambia solo cuando hay reentrenamiento.
FROM python:3.11.6-slim-bookworm AS runtime

ENV PATH="/app/.venv/bin:${PATH}"
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY src/inference/ ./src/inference/
COPY --chown=mluser:mluser config.yaml .
HEALTHCHECK CMD curl -f http://localhost:8080/healthz || exit 1
EXPOSE 8080
ENTRYPOINT ["python", "-m", "src.inference.serve"]
# Los pesos NO van en la imagen: vienen de un volumen montado.
docker run --rm \
    -v /modelos/transformer-v3:/app/weights:ro \
    -p 8080:8080 \
    modelo:transformer-v3

La verificación numérica: los pesos (3.2 GB en este caso) están fuera de la imagen. Cuando reentrenás, solo cambia el contenido del volumen; la imagen puede quedar igual durante meses. Esto desacopla inmutabilidad del código (imagen) de mutabilidad de artefactos (volumen).

Caso 2: CI para entrenar nightly

FROM nvidia/cuda:12.1.1-cudnn8-runtime-ubuntu22.04

ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y python3.11 python3-pip && \
    rm -rf /var/lib/apt/lists/*
RUN pip install --no-cache-dir \
    torch==2.3.0+cu121 \
    --index-url https://download.pytorch.org/whl/cu121

WORKDIR /workspace
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
ENTRYPOINT ["python", "-m", "src.train"]

Acá el orden importa distinto: requirements.txt va antes porque las deps son pesadas (~3 min de install) y el código cambia mucho. Mismo principio, distinta ejecución. Verificación: dos commits consecutivos sin tocar requirements.txt deben reutilizar la capa de pip y bajar el tiempo de build de 4 min a ~30 s.

Caso 3: reproducibilidad de paper para peer review

# Para revision/peer review: la imagen debe correr bit-identico al paper.
FROM python:3.10.13-slim-bullseye
ENV PYTHONHASHSEED=0
COPY requirements.lock .
RUN pip install --no-cache-dir -r requirements.lock
COPY paper_code/ ./paper_code/
ENTRYPOINT ["python", "-m", "paper_code.reproduce"]

PYTHONHASHSEED=0 congela el hash de los set y dict (crítico para reproducibilidad entre runs en distintos sistemas). El requirements.lock (no .txt) fija versiones exactas. Sin lock, mañana pip install resuelve a otra versión y el resultado numérico cambia. La verificación es trivial: dos ejecuciones en hosts distintos deben producir los mismos metrics.json.

6. Debugging: cuando todo se va a la mierda

Problema 1: el build tarda 18 minutos en cada commit

Síntoma: $T_{\text{build}}$ se acerca a $\sum t_i$ cada vez, no respeta el cache.

Código que reproduce:

# Dockerfile "malo" — invalida cache con cualquier cambio.
FROM python:3.11
COPY . .                              # <-- primer error: invalida cache
RUN pip install -r requirements.txt  # <-- siempre se re-ejecuta
CMD ["python", "serve.py"]

Detección numérica:

docker builder prune -af       # limpiar cache para test reproducible
time docker build --no-cache -t test:v1 .   # baseline
time docker build -t test:v1 .              # segunda vez: deberia ser 5-10x mas rapido
# Si la segunda no es mas rapida, el cache esta mal.

Soluciones:

  1. Mover COPY solo-de-manifests (pyproject.toml, requirements.txt, package.json) antes de pip install. Es la regla nº1.
  2. Usar --mount=type=cache con BuildKit para cachear /root/.cache/pip entre builds sin que esa caché se incluya en la imagen.
  3. Combinar apt-get update && apt-get install -y ... && rm -rf /var/lib/apt/lists/* en una sola capa (cada RUN es una capa separada, los RUN consecutivos no comparten filesystem en build-time).

Problema 2: la imagen pesa 3.4 GB y el disco del registry está lleno

Síntoma: docker image ls muestra modelo:v1 con 3.4 GB. Causa típica: incluiste pip install torch sin multi-stage, y la imagen base tiene cuda-devel (no cuda-runtime).

Código que reproduce:

FROM nvidia/cuda:12.1.1-devel-ubuntu22.04   # <-- 5 GB base!
RUN pip install torch
COPY . .

Detección numérica: cada capa individual mayor a 100 MB merece auditoría.

docker history modelo:v1 --no-trunc --format "{{.Size}}\t{{.CreatedBy}}" | \
    awk '$1 ~ /GB$/ {print "Layer gigante: " $0}'

Soluciones:

  1. Cambiar -devel por -runtime (5 GB → 1.2 GB base). La diferencia es que -devel trae compiladores, headers y herramientas; -runtime solo lo necesario para ejecutar binarios CUDA ya compilados.
  2. Usar multi-stage build: FROM ... AS builder para compilar/instalar, FROM ... AS runtime para la imagen final. Lo que se queda en la imagen final es solo lo necesario para correr.
  3. Pasar a distroless (gcr.io/distroless/python3-debian12) o python:3.11-alpine para imágenes mínimas. Alpine tiene caveats con musl vs glibc (no recomendado si usás PyTorch con CUDA), pero para servicios Python puros es excelente: ~50 MB base.

Problema 3: "Permission denied" al escribir logs

Síntoma: tu contenedor corre como mluser (UID 10001) y no puede escribir en /app/logs/ porque la capa de imagen la creó root.

Soluciones:

  1. chown en el Dockerfile mismo: RUN chown -R mluser:mluser /app/logs.
  2. Mejor: redirigir logs a stdout (ENV PYTHONUNBUFFERED=1 ya está en el Dockerfile de la sección 4) y dejar que el orquestador (kubectl logs, CloudWatch) los capture.
  3. Si necesitás volumen persistente: docker run -v logs-vol:/app/logs con un volumen que tenga los permisos correctos, o securityContext.runAsUser en el manifiesto de Kubernetes.

7. Optimizaciones de produccion

Tecnica 1: BuildKit con cache mounts

BuildKit permite cachear dependencias entre builds sin que esa caché se incluya en la imagen final. Trade-off: requiere BuildKit habilitado (DOCKER_BUILDKIT=1 o Docker 23+ que ya lo trae por default).

# syntax=docker/dockerfile:1.7
FROM python:3.11-slim
WORKDIR /app

# El cache de pip se monta solo durante este RUN.
# No se incluye en la imagen final.
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# Codigo al final: invalida cache solo en la ultima capa.
COPY src/ ./src/

Resultado medible: build sin cache mounts ~3 min; con cache mounts en CI (segunda corrida) ~12 s. La diferencia es $T_{\text{BuildKit}}$ atacando las capas que cambian poco (las de pip install). Si querés ir más allá, podés montar /go/pkg/mod para Go, /root/.cargo/registry para Rust, /root/.npm para Node.

Tecnica 2: distroless + multi-stage para máximo endurecimiento

Para servicios donde no necesitás shell ni apt en runtime, distroless es una imagen que solo trae el runtime. No hay shell, no hay gestor de paquetes. Reduce superficie de ataque y tamaño.

FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

FROM gcr.io/distroless/python3-debian12:nonroot
COPY --from=builder /root/.local /home/nonroot/.local
COPY --from=builder /app /app
USER nonroot
WORKDIR /app
ENV PATH=/home/nonroot/.local/bin:$PATH
ENTRYPOINT ["python", "-m", "src.serve"]

Trade-off explícito: no podés hacer docker exec -it bash porque no hay shell. Vas a tener que debuggear via docker logs, sidecars (kubectl debug), o nsenter desde el host. Pero ganás que un atacante que logra RCE dentro del contenedor no puede instalar nada nuevo.

8. Conclusion: por que esto te salva el pellejo en produccion

  • El orden de las instrucciones del Dockerfile es control de versiones del cache de build. La inversa del orden natural (manifests primero, código al final) maximiza la tasa de cache hit entre commits.
  • Multi-stage build es andamio que se desarma. No mezcles la etapa de compilación con la de runtime; duplicás capas y tamaño sin darte cuenta.
  • El tamaño de la imagen es dinero que sale de tu bolsillo: cada GB en un registry privado (ECR ~$0.10/GB-mes, GCR similar, Harbor on-prem tiene costo de almacenamiento) tiene un costo recurrente; cada GB que se transfiere al cluster alarga el pod startup.
  • El cache de layers es matemática de DAG $G = (V, E)$, no opinión. Optimizar es ordenar topológicamente para maximizar el subgrafo que matchea digests previos.

Mini-checklist antes de mergear tu Dockerfile:

  • [ ] requirements.txt / pyproject.toml copiado antes del COPY . .
  • [ ] Multi-stage build cuando hay compilación o deps que no necesitás en runtime
  • [ ] USER no-root antes del ENTRYPOINT
  • [ ] HEALTHCHECK definido (el orquestador necesita saber cuándo el servicio está muerto)
  • [ ] .dockerignore excluye .git, __pycache__, *.pyc, .venv, data/raw/, notebooks/
  • [ ] apt-get install SIEMPRE con rm -rf /var/lib/apt/lists/* en la misma capa
  • [ ] Imagen base con tag específico (python:3.11.6-slim), NUNCA :latest
  • [ ] HEALTHCHECK y EXPOSE reflejan los puertos reales del servicio, no puertos "esperados"

La próxima vez que alguien en tu equipo te diga "es que Docker es lento", mandalo a leer este artículo y a calcular su propio $T = \sum_{i=1}^{n} t_i \cdot \mathbb{1}\!\left[\text{cache\_miss}(l_i)\right]$. Docker no es lento: el Dockerfile mal escrito es lento. Y esa vaina se arregla con aritmética, no con más RAM.

Y eso, parce, es la diferencia entre deployar a las 4pm o a las 4am. 🛠️
