El Problema: Todos Usan el Mismo Modelo Para Todo

Mira la realidad: la mayoría de las aplicaciones de LLM mandan TODOS los requests a GPT-4 o Claude Opus. Pero date cuenta:

  • Clasificar si un email es spam o no → lo puede hacer un modelo de 1B parámetros en 50ms
  • Extraer fechas de un documento → lo puede hacer GPT-3.5 en 200ms
  • Escribir un ensayo complejo sobre física cuántica → sí necesitas GPT-4 o Claude

Si estás usando GPT-4 ($0.03/1K tokens input) para clasificar emails que con un modelo de 7B parámetros locales ($0.00 porque es tuyo) haces igual... estás tirando el dinero.

La matemática es simple:

# Costo por 1M tokens
GPT4_TURBO_COST = 10.00   # USD
GPT35_TURBO_COST = 0.50    # USD
LOCAL_7B_COST = 0.00      # USD (si tienes el servidor)

# Si 70% de tus requests son "simples" (classification, extraction, etc)
# y procesas 1M tokens/mes:
SIMPLE_REQUESTS = 700_000  # 70%
COMPLEX_REQUESTS = 300_000  # 30%

# Opción 1: Todo GPT-4
COST_ALL_GPT4 = 1_000_000 / 1_000_000 * GPT4_TURBO_COST
# = $10.00 por millón

# Opción 2: Routing (simple -> GPT-3.5, complex -> GPT-4)
COST_ROUTED = (
    SIMPLE_REQUESTS / 1_000_000 * GPT35_TURBO_COST +
    COMPLEX_REQUESTS / 1_000_000 * GPT4_TURBO_COST
)
# = $0.35 + $3.00 = $3.35 por millón

AHORRO = ((COST_ALL_GPT4 - COST_ROUTED) / COST_ALL_GPT4) * 100
print(f"Ahorro con routing: {AHORRO:.1f}%")
# Output: Ahorro con routing: 66.5%

66.5% de ahorro. No es cualquier cosa.

Routing: La Lógica de Decidir Qué Modelo Usar

El routing puede ser:

  • Static/Rule-based: Basado en heurísticas simples (longitud del input, tipo de task, flags explícitos)
  • ML-based: Un modelo pequeño aprende a predecir qué tan difícil es un request y decide

Empecemos con lo más simple — routing basado en heurísticas — que ya te da el 80% del beneficio:

from enum import Enum
from typing import Literal

class Model(Enum):
    GPT4_TURBO = "gpt-4-turbo"
    GPT35_TURBO = "gpt-3.5-turbo"
    CLAUDE_3_HAIKU = "claude-3-haiku-200k"
    LOCAL_LLAMA = "local-llama-7b"

class RouteDecision:
    def __init__(self, model: Model, confidence: float, reasoning: str):
        self.model = model
        self.confidence = confidence
        self.reasoning = reasoning

def route_request(
    user_input: str,
    task_type: str = None,
    explicit_complexity: str = "auto"
) -> RouteDecision:
    """
    Decide qué modelo usar basándose en heurísticas.
    Returns: RouteDecision con modelo recomendado y confianza.
    """

    # Si el usuario explícitamente pidió algo simple o complejo
    if explicit_complexity == "simple":
        return RouteDecision(
            Model.GPT35_TURBO, 0.95,
            "Usuario solicitó respuesta simple"
        )
    if explicit_complexity == "complex":
        return RouteDecision(
            Model.GPT4_TURBO, 0.95,
            "Usuario solicitó análisis profundo"
        )

    # Si sabemos el tipo de tarea, routing directo
    if task_type:
        task_routing = {
            "classification": Model.LOCAL_LLAMA,      # Clasificar emails, sentimientos
            "extraction": Model.GPT35_TURBO,           # Extraer fechas, nombres, entidades
            "summarization_short": Model.GPT35_TURBO,  # Resumir documentos cortos
            "summarization_long": Model.GPT4_TURBO,    # Resumir libros enteros
            "code_generation": Model.GPT4_TURBO,       # Código complejo
            "reasoning": Model.GPT4_TURBO,             # Matemáticas, lógica
            "creative": Model.GPT4_TURBO,                # Escritura creativa
            "chat_simple": Model.GPT35_TURBO,          # Chat casual
            "chat_complex": Model.GPT4_TURBO,          # Chat con contexto largo
        }
        if task_type in task_routing:
            return RouteDecision(task_routing[task_type], 0.90, f"Task type: {task_type}")

    # Heurísticas basadas en características del input
    input_length = len(user_input)
    has_code = "```" in user_input or "def " in user_input or "function " in user_input
    has_math = any(char in user_input for char in ["∫", "∑", "lim", "∂", "√", "λ"])
    is_very_long = input_length > 10000  # > 10K caracteres

    # Scoring de complejidad
    complexity_score = 0
    if input_length > 5000: complexity_score += 2
    if input_length > 15000: complexity_score += 3
    if has_code: complexity_score += 3
    if has_math: complexity_score += 4
    if is_very_long: complexity_score += 2

    # Decisión final
    if complexity_score >= 7:
        return RouteDecision(Model.GPT4_TURBO, 0.85, f"High complexity (score={complexity_score})")
    elif complexity_score >= 4:
        return RouteDecision(Model.GPT35_TURBO, 0.80, f"Medium complexity (score={complexity_score})")
    else:
        return RouteDecision(Model.LOCAL_LLAMA, 0.75, f"Low complexity (score={complexity_score})")

# Uso
decision = route_request(
    "Extrae las fechas de esta factura: [attachment]",
    task_type="extraction"
)
print(f"Modelo: {decision.model.value}, Razon: {decision.reasoning}")
# Output: Modelo: gpt-3.5-turbo, Razon: Task type: extraction

Cascades: Si el Modelo Barato No Suficiente, Escalar

Las cascades van un paso más allá: empiezas con el modelo barato, evalúas si la respuesta es "sufficient", y si no lo es, escalas al modelo siguiente.

La idea viene de los sistemas de traducción de Google: traduces con un modelo pequeño primero, verificas si la calidad es suficiente, y si no, traduces con el grande.

from dataclasses import dataclass
from typing import Callable, Optional

@dataclass
class CascadeResult:
    model_used: str
    response: str
    escalated: bool
    escalation_reason: Optional[str] = None

class ModelCascade:
    def __init__(self):
        self.models = [
            ("local-llama-7b", 0.0),      # Gratis, rápido
            ("gpt-3.5-turbo", 0.001),      # Barato
            ("gpt-4-turbo", 0.03),         # Caro
        ]
        # Umbrales para decidir si necesitamos escalar
        self.min_confidence_threshold = 0.7
        self.min_quality_threshold = 0.6

    def generate_with_cascade(
        self,
        prompt: str,
        quality_checker: Callable[[str], float],
        max_cost_budget: float = 0.10
    ) -> CascadeResult:
        """
        Intenta con modelos de más barato a más caro.
        Solo escala si la respuesta no pasa el quality check.
        """
        cumulative_cost = 0.0

        for model_name, cost_per_token in self.models:
            # Simular generación (en realidad harías el API call aquí)
            response = self._call_model(model_name, prompt)
            cumulative_cost += cost_per_token * len(prompt.split())

            # Evaluar calidad de la respuesta
            quality_score = quality_checker(response)

            if quality_score >= self.min_quality_threshold:
                return CascadeResult(
                    model_used=model_name,
                    response=response,
                    escalated=False
                )

            # Si no pasó el check, loggear y continuar al siguiente modelo
            print(f"Model {model_name} quality={quality_score:.2f} < {self.min_quality_threshold}, escalating...")

            # Check si ya gastamos demasiado
            if cumulative_cost >= max_cost_budget:
                return CascadeResult(
                    model_used=model_name,
                    response=response,
                    escalated=True,
                    escalation_reason=f"Budget exceeded: ${cumulative_cost:.4f}"
                )

        # Si llegamos aquí, el modelo más caro dio la respuesta
        return CascadeResult(
            model_used=self.models[-1][0],
            response=response,
            escalated=True,
            escalation_reason="Complex request requiring strongest model"
        )

    def _call_model(self, model_name: str, prompt: str) -> str:
        """Placeholder para el API call real"""
        # En producción: OpenAI/Anthropic API calls
        return f"Response from {model_name}"

El quality_checker puede ser:

  • Un embedding similarity entre el prompt y la respuesta (para verificar relevancia)
  • Un classifier pequeño que evalúa si la respuesta tiene "red flags"
  • Longitud mínima/max reasoning steps
  • Un LLM pequeño como judge (meta-LLM evaluation)
def embedding_quality_check(prompt: str, response: str, threshold: float = 0.5) -> float:
    """
    Usa embeddings para verificar que la respuesta es relevante al prompt.
    Retorna score de 0-1.
    """
    from sentence_transformers import SentenceTransformer

    model = SentenceTransformer('all-MiniLM-L6-v2')

    prompt_emb = model.encode(prompt)
    response_emb = model.encode(response)

    # Similitud coseno
    similarity = np.dot(prompt_emb, response_emb) / (
        np.linalg.norm(prompt_emb) * np.linalg.norm(response_emb)
    )

    return float(similarity)

    quality_checker=lambda r: embedding_quality_check(prompt, r)

Mid-Resolution: Routing Basado en Embeddings

Un approach más sofisticado: embeddeas queries históricas y sus respuestas óptimas, y cuando llega una nueva query, encuentras la más similar y usas el mismo modelo que funcionó antes.

from sentence_transformers import SentenceTransformer
import numpy as np

class EmbeddingBasedRouter:
    """
    Routing basado en similitud de embeddings con queries conocidas.
    """
    def __init__(self):
        self.embedding_model = SentenceTransformer('all-MiniLM-L6-v2')
        # DB de queries conocidas y sus modelos óptimos
        self.known_queries = [
            {"query": "clasifica este email como spam o no spam", "model": "local-llama-7b", "quality": 0.95},
            {"query": "traduce este paragraph al ingles", "model": "gpt-3.5-turbo", "quality": 0.92},
            {"query": "escribe un email formal de negocios", "model": "gpt-3.5-turbo", "quality": 0.88},
            {"query": "analiza las implicaciones financieras de este acuerdo", "model": "gpt-4-turbo", "quality": 0.90},
            {"query": "deriva la formula de la relatividad", "model": "gpt-4-turbo", "quality": 0.93},
        ]
        self.query_embeddings = [
            self.embedding_model.encode(q["query"])
            for q in self.known_queries
        ]

    def route(self, new_query: str) -> tuple[str, float]:
        """
        Encuentra la query conocida más similar y usa el mismo modelo.
        Retorna: (model_name, confidence_score)
        """
        query_emb = self.embedding_model.encode(new_query)

        # Encontrar query más similar
        similarities = [
            np.dot(query_emb, q_emb) /
            (np.linalg.norm(query_emb) * np.linalg.norm(q_emb))
            for q_emb in self.query_embeddings
        ]

        best_idx = np.argmax(similarities)
        best_match = self.known_queries[best_idx]
        confidence = similarities[best_idx]

        return best_match["model"], float(confidence)

# Uso
router = EmbeddingBasedRouter()
model, conf = router.route("es spam este correo?")
print(f"Modelo recomendado: {model} (confianza: {conf:.2f})")
# Output: Modelo recomendado: local-llama-7b (confianza: 0.87)

Errores Comunes y Cómo Evitarlos

Error 1: No Hacer Routing y Usar GPT-4 Para Todo

El problema: Usas GPT-4 para clasificar emails, extraer fechas, resumir documentos cortos, y responder "hola". Estás pagando $0.03/1K tokens input cuando un modelo de 7B parámetros local (costo: $0) haría el trabajo igual de bien para el 70% de las requests.

La solución: Implementa routing básico basado en heuristics. No necesitas ML sofisticado — con reglas simples de tipo de tarea y longitud del input puedes cubrir el 80% de los casos. Mira tu log de requests del último mes: ¿cuántos eran realmente "complejos"? Probablemente menos del 30%.

Error 2: Routing Sin Medir Si el Modelo Barato Realmente Es Suficiente

El problema: Haces routing a GPT-3.5 para todas las tareas "simples", pero no mides calidad. Resulta que el 20% de las tasks que pensabas que eran simples en realidad necesitaban GPT-4 — y estás dando respuestas incorrectas o de baja calidad a tus usuarios sin siquiera saberlo.

La solución: Mide calidad de las respuestas con un eval set dorado. Compara la respuesta del modelo barato vs el modelo caro en un set de 100-500 queries representativas. Si el modelo barato falla en más del 5%, no es realmente "sufficient" para esa categoría.

def evaluate_routing_quality(
    eval_set: list[dict],  # {"input": str, "expected_model": str}
    router: EmbeddingBasedRouter,
    openai_fn: callable
) -> dict:
    """
    Evalúa qué tan bien está funcionando tu routing.
    Retorna accuracy (% de veces que usamos el modelo correcto).
    """
    correct = 0
    overprovisioned = 0  # GPT-4 cuando GPT-3.5 bastaba
    underprovisioned = 0  # GPT-3.5 cuando necesitábamos GPT-4

    for item in eval_set:
        model, conf = router.route(item["input"])

        if model == item["expected_model"]:
            correct += 1
        elif model in ["gpt-4-turbo"] and item["expected_model"] in ["gpt-3.5-turbo", "local-llama-7b"]:
            overprovisioned += 1
        else:
            underprovisioned += 1

    return {
        "accuracy": correct / len(eval_set),
        "overprovisioned_pct": overprovisioned / len(eval_set),
        "underprovisioned_pct": underprovisioned / len(eval_set),
    }

# Runs this monthly to tune your routing
results = evaluate_routing_quality(eval_set, router, openai.ChatCompletion.create)
print(f"Routing accuracy: {results['accuracy']:.1%}")
print(f"Over-provisioned: {results['overprovisioned_pct']:.1%}")
print(f"Under-provisioned: {results['underprovisioned_pct']:.1%}")

Error 3: Cascade Sin Proper Fallback — Experiencia Degradada

El problema: Implementas una cascade: intentas con GPT-3.5, si falla intentas GPT-4. Pero no tienes fallback cuando GPT-4 también falla o cuando el usuario tiene poor connectivity. El usuario se queda sin respuesta o con un error feo.

La solución: Todo sistema de cascade necesita tres cosas: (1) timeout bien configurado para no dejar al usuario esperando, (2) fallback a una respuesta predefinida o cacheada cuando todos los modelos fallan, y (3) logging para saber que ocurrió un failure y poder investigar.

class RobustCascade:
    def __init__(self):
        self.models = [
            ("gpt-3.5-turbo", 2.0),   # timeout 2s
            ("gpt-4-turbo", 5.0),     # timeout 5s
        ]
        self.fallback_responses = {
            "classification": "Unable to classify at this time. Please try again later.",
            "extraction": "No information could be extracted. Please rephrase your request.",
            "default": "I'm having trouble processing your request right now. Please try again in a few moments."
        }

    def generate(self, prompt: str, task_type: str = "default") -> str:
        last_error = None

        for model_name, timeout in self.models:
            try:
                response = self._call_with_timeout(
                    model_name, prompt, timeout=timeout
                )
                if response:
                    return response
            except TimeoutError as e:
                last_error = f"Timeout on {model_name}: {e}"
                print(f"WARNING: {last_error}")
                continue
            except Exception as e:
                last_error = f"Error on {model_name}: {e}"
                print(f"ERROR: {last_error}")
                continue

        # Si llegamos aquí, todo falló → fallback
        fallback = self.fallback_responses.get(task_type, self.fallback_responses["default"])
        print(f"CRITICAL: All models failed. Using fallback. Last error: {last_error}")
        return fallback

    def _call_with_timeout(self, model_name: str, prompt: str, timeout: float) -> str:
        """Simula API call con timeout"""
        import time
        time.sleep(0.1)  # Simulación
        return f"Response from {model_name}"

Resumen: Tu Checklist de Model Routing

  • Audita tus requests: Mira los logs del último mes. ¿Qué porcentaje realmente requiere GPT-4? Probablemente menos del 30%.
  • Implementa routing por heurísticas: Tipo de tarea + longitud del input + presencia de código/matemáticas. El 80% del beneficio con 20% del esfuerzo.
  • Mide calidad del modelo barato: No asumas que "más barato = suficiente". Construye un eval set y verifica.
  • Usa cascades para edge cases: Para requests borderline, empieza con modelo barato y escala solo si el quality checker lo indica.
  • Nunca sin fallback: Todo sistema de cascade debe tener respuesta predefinida cuando todo falla. El usuario no debe ver errores crudos.
  • Revisa mensualmente: Los patrones de uso cambian. Lo que hoy es "simple" quizás mañana sea "complejo" con nuevos features.
