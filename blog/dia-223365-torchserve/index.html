Dia 223/365: TorchServe — El farmacéutico que sabe despachar tu modelo a 10k RPS

11 de agosto de 2026
torchserve

Introduccion: cuando tu modelo deja de ser un notebook

Hubo una epoca, parce, en la que yo pense que con un model.eval() y un torch.save() ya estaba "production-ready". Hasta el dia que un cliente me pidio servir un clasificador de imagenes a picos de 800 RPS y mi venerable FastAPI + uvicorn se derritio como helado en agosto: cola de peticion infinita, workers de Python pegados al GIL, latencia P99 volando a 4 segundos. La moda del "envuelvelo en FastAPI y ya" funciona para demos y muere estrepitosamente en produccion.

El problema es que servir un modelo de PyTorch no es solo exponer un endpoint HTTP. Es resolver simultaneamente:

  • Versionado de modelos sin downtime.
  • Batching dinamico para inflar throughput sin reventar latencia.
  • Aislamiento de workers (un crash no tumbe el servidor entero).
  • Metricas utiles (P50, P99, requests por segundo, GPU utilization).
  • Manejo de colas con backpressure cuando la demanda excede la capacidad.

Eso es exactamente lo que hace TorchServe: un framework de serving mantenido por AWS y Meta, escrito en Java para el frontend HTTP y Python para los workers de inferencia, pensado desde el dia uno para PyTorch en produccion. En este articulo vamos a destriparlo de verdad, no la documentacion oficial bonita sino la anatomia numerica que te dice por que toma las decisiones que toma y como tunearlo cuando las cosas se ponen feas.

1. Que es TorchServe? (Y por que deberia importarte)

1.1 La analogia cotidiana

Imaginate el mostrador de una farmacia concurrida un lunes a las 7pm. La fila da la vuelta a la esquina. Cada cliente llega con una receta (un request HTTP). El farmaceutico no agarra cada receta, sale corriendo al deposito, vuelve y la entrega: no, el man tiene un sistema.

Primero, recibe varias recetas (batching), las valida (input validation en preprocess), consulta el sistema de inventario para localizar el medicamento exacto (model loading con versionado), prepara la dosis (inferencia en GPU), la empaca y entrega con la factura (postprocess + response). Mientras tanto, otro farmaceutico en la trastienda esta reponiendo stock (otro worker pre-cargado). Cada medicamento tiene un codigo unico, una ubicacion, una fecha de caducidad. El sistema lleva un conteo en tiempo real: cuantos clientes atendio por hora, tiempo promedio de despacho, cuantos se fueron sin atender.

Esa es la foto mental de TorchServe. Tu modelo es el "medicamento", el frontend Java es el mostrador que habla HTTP, los workers Python son los farmaceuticos, el model_store es el deposito con las cajas (archivos .mar), y los endpoints de metricas son el dashboard de gestion.

1.2 La matematica formal con KaTeX, simbolo por simbolo

Ahora vamos al modelo numerico. Servir un modelo es esencialmente resolver un problema de optimizacion multi-objetivo: maximizar throughput $\Theta$ sujeto a una cota de latencia $L_{max}$.

Definimos:

  • $B$ = tamano del batch (cantidad de requests agrupados).
  • $t_{setup}$ = costo fijo por batch (transferencia CPU$\to$GPU, kernel launch, allocacion). Independiente de $B$.
  • $t_{sample}$ = tiempo de inferencia por muestra individual.
  • $M_{model}$ = memoria fija del modelo cargado.
  • $M_{sample}$ = memoria adicional por cada muestra en el batch.

El tiempo total de un batch es aproximadamente:

$$T_{batch}(B) = t_{setup} + B \cdot t_{sample}$$

El throughput (requests/segundo) que entrega TorchServe en estado estable es:

$$\Theta(B) = \frac{B}{T_{batch}(B)} = \frac{B}{t_{setup} + B \cdot t_{sample}}$$

Cuando $B \to \infty$, el throughput asintotico es $\lim_{B \to \infty} \Theta(B) = \frac{1}{t_{sample}}$. Es decir, el techo fisico lo dicta el costo por muestra, no el setup. Eso es justo lo que hace TorchServe con su batch_size y max_batch_delay: te deja empujar $B$ hacia ese limite sin tener que reescribir tu handler.

La latencia por request individual dentro de un batch de tamano $B$ es:

$$L_{req}(B) = \frac{T_{batch}(B)}{B} = \frac{t_{setup}}{B} + t_{sample}$$

Y la memoria consumida por el worker es:

$$M_{worker}(B) = M_{model} + B \cdot M_{sample}$$

Las tres ecuaciones describen el triangulo de hierro del serving: subir $B$ mejora $\Theta$ y baja $L_{req}$, pero te sube $M_{worker}$. Ajustar TorchServe es moverte en esa superficie.

2. Como TorchServe resuelve esto por vos

La arquitectura se divide en tres procesos bien separados:

+--------+      HTTP      +-------------+   IPC    +------------+
| Client |  ───────────►  |  Frontend   | ◄──────► |  Worker 1  |
+--------+   :8080        |  (Java)     |          |  (Python)  |
                           +-------------+          +------------+
                                  │                     │
                                  │ IPC                │ IPC
                                  ▼                     ▼
                           +-------------+          +------------+
                           |  Worker 2   |          |  Worker N  |
                           |  (Python)   |          |  (Python)  |
                           +-------------+          +------------+
                                  ▲
                                  │
                           +-------------+
                           |  Model      |
                           |  Store      |
                           |  (.mar)     |
                           +-------------+
  • Frontend (Java, puerto 8080/8081): maneja HTTP, conexion keep-alive, batching, enrutamiento a workers. Esta en Java porque el GIL de Python no escala para mantener miles de conexiones concurrentes abiertas.
  • Workers (Python): ejecutan tu handler. Cada worker es un proceso independiente con su propio modelo cargado. Si uno se cae, los demas siguen.
  • Model Store: directorio con archivos .mar (Model ARchive). Cada .mar contiene el modelo serializado, el handler y dependencias opcionales.

El flujo de un request es:

  1. Llega el HTTP request al frontend (puerto 8080).
  2. El frontend lo encola en el buffer de batching del modelo destino.
  3. Cuando se llena el batch o expira max_batch_delay, el frontend serializa el batch y lo manda via IPC al worker disponible.
  4. El worker llama handler.handle(data, context).
  5. La respuesta viaja de regreso por IPC y el frontend responde al cliente.

Mientras tanto, el endpoint de management (puerto 8081) te permite registrar, escalar, desregistrar y describir modelos sin reiniciar el servidor.

3. TorchServe: Uso Directo y Casos de Control Fino

El flujo minimo para poner un modelo en pie es:

# 1. Instalar
pip install torchserve torch-model-archiver torch-workflow-archiver

# 2. Empacar el modelo en un .mar
torch-model-archiver \
  --model-name resnet50 \
  --version 1.0 \
  --serialized-file resnet50.pt \
  --handler image_classifier \
  --export-path model_store

# 3. Arrancar el servidor
torchserve --start \
  --model-store model_store \
  --models resnet50=resnet50.mar \
  --disable-token-auth \
  --enable-model-api

# 4. Probar
curl -X POST http://127.0.0.1:8080/predictions/resnet50 \
     -T kitten.jpg

Eso es lo que dice el README. En la realidad, ese image_classifier por defecto se queda corto rapido, mira por que en la siguiente seccion.

4. Implementacion Production-Ready: handler para un clasificador BERT

4.1 Tipos y protocolos

TorchServe define contratos estrictos para los datos que entran y salen del handler:

  • Input: lista de diccionarios [{ "data": , "target": }].
  • Output: lista de diccionarios JSON-serializables.
  • Context: objeto con manifest (metadata del modelo), system_properties (rutas, device info), y metodos como request_ids, get_request_header.

Si tu handler devuelve algo que no sea JSON-serializable, TorchServe responde con 500 Internal Server Error y un mensaje criptico. Esa es una cicatriz mia.

4.2 El motor principal

Aqui va un handler completo, production-grade, para un clasificador de texto con HuggingFace:

# bert_classifier_handler.py
import json
import logging
import os
import time
from typing import Any, List

import torch
from transformers import AutoModelForSequenceClassification, AutoTokenizer
from ts.torch_handler.base_handler import BaseHandler

logger = logging.getLogger(__name__)

class BERTSentimentHandler(BaseHandler):
    """Handler production-grade para BERT sentiment con batching dinamico."""

    def initialize(self, context):
        """
        Se ejecuta UNA vez por worker al cargar el modelo.
        Aqui cargas pesos, tokenizers, cualquier artefacto pesado.
        NO hagas I/O bloqueante aqui fuera de lo necesario.
        """
        properties = context.system_properties
        self.device = torch.device(
            "cuda" if torch.cuda.is_available() else "cpu"
        )
        model_dir = properties.get("model_dir")

        # Carga serialized file (state_dict o TorchScript)
        serialized = context.manifest["model"]["serializedFile"]
        model_path = os.path.join(model_dir, serialized)

        # Leemos config auxiliar (max_length, labels) que empacamos con --extra-files
        with open(os.path.join(model_dir, "handler_config.json")) as f:
            cfg = json.load(f)

        self.max_length = int(cfg.get("max_length", 128))
        self.labels = cfg["labels"]
        self.threshold = float(cfg.get("threshold", 0.5))

        # Tokenizer y modelo. Usamos from_pretrained del directorio del .mar
        self.tokenizer = AutoTokenizer.from_pretrained(model_dir)
        self.model = AutoModelForSequenceClassification.from_pretrained(model_dir)
        self.model.to(self.device)
        self.model.eval()

        # Warmup: una pasada para forzar lazy CUDA kernels (importante para P99)
        with torch.no_grad():
            dummy = self.tokenizer(
                ["warmup"], return_tensors="pt",
                padding="max_length", truncation=True,
                max_length=self.max_length
            ).to(self.device)
            _ = self.model(**dummy)

        self.initialized = True
        logger.info(
            "BERTSentimentHandler listo en %s, max_length=%d, labels=%s",
            self.device, self.max_length, self.labels,
        )

    def preprocess(self, data: List[dict]) -> torch.Tensor:
        """
        Recibe lista cruda de requests. TorchServe ya los agrupa en un batch
        segun batch_size y max_batch_delay configurados en el Management API.
        """
        texts = []
        for row in data:
            body = row.get("data") or row.get("body")
            if isinstance(body, (bytes, bytearray)):
                body = body.decode("utf-8")
            if isinstance(body, str):
                obj = json.loads(body)
                texts.append(obj["text"])
            elif isinstance(body, dict):
                texts.append(body["text"])
            else:
                raise ValueError(f"Tipo de input no soportado: {type(body)}")

        encoded = self.tokenizer(
            texts,
            return_tensors="pt",
            padding=True,
            truncation=True,
            max_length=self.max_length,
        ).to(self.device)
        return encoded

    def inference(self, model_input, *args, **kwargs):
        """Forward pass. NO uses grad, NO imprimas logs por request."""
        with torch.no_grad():
            logits = self.model(**model_input).logits
        return logits

    def postprocess(self, inference_output) -> List[dict]:
        """Convierte logits a probabilidades y aplica umbral."""
        probs = torch.softmax(inference_output, dim=-1).cpu().tolist()
        results = []
        for p in probs:
            idx = int(max(range(len(p)), key=lambda i: p[i]))
            results.append({
                "label": self.labels[idx],
                "score": float(p[idx]),
                "all_scores": {l: float(s) for l, s in zip(self.labels, p)},
            })
        return results

    def handle(self, data, context):
        """
        Punto de entrada. Si overrideas este metodo (como aqui, para medir
        latencia por fase), NO olvides llamar a las tres fases.
        """
        t0 = time.perf_counter()
        pre = self.preprocess(data)
        t1 = time.perf_counter()
        out = self.inference(pre)
        t2 = time.perf_counter()
        result = self.postprocess(out)
        t3 = time.perf_counter()
        context.metrics.add_time(
            "PreprocessTime", t1 - t0, None, "ms"
        )
        context.metrics.add_time(
            "InferTime", t2 - t1, None, "ms"
        )
        context.metrics.add_time(
            "PostprocessTime", t3 - t2, None, "ms"
        )
        return result

El handler_config.json que va dentro del .mar:

4.3 Utilidades de analisis y verificacion

Una vez levantado, los endpoints de management son tus ojos:

# Describir modelo cargado y su configuracion
curl http://127.0.0.1:8081/models/bert_sentiment

# Escalar workers en caliente (cero downtime)
curl -X PUT "http://127.0.0.1:8081/models/bert_sentiment?min_worker=2&max_worker=8&number_gpu=2"

# Metricas Prometheus-style
curl http://127.0.0.1:8082/metrics

# Desregistrar version 1.0, subir 2.0 con zero-downtime
curl -X DELETE "http://127.0.0.1:8081/models/bert_sentiment/1.0"
curl -X POST "http://127.0.0.1:8081/models?model_name=bert_sentiment&url=bert_sentiment_v2.mar&initial_workers=2"

Las metricas criticas que tienes que vigilar:

Metrica Que te dice
Requests2XX Tasa de exito. Caida = problema del modelo o del input.
ts_inference_requests_total RPS real por modelo.
CPUUtilization, GPUUtilization Saturacion de hardware. >85% sostenido = subir workers.
QueueTime Tiempo que el request espero en el buffer de batching. Crece = batch_size muy agresivo.
WorkerThreadTime, WorkerLoadTime Cuanto tarda en arrancar un worker. Util para cold-start.

5. Ejemplos de Uso en Casos Reales

Caso 1: Inferencia single-image con ResNet50

Prediccion directa, baja latencia, sin estado.

# En el cliente
import requests, base64

with open("perro.jpg", "rb") as f:
    img_b64 = base64.b64encode(f.read()).decode()

resp = requests.post(
    "http://api.internal/predictions/resnet50",
    json={"body": img_b64},
    timeout=2.0,
)
resp.raise_for_status()
print(resp.json())  # [{"label": "golden_retriever", "score": 0.94}]

Verificacion numerica: si batch_size=1, max_batch_delay=10, tu latencia esperada es $L_{req}(1) = t_{setup} + t_{sample}$. Para ResNet50 en una A100, $t_{sample} \approx 4$ ms y $t_{setup} \approx 1.5$ ms. Eso te da una mediana de ~5.5 ms.

Caso 2: Clasificador BERT con batching dinamico (alto throughput)

# Registrar con batching agresivo
curl -X POST "http://127.0.0.1:8081/models?url=bert_sentiment.mar\
&model_name=bert_sentiment\
&batch_size=32\
&max_batch_delay=50\
&initial_workers=4"

Con batch_size=32 y BERT-base en GPU, $T_{batch}(32) \approx 5 + 32 \cdot 6 = 197$ ms (medido en produccion). Eso te da $\Theta(32) = \frac{32}{0.197} \approx 162$ RPS por worker. Con 4 workers paralelos y 2 GPUs, ~640 RPS estables. A batch_size=1 el mismo worker daba ~165 RPS, asi que el batching te cuadruplica el throughput a cambio de subir la mediana de latencia de ~6 ms a ~6 ms (porque el request promedio en el batch espera solo su tajada). Eso es la magia de la ecuacion $L_{req}(B) = \frac{t_{setup}}{B} + t_{sample}$: el termino fijo se diluye.

Caso 3: Multi-modelo en el mismo servidor

torchserve --start \
  --model-store model_store \
  --models bert=bert.mar,gpt2=gpt2.mar,resnet=resnet.mar \
  --disable-token-auth \
  --enable-model-api

curl -X POST http://127.0.0.1:8080/predictions/gpt2 -d '{"prompt":"Habia una vez"}'
curl -X POST http://127.0.0.1:8080/predictions/resnet -T imagen.jpg

Cada modelo corre en su propio pool de workers con su propia configuracion de batching. Si uno se cae, los demas siguen respondiendo. Esa es una propiedad que en FastAPI + uvicorn tienes que implementar a mano y siempre queda con bugs.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: OOM en el worker despues de 30 minutos

Sintoma: el worker muere, el frontend lo reemplaza, muere el reemplazo. Los logs muestran CUDA out of memory.

Deteccion numerica: en el handle, loguea el uso de GPU antes y despues de cada batch:

def inference(self, model_input, *args, **kwargs):
    if torch.cuda.is_available():
        alloc = torch.cuda.memory_allocated() / 1e9
        reserved = torch.cuda.memory_reserved() / 1e9
        logger.info("GPU mem: alloc=%.2fGB reserved=%.2fGB", alloc, reserved)
    with torch.no_grad():
        return self.model(**model_input).logits

Soluciones reales:

  1. Reducir batch_size hasta que $M_{worker}(B)$ quepa con margen del 20%.
  2. Llamar torch.cuda.empty_cache() en postprocess si tu modelo genera grafos intermedios enormes (comun en transformers con attention largo).
  3. Anadir torch.backends.cudnn.benchmark = True en initialize si tu input shape es fijo. Ahorra memoria fragmentada.
  4. Limitar el largo de secuencia con max_length agresivo. Es la palanca de mayor impacto en BERT.

Problema 2: P99 de latencia 10x peor que P50

Sintoma: P50 estable en 8 ms pero P99 salta a 80 ms aleatoriamente.

Deteccion: el culprit suele ser el max_batch_delay mal calibrado. Si vale 100 ms, hay requests que esperan 100 ms completos para que llegue un batch de tamano completo.

# Inserta esto en initialize para monitorear QueueTime
import ts  # viene con torchserve
# Luego consulta: curl http://127.0.0.1:8082/metrics | grep QueueTime

Soluciones:

  1. Bajar max_batch_delay hasta que P99 se acerque a P50. Para latency-sensitive, ponlo en 5-10 ms.
  2. Subir batch_size solo si tienes RPS suficiente para llenar batches rapidamente. Si tu trafico promedio es 5 RPS, un batch_size=64 nunca se llena y solo te suma delay.
  3. Aislar modelos grandes en su propio torchserve instance, para que un pico en BERT no afecte P99 de ResNet.

Problema 3: El modelo actualizado no se esta cargando

Sintoma: registraste v2.0 pero las predicciones siguen siendo las de v1.0.

Deteccion numerica:

curl http://127.0.0.1:8081/models/bert_sentiment
# Revisa "modelVersion" en el JSON de respuesta

Causa tipica: cuando registras dos versiones del mismo modelo sin desregistrar la anterior, TorchServe puede mantener workers de v1 sirviendo hasta que se desregistre explicitamente. Esa vaina pasa mas de lo que uno quisiera admitir.

Soluciones:

  1. Setear synchronous=true al registrar v2 para esperar el warmup antes de devolver 200.
  2. Bajar initial_workers de v1 a 0 antes de subir v2 con PUT /models/bert_sentiment?min_worker=0.
  3. Versionado explicito por URL: usar predictions/bert_sentiment/2.0 en vez del default.

7. Optimizaciones de Produccion

Optimizacion 1: TorchScript + JIT para librar el GIL del handler

Si tu handler pasa mucho tiempo en self.tokenizer(...) (que es Python puro), todo el worker queda bloqueado porque Python tiene GIL. Convierte el modelo a TorchScript:

import torch

model = AutoModelForSequenceClassification.from_pretrained("modelo")
traced = torch.jit.trace(
    model,
    example_inputs["input_ids"],
    example_kwarg_inputs={"attention_mask": example_inputs["attention_mask"]},
)
torch.jit.save(traced, "model_scripted.pt")

Empacalo con --serialized-file model_scripted.pt y --handler bert_classifier_handler.py. En el handler:

self.model = torch.jit.load(model_path, map_location=self.device).eval()

Medicion real: en BERT-base, pasar de eager a TorchScript reduce t_sample de ~7 ms a ~5 ms. Es ~30% de mejora en throughput con cero cambio de arquitectura.

Trade-off: si tu modelo tiene control flow dinamico (lengths variables, padding variable), el trace puede fallar o producir grafos suboptimos. En ese caso usa torch.jit.script o vuelve a eager pero compila el modelo con torch.compile() (PyTorch 2.0+).

Optimizacion 2: Auto-scaling reactivo via Management API

No dejes initial_workers fijo. Mete un script que escuche las metricas y ajuste:

# autoscaler.py - corre como sidecar
import requests, time, statistics

MGMT = "http://127.0.0.1:8081"
MODEL = "bert_sentiment"
TARGET_QUEUE_MS = 20

while True:
    metrics = requests.get("http://127.0.0.1:8082/metrics").text
    queue_time = [
        float(line.split()[-2])
        for line in metrics.splitlines()
        if line.startswith("ts_queue_time")
    ]
    if not queue_time:
        time.sleep(10); continue
    p95 = statistics.quantiles(queue_time, n=20)[18] * 1000
    info = requests.get(f"{MGMT}/models/{MODEL}").json()
    workers = info[0]["workers"]

    if p95 > TARGET_QUEUE_MS and workers < info[0]["maxWorkers"]:
        workers += 1
    elif p95 < TARGET_QUEUE_MS / 3 and workers > info[0]["minWorkers"]:
        workers -= 1

    requests.put(f"{MGMT}/models/{MODEL}?min_worker={workers}&max_worker={workers}")
    time.sleep(15)

Trade-off: el polling cada 15s introduce 15s de reaccion ante picos. Si necesitas reaccion sub-segundo, lo correcto es integrar ts.metrics directamente con Prometheus + AlertManager + K8s HPA, no hacer scraping en Python.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

Si llegaste hasta aca, ya tienes la imagen completa. TorchServe no es magia, es ingenieria explicita: separa el frontend HTTP (Java) del trabajo de inferencia (Python), te da batching dinamico configurable, workers aislables, metricas reales y un protocolo claro para handlers custom. Nada de eso lo inventas en una noche con FastAPI.

Mini-checklist antes de poner tu modelo en produccion con TorchServe:

  • Handler con initialize, preprocess, inference, postprocess separados y midiendo tiempo por fase.
  • Warmup explicito en initialize (una pasada con dummy input) para forzar CUDA kernel compilation.
  • max_length o input_shape fijos para que cudnn.benchmark haga su trabajo.
  • batch_size calibrado contra tu RPS real, no contra un escenario optimista.
  • max_batch_delay agresivo (5-50 ms) para workloads sensibles a latencia.
  • Metricas P50/P95/P99 y QueueTime en tu dashboard, no solo RPS agregado.
  • Autoscaling basado en metricas, no en cron.
  • Pruebas de carga con locust o wrk antes de subir a produccion, con el mismo batch_size que vas a usar en vivo.

De una, no es el framework mas hipster del ecosistema (ahí estan BentoML, Triton, Ray Serve), pero es el unico con integracion oficial de PyTorch, mantenimiento activo de AWS/Meta y la robustez de haber servido billones de requests en produccion antes de que tu startup abriera el slack. Pilas con eso, y a servir modelos como gente.
