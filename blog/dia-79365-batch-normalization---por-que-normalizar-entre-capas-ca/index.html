La Intro que el 85% Se Salta

Parcero, ¿sabes qué pasó cuando una empresa fintech me contrató para revisar su modelo de detección de fraude? Tenían un modelo con 97% de accuracy. Brillante, ¿no? Cuando excavé un poco más, descubrí que su dataset tenía 97% de transacciones legítimas y 3% de fraude. Su "modelo brillante" predecía "legítimo" para TODO. Accuracy de 97% pero detectaba cero fraudes. Ese modelo valía exactamente $0.

Ahí aprendí que accuracy es una métrica mentirosa cuando hay desbalance de clases. Y que precision, recall, y F1-score son las métricas reales que necesitas conocer. El 85% mira accuracy y se declara ganador, pero cuando el negocio tiene costos asimétricos (un fraude cuesta $500, un false positive cuesta $5), la historia es completamente diferente.

Hoy: todas las métricas que el 85% malinterpreta y cómo implementarlas correctamente.

La Matriz de Confusión: Tu Punto de Partida

Antes de hablar de métricas, necesitamos la matriz de confusión. Para un problema binario (fraude sí/no, spam sí/no):

$$\begin{pmatrix} \text{TN} & \text{FP} \\ \text{FN} & \text{TP} \end{pmatrix}$$

Donde:

  • TN (True Negative): Predijimos negativo y era negativo — bien
  • FP (False Positive): Predijimos positivo pero era negativo — alarma falsa
  • FN (False Negative): Predijimos negativo pero era positivo — missed
  • TP (True Positive): Predijimos positivo y era positivo — bien

Para multiclase, la matriz se expande a $C \times C$ donde $C$ es el número de clases.

Accuracy: La Métrica Mentirosa

$$\text{Accuracy} = \frac{\text{TP} + \text{TN}}{\text{TP} + \text{TN} + \text{FP} + \text{FN}}$$

Accuracy es la proporción de predicciones correctas. Su problema: es terrible cuando las clases están desbalanceadas. Si tienes 97% negativo y 3% positivo, un modelo que predice TODO negativo tiene 97% accuracy pero cero utilidad práctica.

Cuándo es útil: Clases balanceadas, o cuando el costo de FP y FN es simétrico.

Precision: ¿Cuántas de mis predicciones positivas son correctas?

$$\text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}}$$

Precision responde: "de todas las veces que dije positivo, ¿cuántas realmente lo eran?" Alta precision = bajo false positive rate. En detección de spam: si tienes precision 90%, de cada 10 emails que marcaste como spam, 9 realmente eran spam y 1 era legítimo (terrible para el usuario).

Cuándo maximizar precision: Cuando los FP son Costly (e.g., spam detection donde marcar un email importante como spam es muy malo, o en sistemas médicos donde un falso positivo causa estrés y procedimientos innecesarios).

Recall: ¿Cuántos de los positivos reales encontré?

$$\text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}}$$

Recall responde: "de todos los positivos que existían, ¿cuántos encontré?" Alta recall = bajo false negative rate. En detección de cáncer: si tienes recall 95%, detectaste el 95% de los cánceres reales. El 5% que te perdiste son personas con cáncer que no fueron detectadas — eso es un costo enorme.

Cuándo maximizar recall: Cuando los FN son Costly (e.g., detección de enfermedades, detección de fraude, seguridad — perder un caso positivo es peor que investigar un falso positivo).

F1-Score: El Balance Entre Precision y Recall

$$\text{F1} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$$

F1 es la media armónica de precision y recall. ¿Por qué media armónica y no media aritmética? Porque la media armónica penaliza más los casos donde una de las dos métricas es baja. Si precision=1.0 y recall=0.0, la media aritmética sería 0.5 pero F1 sería 0.0 — refleja mejor que el modelo es inútil.

Cuándo usar F1: Cuando quieres balance entre precision y recall y las clases pueden estar desbalanceadas. F1 es la métrica default cuando no sabes qué optimizar.

Código Production-Grade

import logging
import numpy as np
import torch
from dataclasses import dataclass
from typing import Literal
from sklearn.metrics import (
    accuracy_score, precision_score, recall_score, f1_score,
    confusion_matrix, classification_report,
    roc_auc_score, precision_recall_curve, average_precision_score
)

logger = logging.getLogger(__name__)


@dataclass
class MetricsResult:
    accuracy: float
    precision: float
    recall: float
    f1: float
    tn: int; fp: int; fn: int; tp: int
    support_pos: int; support_neg: int
    roc_auc: float | None = None
    pr_auc: float | None = None


class BinaryClassificationMetrics:
    """Métricas completas para clasificación binaria con logging."""

    def __init__(self, threshold: float = 0.5):
        self.threshold = threshold

    def compute(
        self,
        y_true: np.ndarray,
        y_prob: np.ndarray | None = None,
        y_pred: np.ndarray | None = None,
    ) -> MetricsResult:
        # Si tenemos probabilidades, threshold
        if y_prob is not None:
            y_pred = (y_prob >= self.threshold).astype(int)
        elif y_pred is None:
            raise ValueError("Provide either y_prob or y_pred")

        # Métricas base
        acc = accuracy_score(y_true, y_pred)
        prec = precision_score(y_true, y_pred, zero_division=0)
        rec = recall_score(y_true, y_pred, zero_division=0)
        f1 = f1_score(y_true, y_pred, zero_division=0)

        # Matriz de confusión
        tn, fp, fn, tp = confusion_matrix(y_true, y_pred, labels=[0, 1]).ravel()

        result = MetricsResult(
            accuracy=acc, precision=prec, recall=rec, f1=f1,
            tn=tn, fp=fp, fn=fn, tp=tp,
            support_pos=int(np.sum(y_true == 1)),
            support_neg=int(np.sum(y_true == 0)),
        )

        # AUC solo si tenemos probabilidades
        if y_prob is not None:
            try:
                result.roc_auc = roc_auc_score(y_true, y_prob)
                result.pr_auc = average_precision_score(y_true, y_prob)
            except ValueError:
                pass

        return result

    def log_report(self, result: MetricsResult, prefix: str = ""):
        p = f"{prefix}: " if prefix else ""
        logger.info(f"{p}Accuracy={result.accuracy:.3f} | "
                   f"P={result.precision:.3f} R={result.recall:.3f} F1={result.f1:.3f}")
        logger.info(f"{p}Confusion: TN={result.tn} FP={result.fp} FN={result.fn} TP={result.tp}")
        if result.roc_auc is not None:
            logger.info(f"{p}ROC-AUC={result.roc_auc:.3f} | PR-AUC={result.pr_auc:.3f}")

    def find_optimal_threshold(
        self,
        y_true: np.ndarray,
        y_prob: np.ndarray,
        metric: Literal['f1', 'recall', 'precision'] = 'f1',
    ) -> float:
        """Encuentra el threshold que maximiza una métrica."""
        thresholds = np.linspace(0.01, 0.99, 99)
        best_score, best_th = -1, 0.5

        for th in thresholds:
            y_p = (y_prob >= th).astype(int)
            if metric == 'f1':
                score = f1_score(y_true, y_p, zero_division=0)
            elif metric == 'recall':
                score = recall_score(y_true, y_p, zero_division=0)
            else:
                score = precision_score(y_true, y_p, zero_division=0)

            if score > best_score:
                best_score, best_th = score, th

        self.threshold = best_th
        logger.info(f"Optimal threshold={best_th:.3f} for {metric}={best_score:.3f}")
        return best_th


if __name__ == '__main__':
    np.random.seed(42)
    y_true = np.array([1]*50 + [0]*950)  # 5% positive class
    y_prob = np.random.rand(1000) * (y_true * 0.8 + 0.2)  # noisy probabilities

    metrics = BinaryClassificationMetrics(threshold=0.5)
    result = metrics.compute(y_true, y_prob)
    metrics.log_report(result, "Imbalanced dataset")

    optimal_th = metrics.find_optimal_threshold(y_true, y_prob, 'f1')
    result_opt = metrics.compute(y_true, y_prob)
    metrics.log_report(result_opt, "With optimal threshold")

Errores Comunes

Error 1: Solo mirar accuracy en datasets desbalanceados

Este es el error que costing empresas millones. En un dataset con 95% negativos, un modelo que predice todo negativo tiene 95% accuracy pero es completamente inútil. El 85% ve "95% accuracy" y celebra.

Fix: SIEMPRE mira la matriz de confusión primero. Luego precision, recall, y F1 por clase. Si las clases están desbalanceadas, accuracy no te dice nada útil.

Error 2: Mezclar precision/recall de diferentes clases

En problemas multiclase, sklearn te da precision/recall por clase y dos promedios: macro y weighted. "Macro avg" promedia las métricas de cada clase por igual (1/num_classes cada una). "Weighted avg" pesa por el support (número de samples de cada clase). Si tus clases están desbalanceadas, la métrica que te importa es weighted avg, no macro avg.

Fix: Para problemas desbalanceados, mira siempre weighted avg y la métrica de la clase minoritaria específicamente.

Error 3: No distinguir entre precision y recall en la toma de decisiones

El 85% sabe que "precision y recall son importantes" pero no sabe cuál optimizar en su contexto específico. ¿Tu costo principal es el ruido (FP) o el missed (FN)? Si es FP → maximizar precision. Si es FN → maximizar recall. Si no estás seguro → maximizar F1.

Fix: Antes de entrenar, define qué te duele más: un falso positivo (FP) o un falso negativo (FN). Eso determina qué métrica optimizar en tu classification_report.

Error 4: No usar ROC-AUC ni PR-AUC para modelos con probabilidades

Si tienes un modelo que output probabilities (no solo predicciones binarias), accuracy, precision, recall y F1 todas dependen de un threshold arbitrario (típicamente 0.5). ROC-AUC y PR-AUC te dan una medida de calidad del modelo INDEPENDIENTE del threshold.

Fix: Si tu modelo output probabilidades, siempre calcula ROC-AUC (o PR-AUC si las clases están muy desbalanceadas) como métrica de calidad global del modelo. Úsalas para comparar modelos, no solo para elegir threshold.

Resumen del Día

  • Accuracy: Proporción de predicciones correctas. Mala para clases desbalanceadas.
  • Precision: De las predicciones positivas, ¿cuántas eran correctas? Minimizar FP.
  • Recall: De los positivos reales, ¿cuántos encontré? Minimizar FN.
  • F1: Media armónica de P y R. Balance entre ambos. Buena para desbalance.
  • Confusion Matrix: TN/FP/FN/TP. La base de todo. Mírala SIEMPRE primero.
  • ROC-AUC: Calidad del modelo independiente del threshold. Para comparar modelos.
  • PR-AUC: Mejor que ROC-AUC cuando las clases están muy desbalanceadas.
  • Support: Número de samples por clase. Crítico para interpretar métricas.
  • Threshold optimization: Encuentra el threshold que maximiza tu métrica objetivo.

El Cierre

Parcero, la próxima vez que alguien te diga "tenemos 97% de accuracy", pregúntales: "¿Y qué porcentaje de tu dataset es la clase positiva? ¿Cuántos falsos negativos tienes? ¿Cuál es tu ROC-AUC?" Si no te pueden responder esas preguntas, su modelo es tan útil como uno que predice todo negativo.

Esa vaina de que "accuracy es la métrica queenmporta" es una mentira que nos hemos contado colectivamente. En producción, lo que importa es qué tipo de error te cuesta más. Enfraude, los FN son caros. En spam, los FP son caros. En diagnóstico médico, ambos son caros pero por razones diferentes. Conoce tu dominio y elige la métrica correcta. ¡Nos vemos en el día 80!
