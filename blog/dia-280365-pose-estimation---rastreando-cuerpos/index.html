Pose Estimation - Rastreando Cuerpos

07 de octubre de 2026

El 85% diseña sistemas con LLMs sin pensar en fallos y el 15% sabe cómo hacerlo bien

Aquí en Colombia tenemos una frase que aplica perfectamente al system design con LLMs: "el que no conoce la馬 que tiene, blame al gobierno". El 85% de los equipos construyen aplicaciones con LLMs como si el modelo fuera infalible — no consideran rate limits, no manejan timeouts, no tienen circuit breakers, no monitorean la calidad de las respuestas. Luego se sorprenden cuando en producción el sistema se cae o empieza a retornar garbage.

El 15% que sabe, diseña sistemas completos con LLMs: con capas de abstracción, patrones de retry robustos, fallback chains, monitoreo real, y una comprensión profunda de dónde están los bottlenecks. Hoy vamos a aprender a ser de ese 15%.

Por qué LLM system design es diferente

Con APIs tradicionales (REST, gRPC), el system design está resuelto: conoces las latencias (normalmente < 100ms), sabes que los errores son determinísticos (500, 404, timeout), y puedes hacer cache de respuestas sin drama. Con LLMs, todo es diferente:

  • Latencia variable y alta: 500ms a 30 segundos para una sola request
  • Errores no-determinísticos: un timeout no es siempre timeout, puede ser una respuesta partial o corrupta
  • Calidad variable: el mismo prompt puede retornar respuestas diferentes, y algunas son malas
  • Costos por token: cada request cuesta dinero, el caching es crítico
  • Rate limits agresivos: los providers (OpenAI, Anthropic) tienen límites estrictos

Estas diferencias hacen que el system design para LLMs requiera patrones específicos que no encontrarás en ningún libro de distributed systems tradicional.

Architecture patterns para LLM applications

El patrón de falla en cadena (Fallback Chain)

Este es el pattern más importante y el que más equipos ignoran. La idea es simple: si el modelo primario falla (rate limit, timeout, error), intentas con un modelo secundario. Y si ese falla, intentas con un tercero. Cada nivel debe ser más barato y más rápido que el anterior.

En la práctica, tu fallback chain podría ser:

  • Primary: GPT-4o — máxima calidad, mayor costo
  • Fallback 1: GPT-4o-mini — calidad razonable, menor costo
  • Fallback 2: Haiku — rápido, barato, para queries simples
  • Fallback 3: Cache hit — si ya respondimos esa pregunta, usar la respuesta cached
  • Ultimate fallback: Respuesta genérica "No puedo responder esto en este momento"

Circuit Breaker pattern

Cuando un provider está fallando (rate limits, degradación), no quieres seguir mandando requests — vas a desperdiciar requests y dinero. El circuit breaker monitorea la tasa de errores y "abre" el circuito cuando detecta que algo está mal, dejando de hacer requests por un período de tiempo antes de probar nuevamente.

Esto es crítico para rate limits de OpenAI que tienen ventanas de tiempo. Si el rate limit está en 500 requests por minuto y tú sigues mandando requests cuando ya llegaste al límite, vas a tener errores 429 por el resto de la ventana.

Async Processing con Webhooks

Para queries largas (generación de essays, código complejo), no quieres synchronous waiting. La arquitectura correcta es:

  1. User manda request, recibe un job ID inmediatamente
  2. El sistema procesa el request de forma async
  3. Cuando termina, notifica al usuario via webhook o polling
  4. El usuario consulta el resultado con el job ID

Esto también permite hacer retry sin que el usuario tenga que esperar — si una request falla a mitad del procesamiento, puedes reintentarla sin que el usuario lo note.

Patrones de confiabilidad

Retry con exponential backoff

Los retries parece simples pero hay muchos ways to get it wrong. Un retry mal implementado puede:

  • Mandar demasiados requests cuando el sistema está recuperándose (thundering herd)
  • No considerar que algunos errores son non-retryable (400 Bad Request)
  • No incluir jitter, causando synchronized retries
import asyncio
import random
import time
from typing import Callable, Optional, TypeVar, Type
from dataclasses import dataclass
from enum import Enum

class RetryStrategy:
    """Strategies para decidir qué errores son retryables."""
    
    @staticmethod
    def is_retryable(exception: Exception) -> bool:
        """Determina si un error debería hacer retry."""
        # Retry en rate limits y errores de servidor
        if hasattr(exception, 'status_code'):
            if exception.status_code == 429:  # Rate limit
                return True
            if exception.status_code >= 500:  # Server error
                return True
            if exception.status_code == 400:
                # Bad request puede ser retryable si es por content filtering
                return "content_filter" in str(exception).lower()
        # Retry en timeouts y connection errors
        if isinstance(exception, (asyncio.TimeoutError, ConnectionError)):
            return True
        return False
    
    @staticmethod
    def get_retry_delay(
        attempt: int,
        base_delay: float = 1.0,
        max_delay: float = 60.0,
        exponential_base: float = 2.0,
        jitter: bool = True
    ) -> float:
        """
        Calcula el delay para el próximo retry con exponential backoff.
        
       delay = min(max_delay, base_delay * (exponential_base ^ attempt)) + jitter
        """
        delay = base_delay * (exponential_base ** attempt)
        delay = min(delay, max_delay)
        
        if jitter:
            # Añade random jitter para evitar thundering herd
            # Jitter uniformly distributed entre 0 y delay/2
            delay = delay + random.uniform(0, delay / 2)
        
        return delay


@dataclass
class RetryConfig:
    """Configuración para el retry logic."""
    max_attempts: int = 3
    base_delay: float = 1.0
    max_delay: float = 60.0
    exponential_base: float = 2.0
    jitter: bool = True
    retryable_exceptions: tuple = (Exception,)
    
    def should_retry(self, attempt: int, exception: Exception) -> bool:
        if attempt >= self.max_attempts:
            return False
        return RetryStrategy.is_retryable(exception)


class LLMRetryHandler:
    """
    Maneja retries para llamadas a LLMs con circuit breaker.
    Implementa exponential backoff con jitter y circuit breaker.
    """
    
    def __init__(self, config: RetryConfig):
        self.config = config
        self.circuit_state = "closed"  # closed, open, half_open
        self.circuit_failures = 0
        self.circuit_successes = 0
        self.circuit_open_time: Optional[float] = None
        self.failure_threshold = 5  # Errores antes de abrir el circuit
        self.recovery_timeout = 30  # Segundos antes de intentar recovery
    
    async def execute_with_retry(
        self,
        func: Callable,
        *args,
        **kwargs
    ):
        """
        Ejecuta func con retry logic y circuit breaker.
        """
        last_exception = None
        
        for attempt in range(self.config.max_attempts):
            # Verificar circuit breaker
            if self.circuit_state == "open":
                if time.time() - self.circuit_open_time > self.recovery_timeout:
                    # Intentar recovery
                    self.circuit_state = "half_open"
                    print(f"Circuit breaker: attempting recovery (half-open)")
                else:
                    # Todavía está abierto, lanzar excepción inmediatamente
                    raise CircuitBreakerOpenError(
                        f"Circuit breaker open. Retry after {self.recovery_timeout}s"
                    )
            
            try:
                result = await func(*args, **kwargs)
                
                # Success - reset circuit if needed
                if self.circuit_state == "half_open":
                    self.circuit_successes += 1
                    if self.circuit_successes >= 3:
                        self.circuit_state = "closed"
                        self.circuit_failures = 0
                        print(f"Circuit breaker: recovered (closed)")
                
                return result
                
            except Exception as e:
                last_exception = e
                
                if not self.config.should_retry(attempt, e):
                    # Error no retryable
                    self.circuit_state = "closed"
                    raise
                
                if self.circuit_state == "half_open":
                    # Failure during recovery - reopen immediately
                    self.circuit_state = "open"
                    self.circuit_open_time = time.time()
                    self.circuit_failures = 0
                    print(f"Circuit breaker: recovery failed, reopening")
                    raise
                
                # Registrar failure para circuit breaker
                self.circuit_failures += 1
                if self.circuit_failures >= self.failure_threshold:
                    self.circuit_state = "open"
                    self.circuit_open_time = time.time()
                    print(f"Circuit breaker: opened due to {self.circuit_failures} failures")
                
                # Calcular delay
                delay = RetryStrategy.get_retry_delay(
                    attempt,
                    self.config.base_delay,
                    self.config.max_delay,
                    self.config.exponential_base,
                    self.config.jitter
                )
                
                print(f"Retry {attempt + 1}/{self.config.max_attempts} "
                      f"after {delay:.2f}s. Error: {type(e).__name__}: {e}")
                
                await asyncio.sleep(delay)
        
        # Agotamos los retries
        raise last_exception


class CircuitBreakerOpenError(Exception):
    """Excepción cuando el circuit breaker está abierto."""
    pass

Quality Guardrails

Uno de los problemas más difíciles en producción es que el LLM puede retornar contenido no deseado o simplemente incorrecto. Los guardrails son la capa que verifica la salida antes de entregarla al usuario:

  • Content filtering: verificar que la respuesta no contiene NSFW, hate speech, etc.
  • Format validation: si esperas JSON, verificar que el JSON es válido
  • Length validation: si la respuesta es demasiado corta o demasiado larga, podría ser señal de problema
  • Semantic validation: verificar que la respuesta realmente responde la pregunta (usando embeddings o un segundo LLM call)

Diseño para escalabilidad

Caching strategies

El caching es crítico para reducir costos y latencia. Pero el caching para LLMs es tricky porque:

  • El mismo prompt puede retornar respuestas diferentes
  • Respuestas semanticamente similares pueden tener surface differences
  • Invalidar cache es difícil — no hay timestamps claros

La estrategia más efectiva es semantic caching: en lugar de guardar respuestas exactas, guardas embeddings del prompt y usas similarity search para encontrar respuestas cached.

import hashlib
import json
from typing import Optional, List, Tuple
import numpy as np

class SemanticCache:
    """
    Semantic cache para respuestas de LLMs.
    Usa embeddings para encontrar respuestas similares.
    """
    
    def __init__(
        self,
        embedding_model,
        vector_store,
        similarity_threshold: float = 0.95,
        ttl_seconds: Optional[float] = None
    ):
        self.embedding_model = embedding_model
        self.vector_store = vector_store  # Pinecone, Chroma, etc.
        self.similarity_threshold = similarity_threshold
        self.ttl_seconds = ttl_seconds
    
    def _get_cache_key(self, prompt: str, model: str, params: dict) -> str:
        """
        Genera un cache key hash del prompt + config.
        Usado como ID único en el vector store.
        """
        content = json.dumps({
            'prompt': prompt,
            'model': model,
            'params': params
        }, sort_keys=True)
        return hashlib.sha256(content.encode()).hexdigest()
    
    def _get_embedding(self, text: str) -> List[float]:
        """Genera embedding para semantic search."""
        return self.embedding_model.encode([text])[0]
    
    async def get(
        self,
        prompt: str,
        model: str,
        params: dict
    ) -> Optional[str]:
        """
        Busca una respuesta cached semanticamente similar.
        Retorna la respuesta si encuentra match, None si no.
        """
        cache_key = self._get_cache_key(prompt, model, params)
        embedding = self._get_embedding(prompt)
        
        # Buscar en vector store
        results = self.vector_store.search(
            embedding=embedding,
            top_k=1,
            filter={'cache_key': {'$ne': cache_key}}  # Excluir el registro actual si existe
        )
        
        if not results or len(results) == 0:
            return None
        
        best_match = results[0]
        similarity = best_match['score']
        
        # Verificar similarity threshold
        if similarity >= self.similarity_threshold:
            cached_response = best_match['payload']['response']
            
            # Verificar TTL si está configurado
            if self.ttl_seconds:
                cached_time = best_match['payload'].get('cached_at', 0)
                if time.time() - cached_time > self.ttl_seconds:
                    # Cache expired
                    return None
            
            print(f"Cache HIT: similarity={similarity:.4f}")
            return cached_response
        
        print(f"Cache MISS: best_similarity={similarity:.4f}")
        return None
    
    async def set(
        self,
        prompt: str,
        model: str,
        params: dict,
        response: str
    ):
        """Guarda una respuesta en el cache."""
        cache_key = self._get_cache_key(prompt, model, params)
        embedding = self._get_embedding(prompt)
        
        self.vector_store.upsert(
            id=cache_key,
            embedding=embedding,
            payload={
                'prompt': prompt,
                'model': model,
                'params': params,
                'response': response,
                'cached_at': time.time()
            }
        )


class CacheConfig:
    """Configuración de caching con multiple strategies."""
    
    def __init__(
        self,
        use_exact_cache: bool = True,
        use_semantic_cache: bool = True,
        semantic_threshold: float = 0.95,
        ttl_seconds: float = 3600,  # 1 hora default
        max_cache_size: int = 10000
    ):
        self.use_exact_cache = use_exact_cache
        self.use_semantic_cache = use_semantic_cache
        self.semantic_threshold = semantic_threshold
        self.ttl_seconds = ttl_seconds
        self.max_cache_size = max_cache_size


async def cached_llm_call(
    cache: SemanticCache,
    prompt: str,
    model: str,
    params: dict,
    llm_func: Callable
) -> Tuple[str, bool]:
    """
    Wrapper que intenta cache primero, luego llama al LLM si no hay match.
    Retorna (response, cache_hit).
    """
    # Intentar cache semántico primero
    if cache:
        cached_response = await cache.get(prompt, model, params)
        if cached_response:
            return cached_response, True
    
    # No hay cache hit, llamar al LLM
    response = await llm_func(prompt, model=model, **params)
    
    # Guardar en cache si tenemos uno configurado
    if cache:
        await cache.set(prompt, model, params, response)
    
    return response, False

Load shedding y prioritization

Cuando el sistema está bajo load, no puedes procesar todas las requests. Load shedding es la práctica de rechazar o depriorizar requests menos importantes cuando los recursos están escasos:

  • Priority queue: requests de usuarios premium van primero
  • Adaptive timeouts: cuando estás bajo load, reducir el timeout máximo aceptable
  • Request coalescing: si 100 usuarios preguntan lo mismo al mismo tiempo, solo procesar uno y servir a todos

Observabilidad: monitoreando lo que importa

El monitoreo para LLMs es diferente del monitoreo tradicional. No solo importan latencia y throughput — importan métricas de calidad que son más difíciles de medir.

Métricas de negocio

  • Task success rate: % de requests que el usuario consideró útiles (feedback explícito)
  • Escalation rate: % de requests que requirieron intervención humana o mejor modelo
  • Cost per successful request: costo total dividido por requests exitosos

Métricas técnicas

  • Latencia p50, p95, p99: no solo el promedio — los percentiles importan más
  • Error rate por tipo: 429s (rate limits), timeouts, 500s, content violations
  • Cache hit rate: qué % de requests se sirven desde cache
  • Model quality metrics: longitud de respuestas, diversidad léxica, repetición

class LLMObservability:
    """
    Instrumentación para observar aplicaciones con LLMs.
    Incluye tracing, metrics, y logging estructurado.
    """
    
    def __init__(self, service_name: str):
        self.service_name = service_name
        self.tracer = trace.get_tracer(service_name)
    
    async def trace_llm_call(
        self,
        span_name: str,
        prompt: str,
        model: str,
        params: dict,
        func: Callable
    ):
        """
        Wrapper que crea un span para cada llamada LLM.
        Registra atributos relevantes para debugging.
        """
        with self.tracer.start_as_current_span(span_name) as span:
            # Set span attributes
            span.set_attribute("llm.model", model)
            span.set_attribute("llm.prompt_length", len(prompt))
            span.set_attribute("llm.temperature", params.get('temperature', 0))
            span.set_attribute("llm.max_tokens", params.get('max_tokens', 0))
            
            start_time = time.perf_counter()
            try:
                response = await func(prompt, model=model, **params)
                elapsed_ms = (time.perf_counter() - start_time) * 1000
                
                # Set response attributes
                span.set_attribute("llm.response_length", len(response))
                span.set_attribute("llm.latency_ms", elapsed_ms)
                span.set_attribute("llm.success", True)
                
                return response
                
            except Exception as e:
                elapsed_ms = (time.perf_counter() - start_time) * 1000
                span.set_attribute("llm.latency_ms", elapsed_ms)
                span.set_attribute("llm.success", False)
                span.set_attribute("llm.error_type", type(e).__name__)
                span.set_attribute("llm.error_message", str(e))
                raise

Los 3 errores más comunes

Error 1: Diseñar sin considerar failure modes

El error: Asumir que el LLM siempre va a responder. En producción, vas a ver: rate limits (429), timeouts, errores 500 del provider, content violations que bloquean respuestas, y modelos que simplemente retornan garbage para ciertos prompts. Si no planeaste para estos casos, tu sistema va a fallar de formas spectaculares.

La solución: Haz una lista de todos los failure modes posibles antes de empezar a construir. Para cada uno:

  • ¿Qué debería pasar cuando ocurra?
  • ¿Cómo notifica al usuario?
  • ¿Se puede retry automáticamente?
  • ¿Cuál es el fallback?

Implementa la fallback chain desde el día uno, no como afterthought.

Error 2: No tener capas de abstracción

El error: Acoplar tu aplicación directamente a la API de OpenAI. Cuando quieras cambiar a Anthropic, o a un modelo open-source, o a tu propio servidor local, vas a tener que reescribir media aplicación.

La solución: Implementa una abstracción (interface o clase base) que defina cómo interactúas con LLMs. Tu lógica de negocio solo conoce esa abstracción, no la implementación específica. Así puedes swap providers sin cambiar código de negocio.

from abc import ABC, abstractmethod
from typing import List, Dict, Optional

class LLMProvider(ABC):
    """Abstract interface para todos los LLM providers."""
    
    @abstractmethod
    async def generate(
        self,
        prompt: str,
        *,
        temperature: float = 0.7,
        max_tokens: int = 1000,
        stop: Optional[List[str]] = None,
        **kwargs
    ) -> str:
        """Genera una respuesta al prompt dado."""
        pass
    
    @abstractmethod
    async def batch_generate(
        self,
        prompts: List[str],
        **kwargs
    ) -> List[str]:
        """Genera respuestas para múltiples prompts."""
        pass
    
    @abstractmethod
    def get_token_count(self, text: str) -> int:
        """Cuenta los tokens en un texto."""
        pass

class LLMWrapper:
    """
    Wrapper que añade funcionalidad extra sobre cualquier provider:
    retries, caching, rate limiting, observabilidad.
    """
    
    def __init__(
        self,
        provider: LLMProvider,
        retry_handler: LLMRetryHandler,
        cache: Optional[SemanticCache] = None,
        observability: Optional[LLMObservability] = None
    ):
        self.provider = provider
        self.retry_handler = retry_handler
        self.cache = cache
        self.observability = observability
    
    async def generate(self, prompt: str, **kwargs) -> str:
        """Generate con retry, cache, y tracing."""
        # Try cache first
        if self.cache:
            cached = await self.cache.get(prompt, self.provider.model, kwargs)
            if cached:
                return cached
        
        # Execute with retry and tracing
        if self.observability:
            response = await self.observability.trace_llm_call(
                "llm.generate",
                prompt,
                self.provider.model,
                kwargs,
                lambda: self.retry_handler.execute_with_retry(
                    self.provider.generate, prompt, **kwargs
                )
            )
        else:
            response = await self.retry_handler.execute_with_retry(
                self.provider.generate, prompt, **kwargs
            )
        
        # Cache the response
        if self.cache:
            await self.cache.set(prompt, self.provider.model, kwargs, response)
        
        return response

Error 3: Escalar sin entender los bottlenecks

El error: "Vamos a meter más instancias de nuestra API porque está lenta". Pero si el bottleneck real es que estás haciendo 3 LLM calls por request y cada uno tarda 5 segundos, agregar más instancias no va a ayudar — vas a gastar dinero en recursos que no resuelven el problema.

La solución: Antes de escalar, haz profiling real del sistema. Usa tracing distribuido para identificar dónde se va el tiempo. Pregúntate:

  • ¿El bottleneck es la latencia del LLM? → Considera modelos más rápidos para queries simples
  • ¿El bottleneck es el cache? → Mejora el hit rate con mejor embedding similarity
  • ¿El bottleneck es la concurrencia? → Más instancias ayudan, pero también considera async processing
  • ¿El bottleneck es los rate limits? → Implementa queueing con backpressure

Resumen: los patrones que separan el 15% que sabe

  • Fallback chain: nunca dependas de un solo modelo o provider
  • Circuit breaker: proteje tu sistema de cascading failures cuando un provider está caído
  • Retry con exponential backoff: pero solo para errores retryables, con jitter para evitar thundering herd
  • Caching semántico: la latencia y costo más bajo posible
  • Abstracción de provider: tu código de negocio no debería conocer a OpenAI
  • Guardrails de calidad: nunca retornes output sin verificar que cumple los estándares
  • Observabilidad real: tracing, métricas, logging que te permitan debuggear cuando las cosas fallen
  • Load shedding: sabe qué hacer cuando estás bajo load — no todo puede ser priority 1

El system design robusto para LLMs no es opcional — es lo que separa las aplicaciones que sobreviven en producción de las que fallan spectacularmente el primer día con load real. Con los patrones de hoy, tienes la base para construir sistemas que no solo funcionan, sino que degradan gracefully cuando las cosas salen mal.

Eso es todo por hoy. Mañana seguimos con más. El que persiste, llega — y en ML, el que documenta y observa, no se pierde cuando las cosas se rompen.
