🔎 ¿Qué es un Knowledge Graph?

Un Knowledge Graph es una red de nodos (entidades) y aristas (relaciones). En lugar de guardar texto plano, guardas:

  • Entidades: personas, lugares, organizaciones, conceptos
  • Relaciones: "trabaja en", "fundó", "ubicado en", "compite con"
  • Propiedades: atributos de cada entidad

Matemáticamente:

G = (V, E) donde V = vertices (entidades), E = aristas (relaciones)

En un KG para NLP, cada nodo tiene un embedding. Las aristas también pueden tener embeddings. La query no es solo "buscar texto similar" — es recorrer el grafo siguiendo relaciones.

🏗️ Construyendo un Knowledge Graph desde Texto

El pipeline completo tiene 4 etapas:

Paso 1: Entity Extraction con LLM

def extract_entities_with_llm(text: str, llm) -> List[Dict]:
    """
    Extrae entidades y relaciones usando un LLM.
    Cada entidad tiene: name, type, mentions (posiciones en texto)
    """

    Relaciones a buscar: {', '.join(RELATION_TYPES)}
    
    Texto: {text}
    
    Devuelve un JSON con:
    - entities: lista de {{name, type, description}}
    - relations: lista de {{from, to, type}}
    """
    
    response = llm.complete(prompt)
    return parse_llm_response(response)

def extract_entities_simple(text: str) -> List[Dict]:
    """
    Alternativa sin LLM: NER rule-based
    Útil para datos estructurados o cuando no tienes acceso a un LLM.
    """
    entities = []
    
    # Patrones comunes para texto en español
    patterns = {
        "PERSON": r"\b[A-Z][a-záéíóúñ]+ [A-Z][a-záéíóúñ]+\b",
        "ORGANIZATION": r"\b[A-Z][a-záéíóúñ]*(?: SA|SAS|LTDA|SRL|Corp|Inc)\b",
        "LOCATION": r"\b[A-Z][a-záéíóúñ]+,?\s+[A-Z][a-záéíóúñ]+\b",
        "DATE": r"\b\d{1,2}/\d{1,2}/\d{2,4}\b|\b\d{4}-\d{2}-\d{2}\b"
    }
    
    for entity_type, pattern in patterns.items():
        matches = re.finditer(pattern, text)
        for match in matches:
            entities.append({
                "name": match.group(),
                "type": entity_type,
                "span": match.span()
            })
    
    return entities

Paso 2: Deduplicación de Entidades (CRÍTICO)

from collections import defaultdict

def deduplicate_entities(entities: List[Dict], similarity_threshold: float = 0.85) -> List[Dict]:
    """
    ERROR COMÚN #2: No hacer deduplicación.
    
    Si "Juan Pérez" aparece en 500 documentos, terminas con
    500 nodos duplicados. Tu KG se vuelve inútil.
    
    La solución: clustering por similitud + canonicalización.
    """
    # Si no tienes embeddings, usa string matching
    name_to_canonical = {}
    entity_clusters = defaultdict(list)
    
    for entity in entities:
        name = entity["name"].lower().strip()
        
        # Buscar si ya existe un canonical similar
        found = False
        for canonical_name in name_to_canonical:
            if levenshtein_similarity(name, canonical_name) > similarity_threshold:
                entity_clusters[canonical_name].append(entity)
                found = True
                break
        
        if not found:
            name_to_canonical[name] = name
            entity_clusters[name].append(entity)
    
    # Crear entidades canonical (una por cluster)
    canonical_entities = []
    for canonical_name, cluster in entity_clusters.items():
        # Usar la forma más completa/larga como canonical
        canonical = max(cluster, key=lambda e: len(e.get("name", "")))
        canonical["cluster_size"] = len(cluster)
        canonical["mentions"] = [e.get("span", (0,0)) for e in cluster]
        canonical_entities.append(canonical)
    
    return canonical_entities

def levenshtein_similarity(s1: str, s2: str) -> float:
    """Similitud basada en distancia de edición."""
    if len(s1) == 0 and len(s2) == 0:
        return 1.0
    
    len1, len2 = len(s1), len(s2)
    dp = [[0] * (len2 + 1) for _ in range(len1 + 1)]
    
    for i in range(len1 + 1):
        dp[i][0] = i
    for j in range(len2 + 1):
        dp[0][j] = j
    
    for i in range(1, len1 + 1):
        for j in range(1, len2 + 1):
            cost = 0 if s1[i-1] == s2[j-1] else 1
            dp[i][j] = min(dp[i-1][j] + 1, dp[i][j-1] + 1, dp[i-1][j-1] + cost)
    
    max_len = max(len1, len2)
    return 1 - dp[len1][len2] / max_len

Paso 3: Construir el Grafo (Neo4j o NetworkX)

# Opción A: NetworkX (en memoria, más simple)
import networkx as nx

def build_graph_networkx(entities: List[Dict], relations: List[Dict]) -> nx.DiGraph:
    """Construye un grafo directed con NetworkX."""
    G = nx.DiGraph()
    
    # Añadir nodos con atributos
    for entity in entities:
        G.add_node(
            entity["name"],
            type=entity["type"],
            description=entity.get("description", ""),
            cluster_size=entity.get("cluster_size", 1)
        )
    
    # Añadir aristas con tipos de relación
    for relation in relations:
        G.add_edge(
            relation["from"],
            relation["to"],
            relation_type=relation["type"]
        )
    
    return G

Paso 4: Query del Grafo para Contexto

def query_graph_for_context(G: nx.DiGraph, query: str, max_depth: int = 3) -> List[Dict]:
    """
    ERROR COMÚN #3: No entender el costo de traversal.
    
    Hacer BFS/DFS sin límite puede ser O(V+E) — catastrófico
    en grafos grandes. Siempre limita la profundidad.
    
    Esta función extrae contexto relevante para una query.
    """
    # Extraer entidades de la query
    query_entities = extract_entities_simple(query)
    
    context_nodes = set()
    context_edges = []
    
    for q_entity in query_entities:
        # Buscar nodo más similar en el grafo
        for node in G.nodes():
            if levenshtein_similarity(q_entity["name"].lower(), node.lower()) > 0.7:
                # Traversal limitado por profundidad
                for neighbor in nx.single_source_shortest_path_length(G, node, max_depth):
                    context_nodes.add(neighbor)
                    # Obtener aristas del nodo
                    for u, v, data in G.edges(data=True):
                        if u == neighbor or v == neighbor:
                            context_edges.append({"from": u, "to": v, **data})
                break  # Solo el match más cercano
    
    return {
        "nodes": [{"name": n, **G.nodes[n]} for n in context_nodes],
        "edges": context_edges
    }

def query_kg_cypher(kg, query: str) -> List[Dict]:
    """
    Query KG con Cypher (para Neo4j).
    Ejemplo: encontrar todas las personas en TechCorp.
    """
    cypher_query = """
    MATCH (p:Person)-[r]-(c:Organization {name: $org})
    RETURN p.name AS person, type(r) AS relationship, c.name AS company
    ORDER BY p.name
    """
    results = kg.run(cypher_query, org=query)
    return [dict(record) for record in results]

🔗 Integrando Knowledge Graph con RAG

class KnowledgeGraphRAG:
    """
    RAG mejorado con Knowledge Graph.
    
    El flujo:
    1. Query entra → extraer entidades
    2. Buscar en KG → obtener contexto estructurado
    3. Buscar en vector store → obtener chunks similares
    4. Combinar ambos contextos → generar respuesta
    """
    
    def __init__(self, vector_store, graph: nx.DiGraph, llm):
        self.vector_store = vector_store
        self.graph = graph
        self.llm = llm
    
    def retrieve(self, query: str, top_k: int = 5) -> str:
        # 1. Contexto del Knowledge Graph
        kg_context = query_graph_for_context(self.graph, query, max_depth=2)
        
        # 2. Contexto vectorial
        vector_results = self.vector_store.similarity_search(query, k=top_k)
        
        # 3. Combinar contextos
        combined_context = self._build_context(kg_context, vector_results)
        
        return combined_context
    
    def _build_context(self, kg_context: Dict, vector_results: List, max_chars: int = 4000) -> str:
        """Combina contexto del KG y vector store de forma inteligente."""
        context_parts = []
        char_count = 0
        
        # Primero: contexto estructurado del KG (más confiable)
        for node in kg_context["nodes"]:
            node_text = f"{node['name']} ({node.get('type', 'entity')})"
            if char_count + len(node_text) < max_chars * 0.4:  # KG max 40%
                context_parts.append(node_text)
                char_count += len(node_text)
        
        # Segundo: chunks del vector store
        for result in vector_results:
            result_text = f"\n\n{result.page_content}"
            if char_count + len(result_text) < max_chars:
                context_parts.append(result_text)
                char_count += len(result_text)
            else:
                break
        
        return "\n".join(context_parts)
    
    def answer(self, query: str) -> str:
        context = self.retrieve(query)
        
        prompt = f"""Basándote en el siguiente contexto, responde la pregunta.
        
        Contexto:
        {context}
        
        Pregunta: {query}
        
        Respuesta:"""
        
        return self.llm.complete(prompt)

📊 La Matemática del KG en RAG

¿Por qué funciona mejor? Porque el embedding vectorial tiene limitaciones:

Problema del embedding plano:

dado un chunk c y una query q, la similitud coseno es:

sim(c, q) = cos(θ) = (c · q) / (||c|| ||q||)

Esto NO captura relaciones transitivas. Si "A relación B" y "B relación C", embeddings planos no capturan que "A tiene relación transitiva con C".

Con Knowledge Graph:

Puedes hacer traversal de relaciones:

reachable(A, C) = ∃ path: A →* C a través de relaciones

Esto captura conocimiento que no existe en ningún chunk individual.

⚠️ Los 3 Errores Fatales

Error 1: No usar KG cuando los datos TIENEN relaciones

El problema: En datos empresariales (contratos, documentos legales, carpetas de RRHH), las relaciones son el dato más valioso. "Quién firma", "quién autorizó", "quién tiene relación jerárquica con quién". Un vector store plano pierde todo esto.

La solución: Analiza tu dominio primero. Si hay entidades que se repiten con relaciones, usa KG.

Error 2: Construir el KG sin deduplicación

El problema: Sin deduplicación, el mismo "Juan Pérez" se convierte en 500 nodos. Tu KG crece sin control y las queries devuelven basura. En un caso real con 10K documentos legales, esto puede generar 50K+ nodos duplicados.

La solución: Implementa deduplicación desde el día 1. Usa embeddings o distance de Levenshtein para canonicalizar.

Error 3: Query del graph sin entender traversal cost

El problema: Un BFS sin límite en un grafo grande puede ser O(V+E). Si tienes 1M de nodos y haces traversal sin depth limit, tu RAG se vuelve más lento que hacer la query directo al LLM.

La solución: Siempre limita max_depth. En producción, usa índices de grafo (apróximate neighbors) en lugar de traversal completo.

✅ Resumen

Hagale pues, parcero. Lo esencial del día:

  • Knowledge Graph = nodos (entidades) + aristas (relaciones). No es opcional cuando tus datos tienen estructura relacional.
  • El pipeline: extract → deduplicate → build → query. Cada paso importa.
  • Deduplicación = diferencia entre un KG útil y uno inútil.
  • Traversal cost = siempre limita profundidad o te mueres de timeout.
  • KG + RAG = contexto estructurado + chunks vectoriales. 100x mejor que RAG plano.
