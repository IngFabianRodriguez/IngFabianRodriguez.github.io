LLM Caching - Semantic Cache con Redis y Embeddings

27 de septiembre de 2026
llmcacheredisembeddings

Introduction

Parcero, hablemos de plata. Cada llamada a GPT-4, Claude o cualquier LLM comercial cuesta centavos, pero centavos sumados se vuelven miles de dolares al mes. Y peor: la mitad de esas llamadas son variaciones de preguntas que ya respondiste antes. Si tu usuario pregunta "como reiniciar Windows", y otro pregunta "how to reset Windows", tu backend paga dos veces por essentially la misma respuesta.

Aqui entra el Semantic Cache: una capa de cache que no compara strings literales, sino significado. Si dos prompts son semanticamente similares, devolvemos la respuesta cacheada sin tocar el LLM. Redis con su modulo de vector search (RediSearch) es el backend perfecto para esto: rapido, en memoria, y con busqueda por similitud de coseno nativa. Vamos a armarlo.

El Problema: Cache Tradicional No Alcanza

Un cache tradicional funciona con exact match: si la pregunta es identica al string, devuelves la respuesta guardada. Pero el lenguaje natural es ruidoso:

  • "Como cambio mi contrasena?"
  • "Quiero actualizar mi password"
  • "donde modifico la clave de acceso?"

Para un cache basado en string, estas tres preguntas son tres keys distintas, tres llamadas al LLM, tres facturas. Pero semanticamente son la misma pregunta. Ahi es donde el semantic cache brilla.

La idea central: en lugar de guardar el texto del prompt como key, guardamos su embedding (un vector denso que representa el significado). Cuando llega un nuevo prompt, calculamos su embedding y buscamos en el cache el vector mas cercano. Si la distancia es menor a un threshold, hit. Si no, miss y llamamos al LLM.

Embeddings: El Puente entre Texto y Vectores

Un embedding es una funcion $f: \text{Text} \rightarrow \mathbb{R}^d$ que mapea texto a un vector de dimensionalidad fija. Modelos como text-embedding-3-small de OpenAI producen vectores de 1536 dimensiones; all-MiniLM-L6-v2 de SentenceTransformers produce 384.

La magia esta en que textos semanticamente similares terminan cerca en el espacio vectorial:

$$\cos(\theta) = \frac{\mathbf{A} \cdot \mathbf{B}}{\|\mathbf{A}\| \|\mathbf{B}\|} = \frac{\sum_{i=1}^{d} A_i B_i}{\sqrt{\sum_{i=1}^{d} A_i^2} \sqrt{\sum_{i=1}^{d} B_i^2}}$$

El cosine similarity mide el angulo entre dos vectores, no la distancia euclidiana. Esto importa porque dos textos pueden tener embeddings de magnitud diferente (por la longitud del texto, por ejemplo) pero el mismo angulo si significan lo mismo.

Valores tipicos de cosine similarity:

  • 0.95 - 1.00: paraphrase casi exacta, cache hit seguro
  • 0.85 - 0.95: misma intencion, ligera diferencia, cache hit probable
  • 0.70 - 0.85: tema relacionado pero diferente pregunta, evaluar
  • < 0.70: diferente tema, cache miss

Redis Stack: El Backend Ideal

Redis clasico es un key-value store. Pero Redis Stack extiende Redis con modulos especializados, entre ellos RediSearch que soporta busqueda vectorial con KNN (K-Nearest Neighbors) usando algoritmos como HNSW o FLAT.

Para semantic cache, el flujo es:

  1. Calcular embedding del prompt entrante
  2. Buscar en Redis el vector mas cercano usando KNN query
  3. Si distancia (1 - cosine_similarity) < threshold, devolver respuesta cacheada
  4. Si no, llamar al LLM, guardar el par (embedding, respuesta), devolver respuesta

Redis no es solo rapido (operaciones en O(log N) con HNSW); tambien es persistente, replicable, y soporta TTL nativo. Cosas que un cache en memoria de Python no te da.

Implementacion desde Cero

Veamos como se ve esto en codigo. Primero, definir el indice en Redis:

import redis
import numpy as np
from redis.commands.search.field import TagField, VectorField, TextField
from redis.commands.search.indexDefinition import IndexDefinition, IndexType
from redis.commands.search.query import Query

INDEX_NAME = "llm-semantic-cache"
DOC_PREFIX = "cache:"
VECTOR_DIM = 1536  # OpenAI text-embedding-3-small
DISTANCE_THRESHOLD = 0.15  # 1 - 0.85 cosine similarity

def create_cache_index(r: redis.Redis):
    schema = (
        TextField("prompt"),
        TextField("response"),
        TagField("model"),
        VectorField("embedding",
            "HNSW", {
                "TYPE": "FLOAT32",
                "DIM": VECTOR_DIM,
                "DISTANCE_METRIC": "COSINE",
            }
        ),
    )
    definition = IndexDefinition(prefix=[DOC_PREFIX], index_type=IndexType.HASH)
    r.ft(INDEX_NAME).create_index(fields=schema, definition=definition)

client = redis.Redis(host="localhost", port=6379)
create_cache_index(client)

Ahora la logica de lookup y store:

import hashlib
import json
import openai

EMBEDDING_MODEL = "text-embedding-3-small"
LLM_MODEL = "gpt-4o-mini"

def get_embedding(text: str) -> np.ndarray:
    response = openai.Embedding.create(input=[text], model=EMBEDDING_MODEL)
    return np.array(response["data"][0]["embedding"], dtype=np.float32)

def semantic_cache_lookup(r: redis.Redis, prompt: str) -> str | None:
    embedding = get_embedding(prompt)
    query = (
        Query("*=>[KNN 1 @embedding $vec as score]")
        .sort_by("score")
        .return_fields("prompt", "response", "score")
        .paging(0, 1)
        .dialect(2)
    )
    params = {"vec": embedding.tobytes()}
    results = r.ft(INDEX_NAME).search(query, params).docs

    if not results:
        return None

    distance = float(results[0].score)
    if distance > DISTANCE_THRESHOLD:
        return None

    return results[0].response

def semantic_cache_store(r: redis.Redis, prompt: str, response: str):
    embedding = get_embedding(prompt)
    key_id = hashlib.sha256(prompt.encode()).hexdigest()[:16]
    key = f"{DOC_PREFIX}{key_id}"
    r.hset(key, mapping={
        "prompt": prompt,
        "response": response,
        "model": LLM_MODEL,
        "embedding": embedding.tobytes(),
    })
    r.expire(key, 86400 * 7)  # TTL de 7 dias

def chat(r: redis.Redis, user_prompt: str) -> str:
    cached = semantic_cache_lookup(r, user_prompt)
    if cached:
        return cached  # Hit: cero costo de API

    response = openai.ChatCompletion.create(
        model=LLM_MODEL,
        messages=[{"role": "user", "content": user_prompt}],
    ).choices[0].message.content

    semantic_cache_store(r, user_prompt, response)
    return response

Esa es la version minima. Funciona, pero hay mejoras obvias: usar pipeline para batch lookups, agregar metadata (timestamp, tokens ahorrados), implementar eviction por tamano maximo del cache, y manejar el caso de prompts multi-turn.

GPTCache: La Solucion Lista

Armar todo desde cero es educativo pero improductivo en produccion. GPTCache es una libreria open-source que ya resuelve los problemas comunes: multi-embedding support, multiple eviction policies, similarity threshold tuning, y adapters para LangChain, LlamaIndex, y OpenAI directo.

from gptcache import Cache
from gptcache.adapter.api import init_similar_cache
from gptcache.embedding import Onnx
from gptcache.manager import CacheBase, VectorBase, get_data_manager
from gptcache.similarity_evaluation.distance import SearchDistanceEvaluation

# Embedding local con ONNX (gratis, sin API)
onnx_emb = Onnx()

# Backend: Redis como vector store + SQLite como object store
data_manager = get_data_manager(
    CacheBase("sqlite"),
    VectorBase("redis", host="localhost", port=6379),
)

cache = init_similar_cache(
    data_manager=data_manager,
    embedding_fn=onnx_emb.to_embeddings,
    similarity_evaluation=SearchDistanceEvaluation(),
    post_process_messages_func=print,
)

# Uso identico al que ya tienes
cache.set("como reinicio Windows?", "Ve a Configuracion > Actualizacion...")
response = cache.get("quiero resetear mi Windows")
print(response)  # Hit si cosine > threshold

Lo poderoso de GPTCache es que puedes mezclar backends: el vector store en Redis (rapido para similarity search), el object store en SQLite o PostgreSQL (persistente para los payloads grandes), y el embedding model local con ONNX (cero costo por embedding).

LangChain SemanticCache

Si ya usas LangChain, el path mas corto es su SemanticCache integrado:

from langchain.cache import RedisSemanticCache
from langchain.globals import set_llm_cache
from langchain.embeddings import OpenAIEmbeddings
import redis

# Configurar el cache semantico globalmente
set_llm_cache(RedisSemanticCache(
    redis_url="redis://localhost:6379",
    embedding=OpenAIEmbeddings(),
    score_threshold=0.15,  # 1 - 0.85 cosine similarity
))

# Ahora TODAS las llamadas a LLM pasan por el cache
from langchain.llms import OpenAI
llm = OpenAI(model_name="gpt-4o-mini")
llm("Capital de Francia?")           # Miss: llamada real al LLM
llm("cual es la capital de Francia?") # Hit: misma respuesta, $0 gastado

Cuidado: este cache es global al proceso de LangChain. Si quieres control granular por usuario o sesion, mejor GPTCache o tu propia implementacion.

Threshold Tuning: El Arte del Cache

El parametro mas importante es el score threshold (distancia maxima permitida). Muy bajo y el cache nunca hit. Muy alto y empiezas a servir respuestas incorrectas a preguntas diferentes.

Estrategia de calibracion:

  1. Empieza en 0.15 (cosine 0.85) como default conservador
  2. Mide hit rate en produccion durante una semana
  3. Analiza los false positives: preguntas que hitearon cache pero la respuesta no era correcta
  4. Ajusta: sube threshold si tienes muchos hits incorrectos, bajalo si el hit rate es muy bajo

Para casos donde las respuestas son factual y deterministas ("capital de Francia"), puedes usar thresholds mas agresivos (0.20-0.25). Para respuestas creativas o contextuales, se conservador (0.10-0.15).

Una tecnica avanzada es usar multiple thresholds: un threshold bajo para respuestas creativas, otro mas permisivo para facts. El router decide cual usar segun la naturaleza del prompt.

Costos Reales: Los Numeros No Mienten

Tomemos un caso real: un chatbot de soporte que recibe 100K preguntas/mes, con un 60% de preguntas repetidas o parafraseadas.

Concepto Sin cache Con semantic cache
Llamadas al LLM 100,000 40,000
Costo por llamada (GPT-4o-mini) $0.0003 $0.0003
Costo LLM mensual $30.00 $12.00
Costo embeddings $0 $0.10
Total mensual $30.00 $12.10

60% de ahorro. Pero el verdadero beneficio viene en latencia: una llamada al LLM toma 1-3 segundos. Un lookup en Redis con HNSW toma 5-20ms. Eso es 100x mas rapido, lo cual cambia la UX completa.

Trampas Comunes

Antes de cerrar, las trampas que he visto en produccion:

  • Cache poisoning: si un usuario mete un prompt malicioso y el LLM responde algo incorrecto, ese par (prompt, response) queda cacheado. Solucion: sanitizar prompts antes de cachear, y tener un TTL agresivo para respuestas que tocan temas sensibles.
  • Context bleeding: si tu chatbot tiene contexto de sesion (nombre del usuario, conversacion previa), el prompt completo varia y no hiteara cache. Solucion: cachear solo el query core, no todo el prompt con contexto.
  • Threshold unico: usar el mismo threshold para todo es suboptimo. Distintos tipos de preguntas tienen distintas tolerancias. Considerar multi-tier cache.
  • Sin eviction: si tu cache crece sin limite, eventualmente Redis se queda sin memoria. Implementar LRU o TTL estricto segun el caso de uso.
  • Embedding drift: si cambias de modelo de embeddings, todos los vectores viejos quedan en un espacio diferente y no se comparan correctamente. Versionar el cache por modelo.

Cuando NO Usar Semantic Cache

No es bala de plata. Hay escenarios donde no aplica:

  • Respuestas altamente contextuales: si cada respuesta depende de un estado externo (precio actual, stock en tiempo real), el cache sirve respuestas stale
  • Preguntas creativas unicas: "escribe un poema sobre mi gato" no deberia hitear cache aunque alguien mas haya pedido algo similar
  • Sistemas con informacion personalizable: si la respuesta depende del usuario, cachear sin discriminacion filtra datos entre usuarios
  • Volumenes muy bajos: si recibes 50 preguntas/mes, el costo del cache (embeddings, infraestructura) no se justifica

La regla de oro: cachea lo que es estable y repetitivo, deja pasar lo que es unico y contextual.

Resumen y Cierre

Pues alla lo tiene, parcero. Semantic cache es la optimizacion con mejor ROI que puedes meter a un sistema LLM en produccion. Con embeddings + Redis + cosine similarity reduces costos entre 50-80% y latencia en ordenes de magnitud. La implementacion basica son 100 lineas de Python; si quieres production-grade, GPTCache o LangChain te lo dan resuelto.

Lo importante es entender las tradeoffs: el threshold determina precision vs hit rate, el embedding model determina calidad del matching, y Redis determina velocidad. Ajusta segun tu caso de uso y mide hit rate continuamente. Cache bien calibrado es dinero y tiempo que te ahorras todos los dias.

La proxima vez que veas una factura de OpenAI de 4 cifras, pensa: cuanto de eso era la misma pregunta respondida 200 veces? Con semantic cache, esa pregunta se responde una sola vez.
