Prompt Engineering Advanced: Los Patrones que el 85% No Conoce

Hagale pues, parcero. Día 243 de este viaje por la IA y hoy nos metemos en el Prompt Engineering que de verdad importa: los patrones avanzados que separan las respuestas decentes de las extraordinarias. Si usted está todavía haciendo prompts sin estructura, esta entrega es pa' usted. Póngase comodo que esto está interesante.

El Problema con el Prompt Engineering Básico

La mayoría de la gente escribe prompts como si estuvieramandándole un WhatsApp a un amigo: "explícame lo del machine learning". Y sí, el modelo responde, pero no responde *bien*. No responde con la precisión, la estructura y la utilidad que usted podría obtener si supiera jugar con las palancas correctas.

El problema es que no está exploando el espacio de posibilidades que ofrecen los modelos modernos. Un LLM no es solo un chatbot que responde preguntas — es un sistema de reasoning que puede seguir cadenas de pensamiento, verificar sus propias respuestas, explorar múltiples caminos de solución, y reflexionar sobre sus errores. Pero para activar esas capacidades, usted necesita preguntar *de la manera correcta*.

Esto no es magia. Es ingeniería. Y hoy vamos a ver los patrones que lo separan del 85% que usa IA de forma básica.

Few-Shot Learning con Selección Inteligente de Ejemplos

¿Por qué few-shot funciona cuando funciona?

Few-shot learning es la capacidad de un LLM de aprender una tarea a partir de unos pocos ejemplos en el prompt. En lugar de explicarle al modelo cómo hacer algo, usted le *muestra* cómo se hace. Esto exploiting el ability del modelo de reconocer patrones en contexto — una habilidad que emerge de su entrenamiento en cantidades masivas de texto.

La matemática detrás de esto es elegante. Considere la verosimilitud de una respuesta dado el contexto:

$$P(respuesta \mid prompt, ejemplos) \propto \sum_i \log P(token_i \mid token_1...token_{i-1}, prompt, ejemplos)$$

El modelo no está "buscando" en los ejemplos como una base de datos. Está usando los ejemplos para calibrar la distribución de probabilidad sobre los tokens de salida. Cada ejemplo influencia cómo el modelo pesa diferentes features de la tarea.

El error del 70%: Muchos ejemplos que confunden

Aquí está el problema que la mayoría de la gente comete: creen que si 3 ejemplos funcionan bien, 10 ejemplos van a funcionar mejor. Y no es así. Aquí entra el principio de diminishing returns y algo más sutil: la interferencia contextual.

Cada ejemplo adicional diluye la señal de los anteriores. El modelo tiene que dividir su "atención" entre más patrones, y los ejemplos menos relevantes pueden introduce ruido que degrada la calidad de la respuesta. Esto es especialmente problemático cuando:

  • Los ejemplos son demasiado similares entre sí (redundancia sin nueva información)
  • Los ejemplos compiten por el mismo espacio semántico
  • Hay inconsistencias sutiles entre ejemplos que confunden al modelo

Algoritmo de Selección Inteligente de Ejemplos

La solución es usar un sistema de selección que maximice la diversidad informativa. En lugar de arbitrarily elegir ejemplos, seleccionamos aquellos que cubren diferentes aspectos de la tarea:

import numpy as np
from sklearn.metrics.pairwise import cosine_similarity

def select_diverse_examples(task_description, candidate_examples, k=5, n_candidates=20):
    """
    Selecciona k ejemplos que maximizan diversidad coverage.
    
    Estrategia: elegir ejemplos que maximicen la diversidad
    semántica mientras cubren diferentes aspectos de la tarea.
    """
    # 1. Embebeamos todos los candidatos y la descripción
    task_emb = embed(task_description)
    candidate_embs = [embed(ex["input"] + ex["output"]) for ex in candidate_examples]
    
    # 2. Calculamos similarity con la tarea
    task_sims = cosine_similarity([task_emb], candidate_embs)[0]
    
    # 3. Filtramos a los top n_candidates más relevantes
    top_indices = np.argsort(task_sims)[-n_candidates:]
    
    # 4. Greedy selection: máxima diversidad
    selected = []
    remaining = list(top_indices)
    
    while len(selected) < k and remaining:
        # Para cada candidato remaining, calculamos diversidad vs seleccionados
        best_candidate = None
        best_score = -float('inf')
        
        for idx in remaining:
            if not selected:
                score = task_sims[idx]  # Solo relevancia
            else:
                # Diversidad = 1 - avg similarity con seleccionados
                avg_sim = np.mean([
                    cosine_similarity([candidate_embs[idx]], [candidate_embs[s]])[0,0]
                    for s in selected
                ])
                # Balance: relevancia + diversidad
                score = 0.6 * task_sims[idx] + 0.4 * (1 - avg_sim)
            
            if score > best_score:
                best_score = score
                best_candidate = idx
        
        selected.append(best_candidate)
        remaining.remove(best_candidate)
    
    return [candidate_examples[i] for i in selected]


def build_few_shot_prompt(task_description, examples, user_query):
    """
    Construye prompt few-shot con ejemplos seleccionados.
    """
    prompt = f"""Tarea: {task_description}

Ejemplos de la tarea correctamente resuelta:
"""
    for i, ex in enumerate(examples):
        prompt += f"""
---
Ejemplo {i+1}:
Input: {ex['input']}
Output: {ex['output']}
---"""
    
    prompt += f"""

Ahora resuelve este caso:
Input: {user_query}
Output:"""
    return prompt

Este algoritmo resuelve un problema de optimización combinatorial: maximizar simultáneamente relevancia y diversidad. La selección greedy con el balance 60/40 entre relevancia y diversidad ha mostrado buenos resultados empíricamente. Ajuste esos pesos según su caso de uso.

Chain-of-Thought con Verificación

Por qué CoT simple puede empeorar las cosas

Chain-of-Thought (CoT) pidiendo "pensemos paso a paso" es probablemente la técnica más conocida de prompt engineering avanzado. Y funciona — hasta que no funciona.

El problema es que CoT sin verificación puede amplificar errores. El modelo genera una cadena de razonamiento, y si hay un error en un paso intermedio, los pasos subsiguientes típicamente construyen sobre ese error en lugar de corregirlo. Esto es lo que los investigadores llaman error propagation en cascada.

La distribución de probabilidad en cada paso está condicionada a todos los pasos anteriores:

$$P(step_n \mid steps_1...n-1, prompt)$$ → si step_k tiene error, $$P(step_n \mid steps_1...k-1, error)$$ puede ser completamente errado

CoT con Verification Loop

La solución es introducir un loop de verificación donde el modelo no solo genera el siguiente paso, sino que verifica los pasos anteriores:

def cot_with_verification(problem, model, max_iterations=5):
    """
    Chain-of-Thought con verificación en cada paso.
    
    El modelo genera un paso, luego verifica si es consistente
    con los pasos anteriores. Si no lo es, corrige.
    """
    reasoning = []
    verification_failures = []
    
    for iteration in range(max_iterations):
        # 1. Generar siguiente paso de razonamiento
        context = "\n".join([
            f"Paso {i+1}: {step}" for i, step in enumerate(reasoning)
        ])
        
        next_step = model.generate(f"""Razonamiento hasta ahora:
{context}

Problema: {problem}

Genera el PRÓXIMO paso de razonamiento. Sé específico y riguroso.""")
        
        reasoning.append(next_step.strip())
        
        # 2. Verificación: ¿es consistente con pasos anteriores?
        verification = model.generate(f"""Verifica si el último paso es consistente 
con el razonamiento previo.

Razonamiento previo:
{context}

Último paso: {next_step}

¿Hay contradicciones o inconsistencias? Si hay, explica cuáles son 
y qué corrección se necesita.""")
        
        if "CONTRADICCIÓN" in verification.upper() or "INCONSISTENTE" in verification.upper():
            verification_failures.append(iteration)
            
            # 3. Si hay error, generamos corrección
            correction = model.generate(f"""El paso anterior tiene un error. 
Corrige el razonamiento.

Razonamiento original:
{context}

Error detectado: {verification}

Genera una versión corregida del razonamiento completo.""")
            
            # Reemplazamos el paso malo
            reasoning = rebuild_reasoning(correction)
    
    return "\n".join([f"Paso {i+1}: {s}" for i, s in enumerate(reasoning)])


def rebuild_reasoning(correction_text):
    """
    Parsea texto de corrección y reconstruye lista de pasos.
    """
    steps = []
    for line in correction_text.split('\n'):
        line = line.strip()
        if line.startswith('Paso') or line.startswith('Step'):
            # Extraemos contenido después del número de paso
            if ':' in line:
                content = line.split(':', 1)[1].strip()
                steps.append(content)
            else:
                steps.append(line)
        elif line and not line.startswith('---') and not line.startswith('**'):
            steps.append(line)
    return steps

Este loop de verificación actúa como un mecanismo de auto-corrección. No es infalible — un modelo puede no detectar sus propios errores — pero reduce significativamente la tasa de errores propagados, especialmente en problemas de múltiples pasos donde la magnitud del error crece con cada paso.

Tree-of-Thought: Exploración Sistemática de Soluciones

Chain-of-Thought sigue una ruta lineal: un paso después de otro. Pero hay problemas donde explorar múltiples caminos en paralelo produce mejores resultados. Tree-of-Thought (ToT) hace exactamente eso: explícitamente mantiene múltiples ramas de razonamiento y evalúa cuál seguir.

Esto es especialmente útil para:

  • Problemas con múltiples heurísticas posibles
  • Tareas donde "volver atrás" es costoso
  • Casos donde la primera solución no es necesariamente la mejor
from dataclasses import dataclass, field
from typing import List, Optional
import heapq

@dataclass
class ThoughtNode:
    """Un nodo en el árbol de pensamiento."""
    content: str
    score: float
    parent: Optional['ThoughtNode'] = None
    children: List['ThoughtNode'] = field(default_factory=list)
    
    def get_path(self):
        """Reconstruye el camino desde la raíz hasta este nodo."""
        path = []
        node = self
        while node:
            path.append(node.content)
            node = node.parent
        return list(reversed(path))
    
    def __lt__(self, other):
        # Para heapq: mayor score = menor prioridad = se procesa primero
        return self.score > other.score


class TreeOfThoughts:
    def __init__(self, model, num_workers=3, max_depth=4, beam_width=3):
        self.model = model
        self.num_workers = num_workers
        self.max_depth = max_depth
        self.beam_width = beam_width  # Cuántas ramas mantener
        
    def generate_branches(self, thought: str, task: str, n: int = 3) -> List[str]:
        """Genera n ramas alternativas desde un pensamiento."""
        prompt = f"""Para el problema: {task}

Pensamiento actual: {thought}

Genera {n} ALTERNATIVAS diferentes para continuar este razonamiento.
Cada alternativa debe explorar un enfoque distinto.
Sé específico sobre qué hace diferente cada alternativa."""

        response = self.model.generate(prompt)
        branches = [b.strip() for b in response.split('\n') if b.strip()]
        return branches[:n]
    
    def evaluate_node(self, thought: str, task: str, goal_check: bool = False) -> float:
        """Evalúa qué tan prometedor es un nodo."""
        evaluation_prompt = f"""Evalúa este pensamiento intermedio:

Pensamiento: {thought}
Problema: {task}

Score de 0 a 10:
- 0-3: Irrelevante o errado
- 4-6: Parcialmente correcto pero incompleto
- 7-8: Prometedor, podría llevar a solución
- 9-10: Muy probable que lead a solución correcta

¿Este pensamiento está en el camino correcto? Score:"""
        
        response = self.model.generate(evaluation_prompt)
        # Parsear score del response
        try:
            score = float([c for c in response if c.isdigit()][0])
            return min(10, max(0, score))
        except:
            return 5.0  # Default neutral
    
    def solve(self, task: str, initial_prompt: str) -> str:
        """Ejecuta Tree-of-Thought para resolver una tarea."""
        # Nodo raíz
        root = ThoughtNode(content=initial_prompt, score=5.0)
        frontier = [root]  # Priority queue de nodos a expandir
        
        while frontier:
            # Tomamos el nodo más prometedor
            current = heapq.heappop(frontier)
            
            # ¿Es solución? Verificamos
            if self.evaluate_node(current.content, task, goal_check=True) >= 9:
                return "\n".join(current.get_path())
            
            # ¿Alcanzamos profundidad máxima?
            if len(current.get_path()) >= self.max_depth:
                continue
            
            # Expandimos
            branches = self.generate_branches(current.content, task, n=self.beam_width)
            
            for branch in branches:
                score = self.evaluate_node(branch, task)
                child = ThoughtNode(content=branch, score=score, parent=current)
                current.children.append(child)
                heapq.heappush(frontier, child)
        
        # Si se acaban las ramas, devolver mejor camino encontrado
        all_nodes = self._collect_all_nodes(root)
        return "\n".join(max(all_nodes, key=lambda n: n.score).get_path())
    
    def _collect_all_nodes(self, root: ThoughtNode) -> List[ThoughtNode]:
        nodes = [root]
        for child in root.children:
            nodes.extend(self._collect_all_nodes(child))
        return nodes

Tree-of-Thought es computacionalmente más caro que CoT — está generando y evaluando múltiples ramas — pero para problemas complejos donde una aproximación lineal falla, la diferencia en calidad puede ser dramática. Piénselo como búsqueda en amplitud vs profundidad en un espacio de soluciones.

Self-Consistency: El Poder de la Agregación

Self-consistency es una técnica dececeptivamente simple pero poderosa: en lugar de generar una solución, generamos múltiples soluciones y nos quedamos con la que más se repite. La intuición es que si diferentes cadenas de razonamiento convergen en la misma respuesta, es más probable que sea correcta.

La formalización es elegante:

$$\arg\max_c \sum_i P(r_i \text{ produce } c \mid prompt)$$

Es decir, la respuesta más consistente es aquella que maximiza la suma de probabilidades de ser producida por diferentes cadenas de razonamiento independientes.

def self_consistency(prompt, model, n_samples=10, temperature=0.7):
    """
    Self-consistency: múltiples soluciones, vote por mayoría.
    
    Args:
        prompt: El problema a resolver
        model: El LLM a usar
        n_samples: Número de soluciones a generar
        temperature: Creatividad en la generación (0.0 = determinista, 1.0 = muy random)
    """
    # Generamos n_samples razonamientos independientes
    responses = []
    for _ in range(n_samples):
        response = model.generate(
            prompt + "\n\nRazona cuidadosamente y proporciona tu respuesta final.",
            temperature=temperature
        )
        responses.append(response)
    
    # Extraemos la respuesta final de cada razonamiento
    final_answers = [extract_answer(r) for r in responses]
    
    # Vote counting
    from collections import Counter
    vote_counts = Counter(final_answers)
    
    # Devolvemos la respuesta más voted
    most_common = vote_counts.most_common(1)[0]
    winner = most_common[0]
    confidence = most_common[1] / n_samples
    
    return {
        "answer": winner,
        "confidence": confidence,
        "votes": dict(vote_counts),
        "reasoning_samples": responses
    }


def extract_answer(text: str) -> str:
    """
    Extrae la respuesta final de un razonamiento.
    Busca patrones como:
    - "La respuesta es: X"
    - "Therefore: X"
    - "Answer: X"
    - La última oración o número significativo
    """
    import re
    
    # Patrones comunes de respuesta
    patterns = [
        r"(?:la respuesta es|answer is|therefore|por lo tanto|the answer is)[:\s]+([A-Z0-9]+)",
        r"(?:respuesta|answer)[:\s]*([^\n.]+)",
        r"\$\$([^\$]+)\$\$",  # Math mode
        r"\$\s*([0-9.]+)\s*\$",  # Inline math
    ]
    
    for pattern in patterns:
        match = re.search(pattern, text, re.IGNORECASE)
        if match:
            return match.group(1).strip()
    
    # Fallback: última línea con número o contenido sustancial
    lines = [l.strip() for l in text.split('\n') if l.strip()]
    for line in reversed(lines):
        if any(c.isdigit() for c in line):
            return line
    return lines[-1] if lines else text

Self-consistency puede mejorar dramáticamente la accuracy en tareas de reasoning matemático y lógico. En experimentos del paper original, la técnica mejoró de 72% a 86% en GSM8K (un benchmark de problemas matemáticos de escuela). El tradeoff es lineal en costo: 10 samples = 10x el costo de una sola generación.

Reflexion: Cuando el Modelo Aprende de sus Errores

Reflexion lleva la auto-corrección un paso más allá. En lugar de solo verificar dentro de una generación, el modelo explícitamente reflexiona sobre su desempeño pasado y usa esa reflexión para mejorar futuras generaciones. Es como tener un meta-cognición que aprende de los fracasos.

class ReflexionAgent:
    """
    Agente que usa reflexión para mejorar iterativamente.
    
    El ciclo: actuar → observar resultado → reflexionar → actuar de nuevo
    """
    
    def __init__(self, actor_model, evaluator_model):
        self.actor = actor_model      # Genera tentativas de solución
        self.evaluator = evaluator_model  # Evalúa si la solución es correcta
        self.reflection_history = []  # Memorias de errores pasados
    
    def act(self, task: str, max_attempts: int = 3) -> dict:
        """
        Intenta resolver la tarea con reflexión.
        """
        for attempt in range(max_attempts):
            # 1. Construir prompt con historia de reflexión
            reflection_context = self._build_reflection_context()
            
            # 2. Generar tentativa
            attempt_prompt = f"""Tarea: {task}

{reflection_context}

{'Recuerda: en intentos anteriores fallaste por estas razones: ' + 
 str([r['error'] for r in self.reflection_history[-3:]]) if self.reflection_history else ''}

Genera una solución. Sé riguroso y evita los errores pasados."""
            
            solution = self.actor.generate(attempt_prompt)
            
            # 3. Evaluar si la solución es correcta
            evaluation = self.evaluator.generate(f"""Evalúa esta solución:

Tarea: {task}
Solución propuesta: {solution}

¿La solución es correcta? ¿Parcialmente correcta? ¿Errada?
Explica tu razonamiento.""")
            
            is_correct = self._parse_evaluation(evaluation)
            
            if is_correct:
                return {
                    "success": True,
                    "solution": solution,
                    "attempts": attempt + 1,
                    "reflection": evaluation
                }
            
            # 4. Si falló, reflexionar sobre el error
            reflection = self.actor.generate(f"""Analiza por qué esta solución falló:

Tarea: {task}
Tu solución: {solution}
Evaluación: {evaluation}

Explica en 1-2 oraciones:
1. ¿Cuál fue el error específico?
2. ¿Qué debes hacer diferente la próxima vez?

Escribe tu reflexión.""")
            
            self.reflection_history.append({
                "attempt": attempt,
                "solution": solution,
                "evaluation": evaluation,
                "reflection": reflection
            })
        
        return {
            "success": False,
            "solution": solution,
            "attempts": max_attempts,
            "reflection": evaluation,
            "history": self.reflection_history
        }
    
    def _build_reflection_context(self) -> str:
        """Construye contexto con memorias de reflexión."""
        if not self.reflection_history:
            return ""
        
        context = "\n\n=== HISTORIAL DE REFLEXIONES ===\n"
        for r in self.reflection_history[-3:]:  # Últimas 3 reflexiones
            context += f"- Error pasado: {r['reflection']}\n"
        return context
    
    def _parse_evaluation(self, evaluation: str) -> bool:
        """Determina si la evaluación indica éxito."""
        evaluation_lower = evaluation.lower()
        positive_indicators = ['correcta', 'correcta', 'bien', 'éxito', 'success', 'correct']
        negative_indicators = ['errada', 'incorrecta', 'mal', 'fallo', 'incorrect', 'wrong', 'error']
        
        # Cuenta indicadores
        pos_count = sum(1 for p in positive_indicators if p in evaluation_lower)
        neg_count = sum(1 for n in negative_indicators if n in evaluation_lower)
        
        return pos_count > neg_count

Reflexion es particularmente poderoso en tareas donde el espacio de errores es amplio y diverso, y donde aprender de errores pasados puede reducir significativamente el tiempo hasta una solución correcta. En tareas de coding, por ejemplo, un agente de Reflexion puede iterar sobre soluciones que fallan tests hasta encontrar una que pase.

Errores Comunes en Prompt Engineering Avanzado

Error 1: Too Many Examples que Causan Confusión

El problema: Muchos developers asumen que más ejemplos = mejor rendimiento. Agregan 10, 15, incluso 20 ejemplos en sus prompts few-shot. El resultado es frecuentemente el opuesto: el modelo se confunde, empieza a seguir patrones de los ejemplos menos relevantes, y la calidad de las respuestas baja.

Esto pasa porque el modelo tiene que "promediar" sobre todos los ejemplos, y si son diversos sin ser complementarios, está mezclando señales contradictorias. Además, ejemplos redundantes introducen costo (tokens) sin aportar información nueva.

La solución: Seleccionar 3-7 ejemplos que maximicen diversidad y cobertura. Idealmente, cada ejemplo debe aportar algo que los otros no tienen. Use el algoritmo de selección de ejemplos que mostré arriba — es simple de implementar y la diferencia en calidad es notable.

Error 2: Chain-of-Thought sin Verificación

El problema: Decir "pensemos paso a paso" y asumir que el razonamiento que emerge es correcto. En problemas de múltiples pasos, un error en el paso 2 corrompe todo el razonamiento subsecuente. El modelo no sabe que se equivocó — sigue adelante construyendo sobre su error como si fuera un hecho.

La solución: Implementar un loop de verificación después de cada paso mayor o al final del razonamiento. El verificador no necesita ser el mismo modelo — puede ser un modelo más pequeño o incluso un heuristic. Lo importante es que haya un checkpoint que valide la cadena antes de proceder.

Error 3: No Iterar sobre los Prompts Sistemáticamente

El problema: Escribir un prompt una vez, probar con 2-3 inputs, y si funciona "bien enough", usarlo en producción. Este enfoque ignora que los prompts son software que requiere iteración, testing, y medición. Prompts que funcionan para casos simples frecuentemente fallan en edge cases.

La solución: Tratar los prompts como código:

  • Versionar los prompts
  • Mantener un eval set de casos edge y casos comunes
  • Medir performance continuamente
  • Iterar basándose en datos, no en intuición

Herramientas como PromptLayer, Weights & Biases Prompts, o incluso un spreadsheet simple pueden hacer una diferencia enorme en la calidad final de sus sistemas basados en LLMs.

Resumen y Cierre

Hoy cubrimos los patrones de prompt engineering que separan el usage básico del uso avanzado: few-shot learning con selección inteligente de ejemplos, chain-of-thought con verificación, tree-of-thought para exploración sistemática, self-consistency para agregación de soluciones, y Reflexion para meta-cognición.

Cada técnica tiene su lugar. Few-shot es excelente cuando usted tiene ejemplos claros de la tarea. CoT brilla en problemas de razonamiento secuencial. ToT es para problemas donde explorar múltiples caminos es valioso. Self-consistency funciona cuando el costo de generar múltiples respuestas es acceptable y la consistencia importa. Y Reflexion es ideal para tareas iterativas donde aprender de errores pasadas mejora el resultado.

El común denominador: todas estas técnicas tratan el LLM como un sistema de reasoning que puede ser dirigido, no como un oráculo que simplemente responde. El modelo es una herramienta poderosa, pero como cualquier herramienta, su rendimiento depende de cómo la use.
