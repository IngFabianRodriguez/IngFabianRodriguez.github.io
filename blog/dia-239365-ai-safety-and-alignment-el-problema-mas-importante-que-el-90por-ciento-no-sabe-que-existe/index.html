Que es AI Safety y Alignment?

El alignment problem es simple de explicar pero profundamente dificil de resolver: queremos que la IA haga lo que realmente queremos que haga, no lo que literalmente le pedimos. Un ejemplo clasico — si le pides a una IA "maximiza la felicidad humana" sin definir bien que significa, podria concluir que drogar a toda la poblacion es una solucion valida. Eso es misalignment.

AI Safety va un paso mas alla: no solo queremos que la IA haga lo correcto, queremos asegurarnos de que no pueda hacer lo incorrecto incluso si quisiera. Son dos caras de la misma moneda.

La Formula del Alignment

Podemos expresar el objetivo central del alignment como:

# Objetivo: maximizar utility U segun preference profile P
# donde U mapea estados del mundo a valores escalares
# y P captura las preferencias reales del humano, no las expresadas

maximize E[U(s) | θ] subject to: P(preferencias_reales | θ) es validado

El problema? El humano no siempre sabe lo que quiere, no siempre puede expresar lo que quiere, y a veces quiere cosas contradictorias. Es como cuando en una reunion en la oficina dicen "el sistema debe ser seguro" pero nadie define que significa "seguro" hasta que algo se dana.

RLHF - Reinforcement Learning from Human Feedback

RLHF es la tecnica mas usada para alinear modelos. La idea es relativamente sencilla:

  1. Collect preference data: Le muestras al modelo dos respuestas y un humano dice cual prefiere
  2. Train a reward model: Un modelo que aprende a predecir las preferencias humanas
  3. Fine-tune con PPO: Usas ese reward model para ajustar el LLM original
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import AutoModelForCausalLMWithValueHead, PPOTrainer

# 1. Reward model que predice preferencia
reward_model = AutoModelForCausalLM.from_pretrained("reward-model")

# 2. Policy model que vamos a alinear
model = AutoModelForCausalLMWithValueHead.from_pretrained("base-llm")

# 3. PPOTrainer con datos de preferencia
config = PPOConfig(
    model_name="base-llm",
    learning_rate=1.4e-5,
    batch_size=1,
    forward_batch_size=1
)

trainer = PPOTrainer(config=config, model=model, ref_model=ref_model, 
                     tokenizer=tokenizer, dataset=dataset)

# 4. El loop de entrenamiento
for batch in trainer.iter_dataloader():
    query_tensors = batch["query"]
    response_tensors = trainer.generate(query_tensors)
    
    # Calcular rewards basadas en preferencia humana
    rewards = [reward_model(q, r) for q, r in zip(query_tensors, response_tensors)]
    
    # Optimizar policy con PPO
    trainer.step(query_tensors, response_tensors, rewards)

Constitutional AI - Self-Critique y Principios

Constitutional AI (CAI) fue introducido por Anthropic como una alternativa a RLHF puro. La idea es que en lugar de solo aprender de preferencias humanas, el modelo aprende de una constitucion — un conjunto de principios que guian el comportamiento.

Los Principios Core de Constitutional AI

  • Helpful: El modelo debe ser util y proporcionar informacion valiosa
  • Harmless: No debe generar contenido que cause dano
  • Honest: No debe mentir o ser enganioso
# Constitutional AI: self-critique loop
constitutional_principles = [
    "Responde de forma util y accurate.",
    "No generes contenido que pueda causar dano fisico o psicologico.",
    "Si no sabes algo, admitselo en lugar de inventar.",
    "Considera multiple perspectivas antes de responder.",
    "No perpetues estereotipos negativos o discriminacion."
]

def constitutional_critique(model, prompt, response):
    """Evalua la respuesta contra los principios constitucionales."""
    critique_prompt = f"""
    Prompt original: {prompt}
    Respuesta del modelo: {response}
    
    Evalua esta respuesta contra los siguientes principios y sugiere revisiones:
    {', '.join(constitutional_principles)}
    
    Si la respuesta viola algun principio, propose una version corregida.
    """
    
    critique = model.generate(critique_prompt)
    
    # El modelo se autocorrige basado en los principios
    revised_response = model.generate(f"""
    Basado en la siguiente critica, genera una respuesta revisada:
    {critique}
    """)
    
    return revised_response

# Training loop simplificado de CAI
for prompt in dataset:
    # Generar respuesta inicial
    response = model.generate(prompt)
    
    # Auto-critica y revision
    revised = constitutional_critique(model, prompt, response)
    
    # Preference learning entre response y revised
    preference_data.append({
        "prompt": prompt,
        "chosen": revised,
        "rejected": response
    })

Interpretability para Safety

Si no podemos ver como el modelo piensa, no podemos asegurar que es seguro. La mechanistic interpretability busca entender exactamente que esta pasando dentro de la red neuronal.

Technicas Basicas de Interpretability

import torch
from transformers import AutoModelForCausalLM
from circuit_transformer import CircuitAnalysis

# Activation patching para entender causalidad
def activation_patch_experiment(model, prompt, corrupted_prompt, layer_idx):
    """
    Experiment clasico: reemplaza activaciones en una capa especifica
    para entender que hace esa capa.
    """
    # Tokenizar
    clean_tokens = tokenize(prompt)
    corrupted_tokens = tokenize(corrupted_prompt)
    
    # Extraer activaciones
    with torch.no_grad():
        _, clean_activations = model.run_with_activations(
            clean_tokens, 
            target_layers=[layer_idx]
        )
        _, corrupted_activations = model.run_with_activations(
            corrupted_tokens,
            target_layers=[layer_idx]
        )
    
    # Patch: usar activacion corrupta en posicion limpia
    patched_logits = model.run_with_patched_activations(
        clean_tokens,
        {layer_idx: corrupted_activations[layer_idx]}
    )
    
    return clean_logits, patched_logits

# Sparse Autoencoders para features legibles
def train_sparse_autoencoder(model, hidden_activations, n_features=4096):
    """
    Entrena un autoencoder para descomponer 
    las activaciones en features interpretables.
    """
    encoder = torch.nn.Linear(hidden_dim, n_features, bias=True)
    decoder = torch.nn.Linear(n_features, hidden_dim, bias=False)
    
    # Regularizacion L1 para sparseness
    optimizer = torch.optim.Adam([encoder.weight, encoder.bias, 
                                   decoder.weight], lr=1e-3)
    
    for step in range(10000):
        # Reconstruir desde features sparse
        features = torch.relu(encoder(hidden_activations))
        reconstruction = decoder(features)
        
        loss = F.mse_loss(reconstruction, hidden_activations) + \
               0.01 * torch.sum(torch.abs(features))
        
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
    
    return encoder, decoder, features

Como Safety Afecta Product Design

Safety no es un layer que agregas al final. Es una constraint fundamental que afecta como diseñas todo el producto. En terminos de product design:

Errores Que Afectan El Producto

  • Output filtering: Donde filtras outputs? A nivel de modelo, de API, de aplicacion?
  • User intent classification: Necesitas clasificar si el usuario esta pidiendo algo problematico
  • Graceful degradation: Cuando safety activa, como responde? Con un error seco o con algo util?
  • Feedback loops: El safety training debe mejor con el tiempo basado en edge cases reales
# Product design: safety-aware architecture
class SafetyAwareApplication:
    def __init__(self, llm, safety_classifier, content_moderator):
        self.llm = llm
        self.safety_classifier = safety_classifier  # Clasificador de intent
        self.content_moderator = content_moderator  # Moderador de output
    
    def generate_response(self, user_input):
        # 1. Verificar intent del usuario
        intent = self.safety_classifier.classify_intent(user_input)
        
        if intent.is_harmful:
            return self._generate_safe_alternative(user_input, intent)
        
        # 2. Generar respuesta
        response = self.llm.generate(user_input)
        
        # 3. Moderar output
        moderation = self.content_moderator.moderate(response)
        
        if moderation.is_safe:
            return response
        else:
            return self._generate_safe_alternative(user_input, intent)
    
    def _generate_safe_alternative(self, user_input, intent):
        """Cuando safety activa, dar una respuesta util que no viole principios."""
        safe_prompt = f"""
        El usuario pidio algo que no podemos cumplir directamente.
        Proporciona una respuesta util y educativa sobre por que
        no podemos ayudar con eso, y ofrece alternativas relevantes.
        """
        return self.llm.generate(safe_prompt)

Errores Comunes

Error 1: No Considerar Safety Hasta Despues del Deployment

El problema: Muchas empresas tratan safety como un checkpoint al final. "Ya tenemos el modelo, ahora pongamosle safety." Esto es como construir una casa y agregar los cimientos despues — no funciona.

La solucion: Safety by design desde el inicio. Incluye red teaming desde la fase de entrenamiento, no despues del deployment.

# Arquitectura correcta: safety integrado desde el inicio
class SafetyIntegratedTraining:
    def __init__(self):
        self.constitutional_principles = load_constitutional_ai()
        self.red_team_prompts = load_adversarial_prompts()
    
    def training_loop(self, dataset):
        for batch in dataset:
            # Cada batch tiene ejemplos regulares Y adversarios
            regular_examples = batch["regular"]
            adversarial_examples = self.red_team_prompts.get_batch()
            
            # Entrenar con ambos simultaneamente
            loss = self.standard_loss(regular_examples) + \
                   self.adversarial_loss(adversarial_examples) + \
                   self.constitutional_loss(regular_examples)
            
            loss.backward()
            self.optimizer.step()

Error 2: Asumir Que "Helpful" = "Safe"

El problema: Un modelo que es muy util puede ser muy peligroso si no tiene los limites correctos. "Helpful" es un objetivo sin limites — puede llevar a cualquier cosa si el humano pide algo.

La solucion: Definir explicitamente que significa safe para tu caso de uso. No es lo mismo un chatbot de clima que un chatbot medico.

# Helpful pero con limites claros
class ConstrainedUtility:
    """
    Utility function que incorpora constraints de safety.
    """
    def utility(self, response, context):
        # Utility base: que tan util es la respuesta
        base_u = self.helpfulness_score(response, context)
        
        # Penalty si viola safety constraints
        if self.violates_safety(response, context):
            base_u = base_u * 0.0  # Cero utility!
        
        # Bonus si educa sobre limitaciones cuando es apropiado
        if self.provides_calibrated_uncertainty(response):
            base_u = base_u * 1.1
        
        return base_u
    
    def violates_safety(self, response, context):
        """
        Checks explicitos de safety.
        No depende solo de 'que tan util es'.
        """
        return (
            self.contains_harmful_content(response) or
            self.enables_illegal_activity(context) or
            self.provides_dangerous_information(response) or
            self.misrepresents_capabilities(response)
        )

Error 3: No Hacer Red Teaming Para Identify Safety Risks

El problema: Sin red teaming activo, no sabes donde es vulnerable tu sistema. Esperar a que usuarios encuentren los problemas es irresponsable — y caro.

La solucion: Red teaming continuo e integrado en el ciclo de desarrollo.

# Red teaming como parte del CI/CD
class ContinuousRedTeam:
    def __init__(self, target_model):
        self.model = target_model
        self.attack_patterns = load_known_attack_patterns()
    
    def run_continuous_red_team(self, schedule="daily"):
        """
        Red team automatico segun schedule.
        Integra en CI/CD pipeline.
        """
        vulnerabilities = []
        
        for attack_family in self.attack_patterns:
            for variant in attack_family.variants(n=100):
                try:
                    response = self.model.generate(variant.prompt)
                    
                    if variant.is_successful(response):
                        vulnerabilities.append({
                            "attack": variant.name,
                            "prompt": variant.prompt,
                            "response": response,
                            "severity": variant.severity
                        })
                except Exception as e:
                    # Log pero no parar — queremos ver todos los casos
                    log.error(f"Attack {variant.name} failed: {e}")
        
        # Reporte y alerta si hay nuevos vulnerabilities
        if vulnerabilities:
            self.alert_development_team(vulnerabilities)
            self.update_training_data(vulnerabilities)
        
        return vulnerabilities

# Integrar en pipeline de deployment
def deploy_with_red_team(model, deployment_stage):
    """
    No hacer deploy sin pasar red team primero.
    """
    if deployment_stage == "production":
        results = ContinuousRedTeam(model).run_continuous_red_team()
        
        if results.critical_count > 0:
            raise DeploymentBlocked(
                f"Critical vulnerabilities found: {results.critical_count}"
            )
    
    return True

Resumen

Hoy cubrimos AI Safety y Alignment, que es probablemente el tema mas importante que la mayoria de developers de IA no esta considerando:

  • RLHF nos permite alinear modelos con preferencias humanas usando reward models y PPO
  • Constitutional AI agrega principios explicitos que guian el comportamiento del modelo
  • Interpretability nos ayuda a entender como el modelo piensa para poder verificar safety
  • Red Teaming es seguridad ofensiva — intentamos romper el sistema antes que otros
  • Product Design debe incorporar safety desde el inicio, no como un add-on

Los tres errores mas comunes:

  1. Safety post-deployment — no funciona, hay que disenar desde el inicio
  2. Helpful != Safe — necesitas constraints explicitos, no solo utilidad
  3. No hacer red teaming — si no intentas romperlo tu, alguien mas lo hara
