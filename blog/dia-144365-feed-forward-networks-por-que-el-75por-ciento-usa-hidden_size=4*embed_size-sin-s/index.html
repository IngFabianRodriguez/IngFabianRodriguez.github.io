Feed Forward Networks - Por qué el 75% usa hidden_size=4*embed_size sin saber la intuición de Frankle

24 de april de 2026
torch.nn

Hola, parcero. Día 144 y hoy vamos con Feed-Forward Networks — las capas que el 75% configura como hidden_size = 4 * embed_size sin entender por qué. Ese "4x" viene de algún lado, pero no de la intuición de Frankle, ni de ningún paper fundamental. Es copy-paste puro. Acompañame a entender qué hace realmente el FFN dentro del Transformer.

📐 Feed-Forward en el Transformer — La matemática

Cada layer del Transformer tiene esta estructura:

$$\text{FFN}(x) = \max(0, xW_1 + b_1)W_2 + b_2$$

o equivalentemente:

$$\text{FFN}(x) = \text{GELU}(xW_1 + b_1)W_2 + b_2$$

en modelos modernos. El punto clave: FFN opera token-wise. A diferencia de attention, que mezcla información entre posiciones, FFN procesa cada token completamente independiente. Esto es exactamente lo que le permite capturar interacciones no-lineales entre features del mismo token.

Estructura:

  • Expansión: $d_{model} \rightarrow d_{ff}$ (típicamente $d_{ff} = 4 \times d_{model}$)
  • Activación: introduce no-linealidad (GELU en vez de ReLU)
  • Contracción: $d_{ff} \rightarrow d_{model}$

🧠 ¿Por qué FFN consume 2/3 del compute?

Este dato sorprende a muchos. En un Transformer layer típico:

  • Attention: $O(d_{model}^2 \cdot n)$ donde $n$ es seq_len
  • FFN: $O(d_{model} \cdot d_{ff})$ por token

Con $d_{ff} = 4d_{model}$ y seq_len típico de 512+ tokens, FFN domina el cómputo total. Es la razón por la que en modelos como LLaMA o Mistral se trabaja tan duro en optimizaciones de FFN (quantization, sparse MoE, etc.).

import torch
import torch.nn as nn
import torch.nn.functional as F
import math


# ============================================================
# FFN básico con diferentes activaciones
# ============================================================

class FeedForward(nn.Module):
    """
    FFN estándar: linear -> activation -> dropout -> linear
    """

    def __init__(self, d_model: int, d_ff: int, activation: str = 'gelu', dropout: float = 0.1):
        super().__init__()
        self.linear1 = nn.Linear(d_model, d_ff)
        self.activation = {
            'relu': nn.ReLU(),
            'gelu': nn.GELU(),
            'silu': nn.SiLU(),
            'swiglu': None,  # maneja separately
        }[activation]
        self.dropout = nn.Dropout(dropout)
        self.linear2 = nn.Linear(d_ff, d_model)

    def forward(self, x):
        x = self.linear1(x)
        if self.activation is not None:
            x = self.activation(x)
        x = self.dropout(x)
        x = self.linear2(x)
        return x


# ============================================================
# SwiGLU — la activación que usa LLaMA, Mistral, etc.
# ============================================================

class SwiGLU(nn.Module):
    """
    SwiGLU: SiLU(x) * sigmoid(x)
   paper: GLU Variants Improve Transformer (2020)
    Usado en: LLaMA, Mistral, Qwen, etc.
    """
    def __init__(self):
        super().__init__()

    def forward(self, x):
        return F.silu(x) * torch.sigmoid(x)


class SwiGLUFFN(nn.Module):
    """
    FFN con SwiGLU — usa 3 linear layers:
    W_gate, W_up, W_down

    FFN_SwiGLU(x) = SwiGLU(xW_gate) * (xW_up)W_down
    """
    def __init__(self, d_model: int, d_ff: int, dropout: float = 0.1):
        super().__init__()
        # El paper original usa d_ff = 4 * d_model
        # Pero con SwiGLU elff = d_ff / 2 porque tenemos 2 proyecciones
        self.w_gate = nn.Linear(d_model, d_ff, bias=False)
        self.w_up = nn.Linear(d_model, d_ff, bias=False)
        self.w_down = nn.Linear(d_ff, d_model, bias=False)
        self.swiglu = SwiGLU()
        self.dropout = nn.Dropout(dropout)

    def forward(self, x):
        # x: (batch, seq, d_model)
        gate = self.w_gate(x)           # (batch, seq, d_ff)
        up = self.w_up(x)               # (batch, seq, d_ff)
        gated = self.swiglu(gate) * up  # SwiGLU aplica silu al gate
        gated = self.dropout(gated)
        return self.w_down(gated)


# ============================================================
# Gated Linear Unit (GLU) — base de SwiGLU
# ============================================================

class GatedLinearUnit(nn.Module):
    """
    GLU: sigmoid(xW_gate) * (xW_up)
   paper: Language Modeling with Gated Convolutional Networks (2017)
    """
    def __init__(self, d_model: int, d_ff: int):
        super().__init__()
        self.w_gate = nn.Linear(d_model, d_ff, bias=False)
        self.w_up = nn.Linear(d_model, d_ff, bias=False)
        self.w_down = nn.Linear(d_ff, d_model, bias=False)

    def forward(self, x):
        gate = torch.sigmoid(self.w_gate(x))
        up = self.w_up(x)
        return self.w_down(gate * up)


# ============================================================
# FFN con residual connection — CRÍTICO para entrenar
# ============================================================

class TransformerBlock(nn.Module):
    """
    Un bloque completo de Transformer con residual connection en FFN.
    Sin residual, el gradiente apenas fluye y el entrenamiento es imposible.
    """
    def __init__(self, d_model: int, num_heads: int, d_ff: int, dropout: float = 0.1):
        super().__init__()
        self.attention = nn.MultiheadAttention(d_model, num_heads, dropout=dropout, batch_first=True)
        self.norm1 = nn.LayerNorm(d_model)
        self.norm2 = nn.LayerNorm(d_model)
        self.ffn = FeedForward(d_model, d_ff, activation='gelu', dropout=dropout)
        self.dropout = nn.Dropout(dropout)

    def forward(self, x, mask=None):
        # Attention con residual y norm
        attn_out, _ = self.attention(x, x, x, attn_mask=mask)
        x = self.norm1(x + self.dropout(attn_out))

        # FFN con residual y norm — ESTA es la conexión residual del FFN
        ffn_out = self.ffn(x)
        x = self.norm2(x + self.dropout(ffn_out))

        return x

class FFNWithResidual(nn.Module):
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.norm = nn.LayerNorm(d_model)
        self.ffn = FeedForward(d_model, d_ff, activation='gelu')

    def forward(self, x):
        return x + self.ffn(self.norm(x))  # residual!


class FFNWithoutResidual(nn.Module):
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.norm = nn.LayerNorm(d_model)
        self.ffn = FeedForward(d_model, d_ff, activation='gelu')

    def forward(self, x):
        return self.ffn(self.norm(x))  # SIN residual!


d_model = 128
d_ff = 512
ffn_res = FFNWithResidual(d_model, d_ff)
ffn_no_res = FFNWithoutResidual(d_model, d_ff)

# Pasar un input, calcular loss, y ver gradientes
x = torch.randn(2, 10, d_model)
target = torch.randn(2, 10, d_model)

# Loss simple MSE
for name, ffn in [('CON residual', ffn_res), ('SIN residual', ffn_no_res)]:
    ffn.zero_grad()
    out = ffn(x)
    loss = F.mse_loss(out, target)
    loss.backward()

    # Gradiente en el primer layer del FFN
    grad_norm = ffn.ffn.linear1.weight.grad.norm().item()
    print(f"  {name}: grad norm en linear1 = {grad_norm:.6f}")

print()
print("→ Sin residual, los gradientes pueden ser mucho más pequeños")
print("→ La skip connection permite que el gradiente fluya directamente")
print("→ Esto es especialmente crítico en redes profundas (12+ layers)")

🧠 GELU — Por qué优于 ReLU

ReLU tiene un problema fundamental: mata todos los valores negativos poniéndolos en cero. Esto es irrecuperable — la información negativa se pierde para siempre.

GELU (Gaussian Error Linear Unit):

$$\text{GELU}(x) = x \cdot \Phi(x) = x \cdot \frac{1}{2}\left[1 + \text{erf}\left(\frac{x}{\sqrt{2}}\right)\right]$$

近似为:

$$\text{GELU}(x) \approx 0.5x\left(1 + \tanh\left[\sqrt{\frac{2}{\pi}}(x + 0.044715x^3)\right]\right)$$

PyTorch usa esta aproximación para eficiencia. GELU:

  • Pondera los valores por su probabilidad (no los mata)
  • Es suave (diferenciable en todas partes)
  • Preserva información negativa para inputs con alta magnitud negativa

🔧 Expansion ratio — ¿realmente debe ser 4x?

El 4x viene del paper original "Attention Is All You Need". La intuición:

  • El FFN expande a un espacio más grande para capturar interacciones más ricas
  • 4x es un balance entre capacidad y compute
  • Se convirtió en convención porque funcionaba bien en la práctica

Pero no hay nada mágico en el 4x. En Paper "FiSM" y otros trabajos recientes muestran que:

  • Modelos pequeños se benefician de expansion ratios menores (2x-3x) para evitar overfitting
  • Modelos grandes pueden usar ratios mayores (4x-8x) sin problema
  • La relación óptima depende del dataset y la profundidad del modelo

🚨 Los 3 errores que verás en producción

Error 1: Usar expansion ratio de 4x sin pensar

Copiar ciegamente d_ff = 4 * d_model de tutoriales sin considerar el tamaño del modelo ni el dataset. Un modelo de 50M parámetros con 4x expansion puede tener más capacidad en FFN que la que necesita, causando overfitting.

Fix: Para modelos pequeños (d_model < 256), prueba expansion=2 o 3. Para modelos grandes (> 1024), 4x o mayor tiene sentido. Siempre haz ablations del expansion ratio.

# BAD: siempre 4x sin considerar el modelo
d_model = 128
d_ff = d_model * 4  # 512 → puede ser overkill para modelo pequeño

# GOOD: dependent del tamaño
d_model = 128
if d_model < 256:
    d_ff = d_model * 2  # 256 — suficiente
elif d_model < 768:
    d_ff = d_model * 4  # 512 — apropiado
else:
    d_ff = d_model * 4  # o mayor

Error 2: No usar residual connections en el FFN

Esto es devastable para el entrenamiento. Sin la skip connection x + FFN(x), los gradientes apenas fluyen a través del FFN en redes profundas. El modelo simplemente no entrena.

Fix: SIEMPRE usa residual connection en el FFN. La estructura correcta es output = x + FFN(LayerNorm(x)), donde el LayerNorm dentro del bloque es tan importante como la skip connection.

# BAD: sin residual
class BadTransformerBlock(nn.Module):
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.ffn = FeedForward(d_model, d_ff)
        self.norm = nn.LayerNorm(d_model)

    def forward(self, x):
        return self.norm(self.ffn(x))  # ← sin residual, gradientes estancados


# GOOD: con residual
class GoodTransformerBlock(nn.Module):
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.ffn = FeedForward(d_model, d_ff)
        self.norm = nn.LayerNorm(d_model)

    def forward(self, x):
        return x + self.ffn(self.norm(x))  # ← residual, gradientes fluyen

Error 3: Ignorar que FFN consume 2/3 del compute total

En modelos grandes, el FFN es el bottleneck de compute. Cuantizar solo los pesos de attention mientras se dejan los del FFN en fp32 es un error. La optimización de FFN (quantization, pruning, MoE) tiene el mayor impacto.

Fix: Al optimizar, prioriza el FFN. En quantization por ejemplo, 4-bit para FFN tiene más impacto que 4-bit para attention weights porque el FFN tiene ~3x más parámetros y compute.

# En un modelo como LLaMA-7B:
# - attention: ~3x7B * 0.5 = ~1GB (aproximado)
# - ffn: ~3x7B * 0.5 = ~2GB (aproximado)

# Optimizar FFN tiene 2x más impacto en footprint y velocidad
# que optimizar attention

📊 FFN como mixture of experts — la conexión

Esta es una perspectiva avanzada pero importante. Un FFN con SwiGLU:

$$\text{SwiGLU}(x) = \text{SiLU}(xW_{\text{gate}}) \odot (xW_{\text{up}})$$

puede verse como una forma simplificada de mixture of experts donde el gate modula qué tanto activa cada parte del expansion. En MoE real (como Switch Transformer), en vez de un solo FFN pesado, tienes múltiples FFNs "expertos" y un router que decide cuál usar por token.

SwiGLU es, en cierto sentido, un MoE de un solo experto con gate continuo — el gate aprende a ponderar diferentes subspaces de la representación.

✅ Resumen y cierre

Hoy cubrimos Feed-Forward Networks desde la matemática hasta los errores comunes. Los puntos clave:

  • FFN procesa cada token independientemente — attention mezcla entre posiciones, FFN procesa features locales
  • GELU > ReLU porque preserva información negativa (no la mata)
  • SwiGLU (LLaMA, Mistral) añade un gate interno que modula la información
  • Expansion ratio de 4x es convención, no ley — para modelos pequeños prueba 2x-3x
  • Residual connection en FFN NO es opcional — es lo que hace que el entrenamiento funcione
  • FFN consume ~2/3 del compute — al optimizar, priorízalo sobre attention

Ese 75% que usa 4x sin pensar? La próxima vez que configures un Transformer, ya sabes qué estás haciendo y por qué.
