🇨🇴 La Pecera Sin Memoria

Imagine que cada vez que usted entra a hablar con un LLM es como llegar a una cafetería en Bogotá donde el mesero no lo reconoce. No importa que ayer le contó sus problemas con el servidor de producción, hoy empieza de cero. Usted repite la historia completa otra vez. El mesero escucha atento, pero no recuerda nada. Así trabajan el 85% de las aplicaciones LLM hoy: cada request llega vacío, sin contexto previo, reconstruyendo todo desde el principio. En este artículo vamos a ver cómo cambiar eso con un sistema de memory management bien diseñado — y por qué el 85% de los desarrolladores no lo hace bien.

Short-Term vs Long-Term Memory en LLMs

Un LLM sin memoria es como un estudiante que cada vez que abre un libro nuevo no recuerda nada de lo que leyó ayer. Técnicamente, un LLM standard tiene un context window que actúa como su memoria de corto plazo: puede ver los últimos N tokens de la conversación y usarlos como referencia inmediata. Pero cuando la conversación se extiende o se necesita información de días o semanas anteriores, esa memoria de corto plazo simplemente no alcanza.

La short-term memory es el contexto que se mantiene dentro de una sesión: los mensajes recientes, el hilo de la conversación actual, los datos que acaban de pasarse. Se mide en tokens y tiene un límite físico impuesto por la arquitectura del modelo. Si usted está en un chat que lleva 50 mensajes, probablemente ya esté perdiendo información de los primeros.

La long-term memory es otra historia. Es el conocimiento acumulado sobre el usuario, preferencias, interacciones pasadas, facts relevantes. Esta información no cabe en el context window y necesita vivir en algún lugar externo: una base de datos, un vector store, un archivo. Sin long-term memory, cada conversación es un陌生人 (desconocido) para el modelo.

La Matemática de la Recuperación de Memoria

El retrieval de información en memory systems se basa principalmente en similarity search sobre embeddings. La idea central: convertir texto en vectores numéricos y encontrar los vectores más similares a la query actual.

Dados dos vectores $u$ y $v$ en $\mathbb{R}^d$, la similitud coseno se define como:

$$\text{sim}(u, v) = \frac{u \cdot v}{||u|| \cdot ||v||} = \frac{\sum_{i=1}^d u_i v_i}{\sqrt{\sum_{i=1}^d u_i^2} \cdot \sqrt{\sum_{i=1}^d v_i^2}}$$

Esta métrica produce valores en $[-1, 1]$, donde 1 significa vectores idénticos y valores cercanos a 0 significan ortogonales (sin relación semántica). En la práctica, para retrieval usamos embeddings como text-embedding-3-small de OpenAI que producen vectores de 1536 dimensiones.

Alternativamente, la distancia euclidiana:

$$d(u, v) = ||u - v||_2 = \sqrt{\sum_{i=1}^d (u_i - v_i)^2}$$

Para vectores normalizados, ambas métricas sonmonótonas entre sí (mayor similitud coseno = menor distancia euclidiana). En un vector store como FAISS o Chroma, el retrieval más cercano se hace con algoritmos aproximados como HNSW (Hierarchical Navigable Small World) que logran $O(\log N)$ en lugar de $O(N)$ para búsqueda exacta.

Arquitectura de un Memory Management System

Un sistema completo de memory management tiene cuatro componentes fundamentales:

  • Memory Store: dónde se persiste la información (vector DB, SQL, Redis)
  • Embedding Layer: convierte texto a vectores para similarity search
  • Retrieval Layer: dada una query, encuentra la información más relevante
  • Memory Lifecycle Manager: decide qué guardar, cuándo actualizar, cuándo borrar

El flujo básico es:

  1. Guardar: cada interacción relevante se embeddea y se almacena en el vector store junto con metadata (timestamp, tipo, usuario)
  2. Recuperar: cuando llega un request nuevo, la query se embeddea y se buscan los k documentos más similares
  3. Rankear: los resultados se reordenan por relevancia, recencia, u otros factores
  4. Insertar en contexto: los documentos más relevantes se incluyen en el prompt que va al LLM

Código: Implementando un Memory Management System

"""
LLM Memory Management System
Sistema de gestión de memoria para aplicaciones LLM.
"""

from dataclasses import dataclass, field
from datetime import datetime
from typing import Optional
from enum import Enum
import numpy as np
import json


class MemoryType(Enum):
    SHORT_TERM = "short_term"      # Memoria de la sesión actual
    LONG_TERM = "long_term"        # Memoria persistente entre sesiones
    EPISODIC = "episodic"           # Eventos o interacciones específicas
    SEMANTIC = "semantic"           # Conocimiento factual persistente


@dataclass
class MemoryItem:
    """Un item individual de memoria."""
    content: str                    # Texto o información almacenada
    memory_type: MemoryType         # Tipo de memoria
    embedding: Optional[np.ndarray] = None  # Vector del embedding
    created_at: datetime = field(default_factory=datetime.now)
    last_accessed: datetime = field(default_factory=datetime.now)
    access_count: int = 0
    importance_score: float = 1.0  # 0.0 a 1.0
    metadata: dict = field(default_factory=dict)

    def access(self):
        """Registra un acceso a esta memoria."""
        self.last_accessed = datetime.now()
        self.access_count += 1


class VectorStore:
    """
    Vector store simple para similarity search.
    En producción usar: FAISS, Chroma, Pinecone, Weaviate.
    """

    def __init__(self, dimension: int = 1536, threshold: float = 0.7):
        self.dimension = dimension
        self.threshold = threshold
        self.vectors: list[np.ndarray] = []
        self.items: list[MemoryItem] = []

    def add(self, item: MemoryItem):
        """Agrega un item al vector store."""
        self.items.append(item)
        self.vectors.append(item.embedding)

    def search(self, query_embedding: np.ndarray, top_k: int = 5) -> list[MemoryItem]:
        """
        Búsqueda por similitud coseno.
        Retorna los top_k items más similares sobre el threshold.
        """
        if not self.vectors:
            return []

        # Calcular similitud coseno con todos los vectores
        similarities = []
        query_norm = np.linalg.norm(query_embedding)
        if query_norm == 0:
            return []

        for vec in self.vectors:
            vec_norm = np.linalg.norm(vec)
            if vec_norm == 0:
                similarities.append(0.0)
                continue
            sim = np.dot(query_embedding, vec) / (query_norm * vec_norm)
            similarities.append(sim)

        # Ordenar por similitud y retornar top_k sobre threshold
        indexed = [(i, sim) for i, sim in enumerate(similarities)]
        indexed.sort(key=lambda x: x[1], reverse=True)

        results = []
        for idx, sim in indexed[:top_k]:
            if sim >= self.threshold:
                self.items[idx].access()  # Registrar acceso
                results.append(self.items[idx])

        return results

    def delete(self, item_id: str):
        """Elimina un item del store."""
        # En un sistema real usar id como índice
        pass


class MemoryManager:
    """
    Gestor central de memoria para aplicaciones LLM.
    Maneja el ciclo de vida completo: guardar, recuperar, olvidar.
    """

    def __init__(
        self,
        vector_store: VectorStore,
        short_term_limit: int = 10,       # Máx items en short-term
        long_term_threshold: float = 0.8,  # Score mínimo para guardar en long-term
        forget_after_days: int = 30        # Días antes de considerar olvidado
    ):
        self.vector_store = vector_store
        self.short_term_limit = short_term_limit
        self.long_term_threshold = long_term_threshold
        self.forget_after_days = forget_after_days

        self.short_term_memory: list[MemoryItem] = []
        self.long_term_memory: VectorStore = VectorStore(threshold=0.6)

    def store_interaction(
        self,
        content: str,
        memory_type: MemoryType,
        embedding: np.ndarray,
        importance: float = 1.0,
        metadata: dict = None
    ):
        """
        Almacena una nueva interacción en el sistema de memoria.
        Decide automáticamente si va a short-term o long-term.
        """
        item = MemoryItem(
            content=content,
            memory_type=memory_type,
            embedding=embedding,
            importance_score=importance,
            metadata=metadata or {}
        )

        if memory_type == MemoryType.SHORT_TERM:
            self._add_short_term(item)
        else:
            self._add_long_term(item, embedding)

    def _add_short_term(self, item: MemoryItem):
        """Agrega a memoria de corto plazo con gestión de límite."""
        self.short_term_memory.append(item)
        # Si excede el límite, comprimir (agregar a long-term los menos importantes)
        if len(self.short_term_memory) > self.short_term_limit:
            self._compress_short_term()

    def _compress_short_term(self):
        """Comprime short-term: los items menos importantes van a long-term."""
        # Ordenar por importance_score * log(access_count + 1)
        scored = [
            (item, item.importance_score * np.log1p(item.access_count))
            for item in self.short_term_memory
        ]
        scored.sort(key=lambda x: x[1])

        # Los del fondo van a long-term
        to_promote = scored[:2]  # Promover los 2 menos importantes
        self.short_term_memory = [item for item, _ in scored[2:]]

        for item, _ in to_promote:
            if item.embedding is not None:
                item.memory_type = MemoryType.LONG_TERM
                self._add_long_term(item, item.embedding)

    def _add_long_term(self, item: MemoryItem, embedding: np.ndarray):
        """Agrega a memoria de largo plazo en el vector store."""
        self.long_term_memory.add(item)

    def retrieve(
        self,
        query_embedding: np.ndarray,
        top_k: int = 5,
        include_short_term: bool = True
    ) -> list[MemoryItem]:
        """
        Recupera memorias relevantes para la query actual.
        Combina resultados de short-term y long-term.
        """
        results = []

        # Short-term: búsqueda directa por relevancia semántica
        if include_short_term and self.short_term_memory:
            # Embed short-term items para buscar
            st_embeddings = [item.embedding for item in self.short_term_memory
                           if item.embedding is not None]
            if st_embeddings:
                # Buscar en short-term con threshold más bajo
                st_store = VectorStore(threshold=0.0)
                for item in self.short_term_memory:
                    if item.embedding is not None:
                        st_store.add(item)
                st_results = st_store.search(query_embedding, top_k=top_k)
                results.extend(st_results)

        # Long-term: similarity search en vector store
        lt_results = self.vector_store.search(query_embedding, top_k=top_k)
        results.extend(lt_results)

        # Deduplicación y reordenamiento
        seen = set()
        unique_results = []
        for item in results:
            if item.content not in seen:
                seen.add(item.content)
                unique_results.append(item)

        # Reordenar: short-term primero, luego por score combinado
        unique_results.sort(
            key=lambda x: (
                x.memory_type == MemoryType.SHORT_TERM,
                x.importance_score * np.log1p(x.access_count),
                x.last_accessed
            ),
            reverse=True
        )

        return unique_results[:top_k]

    def build_context(self, query_embedding: np.ndarray, max_tokens: int = 4000) -> str:
        """
        Construye el contexto de memoria para insertar en el prompt del LLM.
        """
        memories = self.retrieve(query_embedding, top_k=10)
        context_parts = []

        for mem in memories:
            age = (datetime.now() - mem.created_at).days
            type_label = mem.memory_type.value.upper()
            context_parts.append(
                f"[{type_label} ({age}d ago)]: {mem.content}"
            )

        return "\n\n".join(context_parts)

    def forget_old_memories(self):
        """
        Elimina memorias que han pasado el umbral de olvido.
        Implementa el ciclo de vida: store → age → forget.
        """
        cutoff = datetime.now()
        items_to_remove = []

        for item in self.short_term_memory:
            age = (cutoff - item.created_at).days
            if age > self.forget_after_days and item.access_count < 3:
                items_to_remove.append(item)

        for item in items_to_remove:
            self.short_term_memory.remove(item)

def simulate_embedding(text: str) -> np.ndarray:
    """Simula un embedding. En producción usar OpenAI/HuggingFace."""
    # Hash simple para reproducibilidad
    np.random.seed(hash(text) % (2**32))
    vec = np.random.randn(1536)
    return vec / np.linalg.norm(vec)

if __name__ == "__main__":

    memory = MemoryManager(

    )

    # Simular interacciones del usuario
    interactions = [

        ("Está evaluando Pinecone para producción", MemoryType.SEMANTIC, 0.75),
    ]

    for text, mem_type, importance in interactions:
        emb = simulate_embedding(text)

    print("=== Memorias recuperadas ===")
    for mem in relevant:
        print(f"[{mem.memory_type.value}] {mem.content[:60]}... (score: {mem.importance_score:.2f})")

    # Construir contexto para el prompt

    print("\n=== Contexto para LLM ===")
    print(context[:300] + "..." if len(context) > 300 else context)

Los 3 Errores Comunes (y Sus Soluciones)

Error 1: Empezar de Cero en Cada Request

El error más frecuente. Cada vez que llega un mensaje, la aplicación no tiene forma de saber quién es el usuario, qué ha pedido antes, o qué preferencias tiene. El resultado: conversaciones repetitivas, prompts inflados con contexto redundante, y un LLM que actúa como si fuera la primera vez que habla con usted.

Solución: Implementar un MemoryManager centralizado que persista interacciones relevantes entre requests. Usar una sesión o user_id para mantener continuidad. Antes de procesar cada request nuevo, llamar a retrieve() para traer contexto previo e incluirlo en el prompt.

# Antes de cada request: recuperar contexto
user_id = get_current_user_id()
query_embedding = get_embedding(current_message)
memories = memory_manager.retrieve(query_embedding, user_id=user_id)
context = format_memories_for_prompt(memories)
full_prompt = system_prompt + context + current_message

Error 2: Guardar Todo Sin Gestión

El extremo opuesto. Guardar cada mensaje, cada token, cada interacción sin filtro ni lifecycle management. Esto genera un vector store que crece descontroladamente, retrieval lento y ruidoso (recuperando basura irrelevante), y costos de almacenamiento que se disparan.

Solución: Implementar importancia scores y políticas de retención. No todo merece ser recordado. Los facts sobre preferencias del usuario sí; el "¿hola cómo estás?" no. Usar importance_score y access_count para decidir qué promoted a long-term y qué se olvida. Definir un forget_after_days con criterios claros.

# Solo guardar si supera umbral de importancia
if importance_score > 0.6:
    memory_manager.store_interaction(
        content, memory_type, embedding, importance_score
    )

# Olvidar memorias viejas y poco accedidas
memory_manager.forget_old_memories()

Error 3: No Usar Vector Databases para Retrieval

Intentar hacer retrieval por búsqueda exacta de keywords, expresiones regulares, o simplesmente pasar todo el historial como contexto. Esto es computacionalmente costoso (O(N) por query), no escala, y no entiende semántica — si el usuario pregunta por "el problema con la base de datos" y guardó "error conectando a PostgreSQL", una búsqueda por keywords no lo encuentra.

Solución: Usar un vector database real. Opciones:

  • FAISS (Facebook): extremadamente rápido, local, great para producción
  • Chroma: simple de usar, good para prototyping
  • Pinecone/Weaviate: cloud-native, escala automática
  • Qdrant: Rust-based, performante y con filtering avanzado
# Production-grade retrieval con FAISS
import faiss
import numpy as np

class FAISSVectorStore:
    def __init__(self, dimension: int = 1536):
        self.index = faiss.IndexFlatIP(dimension)  # Inner product = cos similarity
        self.items = []

    def add(self, item: MemoryItem):
        # Normalizar para similitud coseno
        vec = item.embedding.reshape(1, -1).astype('float32')
        faiss.normalize_L2(vec)
        self.index.add(vec)
        self.items.append(item)

    def search(self, query: np.ndarray, k: int = 5) -> list[MemoryItem]:
        q = query.reshape(1, -1).astype('float32')
        faiss.normalize_L2(q)
        distances, indices = self.index.search(q, k)
        return [self.items[i] for i in indices[0] if i < len(self.items)]

Resumen y Cierre

El memory management en LLMs no es un lujo — es una necesidad para aplicaciones que quieren sentirse inteligentes y personalizadas. La diferencia entre una app que empieza de cero cada vez y una que recuerda está en la arquitectura de memoria que usted diseña.

Los puntos clave:

  • Distinguir entre short-term (sesión actual) y long-term (persistente)
  • Usar similarity search sobre embeddings para retrieval, no keywords
  • Implementar lifecycle management: no guardar todo, no olvidar todo
  • Medir retrieval latency y precision para iterar sobre el sistema

En Bogotá tenemos una frase: "lo que no se recuerda, se vuelve a vivir". Para las aplicaciones LLM, cada vez que empieza de cero es tiempo perdido, dinero desperdiciado en tokens redundantes, y una experiencia de usuario que se siente tonta. Construya su memory system bien desde el principio — el 85% de las apps no lo hace, y eso es exactamente lo que separa una herramienta decente de una que realmente funciona.
