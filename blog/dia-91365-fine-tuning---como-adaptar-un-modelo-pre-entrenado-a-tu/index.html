Fine-tuning - Cómo Adaptar un Modelo Pre-entrenado a tu Caso sin Perder el Poder del Original

¿Qué es el Fine-Tuning y Por Qué es la Joya de la Corona?

Aquí en Colombia, cuando alguien aprende a tocar Vallenato, no empieza de cero cada vez que cambia de canción — usa los ritmos que ya tiene y los adapta. Eso es exactamente lo que hace fine-tuning en machine learning: tomar un modelo que ya sabe mucho (pre-entrenado) y especializarlo en tu tarea particular sin destruir todo lo que aprendió antes.

Un modelo pre-entrenado como Llama-3 o Mistral viene cargado con conocimiento general del mundo. Fine-tuning es el proceso de continuar el entrenamiento sobre tu dataset específico para que el modelo responda mejor a tu dominio: soporte técnico médico, análisis de contratos legales, clasificación de reseñas de productos colombianos, o lo que necesites.

Full Fine-Tuning vs PEFT: La Batalla Central

Full Fine-Tuning: Todo el Poder, Todos los Problemas

Full fine-tuning significa entrenar todos los parámetros del modelo. Si tienes un modelo de 7 mil millones de parámetros (7B), estás actualizando los 7B. El resultado es excelente en calidad, pero:

  • Costo de VRAM: 7B × FP32 = ~28 GB solo para pesos. Con gradientes y optimizador, fácil 80+ GB.
  • Tiempo: Entrenar semanas en GPUs potentes.
  • Catastrophic forgetting: Puedes hacer que el modelo olvide capacidades generales.
  • Despliegue difícil: Cada tarea necesitaría un modelo completo separado.

PEFT: Entrena Poco, Obtén Mucho

PEFT (Parameter-Efficient Fine-Tuning) cambia la ecuación radicalmente. En lugar de entrenar todos los parámetros, solo entrenas un conjunto pequeño de nuevos parámetros agregados al modelo original. Los pesos pre-entrenados se congelan.

Las técnicas principales:

  • LoRA (Low-Rank Adaptation): Añade pares de matrices descomprimidas cerca de las capas de atención.
  • QLoRA: LoRA sobre modelos cuantizados (4-bit NormalFloat).
  • Adapter Layers: Pequeñas redes feed-forward insertadas entre capas del transformer.

LoRA en Detalle: La Matemática del Ajuste Eficiente

La idea central de LoRA es elegante. Una capa lineal original tiene:

Y = W · X + b

Donde W ∈ ℝd×k. En fine-tuning normal, actualizas W directamente: W' = W + ΔW. El problema es que ΔW tiene la misma forma que W — potencialmente enorme.

LoRA propone descomponer ΔW como producto de dos matrices pequeñas:

ΔW = B · A   donde  B ∈ ℝd×r,  A ∈ ℝr×k

Con r << min(d, k) (el rank). Entonces:

Y = W · X + B · A · X + b

Solo entrenas B y A. Las dimensiones de entrenamiento pasan de d×k a d×r + r×k = r(d+k). Para d=4096, k=4096, r=8: de 16M parámetros a solo 65K. 250x menos.

Configuración Clave de LoRA

# Configuración típica de LoRA
lora_config = {
    "r": 8,                    # rank — mayor = más capacidad, más params
    "lora_alpha": 16,          # scaling factor — típicamente 2x el rank
    "target_modules": ["q_proj", "v_proj"],  # capas donde aplicar LoRA
    "lora_dropout": 0.05,      # regularización
    "bias": "none",            # no entrenar sesgos
    "task_type": "CAUSAL_LM",  # tipo de tarea
}

La scaling factor lora_alpha controla cuánto impacto tienen las adaptaciones LoRA. El scaling real es lora_alpha / r, entonces con r=8, alpha=16 el scaling es 2.0.

QLoRA: LoRA Cuantizado — Más Poder con Menos VRAM

QLoRA (Quantized Low-Rank Adaptation), propuesto por Tim Dettmers, lleva la eficiencia un paso más allá. Primero se carga el modelo completo en 4-bit NormalFloat (NF4), y luego se aplica LoRA sobre esa base cuantizada.

¿Por qué 4-bit NormalFloat?

NF4 no es una cuantización uniforme. Está diseñada específicamente para que los valores de los pesos de redes neuronales (que siguen una distribución cercana a N(0, 0.02)) se distribuyan equitativamente en los 16 niveles de 4-bit. Esto minimiza el error de cuantización.

El pipeline QLoRA:

# 1. Cargar modelo base en 4-bit NF con bitsandbytes
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",          # NormalFloat 4-bit
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,      # cuantización anidada
)

# 2. Aplicar LoRA sobre el modelo cuantizado
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3-8b",
    quantization_config=bnb_config,
    device_map="auto",
)

# 3. Solo se desatacan los adaptadores LoRA en FP16/BF16
# Los pesos base permanecen en 4-bit

El resultado: un modelo de 8B en ~4-5 GB de VRAM. Sin QLoRA necesitarías 40+ GB.

Adapters: Otra Forma de PEFT

Los Adapter Layers son pequeñas redes feed-forward insertadas después de las capas de atención en cada bloque transformer. A diferencia de LoRA que modifica las conexiones existentes, los adapters agregan capacidad computacional.

# Arquitectura adapter típica
class AdapterLayer(nn.Module):
    def __init__(self, d_model, reduction_factor=16):
        super().__init__()
        self.down = nn.Linear(d_model, d_model // reduction_factor)
        self.activation = nn.GELU()
        self.up = nn.Linear(d_model // reduction_factor, d_model)
        self.layer_norm = nn.LayerNorm(d_model)

    def forward(self, x):
        residual = x
        x = self.layer_norm(x)
        x = self.down(x)
        x = self.activation(x)
        x = self.up(x)
        return x + residual  # conexión residual

Los adapters son menos comunes que LoRA en 2026 porque LoRA tiene mejor soporte y resultados más consistentes, pero siguen siendo útiles para multi-task learning donde quieres un adapter por tarea.

¿Cuándo Fine-Tunar vs RAG vs Prompting?

Esta es la pregunta del millón y la respuesta define proyectos enteros:

Usa Prompting Simple (Zero/Few-Shot)

  • El modelo ya sabe la tarea bien
  • No tienes datos etiquetados
  • Es una tarea abierta o creativa
  • Necesitas flexibilidad máxima

Usa RAG (Retrieval-Augmented Generation)

  • El modelo necesita información específica y actualizada
  • Tienes documentos de referencia grandes
  • Necesitas citas y verificabilidad
  • La tarea es más de búsqueda que de generación pura
Error común colombiano: "Tengo muchos datos de soporte técnico, voy a fine-tunear". ¡Espera! Si tus datos son knowledge-heavy (documentación, manuales, knowledge base), RAG probablemente es mejor. Fine-tuning es para estilos, formatos y patrones, no para meter hechos en el modelo.

Usa Fine-Tuning (preferiblemente LoRA/QLoRA)

  • Quieres enseñarle un nuevo formato de salida
  • Necesitas que el modelo siga instrucciones muy específicas
  • Tienes datos etiquetados de calidad
  • Quieres que el modelo adopte un tono o estilo particular
  • La inferencia debe ser barata y rápida (despliegue de adapters)

El Error Crítico: Learning Rate 10x Mayor para la Cabeza

Este es probablemente el error más frecuente en fine-tuning que veo, incluso en tutoriales publicados. Cuando aplicas LoRA o full fine-tuning:

# MAL: mismo learning rate para todo
optimizer = torch.optim.AdamW(model.parameters(), lr=2e-4)

# BIEN: learning rate 10x mayor para la cabeza (output layer)
optimizer = torch.optim.AdamW(
    [
        {"params": model.model.parameters(), "lr": 2e-4},   # backbone
        {"params": model.lm_head.parameters(), "lr": 2e-3}, # cabeza — 10x
    ]
)

¿Por qué? La cabeza (lm_head) es la que aprende a proyectar representaciones a tokens. Los pesos pre-entrenados del backbone ya tienen buenas representaciones — solo necesitan ajustarse suavemente. Pero la cabeza necesita aprender desde cero mappings que probablemente son muy diferentes a los del pre-entrenamiento (especialmente si cambias el vocabulario o el formato de salida).

Matemáticamente, el gradiente de la cabeza es ∼10x más grande en magnitud al inicio del entrenamiento. Usar el mismo LR causa que la cabeza se mueva erráticamente mientras el backbone se arrastra. Separar los LR corrige este desbalance.

# Con LoRA, los parámetros se dividen así:
optimizer = torch.optim.AdamW(
    [
        {"params": model.model.lora.parameters(), "lr": 2e-4},  # LoRA adapters
        {"params": model.lm_head.parameters(), "lr": 2e-3},     # cabeza — 10x
    ]
)

Implementación Completa: LoRA + QLoRA en PyTorch

"""
Fine-tuning con LoRA y QLoRA — Día 91 #365DaysOfAI
Implementación completa: modelo cuantizado + LoRA + training loop
"""
import torch
import torch.nn as nn
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    BitsAndBytesConfig,
    TrainingArguments,
    Trainer,
)
from peft import LoraConfig, get_peft_model, TaskType
import bitsandbytes as bnb
from typing import List, Dict
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


# ─── 1. CONFIGURACIÓN DE QLoRA ────────────────────────────────────────────
def get_bnb_config() -> BitsAndBytesConfig:
    """Configuración bitsandbytes para cuantización 4-bit NormalFloat."""
    return BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_quant_type="nf4",             # NormalFloat de 4-bit
        bnb_4bit_compute_dtype=torch.bfloat16, # Precisión para cálculos
        bnb_4bit_use_double_quant=True,       # Cuantización anidada (ahorra ~0.4 bits/param)
    )


# ─── 2. CONFIGURACIÓN DE LORA ───────────────────────────────────────────────
def get_lora_config() -> LoraConfig:
    return LoraConfig(
        r=8,                           # Rank de descomposición
        lora_alpha=16,                 # Scaling = alpha/r = 2.0
        target_modules=[               # Módulos donde inyectar LoRA
            "q_proj",                  # Proyección de queries
            "v_proj",                  # Proyección de valores
        ],
        lora_dropout=0.05,             # Dropout para regularización
        bias="none",                   # No entrenar biases
        task_type=TaskType.CAUSAL_LM,  # Modelo de lenguaje causal
    )


# ─── 3. CARGA DEL MODELO CON QLoRA ─────────────────────────────────────────
def load_model_with_qlora(model_name: str, lora_config: LoraConfig):
    logger.info(f"Cargando modelo base: {model_name}")
    
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    tokenizer.pad_token = tokenizer.eos_token
    
    bnb_config = get_bnb_config()
    
    model = AutoModelForCausalLM.from_pretrained(
        model_name,
        quantization_config=bnb_config,
        device_map="auto",
        trust_remote_code=True,
    )
    
    logger.info("Modelo cargado en 4-bit NormalFloat")
    
    from peft import prepare_model_for_kbit_training
    model = prepare_model_for_kbit_training(
        model,
        use_gradient_checkpointing=True,
    )
    
    logger.info("Aplicando LoRA adaptadores...")
    model = get_peft_model(model, lora_config)
    
    trainable_params, all_params = 0, 0
    for _, param in model.named_parameters():
        all_params += param.numel()
        if param.requires_grad:
            trainable_params += param.numel()
    
    logger.info(
        f"Parámetros entrenables: {trainable_params:,} / {all_params:,} "
        f"({100 * trainable_params / all_params:.2f}%)"
    )
    
    return model, tokenizer

Errores Comunes y sus Soluciones

Error 1: Olvidar descongelar la Layer Norm al hacer LoRA

# MAL: la layer norm puede quedar congelada

# BIEN: asegurar que las capas necesarias se descongelan explícitamente
for name, param in model.named_parameters():
    if "LayerNorm" in name or "bias" in name:
        param.requires_grad = True  # Descongelar explícitamente

Error 2: LR demasiado alto para LoRA → diverge el entrenamiento

# MAL: usar 1e-3 como en fine-tuning completo
# LoRA tiene menos parámetros, necesita LR más pequeño

# BIEN: LR típico para LoRA es 1e-4 a 3e-4
optimizer = torch.optim.AdamW(
    [{"params": model.model.parameters(), "lr": 2e-4}],
)

Error 3: No usar gradient checkpointing en QLoRA → OOM

# BIEN: habilitar gradient checkpointing para ahorrar ~60% VRAM
model.gradient_checkpointing_enable()
model.enable_input_require_grads()

Resumen: El Arte de Adaptar sin Destruir

Fine-tuning es la herramienta para cuando necesitas que un modelo haga algo específico que no logra con prompting o RAG. LoRA y QLoRA hicieron que esta técnica fuera accesible para cualquiera con una GPU decente — ya no necesitas un cluster de H100 para especializar un modelo de 7B parámetros.

Las claves para que no te salga el tiro por la culata:

  • Si tienes menos de 1,000 ejemplos etiquetados de calidad, no fine-tunear — usa few-shot prompting.
  • Si tu tarea es knowledge-heavy con documentos grandes, RAG es tu amigo.
  • Si necesitas cambiar formato, estilo o comportamiento, fine-tunea con LoRA.
  • Recuerda siempre el LR 10x mayor para la cabeza.
  • Cuantiza a 4-bit NF con bitsandbytes antes de aplicar LoRA (QLoRA).

En Colombia tenemos la ventaja de que el español es una lengua con recursos limitados comparado con el inglés. Fine-tuning de modelos en español no solo mejora la calidad — devuelve identidad lingüística a la tecnología. Un modelo que responde en jerga colombiana, que entiende el contexto criollo, es infinitamente más útil para nosotros que uno que solo conoce expresiones de Silicon Valley.

La próxima vez que tengas un problema de ML y pienses "voy a fine-tunear", respira hondo, mira los puntos anteriores y pregúntate: ¿es realmente fine-tuning lo que necesito, o estoy frente a un problema que se resuelve con un buen prompt?

Nos vemos el Día 92 hablando de Prompt Engineering — porque a veces la mejor técnica es la que no necesitas entrenar.
