Quantization - Modelos Pequeños y Eficientes

Hagale pues, mi gente

Qué más pues, mi gente querida. Aquí andamos en el Día 249 hablando de algo que hoy día es critical para hacer que los modelos grandes funcionen en hardware modesto: Quantization. Resulta que tienes un modelo de 70B parámetros y quieres correrlo en tu laptop con 16GB de RAM. ¿Cómo lo haces? Quantization. Eso sí, con cabeza, no como el 80% que pierde el 40% de la precisión sin necesidad.

Hoy vamos a ver cómo convertir modelos de 32 bits a 8 bits (o menos) sin perder tanta precisión. El objetivo: que modelos que antes necesitaban GPUs de $30,000 corran en tu celular. Café en mano, que esto está buenísimo.

El Problema: Modelos Gigantes y Hardware Limitado

Miremos la matemática básica. Un modelo como LLaMA-70B en FP32 (32 bits por peso):

# Tamaño de un modelo en diferentes precisiones
def calculate_model_size(params_billions, bits):
    bytes_per_param = bits / 8
    total_bytes = params_billions * bytes_per_param * 1_000_000_000
    total_gb = total_bytes / (1024**3)
    return total_gb

# FP32 (32 bits) - Full precision
print(f"LLaMA-70B FP32: {calculate_model_size(70, 32):.1f} GB")

# FP16 (16 bits) - Half precision
print(f"LLaMA-70B FP16: {calculate_model_size(70, 16):.1f} GB")

# INT8 (8 bits) - Quantized
print(f"LLaMA-70B INT8: {calculate_model_size(70, 8):.1f} GB")

# INT4 (4 bits) - Highly quantized
print(f"LLaMA-70B INT4: {calculate_model_size(70, 4):.1f} GB")

Output:

LLaMA-70B FP32: 261.0 GB
LLaMA-70B FP16: 130.5 GB
LLaMA-70B INT8: 65.3 GB
LLaMA-70B INT4: 32.6 GB

261 GB en FP32 vs 32.6 GB en INT4. Puedes pasar de necesitar 4 GPUs A100 (~$30,000) a correrlo en una MacBook con 64GB. Suena obvio cuando lo ves así, pero el 70% de la gente no sabe cómo hacerlo correctamente.

Tipos de Quantization

Básicamente hay dos categorías:

  • PTQ (Post-Training Quantization): Entrenas el modelo normal, luego lo quantizas. Simple, rápido, pero puedes perder precisión.
  • QAT (Quantization-Aware Training): Entrenas con la quantización en mente desde el principio. Más complejo, pero mejor preservación de precisión.

PTQ: El Más Común

El 90% de los casos usan PTQ porque es más simple. Hay varios métodos:

Cuantización por Grupo vs Global

Aquí es donde la gente se confunde. Tienes dos approaches:

Quantización por tensor completo

Un solo factor de escala para todo el tensor. Simple pero impreciso porque los valores pueden variar mucho.

# Naive quantization - un solo scale para todo
def naive_quantize(tensor, bits=8):
    # Encontrar el valor máximo absoluto
    max_val = torch.max(torch.abs(tensor)).item()
    
    # Rango de quantización
    q_min = -(2**(bits-1))
    q_max = (2**(bits-1)) - 1
    
    # Factor de escala global
    scale = max_val / q_max
    
    # Cuantizar
    quantized = torch.round(tensor / scale).clamp(q_min, q_max)
    
    return quantized, scale

# Problema: si el tensor tiene valores entre -0.001 y 0.001 Y también entre -100 y 100,
# un solo scale no representa bien ninguno

Quantización por grupo (per-channel/per-token)

Más preciso porque cada grupo tiene su propio factor de escala.

# Per-channel quantization para weights
def per_channel_quantize(tensor, bits=8):
    """
    Un scale por canal (típicamente por columna en layers lineales).
    Mejora la precisión dramáticamente.
    """
    q_min = -(2**(bits-1))
    q_max = (2**(bits-1)) - 1
    
    # Un scale por canal (axis=0 para weights [out_features, in_features])
    scales = tensor.abs().max(dim=1, keepdim=True)[0]
    scales = scales / q_max
    
    # Cuantizar
    quantized = torch.round(tensor / scales).clamp(q_min, q_max)
    
    return quantized, scales

# Per-token quantization para activaciones
def per_token_quantize(tensor, bits=8):
    """
    Un scale por token (por fila). Común para activaciones en transformers.
    """
    q_min = -(2**(bits-1))
    q_max = (2**(bits-1)) - 1
    
    # Un scale por token (por fila, dim=1)
    scales = tensor.abs().max(dim=1, keepdim=True)[0]
    scales = scales / q_max
    
    quantized = torch.round(tensor / scales).clamp(q_min, q_max)
    
    return quantized, scales

GPTQ: El Estándar Actual para LLMs

GPTQ (Generative Pre-trained Transformer Quantization) es probablemente el método más popular hoy. Usa una técnica inteligente: quantización por columnas con un proceso de "fine-tuning" post-cuantización para minimizar el error.

# Pseudo-código de GPTQ
def gptq_quantize(weights, bits=4, per_channel=True):
    """
    GPTQ:
    1. Cuantiza por columnas
    2. Computa error de reconstrucción
    3. Ajusta pesos restantes para minimizar error
    """
    quantized = []
    scales = []
    
    for col in range(weights.shape[1]):
        weight_col = weights[:, col]
        
        # Cuantizar columna
        if per_channel:
            scale = weight_col.abs().max() / (2**(bits-1))
        else:
            scale = weights.abs().max() / (2**(bits-1))
        
        q_col = torch.round(weight_col / scale).clamp(-(2**(bits-1)), 2**(bits-1)-1)
        
        # Computar error
        error = weight_col - (q_col * scale)
        
        # En GPTQ real, propagar este error a columnas no cuantizadas
        # Y ajustar basado en Hessian para minimizar impacto
        
        quantized.append(q_col)
        scales.append(scale)
    
    return torch.stack(quantized, dim=1), torch.stack(scales)

GGUF: Quantization para CPUs con llama.cpp

GGUF (formerly GGML) es el formato que usa llama.cpp para quantización eficiente en CPU. Soporta varios levels de quantización:

# Niveles de quantización GGUF/Q4
gguf_levels = {
    "Q4_K_S": {"bits": 4, "description": "4-bit, small (más pequeño, más pérdida)"},
    "Q4_K_M": {"bits": 4, "description": "4-bit, medium (balance)"},
    "Q5_K_S": {"bits": 5, "description": "5-bit, small"},
    "Q5_K_M": {"bits": 5, "description": "5-bit, medium (buen balance)"},
    "Q8_0": {"bits": 8, "description": "8-bit (casi FP16, poco usado)"},
}

# Tamaños aproximados para LLaMA-70B
for level, info in gguf_levels.items():
    size_gb = (70 * info["bits"]) / 8
    print(f"{level}: {info['bits']}-bit -> ~{size_gb:.1f} GB")

Q4_K_M es el sweet spot para la mayoría: ~70GB para un 70B model, corre en Macs con 64GB, buena precisión.

AWQ: Activation-Aware Quantization

AWQ (Activation-Aware Weight Quantization) es más nuevo y mejores resultados. Ignora el 1% de weights más importantes y solo quantiza el resto:

# AWQ idea básica
def awq_quantize(weights, activations, bits=4):
    """
    AWQ assumption: algunos pesos son más importantes que otros.
    Los pesos con alta magnitud de activación asociado son críticos.
    """
    # Encontrar pesos importantes (los que interactúan con activaciones grandes)
    importance = torch.abs(weights) * torch.abs(activations).mean(dim=0)
    
    # Identificar top-1% más importantes
    threshold = torch.quantile(importance.flatten(), 0.99)
    important_mask = importance >= threshold
    
    # Cuantizar solo pesos NO importantes
    non_important_weights = weights.clone()
    non_important_weights[important_mask] = 0
    
    quantized, scale = per_channel_quantize(non_important_weights, bits)
    
    # Guardar los pesos importantes en alta precisión
    important_weights = weights[important_mask]
    
    return quantized, scale, important_weights, important_mask

Errores Comunes y Cómo Evitarlos

Error 1: Cuantizar Todo a INT4 Sin Distinción

El problema: Cuantizas el modelo completo a INT4 y esperas que funcione igual. No. Los embeddings, las capas de atención, y las capas finales son más sensibles a quantización. Cuantizarlas agresivamente degrada calidad drásticamente.

La solución: Mezcla precisiones. Mantén capas críticas en INT8 o FP16, quantiza el resto a INT4. Herramientas como AutoGPTQ y bitsandbytes permiten especificar precision por capa.

# Ejemplo de quantización mixta con bitsandbytes
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",  # Normal float 4, mejor que INT4
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_use_double_quant=True,  # Cuantizar también los scales
)

# Mezcla: carga todo en 4-bit pero con NF4 que preserva mejor precisión
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-70b-hf",
    quantization_config=bnb_config,
    device_map="auto"
)

Error 2: No Medir Calidad Post-Quantization

El problema: Cuantizas y deployas sin verificar que la calidad no se degradó. Resulta que tu modelo quantizado da respuestas terriblemente wrong para ciertos casos edge.

La solución: Siempre ejecuta un eval set post-cuantización. Compara perplexity, accuracy en benchmarks, y si puedes, usa LLM como judge para comparar respuestas.

def evaluate_quantized_model(model, tokenizer, eval_dataset, benchmarks):
    """
    Evalúa modelo quantizado vs baseline.
    """
    results = {}
    
    # Perplexity (mide qué tan "sorprendido" está el modelo de datos reales)
    ppl = compute_perplexity(model, eval_dataset)
    results["perplexity"] = ppl
    
    # Benchmarks específicos
    for name, eval_fn in benchmarks.items():
        accuracy = eval_fn(model)
        results[name] = accuracy
    
    return results

# Compara antes y después
baseline_results = evaluate_quantized_model(fp16_model, ...)
quantized_results = evaluate_quantized_model(int4_model, ...)

# Si perplexity subió >5% o accuracy cayó >2%, reconsidera la quantización
degradation = (quantized_results["perplexity"] - baseline_results["perplexity"]) / baseline_results["perplexity"]
print(f"Degradation: {degradation:.1%}")

Error 3: Ignorar el Sesgo (Bias) en Cuantización

El problema: La mayoría de implementaciones solo quantizan weights (matrices), pero ignoran bias, LayerNorms, y activaciones. Esto crea inconsistencias numéricas que degradan calidad.

La solución: Usa librerías maduras como bitsandbytes, AutoGPTQ, or llama.cpp que manejan todos los componentes correctamente.

Resumen: Tu Checklist de Quantization

  • Usa NF4 o INT4 con cuidado: Para LLMs, NF4 (GPTQ) preserva mejor precisión que INT4 vanilla.
  • Per-channel > per-tensor: Siempre que puedas, usa un factor de escala por canal/columna.
  • Mezcla precisiones: Capas críticas en INT8/FP16, el resto en INT4.
  • Evalúa post-quantización: Mide perplexity y accuracy en benchmarks reales.
  • Considera AWQ para casos difíciles: Si INT4 standard no funciona, AWQ típicamente дает mejores resultados.
  • Usa librerías maduras: bitsandbytes, AutoGPTQ, llama.cpp — no intentes implementar quantización desde cero.
