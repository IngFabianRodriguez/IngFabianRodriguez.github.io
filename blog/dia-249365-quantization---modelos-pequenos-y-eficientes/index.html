Hagale pues, mi gente

Qué más pues, mi gente querida. Aquí andamos en el Día 249 hablando de algo que hoy día es critical: Context Window Management. Resulta que los modelos ahora manejan 200K tokens como si nada — GPT-4 Turbo con 128K, Claude con 200K, Gemini hasta con 1M — pero cada token que mandas cuesta plata, y si no sabes manejar eso te puedes disparar la factura sin necesidad.

Hoy vamos a aprender cómo截断 (truncar), rerankear, y hacer caching de forma inteligente. El objetivo: no perder el hilo de la conversación y no matar tu wallet en el proceso. Café en mano, que esto vale la pena.

El Problema Fundamental

Cada modelo tiene un context window máximo: un límite de tokens que puede procesar en una sola llamada. Con 128K tokens estás hablando de aproximadamente 96,000 palabras — más o menos 300 páginas. Suena infinito, pero cuando estás construyendo un sistema de RAG, un chatbot de análisis de documentos, o una aplicación de código que necesita entender múltiples archivos, ese "infinito" se llena rápido.

La matemática es clara:

# Costo por 1M tokens (aproximado GPT-4-Turbo)
COST_PER_MILLION_INPUT_TOKENS = 10.00  # USD
COST_PER_MILLION_OUTPUT_TOKENS = 30.00  # USD

# Si mandas 100 tokens de contexto irrelevante por request
# y tienes 10,000 requests/día:
DESPERDICIO_DIARIO = (100 * 10000) / 1_000_000 * COST_PER_MILLION_INPUT_TOKENS
print(f"Desperdicio diario: ${DESPERDICIO_DIARIO:.2f}")
# Output: Desperdicio diario: $10.00/día

$10/día suena poco, pero son $300USD/month en contexto irrelevante. Multiplícalo por 10 aplicaciones y estás hablando de $3000 mensuales en pura basura. Y eso sin contar que contexto irrelevante puede degradar la calidad de las respuestas — el modelo se confunde cuando le metes demasiado ruido.

Implicit Caching: El Truco que Todos Ignoran

Aquí viene algo interesante. Modelos como GPT-4 Turbo y Claude implementan implicit caching (también llamado KV caching o attention caching). Básicamente: cuando mandas un mensaje que comparte prefijos con mensajes anteriores (como el system prompt), el modelo no recalcula toda la atención — reutiliza los cálculos previos.

Esto significa que si tu system prompt pesa 8K tokens, solo lo pagas una vez... pero solo si el provider lo implementa bien y si结构的 manejas tus mensajes.

#杭州市 # Demo de implicit caching con mensajes estructurados
messages = [

    {"role": "assistant", "content": "Aquí está el análisis..."},  # 200 tokens

Providers como OpenAI con cache_control, Anthropic con cache断续, y otros tienen formas de hintear al modelo qué partes del contexto pueden cachearse. Aprende a usarlas.

Conversation Summarization: No Dejes que el Pasado Te Mate

La estrategia más efectiva para conversaciones largas es resumir periódicamente. Cada N mensajes (típicamente 10-20), insertas un resumen de toda la conversación hasta ese punto y descartas los mensajes individuales.

from transformers import pipeline
import tiktoken

class ConversationManager:
    def __init__(self, model_name="gpt-3.5-turbo", max_tokens=128_000, compression_ratio=0.3):
        self.encoding = tiktoken.get_encoding("cl100k_base")
        self.max_tokens = max_tokens
        self.compression_ratio = compression_ratio  # 30% del original
        self.summarizer = pipeline("summarization", model="facebook/bart-large-cnn")
        self.messages = []
        self.conversation_summary = ""

    def count_tokens(self, text: str) -> int:
        return len(self.encoding.encode(text))

    def should_summarize(self) -> bool:
        """Verifica si，我们需要 resumir"""
        total = sum(self.count_tokens(m["content"]) for m in self.messages)
        # Si vamos al 70% del context window, resumir
        return total > self.max_tokens * 0.7

    def summarize_old_messages(self, llm_callable) -> None:
        """Comprime los mensajes viejos en un resumen"""
        if not self.messages:
            return

        # Construir texto de todos los mensajes
        conversation_text = "\n".join([
            f"{m['role']}: {m['content']}" for m in self.messages
        ])

        # Llamar al LLM para resumir
        summary_prompt = f"""Resumir esta conversación de manera concisa,
        preservando toda la información importante (decisiones, hechos, preferencias del usuario).
        Longitud objetivo: {int(self.count_tokens(conversation_text) * self.compression_ratio)} tokens.

        Conversación:
        {conversation_text}

        Resumen:"""

        new_summary = llm_callable(summary_prompt)

        # Guardar resumen y limpiar mensajes
        self.conversation_summary = new_summary
        self.messages = []

    def add_message(self, role: str, content: str, llm_callable=None) -> None:
        self.messages.append({"role": role, "content": content})

        # Verificar si hay que resumir
        if llm_callable and self.should_summarize():
            self.summarize_old_messages(llm_callable)

    def get_context(self) -> list:
        """Retorna el contexto optimizado para el LLM"""
        context = []
        if self.conversation_summary:
            context.append({"role": "system", "content": f"Resumen de conversación previa: {self.conversation_summary}"})
        context.extend(self.messages)
        return context

Reranking: Seleccionando el Contexto Relevante

En sistemas RAG (Retrieval Augmented Generation), cuando tienes 10,000 documentos y solo puedes pasar 8,000 tokens al modelo, necesitas seleccionar los más relevantes. Aquí entra el reranking.

Básicamente: primero haces retrieval rápido (embedding similarity), obtienes los top-50 resultados, y luego usas un cross-encoder más pesado para reordenar y seleccionar los top-10 definitivos.

from sentence_transformers import CrossEncoder

class Reranker:
    def __init__(self, model_name="cross-encoder/ms-marco-MiniLML-12-v2"):
        self.reranker = CrossEncoder(model_name)

    def rerank(self, query: str, documents: list[str], top_k: int = 10) -> list[tuple]:
        """
        Rerankea documentos basado en relevancia vs query.
        Retorna lista de (documento, score) ordenados por relevancia.
        """
        # Crear pares query-document para el cross-encoder
        pairs = [(query, doc) for doc in documents]

        # Obtener scores de relevancia
        scores = self.reranker.predict(pairs)

        # Ordenar por score descendente
        ranked = sorted(zip(documents, scores), key=lambda x: x[1], reverse=True)

        return ranked[:top_k]

# Uso
reranker = Reranker()
docs = [doc.page_content for doc in retrieved_documents]  # top-50 del retrieval inicial

# Rerankear a top-10 definitivos
relevant_docs = reranker.rerank(user_query, docs, top_k=10)

# Solo estos 10 van al context del LLM
final_context = "\n\n".join([doc for doc, score in relevant_docs])

El math detrás es simple: un embedding model como all-MiniLM-L6-v2 es rápido (O(n) con ANN) pero aproximado. El cross-encoder es más lento (O(n log n)) pero usa atención cruzada query-document, así que es mucho más preciso para decidir relevancia real.

Token Budgeting: La Estrategia del Sistema

Para optimize costs, necesitas un token budget inteligente entre system prompt, user input, y contexto recuperado. La fórmula que uso:

def calculate_token_budget(
    max_context: int = 128_000,
    output_tokens: int = 4_000,
    user_input_tokens: int = None,
    safety_margin: float = 0.1
) -> dict:
    """
    Calcula distribución óptima de tokens.
    max_context: context window del modelo
    output_tokens: tokens reservados para la respuesta
    user_input_tokens: si es None, se calcula automáticamente
    safety_margin: 10% reservado para overhead del tokenizer
    """
    available = max_context - output_tokens
    effective_max = int(available * (1 - safety_margin))

    if user_input_tokens is None:
        # Sistema optimizado: 15% system, 35% retrieved context, 50% user input
        budget = {
            "system": int(effective_max * 0.15),
            "retrieved_context": int(effective_max * 0.35),
            "user_input": int(effective_max * 0.50),
        }
    else:
        # User input fijo, lo demás para system + retrieved
        remaining = effective_max - user_input_tokens
        system_tokens = int(remaining * 0.30)  # 30% del remaining para system
        retrieved_tokens = remaining - system_tokens
        budget = {
            "system": system_tokens,
            "retrieved_context": retrieved_tokens,
            "user_input": user_input_tokens,
        }

    return budget

# Ejemplo
budget = calculate_token_budget(max_context=128_000, output_tokens=4_000)
print(f"Token Budget: {budget}")
# Output: Token Budget: {'system': 16720, 'retrieved_context': 38787, 'user_input': 55411}

Con este budget sabes exactamente cuánto espacio tienes para el system prompt (instrucciones, few-shot examples), para el contexto recuperado (documentos RAG), y para el input del usuario. Si el retrieved context excede el budget, truncas o resúmenes los documentos.

Errores Comunes y Cómo Evitarlos

Error 1: Meter Todo en el Context "Por Si Acaso"

El problema: Entras a un chat con 50 documentos PDF, los metes todos en el contexto, y le preguntas "¿cuál es el teléfono de Juan?". El modelo tiene que procesar 200K tokens de contexto para responder una pregunta sobre 1 línea. Estás pagando 200K tokens de input para una respuesta de 5 tokens.

La solución: Usa retrieval inteligente. Solo pasa los documentos chunks más relevantes. Un embedding search rápido + reranking te da los 3-5 documentos relevantes, no los 50. math: si cada chunk es 500 tokens y necesitas 5 chunks = 2,500 tokens vs 200,000. Ahorro: 98.75%.

# MAL: Meter todo
BAD_prompt = f"""Aquí tienes 50 documentos:

Respuesta:"""

relevant_chunks = retrieve_and_rerank(question, all_documents, top_k=5)

Error 2: No Resumir Conversaciones Largas

El problema: Tienes un chatbot de soporte técnico. Después de 50 mensajes, cada mensaje nuevo viene con los 49 anteriores en el contexto. A los 100 mensajes estás pagando 100x el costo por request.eventually llegas al context window y el sistema se rompe o empieza a truncar mensajes importantes.

La solución: Implementa summarization periódica. Cada 10-15 mensajes, genera un resumen de todo lo anterior y reinicia la lista de mensajes. El resumen preserva las decisiones clave y preferencias del usuario.

# Antes de summarization:
# messages[0] = "Hola, quiero comprar un laptop"
# messages[1] = "Tenemoms Dell XPS 13 y MacBook Air"
# ... (50 mensajes después)
# Cada request incluye los 52 mensajes = 52 * ~100 tokens = 5,200 tokens/input

# Después de summarization:
# conversation_summary = "Usuario quiere comprar laptop. Budget $1500 USD.
# Preferencia: MacBook Air por ecosistema Apple.
# Última pregunta:是否能 financear a 12 meses?"

# messages = [summary] + [últimos 2-3 mensajes relevantes]
# Cada request ahora = ~300 tokens/input
# Ahorro: 94% por request

Error 3: No Hacer Budget Entre System e Input

El problema: El system prompt tiene 15,000 tokens de instrucciones detalladas, few-shot examples, y contexto de la empresa. El usuario pregunta algo simple ("hola") y tu context de 16,000 tokens produce una respuesta de 10 tokens. Estás pagando 16,010 tokens de input para una respuesta de 10 tokens. Costo: $0.16 por "hola".

La solución: Establece budgets fijos. Si el system prompt es grande, considera partirlo: un system prompt base pequeño + instrucciones específicas por task que se añaden solo cuando son necesarias. Usa cache control hints para que el system prompt se cachee y no se reprocese cada vez.

# MAL: System prompt gigante para todo
system_prompt_gigante = """
Eres un asistente de una empresa de 50,000 empleados.

manual de 200 páginas de políticas de la empresa,

# BIEN: System prompt modular
system_prompt_base = "Eres un asistente helpful. Responde de forma clara y concisa."

# El base se cachea. Solo el task-specific se añade cuando aplica.

Resumen: Tu Checklist de Context Window

  • Mide antes de enviar: Cuenta tokens de cada request. Si mandas más de 70% del context window sin necesidad, estás desperdiciando plata.
  • Retrieval inteligente: No metas todo en el contexto. Usa embedding search + reranking para solo pasar lo relevante.
  • Summariza conversaciones: Cada 10-20 mensajes, comprime el historial en un resumen estructurado.
  • Budget fijo: Establece límites claros: X tokens para system, Y para contexto recuperado, Z para input.
  • Usa caching hints: Si tu provider soporta cache control, úsalo para el system prompt y prefijos repetitivos.
  • Trunca con inteligencia: Si un documento es muy largo, no lo cortes a la mitad. Extrae los párrafos más relevantes con embedding similarity.
