Mixture of Experts - Modelos Que Experts En Todo

01 de noviembre de 2026
mixture-of-expertsmoescalingarchitecture

🎯 Por Que Mixture of Experts?

Hagale pues, parcero. Imagínese un equipo donde cada persona es experta en algo diferente: uno sabe de matemáticas, otro de historia, otro de cocina. Cuando llega un problema, se lo mandas al que más sabe del tema. Eso es exactamente Mixture of Experts (MoE): un modelo con múltiples "expertos" internos donde un router decide cuál usar para cada input.

El problema con los modelos densos es que usan TODOS los parámetros para cada input. Un transformer de 100B parametros computa 100B params aunque la pregunta sea "cuál es la capital de Francia?". MoE resuelve esto: solo activa los expertos relevantes.

📐 La Arquitectura MoE

Matemáticamente, MoE tiene esta estructura:

$$y = \sum_{i=1}^{E} G(x)_i \cdot E_i(x)$$

Donde:

  • $E_i(x)$ es el i-ésimo "experto" (generalmente una FFN)
  • $G(x)$ es el router que produce una distribución de probabilidad sobre los expertos
  • $G(x)_i$ es el peso para el experto $i$

El router típicamente usa softmax:

$$G(x)_i = \frac{\exp(w_i(x))}{\sum_{j=1}^{E} \exp(w_j(x))}$$

donde $w_i(x) = \text{Linear}(x)_i$ es un score aprendido.

🏗️ Top-K Gating

Un problema con el gating estándar: si todos los pesos son similares, no hay especialización. Por eso se usa Top-K Gating:

$$G(x)_i = \frac{\exp(w_i(x))}{\sum_{j \in top-k} \exp(w_j(x))}$$

Solo se activan los k expertos con mayor weight. Por ejemplo, en Mixtral 8x7B se usan 2 expertos de 8 disponibles por token.

🔬 Implementacion Basica

import torch
import torch.nn as nn
import torch.nn.functional as F

class Expert(nn.Module):
    """Un experto individual (típicamente una FFN)."""
    def __init__(self, d_model: int, d_ff: int):
        super().__init__()
        self.w1 = nn.Linear(d_model, d_ff, bias=False)
        self.w2 = nn.Linear(d_ff, d_model, bias=False)
        self.activation = nn.SiLU()
    
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        return self.w2(self.activation(self.w1(x)))

class MoELayer(nn.Module):
    """
    Capa Mixture of Experts.
    Usa Top-K gating para seleccionar expertos activos.
    """
    def __init__(self, d_model: int, d_ff: int, n_experts: int, top_k: int = 2):
        super().__init__()
        self.n_experts = n_experts
        self.top_k = top_k
        
        # Router network
        self.gate = nn.Linear(d_model, n_experts, bias=False)
        
        # Los expertos
        self.experts = nn.ModuleList([
            Expert(d_model, d_ff) for _ in range(n_experts)
        ])
    
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        """
        x: [batch, seq_len, d_model]
        """
        batch_size, seq_len, d_model = x.shape
        
        # Flatten para procesamiento eficiente
        x_flat = x.view(-1, d_model)  # [batch*seq_len, d_model]
        
        # Calcular gate scores
        gate_logits = self.gate(x_flat)  # [batch*seq_len, n_experts]
        gate_probs = F.softmax(gate_logits, dim=-1)
        
        # Top-K selection
        top_k_probs, top_k_indices = torch.topk(
            gate_probs, self.top_k, dim=-1
        )
        
        # Normalizar Top-K
        top_k_probs = top_k_probs / top_k_probs.sum(dim=-1, keepdim=True)
        
        # Inicializar output
        output = torch.zeros_like(x_flat)
        
        # Apply experts solo a los top-k
        for k in range(self.top_k):
            expert_idx = top_k_indices[:, k]  # índice del experto k
            expert_weight = top_k_probs[:, k]  # peso del experto k
            
            # Para cada experto, acumular su contribución
            for i in range(self.n_experts):
                mask = (expert_idx == i)
                if mask.any():
                    expert_input = x_flat[mask]
                    expert_output = self.experts[i](expert_input)
                    # Ponderar por peso y acumular
                    output[mask] += expert_output * expert_weight[mask].unsqueeze(-1)
        
        return output.view(batch_size, seq_len, d_model)

# Ejemplo de uso
batch_size, seq_len, d_model = 2, 10, 512
n_experts, top_k = 8, 2

x = torch.randn(batch_size, seq_len, d_model)
moe_layer = MoELayer(d_model, d_model * 4, n_experts, top_k)
output = moe_layer(x)

print(f"Input shape: {x.shape}")
print(f"Output shape: {output.shape}")
print(f"Número de expertos: {n_experts}")
print(f"Expertos activos por token: {top_k}")

⚡ Load Balancing Loss

Problema crítico: el router puede aprender a mandar todo a los mismos expertos (dominancia). Para evitar esto, se usa un load balancing loss:

$$\mathcal{L}_{lb} = \alpha \cdot \text{Var}\left(\frac{1}{B}\sum_{i=1}^{B} f_i\right) + \beta \cdot \text{Var}\left(\frac{1}{B}\sum_{i=1}^{B} P_i\right)$$

Donde:

  • $f_i$ = fraction of tokens routed to expert $i$
  • $P_i$ = mean probability for expert $i$
  • $\alpha, \beta$ = hyperparameters de penalización
class MoELayerWithLoadBalancing(nn.Module):
    """
    MoE con load balancing loss para evitar dominancia de expertos.
    """
    def __init__(self, d_model: int, d_ff: int, n_experts: int, 
                 top_k: int = 2, alpha: float = 0.1):
        super().__init__()
        self.n_experts = n_experts
        self.top_k = top_k
        self.alpha = alpha
        
        self.gate = nn.Linear(d_model, n_experts, bias=False)
        self.experts = nn.ModuleList([
            Expert(d_model, d_ff) for _ in range(n_experts)
        ])
    
    def forward(self, x: torch.Tensor) -> tuple[torch.Tensor, torch.Tensor]:
        """
        Retorna (output, load_balance_loss)
        """
        batch_size, seq_len, d_model = x.shape
        x_flat = x.view(-1, d_model)
        
        # Router decisions
        gate_logits = self.gate(x_flat)
        gate_probs = F.softmax(gate_logits, dim=-1)
        
        # Top-K
        top_k_probs, top_k_indices = torch.topk(gate_probs, self.top_k, dim=-1)
        top_k_probs = top_k_probs / top_k_probs.sum(dim=-1, keepdim=True)
        
        # Load balancing
        # f_i: fraction de tokens al experto i
        # P_i: probabilidad promedio del experto i
        f_i = torch.zeros(self.n_experts, device=x.device)
        P_i = torch.zeros(self.n_experts, device=x.device)
        
        for i in range(self.n_experts):
            mask = (top_k_indices == i).any(dim=-1)
            f_i[i] = mask.float().mean()
            P_i[i] = gate_probs[mask, i].mean() if mask.any() else 0.0
        
        # Load balancing loss
        load_loss = self.n_experts * (f_i * P_i).sum()
        
        # Forward normal
        output = torch.zeros_like(x_flat)
        for k in range(self.top_k):
            expert_idx = top_k_indices[:, k]
            expert_weight = top_k_probs[:, k]
            
            for i in range(self.n_experts):
                mask = (expert_idx == i)
                if mask.any():
                    expert_output = self.experts[i](x_flat[mask])
                    output[mask] += expert_output * expert_weight[mask].unsqueeze(-1)
        
        return output.view(batch_size, seq_len, d_model), load_loss * self.alpha

🌟 Mixtral 8x7B - Ejemplo Real

Mixtral 8x7B es el ejemplo más conocido de MoE bien implementado:

  • 8 expertos por capa
  • 2 expertos activos por token (de ahí el "8x7B" - 8 expertos pero solo activa 2)
  • ~12B parametros activos de los 46.7B totales
  • Equivalente en calidad a un modelo denso de ~70B

La clave del éxito de Mixtral es que los expertos son FFNs especializadas pero compartidas entre capas, permitiendo que cada experto se especialice en diferentes tipos de tokens.

⚠️ Desafios y Problemas

💾 Memoria VRAM

Aunque solo usas k expertos por forward, todos los expertos deben estar en memoria. Un modelo MoE de 8 expertos necesita 8x la memoria de un experto para los pesos. Esto es un problema para deployment.

📦 Comunicacion Bottleneck

En entrenamiento distribuido, los expertos activos pueden estar en diferentes GPUs, creando comunicación excesiva. Esto limita los beneficios de paralelismo.

🎯 Routing Instabilidad

Si el router colapsa y siempre manda los mismos expertos, el modelo no converge bien. Por eso el load balancing loss es crítico.

📈 Resumen y Cierre

MoE es una arquitectura elegante que permite escalar modelos dramáticamente manteniendo el compute activo razonable:

  • Idea central: especializada mejor que generalista
  • Top-K gating: solo activa k de E expertos por token
  • Load balancing: evita que el router colapse
  • Trade-offs: más memoria, menos compute por parametro

El futuro es híbrido: MoE para scaling横方向, y dentro de cada experto podemos usar técnicas como mixture-of-logits o weighted heads. La clave está en balancear especialización con eficiencia.
