RLHF (Reinforcement Learning from Human Feedback) - Cómo Enseñarle a la IA lo que es Correcto sin Etiquetar Datos

19 de marzo de 2026
RLHFreward modelPPOhuman feedbackalignmentRLAIF

Qué tal, Colombia 🇮🇩 Hoy vamos a meternos de lleno en una de las técnicas más importantes —y más complejas— para hacer que un modelo de lenguaje se comporte como uno quiere: el RLHF, o Reinforcement Learning from Human Feedback. Si los LLMs de hoy suenan más naturales, más útiles y menos tóxicos que los de hace dos años, es gracias a esto.

¿Qué problema resuelve el RLHF?

Un modelo de lenguaje entrenado solo con texto siguiente-predicción (next-token prediction) aprende de统计ística pura: "dada esta secuencia de palabras, ¿qué palabra viene?". Eso está bien, pero no le dice nada sobre qué debería decir versus qué no debería. Un modelo puede aprender a completar oraciones sin entender si lo que completa es útil, preciso o apropiado.

El RLHF añade un paso intermedio: en lugar de solo maximizar la probabilidad del próximo token, se entrena el modelo para maximizar una señal de reward que refleja preferencias humanas. Básicamente: "de dos respuestas, ¿cuál prefieres?". Así se绕过 (bypass) la necesidad de especificar reglas explícitas.

El Reward Model desde Pairwise Preferences

El corazón del RLHF es el reward model. La forma más común de entrenarlo es con preference data emparejada: humanos ven dos respuestas (A y B) a la misma pregunta y dicen cuál prefieren. Ese es el training signal.

La idea es sencilla en concepto pero delicado en la práctica:

  • Si el humano prefiere A sobre B → label=1 para A, label=0 para B
  • El reward model aprende a asignar scores más altos a las respuestas preferidas
  • Ese reward model luego guía el fine-tuning del policy model con PPO

Código: Reward Model con Preference Data

import torch
import torch.nn as nn
from transformers import AutoModel, AutoTokenizer
from torch.utils.data import Dataset, DataLoader

class PairwiseRewardDataset(Dataset):
    """Dataset con pares de respuestas y labels de preferencia.

    Cada sample contiene:
    - prompt: la pregunta original
    - response_chosen: la respuesta que el humano prefirió
    - response_rejected: la respuesta que el humano no prefirió
    """
    def __init__(self, pairs, tokenizer, max_length=512):
        self.pairs = pairs
        self.tokenizer = tokenizer
        self.max_length = max_length

    def __len__(self):
        return len(self.pairs)

    def __getitem__(self, idx):
        pair = self.pairs[idx]
        prompt = pair["prompt"]
        chosen = pair["response_chosen"]
        rejected = pair["response_rejected"]

        # Concatenamos prompt + respuesta para el reward model
        chosen_text = f"{prompt}\n\nRespuesta: {chosen}"
        rejected_text = f"{prompt}\n\nRespuesta: {rejected}"

        chosen_enc = self.tokenizer(
            chosen_text,
            max_length=self.max_length,
            padding="max_length",
            truncation=True,
            return_tensors="pt"
        )
        rejected_enc = self.tokenizer(
            rejected_text,
            max_length=self.max_length,
            padding="max_length",
            truncation=True,
            return_tensors="pt"
        )

        return {
            "chosen_input_ids": chosen_enc["input_ids"].squeeze(0),
            "chosen_attention_mask": chosen_enc["attention_mask"].squeeze(0),
            "rejected_input_ids": rejected_enc["input_ids"].squeeze(0),
            "rejected_attention_mask": rejected_enc["attention_mask"].squeeze(0),
        }


class RewardModel(nn.Module):
    """Reward model que aprende de pairwise preferences.

    Recibe el texto completo (prompt + respuesta) y devuelve un scalar
    que representa qué tantoprefiere un humano esa respuesta.
    """
    def __init__(self, model_name="microsoft/deberta-v3-base"):
        super().__init__()
        self.encoder = AutoModel.from_pretrained(model_name)
        self.reward_head = nn.Linear(self.encoder.config.hidden_size, 1)

    def forward(self, input_ids, attention_mask):
        outputs = self.encoder(
            input_ids=input_ids,
            attention_mask=attention_mask
        )
        # Pooling sobre el último hidden state (CLS token)
        cls_output = outputs.last_hidden_state[:, 0, :]
        reward = self.reward_head(cls_output).squeeze(-1)
        return reward


def reward_model_loss(reward_chosen, reward_rejected):
    """Pairwise ranking loss: la respuesta elegida debe tener reward mayor.

    Usamos la formulación de Bradley-Terry:
    L = -log(sigmoid(reward_chosen - reward_rejected))

    Si reward_chosen > reward_rejected, la diferencia es positiva,
    sigmoid la convierte en un valor entre 0 y 1, y el log negativo
    produce una loss baja (buena). El gradiente empuja reward_chosen arriba
    y reward_rejected abajo.
    """
    loss = -torch.log(torch.sigmoid(reward_chosen - reward_rejected) + 1e-5).mean()
    return loss


# --- Ejemplo de entrenamiento ---
if __name__ == "__main__":
    tokenizer = AutoTokenizer.from_pretrained("microsoft/deberta-v3-base")
    reward_model = RewardModel()

    # Datos de ejemplo: prompt + dos respuestas + preferencia
    pairs = [
        {
            "prompt": "¿Cómo funciona un reactor nuclear?",
            "response_chosen": "Un reactor nuclear usa fission de átomos de uranio para generar calor...",
            "response_rejected": "No sé, algo de átomos我觉得..."
        },
        {
            "prompt": "Escribe un email formal solicitando vacaciones.",
            "response_chosen": "Estimado [Jefe], por medio de la presente solicito..."

,
            "response_rejected": "Oye, necesito libres la prox sem..."
        },
    ]

    dataset = PairwiseRewardDataset(pairs, tokenizer)
    dataloader = DataLoader(dataset, batch_size=2, shuffle=True)

    optimizer = torch.optim.AdamW(reward_model.parameters(), lr=1e-5)

    for epoch in range(3):
        for batch in dataloader:
            r_chosen = reward_model(
                batch["chosen_input_ids"],
                batch["chosen_attention_mask"]
            )
            r_rejected = reward_model(
                batch["rejected_input_ids"],
                batch["rejected_attention_mask"]
            )
            loss = reward_model_loss(r_chosen, r_rejected)

            optimizer.zero_grad()
            loss.backward()
            optimizer.step()

            print(f"Epoch {epoch} | Loss: {loss.item():.4f}")

    print("Reward model entrenado ✓")

PPO Fine-Tuning: Maximizar Reward subject a KL Divergence

Una vez tenemos el reward model, usamos PPO (Proximal Policy Optimization) para actualizar el policy model — el LLM base — de forma que maximice el reward predicho sin alejarse demasiado del modelo original.

La función de pérdida de PPO es elegante. Se define sobre la ratio entre la política nueva y la vieja:

import torch
import torch.nn as nn
import torch.nn.functional as F
from transformers import AutoModelForCausalLM, AutoTokenizer
from torch.utils.data import DataLoader

class PPOTrainer:
    """PPO trainer simplificado para RLHF.

    La idea central: maximizar el reward predicho por el reward model
    mientras limitamos cuánto cambia la política respecto al modelo base.
    Eso se logra con dos términos:
      - reward: el reward predicho por el reward model (alto = bueno)
      - kl_penalty: penaliza divergencia excesiva vs reference model

    La constraint de KL es crucial: sin ella, el modelo podría "hacer trampa"
    encontrando formas de maximizar el reward sin generar texto realmente mejor.
    """
    def __init__(
        self,
        policy_model,
        reference_model,
        reward_model,
        tokenizer,
        kl_coef=0.1,
        ppo_clip_eps=0.2,
        device="cuda"
    ):
        self.policy = policy_model.to(device)
        self.reference = reference_model.to(device)
        self.reward_model = reward_model.to(device)
        self.tokenizer = tokenizer
        self.kl_coef = kl_coef  # Peso del término KL
        self.ppo_clip_eps = ppo_clip_eps
        self.device = device

        # Reference model en modo eval (no se actualiza)
        self.reference.eval()

    def compute_kl_divergence(self, prompt_ids, response_ids):
        """Calcula KL(prev_policy || curr_policy) para cada token.

        KL(actual || referencia) = suma sobre tokens de:
          p_actual(token) * log(p_actual(token) / p_referencia(token))

        Esto mide cuánto se ha desviado la política actual de la original.
        """
        with torch.no_grad():
            ref_logps = self._get_log_probs(self.reference, prompt_ids, response_ids)
        curr_logps = self._get_log_probs(self.policy, prompt_ids, response_ids)
        # KL divergence: E_p [log(p/q)]
        kl = torch.exp(ref_logps - curr_logps) * (ref_logps - curr_logps)
        return kl.sum(dim=-1)

    def _get_log_probs(self, model, prompt_ids, response_ids):
        """Calcula log probabilities de los response tokens bajo el modelo."""
        # Crear attention mask que ignora los prompt tokens (solo mide response)
        seq_len = response_ids.size(1)
        # Para un decoder-only model, predecimos response dado prompt
        inputs = torch.cat([prompt_ids, response_ids], dim=1)
        outputs = model(inputs)
        logits = outputs.logits[:, :-1, :]  # shift right
        log_probs = F.log_softmax(logits, dim=-1)

        # Solo mirar los tokens del response
        # response_ids tiene seq_len, logits tiene seq_len también
        response_log_probs = torch.gather(
            log_probs, 2, response_ids.unsqueeze(2)
        ).squeeze(2)
        return response_log_probs

    def clipped_surrogate_loss(self, prompt_ids, response_ids, old_log_probs):
        """PPO clipped surrogate objective.

        En PPO clásico (no RLHF), el ratio = pi_new / pi_old.
        Aquí adaptamos: el ratio compara log probs nuevos vs old (de SFT).

        Clipping evita que actualizaciones pequeñas se vuelvan grandes:
        si el ratio sale del rango [1-ε, 1+ε], se clippea.
        Esto estabiliza el entrenamiento.
        """
        curr_log_probs = self._get_log_probs(self.policy, prompt_ids, response_ids)
        ratio = torch.exp(curr_log_probs - old_log_probs)

        # Clipped ratio
        clipped_ratio = torch.clamp(ratio, 1 - self.ppo_clip_eps, 1 + self.ppo_clip_eps)

        # Reward (del reward model sobre todo el sequence)
        # Para simplicity, usamos el reward del response
        prompt_len = prompt_ids.size(1)
        reward = self.reward_model(
            torch.cat([prompt_ids, response_ids], dim=1)[:, -(prompt_len + response_ids.size(1)):],
            None  # attention mask
        )

        # Advantage estimado (aquí simplificado: reward normalizado)
        advantage = (reward - reward.mean()) / (reward.std() + 1e-8)

        # Surrogate loss con clip
        unclipped_loss = ratio * advantage.unsqueeze(1)
        clipped_loss = clipped_ratio * advantage.unsqueeze(1)
        loss = -torch.min(unclipped_loss, clipped_loss).mean()

        return loss

    def step(self, prompt_ids, response_ids, old_log_probs):
        """Un paso de PPO: computa loss y hace backward."""
        # 1. Clipped surrogate loss (término de policy)
        policy_loss = self.clipped_surrogate_loss(prompt_ids, response_ids, old_log_probs)

        # 2. KL divergence penalty vs reference model
        kl = self.compute_kl_divergence(prompt_ids, response_ids).mean()
        kl_loss = self.kl_coef * kl

        # 3. Total loss
        total_loss = policy_loss + kl_loss

        total_loss.backward()
        return {
            "total_loss": total_loss.item(),
            "policy_loss": policy_loss.item(),
            "kl_loss": kl_loss.item(),
            "kl": kl.item()
        }


# --- Ejemplo de uso ---
if __name__ == "__main__":
    model_name = "gpt2"  # Para demo, usar uno pequeño
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    tokenizer.pad_token = tokenizer.eos_token

    policy = AutoModelForCausalLM.from_pretrained(model_name)
    reference = AutoModelForCausalLM.from_pretrained(model_name)
    reward_model = RewardModel()  # Del ejemplo anterior

    trainer = PPOTrainer(policy, reference, reward_model, tokenizer, kl_coef=0.1)

    # Prompts de ejemplo
    prompts = ["¿Qué es la fotosíntesis?", "Explica la relatividad."]
    for prompt in prompts:
        prompt_enc = tokenizer(prompt, return_tensors="pt")["input_ids"].to(trainer.device)
        # Generar response con la policy actual (simplificado: usar datos de demo)
        response_enc = tokenizer("Respuesta generada por el modelo...", return_tensors="pt")["input_ids"].to(trainer.device)

        # Log probs de la old policy (reference model)
        with torch.no_grad():
            old_lps = trainer._get_log_probs(reference, prompt_enc, response_enc)

        result = trainer.step(prompt_enc, response_enc, old_lps)
        print(f"Prompt: {prompt[:30]}... | KL: {result['kl']:.4f}")

    print("PPO fine-tuning step completado ✓")

La magic del clipped surrogate objective

El término de clipping es lo que hace PPO estable. Sin clip, si el modelo encuentra una forma de mejorar el reward, puede actualizar dramáticamente su política en una dirección que luego es difícil de revertir. El clip [1-ε, 1+ε] limita cuánto puede cambiar la ratio de probabilidad de un token entre actualizaciones. En la práctica, ε=0.2 funciona bien para la mayoría de casos.

DPO: Direct Preference Optimization

El problema con PPO es que es complejidad exponencial: se necesita un reward model separado, un reference model, y PPO mismo. DPO (Direct Preference Optimization) simplifica todo en una sola etapa de fine-tuning con una loss directamente derivada de las pairwise preferences.

La idea de DPO: no necesitamos el reward model durante el entrenamiento. La relación entre reward y preferencias (la llamada preference model) ya está capturada por la Bradley-Terry model. Podemos reparametrizar el problema y optimizar las preferencias directamente.

class DPO Trainer:
    """Direct Preference Optimization — alternativa a PPO que evita reward model.

    DPO reformula el problema de RLHF sin需要一个 reward model separado.
    La key insight: la probabilidad de preferir A sobre B bajo Bradley-Tercy
    se puede escribir como función de las policy distributions de A y B.

    Loss de DPO:
    L = -E_{(x, y_w, y_l) ~ D}[
        log σ(
            β * (log π(y_w|x) - log π(y_l|x) - log π_ref(y_w|x) + log π_ref(y_l|x))
        )
    ]

    donde:
    - y_w = respuesta preferida (winner)
    - y_l = respuesta no preferida (loser)
    - β = temperatura que controla cuán fuerte es la reward signal
    - π = policy que estamos entrenando
    - π_ref = reference model (SFT baseline)
    """
    def __init__(
        self,
        policy_model,
        reference_model,
        beta=0.1,  # DPO temperature
        lr=1e-6
    ):
        self.policy = policy_model
        self.reference = reference_model
        self.beta = beta
        self.optimizer = torch.optim.AdamW(policy_model.parameters(), lr=lr)

        # Reference no se entrena
        for p in reference_model.parameters():
            p.requires_grad = False

    def dpo_loss(self, prompt_chosen, response_chosen, prompt_rejected, response_rejected):
        """Computa DPO loss sobre un par chosen/rejected."""
        # Log probs de la policy para chosen y rejected
        lp_chosen = self._log_prob(self.policy, prompt_chosen, response_chosen)
        lp_rejected = self._log_prob(self.policy, prompt_rejected, response_rejected)

        # Log probs del reference model
        with torch.no_grad():
            lr_chosen = self._log_prob(self.reference, prompt_chosen, response_chosen)
            lr_rejected = self._log_prob(self.reference, prompt_rejected, response_rejected)

        # El término de DPO: π(y_w|x) / π(y_l|x) vs π_ref(y_w|x) / π_ref(y_l|x)
        # Preferencias más fuertes (β alto) amplifican la diferencia
        chosen_reward = self.beta * (lp_chosen - lr_chosen)
        rejected_reward = self.beta * (lp_rejected - lr_rejected)

        # Loss: queremos que chosen tenga reward mayor que rejected
        # log σ(chosen_reward - rejected_reward) -> minimizar = maximizar diferencia
        loss = -F.logsigmoid(chosen_reward - rejected_reward).mean()

        # Metrics para monitorear
        accuracy = (chosen_reward > rejected_reward).float().mean()

        return loss, accuracy

    def _log_prob(self, model, prompt_ids, response_ids):
        """Log probability de response dado prompt bajo el modelo."""
        inputs = torch.cat([prompt_ids, response_ids], dim=1)
        outputs = model(inputs)
        logits = outputs.logits[:, :-1, :]
        log_probs = F.log_softmax(logits, dim=-1)

        # Solo medir sobre los response tokens
        response_log_probs = torch.gather(
            log_probs, 2, response_ids.unsqueeze(2)
        ).squeeze(2)
        return response_log_probs.sum(dim=-1)

    def step(self, batch):
        """Un paso de entrenamiento DPO."""
        loss, accuracy = self.dpo_loss(
            batch["prompt_chosen"],
            batch["response_chosen"],
            batch["prompt_rejected"],
            batch["response_rejected"]
        )

        self.optimizer.zero_grad()
        loss.backward()
        self.optimizer.step()

        return {"dpo_loss": loss.item(), "accuracy": accuracy.item()}


# --- Ejemplo ---
if __name__ == "__main__":
    policy = AutoModelForCausalLM.from_pretrained("gpt2")
    reference = AutoModelForCausalLM.from_pretrained("gpt2")
    tokenizer = AutoTokenizer.from_pretrained("gpt2")
    tokenizer.pad_token = tokenizer.eos_token

    trainer = DPO(policy, reference, beta=0.1)

    # Batch de ejemplo
    batch = {
        "prompt_chosen": torch.tensor([[1, 2, 3]]),
        "response_chosen": torch.tensor([[4, 5, 6]]),
        "prompt_rejected": torch.tensor([[1, 2, 3]]),
        "response_rejected": torch.tensor([[7, 8, 9]]),
    }

    result = trainer.step(batch)
    print(f"DPO Loss: {result['dpo_loss']:.4f} | Accuracy: {result['accuracy']:.2f}")
    print("DPO entrenamiento completado ✓")

DPO ha ganado mucha tracción porque elimina la complejidad de PPO: un solo optimizador, una sola loss, y resultados competitivos. InstructGPT y modelos derivados lo usan ampliamente.

Errores Comunes en RLHF

Error 1: Reward Hacking — el modelo hace trampa

El error más famoso y peligroso. Ocurre cuando el reward model no refleja las preferencias reales de los humanos, y el policy model encuentra formas de maximizar el reward sin generar texto genuinamente mejor.

Ejemplo: El modelo aprende que respuestas más largas tienden a tener más reward (porque los humanos las prefieren en el dataset de entrenamiento), así que empieza a generar respuestas absurdamente largas que dicen poco. O aprende que ciertas frases específicas ("¡Excelente pregunta!") correlacionan con reward alto y las inserta mecánicamente.

Fix:

  • Usar ensemble de reward models para reducir individuales biases
  • Evaluar regularmente con humanos fuera del training set
  • Añadir términos de regularización adicionales (diversity loss, length normalization)
  • El KL penalty alto ayuda a limitar cuánto puede el modelo divergir

Error 2: KL Divergence demasiado alto — destruye capacidades del base

Si el coeficiente KL (β o kl_coef) es demasiado bajo, el modelo puede alejarse peligrosamente del base, perdiendo capacidades que el modelo base tenía bien aprendidas (esto se llama alignment tax).

Fix:

  • Encontrar el kl_coef óptimo vía ablation: empezar en 0.1 e ir bajando
  • Monitorear métricas del base model en benchmarks estándar durante training
  • Considerar un schedule de KL: empezar alto e ir bajando gradualmente
  • Si ves degradación en tareas no relacionadas con el reward, sube el coeficiente

Error 3: Preference Data inconsistente —confusión en el reward model

Los humanos no siempre son consistentes. A vecesprefieren A sobre B, pero B sobre C, y C sobre A. Un reward model entrenado con datos ruidosos o inconsistentes aprende una señal mixta y produce rewards que no corresponden a preferencias reales.

Fix:

  • Agregar más annotators y usar inter-annotator agreement como filtro
  • Descartar samples con disagreement alto (ej: 3 annotators, 2-1 split)
  • Usar técnicas de preference learning que sean robustas a ruido (ej: RAHF, probabilistic preference models)
  • Balancear el dataset: mismo tipo de pregunta debería tener labels consistentes

Resumen

El RLHF es el puente entre un modelo que predice texto y uno que entiende lo que la gente quiere. El reward model convierte preferencias humanas en una señal numérica; PPO usa esa señal para actualizar el modelo sin perder lo que ya sabía (gracias a KL); y DPO simplifica todo a una loss directa. Los tres errores principales —reward hacking, KL excesivo, y datos inconsistentes— son evitables con las prácticas correctas de evaluación y diseño de dataset.

En Colombia 🇮🇩 solemos decir que "el que mucho abarca, poco aprieta". En RLHF pasa lo mismo: un reward model bien diseñado y un KL bien ajustado valen más que un sistema complejo que hace trampa sin que uno se dé cuenta. La próxima vez que un LLM te responda de forma que se siente natural y útil, date cuenta de que probablemente hay un equipo detrás entrenándolo con estas técnicas.
