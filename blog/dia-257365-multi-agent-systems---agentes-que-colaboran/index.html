Vector Databases y Embeddings

Hagale pues, parcero. Llegamos al Día 257 y hoy vamos a hablar de algo que el 80% ignora pero que hace sus RAG 10x mejores: Vector Databases y Embeddings. Esto es la infraestructura que separa los sistemas de búsqueda semántica funcionales de los que de verdad funcionan en producción. Póngase cómodo que esto vale la pena.

🎯 Por Qué los Embeddings Son el Centro de Todo

Un embedding es una representación vectorial densa de texto, imagen o cualquier dato. La magia está en que vectores similares quedan cerca en el espacio n-dimensional:

$$\text{sim}(A, B) = \cos(\theta) = \frac{A \cdot B}{\|A\| \|B\|}$$

Esta simple fórmula de similitud coseno es la base de toda búsqueda semántica. Cuando tu query entra como un vector, los documentos más cercanos en el espacio vectorial son los más relevantes semánticamente. Pero aquí viene el problema: cuando tienes millones de vectores, calcular similitud contra todos es computationally imposible. Ahí entran los vector databases y los algoritmos ANN.

📐 Approximate Nearest Neighbor (ANN)

Buscar el nearest neighbor exacto en espacios de alta dimensionalidad es $O(n \cdot d)$ donde $n$ es el número de vectores y $d$ la dimensionalidad. Para 10 millones de vectores de 1536 dimensiones, eso es completamente inviable en tiempo real. Los algoritmos ANN sacrifican precisión exacta por velocidad dramática:

Métricas clave:

  • Recall@K: Qué porcentaje de los K vecinos reales recuperaste
  • QPS: Queries por segundo
  • Index size: Memoria necesaria para el índice

Los tres algoritmos ANN más importantes:

# Los tres algoritmos ANN fundamentales

# 1. HNSW (Hierarchical Navigable Small World)
# Grafos multi-nivel para búsqueda aproximada
# Bueno para: baja latencia, alta recall, datos pequeños-medianos
index_hnsw = faiss.IndexHNSWFlat(d, m)  # m = conexiones por nodo
index_hnsw.hnsw.efSearch = 64  # calidad de búsqueda
index_hnsw.hnsw.efConstruction = 128  # calidad de construcción

# 2. IVF (Inverted File Index)
# Clustering + búsqueda en clusters cercanos
# Bueno para: datos grandes, memoria limitada
index_ivf = faiss.IndexIVFFlat(quantizer, d, nlist)
index_ivf.nprobe = 16  # cuántos clusters buscar

# 3. PQ (Product Quantization)
# Compresión de vectores para datos masivos
# Bueno para: mil millones+ vectores, memoria muy limitada
index_pq = faiss.IndexPQ(d, m, nbits)  # m subvectores, nbits por subvector

🚀 ChromaDB: El Vector DB para Desarrollo Rápido

ChromaDB se volvió el estándar para desarrollo local y prototipado por su simplicidad:

import chromadb
from chromadb.config import Settings

# Inicializar cliente
client = chromadb.Client(Settings(
    anonymized_telemetry=False,
    allow_reset=True
))

# Crear colección
collection = client.create_collection(
    name="documentos_colombia",
    metadata={"hnsw:space": "cosine"}  # similitud coseno
)

# Agregar documentos con embeddings
collection.add(
    documents=[
        "Bogotá es la capital de Colombia",
        "Medellín se llama la ciudad de la eterna primavera",
        "Cali es known as la salsa capital del mundo"
    ],
    metadatas=[
        {"fuente": "geografia", "ciudad": "bogota"},
        {"fuente": "geografia", "ciudad": "medellin"},
        {"fuente": "cultura", "ciudad": "cali"}
    ],
    ids=["doc1", "doc2", "doc3"]
)

# Búsqueda semántica
resultados = collection.query(
    query_texts=["capital de Colombia"],
    n_results=2
)
print(resultados)

🔢 FAISS: Producción a Escala

Cuando necesitas producción con miles de millones de vectores, FAISS de Meta es el estándar:

import faiss
import numpy as np

# Crear índice para 1 millón de vectores de 768 dimensiones
d = 768  # dimensionalidad (ej: sentence-transformers)
n = 1_000_000

# Método 1: IVF con HNSW como quantizer (lo mejor de ambos mundos)
print("Construyendo índice IVF-HNSW...")
quantizer = faiss.IndexHNSWFlat(d, 32)
index = faiss.IndexIVF(quantizer, d, 32768)  # 32768 clusters
index.nprobe = 64  # buscar en 64 clusters más cercanos
index.set_direct_map_type(faiss.DirectMap.Hashtable)

# Entrenar (requiere suficientes vectores)
index.train(np.random.rand(n, d).astype('float32'))

# Agregar vectores en batches
batch_size = 10000
for i in range(0, n, batch_size):
    vectors = np.random.rand(min(batch_size, n-i), d).astype('float32')
    index.add(vectors)

print(f"Índice construido con {index.ntotal} vectores")

# Búsqueda
query = np.random.rand(1, d).astype('float32')
k = 10  # recuperar los 10 más cercanos
distances, indices = index.search(query, k)
print(f"Top {k} resultados: índices {indices[0]}, distancias {distances[0]}")

⚠️ Los 3 Errores Más Comunes

Error 1: Brute Force en Producción

El problema: Calcular similitud contra todos los vectores funciona con 100 docs, pero con 1 millón tu sistema muere. El recall es 100% pero la latencia es inaceptable.

La solución: Usar ANN desde el principio. Empieza con HNSW que te da 95-99% de recall con 100-1000x speedup:

# NO HACER ESTO en producción
def brute_force_search(query, documents, k=10):
    scores = []
    for doc in documents:
        score = cosine_similarity(query, doc.embedding)
        scores.append((score, doc))
    return sorted(scores, reverse=True)[:k]

# SÍ HACER ESTO desde el inicio
index = faiss.IndexHNSWFlat(d, 32)  # Construir índice ANN
index.add(all_vectors)  # Agregar datos
distances, indices = index.search(query_vector, k)  # Búsqueda O(log n)

Error 2: No Entender el Tradeoff Speed vs Accuracy del ANN

El problema: Elegir parámetros sin entender el impacto. Pones efSearch=16 y te sorprende que el recall sea 70%. O intentas 99% de recall y tu latencia explota.

La matemática: En HNSW, efSearch controla el tamaño del beam search. Mayor efSearch = más nodos explorados = mayor recall pero más lento:

$$O(\text{efSearch}) \approx O(\log(n) \cdot \text{efSearch})$$

La solución: Haz curveas de recall vs latency para tu dataset específico:

import time

def benchmark_ann(index, test_vectors, ground_truth, ef_values):
    results = []
    for ef in ef_values:
        index.hnsw.efSearch = ef
        total_time = 0
        recalls = []
        
        for i, (query, true_neighbors) in enumerate(zip(test_vectors, ground_truth)):
            start = time.time()
            _, indices = index.search(query.reshape(1, -1), k=10)
            total_time += time.time() - start
            
            retrieved = set(indices[0])
            recall = len(retrieved & set(true_neighbors)) / len(true_neighbors)
            recalls.append(recall)
        
        avg_recall = sum(recalls) / len(recalls)
        avg_latency = total_time / len(test_vectors)
        results.append((ef, avg_recall, avg_latency))
        print(f"efSearch={ef}: recall={avg_recall:.3f}, latency={avg_latency*1000:.1f}ms")
    
    return results

# Encontrar el sweet spot para tu aplicación
benchmark_ann(index, queries, ground_truth, [16, 32, 64, 128, 256])

Error 3: No Afinar Parámetros del Índice para Tu Caso

El problema: Usar parámetros por defecto. Tu índice ocupa 20GB cuando podría ocupar 5GB con el mismo recall. O tu búsqueda toma 500ms cuando podría ser 50ms.

La solución: Afinar los 3 parámetros críticos:

# Los tres parámetros que más importan:

# 1. efConstruction (HNSW) - calidad del índice
# Más alto = mejor conectividad del grafo = mejor recall
# Costo: más tiempo de construcción
# Recomendación: 64-128 para producción
index_hnsw.hnsw.efConstruction = 128

# 2. efSearch (HNSW) - calidad de búsqueda
# Debe ser >= k (número de resultados deseados)
# Recomendación: k * 2 a k * 10
index_hnsw.hnsw.efSearch = 128  # si quieres top-10

# 3. nprobe (IVF) - cuántos clusters buscar
# Más clusters = mayor recall = mayor latencia
# Recomendación: start con sqrt(nlist), ajusta según recall
index_ivf.nprobe = int(np.sqrt(index_ivf.nlist))

# Para compresión con PQ, el balanceo precisión/espacio:
# m subvectores (más = más precisión, más memoria)
# nbits por subvector (más = menos compresión, más precisión)
# 8 bits típicamente da buen balance
index_pq = faiss.IndexPQ(d, m=8, nbits=8)  # 8 * 8 = 64 bits por vector vs 768*32 bits original

📝 Resumen

  • Los embeddings son vectores densos que capturan significado semántico
  • ANN permite búsqueda en millones/billones de vectores en tiempo real
  • ChromaDB para prototipado, FAISS para producción a escala, Pinecone/Weaviate para nube
  • HNSW ofrece el mejor balance speed/accuracy para la mayoría de casos
  • Siempre afina efSearch, efConstruction y nprobe para tu dataset específico
