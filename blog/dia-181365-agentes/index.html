Dia 181/365: Agentes — el detective privado que programa en tu nombre

30 de junio de 2026
langchain.agents

Introduccion: Cuando el LLM se vuelve util de verdad

Tengo una cicatriz vieja con esto. En 2023 monte un "asistente SQL" para un equipo de analytics: el LLM generaba queries perfectas, las explicaba con diagramas ASCII, hasta recitaba el manual de Postgres de memoria. Pero cuando el usuario de verdad preguntaba "dame los 10 clientes con mas facturas del Q3 cerrado", el sistema escribia un SELECT bonito en pantalla y se quedaba ahi. Nadie lo ejecutaba. Nadie lo conectaba a la base. El usuario tenia que copiar, pegar, abrir DBeaver, correr, y volver. La adopcion fue del 4%. Murio en seis semanas.

El problema no era el prompt. Era que un LLM solo es una maquina de texto: no toca el mundo, no lee, no escribe. Para que sirva en produccion tiene que observar, decidir, actuar y volver a observar. Eso es un agente. No es magia, es un loop de decision sobre un espacio de acciones que incluye herramientas externas.

En este articulo te voy a mostrar que es formalmente un agente, como langchain.agents lo implementa por debajo, y como convertir un demo de notebook en algo que aguanta trafico real sin quemarte el presupuesto de tokens ni la paciencia del on-call.

1. Que es un Agente? (Y por que deberia importarte)

1.1 La analogia cotidiana

Imaginate un detective privado investigando un caso de fraude corporativo. No tiene acceso a la escena del crimen; tiene que armar el rompecabezas desde afuera.

Ciclo del detective:

  1. Observa una pista nueva (un correo, un testimonio, un registro contable).
  2. Piensa: "esto encaja con la hipotesis de la empresa fantasma, voy a verificar".
  3. Actua: llama a un informante, revisa una base publica, interroga a un sospechoso.
  4. Vuelve a 1 con la nueva evidencia.

Eso es exactamente ReAct (Reason + Act, Yao et al., 2022). La diferencia es que el "detective" es un LLM, las "pistas" son outputs de herramientas, y la "hipotesis" es texto que el modelo escribe en su scratchpad. Cuando el detective ya tiene suficiente, escribe Final Answer y cierra el caso.

Un agente no es "un LLM con_tools=true". Es un sistema que mantiene un historial de (Thought, Action, Observation) y decide en cada paso cual es la siguiente mejor accion dado todo lo que vio.

1.2 La matematica formal

Formalmente, un agente es una politica $\pi_\theta$ sobre un POMDP (Partially Observable Markov Decision Process). La tupla completa es:

$$\langle \mathcal{S}, \mathcal{A}, \mathcal{T}, \mathcal{R}, \Omega, O \rangle$$

Simbolo por simbolo:

  • $\mathcal{S}$ — el conjunto de estados del mundo (la "verdad" que no vemos: la base de datos real, el filesystem, la web).
  • $\mathcal{A}$ — el conjunto de acciones que el agente puede ejecutar. En langchain.agents esto es: llamar a una tool, o terminar con Final Answer.
  • $\mathcal{T}(s' \mid s, a)$ — funcion de transicion: probabilidad de terminar en $s'$ si estabas en $s$ e hiciste $a$. En la mayoria de tools deterministas, $\mathcal{T}$ es degenerada (probabilidad 1).
  • $\mathcal{R}(s, a)$ — recompensa inmediata. En agentes con LLM casi nunca se observa explicitamente; se define implicita como "1 si完成任务, 0 si no".
  • $\Omega$ — el conjunto de observaciones posibles (el output de las tools: filas SQL, codigo HTTP, texto scrapeado).
  • $O(o \mid s, a)$ — probabilidad de observacion: que tan probable es ver $o$ despues de tomar $a$ en estado $s$.

Como el agente nunca ve $\mathcal{S}$ directamente, mantiene una distribucion de creencia $b(s)$ sobre los estados. Despues de cada accion-observacion, la belief se actualiza por Bayes:

$$b'(s') = \eta \cdot O(o \mid s', a) \sum_{s \in \mathcal{S}} \mathcal{T}(s' \mid s, a) \, b(s)$$

donde $\eta$ es la constante de normalizacion para que $\sum_{s'} b'(s') = 1$.

La politica del agente elige la siguiente accion maximizando la utilidad esperada sobre la belief:

$$\pi^*(b) = \arg\max_{a \in \mathcal{A}} \; \mathbb{E}_{s \sim b, s' \sim \mathcal{T}} \left[ \mathcal{R}(s,a) + \gamma \sum_{b'} P(b' \mid b,a) \, U(b') \right]$$

En langchain.agents esta politica se aproxima con un LLM que, dado el contexto $c_t = (o_1, a_1, o_2, a_2, \ldots, o_t)$, muestrea la siguiente accion:

$$\hat{a}_t \sim P_\theta(\cdot \mid c_t) = \frac{\exp(z_t / \tau)}{\sum_{a'} \exp(z_{a'} / \tau)}$$

donde $z_t$ son los logits del LLM para el token de accion y $\tau$ es la temperatura. Con temperature=0 cae en argmax greedy, que es lo que queres en produccion (reproducibilidad).

2. Como langchain.agents resuelve esto por vos

langchain.agents no reinventa la rueda: implementa el loop ReAct con piezas intercambiables. El flujo interno es:

        +----------------------------------+
        |                                  |
        v                                  |
   [LLM call]                              |
   prompt = system + tools + history +     |
            scratchpad                      |
        |                                  |
        v                                  |
   [parse output]                          |
   Thought: ...                            |
   Action: tool_name                       |
   Action Input: {...}                     |
        |                                  |
        +--> Action == "Final Answer" --> [return to user]
        |
        +--> Action == tool_name --> [execute tool]
                                          |
                                          v
                                    [Observation] --+
                                                      |
                                                      |
        +----------------------------------------------+
        |
        v
   [append to scratchpad, loop]

Las piezas clave:

  • BaseSingleActionAgent / BaseMultiActionAgent: la politica. En modo ReAct es un LLM que devuelve texto estructurado.
  • AgentExecutor: el motor que ejecuta el loop, parsea outputs, llama tools, maneja errores, y corta por max_iterations o max_execution_time.
  • BaseTool: la abstraccion sobre cualquier funcion externa (SQL, HTTP, Python REPL, etc.) con un schema JSON.
  • AgentOutputParser: convierte el texto crudo del LLM en AgentAction o AgentFinish.

El scratchpad es la memoria de corto plazo del agente: acumula todos los (Thought, Action, Observation, Observation) hasta el momento. Por eso los prompts de ReAct terminan con {agent_scratchpad}.

3. langchain.agents: Uso Directo y Casos de Control Fino

El caso "feliz" de la documentacion, production-grade minimo viable:

from langchain.agents import create_react_agent, AgentExecutor
from langchain.tools import tool
from langchain_openai import ChatOpenAI
from langchain import hub

@tool
def query_postgres(sql: str) -> str:
    """Ejecuta un SELECT sobre la base de analytics y devuelve filas en JSON."""
    # Aqui iria tu conexion real (psycopg, sqlalchemy, etc.)
    import json
    rows = [{"cliente": "ACME", "facturas": 42, "q3_total": 185000.0}]
    return json.dumps(rows, ensure_ascii=False)

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
prompt = hub.pull("hwchase17/react")  # prompt canonico de ReAct

agent = create_react_agent(llm, [query_postgres], prompt)
executor = AgentExecutor(
    agent=agent,
    tools=[query_postgres],
    max_iterations=8,        # corta loops infinitos
    max_execution_time=45,   # segundos max de pared
    handle_parsing_errors=True,
    return_intermediate_steps=True,  # para debug y auditoria
)

result = executor.invoke({"input": "Top 5 clientes por facturacion del Q3 2024"})
print(result["output"])
for step in result["intermediate_steps"]:
    action, observation = step
    print(f"Tool: {action.tool} | Input: {action.tool_input}")

handle_parsing_errors=True es la primera linea de defensa contra LLMs que se saltan el formato y escriben prosa libre en vez de Action: ....

4. Implementacion Production-Ready: AgenteRobusto

Un agente "de notebook" se rompe en produccion el primer dia. Lo que necesitas es control fino sobre retries, costos, timeouts, observabilidad y fallos de parsing.

4.1 Tipos y protocolos

Primero, definimos excepciones de dominio y el dataclass de resultado. Esto te da errores tipados en vez de try/except Exception genericos.

from dataclasses import dataclass
from typing import Any

class AgentBudgetExceeded(Exception):
    """El costo acumulado supero el presupuesto por consulta."""

class AgentTimeout(Exception):
    """El agente excedio el wallclock permitido."""

class AgentLoopDetected(Exception):
    """El agente entro en un loop de acciones repetidas."""

@dataclass(frozen=True)
class AgentRunResult:
    output: str
    intermediate_steps: tuple
    cost_usd: float
    total_tokens: int
    elapsed_s: float
    iterations: int

4.2 El motor principal

El runner envuelve AgentExecutor con tres contratos: a lo sumo N reintentos, costo acotado por corrida, y wallclock acotado. Las verificaciones se hacen DESPUES de invocar, porque get_openai_callback solo contabiliza dentro de su with.

import logging
import time
from tenacity import retry, stop_after_attempt, wait_exponential
from langchain.callbacks import get_openai_callback

logger = logging.getLogger(__name__)

class ProductionAgentRunner:
    def __init__(
        self,
        executor: AgentExecutor,
        *,
        max_cost_usd: float = 0.50,
        max_wallclock_s: float = 60.0,
        max_iterations: int = 8,
    ) -> None:
        self.executor = executor
        self.max_cost_usd = max_cost_usd
        self.max_wallclock_s = max_wallclock_s
        self.max_iterations = max_iterations

    @retry(
        stop=stop_after_attempt(3),
        wait=wait_exponential(multiplier=1, min=1, max=8),
        reraise=True,
    )
    def run(self, query: str) -> AgentRunResult:
        t0 = time.monotonic()
        # get_openai_callback SOLO cuenta tokens de OpenAI.
        # Si usas Anthropic o local, sustituye por un TokenCounter propio.
        with get_openai_callback() as cb:
            raw = self.executor.invoke({"input": query})
        elapsed = time.monotonic() - t0
        steps = tuple(raw.get("intermediate_steps", ()))

        if elapsed > self.max_wallclock_s:
            raise AgentTimeout(f"{elapsed:.1f}s > {self.max_wallclock_s}s budget")
        if cb.total_cost > self.max_cost_usd:
            raise AgentBudgetExceeded(
                f"${cb.total_cost:.4f} > ${self.max_cost_usd} budget"
            )
        if len(steps) > self.max_iterations:
            logger.warning("Agente uso %d iteraciones (max=%d)", len(steps), self.max_iterations)

        logger.info(
            "agent_run | cost=$%.4f tokens=%d elapsed=%.2fs steps=%d",
            cb.total_cost, cb.total_tokens, elapsed, len(steps),
        )
        return AgentRunResult(
            output=raw["output"],
            intermediate_steps=steps,
            cost_usd=cb.total_cost,
            total_tokens=cb.total_tokens,
            elapsed_s=elapsed,
            iterations=len(steps),
        )

4.3 Utilidades de analisis y verificacion

Para debugging rapido, dos helpers que pagan su sueldo el primer lunes de guardia.

from collections import Counter
from langchain.agents.output_parsers import ReActSingleInputOutputParser

def action_histogram(steps) -> dict[str, int]:
    """Cuenta cuantas veces se llamo cada tool. Sirve para detectar loops."""
    return Counter(step[0].tool for step in steps).most_common()

def detect_repeated_actions(steps, threshold: int = 3) -> dict[str, int]:
    """Devuelve tools llamadas >= threshold veces seguidas o en total."""
    counts = Counter(step[0].tool for step in steps)
    return {tool: n for tool, n in counts.items() if n >= threshold}

# Verificacion numerica manual (comentada para referencia):
# Si action_histogram devuelve {'query_postgres': 5, 'Final Answer': 0},
# tu agente itero 5 veces contra la misma tool sin terminar.
# Eso casi siempre es: tool devuelve error, agente reintenta, mismo error, loop.

5. Ejemplos de Uso en Casos Reales

Caso 1: SQL agent con presupuesto estricto. Acoplamos el runner production al agente SQL del ejemplo anterior.

agent = create_react_agent(llm, [query_postgres], prompt)
executor = AgentExecutor(
    agent=agent, tools=[query_postgres],
    max_iterations=6, max_execution_time=30,
    handle_parsing_errors=True, return_intermediate_steps=True,
)
runner = ProductionAgentRunner(executor, max_cost_usd=0.10, max_wallclock_s=30)

try:
    res = runner.run("Cuantos clientes nuevos hubo en Q3 2024?")
    print(res.output)
    print(f"Costo: ${res.cost_usd:.4f} | Tokens: {res.total_tokens} | Pasos: {res.iterations}")
except AgentBudgetExceeded as e:
    logger.error("Query demasiado cara: %s", e)

Verificacion numerica: un agente ReAct con gpt-4o-mini y 6 iteraciones max usa ~3k tokens de input promedio (prompt + scratchpad) y ~200 de output por iteracion. A $0.15/M input y $0.60/M output, una corrida cuesta ~$0.005. Con budget de $0.10 tienes margen para 20 corridas concurrentes sin susto.

Caso 2: Web research agent. El agente busca, scrapea, resume. Aqui la trampa es que web_search suele devolver JSON enorme; el agente se come el contexto.

@tool

    import json
    return json.dumps([
        {"title": "LangChain Agents", "url": "https://...", "snippet": "..."},
    ])

@tool
def fetch_url(url: str) -> str:
    """Descarga el contenido textual de una URL."""
    # Truncar a 4000 chars para que quepa en contexto con margen.
    return "contenido truncado"

agent = create_react_agent(llm, [web_search, fetch_url], prompt)

Verificacion: si ves total_tokens > 12000 en una sola corrida, casi seguro es que el agente metio una pagina entera en el scratchpad. Truncar fetch_url a 4000 chars mantiene el scratchpad bajo control.

Caso 3: Code execution agent. Util para data scientists que quieren el LLM ejecutando pandas.

@tool
def python_repl(code: str) -> str:
    """Ejecuta codigo Python en un sandbox y devuelve stdout o error."""
    import subprocess, tempfile, os
    with tempfile.NamedTemporaryFile(mode="w", suffix=".py", delete=False) as f:
        f.write(code)
        path = f.name
    try:
        result = subprocess.run(
            ["python", path], capture_output=True, text=True, timeout=10
        )
        return result.stdout or result.stderr
    finally:
        os.unlink(path)

Advertencia: subprocess.run directo es un riesgo de seguridad. En produccion usa RestrictedPython, pyodide en WASM, o un servicio externo como E2B. Esto lo dejo aca para que veas la forma; no lo deployes asi en un sistema multi-tenant.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: Loop infinito sobre la misma tool.

Sintoma: iterations=8, output="Agent stopped due to iteration limit", y action_histogram muestra la misma tool 6+ veces.

Codigo que reproduce:

@tool
def broken_tool(x: str) -> str:
    """Esta tool siempre falla."""
    raise ValueError("algo salio mal")

# Ejecuta: executor.invoke({"input": "intenta X"}) y veras el loop.

Deteccion numerica: detect_repeated_actions(steps, threshold=3) devuelve la tool problematico.

Soluciones (en orden de impacto):

  1. Setear max_iterations agresivamente (5-8 para agentes de una sola tool; 10-15 para multi-tool).
  2. Capturar excepciones dentro de la tool y devolverlas como string en vez de raise. Asi el LLM recibe "Error: timeout" como Observation y puede replantear.
  3. Memoization de tools idempotentes: si el agente llama dos veces con el mismo input, devolver el cache.
  4. Prompt engineering: agregar al prompt "Si una tool falla 2 veces con el mismo error, prueba otra estrategia."

Problema 2: Tool inventada (alucinacion de nombre).

Sintoma: el LLM escribe Action: search_web cuando tu tool se llama web_search. El parser revienta.

Deteccion:

def detect_unknown_actions(raw_output: str, valid_tool_names: set[str]) -> list[str]:
    """Devuelve nombres de tools que el LLM invento."""
    unknown = []
    for line in raw_output.splitlines():
        if line.startswith("Action:"):
            name = line.split(":", 1)[1].strip()
            if name not in valid_tool_names and name != "Final Answer":
                unknown.append(name)
    return unknown

Soluciones:

  1. handle_parsing_errors="Check output format. Use only available tool names." — le da feedback explicito al LLM.
  2. Limitar tool_names en el prompt a una lista explicita; el default de create_react_agent ya lo hace via {tool_names}.
  3. Si la alucinacion persiste, baja la temperatura a 0 y revisa si tu modelo es suficientemente bueno (algunos modelos chicos alucinan nombres con frecuencia).

Problema 3: Explosion de tokens y costo.

Sintoma: total_tokens=45000 en una sola consulta.

Deteccion: cualquier corrida con total_tokens > 15000 en un agente de 5 tools merece auditoria.

Soluciones:

  1. Truncar outputs de tools agresivamente (3000-5000 chars).
  2. Limitar el tamano del scratchpad: si pasa de N tokens, resumir las observaciones mas viejas con el mismo LLM antes de continuar.
  3. max_execution_time corto: un agente que se demora mas de 30-60s en una sola consulta es un agente mal configurado.

7. Optimizaciones de Produccion

Optimizacion 1: Token budget cap en tiempo real.

El ProductionAgentRunner que arme arriba corta DESPUES de ejecutar. Para cortar EN VIVO (cuando el agente todavia esta iterando), usa max_iterations bajo y un callback de streaming que cancele si cb.total_cost excede el 70% del budget. Esto es critico para evitar que un agente con bug queme $5 en una sola request.

Optimizacion 2: Paralelizacion cuando las tools son independientes.

ReAct es inherentemente secuencial: cada Thought depende del Observation anterior. PERO si tu agente necesita, por ejemplo, consultar 5 tablas para un solo reporte, podes pre-computar las observaciones en paralelo con un asyncio.gather y darselas ya resueltas al LLM en el primer prompt. Tradeoff: gastas mas en tools (latencia) pero ahorras 4-5 iteraciones del LLM (costo y latencia de inferencia). En la practica suele ganar el approach paralelo para queries pesadas tipo "dame KPIs de las 5 regiones".

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

  • Empieza siempre con max_iterations=8 y temperature=0. Reproducibilidad y cota dura, en ese orden.
  • Limita el presupuesto por corrida (yo uso $0.10 para tools simples, $0.25 para multi-step). Un agente sin budget cap es un incidente esperando el finde.
  • Troncha outputs de tools a 3000-5000 chars. El scratchpad es la sangre del agente; si se envenena con paginas web enteras, todo el loop se vuelve tonto y caro.
  • Captura excepciones dentro de la tool y devuelvelas como Observation. Dejar que raise suba hasta el parser rompe el loop y te da un error generico que no dice nada.
  • Audita intermediate_steps siempre. En produccion guardalos en una tabla: tool, input, output_len, latency_ms. Sin esa data, estas volando a ciegas.
# Mini-checklist para deployar un agente
checks = {
    "max_iterations set": executor.max_iterations <= 10,
    "temperature is 0": llm.temperature == 0,
    "handle_parsing_errors on": executor.handle_parsing_errors is not False,
    "budget cap exists": runner.max_cost_usd <= 1.00,
    "wallclock cap exists": runner.max_wallclock_s <= 120,
    "intermediate_steps captured": executor.return_intermediate_steps,
}
assert all(checks.values()), f"Falla en: {[k for k,v in checks.items() if not v]}"

Un agente ReAct bien configurado es la diferencia entre un demo que impresiona en el stand del conference y un sistema que soporta 10k requests/dia sin que el on-call se suicide. Pilas con esto: la diferencia entre "funciona en mi notebook" y "funciona en produccion" son estas pequenas cotas y una capa de observabilidad. Cualquiera puede pegar create_react_agent y sacarlo en TikTok; pocos lo deployan sin que se caiga al segundo dia.

Parce, el LLM solo no te va a salvar. El loop ReAct, las cotas duras y la observabilidad si. Mira, si te quemaste con este articiculo, ya sabes que hacer manana. 🛠️
