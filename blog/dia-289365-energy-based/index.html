Dia 289/365: RAG vs Long Context — La camara de seguridad del supermercado que graba 720 horas vs el investigador que sabe que clip pedir

16 de octubre de 2026
Gemini 1.5 1M context vs RAG retrieval

Introduccion: La ilusion de meterlo todo en el prompt

A finales de 2024 un cliente me llamo casi en panico: tenia un contrato marco de 800 paginas, varios idiomas, y necesitaba un bot que respondiera preguntas de procurement sobre cualquier clausula. "Le metemos los 1.5M tokens de Gemini y listo", me dijo el PM. Le dije de una que eso iba a salir caro, pero el queria ver el demo primero. El demo funciono. La factura de fin de mes, no.

Eso es lo que nadie te cuenta del long context: el needle-in-a-haystack se ve spectacular en los benchmarks que publica cada vendor, pero en produccion tienes que pensar en costo, latencia, consistencia y, sobre todo, en si tu caso de uso realmente necesita que el modelo "vea" todo el corpus simultaneamente.

Este articulo no es para venderte Gemini 1.5 Pro con su ventana de un millon de tokens ni para hacerte creer que RAG es la bala de plata. Es para que veas, con numeros, cuando cada uno tiene sentido, cuando los dos se combinan, y cuando te estan vendiendo humo tecnologico.

1. Que significa realmente "long context" y como se compara con RAG

1.1 La analogia cotidiana

Imagina una camara de seguridad 24/7 instalada en un supermercado. Graba 720 horas continuas, cada pasillo, cada cliente, cada movimiento de caja. Eso es Gemini 1.5 con su ventana de un millon de tokens: todo esta ahi, timestampado, listo para ser revisado.

Ahora, el jueves a las 3pm alguien robo una lata de atun en la caja 4. Tienes dos opciones:

  • Opcion A — Visionar las 720 horas: barres todo el material, frame por frame, hasta encontrar al senor del gorro rojo. Te toma dias. Pero tienes contexto completo: sabes que el mismo sujeto estuvo antes en la seccion de vinos mirando la camara, y que salio por la puerta norte.
  • Opcion B — Investigador con sistema de busqueda: el investigator le pregunta al sistema "muéstrame todos los hombres con gorro rojo que pasaron por caja 4 entre las 14:55 y 15:05 del jueves", y en 30 segundos tiene los 40 segundos relevantes, listos para analisis forense.

RAG es la opcion B con esteroides: retrieval semantico en vez de busqueda por atributos visuales. Long context es la A: el modelo tiene acceso a todo el corpus en su ventana, pero tu pregunta es "cual es la escena relevante?" y eso lo hace el propio modelo.

La trampa es que muchos equipos eligen A porque "los modelos ya pueden", sin medir si el ROI justifica el costo o si el caso de uso realmente necesita ver las 720 horas.

1.2 La matematica formal (sin maquillaje)

Empecemos por donde duele: el costo computacional de la atencion. Para una secuencia de longitud $n$ y dimension oculta $d$:

$$\text{FLOPs}_{\text{attn}} = O(n^2 \cdot d)$$

FlashAttention y sus variantes reducen la huella de memoria de $O(n^2)$ a $O(n)$ en HBM, pero no eliminan la complejidad computacional: en algun momento del grafo, la matriz de atencion sigue siendo cuadratica en el numero de tokens. Eso es ley de hierro de los transformers.

Ahora la memoria del KV cache, que es lo que de verdad te mata en produccion:

$$\text{Memory}_{\text{KV}} = 2 \cdot n \cdot n_{\text{layers}} \cdot d_{\text{head}} \cdot n_{\text{kv\_heads}} \cdot \text{bytes}_{\text{precision}}$$

El factor 2 viene de las matrices K y V. Para un modelo estilo Gemini 1.5 Pro (del orden de 90+ capas, head dimension 128, grouped-query attention con un numero reducido de $n_{\text{kv\_heads}}$), un solo request de 500K tokens con cuantizacion de 8 bits ya se mueve en el rango de decenas de gigabytes solo para el cache. Multiplica por la concurrencia de tu sistema y te explota el presupuesto de infraestructura, o el rate limit del proveedor.

RAG, por contraste, tiene esta forma de costo:

$$\text{Cost}_{\text{RAG}} = \text{Embed}(q) + \text{Retrieve}(k) + \text{LLM}(q + \text{top-}k)$$

Con $k \ll n$ (tipicamente $k \in [3, 20]$). La latencia tiende a ser lineal en $k$, no cuadratica, y el contexto que recibe el LLM es pequeno y reutilizable entre queries.

La pregunta que nadie te hace en el blog post del vendor: el costo marginal por query de long context crece linealmente con cada byte de corpus que metes, mientras que RAG cobra principalmente por la query y por una fraccion pequena del corpus.

2. Como RAG vs Long Context Cambia el Diseno de Sistemas

Cuando montas long context, el sistema se ve "simple":

# Arquitectura long-context "ingenua"
def answer(question: str, corpus: list[str]) -> str:
    context = "\n".join(corpus)
    prompt = f"Responde basado en:\n{context}\n\nPregunta: {question}"
    return gemini.generate(prompt, max_tokens=2048)

Eso funciona para un demo. En produccion necesitas prefix caching, control de concurrencia, politicas de truncamiento, y manejo de rate limits. Empieza a verse asi:

import hashlib
from typing import Protocol


class LongContextEngine:
    def __init__(self, model, max_input_tokens: int = 1_000_000):
        self.model = model
        self.max_input_tokens = max_input_tokens
        self._prefix_cache_keys: dict[str, str] = {}

    @staticmethod
    def estimate_tokens(text: str) -> int:
        # Aproximacion conservadora: 1 token ~= 4 chars en espanol/ingles mixto
        return len(text) // 4

    def _cache_key(self, corpus: list[str]) -> str:
        joined = "\n".join(corpus)
        return hashlib.sha256(joined.encode("utf-8")).hexdigest()

    def answer(self, question: str, corpus: list[str]) -> str:
        token_estimate = sum(self.estimate_tokens(c) for c in corpus)
        if token_estimate > self.max_input_tokens:
            raise ValueError(
                f"Corpus demasiado grande ({token_estimate} tokens). "
                "Considere RAG, resumen previo o sliding window."
            )
        prefix_key = self._cache_key(corpus)
        return self.model.generate(
            prompt=f"Contexto:\n{''.join(corpus)}\n\nPregunta: {question}",
            max_output_tokens=2048,
            cached_prefix_id=prefix_key,
        )

La diferencia clave: en long context el sistema entero se reduce al modelo y un cache. No hay pipeline de retrieval que debuggear, no hay chunks mal cortados, no hay embeddings que se degradan con el tiempo. Pero tampoco tienes citacion natural ni puedes controlar que informacion entra al modelo mas alla del orden del prompt.

Cuando montas RAG, el sistema se vuelve un pipeline con seis piezas:

from typing import Protocol


class Embedder(Protocol):
    def embed(self, texts: list[str]) -> list[list[float]]: ...


class VectorStore(Protocol):
    def search(self, vector: list[float], top_k: int) -> list[dict]: ...


class Reranker(Protocol):
    def rerank(self, query: str, docs: list[dict], top_k: int) -> list[dict]: ...


class RAGPipeline:
    def __init__(self, embedder: Embedder, store: VectorStore,
                 reranker: Reranker, llm):
        self.embedder = embedder
        self.store = store
        self.reranker = reranker
        self.llm = llm

    def answer(self, question: str, top_k: int = 5) -> dict:
        q_vec = self.embedder.embed([question])[0]
        # Over-fetch para compensar ruido en el retrieval inicial
        candidates = self.store.search(q_vec, top_k=top_k * 4)
        reranked = self.reranker.rerank(question, candidates, top_k=top_k)
        context = "\n\n".join(d["text"] for d in reranked)
        sources = [
            {"id": d["id"], "score": d["score"]} for d in reranked
        ]
        answer = self.llm.generate(
            prompt=(
                "Responde solo con informacion del contexto provisto. "
                "Cita el id del chunk entre corchetes.\n\n"
                f"Contexto:\n{context}\n\nPregunta: {question}"
            ),
            max_tokens=512,
        )
        return {"answer": answer, "sources": sources}

Aqui el diseno vive o muere en la calidad del retrieval. Cambiaste un problema (costo de contexto lineal en el corpus) por cinco problemas nuevos: chunking, eleccion de embeddings, estrategia de indexacion, rerank, y verificacion de citaciones. Cada uno es un vector de falla y un lugar donde tu sistema puede degradarse silenciosamente.

3. Patrones y Anti-Patrones

Patron 1 — "Long context para sintesis, RAG para retrieval": cuando necesitas que el modelo razone sobre multiples documentos simultaneamente (ej. comparar tres contratos marco y extraer diferencias), long context gana. Cuando necesitas encontrar un dato especifico en un corpus de 50GB, RAG gana sin discusion.

Patron 2 — "RAG hibrido con expansion de contexto": retrieved top-k, luego se expande cada chunk con sus vecinos (ventana de +/- N tokens). Mejora recall en ~15% en corpus tecnico sin disparar el costo.

Patron 3 — "Context distillation": usas long context una vez para generar un resumen denso de cada documento, y luego sirves el resumen como system prompt cacheado. Combina la capacidad de compresion del long context con la velocidad del RAG.

Anti-patron 1 — "Meter todo el knowledge base en el prompt porque total el modelo aguanta": el modelo lo aguanta. Tu billetera no. Y en el momento que el corpus crece, te toca re-arquitecturar en caliente, que es la peor forma de migrar.

Anti-patron 2 — "Hacer RAG de un documento de 4 paginas": si cabe completo en contexto y necesitas que el modelo lo vea entero, lo metes. RAG introduce latencia y puntos de falla innecesarios para ese caso.

Anti-patron 3 — "Confundir recall alto del retrieval con citacion confiable del modelo": un chunk relevante no implica que el modelo lo cite correctamente. Esto lo cubre la evaluacion, no el prompt.

4. Trade-offs en Produccion

Dimension Long Context RAG
Latencia p50 1-4s (depende de prefijo cacheado) 0.4-1.2s
Costo por query Proporcional al tamano del corpus Casi constante
Freshness Re-procesar todo el corpus por cambio Re-embebedar solo docs modificados
Citacion Imprecisa, modelo inventa referencias Natural si retornas metadata del chunk
Debugging "Que parte del prompt fallo?" "Que chunk se recupero mal?" mas granular
Throughput Limitado por memoria de GPU Limitado por el backend de retrieval

El dato que mas duele: el costo por query en long context escala con tu producto. Si tu producto crece (mas documentos, mas usuarios), el costo por query crece linealmente con el corpus. En RAG, el costo marginal por query tiende a bajar conforme optimizas el retrieval pipeline y el rerank mejora.

Otro dato que pocos discuten: en contextos de 500K+ tokens, la calidad de las respuestas sobre informacion que aparece al principio o al final del corpus es notablemente mejor que la del medio. Es el llamado "lost in the middle". RAG mitiga esto porque fuerza al modelo a enfocarse en lo recuperado.

5. Casos de Uso Reales

Caso 1 — Revision de contratos legales (long context gano) Firma de abogados con acervo de 3,000 contratos (~120M tokens). Querian un asistente que respondiera "que contratos tienen clausula de fuerza mayor con jurisdiccion en Colombia y vigencia mayor a 2 anos?". RAG tradicional fallaba: la query requeria agregacion sobre el corpus completo. Gemini 1.5 Pro con contexto de 1M+ pudo sintetizar. Costo: ~$0.50 por query. Aceptable porque el caso de uso es de alto valor (abogados senior, ~10 queries/dia). No escalaria a 10,000 queries/dia sin cambiar la arquitectura.

Caso 2 — Chatbot de soporte sobre base de conocimiento tecnica (RAG gano) 500,000 articulos de documentacion tecnica, ~200M tokens en espanol e ingles. El contexto cambia semanalmente por releases. Long context era inviable: re-procesar 200M tokens por cada query era prohibitivo economicamente. Solucion: RAG con chunking de 512 tokens con overlap 64, embeddings de Cohere embed-v3, rerank con bge-reranker-v2-m3, y pgvector como store. Latencia p95: 850ms. Costo por query: ~$0.003. Freshness: nightly job de re-embedding incremental sobre los articulos modificados.

Caso 3 — Analisis de codebase (hibrido gano) Codebase de 8M lineas de codigo (~40M tokens). El equipo queria responder preguntas tipo "donde se usa esta funcion y que tests la cubren?". No era ni long context puro (40M tokens no caben en 1M con overhead de prompt) ni RAG puro (RAG no entendia dependencias entre archivos del mismo modulo). Solucion hibrida: retrieval semantico sobre signatures + expansion con AST parser para traer el contexto de uso real. El AST parser hacia el trabajo que un chunking naive no podia hacer.

6. Cuando NO Usarlo

Long context NO para:

  • Datos que cambian cada minuto (cache del modelo se invalida, costo por query se dispara).
  • Casos donde necesitas citacion exacta a nivel de parrafo (el modelo pierde precision citando en contextos largos).
  • Throughput alto con presupuesto limitado, especialmente en B2C.
  • Datos sensibles que no quieres exponer a un proveedor externo en su totalidad.

RAG NO para:

  • Documentos unicos que caben en contexto y necesitas razonamiento holistico sobre ellos.
  • Queries que requieren agregacion sobre todo el corpus ("cuantos contratos cumplen X").
  • Cuando tu retrieval es pobre y no tienes presupuesto para invertir en mejor chunking, embeddings, o rerank.
  • Cuando el corpus es tan pequeno (<50 documentos cortos) que indexar introduce complejidad sin beneficio.

7. Stack Tipico en Produccion

Lado long context:

  • Modelos: Gemini 1.5 Pro / Flash (1M-2M tokens), Claude 3.5 Sonnet (200K tokens) para casos donde Gemini no califica por compliance.
  • Prefix caching: habilitado desde el dia uno. Es la diferencia entre $0.50 y $0.05 por query en corpus estatico. Anthropic y Gemini lo soportan nativamente; OpenAI requiere estructuracion explicita del prompt.
  • Context distillation: usar long context para pre-computar un resumen denso que luego se sirve como system prompt cacheado. Reduce costo y latencia sin perder cobertura.

Lado RAG:

  • Vector store: Qdrant o pgvector si ya tienes Postgres en el stack. Weaviate si necesitas hybrid search (BM25 + dense) out-of-the-box.
  • Embeddings: text-embedding-3-large de OpenAI o embed-v3 de Cohere. Evitar embeddings pequenos (<768 dim) para corpus en espanol tecnico, la perdida de recall duele.
  • Reranking: Cohere Rerank 3.5 o bge-reranker-v2-m3. No skip-ear el rerank: mejora precision tipicamente 10-20% sobre el retrieval denso puro.
  • Evaluacion: RAGAS, DeepEval, o tu propio framework con golden set curado. Sin eval no hay RAG en produccion, solo fe.

Conclusion: Decision Framework

Antes de elegir arquitectura, responde estas preguntas en orden:

  • Tu corpus cabe completo en contexto y cambia poco (<10% al mes)? → Long context probablemente, con prefix caching obligatorio.
  • Tu corpus es grande (>1M tokens), cambia seguido, y necesitas citacion exacta? → RAG, sin dudarlo.
  • Tu query requiere agregacion o comparacion multi-documento? → Long context o arquitectura hibrida, RAG puro no resuelve.
  • Tu volumen de queries es alto (>1K/dia) y el presupuesto es estricto? → RAG casi siempre; long context escala mal con el volumen.
  • No tienes equipo para mantener un pipeline de retrieval? → Long context, asumiendo el costo y aceptando citacion debil.

Pilas con esto: long context no reemplazo RAG, y RAG no reemplazo long context. Son herramientas con geometrias de costo distintas. La decision inteligente es medir tamano del corpus, frecuencia de cambio, volumen de queries, y tolerancia a citacion imperfecta. Despues eliges.

Y no hay fiesta: si tu proveedor de long context te ofrece prefix caching, usalo desde el dia uno. Es la diferencia entre $0.50 y $0.05 por query en corpus estatico, y nadie te lo recuerda en el pricing page. 🎯
