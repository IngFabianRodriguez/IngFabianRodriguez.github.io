QLoRA — El gold standard para fine-tuning eficiente que el 80% desconoce

13 de may de 2026
fine-tuningqlorapytorch

Hola, parcero. Llegamos al Día 163 y hoy vamos con QLoRA. Este artículo es para los que tienen una GPU con 24GB de VRAM y sueñan con fine-tunear un Llama-70B. spoiler: se puede. QLoRA es la técnica que el 80% ignora cuando podría salvarles la GPU — y hoy te explico por qué, con código real de PyTorch.

📐 Fundamentos Teóricos

QLoRA = Quantized Low-Rank Adaptation. Es la combinación de dos ideas poderosas:

  • LoRA (Hu et al., 2021): en lugar de fine-tunear todos los pesos, solo entrenamos matrices de bajo rank que descomponen las actualizaciones de pesos como W + ΔW = W + BA, donde B ∈ ℝd×r y A ∈ ℝr×k con r << min(d,k).
  • Quantization: almacenar los pesos del modelo base en 4 bits en lugar de FP16/FP32, reduciendo dramáticamente el memory footprint.

La matemática detrás de QLoRA tiene tres componentes críticos:

1. NF4 (4-bit NormalFloat)

QLoRA usa NF4, un tipo de cuantización óptimo para pesos que siguen una distribución normal. La clave: no es una cuantización uniforme. La fórmula de los niveles de cuantización es:

# Niveles NF4 (ejemplo para 4 bits = 16 niveles)
# Los niveles están espaciados según la CDF de la Normal(0,1)
# escalados al rango [-1, 1]
nf4_levels = [-1.0, -0.6966, -0.5257, -0.3949, -0.2924, -0.2072,
               -0.1350, -0.0729, 0.0, 0.0729, 0.1350, 0.2072,
               0.2924, 0.3949, 0.5257, 0.6966, 1.0]

La ventaja sobre INT4 puro: NF4 tiene niveles más densos cerca de cero (donde la mayoría de los pesos residen) y más espaciados en las colas.

2. Double Quantization

Los quantization constants (un valor por bloque de pesos) también se cuantizan. Específicamente:

  • Cada bloque de 32 elementos tiene su propia constante de cuantización
  • Esa constante se cuantiza a FP8 (8 bits)
  • Ahorro adicional: por cada 64K parámetros, solo 8 bits extra

El ahorro en memoria de double quantization (DQ) es:

# Sin DQ: 1 constante FP32 por bloque de 32 = 32 bits / 32 = 1 bit/param solo para constantes
# Con DQ: la constante se cuantiza a FP8 = 8 bits / 32 = 0.25 bits/param
# Ahorro: 0.75 bits/param en constantes
dq_savings_bits_per_param = 1.0 - 0.25  # = 0.75 bits

3. Gradient Checkpointing

Durante el forward pass, no almacenamos los activations completos — los recomputamos durante el backward pass. Esto intercambia compute por memory:

# En PyTorch, gradient checkpointing reduce memory de O(n) a O(√n)
# pero aumenta compute en ~20-30%
model.gradient_checkpointing_enable()

Combinado con QLoRA, esto permite que un 70B que ocuparía ~140GB en FP16 quepa en ~35GB con QLoRA + gradient checkpointing.

💻 Implementación Práctica

Vamos con código real. Necesitamos: bitsandbytes, transformers, peft, y una GPU con 24GB.

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM
from peft import LoraConfig, get_peft_model, TaskType
from bitsandbytes.nn import Linear4Bit

# 1. Cargar modelo en 4-bit con NF4
model_name = "meta-llama/Llama-2-70b-hf"

# Config de cuantización
bnb_config = {
    "load_in_4bit": True,
    "bnb_4bit_quant_type": "nf4",           # NormalFloat4
    "bnb_4bit_compute_dtype": torch.bfloat16,
    "bnb_4bit_use_double_quant": True,        # Double quantization
}

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,
    device_map="auto",
    trust_remote_code=True,
)
model.enable_gradient_checkpointing()  # Gradient checkpointing

# 2. Configurar LoRA
lora_config = LoraConfig(
    r=64,                          # Rank - más alto = más expressivo pero más params
    lora_alpha=128,                # Scaling factor (típicamente 2x rank)
    target_modules=[                # Módulos a adaptar
        "q_proj", "v_proj",        # Attention
        "k_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj"  # MLP
    ],
    lora_dropout=0.05,
    bias="none",
    task_type=TaskType.CAUSAL_LM,
)

# 3. Aplicar LoRA al modelo cuantizado
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# Output: "trainable params: 166M || all params: 33.7B || trainable%: 0.49"

# 4. Training loop (simplificado)
from torch.utils.data import DataLoader

optimizer = torch.optim.AdamW(model.parameters(), lr=2e-4)

for batch in DataLoader(dataset):
    optimizer.zero_grad()
    
    # El forward pass usa pesos en 4-bit, pero computa en bfloat16
    outputs = model(**batch)
    loss = outputs.loss
    
    loss.backward()  # Gradient checkpointing recombina activations
    
    # Solo actualizamos los pesos LoRA (166M params), no los 33B completos
    optimizer.step()

¿Por qué funciona? Porque durante el forward/backward pass:

  • Los pesos base se dequantizan temporalmente a bfloat16 para la computación
  • Solo los pesos LoRA (A y B) se almacenan en FP16/bfloat16
  • El gradiente solo fluye hacia las matrices LoRA, no hacia los pesos cuantizados

🚨 Errores Comunes y Fixes

Error 1: Full Fine-Tune con GPU limitada

Síntoma: CUDA out of memory cuando intentas fine-tunear un modelo >7B en una GPU de 24GB.

Causa: No usar cuantización cuando el hardware es limitado. Un 70B en FP16 requiere 140GB de VRAM — imposible en una sola GPU consumer.

Fix: Usar QLoRA con load_in_4bit=True y bnb_4bit_quant_type="nf4". Esto reduce el modelo base a ~35GB y permite fine-tuning en GPU de 24GB.

Error 2: Rank de LoRA demasiado bajo

Síntoma: El modelo fine-tuneado pierde expressividad, no captura tareas complejas, el loss no converge bien.

Causa: Elegir r=8 o r=16 cuando el modelo tiene 70B. Con rank tan bajo, la matriz de actualización BA no tiene suficiente capacidad.

Fix: Usar r=64 o r=128 para modelos grandes. El trade-off: más rank = más parámetros entrenables pero mejor quality. Para 70B, r=64 es el sweet spot (166M params entrenables). Para modelos más pequeños (7B), r=16 puede ser suficiente.

Error 3: No usar Gradient Checkpointing

Síntoma: El modelo ocupa casi toda la VRAM disponible y el batch size tiene que ser 1 o 2.

Causa: Sin gradient checkpointing, todas las activations del forward pass se guardan para el backward pass. Para un 70B, esto puede ocupar >50GB adicionales.

Fix: Llamar model.enable_gradient_checkpointing() después de aplicar LoRA. Esto intercambia ~20-30% más compute por ~60% menos memory en activations, permitiendo batch sizes 4-8x más grandes.

✅ Mejores Prácticas

  • Usa NF4 sobre INT4 puro — está diseñado específicamente para pesos normales yda ~1-2% mejor perplexity.
  • Double quantization siempre — el ahorro en memoria es "gratis" en términos de quality.
  • Target modules completos: incluye q_proj, v_proj, k_proj, o_proj, gate_proj, up_proj, down_proj para máxima expressividad.
  • Learning rate: LoRA típicamente necesita 10x más LR que full fine-tune. Prueba entre 1e-3 y 3e-4.
  • Epochs: QLoRA converge más lento que full FT; planifica 3-5 epochs en vez de 1-2.
