LLM Model Selection — El 80% No Sabe Elegir Bien

Hagale pues, parcero. Así como en Bogotá uno no elige taxi cualquiera — porque sabe que el del parrillero de arriba es con el que llega vivo — en el mundo de los LLMs ocurre lo mismo: el 80% escoge cualquier modelo sin análisis, y el 20% que sí sabe lo hace con criterio matemático. Hoy día 341 unravelamos el framework completo para elegir modelos como quien sabe qué carro pedir en la noche del viernes. Café y vamos.

🎯 El Problema No Es Qué Modelo, Es Por Qué Ese Modelo

La mayoría de equipos usan el modelo más popular del momento o el que alguien les recomendó en un meetup. No hay métricas, no hay criterios, no hay data. Solo intuición y FOMO. Esto cuesta plata — mucha plata — y produce resultados inconsistentes.

La selección de modelos debe ser una función de optimización multi-variable, no una decisión de gut feeling:

$$\text{Modelo}^* = \arg\max_{m \in M} \left( \frac{Quality(m)}{Cost(m)} \cdot LatencyWeight(m) \cdot DomainFit(m) \right)$$

Donde:

  • Quality(m): Score de calidad para tu caso de uso específico
  • Cost(m): Costo por token o por request
  • LatencyWeight(m): Importancia de la latencia (1 = da igual, 10 = crítico)
  • DomainFit(m): Qué tan entrenado está el modelo en tu dominio (legal, médico, código, etc.)

📐 Framework de Selección: Los 4 Pilares

Pilar 1: Quality — ¿Qué Tan Bien Responde?

No basta con el benchmark general. Necesitas evaluar en tu dominio específico:

"""
Framework de Evaluación de Calidad para LLM Selection
=======================================================
Evalúa modelos en 4 dimensiones críticas para tu caso de uso.
"""

from dataclasses import dataclass
from typing import Dict, List, Optional
import json


@dataclass
class ModelCandidate:
    name: str
    provider: str  # openai, anthropic, google, meta, local
    context_window: int
    cost_per_1k_input: float  # USD
    cost_per_1k_output: float  # USD
    benchmark_scores: Dict[str, float]  # domain-specific benchmarks


@dataclass
class QualityEvaluation:
    """Evaluación de calidad en el dominio específico del usuario."""
    task_accuracy: float      # 0-100: Accuracy en tareas similares
    instruction_following: float  # 0-100: Qué tan bien sigue instrucciones
    coherence_score: float    # 0-100: Coherencia de respuestas largas
    factual_accuracy: float   # 0-100: Exactitud factual
    safety_score: float       # 0-100: Respuestas seguras y apropiadas


class LLMModelSelector:
    """
    Framework para seleccionar el LLM óptimo basado en múltiples criterios.
    
    Uso:
        selector = LLMModelSelector()
        selector.add_candidate(ModelCandidate(...))
        selector.add_candidate(ModelCandidate(...))
        best = selector.select(
            quality_weight=0.4,
            cost_weight=0.3,
            latency_weight=0.2,
            domain_weight=0.1
        )
    """
    
    def __init__(self, domain: str):
        self.domain = domain
        self.candidates: List[ModelCandidate] = []
        self.evaluations: Dict[str, QualityEvaluation] = {}
    
    def add_candidate(self, candidate: ModelCandidate):
        """Agrega un modelo candidato a la evaluación."""
        self.candidates.append(candidate)
    
    def evaluate_quality(
        self, 
        model_name: str, 
        test_cases: List[Dict]
    ) -> QualityEvaluation:
        """
        Evalúa la calidad de un modelo con test cases específicos.
        
        Args:
            model_name: Nombre del modelo a evaluar
            test_cases: Lista de dicts con {'input': str, 'expected': str, 'criteria': str}
        
        Returns:
            QualityEvaluation con scores en cada dimensión
        """
        # En producción, esto haría llamadas reales al modelo
        # y usaría un evaluator LLM o reglas específicas
        results = {
            'task_accuracy': 0.0,
            'instruction_following': 0.0,
            'coherence_score': 0.0,
            'factual_accuracy': 0.0,
            'safety_score': 0.0
        }
        
        for case in test_cases:
            # Simulación: en producción usarías el modelo real
            # y compararías output vs expected con un evaluator
            pass
        
        return QualityEvaluation(**results)
    
    def calculate_total_score(
        self,
        candidate: ModelCandidate,
        quality_weight: float = 0.4,
        cost_weight: float = 0.3,
        latency_weight: float = 0.2,
        domain_weight: float = 0.1,
        latency_tolerance_ms: int = 2000
    ) -> float:
        """
        Calcula el score total ponderado para un candidato.
        
        Args:
            quality_weight: Peso de la calidad (0-1)
            cost_weight: Peso del costo (0-1)
            latency_weight: Peso de la latencia (0-1)
            domain_weight: Peso del fit de dominio (0-1)
            latency_tolerance_ms: Latencia máxima aceptable en ms
        
        Returns:
            Score compuesto (higher is better)
        """
        eval_data = self.evaluations.get(candidate.name)
        
        if eval_data is None:
            # Usar benchmarks públicos si no hay evaluación custom
            quality = candidate.benchmark_scores.get(self.domain, 70.0)
        else:
            quality = (
                eval_data.task_accuracy * 0.4 +
                eval_data.instruction_following * 0.3 +
                eval_data.factual_accuracy * 0.3
            )
        
        # Normalizar calidad a 0-1
        quality_norm = quality / 100.0
        
        # Costo normalizado (invertido: menor costo = mayor score)
        avg_cost = (candidate.cost_per_1k_input + candidate.cost_per_1k_output) / 2
        cost_norm = max(0, 1 - (avg_cost / 0.10))  # Normalizado vs $0.10 baseline
        
        # Latencia normalizada
        # En producción medirías latencia real
        latency_estimate = candidate.context_window / 1000  # rough estimate
        latency_norm = max(0, 1 - (latency_estimate / latency_tolerance_ms))
        
        # Domain fit (simplificado)
        domain_fit = candidate.benchmark_scores.get(f"{self.domain}_domain", 0.5)
        
        # Score compuesto
        total = (
            quality_norm * quality_weight +
            cost_norm * cost_weight +
            latency_norm * latency_weight +
            domain_fit * domain_weight
        )
        
        return total
    
    def select(
        self,
        quality_weight: float = 0.4,
        cost_weight: float = 0.3,
        latency_weight: float = 0.2,
        domain_weight: float = 0.1,
        top_k: int = 1
    ) -> List[ModelCandidate]:
        """
        Selecciona el/los mejores modelos según criterios ponderados.
        
        Returns:
            Lista de top_k modelos ordenados por score compuesto
        """
        scored = []
        
        for candidate in self.candidates:
            score = self.calculate_total_score(
                candidate,
                quality_weight,
                cost_weight,
                latency_weight,
                domain_weight
            )
            scored.append((score, candidate))
        
        # Ordenar por score descendente
        scored.sort(key=lambda x: x[0], reverse=True)
        
        return [c for _, c in scored[:top_k]]

Pilar 2: Costo — La Ecuación Que El 80% Ignora

En Colombia sabemos de Plata — que no sobra. Y en LLMs el costo es crítico:

$$\text{CostoTotal} = \sum_{i=1}^{N} \left( Tokens_i^{input} \cdot C_{input} + Tokens_i^{output} \cdot C_{output} \right) \cdot Volumen_i$$

"""
Calculadora de Costo Real para LLM Selection
=============================================
Porque no es lo mismo el precio de lista que el costo real.
"""

class LLMCostCalculator:
    """
    Calcula el costo real de operación de un LLM considerando:
    - Costo por token (input/output)
    - Overhead de retries y errores
    - Costo de latencia (si es tiempo real)
    """
    
    def __init__(self, model: str, cost_input: float, cost_output: float):
        self.model = model
        self.cost_input = cost_input  # USD per 1K tokens
        self.cost_output = cost_output
    
    def calculate_monthly_cost(
        self,
        avg_input_tokens: int,
        avg_output_tokens: int,
        requests_per_day: int,
        days_per_month: int = 30,
        error_rate: float = 0.05,  # 5% de requests fallan y se repiten
        context_window_usage: float = 0.7  # % del context window que usamos
    ) -> dict:
        """
        Calcula el costo mensual real.
        
        Returns:
            Dict con desglose de costos
        """
        requests_monthly = requests_per_day * days_per_month
        
        # Tokens mensuales
        tokens_input_monthly = avg_input_tokens * requests_monthly
        tokens_output_monthly = avg_output_tokens * requests_monthly
        
        # Costo base (sin retries)
        cost_base_input = (tokens_input_monthly / 1000) * self.cost_input
        cost_base_output = (tokens_output_monthly / 1000) * self.cost_output
        
        # Costo con retries
        retry_multiplier = 1 / (1 - error_rate)
        cost_with_retries = (cost_base_input + cost_base_output) * retry_multiplier
        
        # Costo de latencia (si es tiempo real, el usuario espera)
        # Asumiendo $0.0001 por segundo de compute
        avg_latency_seconds = 2.5  # Estimado para modelo
        latency_cost = requests_monthly * avg_latency_seconds * 0.0001
        
        # Total
        total = cost_with_retries + latency_cost
        
        return {
            "model": self.model,
            "requests_monthly": requests_monthly,
            "tokens_input_monthly": tokens_input_monthly,
            "tokens_output_monthly": tokens_output_monthly,
            "cost_base": cost_base_input + cost_base_output,
            "cost_with_retries": cost_with_retries,
            "latency_cost": latency_cost,
            "total_monthly": total,
            "total_yearly": total * 12
        }
    
    def compare_models(self, models: list, **kwargs) -> list:
        """Compara costos de múltiples modelos."""
        results = []
        for m in models:
            calc = LLMCostCalculator(m["model"], m["cost_input"], m["cost_output"])
            result = calc.calculate_monthly_cost(**kwargs)
            results.append(result)
        
        # Ordenar por costo total
        results.sort(key=lambda x: x["total_monthly"])
        return results

Pilar 3: Latencia — Cuándo Cada Ms Cuenta

Para chatbots en tiempo real, la latencia es crítica. Para batch processing, no tanto:

$$\bar{L} = \frac{1}{N} \sum_{i=1}^{N} L_i$$

donde $L_i$ es la latencia del request $i$, y queremos $\bar{L} < L_{threshold}$.

Pilar 4: Open vs. Closed — No Es Blanco y Negro

La decisión open vs. closed depende de tu contexto:

  • Open (Llama, Mistral, Falcon): Control total, costo fijo (servidores propios), privacy completa, pero requiere MLOps
  • Closed (GPT-4, Claude, Gemini): Plug & play, actualizado constantemente, pero vendor lock-in y costs impredecibles
  • Hybrid (Fine-tuned open + closed): El mejor de ambos mundos para producción seria

⚠️ Los 3 Errores Que El 80% Comete

Error 1: No Tener Criterios de Selección — La muerte del proyecto

El problema: Usar "porque sí" o "porque todos usan GPT-4". No hay métricas, no hay data, no hay forma de mejorar.

La solución: Implementar el framework de arriba. Sin excusas. Define tus pesos, evalúa al menos 3 modelos, mide.

# Checklist de Selección — Ejécútalo antes de elegir

Error 2: Elegir Basado Solo en Benchmarks — El error del técnico

El problema: "GPT-4 tiene 90 en MMLU, luego es el mejor". No. benchmarks ≠ tu caso de uso.

La solución: Evaluar en tu dominio específico con datos reales. El benchmark es un proxy, no la verdad.

Error 3: No Considerar la Relación Costo-Calidad — El drenaje silencioso

El problema: Usar el modelo más capaz para todo, aunque uno más barato haría el trabajo igual de bien. El costo se come las margins.

La solución: Implementar routing inteligente — tareas simples con modelos baratos, tareas complejas con modelos capaces.

"""
Smart LLM Router — Usa el modelo correcto para cada tarea
============================================================
No todos los requests necesitan GPT-4. 
La mayoría (60-80%) se resuelven con modelos pequeños.
"""

class LLMRouter:
    """
    Router inteligente que directing tasks al modelo óptimo
    basado en complejidad de la query.
    """
    
    def __init__(self):
        self.tier_1 = {  # Alta complejidad
            "model": "gpt-4o",
            "cost": 0.02,  # per 1K tokens total
            "use_cases": ["análisis complejo", "código avanzado", "razonamiento multi-step"]
        }
        self.tier_2 = {  # Mediana complejidad
            "model": "claude-3-5-sonnet",
            "cost": 0.012,
            "use_cases": ["chat general", "resúmenes", "escritura"]
        }
        self.tier_3 = {  # Baja complejidad
            "model": "llama-3.1-8b-instruct",
            "cost": 0.001,
            "use_cases": ["clasificación simple", "extracción básica", "formateo"]
        }
    
    def classify_complexity(self, query: str) -> str:
        """
        Clasifica la complejidad de una query.
        
        Returns: "tier_1", "tier_2", o "tier_3"
        """
        # Señales de baja complejidad
        low_complexity_signals = [
            len(query) < 50,  # Query muy corta
            query.startswith("¿Cuándo"),  # Pregunta factual simple
            "¿Cuál es" in query,
            "Clasifica" in query.lower() and len(query) < 100,
        ]
        
        # Señales de alta complejidad
        high_complexity_signals = [
            "analiza" in query.lower(),
            "compara y contrasta" in query.lower(),
            "explica paso a paso" in query.lower(),
            "escribe código" in query.lower() and "debug" in query.lower(),
            len(query) > 1000,
        ]
        
        if any(high_complexity_signals):
            return "tier_1"
        elif any(low_complexity_signals):
            return "tier_3"
        else:
            return "tier_2"
    
    def route(self, query: str) -> dict:
        """Routea la query al modelo óptimo."""
        tier = self.classify_complexity(query)
        config = getattr(self, tier)
        
        return {
            "model": config["model"],
            "tier": tier,
            "estimated_cost": config["cost"],
            "reasoning": f"Query clasificada como {tier} complejidad"
        }


# === Ejemplo de Savings ===

if __name__ == "__main__":
    router = LLMRouter()
    
    queries = [
        "¿Qué es photosynthesis?",  # tier_3
        "Explica qué es la fotosíntesis y cómo afecta el cambio climático",  # tier_2
        "Analiza el impacto del cambio climático en la agricultura latinoamericana y propone soluciones sostenible",  # tier_1
    ]
    
    print("📊 Routing de Queries:")
    for q in queries:
        result = router.route(q)
        print(f"\n  Query: {q[:50]}...")
        print(f"  → Model: {result['model']} (tier {result['tier']})")
        print(f"  → Costo estimado: ${result['estimated_cost']:.4f}")
    
    # Savings vs usar siempre GPT-4
    always_gpt4_cost = 0.02 * len(queries)
    routed_cost = sum(router.route(q)['estimated_cost'] for q in queries)
    savings = always_gpt4_cost - routed_cost
    print(f"\n💰 Savings vs usar siempre GPT-4: {savings/always_gpt4_cost*100:.0f}%")

📊 Resumen y Cierre

Hoy aprendimos que elegir un LLM no es cuestión de moda o intuición — es una decisión ingeniería con criterios medibles:

  • 🎯 Quality: Evalúa en TU dominio, no en benchmarks genéricos
  • 💰 Cost: Calcula el costo real incluyendo retries y latencia
  • ⏱️ Latency: Define si importa para tu caso de uso
  • 🔓 Open vs Closed: No es ideology, es pragmatismo

Y los 3 errores a evitar:

  1. No tener criterios → Framework de selección documentado
  2. Elegir por benchmarks → Evaluar en dominio específico
  3. Ignorar costo-calidad → Implementar routing inteligente
