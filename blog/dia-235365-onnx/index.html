Introduccion: Cuando tu modelo de PyTorch se niega a vivir en produccion

Mira, te voy a contar una cicatriz real. En 2022 un equipo de vision computacional con el que trabajaba entrenaba en PyTorch sobre GPUs A100 en un cluster interno. El modelo daba metrics brutales en validacion: 0.94 de F1, latencia de inference decente, todo parecia listo. El problema empezo cuando quisimos deployarlo. El equipo de plataforma tenia un stack TensorFlow Serving sobre Kubernetes, porque "asi lo hacemos siempre". Reescribir el modelo a TensorFlow no era trivial: teniamos operaciones custom, atencion multi-cabeza con shapes dinamicas y normalizacion no estandar. Empezamos a reimplementar y la accuracy cayo 3 puntos. Una pesadilla que duro seis semanas.

Esa vaina es exactamente el problema que ONNX vino a resolver, y por eso existe ONNX Runtime como motor de inferencia optimizado. Pero no voy a venderte humo: ONNX no es bala de plata, y si no entiendes como funciona el formato y el runtime, te va a morder igual. En este articulo te voy a mostrar la matematica del grafo computacional, las optimizaciones que ONNX Runtime aplica, codigo production-grade para exportar, validar y servir modelos, y los tres problemas mas comunes que te van a explotar en la cara cuando deployes.

Lo que viene no es un tutorial generico. Es lo que desearia haber leido hace tres anos antes de pelearme con un opset version mismatch a las 3am de un viernes.

1. Que es ONNX? (Y por que deberia importarte)

1.1 La analogia cotidiana

ONNX es al machine learning lo que el contenedor ISO maritime es al transporte de carga global. Antes de que existieran los contenedores estandarizados en los anos 50, cargar un barco era un infierno: cada producto venia en su propio empaque, los estibadores tenian que mover cajas individuales de formas y tamanos caprichosos, y el tiempo de carga en puerto era brutalmente caro. Malcolm McLean, fundador de la compania de camiones que se convirtio en SeaLand, propuso un contenedor de dimensiones fijas que cualquier grua del mundo pudiera levantar, cualquier barco pudiera acomodar y cualquier puerto pudiera manejar. La industria del transporte no se transformo porque los barcos fueran mas grandes, sino porque el contenedor era universal.

ONNX hace exactamente eso con los modelos de ML. Tu modelo es el "contenido": puede haber sido entrenado en PyTorch, TensorFlow, JAX, scikit-learn, Keras o MXNet. ONNX es el "contenedor estandar" con dimensiones fijas: un grafo computacional, operadores versionados (el opset), tipos de datos especificos y metadata serializada en protobuf. ONNX Runtime es la "grua" optimizada que levanta ese contenedor en cualquier puerto: CPU x86, CPU ARM, GPU NVIDIA, GPU AMD, NPU, dispositivos edge, navegadores con WebGPU.

La diferencia brutal: sin ONNX, cada vez que cambias de framework o de hardware target, reescribes. Con ONNX, exportas una vez y deployas donde quieras.

1.2 La matematica formal

ONNX define un modelo como un grafo computacional dirigido aciclico (DAG):

$$G = (V, E, I, O)$$

donde $V$ es el conjunto de nodos (operadores del opset), $E \subseteq V \times V$ son las aristas definidas implicitamente por los nombres de tensores que conectan outputs de un nodo con inputs del siguiente, $I$ es el conjunto de inputs del grafo y $O$ el conjunto de outputs.

Cada nodo $v \in V$ es una tupla de cuatro elementos:

$$v = (\text{op\_type}, \text{inputs}, \text{outputs}, \text{attributes})$$

donde op_type es un string que identifica la operacion segun el opset (por ejemplo Conv, Relu, MatMul, Softmax), inputs y outputs son listas de nombres de tensores, y attributes son parametros fijos del operador (por ejemplo kernel_shape para una convolucion, o axis para una reduccion). Lo clave: cada operador tiene una especificacion matematica formal en el repositorio de ONNX, lo que elimina ambiguedades entre frameworks.

La inferencia es el forward pass sobre este grafo. Si $x_0$ es el tensor de entrada, la salida se calcula como composicion de operadores:

$$y = f_L \circ f_{L-1} \circ \cdots \circ f_1(x_0)$$

donde cada $f_i$ es la funcion matematica que implementa el nodo $i$ segun la especificacion del opset. Por ejemplo, una capa Conv 2D implementa:

$$\text{Conv}(X, W, b)_{i,j,k} = \sum_{m,n} X_{i,j+m,k+n} \cdot W_{m,n,k} + b_k$$

y una Relu:

$$\text{Relu}(x) = \max(0, x)$$

Los pesos del modelo se almacenan como inicializadores del grafo, tensores constantes embebidos en el archivo .onnx. Cuando exportas un modelo de PyTorch a ONNX, los parametros entrenables ($W$, $b$, etc.) se serializan como initializers que quedan fijos en el grafo y separados de los inputs variables en runtime.

2. Como ONNX Runtime resuelve esto por vos

ONNX Runtime es el motor de inferencia optimizado que ejecuta modelos ONNX. El flujo interno, simplificado, es:

+---------------------------+
| Archivo .onnx (protobuf)  |
+---------------------------+
            |
            v
+---------------------------+
| Parser + Validador        |  <- verifica opset, tipos, shapes
+---------------------------+
            |
            v
+---------------------------+
| Graph Optimizer           |  <- constant folding, operator fusion
+---------------------------+
            |
            v
+---------------------------+
| Partitioner               |  <- divide el grafo en subgrafos
+---------------------------+
            |
   +--------+--------+
   |                 |
   v                 v
+--------+    +------------+
| CPU EP |    | CUDA EP    |  <- Execution Providers
+--------+    +------------+

Lo importante aqui son los Execution Providers (EPs): ONNX Runtime no ejecuta todo el modelo en un solo backend. Internamente parte el grafo en subgrafos que pueden correr en diferentes hardwares. Por ejemplo, una capa Reshape se queda en CPU pero una Conv se mueve a CUDA. Los EPs disponibles incluyen CPUExecutionProvider, CUDAExecutionProvider, TensorrtExecutionProvider, DmlExecutionProvider (DirectML para Windows), CoreMLExecutionProvider y NNAPIExecutionProvider para Android.

Las optimizaciones de grafo son donde ONNX Runtime ahorra latencia real. Tres son las mas importantes:

  1. Constant folding: si un operador tiene como input un initializer constante, se calcula en tiempo de carga y se reemplaza por su resultado. Por ejemplo, Sub(x, Constant) donde Constant = 3.0 se precomputa como un nuevo initializer Constant' = -3.0 y un Add (mas barato que un Sub).
  1. Operator fusion: operaciones consecutivas se fusionan en una sola. El caso clasico es Conv + BatchNormalization + Relu, que en frameworks eager se ejecutan como tres kernels separados con sus respectivas lecturas y escrituras a memoria. ONNX Runtime las fusiona en un solo kernel FusedConvBNRelu que mantiene los datos en registros. Lo mismo pasa con MatMul + Add fusionado a FusedMatMul, y Gemm + Relu.
  1. Layout optimization: tensores en formato NCHW (PyTorch) se transforman a NHWC (preferido por TensorRT/CUDA) cuando hay suficientes operaciones que se benefician. Esto es transparente para el usuario.

Hay cuatro niveles de optimizacion configurables, ordenados por agresividad: ORT_DISABLE_ALL, ORT_ENABLE_BASIC, ORT_ENABLE_EXTENDED (incluye complex node fusion como FusedConv y FusedMatMul) y ORT_ENABLE_ALL (lo anterior + layout optimization NCHW a NHWC).

En produccion, casi siempre queres ORT_ENABLE_ALL, con una salvedad importante: layout optimization puede introducir cambios sutiles en el orden de operaciones de reduccion. Si tu validacion downstream es sensible a eso, quedate en ORT_ENABLE_EXTENDED.

3. ONNX: Uso Directo y Casos de Control Fino

La libreria onnx te permite inspeccionar y manipular modelos a nivel de grafo. Esto es util para debugging, validacion y transformaciones custom que el exportador automatico no cubre.

# inspeccion_basica.py
import onnx
from onnx import numpy_helper

model = onnx.load("modelo.onnx")

# 1. Verificar que el modelo esta bien formado
onnx.checker.check_model(model)

# 2. Metadata del modelo
print(f"Producer: {model.producer_name} {model.producer_version}")
print(f"Ir version: {model.ir_version}")
print(f"Opset imports: {[(op.domain, op.version) for op in model.opset_import]}")

# 3. Inputs y outputs
for input_tensor in model.graph.input:
    shape = [d.dim_value if d.dim_value > 0 else d.dim_param
             for d in input_tensor.type.tensor_type.shape.dim]
    dtype = input_tensor.type.tensor_type.elem_type
    print(f"Input '{input_tensor.name}': shape={shape}, dtype={dtype}")

for output_tensor in model.graph.output:
    shape = [d.dim_value if d.dim_value > 0 else d.dim_param
             for d in output_tensor.type.tensor_type.shape.dim]
    dtype = output_tensor.type.tensor_type.elem_type
    print(f"Output '{output_tensor.name}': shape={shape}, dtype={dtype}")

# 4. Inicializadores (pesos)
print(f"\nTotal inicializadores: {len(model.graph.initializer)}")
total_params = 0
for init in model.graph.initializer:
    arr = numpy_helper.to_array(init)
    total_params += arr.size
    print(f"  {init.name}: shape={arr.shape}, dtype={arr.dtype}")

4.1 Tipos y protocolos

# tipos.py
from dataclasses import dataclass
from enum import Enum
import numpy as np

class DTypeONNX(Enum):
    """Mapeo de dtypes ONNX (TensorProto) a numpy."""
    FLOAT = 1
    UINT8 = 2
    INT8 = 3
    UINT16 = 4
    INT16 = 5
    INT32 = 6
    INT64 = 7
    STRING = 8
    BOOL = 9
    FLOAT16 = 10
    DOUBLE = 11
    UINT32 = 12
    UINT64 = 13

    def to_numpy(self) -> np.dtype:
        mapping = {
            1: np.float32, 2: np.uint8, 3: np.int8,
            4: np.uint16, 5: np.int16, 6: np.int32, 7: np.int64,
            8: np.object_, 9: np.bool_, 10: np.float16, 11: np.float64,
            12: np.uint32, 13: np.uint64,
        }
        return mapping[self.value]

@dataclass(frozen=True)
class TensorSpec:
    name: str
    shape: tuple
    dtype: np.dtype

@dataclass
class InferenceRequest:
    inputs: dict[str, np.ndarray]
    request_id: str

@dataclass
class InferenceResponse:
    outputs: dict[str, np.ndarray]
    request_id: str
    latency_ms: float

4.2 El motor principal

# motor.py
import logging
import time
from pathlib import Path

import numpy as np
import onnx
import onnxruntime as ort
from onnxruntime import SessionOptions, GraphOptimizationLevel

from tipos import InferenceRequest, InferenceResponse, TensorSpec, DTypeONNX

logger = logging.getLogger(__name__)


class ONNXInferenceEngine:
    def __init__(
        self,
        model_path: str | Path,
        providers: list[str] | None = None,
        intra_op_threads: int = 0,
        inter_op_threads: int = 0,
        graph_opt_level: GraphOptimizationLevel = (
            GraphOptimizationLevel.ORT_ENABLE_ALL
        ),
    ):
        self._model_path = Path(model_path)
        self._validate_model_file()

        self._sess_options = SessionOptions()
        self._sess_options.graph_optimization_level = graph_opt_level
        self._sess_options.intra_op_num_threads = intra_op_threads
        self._sess_options.inter_op_num_threads = inter_op_threads
        self._sess_options.execution_mode = ort.ExecutionMode.ORT_SEQUENTIAL

        if providers is None:
            providers = self._detect_providers()

        logger.info(
            f"Cargando modelo {self._model_path} "
            f"con providers={providers}"
        )
        self._session = ort.InferenceSession(
            str(self._model_path),
            sess_options=self._sess_options,
            providers=providers,
        )
        self._input_specs = self._extract_input_specs()
        self._output_specs = self._extract_output_specs()

    def _validate_model_file(self) -> None:
        if not self._model_path.exists():
            raise FileNotFoundError(
                f"Modelo no encontrado: {self._model_path}"
            )
        if self._model_path.stat().st_size == 0:
            raise ValueError(
                f"Archivo de modelo vacio: {self._model_path}"
            )
        try:
            onnx.checker.check_model(str(self._model_path))
            logger.debug("Modelo paso onnx.checker")
        except onnx.checker.ValidationError as e:
            logger.warning(f"Modelo no paso onnx.checker: {e}")

    @staticmethod
    def _detect_providers() -> list[str]:
        available = ort.get_available_providers()
        if "CUDAExecutionProvider" in available:
            return ["CUDAExecutionProvider", "CPUExecutionProvider"]
        if "CoreMLExecutionProvider" in available:
            return ["CoreMLExecutionProvider", "CPUExecutionProvider"]
        return ["CPUExecutionProvider"]

    def _extract_input_specs(self) -> list[TensorSpec]:
        specs = []
        for inp in self._session.get_inputs():
            shape = tuple(
                d if isinstance(d, int) else -1
                for d in inp.shape
            )
            dtype = DTypeONNX(inp.type).to_numpy()
            specs.append(
                TensorSpec(name=inp.name, shape=shape, dtype=dtype)
            )
        return specs

    def _extract_output_specs(self) -> list[TensorSpec]:
        specs = []
        for out in self._session.get_outputs():
            shape = tuple(
                d if isinstance(d, int) else -1
                for d in out.shape
            )
            dtype = DTypeONNX(out.type).to_numpy()
            specs.append(
                TensorSpec(name=out.name, shape=shape, dtype=dtype)
            )
        return specs

    def run(self, request: InferenceRequest) -> InferenceResponse:
        for spec in self._input_specs:
            if spec.name not in request.inputs:
                raise KeyError(
                    f"Falta input requerido: {spec.name}"
                )
            arr = request.inputs[spec.name]
            if arr.dtype != spec.dtype:
                raise TypeError(
                    f"dtype incorrecto para {spec.name}: "
                    f"esperado {spec.dtype}, recibio {arr.dtype}"
                )

        start = time.perf_counter()
        outputs = self._session.run(None, request.inputs)
        latency_ms = (time.perf_counter() - start) * 1000.0

        output_dict = {
            spec.name: arr
            for spec, arr in zip(self._output_specs, outputs)
        }
        return InferenceResponse(
            outputs=output_dict,
            request_id=request.request_id,
            latency_ms=latency_ms,
        )

    @property
    def input_specs(self) -> list[TensorSpec]:
        return self._input_specs

    @property
    def output_specs(self) -> list[TensorSpec]:
        return self._output_specs

    def warmup(self, n_iterations: int = 3) -> None:
        """Primera inference siempre es lenta por lazy init y caching."""
        dummy_inputs = {}
        for spec in self._input_specs:
            shape = tuple(s if s != -1 else 1 for s in spec.shape)
            dummy_inputs[spec.name] = np.random.randn(
                *shape
            ).astype(spec.dtype)
        dummy_request = InferenceRequest(
            inputs=dummy_inputs,
            request_id="warmup",
        )
        for _ in range(n_iterations):
            self.run(dummy_request)
        logger.info(f"Warmup completado ({n_iterations} iteraciones)")

4.3 Utilidades de analisis y verificacion

# verificacion.py
import numpy as np
import onnx
import onnxruntime as ort


def verificar_equivalencia_numerica(
    modelo_onnx_path: str,
    framework_predict_fn,
    inputs_test: dict[str, np.ndarray],
    rtol: float = 1e-5,
    atol: float = 1e-5,
) -> dict:
    """Compara outputs de ONNX Runtime vs el framework original."""
    sess = ort.InferenceSession(modelo_onnx_path)
    onnx_outputs = sess.run(None, inputs_test)
    onnx_output_names = [o.name for o in sess.get_outputs()]

    framework_outputs = framework_predict_fn(inputs_test)
    if not isinstance(framework_outputs, dict):
        framework_outputs = {onnx_output_names[0]: framework_outputs}

    resultados = {}
    max_abs_diff = 0.0
    max_rel_diff = 0.0
    for name, onnx_arr in zip(onnx_output_names, onnx_outputs):
        fw_arr = framework_outputs[name]
        abs_diff = float(np.max(np.abs(onnx_arr - fw_arr)))
        denom = np.maximum(np.abs(fw_arr), 1e-10)
        rel_diff = float(np.max(np.abs(onnx_arr - fw_arr) / denom))
        max_abs_diff = max(max_abs_diff, abs_diff)
        max_rel_diff = max(max_rel_diff, rel_diff)
        es_equivalente = bool(
            np.allclose(onnx_arr, fw_arr, rtol=rtol, atol=atol)
        )
        resultados[name] = {
            "max_abs_diff": abs_diff,
            "max_rel_diff": rel_diff,
            "equivalente": es_equivalente,
        }
    resultados["_resumen"] = {
        "max_abs_diff_global": max_abs_diff,
        "max_rel_diff_global": max_rel_diff,
        "todos_equivalentes": all(
            r["equivalente"] for r in resultados.values()
        ),
    }
    return resultados


def analizar_complejidad_grafo(modelo_onnx_path: str) -> dict:
    """Cuenta operadores y volumen de parametros del modelo."""
    model = onnx.load(modelo_onnx_path)
    ops_counter: dict[str, int] = {}
    for node in model.graph.node:
        ops_counter[node.op_type] = (
            ops_counter.get(node.op_type, 0) + 1
        )

    total_params = 0
    for init in model.graph.initializer:
        from onnx import numpy_helper
        arr = numpy_helper.to_array(init)
        total_params += arr.size

    return {
        "total_nodos": len(model.graph.node),
        "total_inicializadores": len(model.graph.initializer),
        "total_parametros": total_params,
        "conteo_operadores": dict(
            sorted(ops_counter.items(), key=lambda kv: -kv[1])
        ),
        "opsets": [
            (op.domain, op.version) for op in model.opset_import
        ],
    }

# exportacion_pytorch.py
import torch
import torch.nn as nn
import numpy as np


class ModeloClasificador(nn.Module):
    def __init__(self, num_classes: int = 10):
        super().__init__()
        self.features = nn.Sequential(
            nn.Conv2d(3, 32, kernel_size=3, padding=1),
            nn.BatchNorm2d(32),
            nn.ReLU(inplace=True),
            nn.MaxPool2d(2),
            nn.Conv2d(32, 64, kernel_size=3, padding=1),
            nn.BatchNorm2d(64),
            nn.ReLU(inplace=True),
            nn.AdaptiveAvgPool2d(1),
        )
        self.classifier = nn.Linear(64, num_classes)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        x = self.features(x)
        x = x.flatten(1)
        return self.classifier(x)


model = ModeloClasificador().eval()
dummy_input = torch.randn(1, 3, 224, 224)

torch.onnx.export(
    model,
    (dummy_input,),
    "clasificador.onnx",
    input_names=["imagen"],
    output_names=["logits"],
    # CRITICO: opset >= 13 para soportar shapes dinamicas correctamente
    opset_version=17,
    dynamic_axes={
        "imagen": {0: "batch_size"},
        "logits": {0: "batch_size"},
    },
    do_constant_folding=True,
    training=torch.onnx.TrainingMode.EVAL,
)


def predict_pytorch(inputs: dict) -> dict:
    with torch.no_grad():
        tensor = torch.from_numpy(inputs["imagen"]).float()
        out = model(tensor).numpy()
    return {"logits": out}


# Verificacion numerica: con batch=1 y batch=8 el error debe ser ~1e-6
from verificacion import verificar_equivalencia_numerica

for bs in [1, 8]:
    test_input = np.random.randn(bs, 3, 224, 224).astype(np.float32)
    resultado = verificar_equivalencia_numerica(
        "clasificador.onnx",
        predict_pytorch,
        {"imagen": test_input},
        rtol=1e-5,
        atol=1e-5,
    )
    print(f"batch={bs}: {resultado['_resumen']}")
# Esperado: max_abs_diff < 1e-5 para ambos batches

Caso 2: Cuantizacion estatica para deployment en CPU edge

# cuantizacion_estatica.py
import numpy as np
import onnxruntime as ort
from onnxruntime.quantization import (
    quantize_static,
    CalibrationDataReader,
    QuantType,
    CalibrationMethod,
)


class LectorCalibracion(CalibrationDataReader):
    """Provee batches representativos para calibrar la cuantizacion."""

    def __init__(
        self,
        num_samples: int = 200,
        shape: tuple = (1, 3, 224, 224),
        seed: int = 42,
    ):
        rng = np.random.default_rng(seed)
        self._data = rng.standard_normal(
            (num_samples, *shape), dtype=np.float32
        )
        self._index = 0
        self._num_samples = num_samples

    def get_next(self):
        if self._index >= self._num_samples:
            return None
        sample = {"imagen": self._data[self._index:self._index + 1]}
        self._index += 1
        return sample

    def rewind(self):
        self._index = 0


quantize_static(
    model_input="clasificador.onnx",
    model_output="clasificador_int8.onnx",
    calibration_data_reader=LectorCalibracion(num_samples=200),
    quant_format=QuantType.QDQ,
    per_channel=True,
    weight_type=QuantType.QInt8,
    activation_type=QuantType.QUInt8,
    calibrate_method=CalibrationMethod.MinMax,
    extra_options={
        "ActivationSymmetric": False,
        "WeightSymmetric": True,
    },
)

# Verificar degradacion: esperado max_abs_diff ~0.02-0.08 para INT8
def predict_int8(inputs: dict) -> dict:
    sess_int8 = ort.InferenceSession("clasificador_int8.onnx")
    out = sess_int8.run(None, inputs)[0]
    return {sess_int8.get_outputs()[0].name: out}


resultado_cuantizado = verificar_equivalencia_numerica(
    "clasificador_int8.onnx",
    predict_pytorch,
    {"imagen": np.random.randn(1, 3, 224, 224).astype(np.float32)},
    rtol=0.1,
    atol=0.1,
)
print(f"Degradacion post-cuantizacion: {resultado_cuantizado}")

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: Opset incompatible

Sintoma: onnxruntime.capi.onnxruntime_pybind11_state.Fail: [ONNXRuntimeError] : 1 : FAIL : Load model from modelo.onnx failed:This is an invalid model. Error in Node(...) : Op(Sqrt) [Op type: Sqrt] is not implemented in CPUExecutionProvider.

Causa: Tu modelo usa operadores de un opset reciente que tu version de ONNX Runtime no soporta, o un operador custom que no esta registrado.

Deteccion:

import onnx
import onnxruntime as ort

model = onnx.load("modelo.onnx")
opsets_usados = sorted({node.op_type for node in model.graph.node})
print(f"Operadores usados: {opsets_usados}")
print(f"Version ORT: {ort.__version__}")
print(
    f"Opset imports: "
    f"{[(o.domain, o.version) for o in model.opset_import]}"
)

Soluciones:

  1. Actualizar onnxruntime: pip install --upgrade onnxruntime (o onnxruntime-gpu si usas CUDA).
  2. Bajar el opset al exportar: torch.onnx.export(..., opset_version=13).
  3. Si necesitas operadores custom, registrarlos via onnxruntime.register_custom_ops_module(...) o reimplementarlos en el grafo con operadores primitivos.

Problema 2: Outputs NaN o Inf despues de exportar

Sintoma: El modelo PyTorch da outputs razonables, pero ONNX Runtime devuelve nan o inf.

Causa: Casi siempre es divergencia numerica entre frameworks. Las causas mas comunes son operaciones en float16 sin cuidado de overflow, logits muy grandes antes de softmax, o division por cero en normalizacion cuando los inicializadores tienen valores extremos.

Deteccion:

import numpy as np
import onnxruntime as ort

resultado = ort.InferenceSession("modelo.onnx").run(
    None, {"imagen": np.random.randn(1, 3, 224, 224).astype(np.float32)}
)
print(f"NaN count: {np.isnan(resultado[0]).sum()}")
print(f"Inf count: {np.isinf(resultado[0]).sum()}")
print(f"Min: {resultado[0].min()}, Max: {resultado[0].max()}")

Soluciones:

  1. Forzar opset_version=17+ y desactivar do_constant_folding=False para debug.
  2. Comparar outputs nodo por nodo agregando todos los outputs intermedios:
import onnx
model = onnx.load("modelo.onnx")
for node in model.graph.node:
    for output in node.output:
        model.graph.output.append(
            onnx.helper.make_tensor_value_info(
                output,
                onnx.TensorProto.FLOAT,
                [None],
            )
        )
onnx.save(model, "modelo_con_intermedios.onnx")
  1. Usar float32 explicito en operaciones sensibles, no float16 sin mixed precision.

Problema 3: Shape mismatch en runtime

Sintoma: Got input dimensions [1, 3, 224, 224] but the node expects [N, 3, 224, 224] compatible dimensions.

Causa: Cuando exportas con shapes estaticas y luego mandas un batch diferente al que esperabas.

Soluciones:

  1. Re-exportar con dynamic_axes={"imagen": {0: "batch_size"}}.
  2. Verificar que el modelo realmente acepta la dimension variable:
import onnxruntime as ort
sess = ort.InferenceSession("modelo.onnx")
for inp in sess.get_inputs():
    print(f"{inp.name}: {inp.shape}")  # Debe tener -1 en la dim variable

7. Optimizaciones de Produccion

Optimizacion 1: Seleccion del nivel de optimizacion segun el caso

# optimizacion_niveles.py
import time
import numpy as np
import onnxruntime as ort
from onnxruntime import SessionOptions, GraphOptimizationLevel


def benchmark_niveles(
    modelo_path: str,
    input_name: str,
    input_shape: tuple,
    n_runs: int = 50,
) -> dict[str, float]:
    """Mide latencia en cada nivel de optimizacion."""
    dummy_input = np.random.randn(*input_shape).astype(np.float32)
    resultados = {}

    for nivel in [
        GraphOptimizationLevel.ORT_DISABLE_ALL,
        GraphOptimizationLevel.ORT_ENABLE_BASIC,
        GraphOptimizationLevel.ORT_ENABLE_EXTENDED,
        GraphOptimizationLevel.ORT_ENABLE_ALL,
    ]:
        opts = SessionOptions()
        opts.graph_optimization_level = nivel
        sess = ort.InferenceSession(
            modelo_path,
            sess_options=opts,
            providers=["CPUExecutionProvider"],
        )
        # Warmup
        for _ in range(5):
            sess.run(None, {input_name: dummy_input})
        # Benchmark
        start = time.perf_counter()
        for _ in range(n_runs):
            sess.run(None, {input_name: dummy_input})
        elapsed = (time.perf_counter() - start) / n_runs * 1000
        resultados[nivel.name] = elapsed
    return resultados


# Trade-off real:
# - ORT_ENABLE_ALL: maxima latencia minima, pero puede romper equivalencia
#   numerica en modelos con operadores Reduce* o normalizaciones raras.
# - ORT_ENABLE_EXTENDED: ~95% del beneficio de ALL sin los riesgos de layout.
# Recomendacion: medir contra un golden set antes de cambiar ALL en prod.

Optimizacion 2: Threading tuning para CPU

El numero optimo de threads depende del workload: CPU-bound (matmul grande) o memory-bound (element-wise). ONNX Runtime por default usa todos los cores disponibles, lo cual casi siempre es suboptimo para inferencia con batch pequeno.

# threading.py
import os
import onnxruntime as ort

# Reglas practicas:
# - batch pequeno (1-4):  intra_op_num_threads = num_cores_fisicos (no logicos)
# - batch grande (32+):   intra_op_num_threads = num_cores_logicos / 2
# - inter_op_num_threads: 0 (auto) para inferencia simple, 1 si no hay
#   paralelismo entre requests del mismo grafo.

opts = ort.SessionOptions()
opts.intra_op_num_threads = max(1, os.cpu_count() // 2)
opts.inter_op_num_threads = 1

Si sirves multiples requests concurrentes, considera un proceso por worker y deja que el OS schedule los cores, en lugar de tener un proceso con muchos threads peleando por el mismo CPU. La contencion entre threads en inference batch pequena suele ser peor que el overhead de tener procesos separados.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

ONNX no es glamour. No es el transformer nuevo que sale cada tres meses. Es infraestructura, y la infraestructura es lo que determina si tu modelo vive o muere en produccion. Te resumo lo que importa:

  • Portabilidad real: exportas una vez, deployas en CPU x86, ARM, GPU, edge, navegador. Sin ONNX, cada target es un proyecto aparte.
  • Latencia predecible: ONNX Runtime aplica operator fusion y graph optimization automaticamente. En benchmarks reales sobre CPU, modelos ResNet-50 van de unos 80ms (PyTorch eager) a unos 30ms (ORT_ENABLE_ALL).
  • Validacion built-in: onnx.checker te dice si el modelo esta bien formado antes de deployar. onnxruntime te dice si el modelo corre antes de gastar dinero en infraestructura.
  • Cuantizacion integrada: 4x compresion y 2-4x speedup en CPU con cuantizacion estatica INT8, sin reentrenar.
# checklist_ejecutable.py
# Correr antes de cada deploy a produccion.
from pathlib import Path
import onnx
import onnxruntime as ort
import numpy as np

CHECKS = []


def check(label: str, fn) -> None:
    try:
        fn()
        CHECKS.append((label, True, ""))
    except Exception as e:
        CHECKS.append((label, False, str(e)))


def main(model_path: str) -> None:
    model = onnx.load(model_path)

    def f1():
        onnx.checker.check_model(model)

    def f2():
        # Opset minimo 13
        ops = [v for d, v in model.opset_import if d == "" or d == "ai.onnx"]
        assert ops and max(ops) >= 13, f"Opset {ops} < 13"

    def f3():
        # Inputs con batch dinamico
        sess = ort.InferenceSession(model_path)
        for inp in sess.get_inputs():
            assert any(
                (isinstance(d, str) and d != "") or d == -1
                for d in inp.shape
            ), f"{inp.name} sin batch dinamico"

    def f4():
        # Warmup exitoso
        sess = ort.InferenceSession(model_path)
        for inp in sess.get_inputs():
            shape = tuple(1 if d in (-1, "") else d for d in inp.shape)
            x = np.random.randn(*shape).astype(np.float32)
            sess.run(None, {inp.name: x})

    check("onnx.checker", f1)
    check("opset >= 13", f2)
    check("batch dinamico", f3)
    check("warmup ok", f4)

    for label, ok, err in CHECKS:
        status = "OK" if ok else "FAIL"
        print(f"[{status}] {label}: {err}")
    if all(ok for _, ok, _ in CHECKS):
        print("Listo para produccion.")
    else:
        raise SystemExit(1)


if __name__ == "__main__":
    main("clasificador.onnx")

Checklist rapido antes de deployar un modelo ONNX:

  1. Exportar con opset_version >= 13 y dynamic_axes para batch.
  2. Validar con onnx.checker.check_model(modelo.onnx).
  3. Comparar outputs contra el framework original con np.allclose(rtol=1e-5).
  4. Medir latencia en ORT_ENABLE_ALL vs ORT_ENABLE_EXTENDED con tu data real.
  5. Si vas a cuantizar, calibrar con datos representativos del dominio, no random.
  6. Warmup antes de medir: la primera inferencia siempre es lenta por lazy init.
  7. Monitorear opset y version de onnxruntime en produccion: un upgrade puede romper ops custom.

Si llegaste hasta aca, ya sabes mas de ONNX que el 80% de los que lo usan a diario. De una, guardate este articulo en favoritos porque lo vas a necesitar cuando te toque deployar el proximo modelo.
