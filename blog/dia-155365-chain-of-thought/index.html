Dia 155/365: Chain-of-Thought — El electricista que diagnostica tu corto antes de cambiar el breaker

4 de junio de 2026
Prompt structure

Introduccion: El cliente quejandose y el electricista improvisado

Te llega el ticket: "no hay luz en la sala". Si le contestas al cliente "cambie el breaker" sin antes medir, eres el electricista que sale quemado y deja al cliente peor. Lo mismo pasa cuando le pides a un LLM que responda una pregunta compleja sin darle espacio para "medir" — sin una cadena de razonamiento intermedia. La primera vez que meti Chain-of-Thought (CoT) en un pipeline de Q&A sobre contratos legales, la precision salto del rango 60% al 83% en una sola tarde. Pero el costo de tokens casi se duplico y la latencia subio 1.8x. Esa es la trade-off real, no la del blog corporativo que te vende "razonamiento avanzado" como si fuera gratis.

Aca no vengo a venderte CoT como varita magica. Vengo a contarte cuando vale la pena pagar el costo, cuando no, y como implementarlo de forma que no te explote el presupuesto en produccion. Parce, si trabajas con LLMs y nunca te has quemado con un CoT mal calibrado, este articulo te va a ahorrar la cicatriz.

1. Que es Chain-of-Thought? (Y por que deberia importarte)

1.1 La analogia cotidiana

Imaginate un electricista que recibe una llamada: "se fue la luz". Un electricista improvisado llega, ve la oscuridad y empieza a cambiar cosas al azar — breaker primero, despues toma, despues cable. Pierde tiempo, cobra de mas, y a veces el problema era una conexion suelta de 5 minutos.

Un electricista serio hace otra cosa: llega, saca el multimetro, mide voltaje en el panel, luego en cada circuito, sigue el cable fisicamente hasta encontrar donde se interrumpio, documenta cada paso, y solo entonces repara. Ese "medir paso a paso" es Chain-of-Thought. No es que el electricista sea mas inteligente — es que el acto de medir de manera secuencial y explicita lo obliga a no saltar pasos, y cuando algo sale mal puede volver atras y revisar donde se equivoco.

En LLM, CoT es exactamente eso: en vez de saltar directo de input -> respuesta, forzamos al modelo a producir tokens intermedios de razonamiento (input -> razonamiento -> respuesta). Esos tokens intermedios no son decorativos: condicionan la generacion final. Cuando el modelo escribe "como X es par entonces Y", al momento de generar la respuesta final el contexto contiene esa conclusion intermedia, lo cual cambia la distribucion de probabilidad del siguiente token. Es memoria de trabajo scratchpad, no poesia.

1.2 La matematica formal

En generacion autoregresiva estandar, el modelo factoriza la probabilidad de una respuesta $y$ dado un input $x$ como:

$$p_\theta(y \mid x) = \prod_{t=1}^{|y|} p_\theta(y_t \mid x, y_{Donde $\theta$ son los parametros del modelo, $y_t$ es el token en la posicion $t$, e $y_{

Con Chain-of-Thought, introducimos una variable latente $z$ que representa la cadena de razonamiento:

$$p_\theta(y \mid x) = \sum_{z \in \mathcal{Z}} p_\theta(z \mid x) \cdot p_\theta(y \mid x, z)$$

O equivalentemente, marginalizando sobre la cadena:

$$p_\theta(y \mid x) = \mathbb{E}_{z \sim p_\theta(\cdot \mid x)} \big[ p_\theta(y \mid x, z) \big]$$

Donde $\mathcal{Z}$ es el espacio combinatorio de todas las cadenas de razonamiento posibles. El modelo primero muestrea una cadena $z$ condicionada al input, y luego condiciona la respuesta final sobre esa cadena. En la practica esto se implementa concatenando en el prompt: prompt(x) + cadena_z + respuesta_y, donde $z$ se genera antes que $y$ y queda como prefijo en el contexto.

La intuicion clave: para problemas multi-paso, la distribucion $p_\theta(y \mid x)$ tiene alta entropia (muchas respuestas plausibles compiten), pero $p_\theta(y \mid x, z)$ para una buena $z$ tiene entropia baja (la cadena colapsa la distribucion hacia una sola respuesta correcta). CoT funciona porque cambia la condicion — pasamos de un espacio de salida dificil a uno facil.

Para Self-Consistency (Wang et al., 2022), muestreamos $N$ cadenas independientes y votamos:

$$\hat{y} = \arg\max_{y} \sum_{k=1}^{N} \mathbb{1}[y^{(k)} = y]$$

Donde $y^{(k)}$ es la respuesta final extraida de la cadena $k$. La hipotesis es que cadenas diversas convergen en la respuesta correcta mas frecuentemente que en las incorrectas — una especie de wisdom of crowds dentro del mismo modelo.

2. Como CoT Cambia el Diseno de Sistemas

Cuando metes CoT en produccion, ya no estas escribiendo un prompt — estas diseniando un sistema de dos etapas acopladas. Eso impacta:

Costo y latencia: una cadena tipica de CoT agrega entre $3$ y $8$ veces el numero de tokens de la respuesta final. Si tu respuesta eran 50 tokens, ahora son 200-400 con la cadena. Self-Consistency con $N=5$ lo multiplica por 5 otra vez. Traduccion: si tu factura era $\$1,000$ al mes, ahora es $\$2,500 - \$5,000$. Y la latencia crece casi linealmente con tokens generados.

Parsing de la cadena: la respuesta que llega al usuario no es la cadena completa — es la conclusion final. Necesitas un parser robusto que separe la cadena del output. La forma naive (split("Respuesta final:")) se rompe cuando el modelo alucina formatos. La forma production-grade: structured output con JSON schema.

from pydantic import BaseModel, Field

class CoTResponse(BaseModel):
    reasoning: str = Field(..., description="Cadena de razonamiento paso a paso")
    answer: str = Field(..., description="Conclusion final entregada al usuario")
    confidence: float = Field(..., ge=0.0, le=1.0)

# El prompt fuerza al modelo a emitir JSON con esa estructura.
# El parser valida con Pydantic; falla ruidosamente si el JSON esta mal
# o si confidence esta fuera de rango, y el caller decide que hacer.

Observabilidad: si no logueas la cadena de razonamiento, no puedes hacer postmortem cuando algo sale mal. Necesitas trazabilidad: input, cadena generada, respuesta parseada, score de confianza, latencia por etapa. Langfuse, Helicone o Phoenix te dan eso out of the box.

Evaluacion: ya no evalúas solo accuracy de la respuesta final — evalúas la calidad de la cadena. Una cadena plausible pero incorrecta al final es peor que una respuesta directa incorrecta, porque genera confianza falsa. Metricas utiles: faithfulness de la cadena (los pasos se siguen unos a otros), groundedness (los pasos se anclan al input), y answer accuracy condicionada a cadena valida.

3. Patrones y Anti-Patrones

Patrones que funcionan:

  • Zero-shot CoT: agregar "Pensemos paso a paso" al final del prompt. Kojima et al. (2022) mostraron que esta sola frase desbloquea razonamiento en modelos grandes sin necesidad de ejemplos. Funciona mejor de lo que uno esperaria.
  • Few-shot CoT: incluir 3-5 ejemplos completos con su cadena de razonamiento en el prompt. Mas costoso en tokens de input pero usualmente mas robusto que zero-shot en tareas especializadas.
  • Self-Consistency: muestrear 5-7 cadenas con temperatura $0.7$ y votar. Mejora 5-10 puntos de accuracy tipicamente en problemas matematicos y logicos. Pero ojo: $5\times$ el costo.
  • Least-to-Most (Zhou et al., 2022): descomponer el problema en sub-problemas secuenciales donde la respuesta de uno alimenta al siguiente. Excelente para problemas composicionales.
  • ReAct (Yao et al., 2022): intercalar razonamiento con acciones sobre herramientas externas. Patron canonico de agentes. La cadena es Thought -> Action -> Observation -> Thought -> ....

Anti-patrones que te van a doler:

  • CoT en problemas de un solo paso: si la pregunta es "¿cual es la capital de Francia?", pedir CoT es desperdiciar 200 tokens en "la capital de Francia es una ciudad europea, tiene aproximadamente X millones de habitantes, su nombre en frances es... Paris." Tu latencia sube, tu costo sube, y el modelo no mejora nada porque no hay cadena que seguir.
  • Confiar en cadenas alucinadas: el modelo puede generar razonamiento que suena plausible pero no se sigue logicamente. Si no validas, el usuario recibe "porque A y B entonces C" donde A y B son inconsistentes. Validacion automatica o humana es obligatoria en dominios sensibles.
  • CoT con modelos debiles: modelos chicos (< 7B parametros tipicamente) no siguen cadenas de manera fiable — se pierden, repiten pasos, o generan razonamiento circular. CoT brilla en modelos de escala suficiente. Si tu modelo es chico, mejor few-shot directo.
  • Cadenas demasiado largas: si el modelo entra en bucle o verborrea, la cadena crece sin mejorar la respuesta. Ponele un max_tokens duro en la cadena y un timeout. Si llega al limite sin conclusion, descarta y reintenta con temperatura mas alta.
  • Forzar formato rigido sin flexibilidad: pedir "exactamente 5 pasos" o "cada paso en una linea" mata la naturalidad de la cadena. Mejor pedir estructura flexible con un parser tolerante.

4. Trade-offs en Produccion

La tabla que arme despues de varios meses ajustando un sistema de CoT en produccion:

Dimension Sin CoT Con CoT Self-Consistency (N=5)
Accuracy (GSM8K-like) ~0.60 ~0.84 ~0.91
Tokens de output 50 280 1400
Latencia p50 (streaming) 0.8s 2.1s 4.5s
Costo por 1k requests $\$1.00$ $\$4.50$ $\$22.50$
Tasa de cadenas sin conclusion 0% ~4% ~6%

Las decisiones reales que tome:

  1. CoT solo cuando la tarea es multi-paso verificable. Para extraccion de entidades o clasificacion, sin CoT. Para Q&A legal o matematico, CoT obligatorio.
  2. Self-Consistency solo cuando el costo de un error es muy alto. Por ejemplo: generacion de SQL para queries contra una base medica. Un SQL incorrecto tiene costo humano alto. Ahi pago los $\$22.50$ por 1k requests feliz.
  3. Streaming siempre. Si la cadena tarda 4 segundos, el usuario necesita ver progreso. Sin streaming, la percepcion de latencia es 3x peor.
  4. Cache de cadenas para queries repetidas. Si el 30% de tus queries son variaciones de las mismas preguntas, cachea la cadena. Hit rate del 25% reduce el costo real a la mitad.
  5. Fallback graceful. Si el parser falla o la cadena llega sin conclusion, cae a respuesta directa sin CoT. Mejor respuesta degradada que 500 error.

5. Casos de Uso Reales

Caso 1 — Q&A legal sobre contratos (mi produccion): pipeline que recibe clausulas de contratos comerciales y responde "¿esta clausula permite terminacion unilateral sin penalidad?". Sin CoT estabamos alrededor de 0.60-0.65 de accuracy. Con CoT few-shot (3 ejemplos de cadenas juridicas) subimos al rango 0.83. Donde mas mejoro: en casos ambiguos donde la respuesta depende de interpretar "terminacion" vs "rescision" vs "caducidad". La cadena obligaba al modelo a definir terminos antes de concluir.

Caso 2 — Razonamiento matematico (Wei et al., 2022, PaLM 540B en GSM8K): el paper original reporto salto de 18% (standard prompting) a 57% (CoT) en problemas de matematica de primaria. Con Self-Consistency encima, llegaron a 74%. Es el caso mas citado porque la magnitud del salto es brutal — problemas que requieren 4-5 pasos de aritmetica secuencial eran casi imposibles sin cadena.

Caso 3 — SQL generation en benchmarks enterprise (estilo Spider 2.0): con CoT estructurado (Thought -> SQL -> Validation), accuracy subio del rango 55% al 78% aproximado. El patron clave: la cadena incluye un paso de "validacion" donde el modelo corre mentalmente el query y verifica coherencia antes de emitir el SQL final. Es Self-Consistency barato — una sola cadena con verificacion interna.

6. Cuando NO Usarlo

Se sincero: hay un monton de casos donde CoT es over-engineering.

  • Clasificacion binaria o multiclase: spam/no-spam, sentimiento positivo/negativo. No hay cadena que seguir. CoT aqui es ruido.
  • Extraccion de entidades estructuradas: nombre, fecha, monto. CoT alucina entidades extras en la cadena.
  • Traduccion simple o paraphrase: no hay razonamiento que descomponer.
  • Alta volumetria, baja latencia: si procesas 100k requests por hora y cada CoT cuesta 200 tokens extra, el costo se vuelve prohibitivo.
  • Modelos chicos (< 7B): CoT degrada la calidad porque el modelo no sigue la cadena. Mejor few-shot directo.
  • Cuando el razonamiento correcto es secreto de negocio: si la cadena misma es el IP, no la quieres en el prompt porque sera visible para cualquiera que pueda hacer prompt extraction.

7. Stack Tipico en Produccion

Para sistemas que usan CoT en serio:

  • Orquestacion: LangChain o LlamaIndex para el pipeline. DSPy si quieres automatic prompt optimization (compila el prompt a partir de ejemplos, no a mano).
  • Serving: vLLM o TGI si corres open-source. Si usas API (OpenAI, Anthropic, Bedrock), directo con su SDK + retry logic.
  • Structured output: BAML o Pydantic + instructor para forzar el formato reasoning + answer. Sin esto, parseas con regex y sufres.
  • Observabilidad: Langfuse, Helicone o Arize Phoenix. Necesitas ver la cadena, no solo el input/output.
  • Evaluacion: Promptfoo, DeepEval o Braintrust para correr eval suites que midan calidad de cadena y accuracy final por separado.
  • Cache: Redis para cadenas repetidas. RedisVL si haces busqueda semantica sobre cadenas previas.

8. Conclusion: Decision Framework

Antes de meter CoT en produccion, responde estas cinco preguntas:

  • ¿La tarea tiene multiples pasos logicos verificables? Si no, no hay cadena que valga.
  • ¿El costo de un error es mayor que el costo de los tokens extra? Si un acierto vale mas que $\$0.01$ y CoT cuesta $\$0.005$, paga.
  • ¿Tu modelo base es suficientemente capaz de seguir la cadena? Si no, escala el modelo antes.
  • ¿Puedes parsear y validar la cadena de forma robusta? Si no, primero structured output, despues CoT.
  • ¿Tienes observabilidad para debuggear cuando la cadena sale mal? Si no, cualquier optimizacion despues es ciega.

Si contestaste si a las cinco: mete CoT y no mires atras. Si fallaste alguna, trabaja primero esa dimension antes de habilitarlo. Esa vaina no perdona atajos.

No hay fiesta — CoT no es la solucion, es una herramienta con costo. El electricista que sabe medir antes de cambiar piezas es el que sobrevive a los clientes bravos del lunes. Quedate embalado con eso. 🔧
