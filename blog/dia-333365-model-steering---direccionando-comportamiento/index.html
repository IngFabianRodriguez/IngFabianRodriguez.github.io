🔬 Qué Hacen Realmente Estos Frameworks

LangChain: El Framework de Orquestación

LangChain es fundamentalmente un framework de orquestación. Su fortaleazo es encadenar componentes: LLMs, retrievers, tools, memory, callbacks. No es una base de datos vectorial, no es un LLM, no es un servidor de inferencia. Es el pegamento que conecta todo eso.

LlamaIndex: El Framework de Indexación y Retrieval

LlamaIndex nació como un índice optimizado para RAG (Retrieval-Augmented Generation). Su nombre lo dice: Index. Tiene conectores a fuentes de datos, algoritmos de chunking, estrategias de embedding, y un sistema de retrieval que puede usar con cualquier LLM. Es más opinionado que LangChain en cómo organizar datos.

La confusión viene de que ambos公开发布 de todo: LangChain tiene sus retrievers, LlamaIndex tiene sus chains. Pero el núcleo es diferente.

La Math Behind RAG

El retrieval en RAG funciona con similitud coseno entre embeddings:

similarity(a, b) = cos(θ) = (a · b) / (||a|| × ||b||)

Donde a y b son vectores de embedding. En práctica, el recall@k se mejora combinando dense retrieval (embeddings) con sparse retrieval (BM25). La fórmula híbrida:

score = α · sim_dense(q, d) + (1-α) · sim_sparse(q, d)

Con α ∈ [0, 1] controlando el peso. En LlamaIndex esto es VectorIndexRetriever + BM25Retriever combinados con QueryFusionRetriever.

⚠️ Los 3 Errores del 80%

Error 1: No Entender Qué Hace Cada Framework

El desarrollador typique hace:

# ❌ MAL: LangChain como todo-en-uno
from langchain.vectorstores import Chroma
from langchain.embeddings import OpenAIEmbeddings

# Esto NO es LangChain haciendo RAG bien
# Es solo un wrapper alrededor de Chroma
vectorstore = Chroma.from_documents(documents, OpenAIEmbeddings())

El problema es que usa LangChain como si fuera una base de datos vectorial. LangChain aquí solo envuelve Chroma. No está orquestando nada, no está chainando pasos. Está haciendo un import innecesario que añade abstracción sin valor.

Fix:

# ✅ BIEN: Usa la herrami correcta para cada cosa

# Para retrieval: usa Chroma/Pinecone/qdrant directamente
# O LlamaIndex si necesitas indexación sofisticada
from llama_index import VectorStoreIndex, SimpleDirectoryReader
from llama_index.vector_stores import ChromaVectorStore

# Carga documentos con LlamaIndex (mejor chunking)
documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents, vector_store=ChromaVectorStore())

# Y usa LangChain SOLO para orquestar chains de tools
from langchain.agents import initialize_agent, Tool
from langchain.llms import OpenAI

# Ahora sí LangChain brilla: orquestando tools
llm = OpenAI(temperature=0)
tools = [Tool(name="Search", func=search_fn, description="...")]
agent = initialize_agent(tools, llm, agent="zero-shot-react-description")

Error 2: Overusing Cuando No Es Necesario

El segundo error massivo es introducing LangChain o LlamaIndex en proyectos que no los necesitan. Muchos devs construyen un chatbot simple sobre 10 PDFs y immediatamente arman esto:

# ❌ OVERKILL: RAG sencillo con stack innecesario
from langchain.document_loaders import PDFMinerLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.vectorstores import Pinecone
from langchain.embeddings import OpenAIEmbeddings
from langchain.chains import RetrievalQA
from langchain.chat_models import ChatOpenAI

# Todo esto para un chatbot que podría ser 50 líneas con llama_index
# + una API route en FastAPI

El math del overhead: por cada request RAG, tienes latencia extra de:

  • Text splitting: O(n log k) donde k = chunk_size
  • Embedding generation: latencia de red a OpenAI
  • Vector search: O(d · n) donde d = dimensions, n = num vectors
  • Context window del LLM: token count × cost per token

Si solo tienes 20 documentos, un simple grep -r "query" + LLM con full context es más rápido y más barato. La complejidad de RAG solo se justifica a escala.

Fix — Decision Framework:

def should_use_rag(num_docs: int, avg_doc_size: int, query_type: str) -> bool:
    """
    Decision framework: ¿necesitas RAG?

    RAG se justifica cuando:
    - num_docs > threshold (100+ documentos)
    - queries son específicas (no resúmenes)
    - docs actualizan frecuentemente
    - cost de full context > cost de retrieval + shorter context
    """
    full_context_tokens = avg_doc_size * num_docs
    retrieval_tokens = 1000  # typical retrieved context
    overhead_ratio = full_context_tokens / retrieval_tokens

    # Si overhead > 10x, RAG probablemente vale la pena
    return overhead_ratio > 10 or query_type == "specific_retrieval"

Error 3: No Saber Cuándo NO Usar un Framework

El tercer error es el reverse: no usar frameworks cuando sí ayudarían, o peor, reinventar la rueda.

# ❌ MAL: Reinventar lo que LlamaIndex hace mejor
def naive_rag(query, documents, llm):
    """NAIVE RAG: reinventing wheel"""
    # Embed query
    query_embedding = get_embedding(query)  # you coded this yourself

    # Search manually (you wrote this vector search)
    scores = []
    for doc in documents:
        doc_embedding = get_embedding(doc)
        score = cosine_similarity(query_embedding, doc_embedding)
        scores.append((score, doc))

    # Sort and take top-k
    top_docs = sorted(scores, key=lambda x: x[0], reverse=True)[:5]

    # Build context
    context = "\n".join([doc for _, doc in top_docs])

    # Call LLM
    response = llm(f"Context: {context}\n\nQuestion: {query}")
    return response

# Esto reinventa:
# - Chunking strategy
# - Embedding optimization
# - Retrieval ranking
# - Context window management
# ...y probablemente lo hace peor que llama_index

Fix — Usa LlamaIndex para retrieval, no lo reinentes:

# ✅ BIEN: Abstrae lo que ya está bien resuelto
from llama_index import VectorStoreIndex, SimpleDirectoryReader
from llama_index.retrievers import VectorIndexRetriever
from llama_index.query_engine import RetrieverQueryEngine

# El built-in ya tiene:
# - Semantic chunking optimizado
# - Hybrid search (dense + sparse)
# - MMR (Maximal Marginal Relevance) para diversidad
# - Citation tracking

documents = SimpleDirectoryReader("./data", recursive=True).load_data()
index = VectorStoreIndex.from_documents(documents)

# Configura retrieval avanzado
retriever = VectorIndexRetriever(
    index=index,
    similarity_top_k=10,
    vector_store_query_mode="hybrid",  # dense + sparse
    alpha=0.5  # hybrid weight
)

query_engine = RetrieverQueryEngine.from_args(
    retriever,
    node_postprocessors=[...],  # MMR, SimilarityPostprocessor
)
response = query_engine.query("tu pregunta")

🔗 Cómo Combinar Ambos Frameworks

El mejor setup es usar LlamaIndex para retrieval y LangChain para orquestación. No son competidores, son complementarios:

# ✅ ARQUITECTURA HÍBRIDA: Lo mejor de ambos mundos
from llama_index import VectorStoreIndex, SimpleDirectoryReader
from llama_index.vector_stores import ChromaVectorStore
from llama_index.llms import LangChainLLM  # Bridge!
from langchain.chat_models import ChatOpenAI
from langchain.agents import initialize_agent, Tool
from langchain.text_splitter import RecursiveCharacterTextSplitter

# 1. INDEXACIÓN con LlamaIndex (donde brilla)
documents = SimpleDirectoryReader(
    "./data",
    file_extractor={".pdf": "PDFReader", ".csv": "PagedCSVReader"}
).load_data()

# Advanced chunking que LlamaIndex hace bien
index = VectorStoreIndex.from_documents(
    documents,
    chunk_size=512,
    chunk_overlap=64,
    vector_store=ChromaVectorStore(),
)

# 2. RETRIEVAL con LlamaIndex
retriever = index.as_retriever(similarity_top_k=5)

# 3. ORQUESTACIÓN con LangChain (donde brilla)
llm = ChatOpenAI(model="gpt-4-turbo", temperature=0)

def retrieval_func(query: str) -> str:
    """Tool que LangChain puede llamar para buscar contexto"""
    nodes = retriever.retrieve(query)
    return "\n".join([node.text for node in nodes])

# LangChain agent orchestrando tools + retrieval
tools = [
    Tool(
        name="KnowledgeBase",
        func=retrieval_func,
        description="Busca información en la base de conocimiento. Input: pregunta detallada."
    ),
    Tool(
        name="Calculator",
        func=calc_tool,
        description="Para cálculos matemáticos. Input: expresión matemática."
    ),
]

agent = initialize_agent(
    tools,
    llm,
    agent="conversational-react-description",
    memory=ConversationBufferMemory(memory_key="chat_history"),
    verbose=True
)

# El agent decide cuándo buscar en KB (LlamaIndex retrieval)
# y cuándo usar otras tools
response = agent.run(input="¿Qué dice la política de devoluciones?")

🚀 Resumen y Cierre Colombiano

Pues ahí lo tienen, parcero. La clave del día 333:

  • LangChain = orquestación de components, chains, tools, y agents. No es tu vector database.
  • LlamaIndex = indexación y retrieval optimizado para RAG. No es tu orchestrator.
  • El 80% reinventa porque no entiende qué problema resuelve cada herramienta.
  • El 20% usa bien combinándolos donde cada uno brilla: LlamaIndex retrieval + LangChain orchestration.
  • No todo necesita RAG. A veces 10 líneas con requests direct al LLM resuelven más rápido.

La próxima vez que vayas a montar un "RAG system con LangChain y LlamaIndex", pregúntate primero: ¿realmente necesito los dos? ¿Dónde exactamente? ¿Qué problema resuelve cada componente que no puedas resolver más simple?
