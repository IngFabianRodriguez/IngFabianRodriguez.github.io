Chain of Thought - Por qué el 75% implementa CoT sin saber cuándo funciona

15 de may de 2026
prompt-engineering

Hola, parcero. Día 165 y hoy vamos con Chain of Thought (CoT). Este es probablemente el concepto más malinterpretado en prompt engineering. El 75% de los practitioners implementa CoT sin entender cuándo realmente funciona y cuándo es solo overhead innecesario. Vamos a arreglar eso.

🤔 Qué Es Chain of Thought Exactamente

Chain of Thought no es "pedirle al modelo que piense step by step". Eso es una versión simplificada que se volvió popular en Twitter y que ha causado más confusión que claridad.

CoT es un patrón de razonamiento explícito donde:

  • El modelo genera interleaveadamente razonamiento (chain) y respuestas
  • Cada paso del razonamiento construye sobre el anterior
  • El output final es una consecuencia lógica de la cadena

La definición formal de Wei et al. (2022):

$$P(y_1, y_2, ..., y_n | x) = \prod_{i=1}^{n} P(y_i | x, y_1, ..., y_{i-1})$$

Donde $y_i$ puede ser un token de razonamiento o un token de respuesta. La clave es que el modelo decide dinámicamente qué es qué.

📊 Cuándo CoT Funciona vs Cuándo No

✅ CoT SI Funciona Para:

  • Problemas multi-step: math, lógica, programación
  • Tareas donde el error es cascada: un error en paso 1 arruina todo
  • Modelos con suficiente capacidad: ~100B+ parámetros
  • Cuando puedes verificar el razonamiento: tienes el answer key

❌ CoT NO Funciona Para:

  • Preguntas de hecho simples: "¿Cuál es la capital de Francia?"
  • Tareas donde el modelo ya sabe la respuesta: CoT añade overhead sin beneficio
  • Modelos pequeños (<10B): el razonamiento explícito degrada performance
  • Generación creativa: historias, poems, brainstorming
  • Clasificación simple: sentiment analysis, categorización

El Math de Por Qué Funciona

Para tareas que requieren $k$ pasos de razonamiento, CoT permite que el modelo:

$$\text{Accuracy}_{CoT} \approx \prod_{i=1}^{k} p(\text{step}_i | \text{previous steps})$$

Sin CoT, el modelo intenta predecir directamente $y$ dado $x$, lo cual es equivalente a:

$$p(y | x) = p(y | \text{razonamiento implícito})$$

El problema es que el razonamiento implícito tiene menos compute dedicado que el razonamiento explícito de CoT.

🔧 Zero-Shot CoT vs Few-Shot CoT

Zero-Shot CoT (AutoCoT)

Usa la frase mágica "Let's think step by step" para activar razonamiento:

# Zero-shot CoT - simple pero efectivo
prompt = """Pregunta: Si un tren sale de A a 60km/h y otro de B a 90km/h
            y la distancia es 300km, ¿cuándo se encuentran?

Respuesta: Let's think step by step."""

response = model.generate(prompt)
# El modelo genera su razonamiento explícito

Few-Shot CoT

Más efectivo pero requiere ejemplos manualmente curados:

# Few-shot CoT - mejor para tareas complejas
few_shot_prompt = """Pregunta: Juan tiene 5 manzanas, compra 3 más,
                    luego regala 2. ¿Cuántas tiene?
Razonamiento: Juan empieza con 5 manzanas.
              Compra 3 más: 5 + 3 = 8 manzanas.
              Regala 2: 8 - 2 = 6 manzanas.
Respuesta: 6

Pregunta: Un reloj suena cada 6 segundos. ¿Cuántas veces suena en 1 minuto?
Razonamiento:"""

response = model.generate(few_shot_prompt)
# El formato de razonamiento guía al modelo

⚠️ Errores Comunes que el 75% Comete

Error 1: Usar CoT Para Todo

CoT no es un booster universal. Para preguntas donde el modelo ya sabe la respuesta, CoT añade:

  • Latencia extra (tokens de razonamiento)
  • Coste adicional (más tokens = más dinero)
  • Posibles errores de razonamiento que no existirían con respuesta directa
# ❌ MAL: CoT para pregunta trivial
prompt = """Pregunta: ¿Qué es Python?
Let's think step by step."""

# ✅ BIEN: Sin CoT para hechos simples
prompt = """Pregunta: ¿Qué es Python? Respuesta:"""

Error 2: No Separar Razonamiento de Respuesta

El output de CoT mezcla dos tipos de contenido que deben manejarse diferently:

# ❌ MAL: No separar outputs
response = model.generate(prompt)
# response contiene razonamiento + respuesta entrelazados

# ✅ BIEN: Parsear explícitamente
def extract_answer(response):
    parts = response.split("Respuesta:")
    reasoning = parts[0].replace("Razonamiento:", "").strip()
    answer = parts[1].strip() if len(parts) > 1 else None
    return reasoning, answer

reasoning, final_answer = extract_answer(response)

Error 3: Confundir CoT con ReAct

Son conceptos diferentes:

  • CoT: razonamiento interno, no interactúa con herramientas
  • ReAct: combina razonamiento con acciones (tool use)
# CoT: solo razonamiento
"Vamos a resolver esto paso a paso..."

# ReAct: razonamiento + acción + observación
"Primero necesito buscar X. Acción: search(X). Observación:..."

📈 Self-Consistency: Mejora Drástica con Muestreo

Wang et al. (2022) propuso un método simple para mejorar CoT: muestrea múltiples razonamientos y vota por el más común.

from collections import Counter

def self_consistency(prompt, model, n_samples=20):
    """CoT con self-consistency - mejora 10-20% en benchmarks"""
    responses = []
    
    for _ in range(n_samples):
        # Muestrea con temperature > 0 para diversidad
        response = model.generate(
            prompt, 
            temperature=0.7,
            do_sample=True
        )
        reasoning, answer = extract_answer(response)
        responses.append(answer)
    
    # Votación mayoritaria
    counter = Counter(responses)
    final_answer = counter.most_common(1)[0][0]
    
    return final_answer, counter

El math detrás:

$$\hat{y} = \text{mode}\{y_1^{(s)}, y_2^{(s)}, ..., y_n^{(s)}\}$$

Donde $s$ indica diferentes muestreos. La respuesta final es la moda de todas las respuestas generadas.

🏁 Resumen

  • CoT funciona: problemas multi-step, modelos grandes, tareas verificables
  • CoT no funciona: hechos simples, modelos pequeños, tareas creativas
  • Zero-shot CoT: usa "Let's think step by step"
  • Few-shot CoT: mejor para tareas complejas, requiere ejemplos
  • Self-consistency: muestrea múltiples veces, vota por el más común
  • No es ReAct: CoT es interno, ReAct incluye herramientas
