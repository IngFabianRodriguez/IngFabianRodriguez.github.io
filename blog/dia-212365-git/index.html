Dia 212/365: Git — El kardex criptografico que te salva cuando alguien pierde el `.git`

31 de julio de 2026
git

Introduccion: El viernes que git push --force borró el audit trail

No importa si trabajás en una fintech, un hospital, una pipeline de ML o un microservicio crítico: en algún momento alguien hace git push --force contra la rama equivocada, corrompe el .git con un disco fallando, o pregunta "¿qué hay en este oid?". Los tres casos se vuelven procedimientos de 5 minutos cuando entendés que Git no es "una base de datos de archivos con historia": es un Merkle DAG content-addressed con hashes criptográficos que se autorrefuerzan. Git es aritmética de SHA-1, refs mutables y packs con delta compression, y te lo voy a mostrar operativamente con código que podés correr tal cual.

1. Que es Git? (Y por que deberia importarte)

1.1 La analogia cotidiana: el kardex de una droguería de control especial

Imaginá el kardex (libro foliado y numerado) que toda farmacia colombiana debe llevar cuando dispensa medicamentos de control especial: morfina, fentanilo, midazolam. Cada movimiento queda registrado con fecha, sustancia, lote, cantidad, responsable, y — esto es lo clave — una firma o sello que vincula la entrada actual con la anterior. Si alguien arranca una hoja, el INVIMA lo detecta en la primera inspección. Si alguien cambia un número, queda evidencia forense porque cada fila tiene un identificador único (hash) que depende criptográficamente de las anteriores.

Eso, mutatis mutandis, es Git:

  • Identificador único por contenido (no por nombre): el oid de cada objeto es un hash del contenido. A prueba de colisiones prácticas (con las reservas que más adelante discutimos sobre SHA-1).
  • Inmutabilidad: reescribir el pasado cambia el hash raíz, y como cada commit referencia el commit padre, la cadena entera se invalida hacia adelante.
  • DAG (grafo acíclico dirigido): las branches son protocolos clínicos alternativos; los merges consolidan varias ramas en una sola.

Por eso cuando auditoría o compliance te pregunta "¿cómo garantizás que nadie modificó un archivo en producción?", la respuesta es la cadena de hashes, no un "tenemos backups".

1.2 La matematica formal, simbolo por simbolo

Git expone cuatro tipos de objetos. Cada uno es un blob opaco precedido por un header canónico:

$$O = (\text{type}, \text{size}, \text{content})$$

Donde $\text{type} \in \{\texttt{blob}, \texttt{tree}, \texttt{commit}, \texttt{tag}\}$ y $\text{size}$ es la longitud en bytes de $\text{content}$. El header completo es $\text{type}\;\text{SP}\;\text{size}\;\text{NUL}\;\text{content}$, donde SP es ASCII 0x20 y NUL es 0x00. Esto es el "formato canónico": cualquier desviación produce un oid distinto.

El identificador único (oid) es un hash SHA-1 sobre ese header concatenado con el contenido:

$$\text{oid} = \text{SHA-1}\big(\text{type}\;\text{SP}\;\text{size}\;\text{0x00}||\text{content}\big)$$

Notá dos cosas. Primero, no es el hash solo del contenido: el tipo entra al cálculo para que un blob y un tree (o commit) con los mismos bytes no colisionen. Segundo, ese SHA-1 es de 160 bits — 40 chars hex — y Git lo almacena shardado en disco: los primeros 2 chars son el subdirectorio ($\texttt{xx/yyyyyyy...}$), los 38 restantes el nombre del archivo. Esto da fan-out de 256 buckets que mantiene cada directorio del .git/objects con tamaño acotado (Linux habilita multi-pack-index desde git 2.27 para escalar ese diseño en monorepos con millones de objetos).

La estructura es un Merkle DAG con cuatro tipos:

  • blob: archivo plano sin nombre (raw bytes, sin metadata del path).
  • tree: directorio. Lista serializada de entradas $(\text{mode}, \text{name}, \text{oid})$ ordenadas lexicográficamente — el orden hace al tree determinístico: misma estructura ⇒ mismo oid.
  • commit: snapshot. Contiene el $\text{tree}$ raíz, cero o más padres $\langle P_0, P_1, \ldots, P_{n-1} \rangle$, autor, committer y mensaje.
  • tag: anotación que apunta a otro objeto (típicamente un commit) con metadata extra (tagger, mensaje, firma GPG/SSH opcional).

Para un commit:

$$C = \big(\text{tree},\; \langle P_0, P_1, \ldots, P_{n-1} \rangle,\; \text{author},\; \text{committer},\; \text{message}\big)$$

En un commit normal $n = 1$ (un solo padre: historia lineal). En un merge $n \geq 2$ (varios padres: consolidación de ramas). El primer commit de un repo tiene $n = 0$ (raíz, sin referencias previas).

La propiedad clave es la invariancia Merkle: cambiar un solo byte en cualquier blob propaga nuevos oids hacia arriba. Si modificás un archivo en el commit $C$:

$$\text{oid}'_{\text{blob}} \neq \text{oid}_{\text{blob}} \implies \text{oid}'_{\text{tree}} \neq \text{oid}_{\text{tree}} \implies \text{oid}'_{C} \neq \text{oid}_{C}$$

Por tanto, cualquier observador externo verifica la integridad de toda la historia computando un solo hash: el del HEAD. Esa es la elegancia. Git no necesita una base de datos central ni un servidor de timestamps: la cadena criptográfica es autosuficiente.

2. Como Git resuelve esto por vos (mecanismo interno)

Cuando ejecutás git commit, Git hace cuatro cosas en orden:

  1. Hashea cada blob modificado y lo escribe a .git/objects/xx/yyyy... con zlib nivel 6.
  2. Construye un tree nuevo serializando las entradas en orden lexicográfico y lo hashea.
  3. Construye un commit con header tree \nparent \nauthor ...\ncommitter ...\n\n y lo hashea.
  4. Mueve la ref refs/heads/main al nuevo commit (operación atómica: write a tempfile + rename).

El paso (4) es lo único mutable del modelo: las refs son punteros mutables. Todo lo demás es append-only. Esa separación es poderosa: podés tener 100 refs apuntando al mismo commit y moverlas independientemente sin corromper objetos.

Los packs (.git/objects/pack/*.pack) cambian el juego cuando el repo crece. Git agrupa objetos en archivos binarios con delta compression: para cada objeto almacena una descripción basada en otro objeto cercano del pack ("copia bytes 0-1023 del objeto X, inserta foo en offset 200, longitud 3"). La ventana típica es 10 objetos, el deep limit es 250, ambos configurables con --depth y --window en git pack-objects. Para clonar repos grandes, Git transmite un thin pack (sin bases de delta) y el cliente resuelve las deltas localmente con git index-pack. Clonar el kernel de Linux baja del orden de un gigabyte en lugar de varios.

Los *.idx son tablas hash $H: \text{oid} \rightarrow \text{offset}_{pack}$ que cargan en memoria para resolver "dame este oid" sin recorrer el pack completo. Con multi-pack-index, esa tabla se comparte entre múltiples packs, evitando re-empaquetar al consolidar muchos packs incrementales.

3. Git: Uso Directo y Casos de Control Fino

Más allá de add/commit/push, Git expone una capa de plomería (git cat-file, git hash-object, git mktree, git commit-tree, git update-ref) que te permite tratar los objetos como una base de datos direccionable por contenido. Estas primitivas son el sustrato sobre el que git add y git commit están construidos. Si las entendés, podés construir encima: auditor de integridad, migrador de histories, filtro binario custom.

Calcular el oid de una cadena sin escribir a disco:

$ echo -n "hello world" | git hash-object --stdin
3b18e512dba79e4c8300dd08a66c7fd0917bc09f

Y luego escribirlo al object store:

$ echo -n "hello world" | git hash-object -w --stdin
3b18e512dba79e4c8300dd08a66c7fd0917bc09f

Inspeccionar el tipo y el contenido:

$ git cat-file -t 3b18e512dba79e4c8300dd08a66c7fd0917bc09f
blob

$ git cat-file -p 3b18e512dba79e4c8300dd08a66c7fd0917bc09f
hello world

Construir un tree y un commit "a mano" con mktree y commit-tree te da control total sobre el contenido de un commit sin pasar por el index ni el working tree — útil en pipelines de release donde querés firmar un release notes sin tocar archivos.

4. Implementacion Production-Ready: pygit-mini

No vamos a reimplementar Git (son ~700k líneas de C), pero sí un subset mínimo que podés correr tal cual como referencia para entender el modelo de objetos y validarlo contra un repo real. Cada módulo es atómico y ejecutable en aislamiento.

4.1 Tipos y protocolos

# pygit/git_objects.py — Production-grade, executable as-is.
from __future__ import annotations

import hashlib
import zlib
from dataclasses import dataclass
from enum import Enum


class ObjectType(str, Enum):
    BLOB = "blob"
    TREE = "tree"
    COMMIT = "commit"
    TAG = "tag"


@dataclass(frozen=True)
class GitObject:
    """Inmutable: el oid depende solo del contenido canonico."""
    type: ObjectType
    content: bytes

    def canonical(self) -> bytes:
        # Formato Git: "<type> <size>\0<content>" en bytes.
        header = f"{self.type.value} {len(self.content)}".encode()
        return header + b"\x00" + self.content

    @property
    def oid(self) -> str:
        # Git historicamente usa SHA-1. La migracion a SHA-256 mantiene
        # el mismo algoritmo; solo cambia la funcion hash.
        return hashlib.sha1(self.canonical()).hexdigest()

    def serialize(self) -> bytes:
        # .git/objects almacena el formato canonico comprimido con zlib.
        return zlib.compress(self.canonical(), level=6)


def blob(content: bytes) -> GitObject:
    return GitObject(ObjectType.BLOB, content)

4.2 El motor principal (ObjectStore)

# pygit/object_store.py — Disk-backed, sharded exactly like .git/objects/.
from __future__ import annotations

import pathlib
from typing import Iterator

from git_objects import GitObject, ObjectType


class ObjectStore:
    """Object store sharded on-disk, identico a .git/objects/."""

    def __init__(self, root: pathlib.Path) -> None:
        self.root = pathlib.Path(root) / ".git" / "objects"
        self.root.mkdir(parents=True, exist_ok=True)

    def _path(self, oid: str) -> pathlib.Path:
        # Shard: los primeros 2 chars del oid son el subdirectorio.
        # 256 buckets mantienen cada directorio con menos de ~16k entradas
        # en repos de hasta millones de objetos (fan-out constante).
        if len(oid) < 3:
            raise ValueError(f"oid demasiado corto: {oid!r}")
        return self.root / oid[:2] / oid[2:]

    def put(self, obj: GitObject) -> str:
        """Idempotente: mismo contenido => mismo oid => no reescribe."""
        path = self._path(obj.oid)
        if not path.exists():
            path.parent.mkdir(parents=True, exist_ok=True)
            path.write_bytes(obj.serialize())
        return obj.oid

    def get(self, oid: str) -> GitObject:
        """Carga y descomprime. KeyError si no existe."""
        path = self._path(oid)
        if not path.exists():
            raise KeyError(f"objeto {oid} no encontrado en el store")
        return self._deserialize(path.read_bytes())

    def has(self, oid: str) -> bool:
        return self._path(oid).exists()

    def _deserialize(self, compressed: bytes) -> GitObject:
        raw = zlib.decompress(compressed)
        null = raw.index(b"\x00")
        header, content = raw[:null], raw[null + 1 :]
        type_str, size_str = header.split(b" ", 1)
        # Validacion: el size en el header debe coincidir con los bytes.
        if int(size_str) != len(content):
            raise ValueError(
                f"size mismatch: header declara {size_str}, "
                f"content tiene {len(content)} bytes"
            )
        return GitObject(type=ObjectType(type_str.decode()), content=content)

    def __iter__(self) -> Iterator[str]:
        """Itera todos los oids del store (shards incluidos)."""
        if not self.root.exists():
            return iter([])
        for shard in self.root.iterdir():
            if not shard.is_dir() or len(shard.name) != 2:
                continue
            for f in shard.iterdir():
                yield shard.name + f.name

4.3 Utilidades de analisis y verificacion

# pygit/verify.py — Reachability y verificacion de integridad.
from __future__ import annotations

from typing import Iterable

from git_objects import GitObject, ObjectType
from object_store import ObjectStore


def verify_oid(store: ObjectStore, oid: str) -> bool:
    """Re-hashea el objeto cargado y compara con el oid del path.

    Detecta bit-rot y tampering: si el archivo esta corrompido, el hash
    recomputado no coincide con el nombre del archivo.
    """
    obj = store.get(oid)
    return obj.oid == oid


def reachable_from(store: ObjectStore, roots: Iterable[str]) -> set[str]:
    """DFS por punteros parent: devuelve todos los objetos alcanzables.

    Reproduce lo que hace `git rev-list --reachable` internamente. Si los
    `roots` son todas las refs, el resultado es la historia alcanzable
    completa (util para calcular el ratio garbage/reachable).
    """
    seen: set[str] = set()
    stack = list(roots)
    while stack:
        oid = stack.pop()
        if oid in seen:
            continue
        seen.add(oid)
        try:
            obj = store.get(oid)
        except KeyError:
            continue  # Referencia colgante. Registramos pero no rompemos.
        if obj.type == ObjectType.COMMIT:
            for line in obj.content.splitlines():
                if line.startswith(b"parent "):
                    stack.append(line[len(b"parent "):].decode())
        elif obj.type == ObjectType.TREE:
            # Formato tree: "<mode> <name>\0<oid-20-bytes>" por entrada.
            content = obj.content
            i = 0
            while i < len(content):
                nul = content.index(b"\x00", i)
                _mode_name = content[i:nul]
                oid_bytes = content[nul + 1 : nul + 21]
                stack.append(oid_bytes.hex())
                i = nul + 21
    return seen

5. Ejemplos de Uso en Casos Reales

Caso 1: construir un commit desde cero con la plomería de Git

Replica lo que hace un hook pre-receive cuando necesitás validar un commit antes de aceptarlo, sin pasar por el index ni el working tree:

from git_objects import GitObject, ObjectType, blob
from object_store import ObjectStore
import pathlib

store = ObjectStore(pathlib.Path("/tmp/repo_demo"))

# Paso 1: hashear el contenido y escribir el blob.
b_oid = store.put(blob(b"x_new=42.0\ny_true=37\n"))
print(b_oid)  # => "557db03de997..." (40 chars hex)

# Paso 2: construir un tree minimo con un archivo. Formato: "<mode> <name>\0<oid-20-bytes>".
tree_content = b"100644 config.yml\x00" + bytes.fromhex(b_oid)
t_oid = store.put(GitObject(ObjectType.TREE, tree_content))

# Paso 3: construir un commit raiz (sin parent).
commit_content = (
    f"tree {t_oid}\n"
    f"author Dev <dev@example.com> 1700000000 +0000\n"
    f"committer Dev <dev@example.com> 1700000000 +0000\n"
    f"\n"
    f"update config\n"
).encode()
c_oid = store.put(GitObject(ObjectType.COMMIT, commit_content))
print(c_oid)  # => oid del commit raiz recien creado

# Verificacion Merkle: cambiar un byte del blob invalida todo hacia arriba.
b2_oid = store.put(blob(b"x_new=42.1\ny_true=37\n"))  # 42.0 -> 42.1
assert b_oid != b2_oid, "blob oids deben diferir"
# Reconstruir tree+commit con el nuevo blob daria oids distintos en todos los niveles.

Caso 2: detectar corrupcion silenciosa con verify_oid

Tuve un disco fallando en un servidor de builds. La corrupcion de .git/objects no aparece como error inmediato — solo como "fatal: bad object HEAD" semanas después. Defensa proactiva: barrear todos los oids y re-hashear.

from verify import verify_oid
import pathlib

store = ObjectStore(pathlib.Path("/var/lib/builds/prod_repo"))
errors = [oid for oid in store if not verify_oid(store, oid)]
if errors:
    print(f"BIT-ROT DETECTADO en {len(errors)} objeto(s)")
    # Estrategia: re-poblar desde el remote autorizado.
    # git fetch origin '+refs/heads/*:refs/remotes/origin/*'

Es lo que hace git fsck --full --strict: barre los oids accesibles y los re-hashea para validar que el contenido en disco coincide con el nombre del archivo.

Caso 3: medir cuantos objetos sueltos son alcanzables

Para decidir cuándo correr git gc o migrar de disco, medí el ratio reachable/total. En CI monorepos los objetos sueltos se acumulan por años de pipelines que escriben y nunca borran:

from verify import reachable_from
import pathlib

store = ObjectStore(pathlib.Path("/var/lib/builds/prod_repo"))

# Lee las refs locales (refs/heads/*.loose). En produccion anadir
# .git/packed-refs para refs en pack.
refs_dir = pathlib.Path("/var/lib/builds/prod_repo/.git/refs/heads")
refs = [f.read_text().strip() for f in refs_dir.glob("*") if f.is_file()]

reachable = reachable_from(store, refs)
total = sum(1 for _ in store)
ratio = len(reachable) / total if total else 0.0
print(f"reachable {len(reachable)} / total {total} = {ratio:.2%}")
# Tipico: 0.85-0.95. Si <0.5 hay muchos huerfanos -> gc prioritario.

6. Debugging: Cuando Todo se Va a la Mierda

Problema 1: error: bad object HEAD

Corrupcion confirmada. Detectá con:

$ git fsck --full --strict
broken link from tree <oid> to blob <oid>
missing blob <oid>

Causa tipica: bit-rot en disco o git push --force mal calibrado. Tres soluciones en orden de agresividad:

  1. Buscar en el reflog: git reflog --all | grep — el commit puede estar en el reflog local (90 días por defecto, configurable con gc.reflogExpire).
  2. Re-poblar desde el remote: git fetch origin '+refs/heads/:refs/remotes/origin/'. Ojo: el + reescribe refs locales.
  3. Nuclear, con backup primero: cp -a .git .git.bak, después borrar .git/objects// problematicos y re-clonar desde el remote.

Problema 2: el repo pesa 14GB y git gc no lo baja

Causa: objetos sueltos acumulados por años de pipelines CI. Diagnostico numerico:

$ git count-objects -v
count: 1840233
size: 4128.45 MiB       # objetos sueltos (no en pack)
in-pack: 13211921
packs: 1
size-pack: 9812.34 MiB
prune-packable: 0
garbage: 1840233        # <- si garbage ~ count, hay GC pendiente

Soluciones en orden:

  1. Estándar: git gc --aggressive --prune=now --quiet. --aggressive baja el delta window para re-empaquetar más fuerte; --prune=now borra sueltos no alcanzables. Medí después con git count-objects -v.
  2. Manual con control fino: git repack -a -d --depth=250 --window=250 para controlar el delta window sin tocar GC.
  3. Custom pack: git pack-objects --depth=250 --window=250 packtmp < <(git rev-list --all) para crear packs a medida.

Problema 3: esa vaina del SHAttered

En 2017 Google y CWI Amsterdam demostraron colisiones prácticas de SHA-1 (SHAttered) con costo estimado de seis cifras bajas en cómputo alquilado. En 2020 publicaron SHA-1 con prefijo elegido ("Shambles") por menos de 50k USD. Git no es directamente explotable porque el header canónico incluye el tipo y el tamaño, pero la superficie de ataque crece. Tres mitigaciones:

  1. Verificar la cadena manualmente para datos sensibles: rehashear blob → tree → commit y confirmar que el oid del HEAD coincide con lo esperado.
  2. Migrar a SHA-256: builds experimentales con GIT_DEFAULT_HASH=sha256 (git 2.42+). Misma interfaz, hash más fuerte.
  3. Firmar tags y merges críticos con GPG o SSH keys; el oid puede ser ambiguo, pero la firma externa no lo es.

7. Optimizaciones de Produccion

Pack files + multi-pack-index

Para repos con muchos refs (CI monorepos), git gc por defecto crea un solo pack. Habilitar core.multiPackIndex=true permite reparticionar packs sin re-empaquetar desde cero:

# .git/config
[core]
    repositoryFormatVersion = 1
    multiPackIndex = true
[pack]
    packSizeLimit = 2g

Trade-off: el idx consume RAM adicional al cargar (proporcional a $\text{objects} \times 4$ bytes). Para monorepos con >1M objetos vale la pena; para repos personales, no.

Alternates (object sharing entre clones)

Si tenés N clones del mismo repo en una misma workstation o runner de CI, podés compartir la particion de objetos vía .git/objects/info/alternates:

$ echo "/mnt/shared/.git/objects" >> /var/lib/builds/repo/.git/objects/info/alternates

Esto ahorra hasta un 80% de disco en workstations de devs y en CI runners. Trade-off: si borrás /mnt/shared perdes los objetos de todos los clones. Backups primero, siempre.

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion 📜

Entender Git como Merkle DAG con content addressing te blinda en cuatro frentes:

  • Auditabilidad criptográfica: cualquier modificacion no autorizada rompe la cadena; git fsck (o tu propio verify_oid) lo detecta antes que un diff visual.
  • Recuperacion ante desastres: reflog, packs y fsck permiten reconstruir estado desde objetos sueltos.
  • Performance predecible: packs con delta compression dan factor 10-100× en transferencia. Monitorea count-objects -v en CI.
  • Portabilidad: el formato .git/objects es estable desde 2005; ningún proveedor te deja atrapado.

Mini-checklist antes de cada merge a main:

  • [ ] git fsck limpio antes del push (correlo en CI).
  • [ ] No --force a main sin approvals de N revisores y CI en verde.
  • [ ] protected-branches con required status checks activos.
  • [ ] Backup del reflog (.git/logs) antes de cualquier gc agresivo.
  • [ ] Monitoreo de count-objects -v en el dashboard del monorepo.

Pilas con el reflog, parce: ese archivo es la red de seguridad cuando un git push --force sale mal un viernes a las 6pm. El modelo de Git no es magia — es aritmética de hashes, estructura Merkle DAG y tres vigas de soporte (refs mutables, reflog, packs). Cuando las entendés, dejás de rezar y empezás a confiar.
