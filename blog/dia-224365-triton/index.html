Dia 224/365: Triton — el patio de maniobras de tu GPU

12 de agosto de 2026
tritonserver (NVIDIA container)

Introduccion: Cuando tu "modelo en produccion" se vuelve un nido de ratas

Parcero, hablemos de algo que casi nadie te cuenta cuando estudias ML: el momento en que pasas de cuadernos Jupyter a tener que servir tres, cinco, quince modelos en una sola GPU que cuesta mas que un carro, y resulta que uno come 12 GB, otro 8 GB, otro 4 GB, sumas mentalmente y la cuenta no te da. O peor: te da, pero cada modelo vive en su propio contenedor Docker, con su propio FastAPI, con su script de preprocesamiento distinto. Cuando Prometheus llega a graficar la latencia, parece un electrocardiograma de alguien pasando un susto.

Eso es exactamente el problema que NVIDIA Triton Inference Server ataca. No es la unica opcion (TensorFlow Serving, TorchServe, BentoML y Ray Solve existen), pero es la unica que fue construida desde el nucleo bajo la premisa de que una GPU es un recurso compartido, no un terreno baldio donde cada modelo pone su cerca. Sirve modelos compilados en TensorRT, ONNX, PyTorch puro, TensorFlow, e incluso pre/postprocesamiento custom en Python, todo bajo un solo servidor C++ con HTTP/GRPC de baja latencia, batching dinamico y metricas decentes.

Este articulo es para el senior que ya se quemo intentando hacer convivir ResNet50 con un LLM de 7B en la misma A100, y quiere entender la matematica detrAs de por que Triton decide ejecutar modelos en paralelo, y como exprimir cada microsegundo sin tener que reescribir el cliente.

1. Que es Triton? (Y por que deberia importarte)

1.1 La analogia cotidiana: el patio de maniobras de una estacion ferroviaria

Imaginate el patio de maniobras de una estacion de tren de carga. Por una sola via van llegando furgones vacios, vagones cisterna, contenedores refrigerados, todos separados y mezclados. El operario del patio (Triton) recibe cada furgon, lo clasifica por destino, lo acopla con otros que van al mismo lugar (eso es el dynamic batching), decide en que via de salida lo monta segun peso y urgencia, y mantiene varias vias funcionando en paralelo para que un tren rapido no quede esperando a uno lento. Ademas, tiene un panel donde ve cuantos furgones hay en cola, cual via se esta congestionando, y puede mover locomotoras entre vias si hace falta (eso es concurrent model execution + model instance groups).

Cuando tu peticion HTTP llega a Triton, el flujo es identico:

  1. Llega con un payload (tensores) y un nombre de modelo destino.
  2. Si hay otra peticion para el mismo modelo esperando, las pega juntas en un solo batch.
  3. Despacha el batch al backend correspondiente (TensorRT, ONNX, PyTorch, lo que sea).
  4. Devuelve los tensores de salida por la misma conexion.

Y eso, mira, es lo que hace a Triton especial: el batching no lo hace tu cliente (con todo el problema de coordinacion que eso implica), lo hace el servidor, transparente y con latencia optima.

1.2 La matematica formal: por que el batching dinamico es optimo

El problema central de servir modelos en GPU es el contraste entre latencia de una sola peticion y throughput del sistema. Cada invocacion al modelo tiene un costo fijo de lanzamiento en GPU (kernel launches, transferencias CPU-GPU, setup de CUDA streams) y un costo variable que escala con el tamano del batch.

Llamemos $T_{kernel}$ al tiempo de computo GPU para un batch, $T_{launch}$ al overhead fijo por invocacion, y $B$ al tamano del batch. El tiempo total de una peticion llegando sola es:

$$T_{single} = T_{launch} + T_{kernel}(1)$$

Cuando agregamos batching, $n$ peticiones que llegaron en la misma ventana se procesan juntas:

$$T_{batched}(n) = T_{launch} + T_{kernel}(n)$$

El throughput se dispara porque la mayoria de operaciones en GPU (convoluciones, multiplicaciones de matrices) son sub-lineales en $n$ hasta cierto punto. Para una capa densa idealizada:

$$T_{kernel}(n) \approx \frac{T_{kernel}(1)}{n} + \epsilon_{mem}$$

donde $\epsilon_{mem}$ representa el cuello de botella en ancho de banda de memoria, que si es lineal en $n$.

Pero hay un costo: la espera. Si una peticion llega sola, el servidor espera $d_{batch}$ microsegundos a que se acumulen otras. Esa espera tiene que ser menor que el beneficio de throughput. El delay window optimo en Tritonserver se configura en config.pbtxt:

dynamic_batching {
  max_queue_delay_microseconds: 100
  preferred_batch_size: [ 4, 8, 16 ]
}

El servidor agota la ventana de $d_{batch}$ para acumular el mayor batch posible, respetando las preferred sizes que tu GPU traga sin degradacion de latencia.

2. Como tritonserver resuelve esto por vos

                          ┌──────────────────────────────────┐
   HTTP :8000  ─────────►  │ Triton C++ HTTP Frontend        │
   gRPC :8001  ─────────►  │ Triton C++ gRPC Frontend        │
   Metrics :8002 ───────►  │ Metrics Reporter (Prometheus)   │
                           └─────────────────┬────────────────┘
                                             │
              ┌──────────────────────────────┼──────────────────────────────┐
              ▼                              ▼                              ▼
     ┌──────────────────┐          ┌──────────────────┐          ┌──────────────────┐
     │ Scheduler ResNet │          │ Scheduler LLM 7B │          │ Scheduler Custom │
     │ max_batch=64     │          │ max_batch=8      │          │ Python backend   │
     └────────┬─────────┘          └────────┬─────────┘          └────────┬─────────┘
              │                            │                              │
              ▼                            ▼                              ▼
          [ GPU 0 ]                     [ GPU 1 ]                   [ GPU 0 / CPU ]

El corazon de Triton es un scheduler por modelo. Cada modelo cargado tiene su propio scheduler con una cola de peticiones, una politica de batching, y un pool de instancias asignadas a dispositivos (GPU idx, MIG slice, CPU). Las peticiones se deserializan (protobuf si gRPC, JSON si HTTP), se encolan en su scheduler, y cada scheduler decide cuando ejecutar.

Los backends son modulos cargables (.so en Linux) que implementan la interfaz abstracta TritonBackend. NVIDIA distribuye oficialmente:

Backend Formato de modelo Caso de uso tipico
tensorrt .plan (engine serializado) Max throughput, INT8 cuantizado
onnxruntime .onnx Interoperabilidad, modelos exportados
pytorch model.pt con torch.compile Modelos PyTorch sin conversion
tensorflow model.savedmodel Legacy TFX pipelines
python model.py con decoradores Triton Pre/postprocesamiento custom, ensemble
openvino .xml + .bin Hardware Intel

Ademas Triton soporta ensemble models: declaras en config.pbtxt que la salida de un modelo es la entrada de otro, sin escribir una linea de codigo de orquestacion.

3. tritonserver: Uso Directo y Casos de Control Fino

3.1 El container oficial

La forma mas rapida de arrancar:

# Pull del container estable
docker pull nvcr.io/nvidia/tritonserver:24.08-py3

# Crear el model repository (estructura versionada)
mkdir -p model_repository/resnet50/1
cp resnet50.onnx model_repository/resnet50/1/model.onnx

# Lanzar exponiendo 2 GPUs y volumen de modelos
docker run --gpus=all \
  --shm-size=1g --ulimit memlock=-1 --ulimit stack=67108864 \
  -p8000:8000 -p8001:8001 -p8002:8002 \
  -v $(pwd)/model_repository:/models \
  nvcr.io/nvidia/tritonserver:24.08-py3 \
  tritonserver --model-repository=/models \
               --log-verbose=1 \
               --strict-model-config=true

El flag --log-verbose=1 es brutal para debugging inicial: te muestra cada carga de modelo, cada intento de allocation, y cada error de backend con traceback completo. strict-model-config=true obliga a que TODOS los modelos tengan config.pbtxt (no fallback a auto-deteccion), lo cual es deseable en produccion.

3.2 Cuando SI bajes al cliente C++ (control de latencia)

Si necesitas control fino (por ejemplo, en un pipeline de video a 60 FPS donde cada milisegundo cuenta), el cliente C++ de Triton te permite hacer inference asincrona y compartir CUDA streams:

#include <triton/core/tritonserver.h>
namespace tc = triton::client;

int main() {
  std::unique_ptr<tc::InferenceServerGrpcClient> client;
  tc::InferenceServerGrpcClient::Create("localhost:8001", false, &client);

  // Verificar readiness antes de aceptar trafico
  bool ready = false;
  client->IsServerReady(&ready);
  if (!ready) { return 1; }

  // Declarar peticion asincrona
  tc::InferRequest req;
  req.mutable_model()->set_name("resnet50");
  req.mutable_model()->set_version("1");

  auto* input = req.add_inputs();
  input->set_name("input__0");
  // Serializar tensor FP32 [3,224,224] y llamar AsyncInfer()...

  return 0;
}

4. Implementacion Production-Ready: el repo multi-tenant

4.1 Tipos y protocolos: model repository versionado

La estructura canonica para servir multiples modelos con versionado:

model_repository/
├── resnet50/
│   ├── 1/
│   │   └── model.onnx              # version 1 - ONNX
│   ├── 2/
│   │   └── model.plan              # version 2 - migrada a TensorRT
│   └── config.pbtxt                # config compartida para todas las versiones
├── llama_7b_int4/
│   ├── 1/
│   │   ├── model.pt                # PyTorch torch.compile
│   │   └── tokenizer.json
│   └── config.pbtxt
└── preprocessing/
    ├── 1/
    │   └── model.py                # Python backend: reescalar, normalizar
    └── config.pbtxt

4.2 El motor principal: config.pbtxt

Este archivo es donde declaras TODO: input shapes, output types, batching, optimizacion GPU, prioridad y dispositivo. Para un ResNet-50 con dynamic batching optimo:

name: "resnet50"
platform: "onnxruntime"
max_batch_size: 64

input [
  {
    name: "input__0"
    data_type: TYPE_FP32
    dims: [ 3, 224, 224 ]
  }
]

output [
  {
    name: "logits"
    data_type: TYPE_FP32
    dims: [ 1000 ]
  }
]

instance_group [
  {
    count: 2                         # 2 replicas en la misma GPU
    kind: KIND_GPU
    gpus: [ 0 ]
  }
]

dynamic_batching {
  preferred_batch_size: [ 8, 16, 32 ]
  max_queue_delay_microseconds: 200
  priority_levels: 2
  default_priority_level: 1
}

optimization {
  execution_accelerators {
    gpu_execution_accelerator: [
      { name: "tensorrt" }
    ]
  }
  output_pinned_memory: true
}

Para el LLM de 7B con prefill autoregresivo, los parametros son distintos (VRAM manda):

name: "llama_7b_int4"
platform: "pytorch_libtorch"
max_batch_size: 8

input [
  { name: "input_ids"      data_type: TYPE_INT64 dims: [ -1 ] }
  { name: "attention_mask" data_type: TYPE_INT64 dims: [ -1 ] }
]

output [
  { name: "logits" data_type: TYPE_FP32 dims: [ -1, 32000 ] }
]

instance_group [
  {
    count: 1                          # 1 instancia, GPU no aguanta mas
    kind: KIND_GPU
    gpus: [ 1 ]                       # aislada en GPU 1
  }
]

dynamic_batching { }

4.3 Utilidades de analisis y verificacion: perf_analyzer y model_analyzer

perf_analyzer viene dentro del SDK container y mide latencia vs concurrencia. Es obligatorio correrlo antes de cualquier despliegue:

# Mide p99 con 4 clientes concurrentes, batches unitarios
docker run --rm --network=host \
  nvcr.io/nvidia/tritonserver:24.08-py3-sdk \
  perf_analyzer \
    -m resnet50 \
    -b 1 --shape=input__0:3,224,224 \
    --concurrency-range=1:32 \
    --measurement-mode=count_windows \
    --measurement-request-count=2000

model_analyzer es la herramienta pesada que barre automaticamente el espacio de configuraciones (numero de instancias, batch sizes, backends, formatos de precision) midiendo throughput bajo restricciones SLO de latencia, y emite un reporte con la config recomendada. No reemplaza tu intuicion, pero te ahorra dias de prueba y error cuando tienes varios modelos candidatos.

# Instalacion y corrida tipica
pip install triton-model-analyzer
triton_model_analyzer \
  --model-repository=./model_repository \
  --client-config=./perf_analyzer.yaml \
  --profile-models=resnet50 \
  --export-path=./analysis_results

5. Ejemplos de Uso en Casos Reales

5.1 Vision pipeline multi-modelo (deteccion + clasificacion)

Para servir un pipeline donde primero pasa por YOLO, recorta las cajas detectadas, y clasifica cada recorte, lo natural es declarar un ensemble. La peticion llega una sola vez al servidor, y Triton rutea entre los dos modelos internamente.

config.pbtxt del ensemble:

name: "vision_pipeline"
platform: "ensemble"
max_batch_size: 32

input [
  { name: "RAW_IMAGE" data_type: TYPE_UINT8 dims: [ -1, -1, 3 ] }
]

output [
  { name: "DETECTIONS" data_type: TYPE_FP32 dims: [ -1, 6 ] }
]

ensemble_step {
  model_name: "yolo_v8"
  input_map  { key: "images" value: "RAW_IMAGE" }
  output_map { key: "boxes"  value: "bboxes" }
}
ensemble_step {
  model_name: "classifier"
  input_map  { key: "image" value: "RAW_IMAGE" }
  input_map  { key: "boxes" value: "bboxes" }
  output_map { key: "labels" value: "DETECTIONS" }
}

instance_group [
  { count: 1 kind: KIND_GPU gpus: [ 0 ] }
]

Cliente Python usando tritonclient.http:

import tritonclient.http as httpclient
import numpy as np

client = httpclient.InferenceServerClient(url="localhost:8000")

# Imagen raw 1080p
raw = np.random.randint(0, 255, size=(1080, 1920, 3), dtype=np.uint8)
inp = httpclient.InferInput("RAW_IMAGE", raw.shape, "UINT8")
inp.set_data_from_numpy(raw)

res = client.infer(model_name="vision_pipeline", inputs=[inp])
detections = res.as_numpy("DETECTIONS")
print(f"{len(detections)} objetos en escena")    # ej: 7 objetos

Verificacion numerica manual: si yolo_v8 retorna N cajas y classifier retorna M < N labels, hay una caja sin clasificar. Conteo esperado: detections.shape[0] == classifier_labels.shape[0].

5.2 LLM serving con control de version por tenant

Para servir el mismo LLM en dos versiones (A/B test entre INT4 y FP8) y rutear por tenant via header HTTP:

name: "llama_7b"
platform: "pytorch_libtorch"
version_policy: { latest: { num_versions: 2 } }   # mantiene v1 y v2 cargadas

input  [ { name: "input_ids" data_type: TYPE_INT64 dims: [ -1 ] } ]
output [ { name: "logits"    data_type: TYPE_FP32  dims: [ -1, 32000 ] } ]

instance_group [ { count: 1 kind: KIND_GPU gpus: [ 1 ] } ]

Cliente:

import tritonclient.http as httpclient
import numpy as np

client = httpclient.InferenceServerClient(url="localhost:8000")

# Tenant A recibe v2, tenant B recibe v1
headers = {"triton_tenant_id": "tenant_a"}
inp = httpclient.InferInput("input_ids", [128], "INT64")
inp.set_data_from_numpy(np.zeros(128, dtype=np.int64))

res = client.infer(
    model_name="llama_7b",
    inputs=[inp],
    headers=headers,
    model_version="2",        # explicito, requerido en A/B
)

Verificacion numerica manual: con cuantizacion INT4, las log-probabilidades tienen menor rango dinamico que en FP16. Si tu harness de evaluacion mide perplexity y p99 sube > 5% respecto a la version FP8, hay drift de calibracion que requiere recalibrar.

6. Debugging: Cuando Todo se Va a la Mierda

6.1 Problema: OOM al activar batching dinamico

Sintoma: el servicio cargaba bien con max_batch_size: 1, pero al subir a 32 el contenedor muere con CUDA_ERROR_OUT_OF_MEMORY en la primera peticion.

Reproduccion:

# config.pbtxt problematico
max_batch_size: 64
instance_group [ { count: 4 kind: KIND_GPU gpus: [ 0 ] } ]   # 4 replicas = 4x VRAM

Deteccion numerica: nvidia-smi -l 1 muestra consumo creciendo linealmente hasta OOM cuando llega el primer batch grande. Si el modelo pesa 4 GB, 4 replicas pesan 16 GB solo del modelo, sin contar KV cache ni activations.

Soluciones (en orden de ganancia):

  1. Bajar count en instance_group: cada instancia replica el modelo entero en VRAM. Si necesitas paralelismo, replica 2 maximo.
  2. Migrar el formato a TensorRT con enable_memory_arena=true: el plan TensorRT reusa memoria entre instancias en configuraciones avanzadas.
  3. Reducir max_batch_size: NO escala linealmente (alli viven los weights), pero si tu modelo usa atencion, el cache KV si escala con batch, y ahi es donde se va la VRAM.

6.2 Problema: Latencia p99 se dispara bajo carga concurrente

Sintoma: con 1 cliente tienes p99 = 45 ms, pero con 32 clientes concurrentes sube a 850 ms. La grafica de Prometheus parece una escalera hacia arriba.

Deteccion: corre perf_analyzer --concurrency-range=1:64 y mira donde la curva se "quiebra". Ese es tu punto de saturacion del scheduler.

perf_analyzer -m resnet50 \
  --shape=input__0:3,224,224 \
  --concurrency-range=1:64 \
  --measurement-mode=count_windows \
  --measurement-request-count=2000 \
  --latency-report-file=latency_report.json

Solucion: en config.pbtxt baja max_queue_delay_microseconds y desactiva niveles de prioridad:

dynamic_batching {
  max_queue_delay_microseconds: 50      # antes: 200
  preferred_batch_size: [ 4, 8 ]         # reducir el "sweet spot"
}
priority_levels: 1                        # antes: 2

Explicacion cuantitativa: cuando el delay es alto, peticiones de baja latencia quedan en cola esperando mas carga. Bajar el delay sacrifica throughput pero recupera p99. Es el trade-off clasico de una cola M/M/c con servidor finito.

6.3 Problema: Backend Python falla silenciosamente en warmup

Sintoma: el modelo carga (server_status dice "ready"), pero la primera peticion tarda 30 segundos y se cae con timeout.

Causa tipica: el backend Python no compila ni aloca caches hasta la primera invocacion. La primera peticion paga el costo del warmup.

Deteccion: en logs verbose busca Execution context is not initialized antes del timeout.

Solucion: declarar entradas y salidas de warmup en config.pbtxt:

name: "custom_model"
platform: "python"
input  [ { name: "x" data_type: TYPE_FP32 dims: [ -1, 784 ] } ]
output [ { name: "y" data_type: TYPE_FP32 dims: [ -1, 10  ] } ]

model_warmup_input [
  {
    name: "x"
    batch_size: 8
    random_data: true
  }
]
model_warmup_output [
  {
    name: "y"
    batch_size: 8
    random_data: true
  }
]

Y en el model.py:

import numpy as np
import triton_python_backend as tpb

class TritonPythonModel:
    def initialize(self, args):
        # Compilar el grafo aqui, ANTES de la primera peticion real
        self.model = load_your_model()
        # Warmup explicito
        dummy = np.random.rand(8, 784).astype(np.float32)
        _ = self.model.predict(dummy)

    def execute(self, requests):
        responses = []
        for req in requests:
            x = req.get_input_tensor("x").as_numpy()
            y = self.model.predict(x)
            out = tpb.Tensor("y", y.astype(np.float32))
            responses.append(tpb.InferenceResponse([out]))
        return responses

7. Optimizaciones de Produccion

7.1 Concurrent model execution para mix de workloads

Si tienes un modelo "bestia" (LLM 7B) que usa 90% de la GPU y un modelo "raton" (clasificador chico) que usa 2%, lo natural es separarlos en GPUs distintas. Pero ¿que pasa cuando el raton recibe picos de trafico y el LLM esta idle? Habilitas priority levels y model rate limiter:

# Clasificador: priority alta, rate limited
instance_group [
  {
    count: 1
    kind: KIND_GPU
    gpus: [ 0 ]
    rate_limiter {
      resources [ { name: "R1" count: 10 } ]    # limita compute priority
    }
  }
]
# LLM: priority baja, pero ejecuciones largas
dynamic_batching {
  priority_levels: 3
  default_priority_level: 2
}

El scheduler del LLM cede GPU cycles cuando llegan peticiones del clasificador. No es perfecto — el aislamiento real requiere MPS o MIG — pero te salva de tener que escribir un orquestador custom.

7.2 Response cache para modelos deterministas

Si tu modelo es determinista (sin dropout, sin sampling aleatorio, mismo input = mismo output), Tritonserver puede cachear respuestas identicas:

response_cache {
  enable: true
  cache_size: 104857600      # 100 MB de cache
}

Caso tipico: recomendaciones para usuarios cold-start donde el mismo embedding de entrada se consulta multiples veces en una ventana de segundos. La ganancia esperada es 30-50% en throughput bajo trafico repetitivo.

Trade-off: memoria RAM del proceso servidor vs latencia en cache hits. No lo uses para LLMs (el espacio de estados es efectivamente infinito y el cache hit rate sera 0.001%).

8. Conclusion: Por Que Esto te Salva el Pellejo en Produccion

Resumen ejecutivo, sin relleno:

  • Un solo servidor, multiples modelos: olvidaste coordinar N FastAPIs, cada uno con su Dockerfile y su health check distinto. Ahorro de complejidad: enorme.
  • Dynamic batching optimo sin tocar cliente: el throughput sube 3-8x automaticamente segun patron de trafico real.
  • Backends intercambiables: migras ResNet de ONNX a TensorRT sin cambiar una linea del cliente. Mismo model_name, misma firma de I/O.
  • Metricas Prometheus nativas en :8002/metrics: p99, qps, GPU util, queue depth, cache hits. Sale listo para Grafana.
  • Versionado y A/B testing declarativo en config.pbtxt: dos versiones del mismo modelo conviviendo, etiquetadas por header o por query parameter.

Mini-checklist antes de poner Triton en produccion:

# 1. Validar que el server carga limpio
curl -s localhost:8000/v2/health/ready | jq

# 2. Confirmar modelos loaded (no "unloaded")
curl -s localhost:8000/v2/models/resnet50/ready | jq

# 3. Benchmark con carga realista
docker run --rm --network=host \
  nvcr.io/nvidia/tritonserver:24.08-py3-sdk \
  perf_analyzer -m resnet50 --concurrency-range=1:64 --shape=input__0:3,224,224

# 4. Saturar con vegeta o locust de tu trafico real por 15 min, medir p99/mem
vegeta attack -duration=15m -rate=200 -targets=requests.bin | vegeta report

# 5. Alertar cuando VRAM llegue al 80% (antes del OOM)
watch -n 5 'nvidia-smi --query-gpu=memory.used,memory.total --format=csv'

Al toque, parcero: si hoy tienes tres o mas modelos sirviendo en produccion sobre la misma infra, no hay fiesta, te toca migrar a Triton. Es de las pocas piezas de MLOps que se justifica por si sola desde el primer dia.
