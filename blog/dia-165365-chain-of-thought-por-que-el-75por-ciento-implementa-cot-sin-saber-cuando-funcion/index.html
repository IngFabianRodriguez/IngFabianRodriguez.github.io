🚀 Por Qué vLLM Cambia El Juego

El problema fundamental con HuggingFace Transformers para serving es que maneja la memoria GPU como si fuera memoria RAM en los 90s: todo o nada, sin paginación, sin compartir. Cada request que llega necesita alojar el KV cache completo en VRAM, y cuando la GPU se llena... pues ahí empieza el swapping y la tristeza.

vLLM introduce PagedAttention, un mecanismo inspirado en la memoria virtual de los sistemas operativos. La idea es simple pero profunda: en vez de asignar bloques contiguos de memoria para el KV cache, vLLM usa bloques de tamaño fijo (típicamente 16 tokens por bloque) que pueden estar dispersos en memoria física pero lógicamente contiguos.

El Math Detrás de PagedAttention

En atención estándar, el KV cache para una secuencia de longitud $L$ ocupa:

$$\text{KV cache size} = 2 \times n_{\text{layers}} \times n_{\text{heads}} \times d_{\text{head}} \times L \times 4 \text{ bytes}$$

Donde el factor 2 es por K y V. Para un LLaMA-7B con 32 capas, 32 heads, y $d_{\text{head}} = 128$:

$$\text{KV cache} = 2 \times 32 \times 32 \times 128 \times L \times 4 \approx 1 \text{ MB por token}$$

Una secuencia de 2048 tokens ocupa ~2 GB solo en KV cache. Con atención paginada, solo alocamos lo que usamos, y el resto de la VRAM queda disponible para más requests simultáneos.

Serving con vLLM (el correcto)

from vllm import LLM, SamplingParams

# Inicialización - una sola vez al inicio del servidor
llm = LLM(
    model="meta-llama/Llama-2-7b-chat-hf",
    gpu_memory_utilization=0.85,  # ¡Clave! Por defecto es 0.9
    tensor_parallel_size=1,        # Para múltiples GPUs: 2, 4, etc.
    max_model_len=4096,           # Ajusta según tu VRAM
    trust_remote_code=True,
)

sampling_params = SamplingParams(
    temperature=0.7,
    top_p=0.95,
    max_tokens=512,
)

# Inference - esto es 10-24x más rápido que HF en throughput
outputs = llm.generate(["¿Por qué el cielo es azul?", "Explica la fotosíntesis"], sampling_params)

for output in outputs:
    print(f"Prompt: {output.prompt}")
    print(f"Generado: {output.outputs[0].text}")
    print(f"Throughput: {output.outputs[0].token_ids.__len__()} tokens")

Lo Que NO Debes Hacer (HuggingFace en Producción)

# ❌ ESTO ES LO QUE EL 90% HACE Y SUFRE EN PRODUCCIÓN
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model_name = "meta-llama/Llama-2-7b-chat-hf"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16,
    device_map="auto",
)

# Cada request crea un nuevo pipeline - Catastrófico para concurrency
def generate_hf(prompt: str) -> str:
    inputs = tokenizer(prompt, return_tensors="pt").to("cuda")
    outputs = model.generate(**inputs, max_new_tokens=512)
    return tokenizer.decode(outputs[0], skip_special_tokens=True)

# En producción con 100 requests concurrentes: GPU OOM o tiempos de respuesta de 30+ segundos

Benchmark Comparativo

import time
import asyncio
from vllm import LLM, SamplingParams

async def benchmark_vllm():
    llm = LLM(model="meta-llama/Llama-2-7b-chat-hf", gpu_memory_utilization=0.85)
    sampling = SamplingParams(temperature=0.7, max_tokens=256)
    
    prompts = [f"Pregunta {i}: Explica algo interesante sobre el tema {i % 10}" for i in range(100)]
    
    start = time.time()
    # vLLM procesa en batches automáticamente
    outputs = llm.generate(prompts, sampling)
    elapsed = time.time() - start
    
    total_tokens = sum(len(o.outputs[0].token_ids) for o in outputs)
    print(f"vLLM: {total_tokens/elapsed:.1f} tokens/segundo")
    print(f"Tiempo total: {elapsed:.2f}s para {len(prompts)} prompts")

asyncio.run(benchmark_vllm())

# Resultados típicos en A100 40GB:
# vLLM:  ~180-240 tokens/segundo (throughput)
# HF:    ~15-25 tokens/segundo (throughput)
# Speedup: 10-15x en throughput real

⚙️ Configuración de gpu_memory_utilization

Este parámetro es probablemente el más malentendido de vLLM. No es "porcentaje de VRAM a usar" de forma naive — es más complejo:

# Configuración CORRECTA según tu hardware
configurations = {
    "A100-40GB": {
        "gpu_memory_utilization": 0.90,
        "max_model_len": 8192,
    },
    "A100-80GB": {
        "gpu_memory_utilization": 0.95,
        "max_model_len": 16384,
    },
    "RTX-3090-24GB": {
        "gpu_memory_utilization": 0.85,
        "max_model_len": 4096,
    },
    "RTX-4090-24GB": {
        "gpu_memory_utilization": 0.88,
        "max_model_len": 4096,
    },
}

# ❌ ERROR COMÚN: Dejar el默认值 sin ajustar
# Esto causa OOM en GPUs con menos de 80GB
llm = LLM(model="meta-llama/Llama-2-70b-hf", gpu_memory_utilization=0.9)  # ¡Falla!

# ✅ CORRECTO: Calcular basado en tu modelo y VRAM
# Para 70B en 4x A100 (320GB total), usa:
llm = LLM(
    model="meta-llama/Llama-2-70b-hf",
    tensor_parallel_size=4,
    gpu_memory_utilization=0.85,  # Deja margen para el sistema operativo
    max_model_len=4096,
)

🔧 Tensor Parallel Para Modelos Grandes

Cuando tu modelo no cabe en una sola GPU, tensor parallelism divide los pesos de las capas de atención a través de múltiples GPUs:

from vllm import LLM

# Modelo que requiere 70GB+ - no cabe en una A100
# Distribución: 70B / 4 GPUs = ~17.5GB por GPU

llm = LLM(
    model="meta-llama/Llama-2-70b-chat-hf",
    tensor_parallel_size=4,      # Número de GPUs (debe ser divisor de num_heads)
    pipeline_parallel_size=1,    # Para más de 8 GPUs, combina con pipeline parallel
    gpu_memory_utilization=0.80, # Más bajo porque hay overhead de comunicación
    max_model_len=4096,
)

🚨 Los 3 Errores que el 90% Comete

Error 1: Usar HuggingFace Transformers en Producción

Este es el error más básico pero más costoso. HF fue diseñado para training y experimentación, no para serving en producción. El throughput que obtienes con HF es típicamente 10-15x menor que con vLLM para la misma hardware.

Fix: Si tienes más de 10 requests/hora en producción, usa vLLM. Siempre. La inversión en migración se paga en reducción de costos de GPU en la primera semana.

Error 2: No Configurar gpu_memory_utilization Correctamente

Dejar gpu_memory_utilization=0.9 sin calcular si realmente tienes ese margen causa OOM crashes en producción. El sistema operativo, drivers de CUDA, y otros procesos también necesitan VRAM.

# ✅ FIX CORRECTO: Calcular antes de lanzar
import torch

def calculate_optimal_config(model_name: str, num_gpus: int):
    total_vram_gb = torch.cuda.get_device_properties(0).total_memory / 1e9 * num_gpus
    
    # Estimar VRAM del modelo
    # Parámetros * 2 bytes (fp16) * 1.2 overhead multiplicativo
    model_vram_estimate_gb = 7 * 1.2  # Ejemplo para 7B model
    
    # Para KV cache y overhead
    available_for_util = (total_vram_gb - 2) / total_vram_gb  # 2GB para sistema
    
    return {
        "gpu_memory_utilization": min(0.92, available_for_util * 0.95),
        "max_model_len": min(4096, int((available_for_util * total_vram_gb * 1e9) / (1e6))),
    }

config = calculate_optimal_config("meta-llama/Llama-2-7b-chat-hf", 1)
print(f"Configuración óptima: {config}")

Error 3: No Usar Tensor Parallel Para Modelos > 13B

Tweet esto: si estás intentando cargar un LLaMA-70B en una sola A100 40GB, no es que "no funcione", es que estás usando el hardware equivocado o la técnica equivocada. Tensor parallel existe por una razón.

# ✅ FIX: Si tu modelo no cabe, usa tensor parallel
# 70B modelo en 4x A100 40GB
# Cada GPU recibe: 70B / 4 = 17.5B parámetros
# Con fp16: 17.5B * 2 bytes = 35GB por GPU
# ¡Cabe! (justo, pero cabe)

# ❌ NO HAGAS ESTO - Intentar forzar todo en una GPU
llm = LLM(model="meta-llama/Llama-2-70b-hf", tensor_parallel_size=1)  # OOM garantizada

# ✅ HAZ ESTO - Distribución inteligente
llm = LLM(
    model="meta-llama/Llama-2-70b-hf",
    tensor_parallel_size=4,  # 4 GPUs para el 70B
    gpu_memory_utilization=0.82,  # Un poco más bajo por el overhead de TP
)

📊 Resumen: vLLM vs HuggingFace Transformers

  • Throughput: vLLM ofrece 10-24x más tokens/segundo que HF para inference
  • Memoria: PagedAttention reduce el KV cache overhead en 40-60%
  • Concurrency: vLLM maneja cientos de requests simultáneos; HF se ahoga
  • PagedAttention: Inspirado en memoria virtual, bloques de 16 tokens, compartir entre requests
  • Tensor Parallel: Essential para modelos >13B, divide pesos entre GPUs
  • gpu_memory_utilization: No es "usar X% de VRAM", es una política de allocation
