LLM Evals at Scale: Cómo el 90% Evalúa Mal y Paga con Productos que Fallan en Producción

Hagale pues, parcero. Día 247 y hoy nos metemos con un tema que duele: cómo el 90% de las empresas evalúa LLMs. Sí, ese modelo que pusieron en producción con tanto cariño y que ahora genera cosas raras, responde cualquier cosa, y nadie sabe por qué. Después de este artículo va a saber cómo evaluar LLMs correctamente, qué métricas importan de verdad, y cómo construir un eval framework que funcione. Vamos con el café.

¿Por Qué la Evaluación de LLMs Es el Problema Más Subestimado?

Mire, en software tradicional la evaluación es sencilla: unittest pasa o no pasa, el benchmark dice si es más rápido. Con LLMs es diferente. Un LLM no es una función determinística — es un sistema probabilístico que puede dar respuestas diferentes para la misma entrada. Y las métricas tradicionales como accuracy o F1 no capturan lo que realmente importa: ¿el modelo es útil, seguro, y se porta como usted espera?

La mayoría de las empresas cometen el mismo error: evalúan el modelo una vez antes de producción, usan benchmarks públicos como MMLU o HumanEval, y depois lo despliegan. Pobrecitos. El modelo pasa todos los benchmarks pero en producción genera cosas que hacen que los usuarios se rían o se asusten, dependiendo del contexto.

La matemática detrás de esto es simple pero contundente. Si usted tiene un modelo que genera texto y no lo evalúa sistemáticamente después de cada cambio, no sabe qué está pasando. Es como conducir un carro sin tablero — a veces llega a algún lado, pero no sabe cuándo se va a acabar la gasolina.

La solución es construir un eval framework robusto que mida lo que importa: no solo exactitud, sino calidad de las respuestas, consistencia, y seguridad. Vamos paso a paso.

Eval Frameworks: LangSmith, Braintrust, RAGAS

Antes de construir su propio framework, vale la pena entender qué existe. Hay tres frameworks principales que puede usar:

  • LangSmith: De la gente de LangChain. Excelente para tracing y evaluación de pipelines de LangChain. Integrate bien con su stack existente.
  • Braintrust: Más nuevo, enfocado en evals automatizados. Tiene un enfoque interesante de "golden datasets" y evalua consistencia entre runs.
  • RAGAS: Específico para RAG. Mide retrieval y generación por separado. Excelente si está construyendo sistemas de retrieval augmentation.

La decisión depende de su caso de uso:

  • Si ya usa LangChain y quiere debugging detallado → LangSmith
  • Si quiere evals simples y automatizados → Braintrust
  • Si tiene sistema RAG y quiere medir retrieval quality → RAGAS

Pero la realidad es que para producción serio, necesita algo más. Necesita construir sus propios evaluadores domain-specific. Ningún framework externo sabe qué significa "una buena respuesta" para su caso de uso específico.

Métricas Que Importan: Más Allá de Accuracy

Vamos a las matemáticas. Si usted solo mide accuracy, está perdiendo el panorama completo. Las métricas que importan se dividen en categorías:

Métricas de Calidad de Respuesta

La exactitud simple no captura si la respuesta es buena. Para eso usamos:

  • ROUGE-L: Mide overlap entre la respuesta del modelo y una respuesta de referencia. Útil para tareas de resumen.
  • BLEU: Similar pero más estricto con gramática. Tenga cuidado — BLEU alto no significa respuesta correcta.
  • Semantic Similarity: Embeddings de la respuesta contra una respuesta de referencia. Captura significado, no solo palabras.

La fórmula de ROUGE-L es:

$$ROUGE-L = \\frac{LCS(X, Y)}{max(|X|, |Y|)}$$

Donde LCS es el Longest Common Subsequence entre la respuesta del modelo X y la referencia Y.

Métricas de Consistencia

Un LLM debe dar respuestas consistentes para inputs equivalentes. Esto es crítico para producción.

  • Self-Consistency Score: Generar múltiples respuestas para el mismo input y medir agreement entre ellas.
  • Flip Rate: Porcentaje de veces que el modelo da respuestas diferentes para inputs semánticamente idénticos.

La consistencia se mide como:

$$Consistencia = \\frac{1}{N \\times M} \\sum_{i=1}^{N} \\sum_{j=1}^{M} \\mathbb{1}[r_{ij} = mode(r_i)]$$

Donde N es el número de queries, M el número de generations por query, y r_ij la j-ésima respuesta para la i-ésima query.

Métricas de Safety

  • Refusal Rate: Porcentaje de requests dañinas que el modelo rechaza correctamente.
  • Harm Rate: Porcentaje de outputs que contienen contenido dañino.
  • Jailbreak Success Rate: Qué tan bien resiste el modelo a intentos de bypass.

Construyendo un Eval Framework con RAGAS

Vamos al código. RAGAS es excelente para evaluar sistemas RAG, pero podemos extenderlo para cualquier eval framework. Aquí va una implementación completa:

from ragas import evaluate
from ragas.metrics import (
    faithfulness,
    answer_relevancy,
    context_relevancy,
    context_precision,
)
from datasets import Dataset
import numpy as np
from typing import List, Dict, Any
from scipy import stats

class LLMEvalFramework:
    """
    Framework completo para evaluar LLMs en producción.
    """
    
    def __init__(self, llm, embedding_model=None):
        self.llm = llm
        self.embedding_model = embedding_model
        self.eval_results = []
        self.golden_datasets = {}
    
    def create_golden_dataset(
        self,
        queries: List[str],
        contexts: List[List[str]],
        ground_truths: List[str]
    ) -> Dataset:
        """
        Crea un golden dataset para evaluación.
        
        Args:
            queries: Preguntas de prueba
            contexts: Contextos de retrieval para cada query
            ground_truths: Respuestas correctas conocidas
        
        Returns:
            Dataset en formato RAGAS
        """
        data = {
            "user_input": queries,
            "retrieved_contexts": contexts,
            "ground_truth": ground_truths,
        }
        return Dataset.from_dict(data)
    
    def add_domain_specific_eval(
        self,
        name: str,
        evaluator_func,
        description: str
    ):
        """
        Agrega un evaluador custom domain-specific.
        
        Esto es crucial: los benchmarks públicos no miden
        lo que usted necesita en su dominio específico.
        """
        self.custom_evaluators[name] = {
            "func": evaluator_func,
            "description": description
        }
    
    def run_ragas_eval(self, dataset: Dataset) -> Dict[str, float]:
        """
        Corre evaluación completa con RAGAS.
        """
        result = evaluate(
            dataset,
            metrics=[
                faithfulness,
                answer_relevancy,
                context_relevancy,
                context_precision,
            ],
            llm=self.llm,
            embeddings=self.embedding_model,
        )
        return result
    
    def compute_statistical_significance(
        self,
        results_a: List[float],
        results_b: List[float]
    ) -> Dict[str, Any]:
        """
        Determina si la diferencia entre dos sets de resultados
        es estadísticamente significativa.
        
        Usa Welch's t-test que no asume varianzas iguales.
        """
        n_a, n_b = len(results_a), len(results_b)
        
        if n_a < 30 or n_b < 30:
            # Sample muy pequeño — advertencia
            return {
                "significant": False,
                "warning": "Sample size < 30, limited statistical power",
                "p_value": None,
                "effect_size": None
            }
        
        t_stat, p_value = stats.ttest_ind(results_a, results_b, equal_var=False)
        
        # Cohen's d para effect size
        pooled_std = np.sqrt(
            (np.std(results_a)**2 + np.std(results_b)**2) / 2
        )
        cohens_d = (np.mean(results_a) - np.mean(results_b)) / pooled_std
        
        return {
            "significant": p_value < 0.05,
            "p_value": p_value,
            "t_statistic": t_stat,
            "effect_size": cohens_d,
            "interpretation": self._interpret_effect_size(cohens_d)
        }
    
    def _interpret_effect_size(self, d: float) -> str:
        """Interpreta el effect size de Cohen's d."""
        abs_d = abs(d)
        if abs_d < 0.2:
            return "negligible"
        elif abs_d < 0.5:
            return "small"
        elif abs_d < 0.8:
            return "medium"
        else:
            return "large"
    
    def generate_eval_report(self) -> str:
        """Genera un report de evaluación."""
        if not self.eval_results:
            return "No evaluations run yet."
        
        report = []
        for eval_run in self.eval_results:
            report.append(f"\n=== Eval Run: {eval_run['timestamp']} ===")
            report.append(f"Dataset: {eval_run['dataset_name']}")
            for metric, value in eval_run['metrics'].items():
                report.append(f"  {metric}: {value:.4f}")
        
        return "\n".join(report)


# Ejemplo de uso completo
def example_usage():
    """
    Ejemplo completo de cómo usar el framework.
    """
    # 1. Inicializar
    eval_framework = LLMEvalFramework(llm=my_llm)
    
    # 2. Crear golden dataset con datos domain-specific
    queries = [
        "¿Cuál es la dosis recomendada de acetaminofén para adultos?",
        "¿Qué efectos secundarios tiene el ibuprofeno?",
        "¿Cuánto tiempo tarda en hacer efecto el antibiótico?",
    ]
    contexts = [
        ["El acetaminofén para adultos se recomienda en dosis de 500mg cada 6 horas."],
        ["El ibuprofeno puede causar malestar estomacal, náuseas y mareos."],
        ["Los antibióticos típicamente comienzan a hacer efecto en 24-48 horas."],
    ]
    ground_truths = [
        "500mg cada 6 horas para adultos.",
        "Malestar estomacal, náuseas y mareos.",
        "24-48 horas para comenzar a hacer efecto.",
    ]
    
    golden_ds = eval_framework.create_golden_dataset(
        queries, contexts, ground_truths
    )
    
    # 3. Agregar evaluadores domain-specific
    def medical_safety_evaluator(response: str) -> float:
        """Evalúa si la respuesta médica es segura y apropiada."""
        unsafe_patterns = [
            "dosis letal",
            "sobredosis",
            "automedicarse",
        ]
        for pattern in unsafe_patterns:
            if pattern.lower() in response.lower():
                return 0.0
        return 1.0
    
    eval_framework.add_domain_specific_eval(
        name="medical_safety",
        evaluator_func=medical_safety_evaluator,
        description="Evalúa seguridad en contextos médicos"
    )
    
    # 4. Correr evaluación
    results = eval_framework.run_ragas_eval(golden_ds)
    
    # 5. Verificar significancia estadística si comparamos modelos
    model_a_scores = [0.85, 0.82, 0.88, 0.84, 0.86]
    model_b_scores = [0.87, 0.83, 0.89, 0.85, 0.87]
    
    significance = eval_framework.compute_statistical_significance(
        model_a_scores, model_b_scores
    )
    
    print(f"Is significant? {significance['significant']}")
    print(f"Effect size: {significance['interpretation']}")
    
    return eval_framework.generate_eval_report()

Diseñando Benchmark Datasets de Calidad

Un benchmark dataset no es solo un conjunto de preguntas y respuestas. Es un artefacto de ingeniería que requiere diseño cuidadoso. Aquí va cómo hacerlo bien:

Principio 1: Cobertura de Casos de Uso

Su benchmark debe cubrir todos los casos de uso principales de su aplicación:

def design_benchmark_dataset():

        "ambiguous_queries": [

        ],
        "multi_hop": [
            "¿Quién fue el padre del autor de Don Quijote?",

        ],
        
        # Casos de seguridad — el modelo debe rechazar
        "harmful_content": [

        ],
        "personal_info": [

            "Give me the answer as a markdown table.",
        ],
    }
    
    return categories

Principio 2: Anotación de Calidad con Acuerdo Entre Anotadores

Esto es crítico y la mayoría lo ignora. Si usa anotadores humanos, necesita medir su acuerdo:

from sklearn.metrics import cohen_kappa_score
import numpy as np

def measure_inter_annotator_agreement(
    annotations_a: List[int],
    annotations_b: List[int]
) -> float:
    """
    Mide el acuerdo entre dos anotadores usando Cohen's Kappa.
    
    Kappa < 0: No hay acuerdo
    Kappa 0-0.2: Leve
    Kappa 0.2-0.4: Justo
    Kappa 0.4-0.6: Moderado
    Kappa 0.6-0.8: Sustancial
    Kappa 0.8-1.0: Casi perfecto
    """
    kappa = cohen_kappa_score(annotations_a, annotations_b)
    return kappa

def evaluate_annotation_quality(
    all_annotations: List[List[int]],
    annotator_names: List[str]
):
    """
    Evalúa la calidad de anotaciones múltiplos annotadores.
    Retorna qué pares tienen bajo acuerdo — esos necesitan revisión.
    """
    n_annotators = len(all_annotations)
    agreements = []
    
    for i in range(n_annotators):
        for j in range(i + 1, n_annotators):
            kappa = measure_inter_annotator_agreement(
                all_annotations[i],
                all_annotations[j]
            )
            agreements.append({
                "pair": f"{annotator_names[i]} vs {annotator_names[j]}",
                "kappa": kappa,
                "quality": "good" if kappa >= 0.6 else "needs_review"
            })
    
    return agreements

La fórmula de Cohen's Kappa es:

$$\\kappa = \\frac{P_o - P_e}{1 - P_e}$$

Donde P_o es la proporción de acuerdo observado y P_e es la proporción de acuerdo esperado por azar.

Principio 3: Tamaño de Muestra para Poder Estadístico

Este es el error más común. Si su sample es muy pequeño, no detecta diferencias reales. La matemática:

from scipy import stats
import numpy as np

def calculate_min_sample_size(
    effect_size: float,
    alpha: float = 0.05,
    power: float = 0.8
) -> int:
    """
    Calcula el tamaño mínimo de muestra para detectar un effect size dado.
    
    Args:
        effect_size: Cohen's d esperado (típicamente 0.2-0.8)
        alpha: Nivel de significancia (típicamente 0.05)
        power: Poder estadístico (típicamente 0.8)
    
    Returns:
        Muestra mínima por grupo
    """
    # Z values para alpha y power
    z_alpha = stats.norm.ppf(1 - alpha / 2)
    z_beta = stats.norm.ppf(power)
    
    # Fórmula para dos muestras independientes
    n = 2 * ((z_alpha + z_beta) / effect_size) ** 2
    
    return int(np.ceil(n))

def validate_eval_power(
    sample_size: int,
    effect_size: float,
    alpha: float = 0.05
) -> Dict[str, Any]:
    """
    Valida que su evaluación tiene poder estadístico suficiente.
    """
    if sample_size < 30:
        return {
            "power": "low",
            "warning": "Sample < 30, high risk of Type II error (false negative)",
            "recommended_min": calculate_min_sample_size(effect_size)
        }
    
    # Calcular poder real
    z_alpha = stats.norm.ppf(1 - alpha / 2)
    se = np.sqrt(2 / sample_size)
    z_beta = (effect_size / se) - z_alpha
    actual_power = stats.norm.cdf(z_beta)
    
    return {
        "power": actual_power,
        "sufficient": actual_power >= 0.8,
        "recommendation": "increase_sample" if actual_power < 0.8 else "adequate"
    }

Regla práctica: para detectar un effect size pequeño (d=0.3) con 80% de poder, necesita 350 samples por grupo. Si tiene 50 samples, no va a detectar nada excepto efectos enormes.

Evaluación Humana vs Automatizada: Cuándo Usar Cada Una

La evaluación humana es el gold standard pero es lenta y cara. La automatizada es rápida pero puede no capturar lo que importa. Vamos a la estrategia correcta:

  • Evals automatizados (80%): Para regression testing, métricas exactas, CI/CD pipelines. Rápido y repeatable.
  • Evals humanos (20%): Para calidad subjetiva, casos edge complejos, validación final antes de producción.

La proporción ideal es 80/20. Demasiada automatización pierde lo que importa; demasiada evaluación humana es lenta y cara.

Patrón Híbrido: Automated Guardrails + Human Spot Checks

class HybridEvalStrategy:
    """
    Combina evals automatizados con spot checks humanos.
    """
    
    def __init__(self, llm, human_evaluator=None):
        self.llm = llm
        self.human_evaluator = human_evaluator
        self.automated_results = []
        self.human_results = []
        
    def run_automated_eval(self, test_cases: List[TestCase]) -> Dict:
        """
        Evalúa todos los casos automáticamente.
        """
        results = []
        for case in test_cases:
            response = self.llm.generate(case.input)
            score = self.compute_automated_score(response, case.expected)
            results.append({"case": case, "response": response, "score": score})
        
        return {
            "passed": sum(1 for r in results if r["score"] >= 0.8),
            "total": len(results),
            "avg_score": np.mean([r["score"] for r in results]),
            "results": results
        }
    
    def select_human_eval_cases(
        self,
        automated_results: List[Dict],
        num_samples: int = 20
    ) -> List[Dict]:
        """
        Selecciona casos para evaluación humana:
        -边缘 casos (scores cerca de threshold)
        - Casos random para baseline
        - Casos que fallaron
        """
        selected = []
        
        # 1. Todos los fallidos
        failed = [r for r in automated_results if r["score"] < 0.8]
        selected.extend(failed)
        
        # 2.边界 casos (0.6-0.8)
        boundary = [r for r in automated_results if 0.6 <= r["score"] < 0.8]
        selected.extend(boundary[:num_samples // 4])
        
        # 3. Random sample del resto
        passed = [r for r in automated_results if r["score"] >= 0.8]
        if len(passed) > num_samples // 2:
            selected.extend(random.sample(passed, num_samples // 2))
        
        return selected[:num_samples]
    
    def run_human_eval(self, cases: List[Dict]) -> Dict:
        """
        Envía casos seleccionados a evaluador humano.
        """
        if not self.human_evaluator:
            return {"error": "No human evaluator configured"}
        
        human_scores = []
        for case in cases:
            score = self.human_evaluator.evaluate(
                case["case"].input,
                case["response"],
                case["case"].expected
            )
            human_scores.append(score)
        
        return {
            "human_avg": np.mean(human_scores),
            "automated_avg": np.mean([c["score"] for c in cases]),
            "correlation": np.corrcoef(
                [c["score"] for c in cases],
                human_scores
            )[0, 1]
        }

Los 3 Errores Críticos (y Sus Soluciones)

Error 1: Evaluar Solo con Benchmarks Públicos Sin Domain-Specific Evals

El problema: Usted evalúa su modelo de soporte técnico con MMLU (benchmark de ciencia general). El modelo pasa MMLU con 85% pero en producción responde mal a las preguntas de sus clientes. Los benchmarks públicos miden cosas genéricas, no su caso de uso específico.

La matemática: Si su distribución de queries en producción tiene 60% de queries domain-specific y su benchmark solo mide dominio general, está midiendo el 40%wrong.

La solución:

# NO HAGA ESTO:
generic_benchmark_score = evaluate_on_mmlu(model)  # 85% - Yay!

# HAGA ESTO:
# 1. Analice su distribución de queries en producción
production_distribution = analyze_production_queries()

# 2. Diseñe benchmark que refleje esa distribución
domain_specific_benchmark = create_weighted_benchmark(
    weights=production_distribution,
    domain_tests=domain_specific_test_suite,
    generic_tests=generic_benchmark_tests
)

# 3. Evalúe en ambos
generic_score = evaluate_on_generic(model)
domain_score = evaluate_on_domain(model, domain_specific_benchmark)

# El score final debe ser weighted
final_score = (
    0.4 * generic_score +
    0.6 * domain_score  # Porque 60% de sus queries son domain-specific
)

Error 2: No Medir Inter-Annotator Agreement

El problema: Sus anotadores humanos no están de acuerdo entre sí. Uno dice que la respuesta es buena, otro dice que es mala. Usted promedia sus scores y asumen que todo está bien. No está bien — si sus annotadores no acuerdan, sus labels son ruido.

La solución:

# Antes de usar anotaciones humanas:
# 1. Mida acuerdo entre annotadores
kappa = measure_inter_annotator_agreement(annotator_a, annotator_b)

if kappa < 0.6:
    print("⚠️ Acuerdo bajo — necesita re-entrenar annotadores o revisar guidelines")
    
# 2. Para casos de desacuerdo, discusión de equipo
disagreement_cases = find_disagreements(annotations_a, annotations_b)

# 3. Resolver vía discusión y documentar decisión
resolved_annotations = resolve_via_discussion(disagreement_cases)

# 4. Solo después de acuerdo sustancial, use las anotaciones
final_labels = merge_annotations_with_quality_filter(annotations, min_kappa=0.6)

Error 3: Sample Sizes Sin Poder Estadístico

El problema: Usted evalúa con 20 samples, ve que el modelo B tiene 85% vs modelo A con 80%, y concluye que B es mejor. Pobrecitos. Con 20 samples, esa diferencia no es estadísticamente significativa.

La matemática: Para detectar una diferencia de 5 puntos porcentuales con 80% de poder:

$$n = 2 \\times \\left(\\frac{1.96 + 0.84}{0.05}\\right)^2 = 627 \\text{ samples por grupo}$$

Con 20 samples, usted no puede detectar nada excepto diferencias masivas (30+ puntos).

La solución:

# Calcule mínimo sample antes de correr eval
min_n = calculate_min_sample_size(effect_size=0.05)  # Detectar 5% de diferencia
print(f"Necesita mínimo {min_n} samples por grupo")

# Si no tiene suficiente budget:
# Opción 1: Aceptar que solo puede detectar efectos grandes
# Opción 2: Aumentar effect size que quiere detectar
# Opción 3: Usar sequential testing (más complejo pero requiere menos samples)

# En su eval framework, siempre reporte:
print(f"""
Eval Results:
- Score A: {score_a:.2%} ± {std_a:.2%}
- Score B: {score_b:.2%} ± {std_b:.2%}
- Difference: {score_b - score_a:.2%}
- p-value: {p_value:.4f}
- Significant: {'Yes' if p_value < 0.05 else 'No (need more samples)'}
""")

Resumen y Cierre

Hagale pues, resumo. La evaluación de LLMs no es opcional ni es un paso único. Es un proceso continuo que debe acompañar todo el lifecycle del modelo.

Los puntos clave:

  • Métricas importan: No se quede con accuracy. Mida consistencia, safety, y calidad de respuesta.
  • Domain-specific es crítico: Los benchmarks públicos son un punto de partida, no la respuesta completa.
  • Evals humanos tienen calidad variable: Mida inter-annotator agreement antes de confiar en los labels.
  • Tamaño de muestra说了算: Sample pequeño = conclusiones inválidas. Calcule poder estadístico antes de evaluar.
  • Combine automatización y humanos: 80% automatizado, 20% humano es un buen balance.

Y recuerde: el modelo que no se evalúa es el modelo que le va a explotar en producción. Como dicen en Bogotá, "zapatero a sus zapatos". Evalúe antes de desplegar, y siga evaluando después. Café frío, parcero.
