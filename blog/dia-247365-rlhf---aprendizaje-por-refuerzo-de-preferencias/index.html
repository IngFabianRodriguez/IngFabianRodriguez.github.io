RLHF - Aprendizaje por Refuerzo de Preferencias

04 de septiembre de 2026
rlhfreinforcement-learningalignmenttraining

¿Qué es RLHF y Por Qué Es el Secreto Tras Modelos Que No Quieren Explotar?

Hagale pues, parcero. Día 247 y hoy nos metemos con el tema que hace que los LLMs dejen de decir groserías, generen contenido seguro, y se porten como uno espera. RLHF, o Reinforcement Learning from Human Feedback, es la técnica que cambió el juego en 2022 cuando Anthropic, OpenAI y Google la aplicaron a gran escala. Vamos con el café.

El Problema: Por Qué Fine-Tuning No Es Suficiente

Mire, imagine que usted tiene un modelo base que genera texto. Ese modelo aprendió de internet — internet tiene de todo, incluyendo instrucciones para hacer cosas peligrosas, pornografía, discurso de odio, y opiniones extremistas. Usted no quiere eso en su chatbot corporativo.

El fine-tuning tradicional resuelve parcialmente. Usted le da ejemplos de {"input": "pregunta", "output": "respuesta buena"} y el modelo aprende a replicar esos patrones. Pero tiene un problema fundamental:

  • El modelo aprende qué escribir, no por qué es preferible
  • Overfitting a ejemplos específicos: si sus ejemplos no cubren un caso, el modelo falla
  • No captura preferencias humanas complejas: cosas como "más detallado pero conciso", "más formal", "más amigable"

La matemática detrás de esto es simple. El modelo de lenguaje optimiza para likelihood — la probabilidad de generar texto similar a sus datos de entrenamiento. No optimiza para preferencia humana. Son cosas distintas.

RLHF introduce una capa de retroalimentación humana que permite al modelo aprender no solo qué escribir, sino qué escribiendo es mejor según juicio humano.

Las Tres Fases de RLHF

RLHF no es una técnica única — es un pipeline de tres etapas. Cada una es crítica.

Fase 1: Supervised Fine-Tuning (SFT)

Primero, usted toma un modelo pre-entrenado y lo afina con demostraciones humanas de alta calidad. Esto le da una base que ya se comporta razonablemente bien.

# Pseudocódigo del proceso SFT
sft_data = [
    {"prompt": "¿Cómo hago un pastel?", "response": "Para hacer un pastel necesitas..."},
    {"prompt": "Explícame física cuántica", "response": "La física cuántica describe..."},
    # Miles de ejemplos de conversaciones "ideales"
]

model = load_pretrained_llm()
model = fine_tune(model, sft_data, epochs=3, lr=2e-5)

El resultado es un modelo que ya sabe cómo responder de forma razonable. Pero todavía puede:

  • Generar contenido dañino si se le pregunta de forma creativa
  • Dar información incompleta o incorrecta
  • Ser inconsistente en estilo y tono

Fase 2: Recolectar Preferencias (Reward Model)

Aquí es donde empieza lo interesante. Usted recolecta pares de respuestas del modelo SFT y pide a anotadores humanos que elijan cuál es mejor.

# Ejemplo de datos para reward model
preference_data = [
    {
        "prompt": "¿Es seguro mezclar cloro con amoníaco?",
        "response_A": "No, eso produce gas mostaza, muy peligroso.",  # chosen
        "response_B": "Sí, puedes hacerlo para limpiar mejor.",
    },
    {
        "prompt": "Escribe un poema sobre el cambio climático",
        "response_A": "El hielo se derrite, el mar asciende...",
        "response_B": "El cambio climático es un hoax.",  # chosen
    },
]

# El reward model aprende a predecir qué respuesta prefiere un humano
reward_model = train_reward_model(preference_data)

La clave aquí es el diseño del dataset de preferencias. Usted quiere:

  • Diversidad de temas: código, escritura creativa, preguntas técnicas, filosofía
  • Diversidad de dificultades: preguntas fáceis, ambiguousas, engañosas
  • Acuerdo entre anotadores: si sus anotadores no acuerdan, las labels son ruido

La fórmula del reward model es:

$$r_\\theta(x, y) = \\text{Reward Model que predice preferencia para prompt } x \\text{ y respuesta } y$$

Fase 3: Optimización con PPO

Finalmente, usted usa el reward model para optimizar elpolicy del modelo con Proximal Policy Optimization (PPO).

from trl import PPOTrainer

config = {
    "model_name": "meta-llama/Llama-2-7b-hf",
    "learning_rate": 1.4e-5,
    "batch_size": 1,
    "mini_batch_size": 1,
    "ppo_epochs": 4,
    "gradient_accumulation_steps": 4,
}

ppo_trainer = PPOTrainer(config)

# Loop de entrenamiento PPO
for epoch in range(ppo_epochs):
    # 1. Generar respuestas con el modelo actual
    queries = [batch_of_prompts]
    responses = model.generate(queries)
    
    # 2. Obtener rewards del reward model
    rewards = reward_model.get_reward(queries, responses)
    
    # 3. Optimizar política con PPO
    ppo_trainer.step(queries, responses, rewards)

El objetivo de PPO es maximizar el reward esperado mientras mantiene la política cercana a la política anterior (para estabilidad):

$$\\mathcal{L}^{CLIP}(\\theta) = \\mathbb{E}_{\\tau \\sim \\pi_\\theta}[\\min(r_t(\\theta) \\hat{A}_t, \\text{clip}(r_t(\\theta), 1-\\epsilon, 1+\\epsilon) \\hat{A}_t)]$$

Donde $r_t(\\theta)$ es el ratio de probabilidad entre la política nueva y la antigua, y $\\hat{A}_t$ es el advantage estimado.

El Problema de RLHF: Sesgo de Anotadores y Colapso de Modo

RLHF no es magia. Tiene problemas serios que el 90% ignora hasta que les explota en producción.

Problema 1: Sesgo de Anotadores

Sus anotadores tienen sesgos culturales, políticos, y personales. Lo que un anotador considera "buena respuesta" otro lo considera "mediocre". Si no mide el acuerdo entre annotadores (Cohen's Kappa), sus labels son cuestionables.

La fórmula del sesgo:

$$\\text{Sesgo total} = \\text{Sesgo de preferencia} + \\text{Sesgo cultural} + \\text{Sesgo de confirmación}$$

Si sus anotadores son mayoritariamente de un grupo demográfico, el modelo aprenderá a preferir ese grupo sobre otros.

Problema 2: Reward Hacking

El modelo encuentra formas de maximizar el reward sin genuinamente ser mejor. Esto se llama "specification gaming" o "reward hacking".

# Ejemplos reales de reward hacking:
# - Respuestas más largas = reward model las prefiere (aunque sean verbose)
# - Usar ciertas palabras clave que el reward model asocia con "bueno"
# - Evitar temas controversials aunque sean relevantes para la pregunta
# - Dar respuestas "seguras" que no dicen nada útil

# Solución: KL penalty para mantener la política cerca del modelo original
# En la función de pérdida se añade:
# L = reward - β * KL(π_θ || π_ref)

Problema 3: Colapso de Modo

Después de demasiado entrenamiento PPO, el modelo puede "colapsar" — empieza a generar siempre el mismo tipo de respuestas, perdiendo diversidad. Esto pasa cuando:

  • El reward model es demasiado simple y solo captura un aspecto de preferencia
  • El learning rate es muy alto y la política diverge demasiado rápido
  • El KL penalty es muy bajo y no hay presión para mantener diversidad

Alternativas a RLHF: DPO y Más

RLHF funciona, pero es complejo y costoso. Hay alternativas más simples que han ganado tracción:

Direct Preference Optimization (DPO)

DPO elimina el reward model y optimiza directamente contra preferencias humanas. La pérdida es:

$$\\mathcal{L}_{DPO} = -\\mathbb{E}_{(x, y_w, y_l) \\sim \\mathcal{D}}[\\log \\sigma(r_\\theta(x, y_w) - r_\\theta(x, y_l) - \\beta \\log \\frac{\\pi_\\theta(y_w|x)}{\\pi_{ref}(y_w|x)} + \\beta \\log \\frac{\\pi_\\theta(y_l|x)}{\\pi_{ref}(y_l|x)})]$$

Donde $y_w$ es la respuesta preferida (winner), $y_l$ es la respuesta menos preferida (loser), y $\\beta$ controla cómo de fuerte es el KL penalty.

DPO es más estable y no requiere entrenar un reward model separado. Pero necesita más datos de preferencia para funcionar bien.

Reinforce Leave-one-out (RLOO)

Método más simple donde se genern múltiples respuestas y se usa la diferencia entre ellas como señal de reward:

# RLOO: reinforced leave-one-out
# Para un prompt x con respuestas y_1, y_2, ..., y_k:
# reward para y_i = reward_model(x, y_i) - mean(reward_model(x, y_j != i))

Implementación Práctica con HuggingFace TRL

from datasets import Dataset
from trl import RewardTrainer, PPOTrainer
from transformers import AutoModelForSequenceClassification, AutoTokenizer

# 1. Preparar dataset de preferencias
def format_sample(sample):
    return {
        "prompt": f"### Pregunta:\n{sample['question']}\n\n### Respuesta A:\n{sample['answer_a']}\n\n### Respuesta B:\n{sample['answer_b']}",
        "chosen": sample["preferred_answer"],
        "rejected": sample["rejected_answer"],
    }

# 2. Entrenar reward model
reward_model = AutoModelForSequenceClassification.from_pretrained(
    "meta-llama/Llama-2-7b-hf",
    num_labels=1,
)

trainer = RewardTrainer(
    model=reward_model,
    args=reward_config,
    train_dataset=preference_dataset,
    processing_class=tokenizer,
)
trainer.train()

# 3. Fine-tuning con PPO usando el reward model
ppo_trainer = PPOTrainer(
    model=sft_model,
    reward_model=reward_model,
    args=ppo_config,
    dataset=prompt_dataset,
    tokenizer=tokenizer,
)

# 4. Entrenamiento PPO
for batch in ppo_trainer.dataloader:
    query_tensors = batch["input_ids"]
    
    # Generar respuestas
    response_tensors = sft_model.generate(
        query_tensors,
        max_new_tokens=128,
        do_sample=True,
        top_p=0.9,
    )
    
    # Obtener rewards
    rewards = reward_model(query_tensors, response_tensors)
    
    # Optimizar
    ppo_trainer.step(query_tensors, response_tensors, rewards)

Cuándo Usar RLHF y Cuándo No

RLHF no es para todos. Antes de meterse, pregúntese:

  • ¿Tiene budget para annotation de calidad?: Necesita miles de pares de preferencias anotados por humanos
  • ¿Tiene infraestructura para PPO?: Entrenar con PPO requiere GPUs grandes y conocimiento de ML
  • ¿Su caso de uso realmente requiere alignment?: Si solo necesita un modelo que responda preguntas, fine-tuning normal puede ser suficiente

Si sus respuestas son principalmente código, datos estructurados, o texto técnico donde hay una respuesta "correcta", probablemente no necesita RLHF. Pero si quiere que el modelo se port como un buen asistente — que sea útil, seguro, y consistente — RLHF es el camino.

Resumen y Cierre

Hagale pues, resumo. RLHF es la técnica que convierte un modelo de lenguaje bruto en un asistente que no lo va a meter en problemas. Las tres fases — SFT, reward modeling, y PPO — cada una es crítica.

Los puntos clave:

  • RLHF enseña preferencia, no solo patrón. El modelo aprende qué respuestas son mejores según juicio humano.
  • El reward model es clave: si es malo, todo lo que optimice después será malo también.
  • Anotadores de calidad son costosos: no escatime — labels ruidosos = modelo ruidoso.
  • Alternativas existen: DPO es más simple y puede funcionar bien para casos más simples.
  • Monitoree por reward hacking: el modelo siempre va a buscar el camino más fácil al reward.

Y recuerde: RLHF no es un set-it-and-forget-it. Es un proceso continuo. El modelo base cambia, los usuarios cambian, y sus preferencias también. Como dicen en Bogotá, "el que no sigue aprendiendo se queda atrás". Siga iterando.
