Docker para ML - Por qué el 80% de los modelos funcionan en tu laptop pero no en producción

13 de april de 2026
docker

Hola, parcero. Llegamos al Día 133 y hoy vamos con un tema que me toca deep el alma: Docker para Machine Learning. Ese gap entre "funciona en mi laptop" y "funciona en producción" tiene nombre y apellido — y casi siempre se llama *entorno mal configurado*. Acá te cuento cómo resolverlo de una vez por todas, con código que de verdad deploya.

📐 Fundamentos Teóricos

¿Por qué tu modelo funciona en todas partes menos en producción?

El problema central es que tu laptop tiene un entorno Python con X versión de CUDA, Y versión de cuDNN, Z paquetes con dependencias冲突. Cuando ese mismo código llega a un servidor nuevo, las cosas se rompen de formas que ni el log revela. Docker resuelve esto creando un entorno aislado, portable y versionado que incluyes con tu código.

Contenedores vs Imágenes

  • Imagen: plantilla inmutable (el Dockerfile produce esto)
  • Contenedor: instancia corriendo de esa imagen
  • Registro: lugar donde subes/descargas imágenes (Docker Hub, GCR, ECR)

La matemática de la reproducibilidad

La reproducibilidad en ML depende de cuatro fuentes de no-determinismo:

$$\text{Semilla global} = f(\text{Python seed}, \text{NumPy seed}, \text{TensorFlow seed}, \text{cuDNN seed})$$

Si cualquiera de estos no se fija en Docker, los resultados varían entre ejecuciones — y eso en producción es un desastre.

nvidia-docker y CUDA compatibility matrix

NVIDIA mapea versiones de CUDA a capability de GPU. La fórmula de compatibilidad es:

$$\text{Compute Capability} \leq \text{CUDA version soporte}$$

Por ejemplo: una GPU con compute capability 8.6 (Ampere) necesita CUDA $\geq 11.0$. Usar `nvidia/cuda:latest` sin verificar esto causa el error clásico: CUDA error: no kernel image is available for execution.

💻 Implementación Práctica

Dockerfile para Training

# syntax=docker/dockerfile:1.4
FROM nvidia/cuda:11.8.0-cudnn8-runtime-ubuntu22.04

# Fijar seeds ANTES de cualquier operación
ENV PYTHONHASHSEED=42
ENV TORCH_USE_RTLD_GLOBAL=YES
ENV CUDA_LAUNCH_BLOCKING=1

WORKDIR /app

# Copiar solo requirements primero (para cache de Docker)
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt

# Copiar código
COPY . .

# Fix: usar WORKDIR explícito y no hardcodear paths
CMD ["python", "train.py"]

Multi-stage build para reducir imagen de training

# syntax=docker/dockerfile:1.4
# Stage 1: build
FROM python:3.10-slim AS builder
WORKDIR /app
RUN pip install --user uv
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --user -r requirements.txt

# Stage 2: runtime (imagen limpia y pequeña)
FROM nvidia/cuda:11.8.0-cudnn8-runtime-ubuntu22.04
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY --from=builder /app/train.py .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "train.py"]

Dockerfile para Inference con FastAPI

# syntax=docker/dockerfile:1.4
FROM nvidia/cuda:11.8.0-cudnn8-runtime-ubuntu22.04

WORKDIR /app

# Instalar runtime de Python + FastAPI
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3.10 python3-pip && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY ./app /app/app

# Usuario no-root por seguridad
RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

docker-compose.yml para training

version: "3.9"
services:
  train:
    build:
      context: .
      dockerfile: Dockerfile.train
    runtime: nvidia
    environment:
      - NVIDIA_VISIBLE_DEVICES=0
      - PYTHONHASHSEED=42
      - TORCH_NUM_THREADS=4
    volumes:
      - ./data:/app/data
      - ./outputs:/app/outputs
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

Cómo usar nvidia-docker para GPU

# Verificar que nvidia-docker está instalado
nvidia-docker --version

# Test rápido de GPU en contenedor
docker run --rm --gpus all nvidia/cuda:11.8.0-base-ubuntu22.04 \
    nvidia-smi

# Build y corre con GPU
docker build -f Dockerfile.train -t ml-train .
docker run --rm --gpus all -v $(pwd)/data:/app/data ml-train python train.py

🚨 Errores Comunes (y sus fixes)

Error 1: No fijar random seeds en Docker → sin reproducibilidad

Síntoma: El mismo código produce loss diferente en cada `docker run`.

Causa raiz: Python heredan `PYTHONHASHSEED` del sistema, que por defecto es variable. Además, cuDNN tiene benchmark mode que optimiza pero no es determinístico.

# Fix: importa esto AL PRINCIPIO de train.py, antes de cualquier import
import random
import numpy as np
import torch

SEED = 42
random.seed(SEED)
np.random.seed(SEED)
torch.manual_seed(SEED)
torch.cuda.manual_seed_all(SEED)
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False
os.environ["PYTHONHASHSEED"] = str(SEED)

También en Dockerfile:

ENV PYTHONHASHSEED=42
ENV CUDNN_DETERMINISTIC=1
ENV CUDNN_BENCHMARK=0

Error 2: No usar --mount type=cache para pip cache → builds lentos

Síntoma: Cada `docker build` tarda 10+ minutos aunque no cambies requirements.

Causa raiz: Sin cache mount, pip descarga todos los paquetes desde cero en cada build layer nuevo.

# Antes (sin cache)
RUN pip install -r requirements.txt

# Después (con cache mount)
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt

El `--mount=type=cache` persiste el directorio de pip entre builds. Solo se reconstruye el layer si `requirements.txt` cambia.

Error 3: Usar latest CUDA image sin verificar compute capability

Síntoma: CUDA error: no kernel image is available for execution on the device

Causa raiz: `nvidia/cuda:latest` puede ser CUDA 12.x que requiere compute capability $\geq 5.0$ (Kepler+). Si tienes una GPU vieja, no es compatible.

# Primero: verifica tu GPU capability
nvidia-smi --query-gpu=compute_cap --format=csv,noheader
# Ejemplo output: 8.6

# Segundo: match con tabla de compatibilidad
# CC 8.0-9.0 (Ampere/Ada) → CUDA 11.0+
# CC 7.0-7.5 (Turing/Volta) → CUDA 10.0+
# CC 6.0-6.1 (Pascal) → CUDA 9.0+
# CC 3.0-5.2 (Kepler-Maxwell) → CUDA 8.0

# Tercero: elige la imagen correcta
docker pull nvidia/cuda:11.8.0-cudnn8-runtime-ubuntu22.04  # Para CC 6.0+
docker pull nvidia/cuda:12.2.0-cudnn8-runtime-ubuntu22.04   # Para CC 8.0+

✅ Mejores Prácticas

  • Multistage builds: reduce el tamaño final de la imagen separating build vs runtime deps
  • Usuario no-root: siempre crea un usuario para correr la app, nunca root
  • .dockerignore: exclude data, .git, __pycache__, .venv para que el build context sea pequeño
  • Health check: agrega `HEALTHCHECK` en docker-compose para saber cuándo tu contenedor está listo
  • Tags de imagen semánticos: nunca `latest` en producción — usa `11.8.0-cudnn8`
  • Versiona tu entorno: guarda el `requirements.txt` con hashes para reproducción exacta

Resumen y cierre

Hoy cubrimos Docker para ML desde cero: containers, Dockerfiles para training e inference, nvidia-docker para GPU, y los tres errores que más veo en producción. La reproducibilidad no es opcional — es la base de todo.

El 80% de los modelos que fallan en producción no fallan por el código ni por los datos. Fallan porque el entorno de deployment no matchea con el de desarrollo. Docker resuelve esto, pero hay que hacerlo bien: fijando seeds, usando cache mounts, y verificando compatibilidad de CUDA con tu GPU.
